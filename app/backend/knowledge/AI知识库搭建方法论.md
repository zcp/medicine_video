# 项目 AI 知识库搭建方法论

> 一套可复用的方法论，用于在任何新项目上快速建立结构化 AI 知识库体系

---

## 零、核心理念

### 三个基本原则

1. **以实际代码为准** — 文档是代码的映射，不是独立的存在。所有内容必须通过分析实际代码获得，不能依赖过时文档或口头描述
2. **分阶段执行** — 每一步保持上下文精简，一次只做一件事，质量高于速度
3. **文档分层管理** — 不同性质的文档分开维护，更新频率不同，避免互相污染

### 为什么要建知识库

| 问题 | 知识库如何解决 |
|------|---------------|
| 每次新 Session 都要重新解释项目 | CLAUDE.md 自动加载，AI 一分钟恢复上下文 |
| AI 反复建议已被否决的方案 | decisions.md 记录历史决策 |
| AI 踩同样的坑 | known_issues.md 记录所有修复经验 |
| AI 生成的代码不符合项目规范 | code_review_rules.md 提供检查清单 |
| 上下文爆炸导致关键信息丢失 | 分阶段分析，每步上下文可控 |

## 一、目录结构设计

### 1.1 标准目录结构

```
project-root/
├── CLAUDE.md                    ← 根目录（AI 自动读取）
├── knowledge/                   ← 知识库独立目录
│   ├── CLAUDE.md                ← 硬链接，便于集中查阅
│   ├── README.md                ← 导航指南
│   ├── project_summary.md       ← 开发进度看板
│   ├── architecture.md          ← 系统架构设计
│   ├── database.md              ← 数据库设计文档
│   ├── api.md                   ← API 接口说明
│   ├── decisions.md             ← 重要设计决策
│   └── ai/
│       ├── prompt_rules.md      ← Prompt 模板库
│       ├── code_review_rules.md ← 代码审查标准
│       └── known_issues.md      ← 已知问题和注意事项
├── docs/                        ← 原有项目文档（保持不变）
└── ...
```

### 1.2 为什么不是 docs/ 目录

- `docs/` 通常已有大量旧文档，不易区分新旧
- 独立 `knowledge/` 目录职责清晰：专门给 AI 用的知识库
- 便于未来迁移或分享（整个 knowledge/ 目录就是一个独立的知识包）

### 1.3 CLAUDE.md 的硬链接设计

```bash
cd project-root
mklink /H knowledge\CLAUDE.md CLAUDE.md   # Windows
ln CLAUDE.md knowledge/CLAUDE.md           # Linux/Mac
```

**好处**：
- 根目录一份，AI 自动读取
- knowledge/ 目录一份，便于集中查阅
- 硬链接：改一处，两处同步更新，不占额外磁盘空间

### 1.4 不同项目类型的适配

| 项目类型 | 必须的文档 | 可选的文档 |
|----------|-----------|-----------|
| 纯后端服务 | CLAUDE.md, project_summary.md, architecture.md, database.md | api.md（接口少时可省略） |
| 纯前端项目 | CLAUDE.md, project_summary.md, architecture.md | 可新增 components.md（组件库文档） |
| 全栈项目 | 全部文档 | 可新增 deployment.md（部署文档） |
| 微服务项目 | 每个服务一份 CLAUDE.md，共享其他文档 | 可新增 service_map.md（服务关系图） |

## 二、分阶段执行流程

### 总览

```
阶段1：创建目录和模板（5分钟）
阶段2：生成 CLAUDE.md（30分钟）
阶段3：生成 project_summary.md（20分钟）
阶段4：生成 architecture.md（45分钟）
阶段5：生成 database.md（30分钟）  ← 如项目无数据库可跳过
阶段6：建立 decisions.md（15分钟）
阶段7：创建 AI 辅助文档（20分钟）
阶段8：验证和优化（10分钟）

总计：约 2.5-3 小时
```

### 阶段1：创建目录和模板

**目标**：建立完整的目录结构和空白文档模板

**执行步骤**：
1. 在项目根目录创建 `knowledge/` 和 `knowledge/ai/` 目录
2. 创建所有空白文档（使用下方的标准模板）
3. 创建 `README.md` 导航文件
4. 提供各文件的初始结构骨架（带章节标题和简短说明）

**关键原则**：
- 模板只需要框架结构，不需要实际内容（内容是后续阶段的任务）
- 每个模板文件应包含清晰的章节标题和简短说明
- README.md 应该说明每个文档的用途和更新频率

**输出**：9-10 个空白/框架文档

---

### 阶段2：生成 CLAUDE.md

**目标**：生成项目恒定信息的索引卡片

**核心指令**：
```
请分析实际项目结构、依赖文件、配置文件和代码规范，生成 CLAUDE.md。

数据来源（按优先级）：
1. 实际项目目录结构（用 Glob/Read 工具查看）
2. 依赖文件（package.json、requirements.txt、Cargo.toml 等）
3. 配置文件（.env、docker-compose.yml 等）
4. 数据库迁移文件
5. 项目已有文档（仅作参考，需与实际代码比对）

必须包含的内容：
- 项目简介（一段话说明项目是什么）
- 技术栈表格（技术名、版本、用途）
- 目录结构树（每个目录的职责）
- 开发规范（代码分层、命名约定）
- 常用命令（开发、测试、部署）
- 环境配置说明
- 不应修改的模块
- 知识库导航（指向 knowledge/ 下其他文档的链接表）

不要包含的内容：
- 开发进度（属于 project_summary.md）
- 历史决策（属于 decisions.md）
- 详细的表结构（属于 database.md）
```

**生成后的动作**：
- 创建硬链接 `knowledge/CLAUDE.md`
- 确认文件放在根目录

---

### 阶段3：生成 project_summary.md

**目标**：生成项目的进度看板

**核心指令**：
```
请分析实际项目状态，生成 project_summary.md。

数据来源：
1. API 端点文件（了解已实现的功能）
2. CRUD/Service 文件（了解业务逻辑覆盖）
3. 测试文件（了解测试覆盖情况）
4. 部署配置文件（了解部署状态）
5. 最近的 Git 提交（如果有）

必须包含的内容：
- 已完成功能列表（按模块分类，列出关键文件路径）
- 当前开发状态
- 待办事项（按高/中/低优先级）
- 测试覆盖情况（单元测试和集成测试文件数）
- 部署状态（服务清单和端口映射）
- 风险评估表格
- 下一步计划

不要包含的内容：
- 详细的架构分析（属于 architecture.md）
- 完整的表结构（属于 database.md）
```

---

### 阶段4：生成 architecture.md

**目标**：生成系统架构蓝图

**核心指令**：
```
请分析项目目录结构、API 路由注册、服务文件、模型文件，生成 architecture.md。

数据来源：
1. API 路由注册文件（了解模块划分）
2. 核心基础设施（认证、配置、数据库连接、异常处理）
3. Services 和 CRUD 文件（了解分层实现）
4. 部署配置文件（docker-compose.yml）

必须包含的内容：
- 整体架构分层图（API → Service → CRUD → Model → DB）
- 项目模块总览树（每个目录下的文件清单）
- 一个具体请求的完整调用链路（从 HTTP → API → Service → CRUD → Model → DB）
- 核心基础设施分析（认证流程、配置系统、数据库连接、响应格式、异常体系）
- 数据模型关系图
- 部署架构图（Docker 服务拓扑）
- 服务间通信方式
- API 路由结构树
- 安全设计说明
- 技术选型汇总表

分析技巧：
- 追踪一个完整的请求调用链来验证分层设计
- 检查每个层次是否遵守职责边界
- 确认实际代码中每层是否有越界行为
```

---

### 阶段5：生成 database.md

**目标**：生成数据库设计词典

**核心指令**：
```
请分析所有 ORM 模型文件和 SQL 迁移文件，生成 database.md。

数据来源：
1. 所有 ORM 模型文件（了解表结构和关系）
2. SQL 迁移文件（了解变更历史）
3. 数据库配置文件（了解连接参数）

重要：如果项目使用 Docker 部署数据库，尝试执行 docker 命令连接实际数据库验证。
如果不能连接实际数据库，以 ORM 模型为准（模型是表结构的真实来源）。

必须包含的内容：
- 数据库概览（类型、版本、ORM 框架、表数量统计）
- 设计规范（UUID 策略、时间戳模式、软删除策略、幂等设计）
- 数据库模型关系图（ER 图）
- 每张表的完整字段说明（字段名、类型、约束、默认值、注释）
- 索引清单
- 外键关系
- 数据迁移历史
- Redis 缓存设计（如有）或 NoSQL 设计（如有）
- 查询规范和事务管理说明
- 性能优化建议

每张表的文档应包含：
- 字段列表（所有列）
- 索引列表
- 外键关系
- 特殊的业务约束
```

---

### 阶段6：建立 decisions.md

**目标**：建立决策档案

**核心指令**：
```
请基于实际代码分析和修复文档，生成 decisions.md。

数据来源：
1. 实际代码中的设计模式（如 UUID 策略、软删除）
2. 项目修复文档（如路由修复、UUID 崩溃修复）
3. 配置文件中的验证逻辑
4. 项目中已有的技术选型报告

必须包含的内容：
- 每项决策：标题、日期、内容、原因、实现方式、设计考量、影响
- 已确认的技术选型汇总（不应再重新讨论的选型）
- 决策模板（方便后续添加新决策）

常见的决策类别：
- 技术选型决策
- 架构设计决策
- 编码规范决策
- 安全策略决策
- 部署策略决策
```

---

### 阶段7：创建 AI 辅助文档

**目标**：创建 AI 协作的三个辅助文件

**创建顺序**：
1. code_review_rules.md（代码审查标准）
2. known_issues.md（已知问题列表）
3. prompt_rules.md（Prompt 模板库）

#### 7a. code_review_rules.md

**内容来源**：
- 从 decisions.md 中提取编码规范
- 从项目实际代码模式中提取规范
- 从 known_issues.md 中提取常见的错误模式

**必须包含**：
- 项目特有审查清单（如 UUID 生成方式、时间戳模式、路由注册等）
- 已知高频问题模式（附带正确和错误的代码示例）
- 自我审查清单

#### 7b. known_issues.md

**内容来源**：
- 项目中的修复说明文档
- Git 历史中的重要修复
- 团队积累的经验

**必须包含**：
- 历史修复问题表和教训
- 当前已确认的问题
- 常见陷阱
- 不要重复分析的内容
- 技术债务清单

#### 7c. prompt_rules.md

**内容来源**：
- 提炼本项目实际使用有效的 AI 指令
- 为项目定制化的 Prompt 模板

**必须包含**：
- 文档维护 Prompt（更新 project_summary、记录决策）
- 新模块开发 Prompt（创建完整模块的标准指令）
- 代码审查 Prompt（按项目标准审查）
- 新会话恢复 Prompt（一键恢复上下文的指令）
- 测试编写 Prompt
- 问题排查 Prompt

---

### 阶段8：验证和优化

**目标**：确保所有文档正确可用

**检查清单**：

```
文件完整性：
□ 所有文件是否存在（包括硬链接）
□ 所有文件是否非空（至少 50 行）

交叉引用：
□ 文档间的链接是否指向存在的文件
□ 使用 grep 检查文中 [link](./file.md) 格式的引用

内容一致性：
□ 技术栈版本在不同文档中是否一致
□ 模块数量、表数量等统计数据是否一致
□ 文件路径是否与实际一致

实用性：
□ CLAUDE.md 是否 ≤500 行（太长会浪费上下文）
□ README.md 是否提供清晰的使用指南
□ 新会话恢复 Prompt 是否可以使用
```

**最终输出**：完整的知识库交付

## 三、各文档的内容规范

### 3.1 CLAUDE.md 规范

| 维度 | 要求 |
|------|------|
| 位置 | 项目根目录 |
| 长度 | ≤ 500 行 |
| 内容性质 | 半年以上不变的信息 |
| 禁止内容 | 开发进度、历史决策、详细表结构 |
| 必须包含 | 技术栈、目录结构、开发规范、常用命令、知识库导航 |

### 3.2 project_summary.md 规范

| 维度 | 要求 |
|------|------|
| 更新频率 | 每日或每次重要变更 |
| 内容性质 | 经常变化的信息 |
| 必须包含 | 已完成功能、正在开发、待办事项、测试覆盖、风险评估 |
| 关键要求 | 保留历史变更日志 |

### 3.3 architecture.md 规范

| 维度 | 要求 |
|------|------|
| 更新频率 | 架构变更时 |
| 内容性质 | 结构性和关系性信息 |
| 必须包含 | 分层图、模块清单、调用链路、部署架构 |
| 图表格式 | 使用 Mermaid 或 ASCII 图形 |

### 3.4 database.md 规范

| 维度 | 要求 |
|------|------|
| 更新频率 | 数据库变更时 |
| 内容性质 | 数据结构和关系 |
| 每张表 | 必须列出所有字段、索引、外键 |
| 额外要求 | ER 图、迁移历史 |

### 3.5 decisions.md 规范

| 维度 | 要求 |
|------|------|
| 排序方式 | 按时间倒序 |
| 每项决策 | 标题 + 日期 + 内容 + 原因 + 实现方式 + 影响 |
| 特别重要 | 否决的方案也要记录 |

### 3.6 AI 辅助文档规范

| 文档 | 更新时机 | 核心原则 |
|------|----------|----------|
| prompt_rules.md | 发现新高效 Prompt | 基于项目定制，别放通用模板 |
| code_review_rules.md | 规范变更 | 有正确/错误代码示例对比 |
| known_issues.md | **每次修复 Bug 后** | 最重要！是团队的避坑指南 |

## 四、维护机制

### 日常维护命令

```bash
# 每次开发结束
请更新 knowledge/project_summary.md，记录本次变更

# 每次 Bug 修复后
请更新 knowledge/ai/known_issues.md，记录问题和修复方案

# 每次重要决策后
请更新 knowledge/decisions.md，添加决策记录

# 数据库变更后
请更新 knowledge/database.md，同步表结构变化
```

### 定期审查

| 审查频率 | 内容 |
|----------|------|
| 每周 | 更新 project_summary.md 的开发状态 |
| 每月 | 评估 known_issues.md 中的技术债务是否有进展 |
| 每季度 | 审查 CLAUDE.md 是否需要更新（技术栈升级？） |
| 每次架构变更 | 更新 architecture.md |

### 质量红线

1. CLAUDE.md **绝对不能超过 500 行**
2. 所有文档中的**代码示例必须是实际代码**，不能是虚构的
3. 交叉引用**必须可访问**（链接指向的文件存在）
4. 统计数据**必须在各文档中保持一致**

## 六、常见问题

### Q：项目已经有 CLAUDE.md 了，还要建知识库吗？

A：要。单一的 CLAUDE.md 只能承载恒定信息。项目还需要进度看板（project_summary.md）、决策档案（decisions.md）、避坑指南（known_issues.md）等。可以把现有的 CLAUDE.md 作为基础，扩展成完整的知识库。

### Q：小型项目也需要完整的知识库吗？

A：可以简化。小项目至少需要 3 个文件：
- CLAUDE.md（基础信息）
- project_summary.md（进度）
- known_issues.md（踩过的坑）

### Q：文档多久更新一次？

A：project_summary.md 最频繁（每次开发后），known_issues.md 每次修 Bug 后，其余按需。关键是 "做了就记，别拖"。

### Q：多人团队如何使用？

A：知识库文件放在 Git 仓库中，团队成员通过 AI 协助更新。重要：`project_summary.md` 的更新可以作为 PR 的一部分提交。
