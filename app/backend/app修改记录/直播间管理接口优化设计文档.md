## 一、需求概述

### 1.1 背景

当前管理员进入「我的直播」页面后，前端直接展示全部直播间列表，仅支持按标题关键词搜索和按所有者筛选，缺少运营管理场景的核心能力：

1. **无状态筛选**：管理员无法按"正在直播 / 预告 / 回放可用 / 已结束"筛选直播间
2. **无时间筛选**：无法按创建时间或开播时间范围筛选
3. **无批量操作**：不支持批量删除、批量设置分类等运营高频操作
4. **列表信息不完整**：房间卡片缺少实时状态、专家名、分类名、标签、场次数等关键运营信息，导致前端需要逐房间额外请求（N+1 查询问题）
5. **排序维度单一**：仅支持 `created_at` 排序，无法按开播时间排序（预告场景的核心需求）

### 1.2 本次优化目标

| # | 目标 | 类型 |
|---|------|:--:|
| 1 | `GET /rooms` 新增状态、时间筛选参数 | 现有端点扩展 |
| 2 | `GET /rooms` 支持 `start_time` 排序 | 现有端点扩展 |
| 3 | `GET /admin/rooms/summary` 管理摘要列表（含聚合字段） | **新端点** |
| 4 | `DELETE /admin/rooms/batch` 批量删除 | **新端点** |
| 5 | `POST /admin/rooms/batch/categories` 批量设置分类 | **新端点** |
| 6 | 补齐 `live_sessions` 和 `live_rooms` 查询索引 | DB 迁移 |

### 1.3 非目标

以下功能不在本次范围内，留待独立设计文档：
- 场次管理子页面（Session 的编辑/删除/导入——现有端点已完备，属于前端组合调用）
- 批量添加 Tab（`POST /admin/rooms/batch/tabs`，P1 追加）
- 按专家/标签筛选（`?expert_id=` / `?tag_id=`，P1 追加）
- 管理员创建房间为其他用户（当前 `POST /rooms` 创建者即为房间 Owner）

## 二、现状分析

### 2.1 当前 `GET /api/v1/rooms` 支持的参数

```
GET /api/v1/rooms?page=1&size=10&q=关键词&sort=created_at:desc&owner_only=false
```

| 参数 | 类型 | 作用 | 限制 |
|------|------|------|------|
| `page` | int | 分页 | 已有 |
| `size` | int | 每页条数 | 已有 |
| `q` | str | 搜索（UUID精确 / 标题模糊） | 已有 |
| `sort` | str | 排序（仅 `LiveRoom` 表自有字段） | **无法按 session 字段排序** |
| `owner_only` | bool | 仅看自己的房间 | 已有 |

### 2.2 核心缺失

| 缺失能力 | 根因 |
|---------|------|
| 按直播状态筛选 | `LiveRoom` 无 `status` 字段，状态存在于 `LiveSession.status` |
| 按开播时间排序 | `sort` 参数仅校验 `hasattr(LiveRoom, field)`，`start_time` 在 `LiveSession` 表 |
| 聚合展示字段 | 公开 `GET /rooms` 不宜做 4 表 JOIN（影响 C 端首页性能） |
| 批量操作 | 无对应端点 |

### 2.3 关键数据表关系

```
live_rooms ──< live_sessions ──< live_session_experts >── experts
    │              │
    │              └──< session_tags >── tags
    │
    └──< live_room_categories >── categories
```

- **房间状态**: 每个房间取 `live_sessions` 中最新一条（按 `start_time DESC`）的 `status`
- **聚合字段**: 需要跨 4 张关联表批量查询

### 2.4 状态枚举定义

`LiveSessionStatus`（`app/models/live_core.py` L21-28）：

```python
class LiveSessionStatus(str, enum.Enum):
    SCHEDULED = "scheduled"   # 预告
    LIVE = "live"             # 直播中
    FINISHED = "finished"     # 已结束（回放未生成）
    PROCESSING = "processing" # 回放生成中
    READY = "ready"           # 回放可用
    ERROR = "error"           # 回放失败
```

本次设计**透传原始枚举值**，不做后端打包。前端自行按业务需求映射 Tab。

## 三、方案设计

### 3.1 架构原则

```
C 端（首页/搜索）                    管理端（Admin）
─────────────────                  ────────────────
GET /api/v1/rooms                  GET /api/v1/admin/rooms/summary
  + status / created_after/before    + category_ids / expert_id / tag_id
  + sort=start_time                    + session_start_after/before
  (简单字段, 不 JOIN 聚合)             (含 expert_names/category_names/
                                        tag_names/session_count)
                                          │
                               DELETE /api/v1/admin/rooms/batch
                               POST  /api/v1/admin/rooms/batch/categories
```

**决策理由**：
- `GET /rooms` 是公开接口，C 端首页高频调用。加入 4 表 JOIN 的聚合字段会让所有用户买单性能代价
- `GET /admin/rooms/summary` 仅 Admin 调用，可以放心做复杂聚合，且支持管理特有的筛选维度（分类/专家/标签）

### 3.2 筛选栏与 Tab 的前后端分工

```
前端                                    后端
────                                    ────
用户点击 [直播中] [预告] 标签              → GET /rooms?status=live&status=scheduled
用户点击 [今天] [近7天] [近30天]           → 前端计算 created_after = 7天前的 T00:00:00Z
用户点击 [回放可用]                       → GET /rooms?status=ready
用户改变排序 [开播时间▼]                  → GET /rooms?sort=start_time:asc
用户搜索 "心脏病"                        → GET /rooms?q=心脏病

前端不关心 status 枚举值拆分成几个 Tab    后端不关心 Tab 名称和分组逻辑
→ 后端透传原始枚举值                     → 前端自由组合 Tab
```

## 四、数据库索引优化（P0 前置）

### 4.1 问题

当前 `live_sessions` 表**缺少 `room_id` 列的普通索引**。唯一存在的索引是 `uq_live_sessions_room_playback_hash` — 一个部分唯一索引，仅对 `playback_url_hash IS NOT NULL` 的行生效。所有基于 `room_id` 的 JOIN / EXISTS / WHERE 查询都将触发全表扫描。

`live_rooms` 表缺少 `created_at` 索引，日期范围筛选同样是全表扫描。

### 4.2 需要新增的索引

```sql
-- 1. live_sessions 外键基准索引（所有 session JOIN 的基石）
CREATE INDEX idx_live_sessions_room_id ON live_sessions(room_id);

-- 2. 状态筛选复合索引（status 多选过滤核心）
CREATE INDEX idx_live_sessions_room_status ON live_sessions(room_id, status);

-- 3. 最新场次查询索引（start_time 排序 + latest_session 查询）
CREATE INDEX idx_live_sessions_room_start_time ON live_sessions(room_id, start_time DESC);

-- 4. 房间创建时间索引（日期范围筛选）
CREATE INDEX idx_live_rooms_created_at ON live_rooms(created_at DESC);
```

### 4.3 Model 层同步

索引需要在 `app/models/live_core.py` 中定义（后续通过 Alembic 自动生成迁移脚本）：

```python
# LiveSession.__table_args__ 新增
Index("idx_live_sessions_room_id", LiveSession.room_id),
Index("idx_live_sessions_room_status", LiveSession.room_id, LiveSession.status),
Index("idx_live_sessions_room_start_time", LiveSession.room_id, LiveSession.start_time.desc()),

# LiveRoom.__table_args__ 新增
Index("idx_live_rooms_created_at", LiveRoom.created_at.desc()),
```

> 注意：降序索引需使用 Column 对象的 `.desc()` 方法。SQLAlchemy `Index()` 构造函数接受 Column 对象（而非 `text()` 字符串），`.desc()` 返回的 `UnaryExpression` 会被正确翻译为 `DESC` DDL。

### 4.4 影响范围

新增索引不改变任何查询语义，仅提升性能。对现有功能零影响。

#### CRUD 层实现要点

**文件**: `app/crud/room.py`

##### 5.1.1 status 筛选 — EXISTS 子查询

对 `get_multi_and_total()`、`get_multi_and_total_by_owner()`、`list_with_search()` 三个函数均需新增。

```python
from sqlalchemy import exists

if status_list:
    # 输入校验：拒绝无效的 status 值
    valid_statuses = {e.value for e in LiveSessionStatus}
    invalid = [s for s in status_list if s.lower() not in valid_statuses]
    if invalid:
        raise InvalidParameterException(f"无效的状态值: {invalid}", code=4001)

    status_enum_values = [LiveSessionStatus[s.upper()] for s in status_list]
    query = query.where(
        exists().where(
            and_(
                LiveSession.room_id == LiveRoom.id,
                LiveSession.status.in_(status_enum_values)
            )
        )
    )
```

> **校验优先于枚举转换**：先用 `{e.value for e in LiveSessionStatus}` 构造合法值集合，拒绝非法输入（返回 400/4001），避免 `LiveSessionStatus["INVALID"]` 抛 `KeyError` → 500。

**为什么用 EXISTS 而非 LEFT JOIN**：
- EXISTS 在找到第一个匹配行即停止，不产生重复行
- 不需要返回 Session 数据时无需 JOIN
- PostgreSQL 查询计划器对 EXISTS 优化更好

##### 5.1.2 created_at 筛选

```python
if created_after:
    query = query.where(LiveRoom.created_at >= created_after)
if created_before:
    query = query.where(LiveRoom.created_at <= created_before)
```

`LiveRoom.created_at` 是表自有字段，直接 WHERE 即可，无需 JOIN。

##### 5.1.3 start_time 排序

```python
if sort_field == 'start_time':
    # 相关子查询: 每个房间取最新 session 的 start_time
    latest_session = (
        select(LiveSession.start_time)
        .where(LiveSession.room_id == LiveRoom.id)
        .order_by(LiveSession.start_time.desc())
        .limit(1)
        .correlate(LiveRoom)
        .scalar_subquery()
    )
    if direction == 'DESC':
        query = query.order_by(latest_session.desc().nulls_last())
    else:
        query = query.order_by(latest_session.asc().nulls_last())
```

**`nulls_last()`** 确保没有 Session 的房间排在列表末尾，不干扰有内容的房间排序。

#### CRUD 层实现要点

**文件**: `app/crud/room.py`（新增 4 个辅助函数）

采用 **"主查询 + 3 次批量聚合查询"** 模式，避免 N+1：

```python
# Step 1: 主查询 — 房间 + 最新 Session（带筛选、排序、分页）
async def get_rooms_with_latest_session(
    db: AsyncSession,
    filters: RoomSummaryFilter,
    user_id: Optional[uuid.UUID],
    role: Optional[str],
) -> Tuple[List[dict], int]:
    """
    返回 (rooms_summary_list, total)
    每个 room dict 包含 LiveRoom 字段 + live_status / current_session_id / session_start_time
    """
    # 构建子查询：每个房间的最新 session
    latest_session_subq = (
        select(
            LiveSession.room_id,
            LiveSession.status.label('live_status'),
            LiveSession.id.label('session_id'),
            LiveSession.start_time.label('session_start_time'),
            func.row_number()
                .over(
                    partition_by=LiveSession.room_id,
                    order_by=LiveSession.start_time.desc()
                ).label('rn')
        )
        .subquery()
    )

    # 主查询 JOIN 最新 session（rn=1 即每个房间取一条）
    query = (
        select(
            LiveRoom.id,
            LiveRoom.title,
            LiveRoom.cover_url,
            LiveRoom.is_private,
            LiveRoom.user_id,
            LiveRoom.created_at,
            LiveRoom.updated_at,
            latest_session_subq.c.live_status,
            latest_session_subq.c.session_id.label('current_session_id'),
            latest_session_subq.c.session_start_time,
        )
        .outerjoin(
            latest_session_subq,
            and_(
                latest_session_subq.c.room_id == LiveRoom.id,
                latest_session_subq.c.rn == 1
            )
        )
    )
    # ... 应用 role 可见性过滤 + status 筛选 + 日期筛选 + 排序 + 分页


# Step 2: 批量查聚合 — 3 次查询覆盖所有房间
async def batch_get_category_names(db, room_ids: list) -> dict:
    """返回 {room_id: [name, ...]}"""
    ...

async def batch_get_expert_names(db, room_ids: list) -> dict:
    """返回 {room_id: [name, ...]}，取全部 session 的专家去重"""
    ...

async def batch_get_tag_names(db, room_ids: list) -> dict:
    """返回 {room_id: [name, ...]}，取全部 session 的标签去重"""
    ...

async def batch_get_session_counts(db, room_ids: list) -> dict:
    """返回 {room_id: count}"""
    ...
```

**查询次数**：1（主查询）+ 3（批量聚合）= **4 次**，处理任意数量的房间。对比前端 N+1 模式（20 个房间 = 20×4 = 80 次），减少了 95%。

5. **需恢复现有保护**：当前 `room_service.py` L362-366 的直播保护被注释掉了，实现时需恢复

is_live = await crud_room.is_live(db=self.db, room_id=room_id)

### 5.5 `GET /api/v1/admin/rooms/summary` P1 筛选参数

以下参数在 `summary` 端点主查询中通过 EXISTS 子查询实现。筛选与展示采用一致的语义——均基于该房间**所有 session 的全量数据**（不限于最新一条），避免"筛选命中但卡片不显示"的困惑。

```python
# category_ids 筛选（支持多选，取并集）
if category_ids:
    query = query.where(
        exists().where(
            and_(
                LiveRoomCategory.room_id == LiveRoom.id,
                LiveRoomCategory.category_id.in_(category_ids)
            )
        )
    )

# expert_id 筛选（匹配该专家在任一 session 中出现过的房间）
if expert_id:
    query = query.where(
        exists().where(
            and_(
                LiveSession.room_id == LiveRoom.id,
                LiveSessionExpert.session_id == LiveSession.id,
                LiveSessionExpert.expert_id == expert_id
            )
        )
    )

# tag_id 筛选（匹配该标签在任一 session 中被标记过的房间）
if tag_id:
    query = query.where(
        exists().where(
            and_(
                LiveSession.room_id == LiveRoom.id,
                SessionTag.session_id == LiveSession.id,
                SessionTag.tag_id == tag_id
            )
        )
    )

# session_start 时间范围（基于最新 session 的子查询列）
if session_start_after:
    query = query.where(latest_session_subq.c.session_start_time >= session_start_after)
if session_start_before:
    query = query.where(latest_session_subq.c.session_start_time <= session_start_before)
```

> **筛选与展示一致性**：`expert_id` / `tag_id` 的 EXISTS 筛选基于**全部 session**，响应中的 `expert_names` / `tag_names` 同样取**全部 session 去重后的专家/标签列表**（见 §5.2 `batch_get_expert_names`），而非仅最新 session。避免"按张三筛选命中了但卡片显示李四"的困惑。
