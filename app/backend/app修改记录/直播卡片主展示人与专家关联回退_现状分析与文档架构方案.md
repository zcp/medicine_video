## 四、正式业务口径（需求，两版方案共识，保持不变）

### 4.1 直播卡片与详情页顶部主展示人规则

直播卡片和直播详情页顶部都只需要一个统一的主展示人，不要求前端识别其身份。

| 展示位置 | 有关联专家 | 无关联专家 | 主要展示字段 |
|---|---|---|---|
| 直播卡片 | 显示第一个关联专家 | 显示直播间创建者 | 标题、头像、姓名、医院 |
| 直播详情页顶部 | 显示第一个关联专家 | 显示直播间创建者 | 头像、姓名、医院 |
| 直播详情页专家 Tab | 显示全部关联专家，包含第一个专家 | 为空或显示空态，不显示创建者 | 专家列表字段 |

主展示人字段规则：

| 条件 | 姓名来源 | 头像来源 | 医院/职称 |
|---|---|---|---|
| 有关联专家 | 第一个关联专家 | 专家头像 | 返回专家实际资料，卡片重点展示医院 |
| 无关联专家 | 创建者 `nickname`，其次 `username`，最后兜底"用户" | 创建者 `avatar_url` | 医院、职称为空 |

前端只根据字段是否有值进行渲染：

- 始终尝试显示标题、姓名和头像。
- `hospital` 有值时显示医院；`title` 等后续页面如需展示，也按有值才显示。
- 字段为空时不显示对应行。
- 不新增前端必须依赖的 `host_type`、`is_expert` 或 `display_type`。
- 专家 Tab 是"关联专家列表"，不是"主展示人列表"；无专家时不应把普通创建者放入专家 Tab。

### 4.2 "第一个专家"的规则

统一采用：

```text
sort_order ASC,
created_at ASC,
id ASC
```

含义：

1. 先使用业务顺序字段（数字越小越靠前，与前端创建流程传入的 `sort_order: i` 一致）。
2. 顺序相同按关联创建时间。
3. 时间仍无法区分时按 UUID 保证结果稳定。

`role` 字段继续保留，用于未来多专家角色业务，不作为本需求的主展示人选择条件。

## 五、当前实现审计（前后端代码级核实，2026-08-02）

### 5.1 创建直播的真实流程

当前前端不是一次性创建"房间+场次"，而是：

```text
创建房间
  -> 房间创建成功
  -> 自动在房间下创建一个场次
  -> 如需关联专家，再将专家关联到 session_id
```

关键事实（前端代码核实）：

- 创建/编辑页面在调用 `setSessionExperts` 时**已传入 `role` 和 `sort_order`**（`src/pages/app/live-manage/create.vue:1187-1191`、`src/components/app/CreateLiveDrawer.vue:1183-1187`），规则为 `role: i === 0 ? '主讲' : '嘉宾', sort_order: i`。
- 即：**第一个专家天然是"主讲"且 sort_order 最小**，前端读取时统一 `find(e => e.role === '主讲') || list[0]`。
- 现状一个直播间对应一个场次，前端无多场次场景。

因此"创建请求没有专家角色字段"的准确表述应为：

> 创建房间 / 创建场次请求本身没有专家字段；但创建流程后续调用的"设置场次专家"接口已接收并保存 `role` 与 `sort_order`。本次无需新增任何创建侧字段，只需确保读取排序与 `sort_order` 语义一致。

### 5.4 缺口清单（本次范围内）

#### 缺口 B：首页/专家列表排序与 sort_order 语义冲突（P0）

后端 `get_session_experts()` 用 `sort_order.desc()`，首页 LATERAL 用角色优先级，均与"第一个专家 = sort_order 最小"冲突。需统一改为 `sort_order ASC, created_at ASC, id ASC`。

#### 缺口 C：首页无创建者 fallback 且缺头像（P1）

`_select_host()` 无专家返回 None；`HomepageHostInfo` 无 avatar_url；首页 SQL 无专家头像字段（`e.avatar_url`）。需补齐：

- 有专家：`avatar_url` = 专家头像（SQL 补 `e.avatar_url AS expert_avatar`）
- 无专家：fallback 创建者（nickname > username > "用户"），`avatar_url` = 创建者头像

#### 缺口 I：详情页无专家兜底数据缺失（P1）

`GET /rooms/{id}` 不返回创建者昵称/头像，前端 LiveView 无可用数据源（前端 `Room.user_name` 仅为类型定义）。需后端 room detail 补创建者基础字段（决策 4）。

#### 缺口 E：收藏/订阅/观看历史仅行为记录，无卡片字段（P2，最大痛点）

后端三个列表仅返回行为字段，前端被迫逐条 N+1 请求并随机造假。需聚合返回最小卡片字段。

## 六、总体技术架构（收敛版）

### 6.1 前后端职责划分

#### 前端负责

1. 创建/编辑页面维护用户选择的专家顺序（已实现，传 `sort_order`）。
2. 卡片渲染后端统一返回的主展示人字段，无身份判断。
3. 专家 Tab 渲染全部关联专家（已实现，同源）。
4. 详情页无专家时渲染 room detail 返回的创建者字段（后端补，P1），移除假专家 `mockExpertData`。
5. P1 上线验证后移除首页 `enrichMissingHostAvatars` 补全 hack。
6. P2 落地后删除收藏/订阅/历史 store 的 N+1 补全链与随机 mock。

#### 后端负责

1. 修正专家关联查询排序（P0）。
2. 首页无专家时创建者 fallback + 头像（有专家时含专家头像）（P1）。
3. room detail 补充创建者基础字段（user_name + 头像，复用 `fetch_user_profiles`）（P1，与首页 fallback 同一能力）。
4. 收藏/订阅/观看历史三列表返回最小卡片字段（P2）。
5. 三列表统一过滤私密房间 `is_private = false`，且**过滤进入 count 与 list 查询层**，保证 total 一致（P2）。
6. 复用 `fetch_user_profiles` 批量获取创建者资料，失败降级"用户"/null。
7. 处理场次不存在、专家已删除、users 服务失败等异常。

### 6.2 聚合服务设计（最小字段集，P2 引入）

新增独立模块（保留初版建议的形态，字段按最小集裁剪）：

```text
backend/live_core_service/app/services/room_card_service.py
```

提供两个维度方法（本次仅服务三列表，方法签名保留初版形态便于未来扩展）：

```text
get_room_card_map(room_ids)      # 收藏、订阅 target_type=room
get_session_card_map(session_ids)  # 观看历史、订阅 target_type=session
```

最小返回字段（**按接口分别定义**，与各前端类型字段对齐；冗余双字段仅作过渡兼容，后续统一清理）：

```text
收藏 FavoriteItem：
room_id / session_id / room_title / room_cover_url / room_live_status
expert_name / expert_avatar / expert_hospital / duration(秒) / view_count / comment_count

订阅 SubscriptionItem：
target 原字段 + title / cover_url / live_status / scheduled_start_time
expert_name / expert_avatar / expert_hospital / duration(秒) / view_count / comment_count

观看历史 WatchHistoryItem：
session 原字段 + title / cover_url / session_status
expert_name / expert_avatar / expert_hospital / duration(秒) / view_count / comment_count
```

规则：

- `expert_*` = 第一个关联专家（`sort_order ASC, created_at ASC, id ASC`）；无专家时 `expert_name/expert_avatar` = 创建者，`expert_hospital` = null。
- 代表场次：取该房间最新创建的场次（现状一房一场，见第十一章决策 1）。**聚合查询禁止复制首页的普通 JOIN**（一房多场次会重复行，见 5.2 风险 8），用 lateral / 窗口函数每个房间只取一个场次。
- `duration`：`end_time - start_time` 秒数（复用首页 SQL 算法）。
- `view_count` = `session_statistics.total_viewer_count`，缺失为 null；`comment_count` 无真实来源，返回 null，**不造假**（前端需确认 null 展示：不显示或"--"，待决策 3）。
- 不返回 `root_category_name` / `sub_department_name` / `host_type` / `is_expert`。
- **私密房间过滤必须进入 count 与 list 查询层**（收藏/订阅 join `live_rooms`，历史 join `live_sessions → live_rooms`，统一 `is_private = false`），保证 `total` 为过滤后总数、`total == items 数量`，禁止在 Service 层取 list 后再过滤。

## 七、为什么不能完全由前端判断

创建/编辑页面可以在本地使用 `selectedExperts[0]`，但列表页面完全由前端自行请求，会产生：

1. 每个房间额外请求专家关联列表（N+1）。
2. 无专家房间再额外请求 users 服务资料。
3. 首页、搜索、收藏、历史、管理页重复实现同一规则。
4. 列表页首屏延迟。
5. 不同页面对"第一个专家"的排序可能不一致。
6. users 服务权限和网关调用暴露给前端。
7. 数据真实性无法保证（当前收藏/订阅/历史已用随机数造假）。

因此：

> 前端负责选择顺序，后端负责持久化顺序和聚合展示。

这不是把展示逻辑全部转移到后端，而是将跨资源、跨服务、跨页面的事实数据聚合放在后端；前端仍然只负责无身份判断的展示。

## 八、风险与建议的控制方案

| 风险 | 等级 | 具体表现 | 控制方案 |
|---|---|---|---|
| 专家顺序不稳定 | 低 | 不同页面显示不同专家 | P0 统一 `sort_order ASC, created_at ASC, id ASC` |
| P0 全局顺序变化 | 低 | `get_session_experts` 一处修改、前端 8 处消费方顺序统一变化 | 方向正确，验收时回归管理 detail/list |
| 老数据主展示人变化 | 低 | 若存在"主讲非 sort_order 最小"的历史数据，主展示人会变 | 展示性变更，产品已确认可接受（决策 14） |
| 首页 SQL 回归 | 中 | LATERAL 子查询是原生 text() SQL，首页为高频接口 | 配 SQL/接口测试，上线前对比验证 |
| users 服务不可用 | 低 | 无法得到创建者头像姓名 | 批量失败不阻断列表；姓名"用户"、头像 null |
| 前端补全逻辑移除时机 | 中 | P1 未验证就删 `enrichMissingHostAvatars` 会短暂空白 | 严格按"P1 上线验证后再删"排期 |
| 前后端发布窗口 | 中 | P2 后端加字段与前端删补全必须同版本 | P2 前后端绑定一个发版 |
| 私密房间泄露 | 低 | 行为列表出现私密房间 | P2 三列表统一过滤 `is_private=false`，**过滤进入 count 与 list 查询层**，保证 total 为过滤后总数、total==items 数量 |
| 详情页兜底数据缺失 | 中 | room detail 无创建者资料，前端无法兜底 | 决策 4：room detail 补 user_name/头像（并入 P1，与首页 fallback 共用 `fetch_user_profiles`） |
| P1 实现成 N+1 | 中 | `_select_host()` 为同步方法，若内部逐条请求 users 服务则结构错误 | 实施约束：`get_homepage_rooms` 批量取资料后传入（见 P1 清单） |
| 首页多场次重复行 | 低（中期） | 首页 SQL `LEFT JOIN live_sessions` 一房多场次会重复 | 现状一房一场未暴露；P2 聚合服务用 lateral/窗口函数，禁止复制普通 JOIN |
| 字段语义不准确 | 低 | `expert_name` 实际可能是创建者 | 接口文档明确"卡片主展示人"；短期 `expert_*` 兼容，不新增 host 字段 |
| 专家已删除或关联脏数据 | 低 | 外键对象为空 | outer join；缺专家即按创建者 fallback |
| 性能回归 | 低 | 三列表聚合增加查询复杂度 | 按当前页 items 批量查，禁止逐条 |
| 详情页顶部与专家 Tab 不一致 | 低 | 顶部显示 A，Tab 第一位是 B | 前端已同源（同一数组），P0 修排序后天然一致 |
| 无专家时误把创建者放入专家 Tab | 低 | 普通用户被展示为专家 | 创建者只作为卡片/顶部 fallback，不进入专家 Tab |

## 十、预期效果

实施完成后，前端不再需要判断"这是专家还是普通用户"，收藏/订阅/历史不再逐条请求和造假。

### 有专家

```text
expert_name = 第一个关联专家姓名
expert_avatar = 第一个关联专家头像
expert_hospital = 第一个关联专家医院
expert_title = 第一个关联专家职称（可选展示）

专家 Tab = [第一个, 第二个, ...] 全部关联专家
```

即：卡片主展示人、详情页顶部主展示人、专家 Tab 第一项三者一致。

### 无专家

```text
expert_name = 创建者昵称或用户名
expert_avatar = 创建者头像
expert_hospital = null
expert_title = null

专家 Tab = []（显示空态）
```

即：创建者只作为卡片和详情顶部 fallback，不进入专家 Tab。

### 能够达到的结果

1. 首页/直播卡片、详情页顶部、专家 Tab 的专家顺序一致。
2. 首页、收藏、订阅、观看历史展示规则一致（搜索/管理列表不在本次范围）。
3. 前端统一消费卡片字段，收藏/订阅/历史消除 N+1 与随机假数据。
4. 创建流程保持"先创建房间，再自动创建场次"的现状，无任何创建侧改动。
5. 专家关联仍以场次为事实来源，数据模型不变。
6. 无专家、无场次或 users 服务异常时，卡片和详情顶部仍能展示合理的创建者兜底信息。
7. 专家 Tab 始终只表达"关联专家列表"，不会混入普通创建者。
8. 后续若重新启用"主讲/主持/嘉宾"，只需在专家选择策略中增加业务版本，不影响 fallback 架构。

## 十三、结论

本需求采用"增量设计、最小侵入、分层实现、统一响应、批量查询、分阶段实施"规范。最终边界：

```text
P0：修正专家关联排序（get_session_experts ASC + 首页 LATERAL 去角色优先级）
P1：首页无专家 fallback 到创建者 + 头像（含专家头像）+ room detail 补创建者字段（详情页兜底）
```
