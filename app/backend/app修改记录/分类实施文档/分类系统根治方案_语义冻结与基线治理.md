## 一、背景与问题阐述

### 1.1 问题现象

分类系统经过 6 轮大规模改造（原始 15 分类 → A2/C 方案 → 融合方案 → Sprint 3/4 → 国家医学标准重构 → P0 前置修复 → 数据治理），**问题仍然反复出现**：

```
2026-06-20   A2/C 方案设计（发现 261 分类中 241 为测试残留）
2026-07-22   实施审查（发现 13 个问题：seed 缺失、三套列表漂移、优先级 bug）
2026-07-23   Sprint 3/4（数据治理 + 科室扩展）
2026-07-28   国标重构（发现 parent_id 从未落地、25 平铺不合规）
2026-07-29   P0 修复（发现语义分裂、父聚合缺失）
2026-08-06   直播间关联修复（发现前端 403 静默吞错）
2026-08-09   数据治理（发现 15 个新问题：删除悬空、树断链、合并缺失）
2026-08-11   实测（测试残留 524 条 active 出网、科室覆盖率 19%、V8 仍未执行）
2026-08-11   复测（数据持续膨胀：766→1209 分类、786→1003 专家）
2026-08-12   环境重置（开发库重建为干净基线：35 分类 / 384 专家 / 41 科室 / 11 直播间）
```

**核心矛盾**：每轮"修复"都声称是最终方案，但下一轮总能发现新问题。这证明**问题不在具体 bug 层面，而在机制层面**——本次环境重置（测试残留被清空）恰好印证：**数据问题可以被重置清空，但机制缺失会让问题在新环境重新长出**。

### 1.2 本方案目标

| 维度 | 目标 |
|:---|:---|
| **根治** | 消灭"修不完"循环：语义冻结（锁死）+ 数据对齐（一次清空）+ 机制建设（防复发） |
| **可验证** | 全环境落到同一基线快照：分类 35 / 科室 ~129 / 体检 0 异常 |
| **可维护** | 进入"基线维护"模式，后续只做增量治理，不再大规模改造 |
| **可部署** | 明确线上部署初始化路径（代码迁移、数据不迁移场景下分类功能不中断） |
| **不过度开发** | 实施边界明确（见附录 D）：不加冗余字段/表，只满足实施要求与使用场景 |

## 四、问题根源与定性

### 4.1 系统性原因（占比 ~80%）

```
S1 语义基线从未冻结
   ├─ categories 一表四职（全局分类/医学科室/专家主分类/直播间分类）边界从未锁死
   ├─ 专家分类粒度（一级 vs 二级）两天翻来回，从未写入强制校验
   └─ 匹配算法返回值语义变更 3 次，无一次伴随全量数据对齐

S2 四方真相源无统一治理
   ├─ DB / ORM / 常量 / 文档各自演进
   ├─ parent_id 设计写了 35 天未实施（V5 建列、ORM 无字段）
   └─ 每次审查都发现"文档声称状态 ≠ 代码实际状态"（连常量注释"36 条"都是错的）

S3 工程执行链断裂
   ├─ 迁移/seed 手动执行：V8 漏执行、S4 种子 40/128、无部署入口
   ├─ 无执行后校验：跑没跑、跑对没跑对无人感知
   └─ 无测试门禁：修复 A 引入 B 无人发现

S4 测试数据与生产数据混同
   ├─ 无隔离机制（879 条测试分类出网是铁证）
   └─ 大量专家挂在测试分类下，公开接口被污染
```

### 4.2 偶发原因（占比 ~20%，但全部暴露系统性缺陷）

| # | 偶发问题 | 暴露的系统性缺陷 |
|:--|:---|:---|
| O1 | V8 未执行、S4 种子 40/128 | S3（无自动化执行、无执行后校验、无部署入口） |
| O2 | standard 标记失真 | S2（数据录入无校验 Gate） |
| O3 | is_verified 恢复丢失 | S3（数据恢复无验证流程） |
| O4 | 存量语义分裂 | S1（决策变更无数据对齐步骤） |

### 4.3 关键判断

> 表面看是"一个个具体问题"，实际是 **4 个系统性缺陷在不同时间点的不同投影**。**环境重置清空了数据，但机制缺失让问题在新环境重新长出（V8 未执行、S4 40/128 原样保留）——这正是"不修系统、只修数据"的下场。** 之前修的是"果"，本方案修的是"因"。

## 五、根治方案设计（三层 + 三线执行）

### 5.1 设计原则

| 原则 | 内容 | 对应问题 |
|:---|:---|:---|
| P1 语义锁定 | 领域语义一次性冻结并写入代码级校验，变更必须走流程 | S1 |
| P2 单一真相源 | 常量/DB/ORM/文档四方以"基线快照 + 同步检查"收敛 | S2 |
| P3 执行可重复 | 迁移/seed 自动化 + 执行记录 + 部署入口 + 执行后自动校验 | S3 |

- ⚠️ **不能根治（也不需要根治）**：分类体系本身会随业务演进（新增科室、调整归类）——这是正常运营，机制保证它"可验证、可审计"，而非"永不变化"。
- ⚠️ **防线依赖**：若未来再次出现"跨团队并行开发 + 手动执行 + 无测试 + 无部署入口"组合，问题仍会再现——3.1 部署自动化 + 3.7 隔离是最后防线。
