# 专家与直播间分类规则冻结方案

## 背景

本次规则冻结用于统一专家分类、直播间分类和全局分类表的业务口径，避免后续继续出现 `department`、`category_id`、`live_rooms.category_id`、`live_room_categories` 多套字段混用的问题。

根据当前数据库核对结果：

- `categories` 是全局医学科室/专业方向分类表，当前包含 20 个启用分类。
- `experts.category_id` 已全部补齐，384 位专家均已关联一个分类。
- 当前不存在 `expert_categories` 多对多表，因此专家实际只支持一个主分类。
- `live_room_categories` 是直播间与分类的多对多关联表，外键约束已存在。
- `live_rooms.category_id` 仍然存在，但属于历史废弃字段；当前 8 条旧字段非空直播间已与新关联表数据一致。
- 当前 81 个直播间中只有 12 个存在新分类关联，另外 69 个无分类直播间多数为测试、权限、上传、筛选用房间，需要后续区分真实业务数据和测试数据。

## 冻结规则

### 全局分类 categories

`categories` 定义为全局医学科室/专业方向分类，服务于专家、直播间、首页、搜索、推荐和统计。

分类名称应保持医学专业语义，例如普通外科、神经外科、心内科、骨科、妇产科、口腔科、器官移植科等。

### 专家分类

`experts.category_id` 表示专家主专业分类，关联 `categories.id`。

该字段用于：

- 专家列表筛选
- 专家搜索过滤
- 首页/推荐聚合
- 分类统计

`experts.department` 表示专家展示用细分科室或细分方向，不作为分类筛选的权威来源。

例如：

- `department = 乳腺外科`，`category_id = 普通外科`
- `department = 甲状腺外科`，`category_id = 普通外科`
- `department = 肾移植专科`，`category_id = 器官移植科`

`experts.expertise_areas` 表示擅长领域，可用于展示和关键词搜索，不作为主分类字段。

当前阶段专家保持单主分类设计，不新增专家多分类表。只有当产品明确需要“一个专家同时出现在多个分类频道”时，再考虑新增 `expert_categories(expert_id, category_id, is_primary, created_at)`。

### 直播间分类

直播间分类以 `live_room_categories` 为唯一业务来源。

直播间允许多分类，因为一个直播内容可能同时属于多个医学方向。公开分类列表、首页搜索、分类筛选和推荐逻辑都应读取 `live_room_categories`。

`live_rooms.category_id` 是历史废弃字段，不应再用于新增、更新、筛选、搜索或推荐逻辑。后续在代码和测试稳定后，再执行数据库迁移删除该字段。

### Topic 分类边界

`topic_categories` 是专题模块自己的分类体系，不等同于全局 `categories`。专题分类不参与专家主分类和直播间医学方向分类规则。

## 第一阶段代码固定范围

第一阶段只做规则说明同步，不改变数据库结构、不强制新增校验、不改变现有接口兼容行为。

本阶段代码改动范围：

- 更新专家 Schema 字段描述，明确 `category_id` 是主专业分类，`department` 是展示用细分科室。
- 更新全局 Category Schema/Model 描述，明确 `categories` 是医学科室/专业方向分类。
- 更新直播间分类 Schema/接口描述，明确直播间分类来源是 `live_room_categories`。
- 更新 `LiveRoomResponse.category_id` 描述，明确其为历史废弃字段。

## 后续阶段

### 第二阶段：代码约束

- 专家创建/更新时校验 `category_id` 必须存在且启用。
- 专家列表和首页搜索统一按 `Expert.category_id` 过滤。
- 直播间创建/更新继续拒绝 `category_id` 入参。
- 直播间分类筛选统一读取 `live_room_categories`。

### 第三阶段：数据治理

- 区分 69 个无分类直播间中的测试数据和真实业务数据。
- 为真实直播间补齐至少一个分类。
- 对专家 `department` 与 `category_id` 做人工巡检，修正明显不合理映射。

### 第四阶段：测试补齐

- 补专家按主分类筛选测试。
- 补直播间按多分类筛选测试。
- 补旧 `live_rooms.category_id` 入参拒绝测试。
- 补首页搜索同时覆盖专家分类和直播间分类的测试。

### 第五阶段：旧字段废弃

- 确认业务代码不再读取 `live_rooms.category_id`。
- 编写正式迁移脚本删除或彻底废弃 `live_rooms.category_id`。
- 重建 Docker 后端服务并执行回归测试。

## 预期效果

完成第一阶段后，团队对分类字段的含义有统一口径，接口文档和代码描述不再含糊。后续阶段再逐步把规则落实到校验、数据治理、测试和数据库迁移中，最终解决分类来源混乱、直播间旧字段冲突、专家科室文本和结构化分类漂移的问题。
