## 〇、前置发现：P1 ORM 模型与 Schema 的 parent_id 未落地

> **关键发现（2026-07-28 方案评审）**：融合方案 P1 设计文档规定的 `categories.parent_id` 相关改动在 ORM 模型层和 Schema 层**从未实际实施**。数据库 V5 迁移已创建 `parent_id` 列，但 Python 代码层完全不感知该列。详情如下。

### 0.1 逐文件核查

| 文件 | P1 设计要求 | 当前实际状态 | 差距 |
|:---|:---|:---|:---:|
| `app/models/content_management.py` `Category` 类 | 新增 `parent_id` Column（FK RESTRICT） | **不存在**。`Category` 类（行49-86）仅含 id / name / slug / icon / description / sort_order / is_active / created_at / updated_at | 🔴 缺失 |
| `app/models/content_management.py` `Category.name` | `unique=True` → 移除，改用部分唯一索引 | **仍为 `unique=True`**（行62） | 🟡 与 V5 部分唯一索引冲突 |
| `app/models/content_management.py` `__table_args__` | 新增 `uq_root_category_name` + `uq_sub_category_name` 部分唯一索引 | **不存在**（行74-79 仅有 sort_order + is_active 两个普通索引） | 🟡 缺失 |
| `app/models/content_management.py` 导入 | 新增 `from sqlalchemy.sql import text` | **缺失**（行6 仅有标准导入） | 🟡 部分索引需要此导入 |
| `app/schemas/content_management.py` `CategoryCreate` | 新增 `parent_id: Optional[UUID]` | **缺失**（行96-99） | 🟡 缺失 |
| `app/schemas/content_management.py` `CategoryUpdate` | 新增 `parent_id: Optional[UUID]` | **缺失**（行102-111） | 🟡 缺失 |
| `app/schemas/content_management.py` `CategoryItem` | 新增 `parent_id: Optional[UUID]` | **缺失**（行114-124） | 🟡 缺失 |
| `app/models/__init__.py` | 追加 `from .expert_departments import ExpertDepartment` | ✅ 已实施 | — |
| `app/schemas/__init__.py` | 追加专家科室 Schema 导入 | ✅ 已实施 | — |

### 0.2 对重构方案的影响

| 影响项 | 说明 |
|:---|:---|
| **ORM 层无法读写 parent_id** | 虽然数据库有 `parent_id` 列（V5 创建），但 SQLAlchemy 不会将其映射到模型实例。`category.parent_id = x` 或 `Category.parent_id` 将触发 `AttributeError` |
| **seed.py 两遍插入无法工作** | `seed_categories()` 中 `cat = Category(..., parent_id=parent.id)` 会在 ORM 层静默忽略 `parent_id`（SQLAlchemy 对未知关键字参数的行为取决于版本） |
| **前端无法获取层级信息** | `GET /content/categories` 返回的 `CategoryItem` 不含 `parent_id`，前端无法构建树形结构 |
| **V5 部分唯一索引缺乏 ORM 对应** | 不影响运行（索引在 DB 层），但 `unique=True` 在模型文档中会产生误导 |

### 0.3 修正决策

**在本方案实施 Phase B 之前，必须先执行 P0 前置修复**，将 P1 设计文档中规定但未实施的 3 个文件变更补齐。这部分已被纳入修订后的 §5.1 变更清单。

## 一、问题阐述

### 1.1 发现背景

2026-07-28 对分类系统进行全链路审查，发现两个关联性问题：

**问题 A：数据库实际数据量与设计文档不符**

前端"专家分类管理"页面（`/pages/app/admin/departments/index`）调用 `GET /content/categories` 返回的分类数据量远低于设计文档 [专家分类管理_App端接口优化设计文档.md](./专家分类管理_App端接口优化设计文档.md) 声明的 25 个根分类。经排查，`categories` 表中仅存在少量历史分类记录，seed 脚本未在数据库重新执行。

**问题 B：分类层级不符合国家医学标准**

当前 25 个分类全部以 `parent_id=NULL` 平铺在同一层级，缺失"内科""外科"这两个最核心的一级科目。根据卫生部《医疗机构诊疗科目名录》的规定，临床科室应采用"一级科目 → 二级科目"的层级体系。当前实现将一、二级科目混在同一层级，不符合行业规范。

### 1.2 问题定性

| 问题 | 根因 | 性质 | 影响面 |
|:---|:---|:---:|:---|
| categories 表记录数不足 | seed 脚本未重新执行，残留旧版数据 | 部署遗漏 | 前端分类选择器数据缺失 |
| 缺失"内科""外科"一级科目 | 原始 15 分类设计即未包含，后续扩展至 25 也未引入层级 | 设计缺陷 | 不符合行业规范，运维认知负担高 |
| 19 个二级科目平铺为根节点 | `categories.parent_id` 已支持（P1 实现），但从未被用于建立层级关系 | 未利用已有能力 | 根分类从 11 膨胀至 25，层次感缺失 |

### 1.3 合规性要求

依据卫生部《医疗机构诊疗科目名录》（卫医发〔1994〕第27号），医疗机构临床科室应遵循以下层级结构：

| 一级科目 | 二级科目（举例） |
|:---|:---|
| 内科 | 心血管内科、消化内科、内分泌科、呼吸内科、肾内科、血液科、风湿免疫科 |
| 外科 | 普通外科、神经外科、骨科、泌尿外科、胸外科、血管外科、整形外科、器官移植科、烧伤科 |
| 妇产科 | 妇科、产科 |
| 儿科 | 小儿外科等 |
| 眼科 | — |
| 耳鼻咽喉科 | 耳科、鼻科、咽喉科 |
| 口腔科 | 口腔内科、口腔颌面外科 |
| 皮肤科 | — |

> **注**：标准中一级科目约 25 个（含预防保健科、急诊科等非临床科室），本方案聚焦与专家分类直接相关的 11 个临床一级科目。

### 2.4 核心匹配算法

文件：`app/services/expert_service.py`

```
DEPARTMENT_CATEGORY_MAP ─────────────┐
  (41 条别名映射，模块级常量)         │
  e.g. '乳腺外科': '普通外科'        │  Priority 1: 别名表精确匹配
                                     │
ROOT_CATEGORIES ─────────────────────┤
  (25 个根分类名列表，模块级常量)      │  Priority 2: 子串匹配
  从 category_constants.py 导入      │  for rc in ROOT_CATEGORIES:
                                     │      if rc in department_text:
                                     │          return (dept, rc)
```

```python
def _match_broad_category(department_text: str) -> Optional[Tuple[str, str]]:
    """
    启发式匹配科室文本 → (dept_name, matched_category_name)

    匹配优先级：
    1. DEPARTMENT_CATEGORY_MAP 别名表精确匹配
    2. ROOT_CATEGORIES 子串匹配（遍历 25 个根分类名）

    无正则回退。无数据库访问。纯模块级函数。
    """
```

**调用链路**：

```
_member_create_expert()
    └─→ ExpertService._resolve_department_and_category()
        ├─→ Priority 1-3: 精确匹配 / 同义词匹配 / category_id 直接传入
        ├─→ Priority 4: 调用 _match_broad_category()
        │   ├─→ 匹配到 → 查 Category.name == cat_name 获取 UUID
        │   └─→ 未匹配到 → 自动创建 ExpertDepartment(is_verified=False)
        └─→ Priority 5: 兜底到"其他"分类
```

## 四、目标架构设计

### 4.1 设计原则

```
1. 最小迁移：只改 categories 表 parent_id 值，expert_departments 和 experts 的 FK 全部不变
2. 向下兼容：所有 API 响应结构不变（每项仍返回 id/name/parent_id），前端按需适配
3. 国家标准：一级科目命名和归属关系严格遵循《医疗机构诊疗科目名录》
4. 单一真相源：ROOT_CATEGORIES / DEPARTMENT_CATEGORY_MAP 统一从 category_constants.py 导出
5. 匹配算法不动骨架：_match_broad_category 只改遍历源，不改优先级逻辑
```

### 4.2 目标数据模型（无结构变更）

```
categories
├── 内科（id=新 UUID, parent_id=NULL）                    ← 新增
│   ├── 心内科（parent_id=内科.id）                       ← parent_id 从 NULL 改为内科.id
│   ├── 消化科
│   ├── 内分泌科
│   ├── 呼吸内科
│   ├── 肾内科
│   ├── 血液科
│   └── 风湿免疫科
│
├── 外科（id=新 UUID, parent_id=NULL）                    ← 新增
│   ├── 普通外科（parent_id=外科.id）                     ← parent_id 从 NULL 改为外科.id
│   ├── 神经外科
│   ├── 骨科
│   ├── 泌尿外科
│   ├── 心胸外科
│   ├── 血管外科
│   ├── 整形外科
│   ├── 器官移植科
│   └── 烧伤与创面修复科

├── 妇产科（parent_id=NULL，不变）
├── 儿科（parent_id=NULL，不变）
├── 眼科（parent_id=NULL，不变）
├── 耳鼻喉科（parent_id=NULL，不变）
├── 口腔科（parent_id=NULL，不变）
```

> 
> 这一变化是合理的设计选择——对于无法精确匹配的科室，归入更宽泛的一级分类比猜测具体二级分类更安全。方案已记录此差异，Phase C 验证中需包含"新建专家的 category_id 指向一级分类"的场景确认。

### 4.4 匹配算法改造

```python
# app/services/expert_service.py

from app.core.category_constants import (
    ALL_CATEGORY_NAMES_SORTED,
    CATEGORY_PARENT_MAP,
    DEPARTMENT_CATEGORY_MAP,
    ROOT_CATEGORIES,
)

def _match_broad_category(department_text: str) -> Optional[Tuple[str, str]]:
    """
    返回 (dept_name, level1_category_name)。

    优先匹配 Level 2（更具体），再匹配 Level 1。
    匹配到 Level 2 时，通过 CATEGORY_PARENT_MAP 自动解析为一级科目名。
    """
    normalized = _normalize_department_text(department_text)
    if not normalized:
        return None

    # P1: 别名表（值已是 Level 1 名）
    mapped = DEPARTMENT_CATEGORY_MAP.get(normalized)
    if mapped:
        return (normalized, mapped)

    # P2: 子串匹配（Level 2 优先——ALL_CATEGORY_NAMES_SORTED 中二级在前）
    for cat_name in ALL_CATEGORY_NAMES_SORTED:
        if cat_name in normalized:
            parent = CATEGORY_PARENT_MAP.get(cat_name, cat_name)
            return (normalized, parent)

    return None
```

### 6.4 `seed.py` 改造要点

```python
# 当前：单遍平铺插入
def seed_categories(db) -> dict:
    categories = {}
    for data in CATEGORIES_DATA:
        cat = Category(id=uuid.uuid4(), name=data["name"], ...)
        db.add(cat)
        categories[data["name"]] = cat
    db.flush()

# 改造后：两遍插入（先 Parent，后 Child）
def seed_categories(db) -> dict:
    categories = {}

    # Phase 1: 插入一级科目（parent_name=None）
    for data in CATEGORIES_SEED_DATA:
        if data.get("parent_name") is not None:
            continue  # 二级暂时跳过
        existing = db.query(Category).filter_by(name=data["name"], parent_id=None).first()
        if existing:
            categories[data["name"]] = existing
        else:
            cat = Category(id=uuid.uuid4(), name=data["name"], slug=data["slug"],
                           sort_order=data["sort_order"], is_active=True)
            db.add(cat)
            categories[data["name"]] = cat
    db.flush()

    # Phase 2: 插入二级科目（parent_name 指向已存在的一级）
    for data in CATEGORIES_SEED_DATA:
        if data.get("parent_name") is None:
            continue
        parent = categories.get(data["parent_name"])
        if not parent:
            raise ValueError(f"父分类 '{data['parent_name']}' 未找到——请检查 CATEGORIES_SEED_DATA 顺序")
        existing = db.query(Category).filter_by(
            name=data["name"], parent_id=parent.id
        ).first()
        if existing:
            categories[f"{data['parent_name']}→{data['name']}"] = existing
        else:
            cat = Category(id=uuid.uuid4(), name=data["name"], slug=data["slug"],
                           sort_order=data["sort_order"], parent_id=parent.id, is_active=True)
            db.add(cat)
            categories[f"{data['parent_name']}→{data['name']}"] = cat
    db.flush()
    return categories
```

## 八、风险评估与缓解

### 8.1 风险矩阵

| # | 风险项 | 概率 | 影响 | 级别 | 缓解措施 |
|:--|:---|:---:|:---:|:---:|:---|
| R1 | **匹配算法回归**：`ALL_CATEGORY_NAMES_SORTED` 中二级优先策略改变子串匹配结果 | 中 | 高 | 🟡 | 用全部 41 个已知科室值回归测试（Phase C1），覆盖率不得低于当前 95% |
| R2 | **"内科"子串误匹配"心内科"**：若排序不当，"内科"先匹配导致丢失"心内科"的精确匹配 | 低 | 高 | 🟢 | `ALL_CATEGORY_NAMES_SORTED` 二级在前，一级在后，确保"心内科"先于"内科"遍历；回归测试覆盖此场景 |
| R3 | **别名表同步遗漏**：`expert_service.py`、`migrate_expert_departments.py`、`migration_expert_category.py` 三处别名表未同步更新 | 中 | 中 | 🟡 | `expert_service.py` 改为从 `category_constants` 导入；migration 脚本同理（Phase B4） |
| R4 | **V10 迁移部分执行**：幂等逻辑失效导致重复插入"内科""外科" | 低 | 中 | 🟢 | `INSERT ... WHERE NOT EXISTS` 确保幂等；`UPDATE` 加 `AND parent_id IS NULL` 守卫 |
| R5 | **seed.py 插入顺序失败**：先插二级时 parent_id 引用的父分类尚不存在 | 低 | 中 | 🟢 | 两遍插入：Phase 1 只插 parent_name=None（一级），Phase 2 才插二级并查表填 parent_id |
| R6 | **前端渲染断链**：前端假设分类平铺，需改为树形渲染 | 高 | 低 | 🟢 | `GET /content/categories` 返回结构不变（仍为平铺列表，每项含 parent_id），前端按需适配树形，不影响现有功能 |
| R7 | **回滚操作失误**：删除一级分类前未先解除子类关联，触发 RESTRICT | 低 | 低 | 🟢 | 回滚脚本中先 `UPDATE parent_id=NULL` 再 `DELETE`，顺序写死在脚本注释中 |

### 8.2 回滚触发条件

| 场景 | 触发条件 | 操作 |
|:---|:---|:---|
