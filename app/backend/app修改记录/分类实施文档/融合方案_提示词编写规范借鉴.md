## 一、母版提示词的 6 层架构

通过对 40 个母版文档的审读，其核心架构由 6 层组成：

```
┌─────────────────────────────────────────────┐
│  Layer 1: 角色定义 (Role Definition)         │  ← 定义 AI 的执行身份
├─────────────────────────────────────────────┤
│  Layer 2: 任务目标 (Task Objective)          │  ← 精确到文件路径的输出清单
├─────────────────────────────────────────────┤
│  Layer 3: 核心上下文 (Core Context)          │  ← 项目结构、现有代码参考、技术栈
├─────────────────────────────────────────────┤
│  Layer 4: 架构约束 (Architecture Constraints)│  ← 分层职责、事务边界、异常处理
├─────────────────────────────────────────────┤
│  Layer 5: 代码生成要求 (Code Gen Reqs)       │  ← 逐文件的精确要求（导入/模式/字段）
├─────────────────────────────────────────────┤
│  Layer 6: 完整性检查清单 (Completeness Chk)  │  ← 验证是否完整、一致、可执行
└─────────────────────────────────────────────┘
```

### Layer 1: 角色定义 — "你是什么角色"

母版的核心模式：**不写通用提示，而是定义 AI 的精确身份与职责边界**。

```
❌ 差的写法： "请帮我写专家模块的CRUD代码"
✅ 母版写法： "你是一名精通学院派架构的资深 Python 后端架构师。
            你擅长将业务需求解耦，并严格执行分层架构。
            你的任务是生成符合以下规范的新 CRUD 层代码..."
```

对融合方案的借鉴：
```
你是一名精通 SQLAlchemy 2.0 + PostgreSQL 的数据库建模专家。
你理解受控词表（Controlled Vocabulary）的设计模式。
你擅长将自由文本字段升级为外键约束，确保数据一致性在数据库层面得到保证。
```

### Layer 2: 任务目标 — "精确到文件路径"

母版特征：**明确列出每个输出文件、包含的类/函数名、不允许做的事情**。

```
✅ 母版写法:
  任务目标:
  - 生成 app/models/expert_departments.py，包含 ExpertDepartment 模型
  - 修改 app/models/experts.py，删除 department 列，新增 department_id FK
  - 修改 app/models/content_management.py，新增 Category.parent_id 列
  - 生成 app/schemas/expert_departments.py，包含 Create/Update/Item/LimitedItem
  - 严禁: 修改任何已有路由入口的 URL 签名
  - 严禁: 创建新的数据库触发器
  
❌ 差的写法: "改一下专家相关的代码"
```

### Layer 3: 核心上下文 — "必须引用的已有代码"

母版最关键的特征：**在提示词中嵌入完整的已有代码，让 AI 能直接"看到"应该模仿的模式**。

```
母版做法:
  B. 现有代码参考
  - 必须提供现有模型文件的完整示例（如 live_core.py）
  - 关键观察点（必须列出）:
    1. Base 类导入方式: from app.database import Base
    2. Enum 重命名为 SAEnum
    3. UUID 字段定义: UUID(as_uuid=True), primary_key=True, default=uuid.uuid4
    4. ... (共12个观察点)

对融合方案的借鉴:
  B. 现有代码参考
  - 参考文件: app/models/experts.py（现有 Expert 模型的完整代码）
  - 参考文件: app/models/content_management.py（现有 Category 模型的完整代码）
  - 参考文件: app/schemas/experts.py（现有 ExpertItem Schema 的完整代码）
  - 关键观察点:
    1. department → department_id 的字段重命名模式
    2. ForeignKey 的 ondelete 策略: experts 用 SET NULL, expert_departments 用 RESTRICT
    3. JSONB 列的定义: synonyms = Column(JSONB, nullable=False, default=list)
```

### Layer 4: 架构约束 — "分层职责的铁律"

母版在这个层最严苛——明确规定了**哪一层负责什么，哪一层不能做什么**。

```
母版的典型约束:
  - 事务处理: CRUD 层处理 commit/rollback，Service 层不直接调用 commit
  - 异常处理: Service 抛自定义异常，Endpoint 捕获并转 JSONResponse
  - 日志: CRUD 记录数据库错误，Endpoint 记录业务异常
  - N+1 防治: 查询使用 selectinload/joinedload
  - 分页: 两次查询（count + offset/limit）

对融合方案的适用性:
  ✅ 全项目已遵循此模式，融合方案直接继承
  ✅ _resolve_department_and_category 是只读查询，放在 Service 层，不涉及 CRUD 写操作
  ✅ merge_departments 是写操作，CRUD 层需要处理事务
```

### Layer 5: 代码生成要求 — "逐字段逐行的精确规范"

母版特征：**不是泛泛地"写好代码"，而是给每一行代码指定精确的写法**。

```
母版例子:
  导入语句要求:
    ✅ TIMESTAMP从 sqlalchemy 导入，不是 sqlalchemy.dialects.postgresql
    ✅ Enum 必须重命名为 SAEnum
    ✅ 导入 func 用于 func.now()
    ✅ 导入 Index 用于显式命名索引
  
  UUID 字段:
    ✅ Column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)
    ❌ Column(UUID, primary_key=True, default=uuid.uuid4)
  
  时间戳:
    ✅ TIMESTAMP(timezone=True), nullable=False, server_default=func.now(), onupdate=func.now()
    ❌ DateTime, default=datetime.utcnow

对融合方案需要新增的精确规范:
  JSONB 列:
    ✅ synonyms = Column(JSONB, nullable=False, default=list)
       # default=list 不是 default='[]'，后者会导致 JSONB 列存字符串
  
  Unique Constraint → Partial Unique Index:
    ✅ 不在 Column 上设 unique=True
    ✅ 使用 __table_args__ + Index(unique=True, postgresql_where=text("..."))
    ❌ 在 name 字段上同时设 unique=True 又建部分索引 → 冲突
```

### Layer 6: 完整性检查清单 — "验证是否能上线"

```
母版的检查清单模式:
  ✅ 所有模型类都在 __init__.py 中注册
  ✅ 所有 FK 列都创建了索引
  ✅ 所有 Enum 都继承了 str, enum.Enum
  ✅ 所有 Pydantic Schema 的 model_config 都包含 from_attributes=True
  ✅ 所有时间戳都使用 server_default=func.now()（数据库级默认值）

融合方案新增:
  ✅ expert_departments.name 的 UNIQUE 约束正确创建
  ✅ categories.name 的旧 UNIQUE 约束已删除，部分唯一索引已创建
  ✅ experts.department_id 的 FK 是 SET NULL（不是 RESTRICT）
  ✅ expert_departments.category_id 的 FK 是 RESTRICT（不是 CASCADE）
  ✅ experts.category_id 的 nullable 已从 True 改为 False
  ✅ trg_sync_expert_category 触发器已确认不引入
```

### P3 提示词的核心内容（Service + API）

```
[角色定义]
你是一名精通 Clean Architecture（学院派）的资深 Python 后端架构师。
你需要严格执行 CRUD/Service/API 三层的职责分离。

[核心架构约束]
- CRUD 层处理事务 (commit/rollback) 和 IntegrityError
- Service 层抛出自定义异常，由 API 层捕获并转 JSONResponse
- Service 层不直接调用 db.commit()
- 禁止使用数据库触发器 → 用应用层 UPDATE 同步

[任务目标 — Service 层]
1. 修改 services/expert_service.py:
   - _resolve_active_category_id → _resolve_department_and_category (只读匹配)
   - 新增 _match_broad_category (子串匹配 + 别名表)
   - 新增 _build_expert_item (填充 department_name, category_name)
   - 新增 merge_departments (合并科室 + 同义词自学习)
   - 新增 update_department_category (修改科室分类 + 应用层显式同步 experts.category_id)

[任务目标 — API 层]
1. 新建 api/v1/endpoints/expert_departments.py:
   - GET /admin/expert-departments (列表)
   - POST /admin/expert-departments (创建)
   - PATCH /admin/expert-departments/{id} (更新)
   - DELETE /admin/expert-departments/{id} (软删除)
   - GET /admin/expert-departments/unmapped (未映射专家列表)
2. 修改 api/v1/endpoints/experts.py:
   - format_expert_response 中 department → department_name (已完成)
   - 所有 public 端点响应增加 category_name 字段

[关键代码模式 - 应用层同步]
# 修改科室分类 + 同步专家
async def update_department_category(self, dept_id, new_cat_id):
    dept = await self.db.get(ExpertDepartment, dept_id)
    dept.category_id = new_cat_id
    
    await self.db.execute(
        update(Expert)
        .where(Expert.department_id == dept_id)
        .values(category_id=new_cat_id)
    )
    await self.db.commit()

[关键代码模式 - 合并科室]
async def merge_departments(self, source_id, target_id):
    SYNONYM_LIMIT = 20
    source = await self.db.get(ExpertDepartment, source_id)
    target = await self.db.get(ExpertDepartment, target_id)
    
    # 自学习同义词
    synonyms = set(target.synonyms or [])
    synonyms.add(source.name)
    if source.synonyms:
        synonyms.update(source.synonyms)
    target.synonyms = list(synonyms)[:SYNONYM_LIMIT]
    
    # 迁移专家
    await self.db.execute(
        update(Expert).where(Expert.department_id == source_id)
        .values(department_id=target_id)
    )
    # 同步 category_id
    await self.db.execute(
        update(Expert).where(Expert.department_id == target_id)
        .values(category_id=target.category_id)
    )
    
    await self.db.delete(source)
    await self.db.commit()
```

##三、母版提示词的核心规范总结

| 规范 | 母版做法 | 融合方案借鉴 |
|:----|:------|:-----------|
| **精确文件清单** | 列出每个输出文件的完整路径 + 包含的类/函数名 | P1-P5 各有精确的文件清单 |
| **已有代码嵌入** | 在提示词中嵌入完整的现有代码，让 AI 能"看到"模式 | 嵌入 experts.py, content_management.py, schemas.py |
| **关键观察点** | 12 个"必须观察的代码模式" | 新增 6 个融合方案特有的观察点（JSONB、部分索引、RESTRICT vs SET NULL） |
| **分层职责铁律** | CRUD→事务, Service→异常, API→转换 | 完全继承，无变化 |
| **逐行精确规范** | 每一行代码的精确写法（导入、字段、约束） | JSONB default=list、部分索引语法、应用层同步模式 |
| **完整性检查清单** | 验证项列表（注册、索引、约束、枚举） | 融合方案新增 6 个验证项 |
| **增量 vs 初始模式** | 自动检测是修改已有文件还是新建文件 | P1 是新文件 + 修改已有文件，明确区分 |
| **一致性验证** | 提示词产出后必须用一致性检查母版验证 | P5 专门做此验证 |
| **唯一真相源原则** | 设计文档 > 学院派架构 > 现有代码 | 融合方案主文档为最高优先级 |
