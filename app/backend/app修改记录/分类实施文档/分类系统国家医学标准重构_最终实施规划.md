## Phase A：数据迁移 — V10 SQL

### 做什么

在数据库层面建立一级/二级层级关系：新增"内科""外科"两条一级科目，将 16 条原根分类的 `parent_id` 从 `NULL` 改为指向内科/外科。

### 具体操作

1. **备份**：`SELECT id, name, parent_id FROM categories WHERE is_active = true ORDER BY sort_order`
2. **执行 V10 SQL**（完整 SQL 见方案 §6.2，已包含幂等守卫和回滚脚本）
3. **验证**：

```sql
SELECT
    COUNT(*) FILTER (WHERE parent_id IS NULL AND is_active = true)  AS root_count,
    COUNT(*) FILTER (WHERE parent_id IS NOT NULL AND is_active = true) AS child_count
FROM categories;
-- 预期：root_count=11, child_count=16
```

### 风险

| 风险 | 级别 | 缓解 |
|:---|:---:|:---|
| 数据库有不在 25 个标准分类中的自定义分类 | 🟡 | V10 SQL 的 `UPDATE WHERE name IN (...)` 只匹配已知列表，自定义分类不受影响，保持 `parent_id=NULL` |
| 幂等失效导致重复插入"内科""外科" | 🟢 | `INSERT ... WHERE NOT EXISTS` + `UPDATE ... AND parent_id IS NULL` 双重守卫 |
| sort_order 与 seed.py 不一致 | 🟢 | V10 SQL 动态计算 sort_order（取最小值-1），seed.py 静态定义（内科=1, 外科=2）。不影响功能——sort_order 仅用于排序 |

### 收益

| 收益 | 说明 |
|:---|:---|
| 数据库层级就绪 | 11 个一级 + 16 个二级，符合卫健委《医疗机构诊疗科目名录》 |
| 下游 FK 零影响 | `experts.category_id` / `expert_departments.category_id` 全部不变 |
| zero-downtime | 纯 UPDATE/INSERT，不需要重启服务 |
| 可回滚 | 回滚脚本先 `UPDATE parent_id=NULL` 再 `DELETE`，顺序不可逆 |

### 核心易错点

B1 是最核心、最易出错的步骤，以下是必须逐条核对的关键点：

```
□ "内科"的 parent_name 是 None（一级科目，不是漏填）
□ "外科"的 parent_name 是 None
□ 心内科/消化科/内分泌科/呼吸内科/肾内科/血液科/风湿免疫科 → parent_name="内科"（不是"外科"）
□ 普通外科/神经外科/骨科/泌尿外科/心胸外科/血管外科/整形外科/器官移植科/烧伤与创面修复科 → parent_name="外科"
□ ALL_CATEGORY_NAMES_SORTED 中"心内科"在"内科"之前（二级优先→一级，避免子串误匹配）
□ len(DEPARTMENT_CATEGORY_MAP) == 41，所有值都是一级名（"外科"/"妇产科"/"耳鼻喉科"/"口腔科"/"儿科"/"生殖医学科"/"其他"）
```

### 风险

| 风险 | 级别 | 缓解 |
|:---|:---:|:---|
| **B2 先于 A 部署** → `_match_broad_category` 返回"内科"/"外科"，但 DB 中不存在 → 全部回退到"其他" | 🔴 | **Phase A V10 SQL 和 Phase B 代码必须打包为同一批次部署**。这是本次实施最重要的单条约束 |
| `ALL_CATEGORY_NAMES_SORTED` 排序不当 → "内科"先于"心内科"被遍历，子串误匹配 | 🟡 | 二级在前、一级在后（通过列表推导式 `if parent_name is not None` 先于 `if parent_name is None` 保证）；C1 回归覆盖 |
| 41 条别名迁移时遗漏条目或值写错 | 🟡 | 提示词 §5.1.3 附有完整的旧值→新值对照表；grep 验证 `len(map) == 41` |
| `seed_categories` 返回值 key 格式变化导致 `seed_live_rooms` 查找失败 | 🟡 | B3 末尾的向后兼容映射：`categories[data["name"]] = categories[f"{parent}→{name}"]` |
| migrate_expert_departments.py 的 `ROOT_CATEGORIES` 导入后匹配精度下降 | 🟢 | 脚本已 FROZEN，不应重新执行。导入同步仅为代码一致性 |

### 收益

| 收益 | 说明 |
|:---|:---|
| 单一真相源 | 3 处 `DEPARTMENT_CATEGORY_MAP` → 1 处（`category_constants.py`），消除同步风险 |
| 匹配覆盖率不退化 | 保持 ≥95%（41 条全量回归验证） |
| 层级可扩展 | 新增二级分类只需在 `CATEGORIES_SEED_DATA` 中追加入口，通过列表推导式自动纳入所有派生常量 |
| seed 幂等且安全 | 两遍插入 + 向后兼容映射，新旧数据共存不冲突 |

## 前端接口变动说明

### 受影响的接口

| 接口 | 变更类型 | 变更内容 | 前端兼容性 |
|:---|:---:|:---|:---|
| `GET /content/categories` | 响应增强 | `CategoryItem` 新增 `parent_id: Optional[UUID]` 字段。`null` = 一级科目（内科/外科/妇产科等），非 `null` = 二级科目（心内科/骨科等） | ✅ 向前兼容——多一个字段不破坏旧解析 |
| `GET /content/categories?include_counts=true` | 同上 | 同上，另含 `expert_count` 和 `room_count` | ✅ 同上 |
| `POST /admin/categories` | 请求增强 | `CategoryCreate` 新增 `parent_id: Optional[UUID]`，管理员可指定父分类创建子分类 | ✅ Optional 字段，不传等同于旧行为 |
| `PATCH /admin/categories/{id}` | 请求增强 | `CategoryUpdate` 新增 `parent_id: Optional[UUID]` | ✅ Optional 字段 |
| `GET /admin/categories` | 响应增强 | 同上 `parent_id` 字段 | ✅ 同上 |
| `POST /admin/experts` | **行为变化** | 传入 `department_name` 时，`_match_broad_category` 返回一级分类名（如"内科"）而非二级（如"心内科"）。新增/导入专家的 `category_id` 将指向一级分类 | ⚠️ category_id 值变化（UUID 仍有效） |
| `POST /admin/experts/batch-import` | **行为变化** | 同上——批量导入专家的 `category_id` 指向一级分类 | ⚠️ 同上 |
| `GET /experts` / `GET /admin/experts` | 无变更 | `category_id` 筛选仍按 UUID 等值查询，存量数据 UUID 不变 | ✅ 零影响 |
| `GET /admin/expert-departments` | 无变更 | 科室管理接口不依赖分类层级 | ✅ 零影响 |

### 不受影响的接口

| 接口 | 原因 |
|:---|:---|
| `GET /experts?category_id=X` | category_id UUID 不变，筛选逻辑不变 |
| `GET /admin/expert-departments` | 独立端点，不涉及 categories 表层级 |
| `POST /admin/expert-departments/merge` | 合并逻辑按 UUID 操作，不依赖层级 |
| `PATCH /admin/expert-departments/{id}/category` | 应用层同步逻辑不变 |
| 所有直播间相关接口 | `live_room_categories` FK 不变 |
| 搜索接口 | category_id 等值过滤不变 |

### 前端可选增强项（不强制，后续独立迭代）

| 增强项 | 利用的新字段 | 说明 |
|:---|:---|:---|
| Tab 分类总览改为树形展示 | `parent_id` | 渲染"内科 → 心内科"、"外科 → 骨科"的层级树 |
| 分类筛选器改为级联选择 | `parent_id` | 先选一级（内科/外科），再下拉二级（心内科/消化科/骨科等） |
| 专家详情展示一级分类名 | `category_name` | 重构后新创建专家 `category_name` 显示一级名（如"内科"） |

### 注意：新旧数据 category_id 层级的差异

重构**不改变**存量数据——`experts.category_id` 和 `expert_departments.category_id` 的 FK 值全部不变。

但重构后**新创建/导入**的专家，`category_id` 将指向**一级分类**（内科/外科等），而非二级分类（心内科/骨科等）。

这意味着 `GET /content/categories?include_counts=true` 中 `expert_count` 的统计分布在两个层级上：
- 存量数据：expert_count 在二级（如"心内科"有 N 个专家）
- 新数据：expert_count 在一级（如"内科"有 M 个专家）

如需按一级分类统一统计（含其所有子分类的专家数），需增强 CRUD 层的递归查询逻辑。详见设计文档 §4.4 的"语义变化说明"。
