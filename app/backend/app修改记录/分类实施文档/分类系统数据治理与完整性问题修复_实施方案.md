## 一、背景与问题阐述

### 1.1 发现背景

2026-08-09 对分类系统进行了三轮全链路审查（首页直播间分类、专家列表分类、专家↔分类关联管理、国家医学分类标准合规），并结合双方独立分析结果交叉验证。审查结论：分类体系的**读路径**（列表、筛选、子孙聚合、统计）实现扎实；但**写路径**（删除、合并、移动）存在 3 个关键缺口——删除引用检查不全、树断裂无保护、合并分类功能缺失，另有若干标准合规与技术债问题。

## 二、问题根源与危害分析

### 2.1 主题一：删除路径的数据完整性（问题 1/2/3）

**根源**：
- `delete_category`（`services/content_management_service.py:580`）核心动作只有一行 `category.is_active = False`，诞生于分类平铺结构年代，V4 引入科室词表、V5 引入 `parent_id`、V10 重构两级树后**写路径从未随之演进**
- 软删除是"纯标志位翻转"，不触发任何 DB 约束（`experts` NO ACTION / `expert_departments` RESTRICT 只防物理删除）
- 引用检查只统计 `experts` + `live_room_categories` 两类，漏 `expert_departments` 与子分类
- 停用父分类不级联子分类；公开列表 `get_categories`（`crud/content_management.py:340-344`）只过滤自身 `is_active`，不校验父节点状态

**危害**：
| 场景 | 后果 |
|:---|:---|
| force 删除含专家的分类 | 专家前台按分类筛选永久不可命中（`experts.py:250-252` 静默返回空），但详情页仍显示已停用分类名——前后台矛盾，无恢复路径 |
| force 删除含房间关联的分类 | `live_room_categories` 行保留但公开接口过滤后不可见，成为僵尸数据 |
| force 删除含科室的分类 | 科室仍挂停用分类下，科室列表照常显示分类名——"停用分类仍被业务引用"死结，且当前代码连警告都不给 |
| 停用一级分类（如"外科"） | 9 个 active 子分类成为孤儿节点，前端树渲染断链；子分类数据全部保留但不可达；父分类筛选被拒而子分类筛选可用——行为矛盾 |
| 计数口径 | 删除报"10 位专家引用"、列表显示"5 位"——数字打架，误导管理员决策（低估→误用 force；高估→不敢治理） |

### 2.2 主题二：治理能力缺失（问题 4/6）

**根源**：
- 全仓只有科室级合并 `merge_departments`（`expert_service.py:1413`），分类作为更上层树节点从未纳入治理能力设计——"只建树、不治树"
- 删除逻辑的 409 提示语"请先迁移引用"（`content_management_service.py:639`）是善意建议，但全项目无对应迁移端点——"能力与提示脱节"

**危害**：
| 场景 | 后果 |
|:---|:---|
| 运营合并重复分类（"消化科"vs"胃肠科"） | 无工具：手工 SQL（高风险不可审计）/ 改名（数据仍分裂）/ force 删除（数据悬空）三选一 |
| 管理员面对 409 | 只有"放弃"或"force 制造悬空"两个选项，治理流程断裂 |
| 脏分类长期累积 | 搜索/筛选/统计质量持续下降，问题随时间指数放大 |

### 2.3 主题三：层级不变量漏洞（问题 5）

**根源**：
- `_validate_category_hierarchy`（`content_management_service.py:76-118`）只校验**新建/挂载路径**（父分类不能是二级），`CategoryUpdate.parent_id` 允许任意修改
- 循环检测注释声称"不能等于自身或自身子孙"，**实际代码只排除自身**（117-118 行）——注释与实际不符
- "合法分类树"的不变量（无三层、无孤儿、父必启用）没有集中定义，创建/更新/删除各路径各自漏检

**危害**：
- 一级"外科"（9 个 active 子分类）被 update 挂到某一级下 → 9 个子分类瞬间变第三层
- 依赖"两层假设"的匹配算法（`ALL_CATEGORY_NAMES_SORTED`）、前端树渲染、`get_category_descendant_ids` 递归**全部失效**
- 统计聚合（子计数累加父）在多层下重复累加 → 计数虚高
- 属于"定时炸弹"型问题：不立即崩，特定数据组合下出错，极难排查

### 2.4 主题四：一致性与体验（问题 7/8）

**根源**：两处独立实现、各定各的语义——专家列表"分类无效"静默返回空；删除检查与管理列表计数各自统计。

**危害**：
- 用户通过历史链接访问停用分类筛选 → 一片空白且无任何提示
- 前端无法区分"空结果"与"分类失效"，无法引导
- 计数数字打架，管理员决策信息错误

### 2.5 主题五：标准合规（问题 9/10/14）

**根源**：
- 种子数据（`category_constants.py`）是"业务裁剪后手工录入"，注释宣称"严格遵循卫生部《医疗机构诊疗科目名录》"但**没有任何对照标准的校验过程**
- 命名偏差：耳鼻喉科（≠耳鼻咽喉科）、心内科（≠心血管内科专业）等；"生殖医学科"不是名录一级科目；"其他"为兜底非标准
- 一级科目缺失：精神科、中医科、康复医学科、麻醉科、医学影像科等高频科目未覆盖
- 部分唯一索引（`uq_root_category_name` / `uq_sub_category_name`，`models/content_management.py:94-98`）允许同名不同级并存，而匹配算法按名称查找时 `scalar_one_or_none()` 抛 `MultipleResultsFound`

**危害**：
- 医疗平台科室名直接面向用户，命名不规范伤害专业可信度；合规审核风险
- 专家导入匹配（`DEPARTMENT_CATEGORY_MAP` 精确匹配 + 子串匹配）依赖分类名，不规范名降低匹配准确率
- 同名歧义在标准名落地（问题 9 方案）后必现——**是命名修复的前置条件**
- 注释宣称失实，误导后续开发者

### 2.6 主题六：技术债与联动（问题 11/12/13/15）

| 问题 | 根源 | 危害 |
|:---|:---|:---|
| 11 SQL 拼接 | `homepage_search.py:439` 手写字符串拼接 UUID | 当前 ID 来自 DB 结果注入风险低，但一旦来源变化即注入面；可维护性差 |
| 12 is_primary 未启用 | 字段先建、规则后置（V11 只回填基线）；注释明确"规则尚未启用" | 主分类语义空转，未来前端依赖主分类展示会出错 |
| 13 种子漂移 | `category_constants.py` 是"单一真相源"但运行时 DB 才是真相；治理后常量必过期 | 合并/改名成果在 seed 重跑时可能被旧常量"复活"或覆盖（已部分缓解：seed 按 name+parent_id 查重跳过，不覆盖 `is_active`） |
| 15 科室合并联动 | `merge_departments` 跨分类合并时同步专家 `category_id`（`expert_service.py:1440-1445`）但科室自身不动 | 分类合并工具需感知"科室合并已迁移的专家"，否则三层引用链（科室→专家→分类）出现中间态不一致 |

## 三、设计原则与目标架构

### 3.1 设计原则

| 原则 | 内容 | 对应问题 |
|:---|:---|:---|
| P1 软删哲学保持 | 分类停用仍为 `is_active=False`，可整体恢复，不物理删除 | 全部 |
| P2 单事务原子性 | 删除/合并/迁移涉及多表写操作必须同一事务，任一步失败整体回滚，不产生"迁了一半"中间态 | 2/3/4 |
| P3 树不变量全路径保证 | 无三层、无孤儿、父必启用——create/update/delete/merge 全部路径过同一校验函数 | 3/5 |
| P4 单一计数口径 | 全系统引用统计收敛为一个函数，`all_count`（物理引用）/ `active_count`（前台可见）语义自明 | 1/8 |
| P5 种子基线 + 增量治理 | seed 纯幂等插入，治理操作（合并/改名）不反向写常量，运行时校验常量引用 | 4/13 |
| P6 标准名/口语名分离 | `name` 存名录标准名（驱动匹配），`display_name` 存口语名（驱动展示），线上无感 | 9/10/14 |

### 3.2 目标数据流

```
删除分类（= 停用整棵子树 + 引用安顿，单事务）
  ├─ 引用统计（统一函数）→ 有引用且非 force → 409（结构化清单）
  └─ force（= 确认级联）：
      ├─ 专家 category_id → 迁移目标（显式 target 或"其他"）
      ├─ 科室 category_id → 同上（不悬空）
      ├─ live_room_categories → 直接解除（弱引用）
      ├─ 级联软删子树（分类 + 全部 active 子分类）
      └─ 返回迁移统计（可审计、可恢复）

合并分类（A → B，单事务）
  ├─ experts → B / expert_departments → B / live_room_categories → B（去重）
  ├─ 子分类 → 默认提升一级 / 参数挂到 B 下
  └─ 软删 A（复用删除路径兜底）

迁移端点（独立工具）
  └─ 与删除的迁移函数为同一实现、两个入口
```

### 3.3 层级校验不变量（集中定义）

```
规则 1: 深度 ≤ 2 层（parent_id → 一级 → 二级）
规则 2: 无环（parent_id ≠ 自身或自身任意子孙）
规则 3: 父分类必须存在且 is_active=True
规则 4: 已有 active 子分类的分类禁止修改 parent_id（防降级三层）
规则 5: 停用父分类时级联停用子树；公开列表父不可见则子不返回
```

## 四、方案选型分析与决策

### 4.1 删除语义（问题 2）—— 选方案 B

| 方案 | 内容 | 评价 |
|:---|:---|:---|
| A | 仅提示，不做任何动作 | ❌ 已被验证为数据垃圾源头，不解决 |
| B | 级联停用子树 + 引用单事务迁移（专家/科室 → 目标或"其他"、解除房间关联） | ✅ **采纳** |
| C | 禁止删除，只提供合并 | ❌ 合并落地晚，先给兜底修复 |

**为什么选 B**：问题已被证明是数据悬空的源头，B 让删除动作形成闭环（停用前引用已安顿）；且与"软删除、可恢复"哲学一致——迁移是引用层的操作，不影响分类数据本身的可逆性。

### 4.2 子分类处置（问题 3）—— 级联停用

| 方案 | 内容 | 评价 |
|:---|:---|:---|
| A | 禁止停用含 active 子分类的父分类 | ❌ 阻塞分类治理，与软删哲学冲突 |
| B | 删除时级联停用子树 + 公开列表防御过滤（父不可见则子不返回） | ✅ **采纳** |

**为什么选 B**：双保险（删除时级联 + 展示时防御）保证任何路径不产生孤儿节点，树不变量成为代码保证而非运气。

### 4.3 命名合规（问题 9）—— display_name 分离

| 方案 | 内容 | 评价 |
|:---|:---|:---|
| A | 直接改名 + 存量迁移脚本 | 需处理 `DEPARTMENT_CATEGORY_MAP` 别名表、C 端展示变化，一次性大规模改名风险 |
| B | `name` 存标准名 + `display_name` 存口语名，C 端展示走 `display_name` | ✅ **采纳** |

**为什么选 B**：`experts`/`expert_departments` 通过 UUID FK 引用分类（改名不触碰引用），URL 用 `slug`（不随 name 变）——改名真实风险面不大，但 **A 会让 C 端展示一夜全变**（用户看到"心内科"突然变"心血管内科"），且 `DEPARTMENT_CATEGORY_MAP` 别名表值需同步改写。B 实现线上无感：匹配算法走标准名（准确率↑）、展示走口语名（无迁移阵痛）。**注意**：B 落地前提是解决问题 14（同名歧义），否则标准名落地后匹配算法必现 `MultipleResultsFound`。

### 4.4 合并时子分类处置（问题 4）—— 参数化，默认挂 target 下

| 选项 | 内容 | 评价 |
|:---|:---|:---|
| A | 子分类提升为一级 | 数据更保守，但合并几次就"根部膨胀" |
| B | 子分类挂到 target 下 | 符合"合并=归入"直觉，深度不变（过校验），层级收敛 |

**决策**：`attach_children` 参数，默认 `false`（挂 target 下），运营按场景选择提升为一级。**注意**：挂 target 下需过规则 4 校验（target 本身不得有子分类导致三层）。

### 4.5 force 语义（问题 2）—— 重定义

| 现状 | 目标 |
|:---|:---|
| `force=true` = 跳过引用检查 | `force=true` = **确认级联**（不跳过任何步骤，全量执行迁移+级联停用） |

**为什么**：原语义与引用检查互斥矛盾——"强制删除"直接制造悬空；重定义后 force 只是"确认执行完整安顿流程"，不再产生垃圾数据。

### 4.6 错误语义（问题 7）—— 统一 400

| 语义 | 场景 |
|:---|:---|
| **400** `InvalidParameterException` | 分类不存在或已停用（参数错误）——与首页房间筛选 `_validate_active_category_or_raise`（`homepage_search.py:32-43`）现状一致 |
| **404** `NotFoundException` | 资源本身不存在（如专家 ID 无效） |

**为什么 400 而非 404**：与现状代码行为对齐（首页已抛 400），避免引入新的不一致；400=状态/参数问题、404=资源问题，前端可区分引导。

### 阶段 1：删除事务重构（问题 2、3）

**解决的问题**：force 删除后引用悬空无兜底；停用一级分类后子分类孤儿；"其他"兜底分类误删风险。

**具体改动**：
1. **`delete_category` 重写**为单事务，操作序列：
   - 统计（阶段 0 函数）→ 有引用且非 force → 409（结构化清单）
   - force（语义=确认级联，不跳过步骤）：
     a. 专家 `category_id` → `target_category_id` 或"其他"（默认）
     b. 科室 `category_id` → 同上（当前代码完全不处理科室）
     c. `DELETE FROM live_room_categories WHERE category_id IN (子树)`（弱引用直接解除）
     d. 级联软删子树（分类 + 全部 active 子分类）
     e. commit，返回迁移统计（`migrated_expert_count / department_count / removed_room_link_count / disabled_child_count`）
2. **禁删规则**：**`slug == "other"`**（V1.1 修正：不用 `name == "其他"`——name 可被 `CategoryUpdate.name` 改名，改名后规则静默失效；slug 有唯一语义且不随 display_name 方案改动）的分类在 service 层直接拒绝删除（兜底依赖保护）
3. `app/api/v1/endpoints/content_management.py:delete_category`（471-509 行）增加可选 `target_category_id` 查询参数透传
4. 公开分类列表 `get_categories`（`content_management.py:340-344`）加防御过滤：**父分类不可见（不存在或 inactive）的子分类不返回**
5. **房间关联语义统一（V1.1 补充）**：传了 `target_category_id` 时 `live_room_categories` **迁移到 target**（保留房间分类信息）；未传时**解除关联**（弱引用）。与阶段 3 迁移端点语义对齐，避免两入口行为不一致

**为什么这样实现**：删除语义定义为"停用整棵子树 + 引用一次性安顿"，与软删哲学一致（可整体恢复）；迁移目标默认"其他"依赖禁删规则保障（不删兜底则迁移目标恒存在）。

**风险与缓解**：
| 风险 | 缓解 |
|:---|:---|
| **破坏性变更**：`force=true` 语义变化，管理前端需同步 | 实施前与前端确认调用方；语义从"跳过检查"变"确认级联"更安全 |
| 事务跨 3 表写操作 | 复用现有 `try/except rollback` 骨架；每步 flush 后校验 |
| 迁移目标"其他"不存在 | 禁删规则 + 迁移前校验兜底存在，缺失则报错阻断 |

**预期效果**：删除后全系统零悬空引用——专家不再永久失联、直播间不留垃圾关联、科室不再挂死；分类树永远"整体可见或整体下线"；删除影响面完全可审计。

**验收清单**：
```
□ 删除含"3 专家+1 科室+2 房间+2 子分类"的一级分类（force）
  → 专家科室落入"其他"、房间关联清零、2 子分类同步 inactive、返回统计
□ 前台分类树无孤儿节点；按父分类与按子分类筛选行为一致
□ DELETE /categories/{其他} → 4xx（禁删兜底）
□ 重新启用分类 → 引用关系（若未迁移的）恢复可见
```

### 阶段 2：层级校验加固（问题 5）

**解决的问题**：update 路径可把一级分类（带子分类）降级造出三层；循环检测只排自身（注释与实际不符）。

**具体改动**（`_validate_category_hierarchy`，`content_management_service.py:76-118`）：
1. 新增规则 4：`existing_category_id` 存在且 `parent_id` 变更时，查询该分类是否有 active 子分类——有则抛 `InvalidParameterException("该分类下有 N 个启用子分类，请先迁移或停用子分类后再调整层级")`
2. 规则 2 补全：循环检测从"仅自身"扩展为"自身 + 全部子孙"（复用 `get_category_descendant_ids`）
3. 提升方向（`parent_id: None`）不受限——一级↔二级双向都过校验

**为什么这样实现**：不变量集中定义（3.3 节五条规则），创建/更新/删除/合并全路径调用同一函数；"先停用子分类再调层级"是合法路径，校验必须放行。

**风险与缓解**：风险低。纯新增校验规则，只影响非法操作；注意合法路径（先停用子分类再调层级）必须通过。

**预期效果**：三层结构在全部路径不可达；"定时炸弹"拆除，依赖两层假设的匹配算法、前端树、递归查询重新成立。

**验收清单**：
```

□ 先停用 9 个子分类再调整 → 成功
□ 把"心内科"提升为一级 → 成功
□ 循环检测：A 的 parent 设为 A 的子孙 → 拒绝
```

### 阶段 4：分类合并端点（问题 4、15）

**解决的问题**：重复/相近分类无法合并；与科室合并联动一致性。

**具体改动**：
1. 新端点 `POST /api/v1/admin/categories/merge`，body：`{source_id, target_id, attach_children: bool = false, dry_run: bool = false}`
2. service `merge_categories` 单事务，5 类数据处理：
   - `experts.category_id`：**仅 `WHERE category_id = source_id`（源分类自身）** → target。⚠️ **V1.1 修正**：合并不删子分类（子分类保留并挂到 B 下/提升一级），子分类下的专家仍指向子分类、**不得迁移**；与阶段 1 删除（级联停用整棵子树、专家全迁）范围不同，勿复用同一迁移范围
   - `expert_departments.category_id`：source → target（不迁移则 RESTRICT 下 source 永不物理删除）
   - `live_room_categories`：source 行 → target，target 已有关联删 source 行；`is_primary` 冲突保留 target 行
   - 子分类：`attach_children=false`（默认）挂到 target 下（过阶段 2 校验）；`true` 提升为一级
   - 软删 source（复用阶段 1 删除路径，双保险）
3. **科室合并联动（问题 15）**：合并前检查"专家 `category_id` 与所属科室 `category_id` 不一致"的专家数量，响应中提示并一并校正——保证"科室→专家→分类"三层引用链最终一致
4. `dry_run=true` 只返回迁移统计不落库；操作写审计日志（⚠️ **V1.2 明确载体**：沿用 service 层 `logger.info/warning` 记录模式——`room_service.py:66` 已有先例，全仓无通用审计表，**暂不建审计表**；若运营后续要求可追溯查询再评估建表）
5. **常量/历史同步**：⚠️ **V1.1 修正**：~~source 名写入 target 的 synonyms~~——`synonyms` 是 `expert_departments` 表的字段，**`categories` 表无此列**，科室合并模式不可照搬。合并后 source 为**软删**（数据行保留 `is_active=False`，名字未丢），历史记录写审计日志即可；`category_constants.py` 注释约定治理操作不反向写常量（P5 原则）
6. **子任务 4.1：科室→分类一致性校验下沉 create/update 入口（V1.2 新增，问题 15 闭环关键）**——⚠️ 终审发现：合并端点的校正会被日常操作持续打回，问题 15 修复不闭环。代码验证事实：`update_expert`（`expert_service.py:926-992`）只校验 `category_id` 存在且启用（954-963 行），**不校验与科室一致**；`ExpertUpdate` 允许单独传 `category_id` 或 `department_id`（`schemas/experts.py:59-60`），双向都能制造不一致：
   - `create_expert`：已从 `department_id` 自动解析 `category_id`（schema 注释），保留；**若同时显式传两者且不一致 → 400**（消除歧义）
   - `update_expert` 新增两条规则：
     a. 传 `category_id` 且专家已有 `department_id` 时，校验 `category_id == 科室.category_id`，不一致 → 400（提示"分类变更请通过科室变更完成"）
     b. 传 `department_id`（未传 `category_id`）时，自动重解析 `category_id` 跟随新科室（与创建路径行为一致）；若同时传两者以科室为准并告警
   - 规则落点在 service 层（`expert_service.py`），复用 `create_expert` 已有的解析逻辑，禁止绕过（CSV 导入走 `_resolve_department_and_category`，天然一致）

**为什么这样实现**：复用 `merge_departments` 已验证的"专家 category_id 随迁移同步"模式升级到分类维度；`dry_run` + 审计日志是高频误操作的必要护栏；与科室合并联动处理保证三层引用链一致；**子任务 4.1 把一致性从"合并时校正"升级为"全路径不变量"（P3 原则延伸）**——否则合并端点修好的数据会被日常 update 随时重新打破。

**风险与缓解**：
| 风险 | 缓解 |
|:---|:---|
| 数据面最多（5 类），`is_primary` 冲突、子分类参数需决策 | `dry_run` 预览 + 单事务 + 审计日志 |
| 与 `merge_departments` 操作顺序（先合并科室再合并分类）产生中间态 | 合并端点自动检测并校正不一致专家（问题 15）；文档明确"先分类后科室"建议 |
| 误操作风险高 | 校验：source ≠ target、均存在且启用、target ≠ "其他"、**target ∉ source 子树**（V1.1 补充：防循环引用中间态） |
| **update_expert 日常路径持续制造科室/专家分类不一致（V1.2 新增）** | **高** | **中** | 子任务 4.1：校验下沉 create/update 入口，双向规则 + 与导入路径天然一致 |

**预期效果**：合并原子、可审计、无悬挂；治理成果持久化（P5 种子策略）；与科室合并形成完整工具链，双向对齐；**专家分类一致性成为全路径不变量，任何入口（创建/更新/合并/迁移/导入）都无法制造漂移**。

**验收清单**：
```

□ dry_run=true → 无任何写操作
□ 合并后 seed 重跑 → source 不复活
□ 存在科室/专家分类不一致时 → 响应提示并校正
□ 子任务 4.1：update_expert 只改 category_id 且与科室不一致 → 400
□ 子任务 4.1：update_expert 只改 department_id → category_id 自动跟随新科室
□ 子任务 4.1：create_expert 同时传 category_id + department_id 且不一致 → 400
□ 子任务 4.1：CSV 导入路径不受影响（走 _resolve_department_and_category）
```

### 阶段 5：错误语义统一（问题 7）

**解决的问题**：按停用/不存在分类筛选专家时 `return [], 0` 静默（`experts.py:250-252`）。

**具体改动**：

2. 管理端 `get_experts_multi_and_total`（355-358 行）保持宽松（管理端允许查停用分类），仅公开端收紧
3. 语义约定：400 = 分类已停用/不存在（参数错误）；404 = 资源本身不存在

**为什么这样实现**：与首页房间筛选现状（`homepage_search.py:32-43` 抛 400）对齐，避免引入新不一致；管理端保留宽松避免影响后台操作。

**风险与缓解**：风险低。公开接口行为变更（空列表 → 400），需确认前端对 400 有通用处理（项目全局错误处理框架已存在）；管理端不受影响。

**预期效果**：前后端行为一致；用户得到明确提示而非静默空白；错误类型可区分、可引导。

**验收清单**：

### 阶段 6：命名合规 + 唯一性处理（问题 9、10、14）

**解决的问题**：分类名不符合名录；一级科目缺失；同名不同级时匹配算法 `MultipleResultsFound`。

**具体改动**（⚠️ V1.1 拆两步实施）：
- **步骤 A（问题 14，先行）**：同名歧义消除——动数据，独立可发布
- **步骤 B（问题 9/10，后行）**：名录对齐 + 科目补录——动常量与策略

**步骤 A 具体改动**：
1. 全仓 grep `Category.name ==` 按名查询点，统一到一个 helper（`get_category_id_by_name(db, name, prefer_sub=True)`）——已确认存在多处：[expert_service.py:342-357](expert_service.py:342-357) 启发式回退、397-402 "其他"兜底、seed.py 匹配等
2. `_match_broad_category` 与 `DEPARTMENT_CATEGORY_MAP` 目标名改为标准名；匹配命中后按 `parent_id` 限定层级（二级优先）查分类，消除同名歧义
3. 迁移：`categories` 表新增 `display_name` 列；回填存量 `display_name = name`（新迁移文件 V12）

**步骤 B 具体改动**：
4. `CategoryItem` schema 增加 `display_name`；C 端展示逻辑切到 `display_name`（NULL 回退 `name`）；`name` 逐步对齐标准名（新增/改名操作走 `name=标准名, display_name=口语名`）。⚠️ **V1.2 明确发布节奏**：**两步独立发布**——第一步后端先发布（新增字段 + 匹配算法切换，`name` 值不动，老客户端向后兼容）；第二步前端切展示逻辑（读 `display_name`）。两步之间禁止改 `name` 存量值，避免"后端换了前端没换"的中间态
5. **标准名校验规则（V1.1 补充）**：`standard=true` 的分类 `name` 必须命中名录标准名清单（`category_constants.py` 维护）；`standard=false` 放行任意合规名。校验放 service 层 `create_category` / `update_category`

### 阶段 7：技术债（问题 11、12、13）

**解决的问题**：SQL 拼接 UUID；is_primary 规则未启用；种子漂移残余风险；专家多对一决策。

**具体改动**：
1. `homepage_search.py:439`：`descendants_str` 字符串拼接 → 参数化（asyncpg 数组参数 `:ids` 绑定）
2. `is_primary`：启用强校验（`set_live_room_categories` 中每房间主分类唯一、主分类必在关联列表——`LiveRoomCategoriesSetRequest` 模型校验已有基础），语义定为"前台展示默认标签"
3. seed 幂等强化：已跳过已存在项（现状满足），补测试固化；`DEPARTMENT_CATEGORY_MAP` 目标名运行时存在性校验，缺失降级子串匹配（问题 13 收尾）
4. 专家多对一：**维持现状**，`knowledge/decisions.md` 记录设计决策（重构成本高、收益不明确）

**为什么这样实现**：参数化消除注入面；is_primary 从标记变真实约束；运行时校验让种子与治理永不冲突（P5 原则收尾）；多对一升级成本高收益不明，记录决策避免反复讨论。

**风险与缓解**：风险低-中。is_primary 强校验可能暴露存量脏数据（V11 只回填基线）——实施前先跑数据体检脚本，发现多主分类先修复再启用。

**数据体检脚本（V1.1 补充，阶段 7 上线前执行）**：全量引用完整性体检，把治理问题在代码修复前先摸清底数——
```
① 孤儿分类：is_active=True 且父分类 inactive 或不存在
② 悬空 category_id：experts.category_id / expert_departments.category_id 指向不存在或已停用分类
③ 多主分类：同一房间存在多个 is_primary=true
④ 无主分类：关联分类>0 但 is_primary 全 false
⑤ 存量脏数据：experts.category_id 与其科室 category_id 不一致的专家
```

**预期效果**：注入面消除；主分类语义明确；治理成果持久化；技术决策可追溯。

**验收清单**：
```
□ 设置房间分类时多主分类 → 400
□ seed 在治理过的库上重跑 → 无复活、无覆盖、无报错
□ 首页房间接口 SQL 无字符串拼接
□ 存量数据体检：无房间存在多个 is_primary=true
```
