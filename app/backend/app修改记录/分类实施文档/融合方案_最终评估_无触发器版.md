> 评估日期：2026-06-23
> 基于全项目代码审读、实际数据库审计、11 个方案版本迭代

## 一、当前项目约束条件

| 约束 | 值 | 对方案选择的影响 |
|:----|:---|:---------------|
| 数据库 | PostgreSQL 15, SQLAlchemy 2.0 + asyncpg | 部分索引、JSONB、平铺 UPSERT 可用 |
| 触发器先例 | 全项目零触发器 | 不引入触发器，保持应用层模式一致 |
| 迁移工具 | 无 Alembic，手动 SQL | 迁移脚本需编号前缀 + 幂等化 |
| 前端 | Vue 3 + Element Plus，MVP 阶段 | 前端改动量可控（新页面可独立开发） |
| 团队规模 | 小团队（git 历史显示少量提交者） | 方案不能过度复杂 |
| 数据量 | 384 专家、796 房间、41 个 department 值 | 当前数据量小，迁移成本低 |
| 业务场景 | 医学教育直播 | 分类需要医学专业性 + 可审计 |

## 二、最终方案定稿

### 方案全名
**A2+C 融合方案：受控词表自适应补全（无触发器版）**

### 一句话描述
categories 运行时只读（20 个根分类锚定） + expert_departments 自适应创建 is_verified=false + 应用层显式同步。

### 与约束条件的对应

| 约束 | 融合方案的对应 |
|:----|:-------------|
| 零触发器 | ✅ 改用应用层显式 UPDATE |
| 手动 SQL 迁移 | ✅ 7 步迁移，每步幂等 + 编号前缀 |
| 前端 MVP | ✅ 4 个新页面 + 2 个改造，可独立开发 |
| 小团队 | ✅ 核心改动集中在 3 个 Service 方法 |
| 小数据量 | ✅ Dry-Run 迁移 + 单事务均可安全执行 |
| 医学专业 | ✅ 20 个根分类 + 40 条别名表保证本体领域覆盖 |

## 三、与传统方案对比

### 对比 1：当前系统（不动）

| 维度 | 当前系统 | 融合方案 |
|:----|:-------|:--------|
| department | 自由文本 VACHAR 120 | FK → expert_departments 受控词表 |
| 新科室处理 | ValueError 中断导入 | 自动创建 + 启发式匹配到正确大类 |
| categories 纯净 | 261 条含 241 垃圾 | 运行时只读，20 条根分类 |
| NULL category_id | 384 人均已补（历史修复后）| 不再允许 NULL（"其他"兜底） |
| 筛选可见性 | 匹配不到就不可见 | 匹配不到也自动创建，及时可见 |
| 同义词归并 | 无 | synonyms 自学习 |
| 开发量 | 0 | 6-9 人天 |

**结论**：当前系统的问题是**数据模型有根本缺陷**（自由文本 + 无受控机制），放着不动会持续累积脏数据。方案必须改。

### 对比 2：简化版 A2（纯分层）

| 维度 | 简化版 A2 | 融合方案 |
|:----|:---------|:--------|
| categories | 分层 + 只读 | 分层 + 只读（一致） |
| department | **保留不动**（只是前端不显示） | **升级为受控词表 FK** |
| 新科室 | 落入"其他"（筛选不可见）| 自动创建 is_verified=false（筛选可见） |
| 运维 | 维护别名表 | 维护别名表 + 每周 5 分钟审核 |

**结论**：简化版 A2 的最大弱点是 department 仍然是自由文本——数据不一致的问题只是被"前端不显示"掩盖了，数据库层面没有解决。融合方案多做了 expert_departments 表，彻底解决了这个根本问题。

### 对比 3：纯 C 方案（受控词表只读）

| 维度 | 纯 C | 融合方案 |
|:----|:-----|:--------|
| expert_departments | ✅ 有 | ✅ 有 |
| categories 只读 | ✅ | ✅ |
| 新科室 | ❌ 精确匹配不到 → 归"其他" | ✅ 自动创建 is_verified=false |
| 导入容错 | ❌ 匹配不到 → 中断 | ✅ 匹配不到 → 自动创建 |

**结论**：纯 C 方案的新科室"黑洞"问题是融合方案直接弥补的。融合方案只要多做一个"匹配不到时自动创建"的写操作，就可以解决纯 C 方案最大的运营痛点。

### 对比 4：抖音纯算法模式

| 维度 | 抖音 | 融合方案 |
|:----|:----|:--------|
| 分类导航 | 无 → 纯推荐 | 有 → 医学专科 Tab 浏览 |
| 用户操作 | 只看算法推荐 | 可主动搜索 + 按科室浏览 |
| 适合医学吗 | ❌ | ✅ |

**结论**：不适合。医学教育需要精确的专科导航，不能只靠推荐。

## 五、最终判决

**融合方案就是这个项目的最佳方案。**

不是因为"它完美无缺"，而是在给定的约束下（全项目零触发器、手动 SQL 迁移、小团队、医学专用），**它是四种方案中唯一同时满足三个关键需求的**：

1. **不引入触发器**（全项目保持一致的应用层模式）
2. **新科室不中断导入**（自适应创建 + 启发式匹配）
3. **categories 表不被污染**（运行时 100% 只读）

**代价**：多做了 expert_departments 表 + 41 条种子数据 + 7 步迁移

**收益**：department 从自由文本变为受控词表，`department ↔ category_id` 不一致的可能性从"代码层约束"降为"数据库 FK 约束保证"。这在医学教育场景中是值得的——一条错误的科室分类可能意味着一位心脏病专家被放在骨科 Tab 下。
