## 二、各问题修复方案

### P0-2：专家分类漂移路径 ✅ **已提前实现**

**当前问题**：

```
merge_departments:
  transfer_experts_to_department(source_id, target_id)
  → UPDATE experts SET department_id = target_id  ← 改了
  → 但 category_id 没改！                          ← 缺失

通用更新接口 PATCH /admin/expert-departments/{id}:
  update_department(db, department_id, department_data)
  → 允许改 ExpertDepartment.category_id
  → 但不会同步 experts.category_id               ← 缺失
```

**修复**：

| # | 文件 | 改动 | 行数 |
|:--|:---|:---|:---:|
| 1 | `services/expert_service.py` `merge_departments` | `transfer_experts_to_department` 之后，若 `source.category_id != target.category_id`，调用已有 `update_experts_category_by_department`（或等价批量 UPDATE）将专家的 `category_id` 同步为目标科室的 `category_id` | +5 |
| 2 | `api/v1/endpoints/expert_departments.py` `update_department` | 通用更新接口：更新前先查旧的 `category_id`，与传入的 `department_data.category_id` 比较；若不同，执行 `UPDATE experts SET category_id = :new_id WHERE department_id = :dept_id` | +10 |

> **说明**：Fix #1 不改 `transfer_experts_to_department` 函数签名（它只收 UUID），而是在 `merge_departments` 的调用方已有 `source` 和 `target` 完整对象，直接判断跨分类后用批量 UPDATE 同步。Fix #2 在 API 层通过比较新旧值判断是否需要同步——不依赖 CRUD 层返回标记（简化实现，消除冗余）。

**风险**：极低。两个改动都是纯增量——原有行为不变，追加同步步骤。

**工时**：1h。

### P0-3：新旧分类语义统一 ✅ **已修复**

**当前问题**：

```
存量专家：category_id = "普通外科".UUID（二级）
新导入未知科室：_match_broad_category → 匹配不到 → 自动创建 → category_id = "外科".UUID（一级）
→ 不同路径进来的心内科医生，落在不同层级
```

**修复原则**：**所有专家的 category_id 统一指向二级分类，一级纯用于导航聚合。**

**修复**：

| # | 文件 | 改动 |
|:--|:---|:---|
| 1 | `expert_service.py` `_match_broad_category` | 匹配到二级时返回**二级名**（不是一级名）：`return (normalized, cat_name)`；只有一级叶子节点才返回自身 |
| 2 | `api/v1/endpoints/expert_departments.py` `_resolve_department_and_category` 调用处 | 调整 category 名称查找逻辑——如果查不到，向上查 parent 一级 |

**关键逻辑变更**：

```python
# _match_broad_category 改法
for cat_name in ALL_CATEGORY_NAMES_SORTED:  # L2 first, L1 second
    if cat_name in normalized:
        parent = CATEGORY_PARENT_MAP.get(cat_name, cat_name)
        # 改前: return (normalized, parent)          ← 始终返回一级名
        # 改后: return (normalized, cat_name)         ← 返回匹配到的分类名本身
        if cat_name == parent:
            return (normalized, cat_name)             # 一级叶子节点
        else:
            return (normalized, cat_name)             # 二级 → 返回二级名
```

### P0-1：父分类聚合子分类数据 ✅ **已提前实现**

**当前问题**：筛选"外科"`category_id` 时只查 `experts.category_id == 外科.UUID`，不包含子分类。

**修复——影响 4 个查询点**：

| # | 文件:行 | 查询类型 | 当前 | 改为 |
|:--|:---|:---|:---|:---|
| 1 | `crud/experts.py:235` 公开专家列表 | `Expert.category_id == category_id` | 精确等值 | `Expert.category_id IN (WITH RECURSIVE sub AS ...)` |
| 2 | `crud/experts.py:354` 管理端专家列表 | 同上 | 同上 | 同上 |
| 3 | `crud/homepage_search.py:396-401` 首页直播间 | `EXISTS (SELECT 1 FROM live_room_categories WHERE category_id = :cid)` | 精确等值 | `category_id IN (子ID列表)` |
| 4 | `crud/content_management.py:251` 分类统计 | `Expert.category_id.in_(cat_ids)` | 查完原始数据后，Python 层构建 `parent_id → children` 索引，子分类计数累加到父分类（见下方详解） |

**实现方式**：创建一个通用辅助函数，避免四处重复：

```python
# crud/content_management.py 新增
async def _get_descendant_category_ids(db: AsyncSession, parent_id: uuid.UUID) -> List[uuid.UUID]:
    """获取一个分类及其所有子孙分类的 ID 列表"""
    result = await db.execute(
        text("""
            WITH RECURSIVE sub AS (
                SELECT id FROM categories WHERE id = :parent_id
                UNION ALL
                SELECT c.id FROM categories c JOIN sub ON c.parent_id = sub.id
            )
            SELECT id FROM sub
        """),
        {"parent_id": parent_id}
    )
    return [row[0] for row in result.fetchall()]
```

**风险**：纯增量。不影响非 category_id 筛选的查询。WITH RECURSIVE 在 PostgreSQL 上性能良好——分类树深度 ≤2，递归最多 11+16=27 条。

> **说明**：分类统计（#4）的改造方式与前 3 处不同——它需要的不是"筛选"，而是"先算出每个叶子分类的真实计数，再把子分类计数累加到父分类"。如果用 CTE 改变查询语义，会把直接关联和递归关联混在一起无法区分。正确做法：① 保持当前直接计数查询不变（`Expert.category_id.in_(cat_ids)`）；② 查完后在 Python 层构建 `parent_id → children` 映射；③ 遍历父分类，将其所有子分类的 `expert_count` 累加到自身。

**工时**：1.5h。

### P1-4：直播间主分类自动递补 ✅ **已修复**

```sql
-- 为每个房间的第一个分类设为主分类（当前全部 is_primary=false）
UPDATE live_room_categories lrc1
SET is_primary = true
WHERE lrc1.created_at = (
    SELECT MIN(lrc2.created_at)
    FROM live_room_categories lrc2
    WHERE lrc2.room_id = lrc1.room_id
)
AND NOT EXISTS (
    SELECT 1 FROM live_room_categories lrc3
    WHERE lrc3.room_id = lrc1.room_id AND lrc3.is_primary = true
);
```

### P1-6：分类树治理约束（最低限度）✅ **已提前实现**

**原则**：不做完整 RBAC 治理系统，只加最关键的 3 个校验。

| # | 文件 | 校验 | 场景 |
|:--|:---|:---|:---|
| 1 | `services/content_management_service.py` `update_category` | `parent_id` 不能指向自己：`parent_id == existing.id → 拒绝` | **仅 update**（create 时不存在自引用） |
| 2 | 同上 | 如果 `parent_id` 不为 None，被引用的父分类 `is_active` 必须为 true | create + update |
| 3 | 同上 | 限制最多 2 层：`parent.parent_id is not None → 拒绝`（因为父分类已经是二级，不能再往下挂三级） | create + update |
| 4 | 同上 | update 时 `parent_id` 不能设为二级分类的 ID——因为二级分类本身不是一级根节点，挂到它下面等于成为三级 | **仅 update**（create 时由规则 3 覆盖） |

```python
# create_category 校验
if category_data.parent_id is not None:
    parent = await db.get(Category, category_data.parent_id)
    if not parent or not parent.is_active:
        raise InvalidParameterException("父分类不存在或已禁用")
    if parent.parent_id is not None:
        raise InvalidParameterException("该父分类已是二级分类，不能再创建子分类（限2层）")

# update_category 校验（在 create 基础上追加）
if category_data.parent_id is not None:
    if category_data.parent_id == existing.id:
        raise InvalidParameterException("不能将分类的父节点设为自己")
    if parent.parent_id is not None:
        raise InvalidParameterException("不能挂到二级分类下（限2层）——目标已是子分类")
```

**工时**：0.5h。
