## 二、覆盖的 10 个核心业务场景

### 场景 1：管理员手动创建专家
```
输入：name="张医生", department_name="乳腺外科"
  → P1: 精确匹配 expert_departments.name = "乳腺外科"
  → 命中 → department_id=xxx, category_id=普通外科
  → Expert 创建完毕，前端「普通外科」Tab 下立即可见 ✅
```

### 场景 2：管理员手动创建专家（新科室）
```
输入：name="李医生", department_name="结构性心脏病组"
  → P1: 精确匹配 → 未命中
  → P1b: 同义词匹配 → 未命中
  → P2: 医学词匹配 '心脏' → 心内科
  → UPSERT: INSERT INTO expert_departments 
    (name='结构性心脏病组', category_id=心内科, is_verified=false)
  → Expert 创建完毕，前端「心内科」Tab 下立即可见 ✅
  → 科室「结构性心脏病组」在管理后台"待审核"列表中可见 ✅
```

### 场景 3：CSV 批量导入 100 个专家
```
遍历 100 行，每行：
  ├── 40 个科室名已存在于 expert_departments → 直接匹配 ✅
  ├── 30 个科室名命中同义词                  → synonyms 匹配 ✅
  ├── 20 个科室名通过医学词匹配自动创建       → 自动创建 ✅
  └── 10 个科室名完全无法匹配 → 归入"其他" → 后续从 unmapped API 发现

整批导入不中断，不因单行匹配失败而回滚 ✅
导入后运营收到 is_verified=false 的科室列表（含自动分类）
```

### 场景 4：用户端分类 Tab 筛选
```
用户点击「心内科」Tab
  → GET /experts?category_id=心内科UUID
  → WHERE experts.category_id = 心内科UUID
  → 返回所有 category_id=心内科 的专家
     （包括那些通过自动创建的 is_verified=false 科室归入心内科的专家）
  → 筛选结果不遗漏任何专家 ✅
  → Tab 栏始终只显示 20 个根分类（干净） ✅
```

### 场景 5：用户端搜索专家
```
搜索框输入 "乳腺"
  → WHERE experts.name ILIKE '%乳腺%'
    OR experts.hospital ILIKE '%乳腺%'
    OR experts.department_id IN (
        SELECT id FROM expert_departments WHERE name ILIKE '%乳腺%'
    )
  → 所有姓名/医院/科室名中含"乳腺"的专家被返回 ✅
  → 不再依赖 experts.department 自由文本 ❌（字段已删除）
```

### 场景 6：前端专家详情页展示
```
GET /experts/{id}
  → 响应包含:
    ├── department_name: "乳腺外科"      ← 来自 expert_departments.name
    ├── department_id: xxx               ← 受控词表的 UUID
    ├── category_id: xxx                 ← 普通外科的 UUID
    └── category_name: "普通外科"        ← 来自 categories.name
  → 前端展示 "乳腺外科 / 普通外科" ✅
  → 不再依赖不存在的 experts.department 字段 ✅
```

### 场景 7：前端直播间卡片展示
```
GET /rooms
  → LEFT JOIN live_room_categories lrc ON lrc.room_id = rooms.id AND lrc.is_primary = true
  → LEFT JOIN categories c ON c.id = lrc.category_id
  → 响应包含 primary_category_name: "心内科"
  → 前端展示真实的分类名，而非硬编码 "--" ✅
```

### 场景 8：管理员审核自动创建的科室（is_verified=false 列表）
```
GET /admin/expert-departments?is_verified=false
  → 返回: ["结构性心脏病组", "冠心病介入组", ...]
  → 按关联专家数降序排列 ✅
  
管理员操作:
  ├── [Approve] → is_verified=true（升级为标准科室）✅
  ├── [Merge]   → 合并到已有科室，源名称吸入同义词列表 ✅
  └── [Edit]    → 修改 category_id（触发器同步到所有关联专家）✅
```

### 场景 9：管理员修正错误匹配
```
管理员发现 "骨肿瘤科" 被错误归入 "肿瘤科"
  → 修改 expert_departments.category_id 从 "肿瘤科" → "骨科"
  → 触发器自动执行:
      UPDATE experts SET category_id = '骨科' WHERE department_id = '骨肿瘤科'
  → 所有关联专家的 category_id 即时更新 ✅
  → 前端 Tab 筛选立即生效 ✅
```

### 场景 10：同义词自动消除 - 连续导入同一个科室的两种写法
```
第1次导入: "冠脉介入组"
  → P2: '心'→心内科 → 自动创建 (is_verified=false)
  
第2次导入: "冠状动脉介入组"
  → P1: 精确匹配 → 未命中
  → P2: '心'→心内科 → 自动创建另一个 (is_verified=false)
  
管理员合并:
  → source_id = "冠状动脉介入组", target_id = "冠脉介入组"
  → 自学习: target.synonyms = ["冠状动脉介入组"]（吸入源名）
  → 关联的 experts 迁移到 target
  → 删除 source 记录

第3次导入: "冠状动脉介入组"
  → P1b: 同义词匹配 → target.synonyms 包含 "冠状动脉介入组" → HIT ✅
  → 不再创建重复科室 ✅
```

## 三、相比纯 A2 和纯 C 方案的核心优势

### 优势 1：categories 表绝对纯净
纯 A2 方案：自动创建的子分类（如"骨肿瘤科"、"结构性心脏病组"）直接写入 `categories` 表。即使 `is_public=false`，也破坏了 `categories` 作为"导航分类锚点"的语义。有 5 个 Bug（正则误匹配等）可导致垃圾数据进入分类表。

融合方案：`categories` 在运行时**永不接收写入**。任何数据录入端的输入不管多不规范，都只影响 `expert_departments` 表。导航分类受保护。

### 优势 2：新科室不产生"不可见"的专家
纯 C 方案：匹配不到的科室（如"结构性心脏病组"）归入"其他"（`department_id=NULL`），该专家在分类 Tab 筛选时被归入"其他"或不可见。运营必须手动从"其他"中找到该专家并逐一分配。

融合方案：匹配不到的科室自动创建为 `is_verified=false` 的 `expert_departments` 记录，同时**自动关联正确的 `category_id`**（通过启发式匹配）。该专家在正确的 Tab 下立即可见，业务不中断。运营不需要紧急处理，可以在方便时审核。

### 优势 3：运维工作量极低
纯 A2 方案：需要"审核分类 → 合并分类 → 孤儿清理"的持续运维流程，月度维护 30min+。

纯 C 方案：需要"从'其他'中找出未映射专家 → 手动创建科室 → 逐一分配"，月度维护 30min+。

融合方案：系统自动完成了分类的归纳工作（启发式匹配）。管理员只需要：
- 定期查看 `is_verified=false` 列表
- 一键 Approve（最常见的操作）
- 偶尔 Merge 同义词（频率取决于重复科室创建频率）

月度维护时间 < 10min。

### 优势 4：受控词表自我学习，录入重复率递减
纯 A2 方案：没有同义词自学习机制。同样科室的不同写法（"冠脉介入组" vs "冠脉支架组"）每次导入都会创建新子分类。

融合方案：Merge 操作将源科室名吸入 `synonyms`→ 下次相同文本直接命中 → 停止创建重复。随使用时间增长，录入质量持续提升。类似于一个持续学习的受控词表。

## 四、剩余的问题（部分可接受，部分需要计划）

### 问题 1：启发式匹配的覆盖盲区（影响 ~5% 数据）
**状态**：⚠️ 已知，可接受

即使追加了 5 条特异性规则，仍有 ~5% 的科室无法通过 P1/P1b/P2 自动匹配（如"外科门诊"、复合名称"肝外科/超声医学科/介入超声专科"）。这些数据会归入 `expert_departments.category_id = 其他`，需要通过 `GET /admin/expert-departments/unmapped` 由运营手动处理。

**结论**：这是算法覆盖率的极限，已通过 unmapped API + 受控词表管理界面来缓解。运营定期处理即可。

### 问题 2：742 个房间无分类（不阻断，但遗留问题）
**状态**：⚠️ 已提供迁移 SQL，但需业务确认哪些房间是真实数据

796 个房间中仅有 54 个有关联分类。融合方案不涉及直播间分类的核心逻辑改动。需要在 Step 3（数据迁移）中根据房间标题/描述的关键词匹配全局分类，匹配不到的归入"其他"。

### 问题 3：触发器方案已否决
**状态**：🟢 已决策不引入触发器，改用应用层显式同步，与全项目模式一致

当前项目零触发器，全部逻辑在 Python 应用层。同步逻辑在同一个 Service 方法内显式执行 `UPDATE experts`，调试在应用日志中即可，测试不需要额外创建触发器。这是更务实的工程选择。

### 问题 4：触发器在事务回滚时的行为
**状态**：🟢 正常

PostgreSQL 的触发器在父语句的事务中运行。如果 `UPDATE expert_departments` 的事务回滚，触发器的 `UPDATE experts` 也会回滚。数据完整性由数据库保证。

### 问题 5：admin 修改 expert_departments.category_id 时的事务大小
**状态**：🟢 当前安全，未来需监控

如果管理员修改一个关联了 100 个专家的科室的 category_id，触发器会执行 100 条 UPDATE 语句。当前数据量下（最大的科室关联 27 个专家），这是毫秒级的操作。但如果未来扩展到 ~10,000 条关联专家，就需要注意事务超时设置。

### 问题 6：前端需要开发新页面（待规划）
**状态**：🟡 中，需排期

融合方案要求前端新增：
1. **科室管理页面**（`/admin/expert-departments`）：列表 + CRUD
2. **未映射专家页面**（`/admin/expert-departments/unmapped`）：列表 + 审批/合并操作
3. **Merge 操作 UI**：选中两个科室 → 合并 → 确认

但这些页面不是阻塞项——方案可以在没有前端 UI 的情况下运行（管理员通过 SQL 或 API 操作）。

### 问题 7：categories 表中的 241 个测试分类需要清理
**状态**：🟡 中，独立任务

当前 261 个分类中有 241 个是测试遗留（`test_cat_*`、`分类_*` 等）。这些数据不影响融合方案的核心逻辑（它们作为 `parent_id=NULL` 的根分类存在，不会因为 migration 而产生副作用），但应在 Step 7 中清理。

## 五、最终判断矩阵

| 维度 | 纯A2 | 纯C | A2+C融合 | 说明 |
|:-----|:----:|:---:|:--------:|:-----|
| categories 纯净度 | 🔴 | 🟢 | 🟢 | 融合方案锁定在只读 |
| 新科室立即可见 | 🟢 | 🔴 | 🟢 | 融合方案自动创建+自动分类 |
| 导入不中断 | 🟢 | 🔴 | 🟢 | 融合方案不因匹配失败中断 |
| 搜索命中率 | 🟢 | 🟡 | 🟢 | 仅 5% 覆盖盲区 |
| 运维时间 | 🔴 | 🟡 | 🟢 | 月度维护 <10min |
| 数据可审核 | 🟡 | 🟢 | 🟢 | is_verified 优于 is_public |
| 长期数据膨胀 | 🔴 | 🟢 | 🟢 | 同义词自学习防止重复创建 |
| 前端必要改动 | 🟡 | 🟡 | 🟡 | 3 个新页面，可并行开发 |
| 当前数据适配性 | 🟡 | 🟢 | 🟢 | 41 个现有值生成别名表 |
| 10-100倍扩展性 | 🟡 | 🟢 | 🟢 | 平铺表读写均优 |

**结论**：融合方案是三种方案中**唯一同时满足"输入容错"和"结构纯净"的架构**。纯 A2 的脏数据问题和纯 C 的黑洞问题在融合方案中同时被消除。剩余的 7 个问题中，5 个是已知可接受的（5%覆盖盲区、触发器兼容性、事务大小等），1 个是独立异步任务（测试分类清理），1 个是需要排期的前端开发（管理界面）。
