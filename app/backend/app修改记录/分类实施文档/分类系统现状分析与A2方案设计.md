## 第三章：A2 方案详细设计

### 3.1 设计原则

```
1. 单一真相源：专家的科室信息只存在一个地方（category_id → categories.name）
2. 分层组织：大类（15个）稳定不变，子分类按需自动创建
3. 自动兜底：新科室自动匹配到大类并创建子分类，管理员不做手动映射
4. 前端兼容：Tab 栏保持 15 个大类，子分类仅影响详情展示和筛选展开
5. 渐进实施：不一次大重构，分阶段上线
```

### 3.2 数据库改动

#### categories 表加 parent_id

```python
class Category(Base):
    __tablename__ = "categories"

    id = Column(UUID, primary_key=True, default=uuid.uuid4)
    parent_id = Column(
        UUID(as_uuid=True),
        ForeignKey("categories.id", ondelete="RESTRICT"),
        # 使用 RESTRICT 而非 SET NULL：防止删除父分类时子分类"篡位"变成根分类
        nullable=True,
        comment='父分类ID。NULL=根分类（大类/一级分类）；非NULL=子分类（具体专业方向）'
    )
    name = Column(String(100), nullable=False, comment='分类名称')
    slug = Column(String(120), nullable=True, comment='URL标识符。子分类建议拼接父分类slug，如 cardiology-arrhythmia')
    icon = Column(String(255), nullable=True)
    description = Column(Text, nullable=True)
    sort_order = Column(Integer, nullable=False, default=0)
    is_active = Column(Boolean, nullable=False, default=True)
    is_public = Column(Boolean, nullable=False, default=True,
                       comment='是否在前台公开显示。False=内部使用，不显示在分类下拉列表')
    created_at = Column(TIMESTAMP(timezone=True), nullable=False, server_default=func.now())
    updated_at = Column(TIMESTAMP(timezone=True), nullable=False, server_default=func.now(), onupdate=func.now())
```

`slug` 说明：子分类的 slug**不设置全局唯一约束**。子分类 slug 应拼接父分类 slug 前缀（如 `cardiology-arrhythmia`）以确保唯一。根分类 slug 仍保持全局唯一（由 `uq_root_category_name` 部分索引间接保证，或通过应用层校验）。

#### 唯一约束 — 使用 PostgreSQL 部分索引

⚠️ **PostgreSQL 行为说明**：`NULL ≠ NULL`，因此 `UniqueConstraint('parent_id', 'name')` 无法约束根分类（`parent_id IS NULL`）的 name 唯一性。必须使用**部分索引**。

```python
__table_args__ = (
    # 根分类（parent_id IS NULL）：name 全局唯一
    Index('uq_root_category_name', 'name', unique=True,
          postgresql_where=text("parent_id IS NULL")),
    # 子分类（parent_id IS NOT NULL）：同父类下 name 唯一
    Index('uq_sub_category_name', 'parent_id', 'name', unique=True,
          postgresql_where=text("parent_id IS NOT NULL")),
    # 常规索引
    Index('idx_categories_parent_id', 'parent_id'),
    Index('idx_categories_sort_order', 'sort_order'),
    Index('idx_categories_is_active', 'is_active'),
)
```

#### 新建迁移 SQL

```sql
-- V2_add_category_hierarchy.sql

-- 1. 添加 parent_id 自引用外键（RESTRICT：防止误删父分类导致子分类被提升为根分类）
ALTER TABLE categories
ADD COLUMN parent_id UUID REFERENCES categories(id) ON DELETE RESTRICT;

-- 2. 添加 is_public 字段
ALTER TABLE categories
ADD COLUMN is_public BOOLEAN NOT NULL DEFAULT true;

-- 3. 创建索引
CREATE INDEX idx_categories_parent_id ON categories(parent_id);

-- 4. 根分类名称全局唯一
CREATE UNIQUE INDEX uq_root_category_name
ON categories (name)
WHERE parent_id IS NULL;

-- 5. 子分类在同父类下唯一
CREATE UNIQUE INDEX uq_sub_category_name
ON categories (parent_id, name)
WHERE parent_id IS NOT NULL;
```

**关键设计**：
- 预置的子分类 `is_public=true`（直接在前台可用）
- 自动创建的子分类默认 `is_public=false`（仅用于绑定和筛选，不展示在公共选择列表中）

### 3.4 核心逻辑改动

#### 3.4.1 字符串规范化辅助函数

导入时对输入字符串做清洗，防止全半角、大小写、繁简体不一致导致的逻辑重复：

> **依赖选择**：推荐纯 Python 库 `zhconv`（~150KB，无 C 依赖），适配 `python:3.9.7-slim` 基础镜像。禁止引入 `opencc`（需 C 编译环境，Docker 构建会失败）。

```python
import unicodedata
import re
import logging

logger = logging.getLogger(__name__)

# 尝试导入纯 Python 繁简体转换库，失败时优雅降级
try:
    import zhconv
    HAS_ZHCONV = True
except ImportError:
    logger.warning("zhconv 未安装，跳过繁简体统一。pip install zhconv 可启用")
    HAS_ZHCONV = False


def _normalize_category_name(raw: str) -> str:
    """
    规范化分类名称：去零宽字符、统一全半角、繁简体归一、统一小写。

    防止因字符微小差异（全半角、零宽字符、繁简体）绕过后端唯一索引。
    所有导入路径（CSV / API 创建 / 迁移脚本）应统一调用此函数。
    """
    if not raw:
        return ""

    # 1. 移除零宽字符及不可见控制字符
    cleaned = re.sub(
        r'[\u200b\u200c\u200d\ufeff\u00ad\u2060\u200e\u200f\u202a-\u202e]',
        '', raw
    )

    # 2. 全半角及兼容性字符归一（NFKC）
    # 例如：全角连字符"－"→ 半角"-"，全角数字"３"→ "3"
    cleaned = unicodedata.normalize('NFKC', cleaned)

    # 3. 繁简体统一（仅在库可用时执行，编译环境无 C 依赖）
    if HAS_ZHCONV:
        try:
            cleaned = zhconv.convert(cleaned, 'zh-hans')  # 统一转为简体
        except Exception as e:
            logger.error(f"繁简体转换失败，跳过: {e}")

    # 4. 英文字符统一小写 + 首尾去空白
    return cleaned.lower().strip()
```

#### 3.4.2 创建/更新专家时的分类匹配

```python
from sqlalchemy.dialects.postgresql import insert

async def _resolve_active_category_id(
    self,
    category_id_raw: Optional[str],
    category_name_raw: Optional[str],
) -> uuid.UUID:
    """
    解析专家主分类。
    修改后：支持自动匹配父类 + 自动创建子分类（UPSERT 防并发）。
    不再返回 None（兜底→"其他"根分类）。
    """
    from app.models.content_management import Category

    # 0. 字符串规范化
    if category_name_raw:
        category_name_raw = _normalize_category_name(category_name_raw)

    # 1. 优先按 UUID 精确查找
    if category_id_raw:
        try:
            category_id = uuid.UUID(category_id_raw)
        except (ValueError, TypeError):
            raise ValueError(f"无效的 category_id 格式: {category_id_raw}")
        cat = await db.get(Category, category_id)
        if cat and cat.is_active:
            return category_id
        raise ValueError(f"分类不存在或已禁用: {category_id_raw}")

    # 2. 按名称查找（新增：自动创建子分类）
    if category_name_raw:
        name = category_name_raw.strip()

        # 2a. 精确匹配（根分类或子分类均可）
        result = await db.execute(
            select(Category.id).where(
                Category.name == name,
                Category.is_active == True
            )
        )
        if cat_id := result.scalar_one_or_none():
            return cat_id

        # 2b. 匹配到父类（根分类）
        parent = await self._match_broad_category(name)
        if parent:
            slug = self._to_slug(f"{parent.slug}-{name}" if parent.slug else name)
            # 使用 UPSERT 避免并发竞态冲突
            stmt = (
                insert(Category)
                .values(
                    name=name,
                    parent_id=parent.id,
                    slug=slug,
                    sort_order=0,
                    is_active=True,
                    is_public=False,   # 自动创建的子分类默认不公开
                )
                .on_conflict_do_nothing(
                    index_elements=['parent_id', 'name'],
                    # 对应子分类唯一索引 uq_sub_category_name
                )
                .returning(Category.id)
            )
            result = await self.db.execute(stmt)
            new_id = result.scalar_one_or_none()

            if new_id:
                logger.info(f"自动创建子分类: name={name}, parent_id={parent.id}")
                return new_id

            # UPSERT 未插入（冲突，另一个请求已创建），查一次返回现有 ID
            existing = await db.execute(
                select(Category.id).where(
                    Category.parent_id == parent.id,
                    Category.name == name,
                )
            )
            existing_id = existing.scalar_one_or_none()
            if existing_id:
                return existing_id
            # 极低概率：并发事务回滚导致查不到，返回到 "其他" 兜底
            logger.warning(f"并发冲突后二次查询仍无结果，降级到其他: name={name}")
            return self.OTHER_CATEGORY_ID

        # 2c. 完全匹配不到 → 在"其他"根分类下创建子分类保留原始科室名
        slug = self._to_slug(f"other-{name}")
        stmt = (
            insert(Category)
            .values(
                name=name,
                parent_id=self.OTHER_CATEGORY_ID,
                slug=slug,
                sort_order=0,
                is_active=True,
                is_public=False,
            )
            .on_conflict_do_nothing(
                index_elements=['parent_id', 'name'],
            )
            .returning(Category.id)
        )
        result = await self.db.execute(stmt)
        new_id = result.scalar_one_or_none()
        if new_id:
            logger.info(f"在'其他'下创建子分类保留科室名: name={name}")
            return new_id

        # 并发冲突，查已有记录
        existing = await db.execute(
            select(Category.id).where(
                Category.parent_id == self.OTHER_CATEGORY_ID,
                Category.name == name,
            )
        )
        return existing.scalar_one_or_none() or self.OTHER_CATEGORY_ID

    # 3. 两者都为空 → "其他"（不再是 None）
    return self.OTHER_CATEGORY_ID
```

**slug 生成说明**：`slug` 不设全局唯一约束。子分类 slug 拼接父分类 slug 前缀（如 `parent_slug-name-slug`）以确保在同一上下文中不冲突。即使不同的父分类下出现同名 slug，也不会引发数据库约束冲突。

#### 3.4.5 父类匹配算法

```python
async def _match_broad_category(self, name: str) -> Optional[Category]:
    """
    从科室文本中提取根分类。
    策略：子串匹配（已能覆盖 90%+ 场景）
    """
    # 加载所有根分类（带缓存，一次会话中只查一次）
    if not hasattr(self, '_broad_categories'):
        result = await self.db.execute(
            select(Category).where(
                Category.parent_id == None,
                Category.is_active == True
            ).order_by(Category.sort_order)
        )
        self._broad_categories = result.scalars().all()

    # 子串匹配：根分类名包含在输入文本中
    for bc in self._broad_categories:
        if bc.name in name:
            return bc

    # 正则提取"XX科"关键词
    import re
    match = re.search(r'([\u4e00-\u9fa5]{2,}科)', name)
    if match:
        dept_word = match.group(1)
        for bc in self._broad_categories:
            if dept_word in bc.name or bc.name in dept_word:
                return bc

    return None
```

> **后期增强（P3）**：可启用 pg_trgm 扩展处理简称/缩写场景（如"神外"→"神经外科"），当前子串匹配已覆盖绝大多数场景。

### 3.8 待审核分类合并机制（P2 阶段）

为应对自动创建子分类的长期累积问题，提供**批量合并 API**。

```python
from sqlalchemy import update, delete, text
from app.exceptions import InvalidParameterException
from app.models.content_management import Category, LiveRoomCategory
from app.models.experts import Expert


async def merge_categories(
    db: AsyncSession,
    source_ids: List[uuid.UUID],
    target_id: uuid.UUID,
) -> Dict[str, int]:
    """
    将多个源分类（通常是待审核的子分类）合并到一个目标分类中。

    原子事务内完成：更新专家关联 → 合并直播间关联 → 删除源分类。
    """
    async with db.begin():
        # 1. 校验目标分类
        target_cat = await db.get(Category, target_id)
        if not target_cat or not target_cat.is_active:
            raise InvalidParameterException("目标分类不存在或已禁用")

        # 2. 批量更新专家表的 category_id（1:N）
        result = await db.execute(
            update(Expert)
            .where(Expert.category_id.in_(source_ids))
            .values(category_id=target_id)
        )
        expert_count = result.rowcount

        # 3. 合并直播间关联（M:N），处理主键冲突
        room_count = 0
        for sid in source_ids:
            # 3a. 为尚未关联目标分类的房间插入新关联
            stmt = text("""
                INSERT INTO live_room_categories (room_id, category_id, is_primary)
                SELECT lrc.room_id, :target_id, lrc.is_primary
                FROM live_room_categories lrc
                WHERE lrc.category_id = :source_id
                  AND NOT EXISTS (
                    SELECT 1 FROM live_room_categories sub
                    WHERE sub.room_id = lrc.room_id
                      AND sub.category_id = :target_id
                  )
                ON CONFLICT (room_id, category_id) DO NOTHING
            """)
            await db.execute(stmt, {"target_id": target_id, "source_id": sid})
            room_count += 1

            # 3b. 删除源关联
            await db.execute(
                delete(LiveRoomCategory.__table__)
                .where(LiveRoomCategory.category_id == sid)
            )

        # 4. 物理删除源分类
        await db.execute(
            delete(Category)
            .where(Category.id.in_(source_ids))
        )

    return {"merged_experts": expert_count, "merged_rooms": room_count}
```

- 默认仅加载 `is_public=true` 的分类
- "待审核"页签列出 `is_public=false` 的子分类，**按关联专家数降序排列**

### 3.9 历史数据迁移最佳实践（阶段三增强）

阶段三的迁移脚本前，增加**数据空跑（Dry-Run）流程**：

```
┌──────────────────────────────────────────────────────────┐
│  步骤 A：帕累托分析                                       │
│                                                          │
│  SELECT department, COUNT(*) FROM experts                │
│  WHERE department IS NOT NULL                            │
│  GROUP BY department ORDER BY COUNT(*) DESC;             │
│                                                          │
│  → 通常前 50 条高频科室名覆盖 90% 数据                    │
│  → 交业务团队人工确认这 50 条映射关系                      │
│  → 写入 MAPPING 字典                                      │
├──────────────────────────────────────────────────────────┤
│  步骤 B：空跑脚本（Dry-Run）                              │
│                                                          │
│  输出 migration_report.csv:                              │
│  [专家ID, 姓名, 原department, 拟匹配大类, 拟创建子分类]      │
│                                                          │
│  → 检查是否有职称类文本（"主治医师"）被归入"其他"          │
│  → 检查是否有错误匹配（"外科"同时命中了多个大类）          │
│  → 基于报表修正 MAPPING 字典                              │
```

## 第四章：风险与缓解

### 4.1 并发导入时的子分类重复创建

**风险**：两个批量导入同时处理相同科室名，同时判断"不存在"后同时插入，导致唯一键冲突。

**缓解**：
- `insert().on_conflict_do_nothing()` UPSERT 确保只成功写入一次
- 冲突时查询已有记录返回，不抛异常
- `batch_import_experts_from_csv_optimized` 本身已对每行使用 `begin_nested()` 隔离，单行失败不影响整批

### 4.2 脏数据污染公共分类库

**风险**：错别字或非规范命名自动创建后在前台展示（如"高血庄组"、"张医生组"）。

**缓解**：
- 自动创建的子分类默认 `is_public=false`，**不展示在公共分类选择器/下拉列表中**
- `is_public=false` 不影响分类的业务绑定和筛选（`_validate_active_category_or_raise` 和 `_expand_category_ids` 均基于 `is_active` 判断，不看 `is_public`）
- 后台提供"待审核分类"面板，管理员可一键通过或批量合并
- 三个状态的语义区分：

| `is_active` | `is_public` | 含义 |
|---|---|---|
| `true` | `true` | ✅ 正常分类，前台可见、可筛选、可下拉选择 |
| `true` | `false` | ✅ 内部分类，可绑定和筛选，但不出现在分类选择列表中（待审核） |
| `false` | — | ❌ 已停用，不可绑定、不可筛选、不展示 |

### 4.3 分类名唯一性保障

**风险**：
- 根分类（`parent_id IS NULL`）：PostgreSQL 中 `NULL ≠ NULL`，联合唯一约束不生效，可能创建多个同名根分类
- 子分类：同父类下可能出现同名

**缓解**：
- 使用 PostgreSQL **部分索引**（Partial Unique Index）分别约束：
  - `uq_root_category_name`：`UNIQUE WHERE parent_id IS NULL` — 根分类全局唯一
  - `uq_sub_category_name`：`UNIQUE (parent_id, name) WHERE parent_id IS NOT NULL` — 子分类同父类下唯一

### 4.4 搜索性能

**风险**：`WHERE category_id = ANY(...)` 中的 ID 列表随子分类数量增长而增长

**缓解**：
- 业务限定 2 层结构，15 个根分类 × 每个最多 ~30 个子分类 = 最多 450 个 UUID
- `IN (450个UUID)` 对 PostgreSQL 是微秒级操作
- `experts.category_id` 和 `live_room_categories.category_id` 均有索引
- 实测前无需优化，实测后如有必要可加 Redis 缓存

### 4.5 前端展示不一致

**风险**：部分专家展示"心内科"（根分类），部分展示"心内科-冠脉介入组"（子分类）

**缓解**：
- 这不是 bug——这就是设计意图。前端详情页展示 `category.name`，根分类时展示宽泛名称，子分类时展示具体名称。
- Tab 筛选时无论根分类还是子分类，都能被正确命中。
- 管理员审核后可决定是否将根分类下的专家迁移到更精确的子分类。

### 4.6 迁移数据丢失

**风险**：`department` 文本比分类名更详细，直接丢弃会丢信息

**缓解**：
- 迁移时将原 `department` 值写入 `category.description` 字段（Text 类型，无长度限制）
- `description = f"原科室: {department}"`
- 管理员可随时从后台查看该字段

### 4.7 父分类误删导致子分类"篡位"（ON DELETE RESTRICT 保护）

**风险**：如果管理员误删一个根分类（虽然极少发生），其下属所有子分类的 `parent_id` 会被置为 `NULL`，使它们一夜之间成为根分类，直接出现在前端 Tab 栏。

**缓解**：
- `parent_id` 外键使用 `ON DELETE RESTRICT`（而非 `SET NULL`），从数据库层面**禁止删除仍有子分类的父分类**
- 分类本身使用 `is_active` 软删除，不走物理 DELETE，日常运营中不涉及此问题
- 管理员必须先手动解除所有子分类的父关联（或软删除所有子分类），才能删除根分类

### 4.8 slug 唯一性冲突

**风险**：不同父分类下的子分类生成相同 slug（如两个"其他"子分类都生成 `other`），如果 `slug` 有全局唯一约束则会插入失败。

**缓解**：
- `slug` 字段在 `categories` 表中**没有全局唯一约束**，允许不同父分类下 slug 重复
- 子分类 slug 生成时拼接父分类 slug 前缀（如 `general-surgery-other`、`cardiology-other`），降低 UI 交互中的阅读困惑
- 此字段仅为 URL 友好标识，不需要用做数据库级唯一性保障

### 4.9 并发二次查询的"幻读"

**风险**：UPSERT 冲突后二次查询 `scalar_one()` 可能抛出 `NoResultFound`（极低概率：并发事务回滚）。

**缓解**：
- 使用 `scalar_one_or_none()` 而非 `scalar_one()`，返回 None 时降级到"其他"兜底
- 同时记录 `logger.warning` 便于排查

### 4.10 字符串规范化导致的匹配遗漏

**风险**：全半角不一致、零宽字符、繁简体混用导致同义科室被识别为不同名称，绕过了唯一索引。

**缓解**：
- 在 `_resolve_active_category_id` 入口统一调用 `_normalize_category_name()` 做清洗：
  - 移除零宽字符（`\u200b`、`\ufeff` 等）
  - 全半角归一（`NFKC` normalization）
  - 英文统一小写
  - 繁简体统一（建议集成 `opencc` 或 `zhconv`）

### 4.11 CRUD 层 category_id 校验缺失

**风险**：当前 `crud/experts.py:37-89` 的 `create_expert` 直接将 `category_id` 写入数据库，**不做任何存在性校验**。虽然所有外部调用路径都已经过 service 层校验，但该 CRUD 函数可能在测试代码、数据迁移脚本或未来的新入口中被直接调用，导致写入无效的 `category_id`。

**缓解**：
- 在 CRUD 层 `create_expert` 中增加 `category_id` 的 UUID 格式校验和存在性断言（不检查 `is_active`，保留给 service 层做完整业务校验）
- 在文档和注释中说明：CRUD 层做基础合法性校验，Service 层做完整业务校验
- 当前 A2 方案的自动匹配逻辑完全在 service 层实现，依赖 service 层保证传入 CRUD 的 `category_id` 值已合法

### 4.12 `update_expert` 未纳入自动匹配

**风险**：`update_expert`（`expert_service.py:698-708`）当前只做精确校验——传了 `category_id` 就检查存在且启用；不传则跳过。A2 方案未将 `update_expert` 纳入自动匹配流程（因为 `update_expert` 不接收 `category_name_raw` 参数）。管理员通过 UI 更新专家科室为新的、尚未创建的子分类名称时，仍需人工先在分类管理中创建该子分类。

**缓解**：
- 明确设计边界：`update_expert` 只做分类选择（从已有分类中选），不做分类创建
- 如果需要创建新子分类，通过管理后台的分类管理接口提前创建
- 如果未来需要，可以在管理后台增加"在编辑专家时创建子分类"的快捷功能（新功能需求，不纳入当前方案）

### 4.13 自动创建子分类的长期膨胀

**风险**：长期运营后，`is_public=false` 的子分类可能累积到数百甚至上千条，导致管理后台加载变慢、运营人员维护困难。

**缓解**：
- 提供批量合并 API（见 3.8 节），将多个类似子分类一键合并到标准分类，自动更新关联的专家和直播间
- 管理后台默认只加载 `is_public=true` 的分类，"待审核"页签按关联专家数降序排列，让运营优先处理最高频的项
- 设计上限警戒：单父类下 `is_public=false` 的子分类超过 50 个时触发告警

### 4.14 专家变更分类后产生"孤儿子分类"

**风险**：专家从 auto-created 子分类迁移到其他分类后，旧子分类可能变为"空分类"（无专家、无直播间关联），成为数据库中的僵尸数据。

**场景**：
```
专家 A → "心内科-结构性心脏病组"（auto-created, is_public=false）
         ↓
专家 A 更新到 "心内科-冠脉介入组"
         ↓
"心内科-结构性心脏病组" 这条记录仍然存在，
但没有任何专家或直播间关联它。
```

**缓解**：
- `update_expert` 在分类变更后自动调用 `_cleanup_orphan_category()`（见 3.4.3 节代码）
- 清理规则：仅当分类同时满足 `is_public=false`（自动创建）且专家计数=0 且直播间计数=0 时，设 `is_active=false`
- 不清理 `is_public=true` 的分类（管理员手动创建的不应自动清除）
- 软删除而非物理删除，方便追溯
