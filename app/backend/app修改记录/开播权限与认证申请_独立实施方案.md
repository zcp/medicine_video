## 一、设计原则

### 1.1 核心分离

```
专家（Expert）        ≠   开播资格（Broadcast Permission）
 ├─ 管理员 curated        ├─ 途径 A：已是专家 → 自动拥有
 ├─ 内容身份（展示用）     ├─ 途径 B：管理员直接授权
 └─ 不可自助获得           ├─ 途径 C：用户自助申请认证 → 管理员审核 → 获得资格
                          └─ 获得后：可开播 + 管理自己直播间，身份仍为 REGULAR
```

### 1.2 关键决策

| 决策 | 说明 |
|:----|:----|
| **专家不可自助申请** | Expert 表由 Admin 手动创建，代表"平台认证的医学专家"这个内容身份 |
| **开播资格可自助申请** | 普通用户提交资质材料，管理员审核通过后获得开播权 |
| **已是专家 → 自动可开播** | `Expert.user_id = current_user AND Expert.is_active = True` → 途径 A 直接通过 |
| **认证通过 ≠ 成为专家** | 通过认证的用户获得开播权 + 管理自己直播间的权利，身份仍为 REGULAR |
| **三路径合并判定** | 任一路径满足即可开播，互不干扰 |

### 1.3 用户故事

| 场景 | 流程 | 最终开播资格来源 |
|:----|:----|:------------|
| 王医生，已在专家列表中 | Admin 已创建 Expert 记录并关联 user_id → 直接可开播 | 途径 A（Expert） |
| 李医生，刚注册平台，不在专家列表中 | 提交执业医师资格证 + 职称证书 → Admin 审核通过 → 可开播 | 途径 C（认证申请） |
| 张运营，负责心内科直播协调 | Admin 在后台直接授权 → 可开播 | 途径 B（管理员授权） |
| 赵医生，在专家列表中但 is_active=False | Expert 记录存在但未激活 → 不可通过 A，可走 C 申请 | 途径 C（认证申请） |
| 钱医生，先通过认证开播，后来 Admin 将之加入专家列表 | 先有 `broadcaster_permissions.source='certification'`，后有 `Expert.is_active=True` → 两者同时满足，`GET /users/me/broadcast-permission` 返回 `source="expert"` | 途径 A（Expert 优先） |

## 二、数据模型设计

### 2.1 新增表 `broadcaster_permissions`

管理员直接授权的开播白名单（途径 B）。认证申请通过后也会在此表创建记录（途径 C 的落点）。

```sql
CREATE TABLE broadcaster_permissions (
    id          UUID PRIMARY KEY,                     -- uuid.uuid4()
    user_id     UUID NOT NULL,                        -- users.public_id（应用层校验）
    granted_by  UUID NOT NULL,                        -- 授权的 Admin user_id
    source      VARCHAR(20) NOT NULL DEFAULT 'admin', -- 'admin'(途径B) 或 'certification'(途径C)
    granted_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    note        TEXT,                                 -- 授权原因

    CONSTRAINT uq_broadcaster_permissions_user UNIQUE (user_id)
);

CREATE INDEX idx_broadcaster_permissions_user ON broadcaster_permissions(user_id);
CREATE INDEX idx_broadcaster_permissions_source ON broadcaster_permissions(source);

COMMENT ON TABLE broadcaster_permissions IS '开播授权白名单：管理员直接授权 或 认证申请通过后自动写入';
COMMENT ON COLUMN broadcaster_permissions.user_id IS '被授权用户 public_id，应用层校验';
COMMENT ON COLUMN broadcaster_permissions.source IS 'admin=管理员直接授权, certification=用户认证申请通过';
COMMENT ON COLUMN broadcaster_permissions.note IS '授权原因';
```

### 2.2 新增表 `certification_applications`

用户自助申请认证的记录表。

```sql
CREATE TYPE certification_status AS ENUM ('pending', 'approved', 'rejected');

CREATE TABLE certification_applications (
    id                  UUID PRIMARY KEY,              -- uuid.uuid4()
    user_id             UUID NOT NULL,                 -- 申请人 public_id
    real_name           VARCHAR(60) NOT NULL,          -- 真实姓名
    hospital            VARCHAR(200),                  -- 所属医院
    title               VARCHAR(120),                  -- 职称（主任医师/副主任医师/主治医师/其他）
    department          VARCHAR(120),                  -- 科室
    purpose             TEXT,                          -- 开播用途说明（帮助 Admin 判断合理性）

    -- 资质材料（文件路径，由文件服务器存储）
    license_image       VARCHAR(512) NOT NULL,         -- 执业医师资格证 照片
    title_cert_image    VARCHAR(512),                  -- 职称证书 照片
    hospital_id_image   VARCHAR(512),                  -- 医院工牌/在职证明 照片

    -- 审核信息
    status              certification_status NOT NULL DEFAULT 'pending',
    reviewed_by         UUID,                          -- 审核人 Admin user_id
    reviewed_at         TIMESTAMPTZ,                  -- 审核时间
    reject_reason       TEXT,                          -- 驳回原因（status=rejected 时必填）

    -- 时间戳
    created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 索引：每用户取最新申请（按 created_at DESC）
CREATE INDEX idx_cert_applications_user_id ON certification_applications(user_id, created_at DESC);

-- 注意：不使用 UNIQUE(user_id) 约束，允许用户被驳回后重新提交新记录。
-- 应用层取 user_id + created_at DESC 的最新一条作为当前申请状态。
-- 历史申请记录保留在表中供审计追溯。

-- 注意：不使用单列 user_id 索引。复合索引 idx_cert_applications_user_id(user_id, created_at DESC) 的引导列 user_id 已覆盖等值查询
CREATE INDEX idx_certification_applications_status ON certification_applications(status);
CREATE INDEX idx_certification_applications_created ON certification_applications(created_at);

COMMENT ON TABLE certification_applications IS '用户自助申请开播认证的记录，含资质材料路径和审核状态';
COMMENT ON COLUMN certification_applications.license_image IS '执业医师资格证照片路径';
COMMENT ON COLUMN certification_applications.title_cert_image IS '职称证书照片路径（可选）';
COMMENT ON COLUMN certification_applications.hospital_id_image IS '医院工牌/在职证明照片路径（可选）';
```

### 2.3 不修改的现有表

| 表 | 理由 |
|:---|:----|
| `experts` | 专家是内容身份，由 Admin 创建。认证通过不创建 Expert 记录 |
| `live_rooms` | Room Owner 模型不变，通过认证的用户仍是 REGULAR，创建房间时 `user_id` 填自己 |
| `users` | 用户身份不升级，始终为 REGULAR |

### 2.4 数据流：认证通过后

```
用户提交认证申请
    ↓
Admin 审核通过（status='approved'）
    ↓
应用层自动执行：
    1. INSERT INTO broadcaster_permissions (user_id, granted_by, source='certification', note='认证申请通过')
    2. UPDATE certification_applications SET reviewed_by=?, reviewed_at=NOW()
    ↓
用户刷新页面 → GET /users/me/broadcast-permission → {can_broadcast: true, source: "certification"}
    ↓
用户可以创建直播间
```

## 四、守卫函数

### 4.1 `_check_broadcast_permission`（room_service.py）

```python
# 文件顶部已有 import
from app.models.experts import Expert
from app.models.broadcaster_permissions import BroadcasterPermission

class RoomService:

    async def _check_broadcast_permission(self, user_id: uuid.UUID) -> bool:
        """
        检查用户是否有开播资格（三路径判定）。

        途径 A：已是平台认证专家（Expert.user_id 匹配 且 Expert.is_active=True）
        途径 B：管理员直接授权（broadcaster_permissions.source='admin'）
        途径 C：认证申请通过（broadcaster_permissions.source='certification'）

        注：途径 B 和 C 查询同一张表，source 字段仅用于区分来源（审计/展示用途），
            判定逻辑不区分 source——表中有记录即通过。
        """
        # 途径 A：认证专家
        result = await self.db.execute(
            select(Expert).where(Expert.user_id == user_id)
        )
        expert = result.scalar_one_or_none()
        if expert and expert.is_active:
            return True

        # 途径 B + C：broadcaster_permissions 表有记录即可
        result = await self.db.execute(
            select(BroadcasterPermission).where(
                BroadcasterPermission.user_id == user_id
            )
        )
        if result.scalar_one_or_none():
            return True

        return False
```

### 5.2 端点详细设计

#### 5.2.1 查询自己开播资格

```
GET /api/v1/users/me/broadcast-permission
Auth: Strict（任何登录用户）
```

**响应**:
```json
{
    "code": 200,
    "data": {
        "can_broadcast": true,
        "source": "expert",
        "source_detail": "平台认证专家（王医生，主任医师）",
        "has_pending_application": false
    }
}
```

**字段说明**:
| 字段 | 类型 | 说明 |
|:----|:----|:----|
| `can_broadcast` | bool | 是否可以创建直播间 |
| `source` | `"expert"` \| `"admin"` \| `"certification"` \| `null` | 资格来源。`null` 表示无资格 |
| `source_detail` | string\|null | 人类可读的来源说明（前端可直接展示） |
| `has_pending_application` | bool | 是否有待审核的认证申请（前端据此显示"审核中"状态） |

**判定逻辑**:
```
1. role in (ADMIN, SUPERADMIN) → can_broadcast=true, source="admin"
2. Expert 表 user_id 匹配且 is_active=true → can_broadcast=true, source="expert"
3. broadcaster_permissions 表有记录 → can_broadcast=true, source=该记录的 source 字段值
4. certification_applications 表有 status='pending' 的记录 → has_pending_application=true
5. 以上均不满足 → can_broadcast=false, source=null
```

> **优先级说明**：Expert（第 2 步）优先于 `broadcaster_permissions`（第 3 步）。同一用户同时满足两条路径时，返回 `source="expert"`。原因是：**专家身份 > 认证身份**——如果 Admin 后来把该用户加进了专家列表，说明平台已将其认定为医学专家，开播来源应以专家身份为准。

#### 5.2.2 提交认证申请

```
POST /api/v1/users/me/certification-application
Auth: Strict（仅 REGULAR。ADMIN/SUPERADMIN 不需要认证）
Content-Type: multipart/form-data
```

**请求参数**:
| 参数 | 类型 | 必填 | 说明 |
|:----|:----|:---:|:----|
| `real_name` | string | ✅ | 真实姓名 |
| `hospital` | string | - | 所属医院 |
| `title` | string | - | 职称（主任医师/副主任医师/主治医师/住院医师/其他） |
| `department` | string | - | 科室 |
| `purpose` | string | - | 开播用途说明（如"每周三科室学术直播"），帮助 Admin 判断 |
| `license_image` | file | ✅ | 执业医师资格证（JPG/PNG, ≤5MB） |
| `title_cert_image` | file | - | 职称证书（JPG/PNG/PDF, ≤5MB） |
| `hospital_id_image` | file | - | 医院工牌/在职证明（JPG/PNG, ≤5MB） |

**业务规则**:
- 已是专家（途径 A）的用户：返回 400 "您已是平台认证专家，无需申请"
- 已有 broadcaster_permissions 记录（途径 B/C）的用户：返回 400 "您已拥有开播资格"
- 已有 pending 申请的用户：返回 400 "您已有待审核的认证申请，请耐心等待"
- 已有 rejected 申请的用户：允许重新提交（INSERT 新行，按 `created_at DESC` 取最新一条作为当前状态。历史申请记录保留在表中供审计追溯）

**响应**:
```json
{
    "code": 200,
    "data": {
        "id": "uuid",
        "status": "pending",
        "created_at": "2026-07-21T10:30:00Z"
    },
    "message": "认证申请已提交，请等待管理员审核"
}
```

#### 5.2.5 Admin 审核通过

```
POST /api/v1/admin/certification-applications/{id}/approve
Auth: Strict（ADMIN/SUPERADMIN）
Body: {} （无请求体）
```

**业务逻辑**:
```
1. 校验申请存在且 status='pending'，否则返回 400
2. 在事务中执行：
   a. INSERT INTO broadcaster_permissions (user_id, granted_by, source='certification', note=从申请中拼备注)
      ON CONFLICT (user_id) DO UPDATE SET
          granted_by = EXCLUDED.granted_by,
          note       = EXCLUDED.note
      -- 注意：ON CONFLICT 不更新 source 字段，保留原始来源。
      -- 例如：用户先通过途径 B（source='admin'）获得资格，后来又走途径 C 认证通过，
      --       此时保留 source='admin' 更准确地反映最初授权来源。
   b. UPDATE certification_applications SET status='approved', reviewed_by=?, reviewed_at=NOW()
3. 返回成功
```

#### 5.2.6 Admin 审核驳回

```
POST /api/v1/admin/certification-applications/{id}/reject
Auth: Strict（ADMIN/SUPERADMIN）
Body: { "reason": "执业医师资格证书照片不清晰，请重新上传" }
```

**业务逻辑**:
```
1. 校验申请存在且 status='pending'，否则返回 400
2. 校验 reason 非空
3. UPDATE certification_applications SET status='rejected', reviewed_by=?, reviewed_at=NOW(), reject_reason=?
4. 返回成功
```

#### 5.2.9 Admin 撤销开播授权

```
DELETE /api/v1/admin/broadcaster-permissions/{user_id}
Auth: Strict（ADMIN/SUPERADMIN）
```

**说明**:
- 硬删除 `broadcaster_permissions` 表中的记录
- 如果该用户同时是认证专家（途径 A），撤销后仍可通过 A 开播
- 不影响 `certification_applications` 表（历史记录保留）

```
POST /api/v1/admin/experts/{expert_id}/link-user
Auth: Strict（ADMIN/SUPERADMIN）
Body: { "user_id": "用户注册后的 public_id" }
```

**用途**：为批量导入的专家（`Expert.user_id IS NULL`）绑定平台用户账号，打通途径 A 开播通道。

**触发场景**：平台上线后，专家注册了账号 → Admin 在后台搜索该专家 → 执行关联。

**业务逻辑**：
```sql
-- 校验：Expert 存在且 user_id 当前为 NULL（避免覆盖已有绑定）
SELECT * FROM experts WHERE id = ? AND user_id IS NULL
-- 校验：user_id 未被其他 Expert 占用（避免一人绑多专家）
SELECT * FROM experts WHERE user_id = ?  
-- 校验通过后执行：
UPDATE experts SET user_id = ? WHERE id = ?
```

**响应**:
```json
{
    "code": 200,
    "message": "专家与平台用户关联成功，该专家已自动获得开播资格"
}
```

**说明**：
- 关联后 `Expert.is_active=True` 的用户自动通过途径 A，无需走认证流程
- Admin 导入专家时已审核资质，关联 user_id 是"补全信息"而非"重新认证"
- 如果该用户已有 `broadcaster_permissions` 记录（例如之前走过途径 C），不影响——途径 A 优先

## 六、文件上传

### 6.1 存储路径与两阶段提交

认证材料复用现有的 `FileHandler` 模式，存储在独立目录：

```
media/certifications/{application_id}/license_{timestamp}.{ext}
media/certifications/{application_id}/title_cert_{timestamp}.{ext}
media/certifications/{application_id}/hospital_id_{timestamp}.{ext}
```

**两阶段提交说明**：文件路径中包含 `application_id`，但该 ID 在写入数据库后才生成。因此保存流程为：

```
阶段一：INSERT certification_applications (license_image 等先置 NULL)
         → 获得 application_id
阶段二：保存文件到 media/certifications/{application_id}/ 目录
         → UPDATE certification_applications SET license_image = 文件 URL
         → COMMIT
```

**失败处理**：
- 如果阶段二失败（文件写入异常），阶段一已 INSERT 的记录存在，`license_image` 为 NULL。
- 应用层处理方式：用户再次提交同一申请时（即当前有 `status='pending'` 且 `license_image IS NULL` 的记录），应视为"草稿"并允许覆盖。
- 更健壮的替代方案（**可选**）：先存文件到临时路径 → 再 INSERT。当前设计保持方案一（先 INSERT），因为现有 `FileHandler` 已有类似模式，复杂度更低。

```sql
    department        VARCHAR(120),
```

## 八、三路径判定汇总

| 路径 | 数据来源 | 获取方式 | source 值 | 说明 |
|:---:|:----|:----|:---:|:----|
| **A** | `experts` 表 | Admin 创建 Expert 记录并关联 user_id | `"expert"` | 平台认证的医学专家身份 |
| **B** | `broadcaster_permissions` 表 | Admin 在后台手动添加 | `"admin"` | 运营/市场人员等非医学开播者 |
| **C** | `broadcaster_permissions` 表 | 用户自助提交认证 → Admin 审核 → 自动写入 | `"certification"` | 医生自助认证，不成为 Expert |

**判定逻辑（OR 关系）**:
```
can_broadcast = (途径 A) OR (途径 B) OR (途径 C) OR (role in ADMIN/SUPERADMIN)
```

## 十、安全性考量

| 风险 | 缓解措施 |
|:----|:----|
| 用户上传伪造证书 | 证书文件仅 Admin 可查看（审核时人工核验），系统不做自动识别 |
| 用户重复提交申请 | 每次提交 INSERT 新行，应用层校验：已有 `status='pending'` 的记录时拒绝再次提交 |
| 已是专家的用户重复申请 | 应用层在提交申请时检查 Expert 表，返回 400 |
| 认证材料泄露 | 文件路径不暴露在公开 API 中，仅 Admin 审核时可访问 |
| Admin 误操作撤销 | 撤销仅删除 `broadcaster_permissions`，途径 A（Expert）不受影响 |
