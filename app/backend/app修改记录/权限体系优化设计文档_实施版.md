## 一、执行摘要

### 1.1 核心结论

经过对 `app/` 目录下全部 13 个 endpoint 文件、12 个 service 文件、3 个 core 文件（auth.py / deps.py / permissions.py）和 `crud/room.py` 的逐行审计，结论如下：

**权限模型（Anonymous → REGULAR → ADMIN → SUPERADMIN + 双轨鉴权 + 404 伪装 + Owner+Admin 所有权 + SQL 级过滤）是成熟且与主流平台对齐的。问题不在"模型"，而在"施工质量"。**

### 1.2 问题总览

| 等级 | 数量 | 类型说明 | 代表项 |
|:----:|:----:|------|------|
| 🔴 P0 安全漏洞 | 4 | 真实的信息泄露/越权/伪造风险 | StreamKey 暴露、场次标签越权、SRS 回调零防护、科室列表缺校验 |
| 🟡 P1 系统性 | 6 | 代码规范导致维护成本翻倍、未来变更高风险 | `.upper()` 52%缺失、守卫函数 6+ Service 重复、8 个 endpoint 硬编码预检查、错误码分裂、`sub` fallback、批量导入函数名误导 |
| 🟢 P2 设计演进 | 8 | 与主流平台的功能差异 + 技术债务清理 | 缺少关注统计、`is_private` 只二值、无操作配额、用户批量通知删除缺失、审计日志无查询入口、无全局异常处理器、MODERATOR 未处置、开播权限 |

## 二、权限体系基础（当前实际实现）

### 2.1 角色定义

项目实际生效的是 **4 个访问状态**（含匿名），通过 JWT Token 中的 `role` 字段区分：

| 状态 | JWT role 字段 | 判断方式（代码） | 生效范围 |
|------|:---:|------|------|
| **L0 匿名** | 无 Token | `get_current_user_optional` 返回 `None` | 全服务 |
| **L1 普通用户** | `REGULAR` | `role not in ['ADMIN','SUPERADMIN']` 后走 else 分支 | 全服务 |
| **L2 管理员** | `ADMIN` | `role in ['ADMIN','SUPERADMIN']` | 全服务 |
| **L3 超级管理员** | `SUPERADMIN` | `role in ['ADMIN','SUPERADMIN']`（与 ADMIN 等价） | 直播核心服务中与 ADMIN 等价；用户模块中独享改角色/查审计/改系统配置 |
| ~~MODERATOR~~ | `MODERATOR` | **代码中零出现，等同 REGULAR** | 数据库 ENUM 中存在，保留未启用 |

### 2.2 认证基础设施

**文件**: `app/core/auth.py` + `app/core/deps.py`

```python
# === 模式 A: Strict Auth（强制鉴权）===
# 依赖: Depends(get_current_user)
# 行为: 无 Token → 401 | Token 无效 → 401
# 适用: 所有写操作（POST/PATCH/DELETE）+ 敏感读（推流密钥、用户私有数据）

# === 模式 B: Optional Auth（可选鉴权）===
# 依赖: Depends(get_current_user_optional)
# 行为: 无 Token → None（匿名） | Token 无效 → 401（严禁降级匿名）
# 适用: 读操作（列表/详情/搜索）
```

### 2.3 权限守卫函数（`app/core/permissions.py` 当前实际实现）

这是权限体系的**核心单点**，被所有 Service 层复用：

```python
def check_room_owner_or_admin(room, user_id, role):
    """写操作权限校验 → 403"""
    if role in ('ADMIN', 'SUPERADMIN'): return
    if room.user_id == user_id: return
    raise PermissionDeniedException("需要管理员或房间创建者权限")

def check_room_visibility(room, user_id, role):
    """读操作可见性校验 → 404伪�"""
    if not room.is_private: return
    if not user_id: raise NotFoundException("Room not found")
    if role in ('ADMIN', 'SUPERADMIN'): return
    if room.user_id == user_id: return
    raise NotFoundException("Room not found")
```

### 2.4 CRUD 层 SQL 权限过滤（`app/crud/room.py`）

```python
async def get_multi_and_total(db, skip, limit, user_id=None, role=None, ...):
    query = select(LiveRoom)
    if role in ['ADMIN', 'SUPERADMIN']:
        pass                                    # 管理员：无过滤，看全部
    elif user_id:
        query = query.where(or_(
            LiveRoom.is_private == False,       # Regular：Public + 自己的 Private
            LiveRoom.user_id == user_id
        ))
    else:
        query = query.where(LiveRoom.is_private == False)  # 匿名：仅 Public
    # 然后 AND 业务筛选条件
```

### 5.3 P0-3: SRS 内部回调 HMAC 签名

**修改文件**: `app/api/v1/endpoints/internal.py`, `app/core/config.py`

**修改内容**:

```python
# config.py — 新增配置项
SRS_CALLBACK_SECRET: str = ""  # 生产环境必须设置，至少 16 字符

# internal.py — 增加 HMAC 签名校验
import hmac
import hashlib
from fastapi import Header, Request

@internal_router.post("/on-publish")
async def on_publish_post(
    request: Request,
    payload: SrsOnPublishPayload,
    signature: str = Header(..., alias="X-SRS-Signature"),
    db: AsyncSession = Depends(get_db)
):
    # 1. HMAC 签名校验
    body_bytes = await request.body()
    expected_sig = hmac.new(
        settings.SRS_CALLBACK_SECRET.encode(),
        body_bytes,
        hashlib.sha256
    ).hexdigest()
    if not hmac.compare_digest(signature, expected_sig):
        raise HTTPException(status_code=401, detail="Invalid signature")

    # 2. 业务逻辑（原有代码）
    await srs_callback_service.handle_on_publish(payload, db)
```

**SRS 配置侧**: SRS 的 `on_publish` hook 需配置携带 `X-SRS-Signature` header，值为 HTTP body 的 HMAC-SHA256。

**预期效果**: 只有持有 `SRS_CALLBACK_SECRET` 的服务能成功签名并调用回调接口，防止内网伪造推流事件。

### 6.3.1 Owner 路由合并方案（P1-3 的子任务）⚠️ 部分完成

> **2026-07 实施 / 2026-07-23 修正**。3 个 Owner 路由器全部删除（`room_tab_router`/`room_brand_owner_router`/`room_category_owner_router`）。inline 硬编码：Brand(1处)+Tab(5处)=6处已删，Category(2处)**保留** inline（分类为全局受控词汇，Admin Only）。房间分类由创建时 `category_ids` 字段实现，不暴露 Owner 管理端点。前端 4 文件 9 处改动配合 URL 切换。以下为原始设计记录。

#### 背景

当前项目中存在 **3 个模块共 7 个端点使用了 Owner 路由模式**（Admin 路由 + Owner 路由两套并行，功能相同但 URL 不同、权限检查方式不同）。这是历史增量开发形成的技术债务——最初只有 Admin 路由（Admin Only），产品要求"房间创建者也应能管理自己的资源"后，开发团队未修改 Admin 路由的权限逻辑，而是新增了 Owner 路由。

而其余功能（Session 的 CRUD、Topic 的 CRUD、Room 自身的 CRUD）均使用**正确的"一套路由 + Service 守卫函数"模式**——endpoint 层不做角色检查，Service 层的 `check_room_owner_or_admin` 统一判断 Admin 或 Owner。

#### 当前 Owner 路由使用清单

| 模块 | Owner 路由器 | 端点数量 | 对应 Admin 路由器 | 功能是否一致 |
|------|------|:---:|------|:---:|
| Tab 管理 | `room_tab_router` | 4（创建/更新/删除/上传图片） | `admin_tab_router` | ✅ **完全一致**（调用同一个 Service 方法，请求体和响应完全相同） |
| 品牌关联房间 | `room_brand_owner_router` | 1（绑定品牌） | `brand_admin_router` | ✅ **完全一致**（同方法、同参数） |
| 房间分类 | `room_category_owner_router` | 2（设置/删除分类） | `live_room_categories_admin_router` | ✅ **完全一致**（同方法、同参数） |
| **公众号关联房间** | *不存在* | 0 | `admin_rooms_official_accounts_router` | ⚠️ **缺失**：写操作只有 Admin 路由，Owner 无法管理自己房间的公众号关联 |

> **注意**: Tab 的 GET 操作不在此合并范围——`admin_tab_router` 的 `GET /admin/rooms/{id}/tabs`（管理后台看全量，含未启用 Tab）与 `public_tab_router` 的 `GET /rooms/{id}/tabs`（前端展示仅激活 Tab）**功能确实不同**，分两套路由是正确的设计，保留不变。

## 七-B、P2-8 开播权限详细设计

> 本方案于 2026-07-19 经多轮代码审查与讨论后定稿。核心原则：**开播权 ≠ 角色（Role），开播权 = 资格（Qualification）**。角色决定"成为 Owner 后能做什么"，资格决定"能否成为 Owner"。

### 7B.1 双路径开播资格模型

```
POST /api/v1/rooms
  │
  ├─ Role = ADMIN / SUPERADMIN
  │    → ✅ 始终可创建（管理后台需要）
  │
  └─ Role = REGULAR
       │
       ├─ 途径 A：认证专家
       │    expert = SELECT * FROM experts WHERE user_id = ?
       │    if expert AND expert.is_active:
       │    → ✅ 认证医生，可开播
       │
       ├─ 途径 B：管理员授权
       │    perm = SELECT * FROM broadcaster_permissions WHERE user_id = ?
       │    if perm:
       │    → ✅ 运营人员，管理人员特许可开播
       │
       └─ 两条途径均未命中
            → ❌ 403："需要认证专家或管理员授权才能创建直播间"
```

### 7B.2 数据库设计
