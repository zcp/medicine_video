## 一、核心结论（TL;DR）

1. **两个分支没有共同祖先**（`git merge-base` 为空），wechat-v1 是独立导入的完整代码快照（`b49c32e`）+ 6 次增量提交。**不能直接 `git merge`，只能人工逐模块对照融合。**
2. **双方各自增强，方向互补**：
   - **main（我方）**：分类层级体系（parent_id + live_room_categories 多对多 + is_primary）、专家科室受控词表（expert_departments）、首页/搜索增强、工作区未提交的手机号归一化 + can_stream 默认允许 + 真实阿里云短信、房间卡片聚合（room_card_service.py，未跟踪）
   - **wechat-v1（对方）**：内容安全分层分级（tier/whitelist/messages + 图片审核）、微信小程序登录、邮箱验证码登录、头像上传审核、留言三段式展示管线 + 用户自删留言、管理端用户/权限增强、账号注销联动、**私密试播通道**、Docker/nginx 部署体系重构
3. **最关键的 4 个融合决策点**（决定融合工作量）：
   - **content_safety 数据表结构冲突（Critical）**：PK String(36)/is_active vs UUID/enabled，约束不一致，分散在 live_core 和 users 两个服务
   - **分类体系二选一（High）**：层级多对多 vs 扁平单列 —— 牵连 homepage_search、room、expert 三处
   - **can_stream 语义统一（High）**：两边都翻转成"默认允许"，但模型/schema/JWT/迁移各改各的
   - **is_private 可见性语义（High）**：我方"完全隐藏(404)" vs 对方"unlisted 持链可读" —— 对方测播间功能依赖此语义
4. **好消息**：双方共享大量同源代码（留言/Tab 路由、专家、搜索、用户行为、品牌等），融合以"我方为基底 + 增量合入"为主。

### 一、终审结论

**融合完成度高（功能 100% 落地、实现正确性核心机制全对）**，但发现 **3 高危 + 5 中危** 隐患。其中 2 个高危为融合直接引入（H1/H2），1 个为基线既有缺陷被审查发现（H3）；中危中 1 个经实测复现（M1）。

### 二、高危修复（已完成，提交 `0558b2d`）

| # | 隐患 | 根因 | 修复 | 验证 |
|---|------|------|------|------|
| H1 | live_core 不校验 token type，refresh token（7 天）可冒充 access token 访问全部业务/管理 API | `auth.py` verify_token 只查 user_id，users 侧有校验 live_core 没有（跨服务不对称） | `payload.get("type") != "access"` 拒绝（1 行） | refresh token→401 / access token→200 |
| H2 | 留言违规拦截被端点 `except Exception` 吞成 500，全局 422/2005 handler 永不触发 | 融合引入 ContentSafetyBlockedException 未同步端点捕获分支（except Exception 是基线代码） | send_message 加 `except ContentSafetyBlockedException → 422/2005` | 违规留言→422/2005 / 未知异常→500 |
| H3 | WS 留言推送无鉴权，任何人可订阅私有房间留言流 | `room_messages_websocket` 直接 accept，无 JWT/可见性检查（基线既有缺陷） | query token 可选鉴权（匿名仅公开房间）+ check_room_visibility 校验，拒绝 close 4401/4403/4404 | 五场景冒烟全过（公开匿名 accept/私有匿名拒/owner accept/他人拒/坏 token 拒） |

> 注：前端当前无 WS 消费代码，H3 加鉴权零兼容负担；修复时确认 `verify_token` 仅两个用户 API 调用方，internal 走 X-Internal-Token 不受影响。
