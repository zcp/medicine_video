## 一、执行摘要

### 1.1 背景

平台存在多组"主实体 ↔ 关联实体 ↔ 被关联实体"关系（直播间/场次 ↔ 标签/专家/品牌/分类，焦点图 ↔ 房间/场次/专题/品牌，用户 ↔ 订阅/收藏）。经 2026-08-14 代码级审查，发现**删除路径上的关联清理覆盖不一致**：部分路径有外键 CASCADE 或手动清理兜底（如删房间），部分路径**无外键、无清理、展示时不校验**（如焦点图 target、单删场次后的用户订阅），存在悬挂引用（dangling reference）风险。

### 1.2 核心结论

1. **"直播间关联标签/专家"在实现上是"场次关联"**：标签走 `session_tags`、专家走 `live_session_experts`，均挂在 `live_sessions` 上，非 `live_rooms`。直播间本身只有分类（`live_room_categories`）与品牌（`brand_rooms`）直接关联。
2. **标签、专家、品牌删除均为软删除（`is_active=False`）**：关联记录全部保留，展示层通过过滤或字段标记控制可见性——设计上是安全的，问题在于**过滤不一致**（专家读取不过滤、标签设置不校验）。
3. **真正的高危点是"无外键的应用层关联"**：
   - `featured_content.target_id`（models/homepage_search.py:34，注释明示不设外键）→ 品牌/房间/场次/专题删除后**悬挂引用**，公开列表不校验 target 有效性 → 前端点击死链；
   - `user_subscriptions.target_id`（models/user_behavior.py:179，同样无外键）→ **单删场次路径不清理**（删房间路径已手动清理），订阅记录悬挂。
4. **分类模块是全项目关联治理范本**：引用计数 + 阻断 + 迁移 + 级联停用闭环（`count_category_references` / `migrate_category_references`），可作为其他模块方案参照。

### 1.3 问题总览

| 级别 | 问题 | 关联域 | 现状 | 建议 |
|:---:|:---|:---|:---|:---|
| 🔴 P0 | 焦点图 target 悬挂引用：品牌/直播间/场次/专题删除后不清理、展示不校验 | 焦点图×品牌/房间/场次/专题 | 悬挂 | 删除时清理 + 读取时校验双保险 |
| 🔴 P0 | 单删场次后 `UserSubscription(SESSION)` 悬挂 | 订阅×场次 | 悬挂 | 删除场次时同步处置订阅 |
| 🟡 P1 | 专家软删除后，场次专家列表仍返回该专家（读取不过滤） | 专家×场次 | 返回已删专家 | 读取时按角色过滤 |
| 🟡 P1 | 软删除标签仍可被"设置"到新场次（写入不校验） | 标签×场次 | 可关联但不展示 | 写入时校验 is_active |
| 🟢 P2 | 品牌软删除后其关联的直播间/专题仍保留引用（语义待定） | 品牌×房间/专题 | 保留 | 保持现状，仅文档化口径 |

### 1.4 范围界定

| 范围 | 内容 |
|------|------|
| ✅ 本次实施 | 焦点图悬挂引用治理（P0-1）、场次删除订阅清理（P0-2）、专家读取过滤（P1-1）、标签写入校验（P1-2）、关联治理基线测试、**测试数据登记与清理管理（E1，贯穿各阶段）** |
| ⏸️ 暂缓 | P2 品牌软删语义口径（产品侧确认）、历史脏数据一次性清洗脚本（视治理后数据核对结果再定） |
| ❌ 不实施 | 分类模块改造（现有闭环已是范本，仅作参照）；为 `featured_content.target_id` / `user_subscriptions.target_id` 补数据库外键（跨表多态关联，PostgreSQL 无直接外键支持，方案见 §7.2）；推送消息/通知等其他跨服务引用；**前端专题功能（Topic 模块前端暂不实现，本次仅做后端数据一致性修复，不触碰任何专题前端契约）** |

### 1.5 预期效果

| 维度 | 现状 | 实施后 |
|------|------|--------|
| 焦点图 target 有效性 | 删除品牌/房间/场次/专题后悬挂，展示不校验 | 删除时同步处置 + 公开列表过滤失效 target，前端不再出现死链 |
| 场次订阅一致性 | 单删场次后订阅悬挂（删房间路径已清理） | 两条删除路径行为一致，订阅记录不悬挂 |
| 场次专家可见性 | 软删专家仍出现在场次专家列表 | 普通用户不可见，管理员可见（便于后台管理） |
| 标签写入校验 | 软删标签仍可被设置 | 与专家写入语义对齐（仅启用标签可关联） |

### 5.7 专家与分类的关联治理专项分析（V1.2 新增）

**结论先行**：专家-分类之间**不存在需要本次治理的问题**——分类模块已实现完整闭环（§5.6），合并/删除场景下专家均有明确、安全的处理路径，本次治理零改动该域。

**结构性差异**：专家-分类是**单值外键关联**（`Expert.category_id` NOT NULL + `NO ACTION` 外键，models/experts.py:61-66），与"无外键多态关联"（焦点图/订阅）结构不同；外键 NO ACTION 本身即拦截非法删除，加应用层三档保护为双保险。

**场景一：合并分类 → 原分类的专家如何处理**（`content_management_service.py merge_categories`，L850-999）：

| 处理项 | 行为 |
|------|------|
| 专家 | `Expert.category_id == source_id` 的专家**整体迁移**到 target（L979-982 复用 `migrate_category_references`） |
| 科室 | ExpertDepartment 先行迁移，再迁专家——保持"科室/专家同分类"一致性（L980） |
| 房间关联 | source 行迁 target，target 已关联去重 |
| 子分类 | 挂到 target 下或提升一级；**子分类下的专家不随迁**（子分类仍在，其下专家不搬家，正确） |
| 软删 source | 引用清空后单行软删（L984） |
| 预览 | `dry_run` 预览统计（L951-967）+ "专家科室分类不一致"数量提示（L937-943） |

即：**合并分类时原分类专家自动、无感归入目标分类**。✅ 闭环

**场景二：删除分类 → 其余专家如何处理**（`delete_category`，L629-766）：

| 场景 | 行为 |
|------|------|
| 无引用 | 直接软删（is_active=False），无专家受影响（L709-715） |
| 有引用 + 非 force | **阻断删除**：返回结构化 references + 中文 warnings，明示"有 N 位专家引用，停用后按分类筛选无法命中"（L677-706） |
| 有引用 + force | 单事务三连：①解析迁移目标（指定 target 或缺省 **"其他"兜底分类**，L719-726）；②迁移专家/科室/房间（**子树级**含子分类，L735-740）；③级联软删整棵子树（L743） |

另有独立迁移端点 `migrate_category`（L794-848，scope=experts/departments/rooms/all），支持不删分类单独挪走引用。

即：**删除分类时专家绝不会成为孤儿**——非 force 被阻断，force 被迁移到指定目标或"其他"兜底。✅ 闭环

**两个已知小瑕疵（记录在案，非本次范围）**：
1. **scope 单迁可制造不一致**：`migrate_category` 支持只迁专家（scope=experts）或只迁科室（scope=departments），单独执行会制造"专家分类与科室分类不一致"；代码有统计提示但未阻止——属已知工具语义，运营需按全量迁移使用。
2. **"其他"兜底分类是硬依赖**：force 删除缺省迁到 slug="other"，该分类不存在时直接报错并引导 seed 初始化（L721-725）——依赖种子数据完整性。

**与本次治理的关系**：分类停用后其下专家**只是按分类筛选时不可命中**（`get_category_descendant_ids` 过滤 is_active，crud/content_management.py:46），专家本身仍正常展示、可被场次关联——这是**有意的设计语义**（已在删除 warnings 中明示），不是缺陷。本次治理的痛点（无外键多态关联）与分类域（单值外键）结构不同，无交叉。

## 六、问题根源分析

### 6.1 结构性根因：无外键的多态关联缺乏生命周期管理

`featured_content.target_id` 与 `user_subscriptions.target_id` 均为**多态外键**（一个字段指向多张表），PostgreSQL 不支持直接声明多态外键约束，设计上退化为"应用层关联 + 应用层校验"。但当前**删除侧**只做了"创建/更新时校验"（焦点图）或"聚合时防御性跳过"（订阅），**删除目标实体时没有反向清理/处置逻辑**，且**展示侧没有有效性兜底** → 悬挂引用必然产生。

### 6.2 治理不一致根因：软删策略的过滤/校验分布不均

| 软删实体 | 写入校验 | 读取过滤 | 恢复语义 |
|---|---|---|---|
| Tag | ❌ 不校验 is_active（P1-2） | ✅ 过滤 | 恢复即自动可见 |
| Expert | ✅ 校验（set_session_experts） | ❌ 不过滤（P1-1） | 恢复即自动可见 |
| Brand | ✅ 校验（绑定前 is_active 校验，brand_service.py:644-656） | ✅ 过滤（get_room_brands） | 恢复即自动可见 |

写入与读取两端的语义不对称，导致"删了但还显示 / 能设置但看不见"的体验断裂。

### 6.3 删除路径覆盖不一致

- 删房间：`delete_room_related` 集中清理 11 类关联 ✅（维护成本在"每次新增关联都要记得补清单"）
- 删场次：依赖 DB 级联（有外键的部分），无外键的部分（订阅/焦点图）无人管 ❌
- 删专题：仅 FK 级联（TopicCategory/BrandTopic），无外键的部分（焦点图）无人管 ❌（V1.1 已纳入处置）
- 删品牌/删专家/删标签：软删为主，关联保留是设计意图，但展示/写入语义未统一

## 七、目标方案设计

### 7.1 设计原则

1. **增量最小化**：不改数据库表结构、不改既有外键、不动认证体系；优先在既有删除路径与查询函数内做增量修改
2. **删除侧 + 读取侧双保险**：删除目标实体时同步处置引用（主），展示查询时过滤失效引用（兜底）——防"漏清"与"历史脏数据"两类问题
3. **软删语义保持**：标签/专家/品牌软删后关联保留、恢复即见，不引入物理删除
4. **与既有语义对齐**：写入校验参照 `set_session_experts`（仅启用可关联）；读取过滤参照 `get_tags_by_session_id`（非管理员不可见已停用）
5. **逐阶段可独立验收**：每阶段 Gate 通过后才进入下一阶段

### 7.2 P0-1：焦点图悬挂引用治理

**方案对比**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 删除时处置（主） | 删房间/场次/品牌/专题时同步处置指向它的 FeaturedContent | 源头治理，不产生新悬挂 | 需要四处删除路径都改；品牌软删时是否处置需决策 |
| B. 读取时过滤（兜底） | 公开列表查询时按 target_type 校验 target 有效性，失效跳过 | 历史脏数据也兜住 | 多态校验查询成本；target_type 5 类需分别写 EXISTS |
| C. 仅读取时过滤 | 不删不改，只过滤 | 改动最小 | 悬挂数据一直留在库里，管理端可见脏数据 |
| **A+B 组合（推荐）** | 删除时处置 + 读取时过滤 | 源头治理 + 历史兜底，双保险 | 改动量最大（但增量小、逻辑简单） |

**推荐 A+B 组合，具体处置策略**：

**删除侧（主）**：
1. **删直播间**：`delete_room_related`（crud/room.py:585）追加处置 `FeaturedContent`：`target_type='room' AND target_id=room_id` 的焦点图 → **软下线**（`is_active=False`，保留记录便于运营恢复）【D1 已定稿：软下线】
2. **删场次**：`session_service.delete_session`（session_service.py:609）同逻辑处置 `target_type='session'` 的焦点图
3. **删品牌**：`brand_service.delete_brand`（brand_service.py:302）：
   - 软删：将指向该品牌的焦点图一并**软下线**（与品牌状态一致）【D3 已定稿：是】
   - 硬删：`check_brand_references` 增加焦点图引用计数，**有引用即拒绝**（与 BrandTopic/BrandRoom 同语义）【D2 已定稿：拒绝】
4. **删专题**（V1.1 新增）：`topic_service.delete_topic`（topic_service.py:423）同逻辑处置 `target_type='topic'` 的焦点图。专题前端暂不实现，本次仅后端数据一致性修复，不动任何专题 API 契约

**读取侧（兜底）**：`crud/homepage_search.py get_featured_content_list`（公开）增加 target 有效性过滤——按 target_type 分别 EXISTS（room 查 live_rooms、session 查 live_sessions、topic 查 topics、brand 查 brands.is_active=true）；失效条目跳过。管理端列表（`get_featured_content_list_paginated`）保持全量可见，便于运营发现并处理。

**为什么这样改**：
- 处置放在删除路径（`delete_room_related` 已是集中清理点），符合现有工程结构，不新增加删除入口
- 软下线而非硬删：保留运营配置痕迹，与品牌软删语义一致（`is_active` 恢复即可重新上线）
- 读取过滤是"防御性兜底"，即使删除路径未来漏改或存在历史脏数据，公开接口也不返回死链

### 7.3 P0-2：单删场次后订阅悬挂治理

**方案**：`session_service.delete_session`（session_service.py:609）在删除场次前，参照 `delete_room_related` 的订阅清理逻辑（crud/room.py:601-607），处置 `UserSubscription`：`target_type='SESSION' AND target_id=session_id` → **硬删**（`delete()`，与删房间路径一致）。

> 注：`delete_room_related` 对 SESSION/ROOM 两类订阅均使用 `delete()` 硬删（crud/room.py:601-622），**非**软删置 `is_active=False`；用户停用清理场景（`deactivate_cleanup_service`）才用软删更新。**D5 已定稿（2026-08-14）：订阅处置采用硬删**，理由见 §13。

**为什么这样改**：
- 与删房间路径（crud/room.py:601-607）行为完全对齐，两条删除路径语义一致，不做双轨差异
- 订阅表唯一约束 (user_id, target_id, target_type) 不受硬删影响（场次已删除，target 不可再订阅）
- 场景小（单个场次），改动集中在 1 处

### 7.4 P1-1：场次专家列表读取过滤

**方案（V1.1 修订：下沉 CRUD 层）**：`crud/experts.py get_session_experts`（L683）增加 `role: Optional[str]` 参数，SQL 级追加过滤条件；`expert_service.get_session_experts`（expert_service.py:1340）将 `role_user` 透传：

```python
# CRUD 层带 role 的 SQL 级过滤（参照 get_tags 的既有模式，content_management.py:168-172）
stmt = select(LiveSessionExpert).where(LiveSessionExpert.session_id == session_id)
if role not in ('ADMIN', 'SUPERADMIN'):
    stmt = stmt.join(Expert, Expert.id == LiveSessionExpert.expert_id) \
               .where(Expert.is_active == True)
```

- 普通用户：`Expert.is_active == False` 的专家**不返回**
- ADMIN/SUPERADMIN：全量返回（管理后台需要看到已停用专家及其场次）
- 响应中 `is_active` 字段保留（前端无需改动）

**为什么这样改**：
- **下沉 CRUD 层是 V1.1 评审修正**：Service 层过滤可被未来直接调用 CRUD 的消费方绕过；CRUD 层带 role 的 SQL 级过滤与 `get_tags`（content_management.py:168-172）、`get_categories` 的既有模式一致，任何调用方都无法绕过
- 与 `get_tags_by_session_id`（content_management.py:1042）的过滤语义对齐
- 与 `set_session_experts`（L1316）"仅启用可关联"形成"写时校验 + 读时过滤"闭环
- 管理员可见保留：已停用专家关联的场次需要后台排查（如"某场次为何显示停用专家"），过滤掉反而丢信息

### 7.5 P1-2：标签写入校验

**方案**：`content_management_service.set_session_tags`（content_management_service.py:1117）在现有"标签存在"校验上追加 `Tag.is_active == True` 校验，任一标签已停用即抛 `InvalidParameterException`（4001，语义与"部分标签ID不存在"一致）。

**为什么这样改**：
- 与 `set_session_experts`（expert_service.py:1316）"仅允许启用状态的专家关联场次"语义对齐

| D1 | 焦点图处置方式：软下线 vs 清空 target 转外链 vs 硬删 | 软下线 / 清空 / 硬删 | ✅ **软下线**（2026-08-14） | ①焦点图记录（图片/标题/排期）是运营资产，target 失效≠内容失效，硬删不可逆；②清空转外链在删除路径上无 URL 输入来源，且"target 空仍在播"状态混乱；③与全系统软删语义统一，管理端可见、可手动恢复。**不做自动恢复**（避免运营已改配 target 的焦点图被意外复活） |

| D5 | 订阅处置方式 | 硬删 / 软删 | ✅ **硬删**（2026-08-14） | ①与删房间路径对齐（一致性）；②不依赖消费方 is_active 过滤纪律（机制性安全）；③软删的历史保留价值为零——场次已物理删，卡片无法渲染，记录不可展示；④改动最小 |

> **D5 定稿依据补充**：消费方 `get_subscriptions` 已带 `only_active=True`（user_behavior_service.py:275/282），软删在当前消费方下不会误展示；但"表内无悬挂 + 不依赖任何消费方纪律"是本次治理的核心目标，硬删从机制上保证，软删靠纪律保证。软删仅在未来出现"订阅行为分析/场次复活/合规审计"需求时才有价值，届时再评估。
