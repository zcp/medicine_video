## 一、执行摘要

### 1.1 背景

私密房间（`is_private=True`）自上线以来处于"能建不能用"状态：本地后端语义为**严格 404 隐藏**（`permissions.py:54-85`，仅 ADMIN/SUPERADMIN + 创建者可访问，其余用户 404 隐藏房间存在性），导致私密房**没有任何对外分发渠道**——除了创建者自己，其他人永远无法进入。产品价值落空（测播、小范围定向直播、内部演示等场景全部无法展开）。

经实测核验：远程 wechat-v1 分支采用 **unlisted（不公开但持链可读）** 语义（`_check_room_visibility` 空校验无条件放行，发现层仅靠列表/搜索 SQL 过滤），天然支持"分享链接给他人即可观看"，且其测播间（test-room）依赖此语义。

### 1.2 核心结论

1. **接入私密房分享能力（unlisted 语义）**：本地后端改动集中在 1 个函数（`permissions.py` 的 `check_room_visibility`），6 个可见性调用点自动跟随；**不照搬 wechat 代码，吸收语义、保留我方集中式权限架构**
2. **App 端分享进入路径采用"剪贴板检测"**（复制邀请文本 → 打开 App → 自动识别 → 弹窗确认进入），纯前端实现、零外部配置，完全契合"复制链接后打开 App 自动提示"的设想
3. **我的页面新增"私密房间"菜单入口，分两阶段**：阶段 1 仅展示**自己创建的**私密房（零后端新表）；阶段 2（暂缓）新增受邀访问记录表 `user_room_access`，展示自己创建 + 受邀访问过的
4. **WS 语义确认方案 B**：REST 读放行；WS 留言流私密房仅**创建者+管理员**可订阅，其余持链观众（含登录用户）走 5s 轮询兜底（保护 H3 已修复的鉴缺口子）
5. **收藏私密房支持**（新增）：收藏操作已不校验可见性（当前即可收藏），仅**收藏列表硬编码过滤私密房**（crud/user_behavior.py:158,178）需放开 ~4 行——收藏成为受邀者"再次进入私密房"的主动入口，部分承接阶段 2 的价值
6. **观看历史保持"私密房不留痕"**（方案 A）：观看历史继续过滤私密房（user_behavior.py:309,330），符合私密房"不被公开发现"的语义
7. **产品确认**：unlisted = 链接泄露即公开，**无审计、无撤回、无分享记录**，持链可看房间内全部内容（Tab 资料/留言/回放）——**已确认接受**；观看不限制、留言/收藏等操作要求登录（与后端现状一致）
8. **小程序分享（F4）移除**：小程序端分享不由我方实现与验证，范围外

### 1.3 范围界定

| 范围 | 内容 |
|------|------|
| ✅ 本次实施 | 后端 unlisted 语义 + WS 方案 B + `/users/me/rooms` 补 is_private 字段 + **收藏列表放开私密房** + 测试适配；App 端剪贴板检测分享；我的页面"私密房间"入口（自己创建） |
| ⏸️ 暂缓（阶段 2） | 受邀访问记录表（`user_room_access`）、我的页面"受邀的私密房"、分享记录/统计 |
| ❌ 不实施 | 小程序分享（F4，已移除）；H5 分享落地页（H5 LiveView 为 mock 未接真实 API）；测播间（test-room，依赖本语义，另行排期）；分享 token/授权码（管控型分享，后续演进）；访问审计/撤回机制；观看历史记录私密房（方案 A，保持不留痕） |

### 1.4 预期效果

| 维度 | 现状 | 实施后 |
|------|------|--------|
| 私密房价值 | 仅创建者/管理员可见，无用处 | 持链可看：测播、小范围定向直播、内部演示等场景可用 |
| App 端进入体验 | 无任何入口 | 复制链接 → 打开 App 自动弹窗确认进入（观看不限制，匿名可看） |
| 我的页面 | 无私密房聚合入口 | "私密房间"菜单：自己创建的私密房列表 |
| 收藏能力 | 收藏私密房后列表不返回（crud 过滤） | 收藏列表返回私密房：受邀者"再次进入"的主动入口 |
| 观看历史 | 私密房不留痕 | 保持不留痕（方案 A，符合隐私语义） |
| 安全边界 | 404 严格隐藏 | 发现层仍过滤（不进列表/首页/搜索），仅持链可读 |

### 2.2 wechat-v1 分支私密房间实现（实测 `git show origin/wechat-v1`）

**语义：私密房 = unlisted（不公开但持链可读），仅靠发现层过滤**

| # | 层 | 实现 | 位置 |
|---|----|------|------|
| 1 | 模型 | `is_private` + **`source_room_id` 自引用 FK**（部分唯一索引，一正式间至多一测播间） | `models/live_core.py:60,69-103` |
| 2 | 读可见性 | `_check_room_visibility` **空校验无条件放行**：任何人（含匿名）持 room_id 即可读；ADMIN 查看仅打日志 | `services/room_service.py` |
| 3 | 留言/Tab 可见性 | **仅注释**"持有 room_id 即可读"，无实际校验代码 | `endpoints/live_features.py:785` |
| 4 | 列表/首页/搜索过滤 | `is_private == False` | `crud/room.py:155,303,307`、`crud/homepage_search.py:336,338,548` |
| 5 | 管理端筛选 | is_private 参数 + updated_at DESC | `crud/room.py:184,199-200` |
| 6 | **测播间** | `POST /rooms/{room_id}/test-room`（幂等 ensure_test_room，复制标题/封面/分类，强制 is_private=true，持链可看） | `endpoints/room.py:359-407` |

**分享机制核查结论**：wechat-v1 **无专门分享端点**（无 share/invite/token 路由），其"分享"即 unlisted 语义本身——"链接（room_id）= 门票"；`session.statistics.total_share_count` 仅是分享次数统计，与访问授权无关。

### 2.5 关键事实（影响方案的事实链）

1. 房主自己的私密房：后端 `GET /users/me/rooms`（owner_only）**包含**（`crud/room.py:336-346`：`is_private == False OR user_id == user_id`），但前端无封装、响应无 is_private 字段 → **菜单入口数据源需补 1 行 + 前端封装**
2. 前端"我的直播"当前**看不到自己的私密房**（数据源问题）→ 本次一并修复
3. 私密房不出现在公开列表/首页/搜索（发现层过滤已完备，unlisted 后无需改动）
4. 写权限（修改/删除）走 `check_room_owner_or_admin`，独立于可见性 → unlisted 只放开"读"，**写不受影响**
5. 留言发送需登录（`get_current_user`）→ 持链者可读但**未登录不能发留言**
6. WS 留言鉴权（H3 修复）当前对私密房拒绝非创建者（close 4403）→ 本次需决策（见 4.3）

## 四、目标方案

### 4.1 设计原则

| 原则 | 内容 | 对应需求 |
|------|------|---------|
| P1 | **发现层语义不变**：私密房继续不进列表/首页/搜索（SQL 过滤已完备，零改动） | R1 |
| P2 | **读写分离**：unlisted 只放开"读"，写（修改/删除/留言发送）权限边界不变 | R1 |
| P3 | **集中式单点修改**：语义变更收敛在 `permissions.py` 一个函数，6 个调用点自动跟随，不照搬 wechat 内联写法 | R1 |
| P4 | **App 分享零配置**：分享进入用剪贴板检测，不依赖 scheme/Universal Link（外部配置成本高） | R6 |
| P5 | **双通道兜底**：分享链接进入 + 我的页面菜单入口互为补充（剪贴板被覆盖时有第二通道） | R6/R7 |
| P6 | **阶段推进**：阶段 1 先跑通"分享→进入→入口"，阶段 2（访问记录）待产品确认后再做 | 全部 |
| P7 | **安全保守**：WS 不跟随完全放行（私密房留言流仅创建者+管理员可订阅），保护 H3 修复成果 | R2 |
| P8 | **主动记录优先**：收藏放开作为受邀者"再次进入"入口（V1.1 新增），优先级高于阶段 2 访问记录表 | R4 |

### 4.2 方案选型

#### 4.2.1 私密房读语义（方案 A/B/C）

| 方案 | 内容 | 评价 |
|------|------|------|
| A | 维持 404 严格隐藏，不做分享 | ❌ 私密房继续无价值，需求落空 |
| B | **unlisted 语义（对齐 wechat）：持链可读，发现层过滤** | ✅ **采纳**：改动最小（1 函数）、分享天然成立、测播间前置铺垫；代价=链接泄露即公开（产品接受） |

### 4.3 目标架构与数据流

```
【分享链-App】详情页"邀请"按钮 → setClipboardData 复制邀请文本
              → 他人打开 App → onShow 读剪贴板 → 正则匹配 room UUID
              → 防重复标记 → GET /rooms/{id} 取标题 → showModal 确认
              → 直接进入 LiveView?roomId={id}（观看不限制，匿名可看；留言/收藏等操作要求登录）
【收藏链】    观众观看私密房 → 收藏按钮（需登录）→ 我的收藏列表返回私密房 → 点击再进
【菜单入口】  我的页面 → 私密房间 → GET /users/me/rooms（含 is_private）

```

| 操作 | 公开房 | 私密房（创建者/管理员） | 私密房（持链普通用户/匿名） |

| 房间详情 /users/me/rooms | ✅ | ✅ | ✅（持链可读，REST） |
| 场次/Tab/留言列表/专题 | ✅ | ✅ | ✅（REST） |
| 留言发送 | ✅（需登录） | ✅ | ✅（需登录，语义不变） |
| **收藏操作/收藏列表** | ✅ | ✅ | ✅（**需登录**；V1.1 放开列表 is_private 过滤） |
| **观看历史** | ✅ | ✅（创建者观看记录） | ❌（**保持不留痕**，V1.1 确认方案 A） |
| WS 留言订阅 | ✅（匿名可） | ✅ | ❌（方案 B：仅创建者/管理员 4403 例外，其余轮询兜底） |

### 附录 B：wechat-v1 分享机制核查摘要

- wechat-v1 **无专门分享端点**：无 share/invite/token 路由，无邀请码/二维码/访问记录/撤回
- 其"分享"= unlisted 语义本身（`_check_room_visibility` 空放行，room.py 无分享路由）
- `total_share_count`（models/live_core.py:190）仅为分享次数统计，与访问授权无关
- **本地 main 接入方式**：不照搬 wechat 代码（内联空校验），改集中函数 `permissions.py` 单点，6 调用点自动跟随——架构上优于 wechat
