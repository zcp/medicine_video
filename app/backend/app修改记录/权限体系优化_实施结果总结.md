## 二、已完成项详细说明

### 2.1 P0 安全漏洞（3/4 完成）

#### P0-1: StreamKey 脱敏 ✅

| 项目 | 内容 |
|:----|:----|
| **问题** | `GET /api/v1/rooms/{id}` 使用 Optional Auth，响应直接包含 `stream_key`，匿名用户可获取公开房间推流密钥 |
| **方案** | 在 endpoint 响应构建处做展示层裁剪 |
| **实现** | `room.py:339`：`stream_key` 仅当 `user_id and (room.user_id == user_id or role in ('ADMIN','SUPERADMIN'))` 时返回真实值，否则返回 `null` |
| **效果** | 匿名用户和非 Owner Regular 用户看到的 `stream_key` 为 `null` |
| **验证** | `tests/integration/test_api_room_permission_state.py` 集成测试覆盖 |

#### P0-2: 场次标签 ownership 检查 ✅

| 项目 | 内容 |
|:----|:----|
| **问题** | `add_session_tag` / `remove_session_tag` 仅检查"是否登录"，不检查 session 所属 room 的 ownership，任何登录用户可操作任意场次标签 |
| **方案** | Service 层增加 JOIN room → `check_room_owner_or_admin` |
| **实现** | `content_management_service.py`：两个方法新增 `session → room → ownership` 链路检查 |
| **效果** | REGULAR 用户只能对自己房间的场次增删标签 |
| **验证** | 集成测试覆盖 |

#### P0-4: 科室列表补 Admin 校验 ✅

| 项目 | 内容 |
|:----|:----|
| **问题** | `GET /admin/expert-departments` 仅 Strict Auth（登录即通过），无 Admin 校验 |
| **方案** | 补充 `_check_admin_permission(role)` 调用 |
| **实现** | `expert_departments.py:26`：新增 role 提取 + `service._check_admin_permission(role)` |
| **效果** | REGULAR 用户访问 `GET /admin/expert-departments` 返回 403，与同文件其余 6 个端点一致 |
| **验证** | 集成测试覆盖 |

#### P0-3: SRS 回调 HMAC ❌ 阻塞

| 项目 | 内容 |
|:----|:----|
| **原因** | 等待 SRS 服务端配置确认 |

| **状态** | 代码未实施，设计已完成 |

### 2.2 P1 系统性改造（6/6 全部完成）

#### P1-1: deps.py 统一 role 规范化 ✅

| 项目 | 内容 |
|:----|:----|
| **问题** | 全库约 52% 的 role 使用未调 `.upper()`，JWT 签发小写 role 时 Admin 功能静默失效 |
| **方案** | 在依赖注入阶段统一规范化 role |
| **实现** | `deps.py`：`get_current_user` 和 `get_current_user_optional` 中增加 `token["role"] = str(token.get("role", "REGULAR")).upper()` |
| **效果** | 全库 endpoint 和 Service 层拿到的 role 100% 大写。下游原有的 `.upper()` 调用无副作用，保留向前兼容 |
| **涉及文件** | `app/core/deps.py`（2 处修改） |

#### P1-2: 守卫函数统一到 permissions.py ✅

| 项目 | 内容 |
|:----|:----|
| **问题** | `_check_admin_permission` 在 6 个 Service 中各重复一份，改一处漏一处产生安全漏洞 |
| **方案** | 删除所有 Service 内部私有守卫函数，改为统一 import |
| **实现** | `permissions.py` 扩展：新增 `check_admin_permission`、`check_resource_owner_or_admin`、`check_authenticated_user`；6 个 Service 文件删除各自定义并改为 `from app.core.permissions import ...` |
| **涉及文件** | `app/core/permissions.py`（扩展） + `expert_service.py`、`content_management_service.py`、`live_features_service.py`、`brand_service.py`、`batch_import.py`、`homepage_search_service.py` |
| **效果** | 权限逻辑集中在 `permissions.py` 单点，未来改一处即可全局生效 |

#### P1-3: Endpoint 预检查下沉 + Owner 路由合并 ⚠️ 部分完成（Category 例外）

| 项目 | 内容 |
|:----|:----|
| **问题** | 8 处 endpoint 层硬编码 `if role not in ('ADMIN','SUPERADMIN'): return 403`；3 套 Owner/Admin 并行路由共 7 个重复端点 |
| **方案** | 删除 3 个 Owner 路由器、7 个 Owner 端点、6 处硬编码（Brand 1处 + Tab 5处）；分类 2处 inline 保留（全局受控词汇，Admin Only） |
| **实现** | 删除 `room_tab_router`(4 端点)、`room_brand_owner_router`(1 端点)、`room_category_owner_router`(2 端点)；6 处 endpoint 硬编码改为 Service 层权限守卫；分类 2 处保留 inline |
| **例外说明** | `content_management.py` 的 Category 接口 inline 保留，因 Category 为全局受控词汇，Owner 通过房间创建 `POST /api/v1/rooms` 时传入 `category_ids` 关联分类，不通过 `/admin/` 端点管理 |
| **删除代码** | ~320 行重复代码 |
| **前端影响** | 7 个 API URL 切换 + 2 处签名适配（前端 4 文件 9 处改动） |
| **效果** | Tab/Brand 功能一套路由，`/admin/` 前缀从"调用者身份标签"变为"管理操作标签"，Service 层精确放行 Admin+Owner；分类 Admin 端点语义不变 |

## 五、关键决策记录

| 决策 | 结论 | 理由 |
|:----|:----|:----|
| P0-1 StreamKey 在 endpoint 层脱敏而非 Service 层 | Endpoint 层 | 鉴权已在 Service 层完成，脱敏是展示层裁剪，不属于业务逻辑 |
| P1-2 守卫函数放在 `permissions.py` 而非 `core/` 其他位置 | `permissions.py` | 该文件已存在且命名语义匹配 |
| P1-3 `/admin/` 语义不变但权限放宽 | 语义变为"管理类操作" | 改名成本高（前端全改），加注释即可。Service 层精确控制权限 |
| P1-5 不移除 deps.py 测试 fixture 的 `sub` | 保留 | fixture 是数据源，不是消费者，移除会影响测试兼容性 |
| P2-8 Expert ≠ Broadcaster | 分离设计 | Expert 是内容身份（Admin curated），Broadcaster 是操作权限（可认证获得），两条轨道解耦 |
