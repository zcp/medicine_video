## 一、执行摘要

### 1.1 背景

小程序端（wechat-v1）已在提交 `890ef2b`（2026-09-01，"标签管理 V2（场次绑标签、resolve 自建与内容安全）"）中落地标签管理 V2：**场次绑/删标签权限收紧为房主或 Admin**、**tag_ids 上限 0～5**、**新增用户侧"解析或创建标签"接口 `POST /content/tags/resolve`**、**tags 表新增溯源字段 `created_by/source`**，并接入内容安全 `tag_name` 场景。

我方 App 端 main 分支在上述提交之前（自 2026-08-14 共同基线 `1395261` 起）**未对 content_management 模块做任何改动**，标签能力仍停留在 V1 口径：任意登录可写他人场次标签、`tag_ids` 1～50、无自建入口、无溯源字段。

为对齐双端能力与契约，计划将 wechat-v1 的标签 V2 能力融合接入 main。本文档记录：功能核验结论 → main 缺口 → 方案对比与决策口径 → 分层改动设计 → **实施项级拆解（风险/改动量/难度）** → 分阶段 Gate 实施规划与验收，作为实施基线。

### 1.2 核心结论

1. **wechat-v1 已把设计文档的阶段 1 + 阶段 2 全部落地**（文档自身仍标注"阶段 2 待实现"，**以代码为准**）。
2. **main 与 wechat-v1 在 content_management 模块的标签子模块同源、分叉极小**（差异均为增量型）；但两分支的 *分类（category）子模块*、迁移体系、seed 体系已分叉 → **禁止整分支 merge，采用"人工逐模块移植 + 直接 main 顺序提交"**。
3. **main 已具备全部所需基础设施**：`app/core/permissions.check_room_owner_or_admin`（房主权限函数已存在并已在 service 层 import）、同构内容安全模块（`check_scene_fields` 已在，仅差 `tag_name` 矩阵一行）、同样的路由/异常码体系、**main.py 全局 422 exception handler 已存在（:65-81）** → 移植成本低、风险可控。
4. **3 项关键口径已在讨论中定稿**：数量上限维持 5（两端契约一致）；resolve 自建标签为**公共词表立即可见**（维持 wechat 现设计，不加私有/审核字段）；**融合直接在 main 上顺序提交，不建 feature 分支**（先推送 main 现状 → 再按原子提交融合）。
5. **V1.1 完成实施前评估**：全案拆解为 **29 项实施项**（低 18 / 中 8 / 中高 2 / 高 1）；改动量估算：生产代码 ~390 行（8 文件）+ 测试 ~550 行（3 文件）+ 迁移/文档 ~40 行；**最高难度项为 Service 单测适配（I4-6）**，**最高风险项为权限收窄破坏性变更（R2）与政治敏感 API 外部依赖（R1）**；测试数据清理纪律落账（§9）。

## 九、测试数据登记与清理规范（全局约束）

> 本节为**实施全周期强制规范**，优先级最高。依据：《数据关联完整性治理》§11.3、《外部直播流创建与手动开播》§5.10 + 附录 C（**V1.6 教训：按"库名/前缀"推断批量清理误删真实数据（4371 个非测试房间 + 228 条内容安全规则），需从备份恢复**）。登记模板见附录 C。

### 9.1 三类数据操作与处置原则

| 类型 | 包含 | 处置方式 |
|------|------|----------|
| 自动测试数据 | pytest/conftest 生成（随 `drop_all` 清零） | 不手工登记；**前提：测试库隔离确认**（conftest 的 POSTGRES_DB 不得指向真实/共享库） |
| 手动验证数据 | 验收/联调时手工创建的 tag/session_tag/用户/场次等 | **创建即登记**（附录 C 模板）→ 阶段末逐条按主键清理 → 残留核验 = 0 |
| 结构/词库变更 | V18 迁移、seed 重跑 | 执行前确认幂等/备份（规则表 dump）；执行时间与脚本登记在案；不做业务测试数据 |

### 9.2 强制纪律

1. **创建即登记**：手动验证数据生成后立即写入登记文件（建议 `标签V2实施_测试数据登记.md`，随实施推进维护），字段：表名 / 主键或唯一键 / 关联信息 / 创建时间 / 用途 / 清理 SQL。
2. **逐条精确清理**：仅按登记清单逐条 `WHERE 主键` 删除；**禁止**按库名、名称前缀、模糊条件批量删除。
3. **残留核验**：每个阶段 Gate 前按登记清单反查残留，输出"已清理/残留 0"结论。
4. **生产环境零业务测试数据**：生产仅执行 V18 迁移 + seed（结构性变更，记录在案），不创建任何 tag/session_tag 验证数据。
5. **备份先行**：任何清理动作前保留可回滚备份（如规则表 dump：`content_safety_rules` 按 tag_name 场景行导出）。

| 阶段 | 数据操作 | 登记项 |
|------|---------|--------|
| 0 | 无（测试基线） | pytest 基线数字 |

| 全程 | 集成测试库数据 | 确认随 drop_all 清零；不纳入手工登记 |
