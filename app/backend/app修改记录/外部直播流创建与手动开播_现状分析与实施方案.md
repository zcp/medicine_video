## 一、执行摘要

### 1.1 背景

当前平台的直播体系设计为 **SRS 推流驱动**：主播用 `stream_key` 向 SRS 推流，SRS 回调驱动场次状态流转（`scheduled → live → finished → processing → ready/error`）。**但推流链路未真正投入使用**，实际业务场景是从第三方平台获取**正在直播或已结束直播的 m3u8 播放地址**，由我方平台按用户设置的直播状态进行播放。

即核心诉求为：

```text
用户创建直播时提供外部 m3u8 播放链接
  → 按用户设置的直播状态（预告/直播中/回放）对外播放该链接指向的视频
  → 用户手动切换状态即切换播放形态
  → 无需依赖 SRS 推流链路
```

### 1.2 核心结论

1. **采用方案 B（source_type 隔离）**：`live_sessions` 新增 `source_type` 字段（`push`/`external`），`push` 场次保持现有 SRS 回调驱动零影响；`external` 场次支持用户手动状态流转，两者互不干扰
2. **创建支持三态**：创建场次时可直接指定 `scheduled`（预告）/ `live`（直播中）/ `ready`（回放），外部 m3u8 地址所有状态下必填
3. **手动状态切换端点**：新增 `POST /api/v1/sessions/{id}/status`，按状态矩阵 + 三条守卫规则流转，**切换即生效即播放**
4. **自动开播**：v1 采用**惰性补转**（读取时到期自动转 live），不依赖定时任务；Celery beat 定时任务作为后续增强
5. **m3u8 代理**：新增 session 关联型代理端点（防 SSRF），解决外部流鉴权头、防盗链、URL 时效问题；公开流采用"只代理 master 清单 + 两级重写直连"（见 §4.5）
6. **App 端为主**：播放用 `<live-player>`（直播流）+ uni `<video>`（回放），小程序尽力兼容，H5 端不实施
7. **测试样本已验证**：4 条公开测试流（Akamai 直播 ×2、Mux/Apple 回放 ×2）2026-08-11 实测全部可用，均符合 H.264 + AAC 标准，可直接作为开发/验收基准（见 §2.4）

### 1.3 范围界定

| 范围 | 内容 |
|------|------|
| ✅ 本次实施 | 后端：`source_type` 迁移 + 创建三态 + 手动状态切换端点 + 惰性补转 + m3u8 代理 + 测试；App 端：创建直播加"直播中"模式、开播/停播/转回放按钮、播放源分流、状态枚举收敛、顺手修复 |
| ⏸️ 暂缓 | Celery beat 定时自动开播（惰性补转已覆盖"有人访问"场景）；`/playback/stats` 播放统计上报（如实施则后端补端点）；播放鉴权（观看需要登录/订阅的场次） |
| ❌ 不实施 | H5 端（播放器/管理页均不动）；SRS 推流链路改造（保持现状）；`ready → scheduled`、`finished → scheduled` 回退；原生 ijkplayer 插件（v1.1 视真机结果再评估） |

### 1.4 预期效果

| 维度 | 现状 | 实施后 |
|------|------|--------|
| 创建直播状态 | 仅能建"预告"场次，回放靠二次 PATCH | 创建时可直接选 预告/直播中/回放 三态 |
| 开播 | 必须 SRS 推流触发回调（推流链路未使用） | 用户手动点"开播"即切 live，立即播放外部 m3u8 |
| 停播 | 无任何停播按钮/端点 | 手动点"停播"切 finished 并记录结束时间 |

| 与推流体系 | — | `source_type` 隔离，push 场次状态流转零影响 |

## 二、当前实现现状

### 2.1 后端现状（backend/live_core_service，实测）

#### 2.1.1 数据模型

**LiveRoom**（`app/models/live_core.py` L31-92）：无状态字段，状态由最新场次聚合

| 字段 | 必填 | 作用 |
|------|:--:|------|
| `title` | ✅ | 房间标题（≤100字，创建时过内容安全校验） |
| `description` | ❌ | 描述 |
| `cover_url` | ❌ | 封面图 |
| `is_private` | ❌ 默认 false | 私密房间 |
| `record_by_default` | ❌ 默认 true | 默认录制 |
| `parent_room_id` | ❌ | 父房间自引用 |
| `stream_key` | 服务端生成 | 推流密钥（`streamkey_{hex16}`），SRS 回调识别房间 |

**LiveSession**（L95-152）：状态挂在场次上

| 字段 | 说明 |
|------|------|
| `status` | 六态枚举（见 2.1.3） |
| `start_time` / `end_time` | 开始/结束时间（UTC） |
| `playback_url` | 播放地址（预告=SRS 直播流写入地址，回放=已录制视频地址） |
| `playback_url_hash` | 规范化 URL 的 sha256（幂等去重，`(room_id, playback_url_hash)` 部分唯一索引） |
| `video_id` | 录制视频 ID（禁止手动修改） |

#### 2.1.2 创建链路

| 端点 | 权限 | 现状 |
|------|------|------|
| `POST /api/v1/rooms`（room.py L47-101） | JWT + 开播门禁 | 创建房间；请求体 `LiveRoomCreate`（title 必填，其余可选） |
| `POST /api/v1/rooms/{room_id}/sessions`（room.py L609-671） | 房间写权限 | 创建场次；`ScheduledSessionCreate`（start_time 必填、**playback_url 必填**）；**状态固定 SCHEDULED**（session_service.py L132），无法直接建 live/ready |
| `POST /api/v1/rooms/{room_id}/sessions/import`（session_import.py） | 房间写权限 | 回放导入（ready），已支持外部 playback_url + 幂等哈希 |

#### 2.1.3 状态机

```text
LiveSessionStatus（models/live_core.py L21-28）：
  scheduled(预告) → live(直播中) → finished(已结束) → processing(回放生成中) → ready(回放可用)
                                                        ↘ error(回放失败)
```

**状态写权限现状**（`session_service.py` L263-401 `update_scheduled_session_info`）：

```text
用户接口（PATCH /sessions/{id}）只允许写 scheduled / ready 两个业务可编辑态；
live / finished / processing / error 由推流回调或后台任务写入，前端 PATCH 一律 403 拒绝。
```

具体限制：
- 转 `ready` 必须 `playback_url` 非空（L336-345）
- 转 `scheduled` 仅限当前已是 scheduled（L332-334）
- `video_id` 禁止手动修改（L314）
- 时间字段仅在 scheduled/ready/error 可编辑（L350-362）
- **`scheduled`/`error` 场次填回放地址会自动转 `ready`**（L385-389）
- 删除保护：`live` 场次不可删除（L471）

#### 2.1.4 开播机制（SRS 回调驱动，无手动端点）

```text
主播推流 → SRS 回调 POST /api/v1/internal/srs/on-publish（internal.py L33）
  → handle_on_publish（srs_callback_service.py L35-107）：
      有 scheduled 场次 → 置 live + start_time=now
      无 → 新建 live 场次
停推 → on-unpublish（L80）→ 置 finished + end_time → Celery post_stream_processing_task
  → processing → ready / error
```

- **无** `POST /rooms/{id}/start`、`/stop`、`/update_status` 类用户端点
- **无** Celery beat 配置（`celery_app.py` 仅 6 行；`compose-app.yml` worker 未带 `-B`），**无定时自动开播**

### 2.3 关键事实（影响方案的事实链）

1. 后端 `live_sessions.playback_url` 是 String(1024)，存外部 m3u8 地址**无需改表结构**，只需新增 `source_type`
2. 前端 App 端 uni `<video>`/`<live-player>` 是原生组件，**不受 CORS 限制**，可直接播放外部 http(s) m3u8（CORS 只是 H5 的问题）
3. 原生组件**无法附加自定义 header**——带鉴权 token 的外部流必须走服务端代理
4. `source_type` 用 `DEFAULT 'push'` 迁移，存量场次零影响
5. 前端 `create.vue` 已能创建"回放(ready)"场次（走 import 接口），说明外部地址入库链路已验证可用
6. 现有测试（`tests/integration/test_internal_callbacks_*.py` 等）断言"live 只能由推流回调写入"，放开手动写 live 需同步调整测试预期

## 三、需求与问题分析

### 3.1 需求拆解

| # | 需求 | 现状缺口 |
|---|------|---------|
| 1 | 创建直播时从外部获取**正在直播**的 m3u8，直接以 live 状态创建 | 创建状态固定 scheduled，无法直接建 live |
| 2 | 创建直播时从外部获取**已结束**的 m3u8，直接以回放状态创建 | 需创建后再 PATCH（体验冗余，但仍可用） |
| 3 | 预告场次同样携带 m3u8，按用户设置的状态播放 | 已满足（playback_url 必填） |
| 4 | 手动切换状态即切换播放形态（scheduled/live/finished/ready） | **核心缺口**：live/finished 仅推流回调可写 |
| 5 | 到点自动开播（可选） | 无定时任务 |
| 6 | App 端播放外部 m3u8（含带鉴权/防盗链的流） | 播放器已具备；鉴权流需代理 |

### 3.2 核心冲突点

```text
现状设计：live/finished 是"SRS 回调专属"的系统态，用户接口只能写 scheduled/ready。
需求设计：live/finished 由用户手动控制（针对外部流）。
冲突本质：状态写权限模型不兼容。
```

**解决方案**：`source_type` 字段把场次分成两类，各自独立的状态写权限模型：

```text
source_type = push（默认）     → 状态写权限保持现状（回调专属），零影响
source_type = external（新增） → 用户手动流转（新端点），与推流路径互不干扰
```

## 四、目标方案

### 4.1 架构总览

```text
App 端（D:\saas_app-main）                       后端（live_core_service）
────────────────────                            ──────────────────────
创建直播(预告/直播中/回放)  → POST /rooms/{id}/sessions     （三态创建，source_type=external）
开播/停播/转回放按钮        → POST /sessions/{id}/status     （手动状态流转）
播放页(live-player/video)   → GET /proxy/m3u8/{session_id}   （m3u8 代理，session 关联）
                            → playback_url 直连（无鉴权流，可配置）
到期首次访问自动开播        → 读取路径惰性补转（GET /sessions/{id}、GET /rooms/{id}）
```

### 4.2 状态矩阵（external 场次专用，V2.0 修订）

| 当前 \ 目标 | scheduled | live | finished | ready |
|---|---|---|---|---|
| **scheduled**（预告） | — | ✅ 开播 | ❌ | ✅ 直接发布回放 |
| **live**（直播中） | ❌ | — | ✅ 停播 | ✅ 转回放 |
| **finished**（已结束） | ❌ | ✅ 恢复开播 | — | ✅ 发布回放 |
| **ready**（回放，终态） | ❌ | ❌ | ❌ | — |

**V2.0 修订说明**：
- 删除 `live→scheduled`：直播中切回预告后"下一次开播时间"无法定义（start_time 已过；到点自动开播由惰性补转驱动），误操作撤销应使用停播（finished）
- 删除 `ready→live`：回放为已公开终态，回放地址（VOD）≠ 直播地址；"重新开播需新地址"逻辑随之移除
- `finished→live` 语义为**恢复开播**：沿用原直播地址（无需新地址）、start_time 保持首次开播时间、end_time 清空

**核心守卫规则（3 条）**：

```text
1. 转 live / ready 必须有非空 playback_url（转 live 为新增校验，转 ready 已有）
2. 转 live 时清空 end_time；转 finished / ready 时 end_time 为空则自动记当前时间
3. 所有流转用条件更新（UPDATE ... WHERE status=<当前状态>）防并发覆盖
```

**不参与手动流转的状态**：`processing` / `error`（error 修复为 ready 的现有逻辑保留）；`push` 场次全部不参与。

**时间管理语义**（V2.0）：`start_time` = 首次开播时间（scheduled→live 写入；恢复开播保持不变）；`end_time` = 最后一次结束时间（live→finished 写入；恢复开播清空）。

### 4.3 创建三态设计

`ScheduledSessionCreate` 扩展（向后兼容）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|:--:|------|
| `start_time` | datetime | ✅ | 计划开始时间（创建 live 时可省略，自动取当前时间） |
| `playback_url` | str | ✅ | 外部播放地址（**所有状态必填**，与现状一致） |
| `status` | enum | ❌ 默认 scheduled | 创建初始状态：scheduled / live / ready |
| `source_type` | enum | ❌ 默认 external | 本次新增（内部服务调用可显式传 push，用户接口固定 external） |

创建规则：

```text
status=scheduled → 现状行为不变
status=live      → start_time 自动置 now，end_time=None（立即开播）
status=ready     → 直接建回放场次（等价于现状"创建后 PATCH 转 ready"，一步到位）
```

### 4.4 手动状态切换端点

```
POST /api/v1/sessions/{session_id}/status
Authorization: Bearer <user_token>
权限：房间 Owner / ADMIN（复用 check_room_owner_or_admin）

请求体：
{
  "status": "live",            // 目标状态（scheduled/live/finished/ready）
  "playback_url": "https://..." // 可选；转 ready/live 时允许更新地址（ready→live 必须提供）
}

响应：成功返回新状态 + start_time/end_time/playback_url
错误：403（非 owner）、422/400（非法流转，如 ready→scheduled）
```

设计要点：

```text
1. 仅 source_type=external 的场次可调用；push 场次返回 403（保持回调独占）
2. 状态矩阵校验 + 三条守卫（§4.2）
3. 条件更新防并发：若当前状态已被并发修改，返回 409 让前端重试
4. 幂等：目标状态 == 当前状态时直接返回成功（不报错）
5. 同步维护 playback_url_hash（复用 utils_playback.calc_playback_url_hash）
```

### 4.5 m3u8 代理端点

```
GET /api/v1/proxy/m3u8/{session_id}
认证：Optional Auth（公开房间可匿名；私密房间需可见性校验）
```

| 设计点 | 决策 | 理由 |
|------|------|------|
| URL 来源 | **session 关联**（查库取 `playback_url`），**不做** `?url=` 通用代理 | 只有用户自己存过的地址可被代理，天然防 SSRF |
| 转发范围 | **公开流（v1）：只代理 master 清单 + 两级重写，子清单/切片重写为外部绝对 URL 后由播放器直连**（App 原生组件无 CORS 限制）；**鉴权流（v1.1）：全量代理**（master+子清单+切片都走代理，因直连无法附加 header） | 直播切片流量大，全量代理成本高；公开流重写直连可把代理流量降到约 1 次/6~10s 的清单请求 |
| **两级重写** | **master 清单**：`#EXT-X-STREAM-INF` 后的相对子清单路径 → 基于 master URL 的绝对外部 URL；**media 清单**：`#EXTINF` 后的相对切片路径 → 基于 media URL 的绝对外部 URL | 播放器请求子清单/切片时直接打外部 CDN；否则相对路径会基于代理 URL 解析导致 404（本轮实测 4 条样本全部为相对路径，见 §2.4） |
| 重写兼容 | 相对路径 / 绝对路径 / 协议相对（`//host/...`）统一用 `urllib.parse.urljoin` 解析；兼容纯音频档（`CODECS` 无视频） | Apple 样本含纯音频档（§2.4 发现 3） |
| 鉴权头 | 配置项 `EXTERNAL_STREAM_HEADERS`（X-API-Key/UA/Referer 按外部平台注入） | 原生组件无法附加 header，代理是唯一解 |
| 重定向 | `allow_redirects=False`，校验最终域名非内网 | 防重定向跳内网 |
| 缓存 | `Cache-Control: no-store`（清单实时变化） | 直播清单不能强缓存 |
| 限额 | 5s 超时 + 响应大小上限（如 10MB） | 防资源耗尽 |
| 校验 | 仅 http/https；拦截内网/环回/私网 IP；DNS rebinding 理论风险接受（v1 做域名解析结果校验，不做连接时 IP pin，见待决策点 13） | SSRF 纵深防御 |

### 4.6 惰性补转（自动开播的 v1 形态）

```text
触发点：GET /sessions/{id}、GET /rooms/{id} 读取路径（以及场次列表）
条件：source_type=external + status=scheduled + start_time <= now
动作：条件更新（WHERE status='scheduled'）转 live，start_time 保持计划值
效果：到点后"有人访问即自动开播"；无人访问时保持 scheduled（用户可手动开播）
```

**优点**：零定时任务依赖、无 beat 运维风险、天然幂等；与手动切换完全兼容。
**局限**：无人访问的场次不会自动流转（对直播场景无实际影响——直播必须有人播有人看）。

### 4.7 App 端播放链路

| 场次状态 | 播放组件 | 播放源 | 说明 |
|------|------|------|------|
| `live` | **`<live-player>`**（mode=live） | 代理地址 `/api/core/proxy/m3u8/{session_id}`（或直连 playback_url，见待决策点 2） | 流媒体专用内核，直播 HLS 兼容性优于普通 video |
| `finished`/`ready` | uni `<video>`（复用 VideoPlayerApp + ShadowParser） | 同上 | 回放为 VOD，普通 video 足够 |

播放源选择逻辑（`LiveView.vue` 改造）：

```text
source_type=external：live/ready/finished 一律播 playback_url（经代理或直连）
source_type=push（存量）：保持现状（live 用 /hls-proxy/{stream_key}.m3u8）
```

### 4.8 前后端分工

```text
前端：状态按钮文案/交互、Tab 分组、播放器组件选择、直连/代理切换
后端：状态矩阵与守卫、时间字段维护、URL 校验与哈希、代理转发与安全
前端不关心 source_type 的实现细节          后端不关心 Tab 名称和按钮形态
```

### 5.6 代理端点（新增 `app/api/v1/endpoints/proxy.py`）

```python
@proxy_router.get("/m3u8/{session_id}")
async def proxy_m3u8(
    session_id: uuid.UUID,
    request: Request,
    current_user: Optional[dict] = Depends(get_current_user_optional),
    db: AsyncSession = Depends(get_db),
) -> StreamingResponse:
    """代理场次 playback_url（session 关联，防 SSRF）"""
    # 1. 查场次 → 校验房间可见性（复用 check_room_visibility）
    # 2. 校验 playback_url 非空且为 http(s)
    # 3. 域名校验：拦截内网/环回/私网 IP（socket 解析后比对，含 IPv6）
    # 4. httpx.AsyncClient(follow_redirects=False, timeout=5) GET，
    #    注入配置头（EXTERNAL_STREAM_HEADERS），透传 query 参数
    # 5. 校验最终域名仍非内网 → 响应体做【两级清单重写】后返回（no-store）
    # 6. 大小限制（读取上限 10MB）与错误兜底（404/502 文案）
```

**两级清单重写逻辑（本轮细化，v1 公开流模式核心）：**

```text
拉取到 master 清单文本后：
  1. 逐行扫描：记录 #EXT-X-STREAM-INF / #EXT-X-MEDIA 后的 URI 行
  2. 对相对路径 URI（如 mastermaster_video10000k.m3u8）：
     new_uri = urljoin(master_url, uri)   → 重写为外部绝对 URL
  3. 对绝对/协议相对 URI：直接保留（协议相对补全 scheme）
  4. 返回重写后的文本（Content-Type: application/x-mpegURL，Cache-Control: no-store）

播放器随后请求子清单（外部绝对 URL 直连，不经代理）→ media 清单内的切片
同样为相对路径 → 播放器基于 media 的外部 URL 自行解析直连外部 CDN。
（media 清单无需代理重写：播放器自带基于清单 URL 的路径解析。）

兼容性要求（§2.4 样本验证得出）：
  - 兼容纯音频档（STREAM-INF 无 RESOLUTION/视频 CODEC）
  - 兼容 URI 行以引号包裹、含 query（如 gear1/prog_index.m3u8?token=xxx）
  - 忽略注释行、空行、#EXT-X-* 标记行（仅重写 URI 行）
```

**v1.1 扩展（鉴权流全量代理）**：当外部流需要 header 鉴权时，子清单/切片直连无法附加 header → 代理需支持会话内任意路径转发（`/proxy/m3u8/{sid}/{外部相对路径}`），本次不实施。

注册：`app/api/v1/api.py` 挂 `/proxy` 前缀。

## 六、风险分析与对应方案

### 6.1 风险一：同一房间混用 push / external 场次导致房间状态跳变（🟡 中）

```text
原因：房间状态聚合取"最新场次状态"（room.py L349-360），若同一房间既有 push 又有
      external 场次，聚合结果可能在不同状态间跳变。
影响：直播管理列表/首页卡片状态显示不稳定。
处理：①产品约定一个房间业务上只走一种来源；②技术上 source_type 已隔离状态写权限，
      push 回调不会改 external 场次、手动切换不会改 push 场次，二者不互相覆盖；
      aggregation 本身不改，行为可预期。
```

### 6.2 风险二：Android 机型 m3u8 兼容性（🔴 高，App 端核心风险）

```text
原因：uni <video> 的 Android 端对 HLS 变体支持差——H.265、fMP4、LL-HLS、AES-128 加密、
      非标准码率都可能播不了；微信小程序 Android 端对 m3u8 支持也一般。
影响：部分机型外部流黑屏/无法播放。
处理：①直播流用 <live-player>（流媒体专用内核，比 video 稳）；
      ②向外部平台确认流规范：H.264 + TS 切片 + 标准 m3u8（拒绝 fMP4/LL-HLS 进 v1 验收）；
      ③真机矩阵覆盖 Android 主流机型（见 8.3）；
      ④若仍不行，v1.1 评估原生 ijkplayer 插件（HBuilderX 打包配置，成本另计）。
```

### 6.3 风险三：外部流鉴权/防盗链（🟡 中）

```text
原因：带 token header 或校验 UA/Referer 的流，原生组件直连必失败（无法附加 header）。
影响：特定外部平台流无法播放。
处理：代理端点支持配置头注入（EXTERNAL_STREAM_HEADERS），按外部平台文档配置；
      这是 v1 必须上代理的硬理由。
```

### 6.4 风险四：代理 SSRF（🟡 中）

```text
原因：代理端点若可代理任意 URL，会被利用探测内网。
影响：内网信息泄露/横向攻击面。
处理：session 关联设计（只代理库中已存的 playback_url）+ 域名/IP 校验（拦截内网、
      环回、私网）+ 重定向拦截 + 仅 http(s) + 超时与大小限制（§4.5 四件套）。
```

### 6.5 风险五：代理流量成本（🟡 中）

```text
原因：若切片全走代理，App 直播一小时约 0.5~1GB 流量。
影响：服务器带宽成本。
处理：v1 公开流采用"只代理 master 清单 + 两级重写"（§4.5）——代理流量降到约
      1 次/6~10s 的清单请求（每小时 <1MB），切片重写为外部绝对 URL 后由播放器
      直连外部 CDN；仅当外部流有鉴权/防盗链时（需 header，v1.1）才全量代理，
      此时流量不可避免，属业务必要成本。
```

### 6.6 风险六：live-player 打包配置（🟢 低）

```text
原因：App 端使用 <live-player> 需在 HBuilderX 勾选模块（或 CLI 配置），发布流程变化。
影响：云打包/自定义基座需提前准备。
处理：阶段 0 验证打包配置可行性；若成本高，降级方案为直播流也用 <video>
      （零打包改动，Android 兼容性风险相应升高）。
```

### 6.7 风险七：现有测试断言破坏（🟡 中）

```text
原因：现有测试断言"live 只能由回调写入"（test_internal_callbacks_*.py 等）。
影响：放开手动写 live 后部分断言失效。
处理：测试按 source_type 分流——push 场次断言不变；external 场次断言新行为；
      全量 pytest 回归。
```

### 6.8 风险八：m3u8 时效性（🟢 低）

```text
原因：外部流 URL 带 token 会过期；直播流结束后清单失效。
影响：播放中断/黑屏。
处理：代理刷新兜底（每次代理请求都读库取最新 URL）；播放器错误事件提示
      "流已失效，请重新获取地址"。
```

### 6.9 风险九：删除保护（🟢 低）

```text
原因：live 场次不可删除（session_service.py L471）。
影响：手动置 live 后需先停播才能删，符合预期。
处理：前端在删除确认弹窗中提示"直播中场次需先结束"；无需代码改动。
```

### 6.10 风险十：惰性补转的写放大（🟢 低）

```text
原因：每次读取都检查 scheduled 到期，高峰期读取量大时会有重复的无效 UPDATE。
影响：极小（条件更新影响行数 0 即跳过，无锁冲突）。
处理：条件更新保证幂等；无需额外措施。
```

## 七、使用场景分析

| 场景 | 用户操作 | 状态流转 | 依赖能力 | 状态 |
|------|---------|---------|---------|:--:|
| **A. 预约 + 手动开播**（最常见） | 创建选"预告"填直播 m3u8 → 到点手动点"开播" | `scheduled → live → finished → ready` | 三态创建 + 状态端点 | ✅ 本次 |
| **B. 正在直播的流** | 拿到外部正在播的 m3u8，创建选"直播中" | 创建即 `live` → 播完 `finished → ready` | 创建直接 live | ✅ 本次 |
| **C. 纯回放发布** | 拿到已结束直播的 m3u8，创建选"回放" | 创建即 `ready`，对外展示回放 | 创建直接 ready | ✅ 本次 |
| **D. 预告期内流已结束** | 预告场次直接切"回放" | `scheduled → ready` | 矩阵允许 | ✅ 本次 |
| **E. 误操作回退** | 直播中点"回到预告" | `live → scheduled` | 矩阵允许 | ✅ 本次 |
| **F. 同一场次再次直播** | 回放场次切"直播"，更新为新 m3u8 | `ready → live`（强制新地址） | 矩阵允许 | ✅ 本次 |
| **G. 自动开播（有人访问）** | 只填预告+地址，什么都不做 | 到期首次被访问时自动 `scheduled → live` | 惰性补转 | ✅ 本次 |
| **H. 自动开播（无人访问也准点转）** | 同上 | 到点无条件 `scheduled → live` | Celery beat 定时任务 | ⏸️ 暂缓 |
| **I. 带鉴权的外部流** | 创建时填带鉴权的 m3u8 | 任意状态播放 | 代理 header 注入 | ✅ 本次 |
