# 前端裁剪展示提示词

## 1. 适用对象与任务目标

本提示词适用于当前项目中**头像裁剪、头像展示与图片预览**的前端实现。

本任务的目标不是简单把图片显示成圆形，而是补齐一条完整、可控、可维护的头像交互链路：
- 从手机本地相册选择图片；
- 进入裁剪流程；
- 在固定圆形裁剪框内对图片进行拖动和缩放；
- 生成裁剪结果图；
- 在个人信息页中以圆形头像展示；
- 点击头像后查看矩形大图；
- 上传成功后刷新头像状态；
- 默认头像和失败兜底保持稳定。

本任务的核心定位是：
- **优先补前端裁剪交互**；
- **优先保证头像展示一致性**；
- **优先与现有 `avatar_url` 上传闭环配合**；
- **不新增重复的图片管理体系**。

---

## 2. 强约束与执行前提

### 2.1 当前任务的默认前提
- 当前仓库中已经存在个人资料编辑页面；
- 当前前端项目位于 `D:\saas_app-main`，其页面与 API 风格已经相对固定，`src/api/auth.ts` 使用 `authUrl()` 统一拼接，`src/utils/request.ts` 封装了请求、鉴权和错误处理；
- 当前任务是对前端头像体验做增强，而不是重写整个资料页；
- 当前任务优先服务“头像裁剪后再上传”的目标，不扩展到图片社交编辑、滤镜、贴纸等复杂场景。

### 2.2 禁止重复造页面
- 禁止新建一套完全独立的个人资料系统；
- 禁止将裁剪逻辑分散到多个页面且彼此不一致；
- 禁止把头像展示、裁剪、预览混成一个难以维护的大页面；
- 如需增加裁剪能力，优先在现有编辑资料页基础上增量补充，必要时再拆出裁剪页或裁剪组件；
- 前端代码风格必须与现有项目保持一致：Vue/uni-app 组合式 API、`ref`/`computed`/`onShow` 管理状态、方法命名清晰、请求调用尽量复用现有 API 封装。

### 2.3 必须先审查再修改
在生成任何代码前，必须先读取并理解：
- 当前个人信息编辑页的结构与状态管理方式；
- 当前头像展示的样式与默认图逻辑；
- 当前图片选择与上传的实现方式；
- 前端 API 封装中与用户资料相关的方法；
- 后端是否已经提供稳定的头像上传结果 URL。

严禁在未审查上述内容前直接：
- 猜测组件结构；
- 猜测裁剪交互方案；
- 猜测头像尺寸与默认图路径；
- 把临时路径误当成最终头像地址。

### 2.4 接口先固定（强制）
在开始实现前，必须先固定并确认以下接口定义，前后端一致后再写代码：
- 头像上传接口路径、请求方法、请求字段、响应字段；
- 资料更新接口是否继续复用 `PATCH /users/me`；
- 最终头像唯一字段必须保持为 `avatar_url`；
- 前端裁剪后上传成功的回填字段必须仍是 `avatar_url`；
- 禁止在实现过程中临时更改字段名或接口路径。

### 2.5 文件级别约束
为了避免范围过宽，生成代码时必须严格限制可修改文件范围。

#### 允许修改的文件范围
- 个人信息编辑页；
- 头像展示组件或头像样式文件；
- 图片裁剪组件或裁剪页面；
- 图片预览入口；
- 前端必要的用户头像状态管理；
- 少量与头像有关的类型定义。

#### 不允许随意修改的文件范围
- 不允许重构整个前端基础请求框架 `src/utils/request.ts`；
- 不允许改动与头像无关的其它业务 API；
- 不允许改动登录、注册、验证码、密码重置等无关流程；
- 不允许新增一套平行的用户资料目录结构；
- 不允许为了裁剪功能大面积调整与业务无关的公共组件。

### 2.6 默认执行顺序
1. 审查当前编辑资料页与头像展示逻辑；
2. 明确当前是否已有裁剪组件或裁剪页；
3. 明确图片预览与上传是否已打通；
4. 固定接口定义与状态字段（只保留 `sourceImage`、`croppedImage`、`avatar_url` 三层状态）；
5. 设计最小可用的裁剪与展示方案；
6. 仅在必要位置补充裁剪交互和预览逻辑；
7. 修改后重新核查头像展示、预览和上传后的刷新是否正常。

## 5. 任务一：补头像裁剪能力

### 5.1 任务目标
让用户选择本地图片后，先进入裁剪流程，再上传最终头像结果图。

### 5.2 建议实现方向
建议优先补以下能力中的一项或多项：
- 独立裁剪页；
- 裁剪组件；
- 固定圆形裁剪框；
- 图片拖动、缩放；
- 生成裁剪结果图；
- 裁剪完成后再进入上传步骤。

### 5.3 设计要求
裁剪交互应满足：
- 裁剪框固定不动；
- 背景图片可拖动；
- 背景图片可缩放；
- 必须限制图片最小/最大缩放比例，防止过小或过大；
- 必须限制拖动边界，防止裁剪区域内露白；
- 裁剪结果尽量输出为正方形，便于后续圆形展示；
- 裁剪失败时要有可见提示与回退方案；
- 如果手势实现复杂，优先保证基础拖拽/缩放稳定，再补细节体验。

### 5.4 优先实现方式
- 优先在现有编辑页中增加裁剪入口；
- 如裁剪逻辑较多，建议独立成裁剪页或裁剪组件；
- 优先保证交互稳定，再考虑视觉细节；
- 不建议在主编辑页里堆叠过多触摸计算逻辑。

### 5.5 完成标准
完成后应满足：
- 用户选图后能进入裁剪；
- 图片能正常拖动、缩放；
- 能生成稳定裁剪结果图；
- 裁剪结果可直接上传到后端；
- 裁剪流程不会破坏原有资料编辑能力。

---

## 6. 任务二：补头像展示能力

### 6.1 任务目标
让个人信息页中的头像展示稳定、统一，并与裁剪后的结果保持一致。

### 6.2 建议实现方向
建议优先补以下能力中的一项或多项：
- 头像统一圆形容器；
- 使用正式 `avatar_url` 展示头像；
- 头像加载失败时显示默认图；
- 页面刷新后仍显示后端返回的正式头像；
- 点击头像能进入预览。

### 6.3 设计要求
头像展示应满足：
- 圆形展示仅属于 UI 呈现，不要求图片文件本身必须是圆形；
- 头像加载失败必须有默认图；
- 本地临时路径只用于裁剪与预览，不用于最终持久化；
- `sourceImage` 只用于选图后的裁剪与即时预览；
- `croppedImage` 只用于上传前的中间态，不得写入最终资料；
- `avatar_url` 是唯一长期持久状态；
- 头像展示与资料页状态保持一致。

### 6.4 优先实现方式
- 优先复用现有 `displayAvatar` 或等价状态；
- 优先从后端返回的 `avatar_url` 读取头像；
- 如有本地临时头像，只用于裁剪中预览；
- 不建议把头像展示逻辑散落在多个页面里重复实现。

### 6.5 完成标准
完成后应满足：
- 个人信息页头像能稳定显示；
- 更新头像后页面能及时刷新；
- 默认头像与失败兜底正常；
- 圆形展示风格统一。

---

## 7. 任务三：补图片预览能力

### 7.1 任务目标
让用户点击头像后可以查看矩形大图，避免只看到圆形裁切后的局部效果。

### 7.2 建议实现方向
建议优先补以下能力中的一项或多项：
- 系统图片预览；
- 自定义预览页；
- 点击头像后展示原图或裁剪结果的大图；
- 保持图片比例正常。

### 7.3 设计要求
预览交互应满足：
- 预览时不要再套圆形遮罩；
- 图片应以矩形大图或标准预览方式显示；
- 支持返回编辑页或资料页；
- 预览页应尽量轻量。

### 7.4 优先实现方式
- 优先复用系统图片预览能力；
- 如需要更强控制，再考虑自定义预览页；
- 不建议为了预览再引入复杂图片编辑逻辑。

### 7.5 完成标准
完成后应满足：
- 点击头像能正常查看大图；
- 大图显示比例正常；
- 不影响头像圆形展示；
- 不影响裁剪和上传流程。

## 8. 与后端的配合要求

### 8.1 裁剪后再上传
前端应在裁剪完成后再调用上传接口，不要把原图直接作为最终头像。

### 8.2 上传成功后回填 URL
上传成功后必须使用后端返回的 `avatar_url` 更新用户资料状态。

### 8.3 资料页刷新
头像上传或资料更新后，必须重新渲染页面中的头像显示。

### 8.4 状态恢复流程
建议把头像上传和资料保存拆成可恢复流程：
1. 先保留本地裁剪结果；
2. 上传成功后再回填 `avatar_url`；
3. 若上传失败，保留裁剪结果与重试入口；
4. 若资料保存失败，不清空裁剪态和本地展示态，允许用户继续重试；
5. 页面重新进入时，始终以后端正式 `avatar_url` 为准。

### 8.5 统一字段
前端必须继续使用现有 `avatar_url`，不要擅自新增重复字段。

## 9. 风险与隐患处理建议

### 9.1 裁剪交互实现复杂
AI 可能在拖拽、缩放、边界约束上写得不够稳。建议的规避方式是：
- 优先把功能拆成三个更具体的实现提示词：
  1. 头像裁剪交互提示词；
  2. 个人信息页头像展示提示词；
  3. 图片预览提示词；
- 如果仍使用一份总提示词，则必须明确“先实现裁剪页/组件，再实现展示页，再实现预览页”，避免一次性塞进一个大页面。

### 9.2 头像 URL 稳定性不足
建议使用稳定 URL，而不是临时路径。优先级建议：
1. 后端返回可长期访问的稳定地址；
2. 前端只保存 `avatar_url`；
3. 页面展示失败时回退默认头像；
4. 不在前端保存任何一次性临时文件地址；
5. 若需要会话内即时预览，本地路径仅限当前会话，不可进入长期状态。

### 9.3 手机端兼容性问题
建议：
- 裁剪页兼容触摸事件；
- 支持相册选择图片，必要时兼容相机；
- 控制图片缩放上下限；
- 裁剪框大小随屏幕自适应；
- 使用 `aspectFill` 或等效方式保证圆形头像显示稳定。

### 9.4 上传失败后的状态恢复不完善
建议把头像上传和资料保存拆成可恢复流程：
1. 先保存裁剪结果到本地状态；
2. 上传成功后再回填 `avatar_url`；
3. 若上传失败，保留裁剪结果与重试入口；
4. 若资料保存失败，不清空裁剪态和本地展示态，允许用户继续重试。

- 让图片裁剪稳定可用；
- 让头像展示统一可靠；
