# 主分支（main）与 wechat-v1 分支对比分析报告

> 分析日期：2026-08-09
> 对比对象：本地 `main`（含未提交工作区改动） vs 远程 `origin/wechat-v1`（另一位同学的最新分支）
> 仓库：https://github.com/HuangShiYu-a/app_wechat_backend.git

---

## 一、核心结论（TL;DR）

1. **两个分支没有共同祖先**（`git merge-base` 为空），wechat-v1 是独立导入的完整代码快照（`b49c32e Import workspace project files`）加上 6 次增量提交。**不能直接 `git merge`，只能人工对照融合。**
2. **双方都在各自侧做增强，方向不同**：
   - **main（你）**：分类层级体系（parent_id + live_room_categories 多对多 + is_primary）、专家科室受控词表（expert_departments）、首页/搜索增强、管理端数据面板（admin_stats，工作区已删除）、未提交的手机号归一化 + can_stream 默认允许 + 真实阿里云短信。
   - **wechat-v1（对方）**：管理端深度优化 —— 内容安全分层分级（tier/whitelist/messages）、**微信小程序登录**、**邮箱验证码登录**、头像上传+图片审核、留言三段式展示管线、**用户自删留言**、账号注销联动清理、**Docker 部署体系重构**、nginx 管理端路由。
3. **最大的三个融合难点**（会决定融合工作量）：
   - **content_safety 数据表结构冲突（critical）**：两分支各有一套 content_safety 表 DDL，PK 类型（String(36) vs UUID）、列名（is_active vs enabled）、约束全部不一致，且分散在 live_core 和 users 两个服务。
   - **分类体系数据结构冲突（high）**：main 是"父子分类 + 多对多 + is_primary"，wechat 是"live_rooms.category_id 扁平单列"——必须二选一。
   - **can_stream 语义冲突（high）**：双方都翻转成"默认允许开播"，但 main 只改了一半（工作区），JWT 默认值、模型、迁移脚本、索引方向两边各有各的改法。

4. **好消息**：双方都保留了大量共享代码（留言/Tab 路由、专家模块、搜索模块、用户行为、品牌等），结构性重叠很高，融合主要是"以一方为基底 + 增量合入"。

## 三、模块级对比明细（11 个模块）

### 3.1 backend/users 服务（认证与用户管理）⭐ 对方优化重点

**wechat-v1 独有（值得融入的新功能）**：
1. **微信小程序登录**：`POST /auth/wechat-login`，code→openid→查/建用户→JWT；`wechat_auth_provider.py`（Mock/Official 双实现）
2. **邮箱验证码登录**：`POST /auth/login/email` + `login_by_email_ticket`，`EmailProvider`（SMTP 465/587 真发信），`aiosmtplib==3.0.2`
3. **头像上传 AvatarUploadService**：走内容安全 + image_moderation 图片审核（V1.0 placeholder），且**拒绝 PATCH /me 传 avatar_url**（只能走 POST /me/avatar）
4. **JWT 增强**：`avatar_url` 声明、`JWT_LEEWAY_SECONDS` 时钟偏差、deps 增加**会话吊销检查**（管理端封禁/禁播后 access token 立即失效）
5. **账号注销联动**：DELETE /users/me 需图形验证码，成功后 best-effort 调 live_core `deactivate-cleanup` 清理房间数据
6. **管理端用户增强**：列表增加 phone_number/nickname/can_stream 筛选；改角色仅 SUPERADMIN 可；ADMIN 状态白名单（NORMAL↔BANNED）；**禁止管理员改自己**；封禁/禁播/降权时精确吊销会话
7. **can_stream 默认允许开播**（与你的工作区改动同向，见冲突 §4.1）

**main 独有（需要保留的）**：
- 邮箱注册 + register_ticket 邮箱验真（注册即登录）
- 密码强度校验 min_length=8（wechat 是 6）
- 工作区：`app/core/phone.py` 手机号归一化、阿里云短信认证 Dypnsapi 真实实现、移除腾讯短信

### 3.2 留言管理（live_features）⭐ 用户点名的模块

**两边路由结构完全一致**：5 个 router（admin_tab/public_tab/public_message/admin_message/message_ws），路径无冲突。`models/live_features.py` 两分支字节级一致。

**wechat-v1 独有（值得融入）**：
1. **写时快照**：send_message 时把昵称**和头像**（avatar_url）快照进留言 extra（main 只存昵称）
2. **三段式展示管线**：写时快照 → 读时个人中心回填 → 注销占位（main 只有后两段，无头像回填）
3. **统一内容安全审核**：留言内容走 `check_content_safety`（scene="message"），替代 main 的 URL 正则过滤 + 可选降级（wechat 是硬校验）
4. **C 端单条删除**：`DELETE /rooms/{room_id}/messages/{message_id}`，管理员可删任意、普通用户删自己（main 没有这个端点）
5. **管理端列表嵌套 user 对象**：AdminMessageItem 含 user（id/nickname/avatar_url）+ user_role_str + 禁言显示，main 只有平铺字段
6. **用户友好拦截文案**：content_safety/messages.py 提供的提示文案

**main 独有**：
- 留言限流 check_message_rate_limit 返回 bool + service 抛 4004（wechat 抛 2004/422，行为略不同）
- main 工作区也在补 avatar_url 回填（说明你也意识到这块）

### 3.3 内容管理（categories/tags）⭐ 用户点名的模块

**高度同源**（API/Schema 几乎逐行一致），差异集中在：
1. **HTTP 动词**：main 用 PUT、wechat 用 PATCH 更新 tag/category —— 前端要一起改，建议统一
2. **分类层级实现方式**：
   - main：V5 部分唯一索引 + V10 数据重构 + Service 树治理校验（深度/循环/父分类启用态）
   - wechat：普通唯一索引 + get_children_categories（tree 参数 + children selectinload）
3. **直播间分类 is_primary 主分类语义**：main 完整实现（primary_category_id 必填校验、自动递补、CRUD 更新），wechat 无此语义
4. **main 独有**：batch_set_live_room_categories（批量设置直播间分类，部分成功语义）—— 这是工作区新加的

### 3.4 内容安全（content_safety）⚠️ 最严重冲突

**两分支各有一套 content_safety 目录**（live_core 下），文件清单高度重合，但：
- **main**：15 个文件，规则集中在 engine + medical_lexicon_data 硬编码全量规则，无 tier/whitelist/messages
- **wechat**：17 个文件，**独有 tier.py（A/B/C/D 分层分档 + block/warn/禁用矩阵）、whitelist.py（分类白名单撤销命中）、messages.py（用户友好文案）**

**critical 冲突**：两套 **数据表 DDL/ORM 完全不一致**：
| 维度 | main | wechat |
|------|------|--------|
| 位置 | live_core_service/app/content_safety | users/app/content_safety + live_core 各一份 |
| PK | String(36) | UUID |
| 启用列 | is_active | enabled |
| 约束 | 无 CheckConstraint | 模型内联 5 个 CheckConstraint |
| 增量迁移 | migrate.py 加 binding_level/rule_category/regulation_ref | 与 main 相同的增量语句 |

**users 服务的 content_safety + image_moderation 是 wechat 独有**（main 完全没有），头像审核依赖它。

### 3.5 管理端房间与统计

### 3.6 专家与科室

## 六、对方优化的核心价值判断

对方这轮优化的**管理端相关**成果按价值排序：

1. **内容安全分层体系**（tier/whitelist/messages + 图片审核）—— 医疗直播合规刚需，价值最高
2. **微信/邮箱登录** —— 获客渠道扩展，中等价值
3. **留言三段式展示 + 用户自删** —— 用户体验提升，价值高且与你的留言模块重叠小
4. **管理端用户/权限增强**（禁改自己、状态白名单、会话吊销）—— 安全加固，价值高

## 七、风险提示

1. **content_safety 双套表结构**是最大的坑：两分支的 migrate.py 都在跑同一批增量语句，融合时若 DDL 不统一，生产库可能直接挂
2. **wechat session.py 双前缀疑似 bug**：融合时顺手修掉
3. **未跟踪文件**：main 工作区的 room_card_service.py 等未跟踪文件要确认纳入版本控制，否则融合后丢失
4. **JWT_SECRET_KEY 一致性**：两服务共享 JWT 验签，融合后必须保证同一密钥
5. **前端适配**：PATCH /me 契约、留言 admin schema、PUT→PATCH 切换，前端都要同步改
6. **品牌电商移除**（DROP brand_members/brand_products）：确认前端无引用再执行
