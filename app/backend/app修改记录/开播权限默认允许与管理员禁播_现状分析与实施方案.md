## 二、当前业务问题

### 2.1 前端现象

前端创建直播时，请求链路如下：

```text
创建直播页面
  → POST /api/core/rooms
  → 请求体仅包含 title、description
  → 后端返回 HTTP 500
  → 前端提示 HTTP Error: 500
```

根据前端日志，创建 Room 的请求数据为：

```json
{
  "title": "test",
  "description": "111111"
}
```

封面图片此时并未传入 `/rooms` 创建接口，因此本次 500 与图片代理、Unsplash 下载失败、本地封面路径无直接关系。

### 2.2 直接原因

当前 `live_core_service` 在创建直播间时读取 JWT 中的 `can_stream`：

```python
can_stream = current_user.get("can_stream", False)
```

然后在 `RoomService.create_new_room` 中执行开播权限检查：

```python
if role not in ("ADMIN", "SUPERADMIN") and not can_stream:
    raise PermissionDeniedException("需要开播资格才能创建直播间")
```

因此，当普通用户 JWT 中 `can_stream=false` 时，会被拒绝创建直播间。

但 `create_room` 接口目前只捕获了 `ParentRoomNotFoundException`，没有捕获 `PermissionDeniedException`，导致业务权限拒绝冒泡为 HTTP 500。

### 2.3 根本原因

根本原因不是前端参数错误，而是当前代码中的权限语义与最新业务决策相反。

当前实际语义是：

```text
普通用户默认不能开播。
只有 can_stream=true 才能开播。
ADMIN/SUPERADMIN 不受 can_stream 限制。
```

目标业务语义是：

```text
普通用户默认可以开播。
只有管理员主动设置 can_stream=false 时才不能开播。
ADMIN/SUPERADMIN 不受 can_stream 限制。
```

也就是说，当前系统已经落地了“白名单授权模型”，但业务现在需要的是“默认允许 + 管理员禁播模型”。

## 三、当前实际实现状态

### 3.1 users 表字段语义

当前用户模型中 `can_stream` 默认值为 `false`：

```python
can_stream = Column(
    Boolean,
    nullable=False,
    default=False,
    server_default=text("false"),
    comment="是否拥有开播资格；与 role 正交",
)
```

这表示新用户默认没有开播资格。

### 3.2 Pydantic Schema 默认值与用户创建链路的默认值来源

当前 `UserBase` 中也将 `can_stream` 默认设置为 `False`：

```python
can_stream: bool = Field(False, description="是否拥有开播资格")
```

注意：注册路径的实际入库值**不取决于 Schema 默认值**——`crud_user.create`（`backend/users/app/crud/crud_user.py:120-134`）构造 `User` 实例时**不写入** `can_stream` 字段：

```python
db_user = User(
    username=user_in.username,
    email=user_in.email,
    # ... 未传 can_stream
)
```

因此新用户的 `can_stream` 完全取决于 ORM 模型默认值（SQLAlchemy 层）与数据库 `server_default`（原生 SQL 插入时）。这意味着：

```text
只要同时修改 ORM 默认值 + 数据库默认值为 true，所有新用户（邮箱注册、手机注册、
一键登录自动注册、SSO 自动建号、管理员手动创建）都会自动获得 can_stream=true，
无需逐个修改注册路径。
```

这是本次方案"改默认值即可覆盖所有新用户"的关键依据，也是当前"所有新用户默认禁播"的直接来源。Schema 默认值仅影响接口示例、文档生成和部分序列化场景。

**副作用（P1/P2 决策，不阻塞本次）**：由于 `crud_user.create` 不写入 `can_stream`，当前**创建用户接口即使传 `can_stream=false` 也不会生效**（入库仍按 ORM 默认值）。若未来需要"管理员创建用户时直接指定禁播"，需修改 `crud_user.create` 显式写入 `can_stream=user_in.can_stream`，并补测试；本次"默认允许开播"不依赖该修改。

### 3.3 JWT 签发默认值

认证服务 `_create_access_token` 当前参数默认值为：

```python
can_stream: bool = False
```

因此，只要某条登录路径调用 `_create_access_token` 时没有显式传入 `can_stream`，JWT 中就会默认携带：

```json
{
  "can_stream": false
}
```

### 3.4 Token 签发路径不一致

当前多条 Token 签发路径中，只有部分路径显式传入了 `can_stream`。未传入的路径会使用 `_create_access_token` 默认值 `False`。

需要重点处理的路径包括：

| 登录/签发路径 | 当前风险 | 目标行为 |
|---|---|---|
| 密码登录 | 已显式读取，但 fallback 是 false | 显式读取 DB，fallback 改 true |
| refresh token | 已显式读取，但 fallback 是 false | 显式读取 DB，fallback 改 true |
| SSO 登录 | 未显式传入，默认 false | 显式传入用户 can_stream |
| 手机验证码登录 | 未显式传入，默认 false | 显式传入用户 can_stream |
| 手机注册后即登录 | 未显式传入，默认 false | 新用户 token 中 can_stream=true |
| 邮箱注册即登录 | 未显式传入，默认 false | 新用户 token 中 can_stream=true |
| 一键登录 | 未显式传入，默认 false | 显式传入用户 can_stream |
| 云函数一键登录 | 未显式传入，默认 false | 显式传入用户 can_stream |

这是当前线上或测试环境中普通用户无法开播的重要来源。

### 3.5 live_core_service 缺省值

创建房间接口当前将缺失的 `can_stream` 视为 `False`：

```python
can_stream = current_user.get("can_stream", False)
```

这意味着旧 Token、第三方 Token 或某些漏签字段的 Token 都会被当作没有开播权限。

### 3.6 管理端能力现状

当前管理端已经具备通过 `PATCH /admin/users/{user_uuid}`（注意：路径参数是用户的 `public_id` UUID，不是内部 `id`）修改 `can_stream` 的能力，并且在修改用户权限相关字段时已经存在会话吊销逻辑（`admin_user_service.py:166-177` 调用 `_revoke_user_sessions`）。

因此本次不需要新增专门的 `stream-ban` 或 `stream-unban` 接口。短期直接复用现有 PATCH 能力即可。具体确认项：

```text
1. 吊销逻辑已实现，无需修改代码，仅需补测试验证。
2. 现有权限检查仅限制 ADMIN 不可修改 SUPERADMIN（admin_user_service.py:147-150），
   未限制 ADMIN 修改 ADMIN，与"管理员可互相管理"的产品口径一致。
3. 普通用户自更新使用 UserUpdateSelf（schemas/users.py:363-368），
   仅含 username/nickname/avatar_url/bio，不含 can_stream，
   普通用户无法自改开播权限，无越权风险。
```

### 3.7 MODERATOR 角色现状

当前系统定义了 `MODERATOR` 角色，但在实际权限体系中基本未使用。

结合既有权限文档，`MODERATOR` 可以视为保留枚举：

```text
当前不在前端开放，不主动分配，不作为独立权限层设计。
在开播权限上按普通用户处理。
```

## 四、目标方案

### 4.1 目标权限语义

本次修改后，`can_stream` 的语义调整为：

```text
can_stream=true  ：允许开播，普通用户默认状态。
can_stream=false ：被管理员禁止开播。
```

管理员和超级管理员仍然绕过该字段：

```text
ADMIN / SUPERADMIN 即使 can_stream=false，也允许创建直播间。
```

MODERATOR 暂不启用，按普通用户处理：

```text
MODERATOR + can_stream=true  ：允许开播。
MODERATOR + can_stream=false ：禁止开播。
```

### 4.2 权限矩阵

| 角色 | can_stream=true | can_stream=false | 说明 |
|---|---:|---:|---|
| REGULAR | 可以开播 | 禁止开播 | 默认 true，管理员可禁播 |
| MODERATOR | 可以开播 | 禁止开播 | 当前不启用，按普通用户处理 |
| ADMIN | 可以开播 | 可以开播 | 管理员绕过开播禁播字段 |
| SUPERADMIN | 可以开播 | 可以开播 | 超级管理员绕过开播禁播字段 |

### 4.3 管理权限规则

结合当前产品决策，本次规则定义为：

| 操作者 | 可管理 REGULAR | 可管理 MODERATOR | 可管理 ADMIN | 可管理 SUPERADMIN |
|---|---:|---:|---:|---:|
| ADMIN | 是 | 是 | 是 | 否 |
| SUPERADMIN | 是 | 是 | 是 | 是 |

当前前端不单独建设超级管理员页面，因此重点保证：

```text
ADMIN 可以管理 ADMIN。
ADMIN 不能管理 SUPERADMIN。
```

补充说明：由于建房门禁豁免 ADMIN/SUPERADMIN（room_service.py:121），管理员之间互相设置 `can_stream=false` **不会影响对方开播**——"禁播"动作仅对 REGULAR/MODERATOR 有意义。是否限制管理员修改管理员的 `can_stream`，与"管理员可管理管理员"的产品口径存在两种兼容理解（详见 5.10）：本方案将该限制定义为**可选增强**，不实施也不阻塞本次需求。

### 4.4 错误返回目标

当用户被管理员禁播后创建直播间，应返回：

```text
HTTP 403
错误码：3002（对齐项目已有“权限不足”错误码）
错误消息：你已被禁止开播，请联系管理员
```

不能继续返回 HTTP 500。

## 五、具体实施方案

### 5.1 数据库迁移

由于当前系统尚未正式投入使用，没有真实禁播数据，可以直接将历史数据全部修正为 `true`。

执行内容：

```sql
ALTER TABLE users ALTER COLUMN can_stream SET DEFAULT true;

UPDATE users
SET can_stream = true;
```

如果当前数据库中存在部分索引：

```sql
WHERE can_stream = TRUE
```

建议调整为面向禁播用户的部分索引：

```sql
DROP INDEX IF EXISTS idx_users_can_stream;

CREATE INDEX idx_users_can_stream
ON users (can_stream)
WHERE can_stream = FALSE;
```

原因：当默认所有用户都可以开播后，`can_stream=true` 会成为大多数数据，索引选择性较低；真正需要后台筛选和运营关注的是 `can_stream=false` 的禁播用户。

同时更新数据库字段注释：

```sql
COMMENT ON COLUMN users.can_stream IS '是否允许开播；默认允许，管理员可设置为 false 禁止普通用户开播';
```

### 5.5 统一 Token 签发路径

所有登录路径都应显式读取用户对象上的 `can_stream`：

```python

    user_public_id,
    user_role,
    username=user_username,
    nickname=user_nickname,

```

对于注册后立即登录的新用户，可以使用：

```python
new_user_can_stream = bool(getattr(new_user, "can_stream", True))
```

或在确认新用户默认允许开播时直接传：

```python
can_stream=True
```

必须覆盖以下路径：

1. 密码登录
2. refresh token

### 5.9 RoomService 门禁逻辑收紧（防御性修正，推荐同批实施）

当前门禁逻辑：

```python
if role not in ("ADMIN", "SUPERADMIN") and not can_stream:
    raise PermissionDeniedException("需要开播资格才能创建直播间")
```

潜在问题：`_create_access_token` 支持 `role=""` 的访客 token（`auth_service.py:259-260`，当前代码注释保留"访客"语义）。当本次把 `can_stream` 默认值改为 `true` 后，如果未来某条路径漏传角色或签发了访客 token，`role=""` + `can_stream=true` 会直接通过当前门禁，**未知角色/访客 token 也能创建直播间**。

当前各登录路径的 role 均取自数据库用户（非空），因此这是理论风险，但收紧成本极低，建议同批完成。目标逻辑：

```python
if role in ("ADMIN", "SUPERADMIN"):
    # 管理员绕过禁播
    pass
elif role not in ("REGULAR", "MODERATOR"):
    # 访客 / 未知角色一律拒绝（即使 can_stream=true）
    raise PermissionDeniedException("无开播权限")
elif not can_stream:
    raise PermissionDeniedException("你已被禁止开播，请联系管理员")
```

语义对照：

```text
REGULAR / MODERATOR + can_stream=true  → 放行
REGULAR / MODERATOR + can_stream=false → 403（禁播）
ADMIN / SUPERADMIN（任意 can_stream）   → 放行
role="" 或其他未知角色（任意 can_stream）→ 403（防御）
```

注意：`role` 从 JWT 读取后需统一大写（live_core 的 `get_current_user` 已做 `.upper()`，但直接构造测试 token 时需自行保证，避免 `"regular"` 被误判为未知角色）。

防御边界说明：`get_current_user` 对**缺失 role 的 token 默认视为 REGULAR**（deps.py:54 `token.get("role", "REGULAR").upper()`），因此 5.9 只能拦截 `role=""` 和未知角色，**不能拦截缺失 role 的 token**（会被当作 REGULAR + can_stream=true 放行）。当前各签发路径均写入 role，且 `POST /rooms` 走 Strict Auth（无 token 直接 401），缺失 role 只可能来自内部签发缺陷或伪造 token（受 JWT 签名保护），风险可控；是否调整为"缺失 role 一律拒绝"不纳入本次范围，如需调整需同步修改 deps.py 默认策略并评估对旧 token 的影响。

### 5.10 管理端禁播边界细化（可选增强，默认不阻塞本次）

> 定位说明：本小节与"管理员可以管理管理员"的产品口径存在两种兼容理解，需产品确认后决定是否实施：

```text
  —— 避免无效操作与误导；
  —— "可管理管理员"需解释为不含开播权限字段；
  —— 若后台展示 can_stream 开关，建议同时在前端对 ADMIN 行隐藏该开关。
```

文件：

现状：`update_user_by_admin` 已有两道静态检查（admin_user_service.py:147-159）：

```text

2. ADMIN 不可将目标用户角色提升为 SUPERADMIN。
```

```python
# 新增检查：ADMIN 不可修改 ADMIN/SUPERADMIN 的开播权限
if (admin_user.role == UserRole.ADMIN

    raise PermissionDeniedError("管理员无权修改管理员的开播权限")
```

```text
2. SUPERADMIN 不受此限制，可修改任何用户的 can_stream。
```

## 六、为什么之前字段为 false 仍可以开播

从当前代码演进判断，之前用户创建后可以开播，最可能的原因是：

```text
can_stream 字段虽然存在，但之前创建直播链路没有真正使用它进行硬拦截。
```

字段存在不代表已经生效。只有当 `live_core_service` 创建房间接口开始读取 JWT 中的 `can_stream`，并在 `RoomService.create_new_room` 中执行检查后，`can_stream=false` 才会真正阻止普通用户开播。

因此，之前邮箱注册用户虽然数据库字段可能是 false，但如果创建直播逻辑未校验该字段，就不会影响开播。现在问题出现，是因为白名单式的开播资格校验已经接入了创建房间链路。

该判断已通过 git 历史验证：`can_stream` 字段与建房门禁（"需要开播资格才能创建直播间"）在同一融合提交（`7e2c914`）中一次性引入，此前基线（`988d9d6`）的创建房间链路不存在该校验。因此之前用户即使 `can_stream=false` 也能创建直播，符合上述推断。

## 七、风险分析与对应方案

### 7.1 风险一：全量改 true 解除历史禁播

当前判断：该风险在本项目当前阶段可以接受。

原因：

```text
系统尚未正式投入使用，没有真实禁播数据。
```

处理方案：

```sql
UPDATE users SET can_stream = true;
```

如果后续正式运营后再次做类似迁移，必须先备份和人工确认。

### 7.2 风险二：Token 生效延迟窗口（双向，需区分是否触发会话吊销）

`can_stream` 写入 JWT，但权限变更是否即时生效，取决于变更路径**是否触发会话吊销**（admin 修改会调用 `_revoke_user_sessions`，全量 SQL UPDATE 不会）。两个方向分四种场景：

```text
方向 A（恢复开播）：
  A1 全量 SQL UPDATE 改 true（本次迁移）：
     不触发吊销 → 旧 token 中 can_stream=false 继续生效，最长 1 小时窗口
     （access token 有效期，auth_service.py:252），需重新登录才能提前恢复。
  A2 管理员 PATCH 解禁（can_stream=false→true）：
     触发吊销 → 旧 access token 被 live_core 401 拒绝，重新登录即恢复。

方向 B（禁止开播）：
  B1 管理员 PATCH 禁播（can_stream=true→false）：
     触发吊销 → 近实时生效（见下方条件表）。
  B2 未来若直接 SQL 改 false：
     不触发吊销 → 旧 access token 最长 1 小时仍可建房间。
```

关键事实（已在代码中验证）：**live_core_service 的鉴权依赖已校验 access token 的吊销状态**——`deps.py:16-40` `_ensure_session_not_revoked` 对比 token `iat` 与 Redis 中 `user_sessions_revoked:{user_id}` 的吊销时间，`get_current_user`（:55-56）与 `get_current_user_optional`（:82-83）均会调用。users 服务侧 `refresh_access_token` 同样校验（auth_service.py:760-766）。吊销记录保留 7 天（auth_service.py:977）。

生效条件（B1 场景）：

```text
| 条件 | 禁播后旧 access token 是否继续有效 |
|---|---|
| Redis 正常，且 users 与 live_core 连同一 Redis（吊销 key 共享） | 否，访问 live_core 即被 401 拒绝，近实时生效 |
| Redis 不可用或两服务 Redis 不一致 | 可能继续有效，最长 1 小时（降级放行，deps.py:39-40） |
| token 缺失 user_id 或 iat | 跳过吊销校验直接放行（deps.py:20-21） |
```

因此"最长 1 小时窗口"仅存在于降级/未共享 Redis 场景；正常部署下禁播是近实时生效的。上线前必须确认两服务 `REDIS_URL` 指向同一实例（users 配置见 config.py:91-97，live_core 见 redis_cache.py:20-21，均优先 `REDIS_URL`）。

处理方案：

```text
1. 禁播/解禁后只能重新登录，不能刷新：管理员修改 can_stream 时已吊销用户会话，
   用户 refresh token 的 iat 早于吊销时间会被 _is_user_sessions_revoked 拒绝
   （提示"凭证已失效，请重新登录"，auth_service.py:981-1004），刷新路径无法获取新权限。
   注意：重新登录不是"清除吊销记录"，而是签发 iat 晚于吊销时间的新 token。
2. 方向 A1（全量 UPDATE 恢复）不触发吊销，旧 token 最长 1 小时仍为 false，
   测试用户遇到时重新登录即可。
3. 上线后新登录用户自然获得 can_stream=true。
4. 正式运营前确保所有登录路径已修复。
5. 如未来要覆盖"直接 SQL 改权限也即时生效"，再引入 Redis 权限缓存或跨服务实时校验（见十二）。
```

3. 若产品选择 5.10 方案 B，则 ADMIN 不可修改 ADMIN/SUPERADMIN 的 can_stream；若选择方案 A（默认），保留现状即可，风险仅为语义误导（设置对管理员开播无实际效果）。
4. 建议保留或补充操作日志，方便后续追踪。
5. 不在本次增加复杂层级审批。

### 7.7 风险七：MODERATOR 角色语义不明确

当前判断：暂不启用。

处理方案：

```text
保留枚举，不在前端开放，不主动分配。
在开播权限上按普通用户处理。
```

### 7.8 风险八：默认值翻转后访客/未知角色 token 可借道放行

影响：

```text
本次把 can_stream 默认值改为 true 后，若某条路径签发 role=""（访客）或未知角色的
token 且 can_stream=true，当前门禁（room_service.py:121）会直接放行，
导致未认证/未知身份也能创建直播间。
```

当前判断：各登录路径的 role 均取自数据库用户（非空），且当前没有签发访客 token 的调用方，因此属于**理论风险**，不是本次修改引入的实际漏洞。

处理方案：

```text
实施 5.9 门禁收紧（角色白名单校验）后，即使未来出现访客/未知角色 token，
```


## 十一、方案最终效果

实施完成后，系统将达到以下效果：

1. **普通用户默认可以创建直播**，符合当前产品需求。
2. **管理员仍可禁止用户开播**，通过现有 `PATCH /admin/users/{user_uuid}` 修改 `can_stream=false` 实现。
3. **所有登录方式权限一致**，不会再出现密码登录可以开播、手机号登录不能开播的差异。
4. **新注册用户默认可以开播**，包括邮箱注册、手机注册、一键登录创建的新用户。
5. **被禁播用户收到明确 403**，不再表现为服务器 500。
6. **MODERATOR 暂不启用但不影响系统**，后续如需要运营审核角色可再单独设计。
7. **管理员可以管理管理员但不能管理超级管理员**，符合当前前端和运营管理边界。
8. **实现成本较低**，不新增数据表，不重构权限体系，不引入跨服务实时查询。
9. **禁播通过管理端 PATCH 触发时近实时生效**（live_core 校验 access token 吊销，见 7.2）；
   全量 SQL 迁移恢复开播不触发吊销，旧 token 存在最长 1 小时窗口，当前阶段可接受。
