### 3.2 分层落点原则（本项目分层规范）

沿用 CLAUDE.md 与《融合方案_提示词编写规范借鉴》的分层铁律，手机号校验的落点规则为：

```
Schema 层（Pydantic field_validator）  ← 第一道闸：请求一进来就校验+归一化，天然返回 422
    ↓
Service 层（防御性校验）               ← 第二道闸：外部系统回传值（运营商 provider、云函数、ticket）不信任
    ↓
CRUD 层（查询兜底）                    ← 第三道闸：兼容历史脏数据，归一化后再匹配
    ↓
前端（体验校验）                       ← 用户可见输入提前拦截，减少无效请求
```

**为什么这么分层：**

- Schema 层收敛**用户直接输入的明文手机号**，保证下游（Redis key、ticket、数据库）拿到的永远是归一化格式——这正是《注册一键登录忘记密码分析文档》11.8 提出的 ticket 模型能成立的前提。
  > ⚠️ **唯一例外：云函数一键登录**（§6.2.3）——因 HMAC 验签必须用原始字符串，该 Schema 字段**只校验不归一化**，归一化推迟到 Service 验签通过之后（§6.3.2）。
- Service 层处理**外部系统回传的手机号**（运营商取号、云函数解密号），因为 HMAC 验签只能证明"没被篡改"，不能证明"格式合法"。
- CRUD 层兜底**历史脏数据**（已入库的 `+86`/空格/横线格式），因为存量用户不能因为本次改造而登录失败。
- 前端负责**体验**：用户输入即校验、即格式化，但不作为安全边界。

## 四、当前问题阐述

### 4.1 问题总览

> **后端当前没有任何手机号格式校验，也没有任何归一化处理。** 手机号以用户原始输入/外部系统原始返回值的形式直接进入 Redis key、ticket、数据库和短信服务商。

具体表现在 4 个层面：

| 层面 | 现状 | 后果 |
|---|---|---|
| 格式校验 | 8 个入口全部无校验（见 4.2） | 任意字符串可触发发码、验码、绑定、注册、登录流程 |
| 归一化 | 无任何归一化，`+8613800138000` 与 `13800138000` 是不同字符串 | **同一手机号被当成多个账号**（详见 4.3.1） |
| Redis key | `otp:{scenario}:{recipient}` 用原始格式拼 key | 同号不同格式各自生成验证码，验证码无法互通 |
| 短信下发 | `recipient` 原样传给 `sms_provider.send()` | `+86` 前缀可能导致短信服务商拒发或计费异常 |

### 4.2 手机号进入系统的全部入口清单（代码核查结果）

| # | 入口 | 位置 | 当前校验 | 说明 |
|---|---|---|---|---|
| 1 | 发送短信验证码 | `schemas/auth.py` `VerificationCodeRequest.recipient`（channel=SMS 时） | ❌ 无 | 原样拼 `otp:{scenario}:{recipient}`（`auth_service.py:447`），原样传给短信商（`auth_service.py:463`） |
| 2 | 校验验证码 | `schemas/auth.py` `VerifyCodeRequest.recipient`（channel=SMS 时） | ❌ 无 | 原样拼 key（`auth_service.py:1358`），签发的 ticket 里存原始格式 |
| 3 | 云函数一键登录 | `schemas/auth.py` `CloudFunctionLoginRequest.phone` | ❌ 无 | HMAC 验签通过后直接查库/建号（`auth_service.py:1276-1296`），`phone[-4:]` 生成昵称（1288）、`social_id=f"carrier:{phone}"`（1291），非法格式直接产生脏数据 |
| 4 | 运营商一键登录 | `services/carrier_auth_provider.py:34-39` 返回值 | ❌ 无 | Mock provider 约定格式为 `mock:+8613800138000`（**自带 +86 前缀**），返回后直接查库/建号（`auth_service.py:1158-1187`） |
| 5 | 绑定手机号 | `schemas/users.py` `PhoneBindRequest.phone_number` | ❌ 无 | 与 ticket 中的 recipient 做**精确字符串比对**（`user_service.py:527`），格式不一致直接误判"票据与手机号不匹配" |
| 6 | 手机号+密码登录 | `schemas/auth.py` `LoginRequest.username`（三合一） | ❌ 无 | 走 `crud_user.get_by_login_identifier`（`crud_user.py:524`），其中手机号匹配要求 `is_phone_verified=True` 且精确等值 |
| 7 | 创建/更新用户 | `schemas/users.py` `UserBase.phone_number` / `UserUpdate.phone_number` | ❌ 无 | 注册走 ticket 不直接传；但 SSO 建号、admin/internal 场景会经过 |
| 8 | 手机号验证码登录 | `PhoneLoginRequest.login_ticket`（间接） | ❌ 无 | 手机号在发码/验码环节进入，随 ticket 流转（`auth_service.py:1017-1063`），源头不受控则此处必脏 |

### 4.3 问题定性

#### 4.3.1 同号多账号（核心风险，历史文档未完整覆盖）

`crud_user.get_by_phone_number`（`crud_user.py:85-100`）与 `get_by_login_identifier`（`crud_user.py:524`）均为**精确等值匹配**：

```
13800138000       → 账号 A
+8613800138000    → 账号 B（如果曾被某种方式写入）
138 0013 8000     → 账号 C
```

后果链：

1. **注册查重失效**：用 `+8613800138000` 注册能绕过"手机号已被注册"检查（注册 ticket 里存的是归一化前的值）。
2. **登录失效**：注册时存了 `+86` 格式，用户输 11 位手机号登录查不到账号；反之亦然。
3. **绑定查重失效**：`user_service.py:532` 用请求格式查占用，脏格式手机号可能查不到已绑定的同号用户。
4. **一键登录冲突**：运营商返回 `+8613800138000`（Mock 即如此，`carrier_auth_provider.py:31`），与用户已注册的 `13800138000` 查不到，自动创建第二个账号。

#### 4.3.2 验证码链路断点

```
发送验证码（格式 A） → Redis otp:{scenario}:{A}
校验验证码（格式 B） → Redis otp:{scenario}:{B} → 查不到 → "验证码不存在或已过期"
```

前端输入 `+86 13800138000` 发码、粘贴 `13800138000` 验码，OTP 必然找不到。这是"用户说验证码发过来了但一直说验证码错误/过期"的典型根因。

#### 4.3.3 绑定比对断链

`user_service.py:527` 要求 `ticket_data["recipient"] == phone_number` 精确相等。绑定页发码时用格式 A、提交时输入格式 B，即使验证码正确也报"绑定票据与手机号不匹配"。

#### 4.3.4 云函数/运营商入口脏数据

`one_tap_login_direct`（`auth_service.py:1287-1291`）用 `phone[-4:]` 生成昵称、`social_id=f"carrier:{phone}"`，`phone` 若是 `"1380013"` 这类字符串，会写入不可读昵称与错误 social_id，污染用户表。

#### 4.3.5 数据库既有可能已存在脏数据

历史短信 Mock 流程允许任意 `recipient` 直接入库（如 `+86` 前缀）。即使本次全部入口校验，存量脏格式用户仍会"登录找不到账号"。

### 4.4 问题优先级

| 优先级 | 问题 | 影响面 |
|---|---|---|
| P0 | 无归一化导致同号多账号 | 注册/登录/绑定/一键登录全部受影响，直接产生重复账号与"找不回账号"投诉 |
| P0 | 发码/验码无校验 | 短信浪费（任意字符串触发下发）、Redis key 污染、验证码链路断链 |
| P0 | 云函数/运营商返回手机号无校验 | 一键登录自动建号写入脏数据 |
| P1 | 绑定无校验 | 绑定流程比对断链、绑定查重失效 |
| P1 | 三合一登录无手机号分支 | 手机号输入格式错误时无明确反馈，走邮箱逻辑产生误导性错误 |
| P1 | UserCreate/UserUpdate 无校验 | admin/SSO 建号可写入脏手机号 |
| P2 | 历史脏数据 | 存量用户登录/绑定异常 |

## 五、目标架构与统一规则

### 5.1 统一校验规则

产品面向中国大陆手机号，统一采用：

```text
^1[3-9]\d{9}$
```

允许用户输入（前端宽容、后端归一化）：

```text
13800138000
138 0013 8000
138-0013-8000
+86 13800138000
86 13800138000
```

### 5.2 归一化规则（入库前必须执行）

```text
1. strip() 去首尾空白
2. 去除所有空格与 "-" 
3. 去掉 "+86" 前缀
4. 去掉 "86" 前缀（仅当去掉后为 11 位）
5. 最终必须匹配 ^1[3-9]\d{9}$
```

归一化后统一以 `13800138000` 格式入库、拼 Redis key、传短信服务商。

**为什么归一化而不是直接拒绝非 11 位输入：**

- 运营商/云函数/短信服务商生态中 `+86` 前缀是事实标准（Mock carrier provider 即返回 `+8613800138000`），拒绝会导致这些入口全部不可用。
- 前端输入习惯（空格/横线分组）在国内 App 中普遍存在，宽容输入 + 统一存储是行业惯例。
- 与《注册一键登录忘记密码分析文档》§5.1"recipient 必须规范化"的要求一致，只是具体格式从 E.164 收敛为纯 11 位（中国区业务简化）。

### 5.3 校验失败的错误处理

| 层 | 行为 |
|---|---|
| Schema 层 | Pydantic `field_validator` 抛 `ValueError` → FastAPI 返回 422（错误信息含"手机号格式不正确"） |
| Service 层 | 抛 `InvalidCredentialsException`（登录/取号场景，避免泄露格式细节）或记日志后拒绝（防御场景） |
| 前端 | 输入框即时提示"请输入正确的手机号"，阻止提交 |

## 六、具体实施方案

### 6.1 新增统一工具模块：`backend/users/app/core/phone.py`

> 不违反"不应修改的模块"约束（`core/` 下禁改的是 auth.py / config.py / database.py 等既有文件，新增工具文件是既有惯例，参见 `core/password.py`）。

```python
"""
手机号工具模块 —— 提供中国手机号格式校验与归一化能力

- 统一校验规则：^1[3-9]\d{9}$
- 统一入库格式：纯 11 位（去除 +86/86 前缀、空格、横线）
- 所有涉及手机号明文入站的 Schema / Service / CRUD 统一引用本模块
"""
import re

CN_PHONE_PATTERN = re.compile(r"^1[3-9]\d{9}$")


def normalize_cn_phone(phone: str) -> str:
    """归一化手机号：去空白/横线、去 +86/86 前缀，返回纯 11 位"""
    value = str(phone or "").strip()
    value = value.replace(" ", "").replace("-", "")
    if value.startswith("+86"):
        value = value[3:]
    elif value.startswith("86") and len(value) == 13:
        value = value[2:]
    return value


def is_valid_cn_phone(phone: str) -> bool:
    """判断手机号是否合法（先归一化再匹配）"""
    return bool(CN_PHONE_PATTERN.fullmatch(normalize_cn_phone(phone)))


def validate_cn_phone(phone: str) -> str:
    """校验并返回归一化后的手机号；非法时抛 ValueError"""
    normalized = normalize_cn_phone(phone)
    if not CN_PHONE_PATTERN.fullmatch(normalized):
        raise ValueError("手机号格式不正确")
    return normalized
```

#### 6.2.3 `schemas/auth.py` — `CloudFunctionLoginRequest.phone`

> ⚠️ **定稿方案（2026-08-01 复核）**：本字段 **只校验格式、不做归一化**。原因：云函数 `get-phone-number/index.js`（`D:\saas_app-main\uniCloud-aliyun\cloudfunctions\get-phone-number\index.js:32-47`）的签名与返回均使用 `res.phoneNumber` **原样字符串**（`sign = HMAC_SHA256(phone + timestamp, PSK)`），后端验签（`auth_service.py:1273-1278`）也用 `f"{phone}{timestamp}"` 原文。若 Schema 层提前归一化（如把 `+8613800138000` 变 `13800138000`），而云函数签名用的是原样值，验签必然失败。归一化推迟到**验签通过之后**（见 §6.3.2）。

```python
class CloudFunctionLoginRequest(BaseModel):
    phone: str = Field(...)
    sign: str = Field(...)
    timestamp: str = Field(...)

    @classmethod

            raise ValueError("手机号格式不正确")
        return v                       # 原样返回，保证验签用原始字符串
```

> **为什么必须校验（对齐你确认的分析）：** HMAC 验签只证明 `phone + timestamp` 未被客户端篡改，不证明 `phone` 是合法手机号；不校验则 `phone[-4:]` 昵称与 `carrier:{phone}` 的 social_id 会产生脏数据。

```python
# crud_user.py
from app.core.phone import normalize_cn_phone

async def get_by_phone_number(db, *, phone_number: str):
    normalized = normalize_cn_phone(phone_number)
    stmt = select(User).where(User.phone_number == phone_number)
    user = (await db.execute(stmt)).scalars().first()
    if not user and normalized != phone_number:
        stmt2 = select(User).where(User.phone_number == normalized)
        user = (await db.execute(stmt2)).scalars().first()
    return user
```

**为什么需要：** 历史已入库的 `+86`/空格格式数据无法靠新入口校验修复；查询层兜底保证存量用户在新老格式下都能被找到，是"增量设计、最小侵入"原则下对存量数据的唯一低风险方案。

```ts
// src/utils/phone.ts
export function normalizeCnPhone(phone: string): string {
  let value = phone.trim().replace(/\s+/g, '').replace(/-/g, '');
  if (value.startsWith('+86')) value = value.slice(3);
  else if (value.startsWith('86') && value.length === 13) value = value.slice(2);
  return value;
}

export function isValidCnPhone(phone: string): boolean {
  return /^1[3-9]\d{9}$/.test(normalizeCnPhone(phone));
}
```

## 七、为什么不建议其他方案

| 方案 | 不建议原因 |
|---|---|
| 只做前端校验 | 前端可被绕过，防不了恶意调用与外部系统；无法保证入库质量 |
| 只在 Service 层校验 | 每个 Service 方法都要重复写校验，Schema 层已有的声明式能力（422 自动错误）被浪费；发码/验码等 Redis key 拼装点仍可能绕过 |
| 只校验不归一化 | §4.3.1 同号多账号问题完全没解决，注册查重/登录/绑定/一键登录继续失效 |
| 归一化在入库时做（只改 crud create） | 只能管新写入，管不了 Redis key、ticket、短信下发这几个更早的环节；验码断链（§4.3.2）依旧存在 |
| 直接用 E.164 格式（+86 前缀）统一存储 | 与现有 `users.phone_number` 中大量已存纯 11 位数据冲突，且登录输入时仍需剥离前缀，复杂度高于纯 11 位 |
| 用数据库触发器/唯一索引约束手机号列 | 归一化前唯一索引无法识别 `+86` 与纯 11 位为同号；触发器需要迁移与维护，违背项目"不在 DB 层引入触发器"的既有决策（见《融合方案_提示词编写规范借鉴》） |
| 新增换绑接口一并实现 | 需求未确认换绑流程细节（是否需旧手机号验证码、是否需密码二次确认），超前实现风险高；先固化校验约束，接口待需求确认 |
