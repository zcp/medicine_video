# 图片上传接口前后端实现提示词

## 1. 适用对象与任务目标

本提示词适用于当前项目中**图片上传能力的前后端联动实现**。

本任务的目标不是单纯实现“选图后上传一张图片”，而是补齐一条稳定、可复用、可展示的头像上传闭环：
- 手机端从本地相册选择图片；
- 前端将图片上传到后端；
- 后端返回稳定可访问的 `avatar_url`；
- 用户资料接口持久化头像 URL；
- 前端个人信息页可正确展示头像；
- 上传失败时不影响昵称、简介等其他资料保存。

本任务的核心定位是：
- **优先补稳定上传链路**；
- **优先保证图片可正常显示**；
- **优先复用现有用户资料接口与字段**；
- **不新增重复的用户资料体系**。

---

## 2. 强约束与执行前提

### 2.1 当前任务的默认前提
- 当前仓库中**已经存在**用户资料更新接口，且 `avatar_url` 字段已进入现有模型与前端类型定义；
- 当前前端项目位于 `D:\saas_app-main`，其 API 风格以 `src/utils/request.ts` + `src/api/*.ts` 的方式组织，接口封装以 `auth.ts` 中的 `authUrl()` 和 `patch/post/get` 为主要模式；
- 当前任务是对头像上传链路进行补充与稳定化，而不是重写整个认证模块；
- 当前任务优先服务“头像能够上传并正常显示”的目标，不扩展到多图管理、图片社交化编辑等复杂场景。

### 2.2 禁止重复造接口
- 禁止新建一套独立的用户资料体系；
- 禁止为了头像上传另起一套完全重复的个人资料接口；
- 禁止将 `avatar_url` 替换为新的重复字段，例如 `avatar`, `head_img`, `profile_pic` 等；
- 如需增加上传能力，优先围绕现有 `PATCH /users/me` 与头像上传接口做增量补充；
- 前端 API 编写方式必须与现有 `auth.ts` 风格一致：使用 `authUrl(path)` 统一拼接，使用 `post/get/patch` 调用，避免手写零散请求地址。

### 2.3 必须先审查再修改
在生成任何代码前，必须先读取并理解：
- 后端用户资料相关 API 文件；
- 后端用户模型与 schema 中关于头像字段的定义；
- 前端个人资料编辑页的当前实现；
- 前端 API 封装中的用户资料更新方法；
- 当前是否已有头像上传接口或通用文件上传能力；
- `D:\saas_app-main\src\api\auth.ts`、`D:\saas_app-main\src\utils\request.ts` 以及对应的状态管理与页面实现。

严禁在未审查上述内容前直接：
- 猜测接口路径；
- 猜测字段名；
- 重写已有资料更新逻辑；
- 新建一套与现有字段不一致的头像方案。

### 2.4 文件级别约束
为了避免范围过宽，生成代码时必须严格限制可修改文件范围。

#### 允许修改的文件范围
- 后端用户资料相关 API 文件；
- 后端用户服务层与数据访问层中与头像字段相关的最小必要部分；
- 前端 `src/api/auth.ts`；
- 前端个人信息编辑页；
- 前端必要的头像类型定义文件；
- 前端与上传有关的最小必要辅助组件或工具文件。

#### 不允许随意修改的文件范围
- 不允许重构整个认证模块；
- 不允许大范围修改 `src/utils/request.ts` 的请求框架；
- 不允许改动与头像无关的其它业务 API；
- 不允许改动登录、注册、验证码、密码重置等无关流程；
- 不允许新增一套平行的用户资料目录结构。

### 2.5 默认执行顺序
1. 审查当前后端用户资料接口与数据模型；
2. 审查当前前端编辑资料页与 API 调用方式；
3. 明确头像上传是否已有专用接口；
4. 如无专用接口，补充最小可用上传链路；
5. 统一前后端字段名、返回值与展示逻辑；
6. 修改后重新核查图片上传与头像展示是否可闭环。

## 3. 当前任务边界

### 3.1 本任务必须实现的内容
- 图片文件上传；
- 图片类型与大小校验；
- 上传后返回可访问的图片 URL；
- 将返回的 `avatar_url` 持久化到用户资料；
- 前端个人信息页可正常读取并展示头像；
- 上传失败时可继续保存其他资料。

### 3.2 本任务不要扩展的内容
本任务**不要**优先扩展以下方向，除非实现上传闭环必须依赖它们：
- 头像裁剪交互；
- 图片压缩算法优化；
- 多图上传；
- 头像历史版本管理；
- 图片审核工作流；
- 用户封面图、背景图等其他图片类型。

## 5. 任务一：补后端图片上传能力

### 5.1 任务目标
让后端能够稳定接收前端上传的本地图片，并返回一个可直接用于前端展示的 URL。

### 5.2 建议实现方向
建议优先补以下能力中的一项或多项：
- 新增或完善头像上传接口；
- 接收 `multipart/form-data` 文件；
- 对文件类型、文件大小、文件名进行校验；
- 将图片保存到稳定存储；
- 返回标准化的 `avatar_url`；
- 支持后续通过资料更新接口写回用户表。

### 5.3 设计要求
后端上传能力应满足：
- 接口命名清晰；
- 返回结构统一；
- 文件存储位置稳定；
- 图片 URL 可长期访问；
- 与现有资料更新接口字段一致；
- 不破坏当前登录与资料读取流程。

### 5.4 优先实现方式
- 优先在现有用户模块中补充头像上传接口；
- 优先复用已有用户资料更新逻辑；
- 优先复用现有返回结构与错误处理方式；
- 如有通用文件上传能力，可先复用，再补齐头像场景的差异化逻辑。

### 5.5 完成标准
完成后应满足：
- 前端上传图片后能拿到稳定 URL；
- URL 写回用户资料后可再次查询到；
- 服务重启后头像仍可访问；
- 文件类型或大小不合法时能够明确报错。

---

## 6. 任务二：补前端上传对接能力

### 6.1 任务目标
让前端编辑资料页能够从手机本地相册选择图片，并将图片正确上传到后端。

### 6.2 建议实现方向
建议优先补以下能力中的一项或多项：
- 使用系统相册或摄像头选择图片；
- 将图片临时路径转为上传文件；
- 调用头像上传接口；
- 上传成功后更新本地头像显示；
- 上传失败时允许继续保存昵称和简介；
- 页面刷新后继续显示后端返回的正式头像 URL。

### 6.3 设计要求
前端上传对接应满足：
- 选择图片后有明确反馈；
- 上传状态可感知；
- 上传完成后刷新头像展示；
- 本地临时路径只用于过渡，不作为最终持久化地址；
- 前后端字段名一致，避免映射错误。

### 6.4 优先实现方式
- 优先在 `edit-profile` 页面中复用当前资料保存逻辑；
- 优先使用现有 `updateProfile()` 封装；
- 如需单独上传头像，上传成功后再统一回写 `avatar_url`；
- 不建议在前端里写死接口地址或硬编码返回结构。

### 6.5 完成标准
完成后应满足：
- 用户从相册选择图片后可成功上传；
- 上传成功后头像在页面中立即刷新；
- 保存资料时不会丢失头像 URL；
- 上传失败不会影响昵称、简介等其他字段保存。

---

## 7. 接口与数据定义要求

### 7.1 头像上传接口
建议采用如下模式之一，并在全项目中统一：
- `POST /users/me/avatar`；
- 或与现有用户模块风格一致的等价路径。

请求建议：
- `multipart/form-data`；
- 文件字段统一命名为 `file`。

响应建议：
```json
{
  "code": 200,
  "message": "success",
  "data": {
    "avatar_url": "https://example.com/uploads/avatar/xxx.jpg"
  }
}
```

### 7.2 用户资料更新接口
继续复用现有 `PATCH /users/me`，建议支持：
```json
{
  "nickname": "新昵称",
  "bio": "个人简介",
  "avatar_url": "https://example.com/uploads/avatar/xxx.jpg"
}
```

### 7.3 用户信息读取接口
`GET /users/me` 应继续返回 `avatar_url`，供前端个人信息页直接渲染。

## 8. 风险与隐患处理建议

### 8.1 上传失败后的状态恢复不完善
建议把“头像上传”和“资料保存”拆成可恢复流程：
1. 先执行头像上传；
2. 头像上传成功后再执行资料保存；
3. 若上传失败，允许用户只保存昵称/简介；
4. 若资料保存失败，保留本地裁剪结果和待提交状态，方便重试。

### 8.2 头像 URL 稳定性不足
建议统一使用稳定可访问地址，不要把临时文件地址作为最终头像 URL。优先级建议：
1. 对象存储稳定 URL；
2. 持久化静态目录 + Nginx 暴露；
3. 避免临时目录或进程内临时路径。

### 8.3 手机端兼容性问题
建议：
- 选择图片时支持相册与相机；
- 上传前压缩可作为后续优化，但不作为本轮前置硬要求；
- 前端展示使用 `aspectFill` 或等效方式；
- 失败时必须回退默认头像。
