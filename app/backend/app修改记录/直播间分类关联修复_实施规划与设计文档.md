## 一、执行摘要

### 1.1 背景

创建直播间时用户可以选择关联分类（最多 3 个），但**关联了分类的直播间不会显示到首页对应的分类 tab 下**。用户侧表现为"选分类毫无用处"。

### 1.2 核心结论

**后端过滤链路完整可用，真正断点在"创建时分类写入链路"**：

1. 后端 `GET /homepage/rooms?category_id=` 已真实实现按分类过滤（`EXISTS` 子查询 + 父分类递归展开子孙 + 排除私密房间），**不是白写**
2. 前端创建直播间时**没有**把分类放进 `POST /rooms` 主请求（后端原生支持 `category_ids` 字段且无权限门槛），而是单独调用 **仅 ADMIN/SUPERADMIN 可用的** `POST /admin/rooms/{room_id}/categories`
3. 普通用户（医生/专家等 REGULAR 角色）调用该 admin 端点必然 **403**，而前端 catch 只 `console.error` 不阻断 → **用户看到"创建成功"，分类实际从未写入**
4. 首页分类 tab 的过滤基于 `live_room_categories` 表 → 表里没数据 → tab 下自然看不到

**一句话**：功能"后端已实现、前端已暴露选择 UI、写入失败被静默吞掉"，是权限错配 + 静默吞错 + 消费端缺失三重问题叠加。

### 1.3 问题总览

| 级别 | 问题 | 状态 |
|:---:|:---|:---:|
| 🔴 P0 | 创建链路权限错配：前端走 admin 端点，普通用户 403，分类写入必然失败 | 未修复 |
| 🔴 P0 | 403 错误被 catch 静默吞掉，用户无感知 | 未修复 |
| 🟡 P1 | 前端零消费端：详情页硬编码"肝胆外科"、编辑页无分类、列表/播放页无展示 | 未修复 |
| 🟡 P1 | 编辑链路缺失：`LiveRoomUpdate` 无 `category_ids`，用户无法修改已建房间分类 | 未修复 |
| 🟡 P1 | Mock 降级隐患：分类 id 为 `'1'~'8'` 非 UUID，修复后若提交将导致 422 创建失败 | 未修复（修复时规避） |
| 🟢 P2 | 首页 JOIN 无 DISTINCT 分页重复问题 | 未修复（附带项） |

### 1.4 修复后预期效果

- 普通用户创建直播间时选择的分类**真实写入** `live_room_categories` 表
- 首页分类 tab 点击后**能过滤出**该分类下的直播间（父分类自动包含子分类）
- 详情页展示直播间**真实关联的分类**（替代硬编码）
- 编辑页支持**查看与修改**已关联分类（历史数据补救入口）
- 创建流程不因分类问题失败（无效分类降级安全）

## 三、问题根源分析

### 3.1 直接原因：权限错配 + 静默吞错

```
后端提供两条写入路径：
  POST /rooms 携带 category_ids      → 任意有开播资格用户 ✅（后端已实现）
  POST /admin/rooms/{id}/categories → 仅 ADMIN/SUPERADMIN ❌

前端选择了后者（create.vue 步骤5），且 catch 吞掉 403：
  → 普通用户创建：分类写入 100% 失败，无任何提示，创建流程"成功"
  → 首页 tab 过滤：EXISTS 查不到关联 → tab 下永远看不到该房间
```

### 3.2 结构性原因：只写不读，无消费端

- `getRoomCategories`（公开读接口）前端**零调用**
- 详情页硬编码、编辑页无回填、列表/播放页无展示 → 用户和开发者都无法自检分类是否写入
- 即使管理员写入成功，前端也无任何可见变化，功能"形同虚设"

### 3.3 潜在风险：Mock 降级 422

修复后若分类进入主 payload，Mock 降级的非 UUID id（`'1'`）将触发后端 Pydantic UUID 校验失败 → **整个创建流程 422 失败**（当前实现因主 payload 不带分类反而无此问题）。这是修复引入的**新风险**，方案必须前置 UUID 过滤。

## 四、方案设计

### 4.1 设计原则

1. **最小安全幅度**：核心修复 = 前端把 `category_ids` 并入 `POST /rooms` 主 payload（后端零改动）；不放开 admin 端点权限（安全边界不动）
2. **前后端职责清晰**：前端负责参数组织与错误提示，后端负责校验与数据写入（沿用现有 `set_live_room_categories`，不新增写路径）
3. **消费端补齐**：详情页动态展示 + 编辑页可修改，让功能"可见、可自检、可补救"
4. **不引入新风险**：前置 UUID 过滤防 Mock 422；无效分类保持后端现有"静默跳过"语义（与创建路径 A 一致）
5. **每阶段可独立验收**：Gate 审查通过才进入下一阶段

### 4.2 前端改动（阶段一：创建链路核心修复）

| # | 文件 | 改动 |
|:--|:---|:---|
| 1 | `src/pages/app/live-manage/create.vue` | ① `createRoomPayload` 条件注入 `category_ids`（**仅保留 UUID 格式的 id**，非 UUID 过滤 + toast 提示分类数据异常）；② 删除步骤 5 `setRoomCategories` 兜底块（L1245-1257）；③ 删除 L395 import |
| 2 | `src/types/room.ts` | `RoomCreatePayload` 增加可选 `category_ids?: string[]`（可选类型，不影响 `updateRoom`/`MultiVenueManage.vue` 等既有调用点） |
| 3 | `CreateLiveDrawer.vue` | 同 1 的三处改动（死代码顺手修，防复活踩坑） |

**为什么这样改**：
- `addNewRoom` 完全透传 payload（`store/room.ts:160`）→ 加字段即达后端，`LiveRoomCreate` 原生支持，**后端零改动**
- 删除步骤 5：主链路已承载分类写入，保留它只会对普通用户产生必 403 的冗余请求和误导性报错日志
- UUID 前置过滤：直接规避 Mock 降级 422（见 3.3）

### 4.3 后端改动（阶段二：编辑链路）

| # | 文件 | 改动 |
|:--|:---|:---|
| 1 | `schemas/live_core.py` `LiveRoomUpdate`（L43-50） | 增加 `category_ids: Optional[List[uuid.UUID]] = Field(None, max_length=5)` |
| 2 | `crud/room.py:560` `update` | 追加 `update_data.pop('category_ids', None)`（**关键**：现有 L564-565 会对所有 `exclude_unset` 字段 setattr 到 `LiveRoom`，不 pop 则 AttributeError → 500） |
| 3 | `services/room_service.py` `update_room_info`（L319-378） | 提取 `category_ids` → 房间字段更新后调用 `set_live_room_categories(..., mode='replace')` + commit（参照 `create_new_room` L144-175 模式）；无效分类静默跳过保持一致 |

**为什么这样改**：
- 前端编辑页走 `updateRoom` → **PATCH** `/rooms/{room_id}`（`store/room.ts:198`，已核实），端点已存在（`room.py:378`）且用 `LiveRoomUpdate`、owner 校验已就位（`room_service.py:360`）→ 后端仅需 3 处增量
- **不放开** `POST /admin/rooms/{id}/categories` 权限：owner 编辑走 PATCH 是既有安全模型，admin 端点保持管理专用
- 分类校验/写入复用现有 `set_live_room_categories`，不新增逻辑路径

### 4.4 前端消费端增强（阶段二）

| # | 文件 | 改动 |
|:--|:---|:---|
| 1 | `src/pages/app/live-manage/detail.vue:67-72` | 硬编码"肝胆外科" → `getRoomCategories(room_id)` 动态渲染（公开接口，无权限问题）；空则隐藏该行 |
| 2 | `src/pages/app/live-manage/edit.vue` | 新增分类选择 UI：进入时 `getRoomCategories()` 回填 → 保存时经 `updateRoom`（PATCH）提交 `category_ids` |

**为什么这样改**：
- 详情页动态展示 = 用户自检手段（"我选的分类存住了吗"），同时修复硬编码假数据
- 编辑页分类 = 历史数据补救入口（修复前创建的"以为关联了分类"的房间无法区分是否选过分类，**无法自动回填**，只能靠编辑功能手动补）

### 4.5 API 兼容性

| 接口 | 变化 | 影响 |
|:---|:---|:---|
| `POST /rooms` | 无变化（`category_ids` 早已支持） | 前端开始传该字段，旧客户端不受影响 |
| `PATCH /rooms/{id}` | `LiveRoomUpdate` 新增可选字段 | 向后兼容（可选字段，不传则行为不变） |
| `GET /homepage/rooms?category_id=` | 无变化 | 过滤已实现 |
| `GET /rooms/{id}/categories` | 无变化 | 前端开始消费 |
| `POST /admin/rooms/{id}/categories` | 无变化 | 权限保持，前端不再调用（删除兜底） |
