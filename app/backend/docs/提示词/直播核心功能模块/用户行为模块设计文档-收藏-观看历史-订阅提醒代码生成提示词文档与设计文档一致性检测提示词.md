**严格要求**：

- 不允许任何形式的“自由发挥”或“善意推测”；

- 对每一个检测点，都需要给出明确的 `[一致] / [不一致] / [缺失]` 结论。

## 3. 检测维度 (Detection Dimensions)

### 3.1 功能覆盖度 (Function Coverage)

1. **检测点 1.1 (功能完整性)**  
   - 检查 `Doc-Design` 中描述的所有功能点是否都在 `Doc-CRUD` 或 `Doc-API` 中出现并有明确规划，包括但不限于：  
     - 用户收藏：收藏 / 取消收藏 / 查询当前用户收藏列表；  
     - 观看历史：记录观看事件 / 查询观看历史（仅最新记录）；  
     - 订阅提醒：创建订阅 / 取消订阅 / 查询订阅列表。  

2. **检测点 1.2 (功能冗余)**  
   - 检查 `Doc-CRUD` / `Doc-API` 中是否存在 `Doc-Design` **未提及**的“额外”功能或 API 端点；  
   - 如果存在，需要判断这些功能是否：  
     - 明显属于本模块的合理扩展（如更细粒度的查询参数）；  
     - 或可能引入与设计文档不一致的行为。  

### 3.2 业务逻辑与执行流程 (Business Logic & Flow)

1. **检测点 2.1 (步骤一致性)**  
   - 检查 `Doc-API` / `Doc-CRUD` 中描述的业务执行流程是否与 `Doc-Design` 中描述的流程一致，例如：  
     - 收藏流程：从当前登录用户获取 `user_id` → 校验房间存在（如有）→ 创建或恢复收藏记录；  
     - 观看历史：为同一 `(user_id, session_id)` 只保留一条最新记录；  
     - 订阅流程：根据 `target_type` 判断 `room_id` / `session_id` 的必填性。  

2. **检测点 2.2 (数据流转)**  
   - 检查设计文档中关于数据流转的要求（如“user_id 来自 JWT，不从请求体传入”）是否在 `Doc-CRUD` / `Doc-API` 中得到准确体现；  
   - 检查是否明确了模型字段与 Schema 字段之间的映射关系。  

3. **检测点 2.3 (事务边界)**  
   - 检查设计文档中对事务边界的描述（显式或隐式），是否在提示词中被正确体现，例如：  
     - CRUD 层不进行 `commit/rollback`；  
     - Service 层负责写操作的事务控制和异常回滚。  

### 3.3 数据库规范 (Database Specifications)

1. **检测点 3.1 (字段名称)**  
   - 检查 `Doc-CRUD` 中引用的表名、字段名是否与 `Doc-Design` 的 DDL 部分完全一致：  
     - `user_favorites(user_id, room_id, is_active, created_at, ...)`  
     - `watch_history(user_id, session_id, progress, watched_at, is_latest, ...)`  
     - `user_subscriptions(user_id, target_type, room_id, session_id, is_active, created_at, ...)`  

2. **检测点 3.2 (字段类型)**  
   - 检查 `Doc-CRUD` 中提到的字段类型（UUID、Boolean、Integer、TIMESTAMPTZ、Enum 等）是否与设计文档中的类型定义一致。  

3. **检测点 3.3 (字段约束)**  
   - 检查提示词中是否正确反映了设计文档中的唯一约束、外键约束和软删除字段：  
     - 收藏：`UNIQUE (user_id, room_id)`；  
     - 订阅：`UNIQUE (user_id, target_type, room_id, session_id)`；  
     - 外键：`room_id` / `session_id` 的 `ON DELETE CASCADE` 行为（如设计文档有定义）；  
     - 软删除标记 `is_active`、最新记录标记 `is_latest` 的默认值与语义。  

### 3.4 API 结构规范 (API Structure)

1. **检测点 4.1 (路由 URL)**  
   - 检查 `Doc-API` 中的 API 路由是否与 `Doc-Design` 中约定的一致，重点关注：  
     - 是否统一采用 `/users/me/...` 作为当前用户行为的前缀；  
     - 是否避免引入设计文档之外的路径结构。  

2. **检测点 4.2 (HTTP 方法)**  
   - 检查提示词中所有端点的 HTTP 方法是否符合设计文档及 REST 约定：  
     - `POST` 用于创建行为（收藏、记录观看事件、创建订阅）；  
     - `GET` 用于查询行为（列表 / 历史 / 订阅）；  
     - `DELETE` 用于取消或删除订阅 / 收藏。  

3. **检测点 4.3 (请求体 Schema)**  
   - 检查请求体中是否严格按照设计文档约定的字段使用 Schema：  
     - 收藏：只接受 `room_id`，不接受 `user_id`；  
     - 观看历史：接受 `session_id` + 可选 `progress`；  
     - 订阅：`target_type` + 对应的 `room_id` 或 `session_id`。  

4. **检测点 4.4 (查询参数)**  
   - 如设计文档中提及分页或 limit 参数，检查 `Doc-API` 是否正确体现这些参数名、类型与默认值。  

### 3.5 响应与异常处理 (Response & Exception Handling)

1. **检测点 5.1 (成功响应)**  
   - 检查 `Doc-API` 中是否明确要求使用统一的 `success_response` 结构，并与项目整体规范一致。  

2. **检测点 5.2 (业务异常)**  
   - 如果设计文档中对“重复收藏”、“重复订阅”等业务异常有文字描述，检查提示词是否为这些场景规划了相应的异常类型（如 `InvalidParameterException` 或统一业务异常）。  

3. **检测点 5.3 (错误码 & 状态码)**  
   - 如设计文档中对本模块定义了具体业务错误码或 HTTP 状态码要求，检查提示词是否遵守这些约定；  
   - 若设计文档对错误码未做细粒度约束，应在报告中标记为“无冲突但可后续细化”。  

### 3.6 跨层规范 (Cross-Cutting Concerns)

1. **检测点 6.1 (安全规范)**  
   - 检查 `Doc-API` 是否严格遵守“用户行为接口必须要求登录（Strict Auth）”的设计要求，使用 `get_current_user` 等依赖；  
   - 确认未出现不需要鉴权的用户行为接口。  

2. **检测点 6.2 (日志规范)**  
   - 检查 `Doc-CRUD` 是否延续了项目中“INFO 日志 + UUID 脱敏（记录前 8 位）”的要求。  

3. **检测点 6.3 (隐式规范)**  
   - 检查 `Doc-CRUD` / `Doc-API` 在命名上是否遵守设计文档中的隐式规范，例如统一使用 `user_id`、`room_id`、`session_id` 等名称，不混用其他写法。  

### 3.7 API-Service 对应关系检测 (API-Service Mapping Verification)

1. **检测点 7.1 (API 端点 → Service 方法)**  
   - 检查 `Doc-API` 中列出的每一个 API 端点，是否都能在 Service 提示词中找到对应的方法签名和说明（排除权限守卫等内部方法）。  

2. **检测点 7.2 (Service 方法 → API 端点)**  
   - 检查 Service 提示词中定义的业务方法（收藏/取消收藏/记录观看事件/创建订阅/取消订阅/查询列表等），是否都能在 API 提示词中找到对应的端点；  
   - 如果存在 Service 方法没有匹配的 API 端点，应在报告中标记为“可能多余或缺少 API 映射”。
