### 4.3.1 Async Generator Fixture 处理规范（⚠️ 关键）

**⚠️ 重要**：`public_room`、`private_room`、`private_room_owned_by_user` 等 fixture 是异步生成器（async generator），在特定情况下（如嵌套循环）pytest 可能无法自动解析，导致直接访问 `.id` 属性失败。

**✅ 推荐方案：在循环外部直接迭代 fixture generator**

当测试使用嵌套循环（`async for client in async_client:` + `async for db in db_session:`）时，必须在外层循环内、内层循环之前解析所有依赖 `db_session` 的 fixture：

```python
@pytest.mark.asyncio
async def test_example(
    async_client,
    db_session,
    public_room,
    private_room
):
    async for client in async_client:
        # ← 关键：在外层循环内、内层循环之前解析fixture
        async for pr in public_room:
            public_room_id = pr.id
            break
        async for pvr in private_room:
            private_room_id = pvr.id
            break
        
        # ← 然后才进入内层循环
        async for db in db_session:
            # 使用 public_room_id 和 private_room_id
            response = await client.get(f"/api/v1/rooms/{public_room_id}")
            assert response.status_code == 200
```

**关键点**：
- **解析位置**：在外层循环内、内层循环之前解析 fixture
- **避免重复消费**：每个 fixture 只迭代一次，使用 `break` 退出循环
- **原因**：如果在内层循环中解析 fixture，当进入内层循环时 generator 可能已被 pytest 消费，无法再次获取值

**❌ 错误写法**：
```python
async for client in async_client:
    async for db in db_session:
        # ❌ 错误：在内层循环中解析fixture，可能导致generator已被消费
        room_id = await get_fixture_room_id(public_room)
        response = await client.get(f"/api/v1/rooms/{room_id}")
```

**✅ 替代方案（仅用于简单循环场景）**：

如果测试只有简单的 `async for client in async_client:` 循环（没有嵌套循环），可以使用辅助函数：

```python
import inspect

async def get_fixture_room_id(room_fixture):
    """
    辅助函数：从room fixture中安全地获取room_id
    处理async generator fixture的情况
    """
    # 如果fixture已经被pytest解析，直接返回id
    if hasattr(room_fixture, 'id') and not inspect.isasyncgen(room_fixture):
        return room_fixture.id
    
    # 如果是async generator，尝试获取值
    if inspect.isasyncgen(room_fixture):
        try:
            room_obj = await room_fixture.__anext__()
            return room_obj.id
        except StopAsyncIteration:
            # Generator已经被消费，说明pytest已经解析了它
            if hasattr(room_fixture, 'id'):
                return room_fixture.id
            raise ValueError("无法从fixture中获取room_id：generator已被消费且未解析")
    
    # 默认情况：直接返回id
    return room_fixture.id

# 使用
async for client in async_client:
    room_id = await get_fixture_room_id(public_room)
    response = await client.get(f"/api/v1/rooms/{room_id}")
```

**⚠️ 注意**：辅助函数方案不适用于嵌套循环场景，因为在这些场景中 fixture generator 可能已被消费。

### 4.8 异步 SQLAlchemy 会话的测试规范

**🚨 禁止操作**：
- **严禁使用** `db.expire_all()` 或 `db.expire(obj)`（会在异步环境中引发 `MissingGreenlet` 错误）

**🚨 避免 Identity Map 缓存污染**：
- 若测试创建了对象（会话 A），但 API 在另一会话（B）修改了该对象，会话 A 再查询该 ID → 会直接命中缓存，无法看到最新值

**⭐ 正确验证最新数据库值的两种模式**：

1. **最推荐方式**：完全依赖 API 返回 JSON，测试不访问数据库
   ```python
   # 只断言 API 返回的内容
   assert response.json()["data"]["title"] == "新标题"
   ```

2. **若必须访问数据库**：必须使用新的独立会话
   ```python
   from app.db.session import async_session_factory
   
   async with async_session_factory() as new_db:
       stmt = select(LiveRoom).where(LiveRoom.id == room_id)
       result = await new_db.execute(stmt)
       obj = result.scalar_one_or_none()
       assert obj.title == "新标题"
   ```

## 13.6 常见错误预防措施（基于16类错误总结）

**⚠️ 重要**：以下是根据实际测试中遇到的16类错误总结的预防措施，生成测试代码时必须严格遵守。

### 13.6.1 类型1：缺少 role 参数（最常见）

**预防措施**：
- ✅ 所有Service方法调用都必须传递 `role` 参数（字符串格式：`"REGULAR"`、`"ADMIN"`、`"SUPERADMIN"`）
- ✅ 在方法调用前定义 `role` 变量：`role = "REGULAR"` 或 `role = "ADMIN"`
- ✅ 不要使用未定义的 `regular_user_role` fixture，应直接定义字符串

**示例**：
```python
# ✅ 正确
role = "REGULAR"
await service.create_room(data, user_id=user_id, role=role)

# ❌ 错误
await service.create_room(data, user_id=user_id)  # 缺少role参数
```

### 13.6.2 类型2：变量名未定义

**预防措施**：
- ✅ 所有使用的 fixture 必须在测试函数签名中声明（如 `regular_user_id: uuid.UUID`、`regular_user_token: str`）
- ✅ 在测试函数内部使用的变量必须在使用前定义（如 `headers = {"Authorization": f"Bearer {token}"}`）
- ✅ 不要使用未定义的变量名（如 `regular_user_role`，应使用 `role = "REGULAR"`）

### 13.6.3 类型3：异常类型不匹配

**预防措施**：
- ✅ 使用正确的异常类型名称（例如：`PermissionDeniedException` 而不是已废弃的异常类型）
- ✅ 在 `pytest.raises` 中使用正确的异常类型
- ✅ 更新导入语句以使用正确的异常类型

**示例**：
```python
# ✅ 正确
from app.exceptions import PermissionDeniedException
with pytest.raises(PermissionDeniedException):
    ...

# ❌ 错误
from app.exceptions import TopicPermissionDeniedException  # 不存在的异常类型
```

### 13.6.4 类型4：Async Generator Fixture 访问属性问题（最常见的集成测试问题）

**预防措施**：
- ✅ 对于嵌套循环（`async for client in async_client:` + `async for db in db_session:`），在外层循环内、内层循环之前解析所有依赖 `db_session` 的 fixture
- ✅ 使用直接迭代模式：`async for pr in public_room: public_room_id = pr.id; break`
- ✅ 避免在循环内部重复消费 async generator

### 13.6.5 类型5：CRUD层参数名不匹配

**预防措施**：
- ✅ Service 层参数名为 `role`，但 CRUD 层参数名为 `current_user_role`
- ✅ 在断言 CRUD 层调用时，使用 `call_args[1]['current_user_role']` 而不是 `call_args[1]['role']`

### 13.6.6 类型6：Mock对象状态不符合权限要求

**预防措施**：
- ✅ 为匿名用户测试创建 `PUBLISHED` 状态的 topic 或 `is_private=False` 的房间
- ✅ 设置 `mock_room.is_private = False`（对于公开房间测试）
- ✅ 确保 mock 对象的状态符合测试场景的权限要求

**示例**：
```python
# ✅ 正确（匿名用户测试）
mock_room = MagicMock(id=room_id, is_private=False)  # 公开房间，匿名用户可访问

# ❌ 错误
mock_room = MagicMock(id=room_id, is_private=True)  # 私有房间，匿名用户无法访问
```

### 13.6.7 类型7：FastAPI HTTPException 响应格式不一致

**预防措施**：
- ✅ 兼容两种错误响应格式：FastAPI 默认格式（`{"detail": "..."}`）和自定义格式（`{"code": ...}`）
- ✅ 在访问 `code` 字段前检查字段是否存在

**示例**：
```python
response_json = response.json()
if "code" in response_json:
    assert response_json["code"] in [1001, 401]
else:
    assert "detail" in response_json  # FastAPI默认错误格式
```

### 13.6.8 类型8：权限检查返回状态码变更

**预防措施**：
- ✅ 了解不同异常的状态码和错误码：
  - `PermissionDeniedException` → 403, code 3002
  - `SessionActionForbiddenException`（更新） → 403, code 2004
  - `SessionActionForbiddenException`（删除） → 403, code 2005
  - `NotFoundException` → 404, code 2001
- ✅ 根据实际业务逻辑更新测试期望

### 13.6.9 类型9：响应字段缺失

**预防措施**：
- ✅ 在访问响应字段前检查字段是否存在
- ✅ 只检查本测试创建的数据，避免检查其他测试留下的数据

**示例**：
```python
for item in data["items"]:
    if item["id"] in [str(room1.id), str(room2.id)]:  # 只检查本测试创建的数据
        if "is_private" in item:  # 检查字段是否存在
            assert item["is_private"] == False
```

### 13.6.10 类型10：AssertionError - 断言期望的参数与实际不符

**预防措施**：
- ✅ Service 层方法调用 CRUD 层的 `get` 时只传递 `room_id`，不传递 `user_id`
- ✅ 权限检查在 Service 层完成，CRUD 层只负责数据查询
- ✅ 在断言 CRUD 层调用时，不要包含 `user_id` 参数

**示例**：
```python
# ✅ 正确
mock_get.assert_called_once_with(db=None, room_id=room_id)

# ❌ 错误
mock_get.assert_called_once_with(db=None, room_id=room_id, user_id=user_id)
```

### 13.6.11 类型11：SQLAlchemy表达式布尔值判断错误

**预防措施**：
- ✅ SQLAlchemy 的 SQL 表达式对象不能直接用于布尔判断
- ✅ 使用 `is not None` 或 `is None` 来判断表达式是否存在

**示例**：
```python
# ✅ 正确
if search_conditions is not None:
    query = query.where(search_conditions)

# ❌ 错误
if search_conditions:  # SQLAlchemy 表达式不能用于布尔判断
    query = query.where(search_conditions)
```

**注意**：此错误主要在CRUD层代码中出现，测试代码中较少遇到，但应了解此规范。

### 13.6.12 类型12：批量导入需要管理员权限

**预防措施**：
- ✅ 批量导入 API 需要 `ADMIN` 或 `SUPERADMIN` 角色
- ✅ 使用 `async_client_with_admin_role` fixture 而不是普通 `async_client`
- ✅ 在测试函数中添加 `async_client_with_admin_role` 参数
- ✅ 将管理员客户端获取放在循环外部，避免重复创建

### 13.6.13 类型13：错误消息语言不匹配

**预防措施**：
- ✅ 兼容中英文两种错误消息
- ✅ 使用 `or` 连接多个断言条件

**示例**：
```python
assert "资源不存在" in response_json["message"] or "not found" in response_json["message"].lower()
```

### 13.6.14 类型14：测试数据一致性问题

**预防措施**：
- ✅ 创建测试数据时使用正确的 `user_id`，确保与 Token 中的 `user_id` 一致
- ✅ 使用 `regular_user_id` fixture 而不是硬编码的 `user_id`
- ✅ 确保测试数据属于当前用户，避免权限检查提前失败

**示例**：
```python
# ✅ 正确
room = await create_test_room_in_db(db, user_id=regular_user_id)

# ❌ 错误
room = await create_test_room_in_db(db)  # 使用默认user_id，可能导致权限检查失败
```

### 13.6.15 类型15：Mock db未正确设置

**预防措施**：
- ✅ Service 方法需要访问 `self.db` 时，必须提供 mock db：`Service(db=MagicMock())`
- ✅ Mock CRUD 层的数据库操作，而不是依赖真实的数据库连接

**示例**：
```python

service = RoomService(db=MagicMock())
mock_get = mocker.patch("app.crud.room.get", new_callable=AsyncMock)

# ❌ 错误

```

### 13.6.16 类型16：后端代码导入错误

**预防措施**：
- ✅ 如果测试中发现后端代码使用了异常类但没有导入，需要修改后端代码（这不是测试代码的问题）
- ✅ 在后端代码的导入语句中添加缺失的异常类

**示例**：
```python

from app.exceptions import NotFoundException

```

**注意**：此错误主要出现在后端代码中，测试代码中较少遇到，但应了解此规范。
