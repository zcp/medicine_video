### 3.2. 业务逻辑与执行流程 (Business Logic & Flow)

#### 检测点 2.1 (步骤一致性)
**问题**: `Doc-API` 和 `Doc-CRUD` 中描述的函数执行流程是否与 `Doc-Design` 中描述的业务步骤**完全一致**？

**品牌模块关键业务流程**:
1. **创建品牌**: 权限检查 → 唯一性验证 → 创建记录 → 返回结果
2. **删除品牌**: 
   - 软删除: 权限检查（ADMIN） → 404检查 → 设置is_active=False → 返回结果
   - 硬删除: 权限检查（SUPERADMIN） → 404检查 → **引用关系检查**（brand_topics + brand_rooms） → 删除记录 → 返回结果
3. **批量关联专题**: 权限检查 → 品牌404检查 → **批量验证专题ID** → 批量插入（幂等性） → 返回结果
4. **绑定直播间品牌**: 权限检查 → 直播间404检查 → **批量验证品牌ID（is_active=True）** → **全量替换策略**（先删后插） → 返回结果

---

#### 检测点 2.2 (数据流转)
**问题**: `Doc-Design` 中描述的数据处理逻辑是否在对应的文档中得到准确体现？

**品牌模块数据处理逻辑**:
1. **批量验证**: Service层在调用CRUD层之前必须完成所有批量ID验证
2. **唯一性约束处理**: CRUD层捕获`IntegrityError`并转换为`DatabaseIntegrityException`
3. **软删除策略**: Brand表使用`is_active`字段，BrandTopic和BrandRoom硬删除
4. **N+1问题防治**: `get_brand_with_topics`使用`selectinload`预加载关联数据
5. **分页模式**: 使用两次查询（COUNT + SELECT）

---

#### 检测点 2.3 (事务边界)
**问题**: `Doc-Design` 中（明示或暗示）的事务处理范围是否在 `Doc-CRUD` 中被正确实现？

**品牌模块事务边界**:
1. **单表操作**: 使用单次`await db.commit()`（创建、更新、删除品牌）
2. **批量操作**: 使用`async with db.begin()`显式事务（`bind_room_brands`：先删后插）
