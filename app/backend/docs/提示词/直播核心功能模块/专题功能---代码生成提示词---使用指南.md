## 🎯 为什么采用两阶段方式？

### 与直播功能的三阶段对比

**直播功能使用三阶段**：
- 第一阶段：CRUD层
- 第二阶段：Service层
- 第三阶段：重构Endpoint层（从直接调用CRUD改为调用Service）

**专题功能使用两阶段**：
- 第一阶段：CRUD层
- 第二阶段：Service层 + Endpoint层（一次性生成最终架构）

### 为什么不需要重构？

1. **业务复杂度**：专题功能涉及3个表的级联操作、复杂权限验证、层级化数据查询
2. **必要性**：Service层从一开始就是必需的，不存在"先简单后复杂"的演进过程
3. **开发效率**：避免重复工作，直接生成最终架构

## ✅ 核心编码原则强化说明

### 🛡️ 安全异步异常处理（重中之重）

这是**最容易被忽略但最重要**的规则，必须严格执行：

#### 问题根源
在异步SQLAlchemy中，当数据库操作失败后（如 `IntegrityError`），ORM对象会与数据库会话分离（detached）。此时访问对象属性会导致 `DetachedInstanceError`。

#### 解决方案
**在进入 `try` 块之前**，提前提取所有需要在 `except` 块中使用的变量。

#### 错误示例 ❌
```python
async def update_topic(self, topic_id: UUID, user_id: UUID, obj_in: TopicUpdate):
    topic = await crud_topic.get(self.db, topic_id)
    
    try:
        updated_topic = await crud_topic.update(self.db, topic, obj_in)
        await self.db.commit()
        return updated_topic
    except IntegrityError as e:
        await self.db.rollback()
        # ❌ 危险！topic对象可能已失效
        logger.error(f"更新失败: topic_id={topic.id}, title={topic.title}")
        raise
```

#### 正确示例 ✅
```python
async def update_topic(self, topic_id: UUID, user_id: UUID, obj_in: TopicUpdate):
    # ✅ 提前提取变量
    topic_id_for_logging = topic_id
    user_id_for_logging = user_id
    
    topic = await crud_topic.get(self.db, topic_id)
    if topic:
        # ✅ 再次提取对象属性
        topic_title_for_logging = topic.title
    
    try:
        updated_topic = await crud_topic.update(self.db, topic, obj_in)
        await self.db.commit()
        return updated_topic
    except IntegrityError as e:
        await self.db.rollback()
        # ✅ 使用局部变量
        logger.error(
            f"更新失败: topic_id={topic_id_for_logging}, "
            f"title={topic_title_for_logging}, error={str(e)}"
        )
        raise
```

### 其他核心原则

1. **RESTful路径规范**：
   - 路由器 `prefix` 不以斜杠结尾
   - 集合端点使用 `path="/"`
   - 单个资源使用 `path="/{resource_id}"`

2. **响应处理规范**：
   - 成功：`return success_response(data=...)`
   - 失败：`return JSONResponse(status_code=..., content=error_response(...))`

3. **环境变量驱动**：
   - 所有外部服务连接使用 `os.getenv()`

4. **权限验证位置**：
   - **必须在Service层**进行权限验证
   - Endpoint层只负责异常转换

## 🔧 常见问题与解决

### Q1: 如何处理跨表的复杂查询？

**A**: 在CRUD层使用JOIN查询，在Service层组装结果。

示例（专题详情的层级化数据）：
```python
# CRUD层：只负责查询
async def get_with_categories(db: AsyncSession, topic_id: UUID):
    return await db.execute(
        select(Topic).options(selectinload(Topic.categories))
        .where(Topic.id == topic_id)
    )

# Service层：组装层级化数据
```

### Q2: 批量操作如何处理事务？

**A**: 在Service层统一管理事务，CRUD层提供批量操作函数。

示例（批量添加直播间）：
```python
# CRUD层：批量添加
async def batch_add_rooms(db: AsyncSession, category_id: UUID, rooms: List):
    db.add_all([TopicCategoryRoom(...) for room in rooms])
    await db.commit()

# Service层：验证+事务管理
async def add_rooms_to_category(self, category_id: UUID, user_id: UUID, rooms: List):
    # 1. 权限验证
    category = await self._verify_category_permission(category_id, user_id)
    
    # 2. 验证直播间存在性
    await self._verify_rooms_exist([r.room_id for r in rooms])
    
    # 3. 检查重复关联
    for room in rooms:
        if await crud_topic.check_room_association_exists(...):
            raise RoomAlreadyAssociatedException(...)
    
    # 4. 批量添加（事务在CRUD层处理）
    return await crud_topic.batch_add_rooms(self.db, category_id, rooms)
```

### Q3: 如何避免N+1查询问题？

**A**: 使用 `selectinload` 或 `joinedload` 预加载关系。

```python
# ❌ 错误：会产生N+1查询
topics = await get_all_topics(db)
for topic in topics:
    print(topic.categories)  # 每次都会查询数据库

# ✅ 正确：使用预加载
select(Topic).options(selectinload(Topic.categories))
```

### Q4: 如何处理级联删除？

**A**: 数据库已配置 `ON DELETE CASCADE`，CRUD层直接删除父对象即可。

```python
# 删除专题时，分类和关联会自动删除
async def remove(db: AsyncSession, db_obj: Topic):
    await db.delete(db_obj)  # 级联自动处理
    await db.commit()
```
