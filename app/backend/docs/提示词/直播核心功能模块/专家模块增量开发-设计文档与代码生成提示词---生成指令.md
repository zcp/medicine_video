## 四、增量需求摘要（必须在设计文档与代码生成提示词中完整覆盖）
以下三项需求必须在《专家模块增量开发设计文档》中完整描述，并在两份代码生成提示词中转化为可执行的「修改/新增清单」。
3.1 专家启用状态 is_active（与品牌等模块的软删除对齐）
目标：专家软删除统一改为「设置 is_active = false」，不再使用 is_featured 表示删除；is_featured 仅表示「是否首页推荐」。
数据库：在 experts 表新增字段 is_active BOOLEAN NOT NULL DEFAULT true，并补充注释与索引；提供迁移说明（或 Alembic revision 要点）。
Model/Schema：Expert 模型新增 is_active；ExpertCreate、ExpertUpdate、ExpertItem 等与专家对象相关的 Schema 增加 is_active（创建默认 True，更新可选，响应必含）。
CRUD：
create_expert：写入 Schema 中的 is_active（默认 True）。
get_expert：不在此层按 is_active 过滤。
get_expert_by_user_id：不按 is_active 过滤（已下架专家仍占用 user_id）。
get_featured_experts：查询条件增加 Expert.is_active == True（与 is_featured 条件同时生效）。
get_experts_multi_and_total：增加可选参数 is_active，并在 Admin 列表筛选中使用。
update_expert：允许更新 is_active。
delete_expert：改为仅设置 expert.is_active = False，不再修改 is_featured。
Service：
_check_expert_visibility：改为依据 expert.is_active 判断可见性（非 Admin 且 is_active 为 False 则 404），删除所有「is_featured 表示已删除」的逻辑与注释。
get_experts_list：增加 is_active 参数并传给 CRUD。
get_followed_experts：若约定「我的关注」只展示启用专家，则在构造列表时过滤掉 sub.expert.is_active == False（或由 CRUD get_user_subscriptions 增加过滤）；若展示已下架专家，则 FollowedExpertItem 需含 is_active。
check_is_followed：在调用 get_subscription 之前先 get_expert + _check_expert_visibility，专家不存在或已下架时返回 404；响应 key 保持 is_followed。
set_session_experts：校验每个 expert 时增加「仅允许 is_active=True 的专家关联场次」，否则抛出 InvalidParameterException。
API：
所有返回专家对象的响应（含 format_expert_response）增加 is_active 字段。
Admin GET /experts 增加 Query 参数 is_active（可选），并传给 Service。
文档与测试：设计文档 1.3 软删除策略改为「设置 is_active=false」；2.1 experts 表 DDL、3.x Schema、4.x API 示例同步增加 is_active；测试建议中覆盖 is_active 的创建/更新/删除/列表筛选及可见性。
3.2 专家信息批量导入（CSV）
目标：支持通过上传 CSV 批量创建专家，行为与错误处理方式参考《媒体下载服务 batch_import_csv》文档（错误隔离、可选去重、结果统计）。
接口：POST /api/v1/admin/experts/batch-import（或与现有 Admin 专家路由一致），需 Admin 权限，multipart/form-data，参数含 file、可选 skip_duplicates。
CSV 格式：必需列至少包含 name；可选列与现有 ExpertCreate 对齐（如 title、hospital、department、expertise_areas、bio、avatar_url、is_featured、sort_order、is_active），缺省 is_active 视为 true。
去重：若 skip_duplicates=true，去重键建议 (name, hospital) 或 (name, hospital, department)；实现可调用现有 get_experts_multi_and_total(..., name=, hospital=, limit=1) 判断是否存在。
返回结构：与参考文档对齐（total、success、failed、skipped、created_expert_ids、failed_rows、skipped_rows、processing_time）；HTTP 状态码与业务码约定（如 201 全成功、207 部分成功、400 格式错误等）。
实现层次：Schema 新增批量导入请求/响应类；Service 新增 batch_import_experts_from_csv；API 新增 batch-import 端点；CRUD 无需新增函数（复用 create_expert 及现有列表查询做去重）。
设计文档：单独小节描述 CSV 列定义、去重规则、错误隔离、响应格式、执行流程；修改点清单中列出新增的 Schema、Service 方法、API 端点及涉及文件。文件校验（扩展名 .csv、最大文件大小与最大行数限制、UTF-8 编码）及对应错误码（如 400/413）与《媒体下载服务 batch_import_csv》参考文档保持一致，并在增量设计文档与 API 端点描述中显式写出。
3.3 判断当前用户是否已关注某专家（增强现有接口）

**目标**：现有已有「是否已关注」独立接口（如 check_is_followed）；需增强为：先校验专家存在且 is_active=true，再查询关注关系；专家不存在或已下架时返回 404，与专家详情行为一致。

**接口约定**：不新增路径，沿用现有「是否已关注」路由；响应 key 保持 **is_followed**（不改为 is_following）。「当前用户是否已关注该专家」**仅通过该独立接口**查询；若业务需要在专家详情、专家列表等接口的响应中顺带返回「当前用户是否已关注」（如 is_followed 字段），须在设计文档中单独约定：列出需增加该字段的接口、仅当已登录时返回、与独立接口逻辑一致（先专家可见性再查 user_expert_subscriptions），并在 API 变更与两份代码生成提示词中显式列出；本指令默认不要求详情/列表接口带 is_followed，除非设计文档中明确写出。

**设计文档**：在执行流程与错误处理中明确「先 get_expert + _check_expert_visibility，再 get_subscription」；修改点清单中仅列 Service 的 check_is_followed 逻辑变更，不新增 API 路径。
