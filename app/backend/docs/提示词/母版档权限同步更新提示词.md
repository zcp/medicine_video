## 2. 母版权限管理核心内容（必须完整同步）

### 2.1. 三层权限职责分工（完整版）

**核心内容**：
1. **API 层 (Endpoint)**：负责 Authentication（认证）
   - 使用 `get_current_user` 或 `get_current_user_optional`
   - 提取 `user_id` (UUID) 和 `role` (str)
   - 传递给 Service 层
   - **不做权限判断**

2. **Service 层**：全权负责 Authorization（鉴权）
   - 接收 `user_id: UUID` 和 `user_role: str`
   - 调用权限守卫函数
   - 决定是否允许访问
   - 传递权限参数给 CRUD 层

3. **CRUD 层**：负责 SQL 层面权限过滤
   - 接收 `current_user_id: Optional[UUID]` 和 `role: Optional[str]`
   - 在 WHERE 条件中应用权限过滤
   - Admin查询：无过滤
   - Regular User查询：`WHERE (status='published' OR (status IN ('draft', 'archived') AND user_id=current_user_id))`
   - Anonymous查询：`WHERE status='published'`
   - 业务筛选与权限过滤：AND 关系

### 2.2. 双轨鉴权模式

| 模式 | 行为 | 适用场景 | API 层依赖 |
|-------|------|---------|-------------|
| Strict Auth | 无 Token → 401<br>Token 无效 → 401 | 所有写操作 | `get_current_user` |
| Optional Auth | 无 Token → None<br>Token 无效 → 401 | 所有读操作 | `get_current_user_optional` |

### 2.3. 权限守卫函数

**类型 1：资源可见性检查**
- 通用函数：`_check_resource_visibility(resource, user_id, role, is_published_field, published_value)`
- 模块适配：各模块可基于此实现专用函数（如 `_check_topic_visibility`）

**类型 2：写权限检查**
- 通用函数：`_check_write_permission(resource, user_id, role)`

### 2.4. 404 伪装机制

- 对于无权访问的私有资源，必须抛出 `NotFoundException`（404）
- **严禁**返回 `PermissionDeniedException`（403）
- 原因：防止资源探测攻击

### 2.5. Repository 层权限过滤

**原则**：
- 禁止内存过滤（性能陷阱）
- 在 SQL 查询中应用权限过滤
- 业务筛选与权限过滤使用 AND 关系
- 总数查询和数据查询使用相同的 WHERE 条件
