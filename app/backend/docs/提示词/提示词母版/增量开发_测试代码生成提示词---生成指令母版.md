# 增量开发 - 测试代码生成提示词 生成指令母版

**版本**: V1.1  
**用途**: 通用母版，指导 AI 为任意模块的增量开发生成《[模块名]增量开发_测试代码生成提示词.md》，并可**一次运行**自动继续生成全部增量测试代码。  
**产出**: 模块特定的增量测试代码生成提示词文档 +（合并模式下）对应所有增量测试 `.py` 代码。

**运行模式**：
- **合并模式（推荐）**：一次使用本母版，AI 先生成提示词文档并保存，再**在同一对话内**自动根据该文档生成并追加所有增量测试代码，无需新建对话。
- **仅生成提示词**：只生成提示词文档，测试代码需另开对话按生成的文档 Section 7 生成。

**配套母版**：《测试代码生成提示词母版》——产出的测试代码生成提示词须与其结构、测试哲学、测试策略、测试规范保持一致。

**原则**: 最小幅度修改、不修改已有测试、conftest 优先不修改、增量数据库验证、动态读取禁止猜测。

**通用性说明**：本母版适用于任意模块的增量开发；配置区使用占位符（如 [模块名称]、[服务名]），执行时根据配置动态读取具体文件以构建上下文，避免臆造与冲突。具体示例参见附录。

# 📘 一、目的

本元提示词用于**增量测试生成流程**，支持两种用法：

1. **合并模式（推荐）**：**一次**使用本母版，AI 先完成「规划师」任务：根据配置区动态读取主设计文档、增量设计文档、CRUD/Service/API 增量提示词及既有测试提示词，生成并保存《[模块名]增量开发_测试代码生成提示词.md》；然后**在同一对话内**自动切换为「执行者」，根据刚生成的文档 Section 6 与 Section 7 读取依赖文件并生成全部增量测试 `.py` 代码，追加到已有测试文件中。**无需新建对话**。
2. **仅生成提示词**：只完成规划师任务，产出提示词文档；测试代码需用户另开对话并引用该文档再生成。
3. **核心价值**：确保生成的测试提示词与测试代码均满足测试母版的所有测试哲学、测试策略、测试规范，且**不猜测任何字段/函数**，通过**动态读取**构建充足上下文；各环节配有检测清单，保证执行一致、结果可验证。

# 📘 二、使用方法

### 2.0 使用方式（简化 / 完整）

- **方式1：简化方式（推荐）**  
  用户只提供：**设计文档**（@主设计文档、@增量设计文档）、**提示词母版**（@测试代码生成提示词母版）、**既有测试提示词**（@）、**模块名**（snake_case）、**输出目录**、**测试模式**；可选提供增量需求与测试范围。**目标代码文件**不提供，由 AI 根据「代码文件自动查找规则」自动搜索匹配；CRUD/Service API 增量提示词路径可由模块名按命名约定推断。
- **方式2：完整方式**  
  用户填写配置区全部项，或显式提供**目标代码文件**列表（及主/增量设计文档、CRUD/Service API 增量提示词、既有测试提示词等）；AI 不自动查找，以用户提供为准。

### 2.1 合并模式（推荐，一次完成提示词文档 + 所有测试代码）

1. **简化方式**：按 2.5「推荐使用格式」填写并 @ 引用设计文档、母版、既有测试提示词；提供**模块名**、**输出目录**、**测试模式**（如 `incremental`）；不提供目标代码文件。**完整方式**：填写配置区所有路径与占位符。
2. 填写用户输入区的增量需求、测试范围（可选）；**运行模式**选择**合并模式**（或留空，默认即合并模式）。
3. 新建 Cursor 对话。
4. 使用 `@` 引用：`docs/提示词/自动化测试/测试代码生成提示词母版.md`、主设计文档、增量设计文档、既有测试提示词；（完整方式下还需引用 CRUD/Service API 增量提示词）。若为简化方式，可不引用具体代码文件，AI 将按「代码文件自动查找规则」自动查找。
5. 将本母版完整粘贴到输入框（含已填写的配置区与用户输入区），或按 2.5 使用推荐格式，并发送。
6. AI 将**先**按「七、执行顺序」生成并保存《[模块名]增量开发_测试代码生成提示词.md》，**再在同一对话内**自动根据该文档 Section 6 读取依赖文件、按 Section 7 逐项生成增量测试代码，**追加**到现有测试文件中。不修改已有测试函数与 conftest 已有内容。
7. 各环节须通过对应检测清单（见「七、执行顺序」及「各环节检测清单」）。

### 2.2 仅生成提示词（不生成测试代码）

1. 同 2.1 步骤 1–5；在用户输入区**运行模式**选择**仅生成提示词**。
2. AI 只完成规划师任务：生成并保存《[模块名]增量开发_测试代码生成提示词.md》，不生成 `.py` 测试代码。

### 2.3 分步使用（第二阶段单独进行时）

若此前已用「仅生成提示词」产出提示词文档，可单独进行第二阶段：

1. 新建 Cursor 对话。
2. 使用 `@` 引用生成的《[模块名]增量开发_测试代码生成提示词.md》及其中 Section 6 列出的依赖文件。
3. 输入：「请严格按照《[模块名]增量开发_测试代码生成提示词.md》Section 7 的任务列表生成增量测试代码。先读取 Section 6 全部依赖文件再生成。只追加新测试函数，不修改已有测试与 conftest。」
4. AI 将生成 `.py` 测试文件，**追加**到现有测试文件中。

### 2.6 代码文件自动查找规则

**适用条件**：使用方式为**简化**且用户**未提供**目标代码文件列表时，AI 按以下规则自动查找并验证存在性。

- **按模块名（snake_case）查找**：

| 层级 | 路径规则 | 示例（module_name=homepage_search） |
|------|-----------|-------------------------------------|
| Model | `{项目基础路径}/app/models/{module_name}.py` | `backend/live_core_service/app/models/homepage_search.py` |
| Schema | `{项目基础路径}/app/schemas/{module_name}.py` | `backend/live_core_service/app/schemas/homepage_search.py` |

| API | `{项目基础路径}/app/api/v1/endpoints/{module_name}.py` | `backend/live_core_service/app/api/v1/endpoints/homepage_search.py` |

# 📘 五、测试规范与标准（必须继承到生成的文档中）

生成的《[模块名]增量开发_测试代码生成提示词.md》**必须**明确要求执行者遵循以下规范，并在 Section 2-5 中完整继承测试母版内容：

### 5.1 增量测试模式

- **测试模式**：明确标注为**增量测试生成模式**
- **最小幅度修改**：
  - ✅ 只追加新测试函数，不修改、不删除、不重命名已存在的测试函数
  - ✅ 不修改已有测试文件中的任何已有内容
  - ✅ 保持现有测试的命名约定、代码风格和组织结构
- **conftest.py 约束（严格执行）**：
  - **优先不修改**：尽量复用现有 Fixture，仅在确有需要且无冲突时新增
  - 若必须新增 Fixture：仅允许**添加**新 Fixture、函数、变量、导入
  - ❌ 严禁修改、删除、重命名已有 Fixture、函数、变量
  - ✅ 新增前必须做冲突检查（命名、功能重复）
  - 若存在命名冲突或功能重复：应在**测试文件内部**定义新 Fixture，**避免修改 conftest.py**
  - **冲突检查步骤**：
    1. 读取现有 `conftest.py` 完整内容
    2. 识别所有已定义的 Fixture、函数、变量、导入
    3. 检查新增内容是否与现有命名冲突
    4. 若冲突则在测试文件内部定义，而非 conftest.py
- **辅助函数优先原则**：
  - 当依赖数据需要使用 `db_session` 时，**优先使用辅助函数**而非 Fixture
  - 避免 Fixture 与测试函数同时依赖 `db_session` 导致的 async_generator 冲突
  - 辅助函数定义在测试文件顶部，命名为 `create_test_<resource>`

### 5.2 增量数据库验证

- **原则**：数据库可能已有数据，**必须**使用增量判断方式验证，不得基于「总数」断言
- **正确做法**：
  - 创建测试：记录测试前 count/ids 基线，执行操作后断言 count 增加 1 或新记录 ID 在结果中
  - 删除测试：记录测试前 count，执行后断言 count 减少 1
  - 列表查询：记录测试前 ID 集合，创建新数据后断言新 ID 出现在结果中

### 5.2.1 排序敏感测试的 sort_order 规范

- **问题场景**：当测试依赖分页查询（`limit`）且数据库可能有预存数据时，测试创建的数据可能因排序（如 `sort_order ASC`）被排到 `limit` 范围之外，导致断言失败
- **强制规范**：
  - 使用 `create_test_<resource>` 辅助函数创建测试数据时，若该数据需要出现在分页查询结果中，**必须显式设置 `sort_order=0`**
  - 示例：`await create_test_expert(db, is_featured=True, sort_order=0)`
- **适用场景**：
  - 测试 `get_featured_<resource>` 等带 `limit` 的查询
  - 测试 `get_<resource>_list` 等分页查询中需验证特定记录存在
  - 测试按 `is_featured=True` 等条件筛选后需验证创建的记录出现在结果中

### 5.3 随机 ID 与唯一性

- **唯一字段**：所有 unique 约束字段**必须**使用 Faker 或 `uuid.uuid4().hex[:8]` 等生成唯一值（从 Model 定义中动态读取唯一字段）
- **外键字段**：**禁止**使用 `uuid.uuid4()` 作为外键值，必须先创建父对象，再使用其 ID
- **JWT/认证**：`user_id` 必须从 Token 解析，不得用随机 UUID 替代（除非明确测试「用户隔离」）

### 5.4 事务与隔离

- **默认**：测试函数中**不要**调用 `await db.commit()`，依赖 `db_session` fixture 的自动 rollback
- **例外**：仅当测试唯一性约束冲突、级联删除/外键约束时，可调用 commit

### 5.5 其他强制规范

- **函数式测试**：禁止类式测试（`class TestXXX:`），所有测试函数直接定义在模块级别
- **async for 解包**：`db_session`、`async_client` 等 async generator fixture 必须使用 `async for x in fixture:` 解包
- **Service 层 Mock**：`db` 必须使用 `AsyncMock()`，CRUD 使用 `new_callable=AsyncMock`
- **外键自检**：生成后须检查 Arrange 中是否为每个外键显式创建了父对象
- **Arrange-Act-Assert 结构**：所有测试用例必须遵循该结构，并使用注释清晰分开

### 5.5.1 Service 层方法签名与 Mock 完整性（必须写入生成的文档）

生成的文档**必须**要求执行者遵守以下约定，避免签名不一致、可见性字段错误、await Mock 等错误：

- **方法签名从源码读取**：生成 Service 层测试前，**必须**从 Service 源码读取被测方法的**完整签名**（参数名、类型、顺序），**禁止**仅凭方法名或旧用例推断参数；测试调用须与源码签名一致（如三参的 _check_user_resource_permission 或 _check_write_permission 须传三参）。
- **调用链上的 CRUD 均须 Mock**：若 Service 方法内部会依次调用多个 CRUD（如 check_is_followed 先 get_expert 再 get_subscription），**必须 mock 该调用链上的所有 CRUD**，避免真实 CRUD 对 Mock 的 `db` 执行 `await` 导致 TypeError。
- **软删除/可见性字段以设计文档为准**：软删除、下架、可见性的**构造与断言**必须与**当前设计文档**一致（若设计写 is_active，则测试用 is_active；**禁止**沿用旧字段如 is_featured）。

### 5.5.2 返回值序列化规范（必须写入生成的文档）

生成的文档**必须**要求执行者遵守以下约定，避免 UUID/datetime 等对象序列化失败：

- **UUID 字段处理**：Service 层返回字典时，所有 UUID 类型字段必须转换为字符串（使用 `str(uuid_obj)`）
- **批量操作返回值**：`created_ids`、`updated_ids`、`deleted_ids` 等列表字段必须包含字符串而非 UUID 对象
- **测试验证**：测试中断言 ID 时，注意类型一致性（字符串 vs UUID），必要时使用 `str()` 或 `uuid.UUID()` 转换

### 5.6 Mock 数据类型规范（MANDATORY）

- **禁止使用 MagicMock**：严禁使用 `MagicMock(**dict)` 模拟 Model 对象
- **使用真实 Model 类**：必须导入真实 Model 类创建 Mock 对象
- **Mock 链配置**：
  - `db = AsyncMock()` 作为 db 对象
  - `db.execute.return_value` 应为同步 Mock（因为 await 后的返回值是同步对象）
  - 复杂调用链使用 `Mock(scalars=Mock(return_value=Mock(all=Mock(return_value=[...]))))`

### 5.7 Service 层响应结构检查

- **动态读取 Service 层代码**：确认返回的 `data` 字段类型（Pydantic 对象 vs 字典）
- **类型区分**：
  - Pydantic 对象使用属性访问（`result["data"].id`）
  - 字典结构使用字典访问（`result["data"]["brand_info"].id`）
- **类型转换注意**：`uuid.UUID` 与 `str` 的比较可能需要转换

### 5.8 测试工具 API 兼容性

- **使用标准库 ANY**：从 `unittest.mock` 导入 `ANY`，不使用 `pytest.any`（已弃用）
- **导入规范**：`from unittest.mock import AsyncMock, Mock, patch, ANY`

### 5.9 SQLAlchemy 加载策略规范

- **joinedload + 一对多**：必须使用 `.unique()` 去重
- **joinedload + 多对一**：不需要 `.unique()`
- **selectinload**：不需要 `.unique()`
- **动态判断**：必须读取 CRUD 代码确认实际使用的加载策略
