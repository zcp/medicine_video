# 增量开发设计文档生成提示词母版

**版本**: V1.1  
**用途**: 指导 AI 根据新需求与修改点，在已有模块主设计文档基础上，生成「增量开发设计文档」及「CRUD / Service+API 增量代码生成提示词」  
**产出**: 1 份增量设计文档 + 1 份 CRUD 增量代码生成提示词 + 1 份 Service 与 API 增量代码生成提示词；完整自动化时还可产出并写入 CRUD/Service/API 层最终代码。

**说明**：本母版产出设计文档与**代码生成提示词**；最终代码在步骤 4、5 中利用产出的提示词生成并写入项目。**推荐流程**：一致性检查须在**提示词文档生成之前**与**代码生成之前**完成；若一致性不满足，后续提示词与代码均可能存在问题。**以下步骤可串联为一次自动化流程**，顺序不可颠倒：先产出增量设计文档（步骤 1）→ 一致性检查（步骤 2，**使用《增量开发设计文档与主设计文档一致性检查提示词母版》**）→ 通过后再产出两份提示词（步骤 3）→ 代码生成（步骤 4、5）→ 集成与验证（步骤 6）。

**代码生成步骤**（须严格按顺序执行；可与本母版串联为自动化流程，直至产出最终代码）：
1. **生成增量设计文档**：本母版先仅执行并产出**增量设计文档**，落盘。不在此步产出两份提示词。
2. **增量设计文档与主设计文档一致性检查**：使用《增量开发设计文档与主设计文档一致性检查提示词母版》对步骤 1 产出的增量设计文档与主设计文档进行一致性检查（方向 A：增量服从主文档；方向 B：主文档吸纳增量）。**仅当通过或修订后通过后，方可进入步骤 3**；未通过时不得生成提示词与代码。
3. **生成两份增量代码生成提示词**：基于**已通过一致性检查的**增量设计文档，产出 CRUD 增量代码生成提示词、Service 与 API 增量代码生成提示词，落盘。
4. **CRUD 层代码生成**：在同一流程内读取步骤 3 产出的「CRUD 增量代码生成提示词」，与配置区既有 CRUD 提示词、主设计文档、已有 Model/CRUD 代码路径一并作为上下文，生成/修改 CRUD 层代码并**写入项目对应文件**（如 `backend/live_core_service/app/crud/xxx.py`）。
5. **Service 与 API 层代码生成**：在同一流程内读取步骤 3 产出的「Service 与 API 增量代码生成提示词」，与既有 Service/API 提示词、主设计文档、已有 Service/API 代码路径一并作为上下文，生成/修改 Service 与 API 层代码并**写入项目对应文件**（如 `backend/live_core_service/app/services/xxx_service.py`、`app/api/v1/endpoints/xxx.py`）。
6. **集成与验证**：按增量设计文档进行联调、测试；必要时可再次使用一致性检查母版做回归检查。

**配套母版**：《增量开发设计文档与主设计文档一致性检查提示词母版》——产出的增量设计文档可使用该母版进行一致性检查，确保与主文档双向一致。

**原则**: 最小幅度修改、与既有设计零冲突、所有修改点显式列出、代码规范与既有提示词一致。

**通用性说明**：本母版适用于任意模块的增量开发；配置区、用户输入区、产出结构均使用占位符（如 [模块名称]、[表名]），执行时根据配置动态读取具体文件内容以构建上下文，避免臆造与冲突。具体示例参见附录。

# 📖 使用方法

**简化输入**：用户只需提供以下三项即可启动本母版流程：

1. **主设计文档**：路径或文档名称（如 `docs/03_系统设计/直播核心功能设计文档_v6_xxx模块设计文档-xxx.md`）。
2. **增量设计文档或需求**：本次增量的设计文档路径，或对增量目标、修改点的文字描述。
3. **功能模块名**：如「用户行为模块」「专家模块」「品牌模块」，用于文档命名与表述。采用自动化流程时，功能模块名可由主设计文档路径或内容推断，用户仅需提供主设计文档与新增需求即可。

**参数化调用**（与后端开发自动化流程对接时，可传入以下参数，由 AI 或脚本据此填写配置区并执行）：
- **design_doc** / **主设计文档路径**：同上。
- **module_name**：技术模块名（如 `brand_topic_room`、`user_favorites`），用于推断 CRUD/Service/API 文件路径。
- **functional_module_name**：功能模块名/表述名（如「品牌」「用户行为」），用于文档命名与表述。
- **project_path**：项目子路径（如 `live_core_service`），对应 `backend/live_core_service` 下的 Model/CRUD/Service/API。
- **output_base_dir**：产出提示词存放目录（如 `docs/提示词/直播核心功能模块`），相对于项目根目录。
- **auto_fix**（可选）：是否在产出后自动修复或校验，由具体流程约定。

**AI 职责**：根据上述三项或参数化输入，自动发现并填写配置区中的 CRUD 代码生成提示词路径、Service/API 代码生成提示词路径、已有 Model/CRUD/Service/API 代码路径（通过项目内文件结构与命名约定推断或检索）；并严格按第三节要求动态读取这些路径下的文件内容以构建上下文，再执行后续产出。用户无需手工填满配置表。采用简化输入时，修改点清单可由 AI 根据主设计文档与增量需求自动推导，用户无需逐条列出。**完整自动化时须严格按「代码生成步骤」顺序执行**：先产出增量设计文档（步骤 1），完成步骤 2 一致性检查（使用《增量开发设计文档与主设计文档一致性检查提示词母版》）通过后再产出两份提示词（步骤 3），再生成并写入代码（步骤 4、5），无需用户再次发起请求即可得到可运行代码。

# 📘 一、角色与任务

你是一名熟悉直播业务后端架构的技术文档与提示词撰写专家。你的任务是：

1. **生成一份《[模块名称]增量开发设计文档》**，与主设计文档在结构、用语、规范上完全一致，且无任何冲突或矛盾；在文档中显式列出所有需要修改的地方（含：文档章节、表结构、Schema、API、执行流程、测试建议等），做到不遗漏、不过度修改。

2. **生成两份增量代码生成提示词文档**：
   - CRUD 增量代码生成提示词：与既有 CRUD 提示词在结构、职责划分、函数清单格式、质量标准上保持一致，仅包含本次增量涉及的修改与新增。
   - Service 与 API 增量代码生成提示词：与既有 Service/API 提示词在结构、权限/鉴权约定、方法清单格式、质量标准上保持一致，仅包含本次增量涉及的修改与新增。

3. **所有产出均需满足「最小幅度开发」**：只改、只增必须项，不改变既有接口路径与响应结构（除按设计新增字段或新接口），不引入与主设计文档或既有代码生成提示词的冲突与不一致。

**完整自动化时的执行顺序**：先完成任务 1（生成增量设计文档）并落盘；经「代码生成步骤」步骤 2 使用《增量开发设计文档与主设计文档一致性检查提示词母版》进行一致性检查且通过后，再完成任务 2（生成两份增量代码生成提示词）。一致性检查未通过时不得生成提示词与代码。

**与已有文档的一致性（硬性要求）**：生成的设计文档与两份代码生成提示词文档，必须与已有相关文档（主设计文档、既有 CRUD 提示词、既有 Service/API 提示词）在结构、用语、规范、命名上保持完全一致，不得存在任何冲突或不一致；若引用已有内容，须与原文一致，不得改写或臆造。
