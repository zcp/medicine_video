
### 2. 代码生成提示词文档之间一致性检测提示词 (严格审计)

**目标**：这个提示词用于**审计**。它将比较两个模块（例如 `Topic` 和 `Tab/Message`），并找出它们之间**所有**的风格差异。
 #### **高效 AI 架构一致性审计提示词**

 **1. 角色定义 (Role Definition)**

 你是一名严苛的、注重细节的首席架构师。你的唯一任务是确保微服务中的所有功能模块在架构风格上保持 100% 一致。

 **2. 核心输入 (Core Context)**

 * **模块 A (基准/学院派)**:
     * `[粘贴模块 A 的 CRUD 提示词，例如 "专题功能---代码生成提示词---第一阶段-CRUD层.md"]`
     * `[粘贴模块 A 的 Service/API 提示词，例如 "专题功能---代码生成提示词---第二阶段-Service与Endpoint层.md"]`
 * **模块 B (待审计)**:
     * `[粘贴模块 B 的 CRUD 提示词，例如 "直播核心功能---tab和留言CRUD层代码生成提示词.md"]`
     * `[粘贴模块 B 的 Service/API 提示词，例如 "直播核心功能---tab和留言Service层和API层代码生成提示词.md"]`

 **3. 任务目标 (Task Objective)**

 请逐一检测并对比“模块 A”和“模块 B”在所有架构规范上的**不一致之处**。

 **4. 关键审计清单 (!!! 逐一检测，不要遗漏 !!!)**

 **4.1. 架构分层与职责 (Architecture & Responsibility)**
 * **事务管理**: 事务 (`db.commit()`) 是在 `CRUD` 层处理（学院派）还是 `Service` 层处理（实用派）？它们是否一致？
 * **异常处理**: 异常 (`try/except`) 是在 `CRUD` 层处理（学院派）还是 `Service` 层处理（实用派）？它们是否一致？
 * **日志记录**: 数据库错误日志是在 `CRUD` 层还是 `Service` 层？它们是否一致？

 **4.2. Service 层规范 (Service Layer)**
 * **异常类型**: Service 层是抛出**自定义异常**（如 `TopicNotFoundException`）还是 `HTTPException`？它们是否一致？
 * **职责**: Service 层是“薄”（仅业务逻辑）还是“厚”（包含事务、日志、HTTP 异常）？它们是否一致？

 **4.3. API (Endpoint) 层规范 (API Layer)**
 * **异常处理**: API 层是“厚”（包含 `try/except` 来捕获自定义异常）还是“薄”（不处理异常）？它们是否一致？
 * **响应格式化**: 数据的格式化（如 `base_url` 拼接）是在 `API` 层还是 `Service` 层？它们是否一致？

 **4.4. 安全规范 (Security)**
 * **安全异步处理**: 两个模块是否都遵循了“**安全异步异常处理**”规范（在 `try` 块前提取变量）？

 **4.5. 数据库规范 (Database)**
 * **N+1 查询**: 两个模块是否都明确要求使用 `selectinload` / `joinedload`？
 * **CRUD 风格**: 两个模块的 CRUD 函数（`create`, `update`）是接收 `Schema` 对象还是 `Model` 对象？

 **5. 交付物 (Deliverable)**

 请生成一份详细的**不一致性报告**，明确指出“模块 B”在哪些方面与“模块 A (学院派)”的架构风格**不匹配**。
