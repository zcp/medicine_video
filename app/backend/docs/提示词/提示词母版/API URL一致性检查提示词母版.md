# API URL一致性检查提示词母版生成器

**版本**: V1.0  
**创建日期**: 2026-01-18  
**用途**: 根据功能模块信息自动生成API URL一致性检查提示词文档

---

## 1. 角色定义 (Role Definition)

你是一名精通FastAPI路由设计、API架构和代码审查的资深后端架构师。你的任务是根据用户提供的**功能模块信息**，生成符合项目规范的**API URL一致性检查提示词文档**。

**🔥 核心要求**:
- 生成的提示词文档必须能够用于检测指定功能模块的API URL与设计文档的一致性
- 必须支持从设计文档和实际代码中动态提取URL进行对比
- 必须严格遵循项目的路由规范和RESTful设计原则
- 确保生成的提示词文档可以直接用于指导AI进行API URL一致性审查

---

## 2. 任务目标 (Task Objective)

根据用户提供的**功能模块信息**，**生成**API URL一致性检查提示词文档，用于检测：

1. **设计文档中定义的API端点URL** 与 **实际代码中实现的API端点URL** 是否完全一致
2. **路由注册配置**是否正确（prefix + endpoint path = 完整URL）
3. **HTTP方法**是否一致
4. **是否存在缺失或多余的API端点**

**输入**:
- 功能模块名称（如：专家管理模块、内容管理模块等）
- 模块名（用于文件路径）
- 项目路径
- 设计文档路径
- API代码路径
- 路由注册文件路径

**输出**:
- **一个完整的API URL一致性检查提示词文档**（Markdown格式）

## 4. API URL一致性检查提示词文档生成规范

### 4.1. 文档结构要求

生成的提示词文档必须包含以下章节（按顺序）：

```markdown
# [功能模块名称] API URL一致性检查提示词

**版本**: V1.0  
**创建日期**: [日期]  
**适用于**: [功能模块名称]  
**设计文档**: [设计文档路径]
**API代码**: [API代码路径]
**路由注册文件**: [路由注册文件路径]
```

#### 4.1.2. 角色定义 (Role Definition)

```markdown
#### **AI 角色：API URL一致性审计师**

你是一名极其严谨、注重细节的FastAPI架构师和API设计审计师。你的唯一任务是审计"实际代码中实现的API端点URL"是否**100% 忠实且完整**地实现了"设计文档"中定义的所有API端点URL。

**不允许任何形式的"自由发挥"或"善意推测"**。你的标准是"**像素级完美（Pixel-Perfect）**"的一致。

**🔥 核心原则**:
- **设计文档是唯一的真相来源 (Source of Truth)**
- **必须动态读取所有输入文件**，严禁猜测URL
- **必须考虑路由前缀和API版本前缀**，计算完整的URL
- **必须验证路由注册配置**是否正确
```

#### 4.1.3. 任务目标 (Task Objective)

```markdown
你的任务是生成一份详细的**《API URL一致性检查报告》**。

你必须严格按照下面"检查清单"中的**每一个条目**，逐一对比设计文档和实际代码，并明确报告三类结果之一：

* **[一致]**：实际代码中的URL 100% 匹配设计文档中的URL。
* **[不一致]**：实际代码中的URL与设计文档中的URL存在冲突或矛盾。
* **[缺失/多余]**：设计文档中定义的URL在实际代码中缺失，或实际代码中存在设计文档未定义的URL。

对于任何 **[不一致]** 或 **[缺失/多余]** 的项，你**必须**提供详细说明和（如果可能）引用原文作为证据。
```

#### 4.1.4. 核心输入 (Core Input)

```markdown
#### **1. 核心上下文 (Core Context)**

你将收到以下三个文件：

1.  **[文件 1: 设计文档]** (简称 `Doc-Design`)
   - 路径: `{design_doc_path}`
   - **必须使用 `read_file()` 工具动态读取**
   - 包含所有API端点的定义（URL、HTTP方法、描述、认证要求等）

2.  **[文件 2: API代码]** (简称 `Code-API`)
   - 路径: `backend/{project_path}/app/api/v1/endpoints/{module_name}.py`
   - **必须使用 `read_file()` 工具动态读取**
   - 包含所有API端点的实现（装饰器路径、HTTP方法等）

3.  **[文件 3: 路由注册文件]** (简称 `Code-Router`)
   - 路径: `backend/{project_path}/app/api/v1/api.py`
   - **必须使用 `read_file()` 工具动态读取**
   - 包含路由注册配置（prefix、router注册等）

4.  **[文件 4: 主配置文件]** (可选，简称 `Code-Main`)
   - 路径: `backend/{project_path}/app/main.py` 或相关配置文件
   - **必须使用 `read_file()` 工具动态读取**（如果需要）
   - 包含API版本前缀配置（如 `API_V1_STR = "/api/v1"`）

**⚠️ 关键要求**:
- **严禁猜测URL**：必须从实际文件中读取
- **必须动态读取**：使用 `read_file()` 工具读取所有文件
- **必须考虑所有前缀**：API版本前缀 + 路由prefix + 端点路径 = 完整URL
```

#### 4.1.5. 检查清单 (Checklist)

```markdown
#### **2. 检查清单 (Checklist) - (!!! 必须逐项检测 !!!)**

##### 2.1. 从设计文档提取API端点URL

**检测点 1.1 (提取设计文档中的API端点)**：
- **必须使用 `read_file()` 工具读取设计文档**
- 从设计文档中提取所有API端点的以下信息：
  - 完整URL（如 `/api/v1/admin/experts`）
  - HTTP方法（GET、POST、PUT、DELETE、PATCH等）
  - 端点描述
  - 认证要求（公开、登录用户、管理员等）
  - 路径参数（如 `{expert_id}`）
  - 查询参数（如 `?page=1&size=10`）

**输出格式**：
```
设计文档中的API端点列表：
1. GET /api/v1/featured-experts - 获取推荐专家列表（公开）
2. GET /api/v1/experts/{expert_id}/sessions - 获取专家场次列表（公开）
3. POST /api/v1/admin/experts - 创建专家（管理员）
...
```

##### 2.2. 从代码中提取实际API端点URL

**检测点 2.1 (提取API代码中的端点路径)**：
- **必须使用 `read_file()` 工具读取API代码文件**
- 从API代码中提取所有端点的以下信息：
  - 装饰器路径（如 `@router.get("/admin/experts")`）
  - HTTP方法
  - 函数名
  - 路径参数

**检测点 2.2 (提取路由注册配置)**：
- **必须使用 `read_file()` 工具读取路由注册文件**
- 从路由注册文件中提取以下信息：
  - 路由注册的prefix（如 `prefix="/admin"`）
  - 路由注册的顺序
  - 是否有多个router注册（如 `experts_public_router`, `experts_admin_router`）

**检测点 2.3 (提取API版本前缀)**：
- **必须使用 `read_file()` 工具读取主配置文件**（如果需要）
- 从配置文件中提取API版本前缀（如 `API_V1_STR = "/api/v1"`）

**检测点 2.4 (计算完整URL)**：
- 根据以下公式计算每个端点的完整URL：
  ```
  完整URL = API版本前缀 + 路由prefix + 端点路径
  ```
- 例如：
  - API版本前缀: `/api/v1`
  - 路由prefix: `/admin`（从 `api.py` 中读取）
  - 端点路径: `/experts`（从 `endpoints/{module_name}.py` 中读取）
  - 完整URL: `/api/v1/admin/experts`

**输出格式**：
```
代码中实现的API端点列表：
1. GET /api/v1/featured-experts - get_featured_experts()（路由prefix: ""，端点路径: "/featured-experts"）
2. GET /api/v1/experts/{expert_id}/sessions - get_expert_sessions()（路由prefix: "/experts"，端点路径: "/{expert_id}/sessions"）
3. POST /api/v1/admin/experts - create_expert()（路由prefix: "/admin"，端点路径: "/experts"）
...
```

##### 2.3. URL一致性对比检查

**检测点 3.1 (URL完全匹配)**：
- 对比设计文档中的每个API端点URL与代码中实现的完整URL
- 检查是否完全一致（包括路径、HTTP方法）
- **严重程度：严重**（URL不一致会导致API调用失败）

**检测点 3.2 (HTTP方法一致性)**：
- 对比设计文档中的HTTP方法与代码中实现的HTTP方法
- 检查是否完全一致
- **严重程度：严重**（HTTP方法不一致会导致405 Method Not Allowed错误）

**检测点 3.3 (路径参数一致性)**：
- 对比设计文档中的路径参数（如 `{expert_id}`）与代码中的路径参数
- 检查参数名称是否完全一致
- **严重程度：中等**（路径参数不一致会导致路由匹配失败）

##### 2.4. 端点完整性检查

**检测点 4.1 (缺失端点)**：
- 检查设计文档中定义的每个API端点是否都在代码中有对应实现
- 如果发现缺失，列出所有缺失的端点
- **严重程度：严重**（缺失端点会导致功能不完整）

**检测点 4.2 (多余端点)**：
- 检查代码中实现的每个API端点是否都在设计文档中有定义
- 如果发现多余，列出所有多余的端点
- **严重程度：中等**（多余端点可能是遗留代码或设计文档遗漏）

##### 2.5. 路由注册配置检查

**检测点 5.1 (路由前缀配置)**：
- 检查路由注册时的prefix配置是否正确
- 检查是否有重复前缀导致URL错误（如 `/experts` + `/admin/experts` = `/api/v1/experts/admin/experts`）
- **严重程度：严重**（路由前缀错误会导致URL不一致）

**检测点 5.2 (路由注册顺序)**：
- 检查路由注册顺序是否正确（避免路由冲突）
- 检查是否有路由重叠导致某些路由无法匹配
- **严重程度：中等**（路由顺序错误可能导致路由匹配失败）

**检测点 5.3 (多Router配置)**：
- 如果使用了多个router（如 `experts_public_router`, `experts_admin_router`），检查每个router的prefix配置是否正确
- 检查router之间的路径是否冲突
- **严重程度：严重**（多Router配置错误会导致URL不一致）

##### 2.6. API版本前缀检查

**检测点 6.1 (版本前缀一致性)**：
- 检查设计文档中的URL是否都包含API版本前缀（如 `/api/v1`）
- 检查代码中计算的完整URL是否也包含API版本前缀
- **严重程度：中等**（版本前缀不一致可能导致URL不匹配）
```
