## 上下文

我将提供一个现有的 Python 爬虫脚本 `dynamicCrawler_vzan.py`。
当前脚本特点：

* 使用 `liveroomlist_vzan_api.csv` 作为“主状态库”（记录所有已爬直播间），通过读取这个 CSV 来避免重复爬取。
* 这种方式容易造成：

  * 状态更新不可靠（写 CSV 失败就会丢状态）；
  * 重复数据难以控制；
  * 不方便做“失败重试”和“基于时间的增量爬取”。

**现在要做的事情：**

1. 把“状态管理”从 CSV 改用 SQLite 数据库 `vzan_crawler.db`。
2. 实现一个**三重循环**的爬取策略，满足：

   * 所有**成功数据**最终都写入 SQLite；
   * 所有**失败数据**（包括 ID 失败、页面失败）都被记录，下次可以重试；
   * **不重复**写数据（包括 SQLite 和本轮增量 CSV）；
   * 合理利用时间顺序，只爬“从最新数据到截止日期”的增量，**但不漏爬任意一条应该爬的数据**。
3. **保留** `liveroomlist_inc_vzan_backup.csv` 的增量输出逻辑，这个文件用于后续导入 PostgreSQL。

## 核心要求（总览）

1. **状态库：** 移除对 `liveroomlist_vzan_api.csv` 作为“主状态库”的依赖，用一个 SQLite 数据库（例如 `vzan_crawler.db`）替代。
2. **数据库结构：**
   在 `vzan_crawler.db` 中维护两张表：

   * `liversoms`：保存**逐条直播间的最终状态**（成功 / 失败）。

     * 主键：`id TEXT PRIMARY KEY`
     * 其它列：基于 `extract_liveroomlist_data()` 中 `live_info` 的 key（比如 `title`, `addtime`, `starttime`, `zbId`, `liveType`, `viewCount`, `videosrc`, `liveroom_url`, `video_url`, `cover_url`, `original_playback_url`, `edited_playback_url`, `enc_tpid`, `error_reason` 等）。
   * `failed_pages`：记录**分页接口失败的页面 URL**。

     * `page_url TEXT PRIMARY KEY`
3. **时间锚点字段统一为 `starttime`：**

   * **latest_success_time 必须基于 `starttime` 字段计算**，而不是 `addtime`。
   * `starttime` 在 SQLite 中必须以**可比较的排序格式**（如 `YYYY-MM-DD HH:MM:SS` 文本或 DATETIME）存储。
   * 计算 `latest_success_time` 时，只从 `video_url IS NOT NULL AND video_url != ''` 的记录中取 `MAX(starttime)`。
   * 失败记录即使时间更晚，也不能影响 `latest_success_time`，以避免混乱。
4. **增量文件：**

   * 必须**保留** `liveroomlist_inc_vzan_backup.csv` 的生成逻辑，对应变量 `self.liveroom_list_savefile_inc` 不可改名。
   * 此文件只包含“**本次运行中新爬取或重爬成功的数据**”（去重后的 ID 集）。
5. **三重循环策略：**

   * 循环 1：**重试 Page 失败**（从 `failed_pages` 表读取）；
   * 循环 2：**按时间顺序的增量爬取（带页面级停止）**；
   * 循环 3：**重试 ID 级失败**（从 `liversoms` 中 `video_url 为空` 的记录获取 ID）；
   * 任何一处都不能“页内因时间条件提前 break 导致漏爬后面的记录”。
6. **字段 / 变量名不得篡改：**

   * 所有与 `live_info` 字典、CSV 输出、文件路径相关的字段名，必须与现有代码保持一致。

```
def normalize_url(url):
    """
    标准化 URL：去除空格、多余斜杠、排序查询参数、去除锚点等。
    保证所有 URL 格式一致，避免因不同格式的 URL 导致重复存储或重复下载。
    
    :param url: 待标准化的 URL
    :return: 标准化后的 URL，如果输入为空或无效则返回原值
    """
    from urllib.parse import urlparse, urlunparse, parse_qsl, urlencode

    # 处理空值或无效输入
    if not url or not isinstance(url, str):
        return url if url else ""

    # 去除 URL 中的空格
    url = url.strip()
    
    if not url:
        return ""

    try:
        # 解析 URL
        parsed_url = urlparse(url)

        # 去除末尾斜杠
        path = parsed_url.path.rstrip('/')

        # 对查询参数进行排序
        query = parsed_url.query
        if query:
            # 使用 parse_qsl 解析查询参数，返回 [(key, value), ...] 格式
            query_params = parse_qsl(query)
            # 按 key 排序，然后按 value 排序（如果 key 相同）
            sorted_params = sorted(query_params, key=lambda x: (x[0], x[1] or ''))
            sorted_query = urlencode(sorted_params)
        else:
            sorted_query = ""

        # 去除锚点（fragment）
        new_url = urlunparse((
            parsed_url.scheme,
            parsed_url.netloc,
            path,
            parsed_url.params,
            sorted_query,
            ''  # fragment 设为空字符串
        ))

        return new_url
    except Exception as e:
        # 如果解析失败，返回原 URL
        return url
```

### 阶段 2：执行（三重循环）

> 这一阶段是整个策略的核心，必须体现：
>
> * **先重试页面失败 → 再做增量爬取 → 最后重试 ID 失败**；
> * 页内只用 `continue` 跳过，不允许因为时间条件 `break` 导致后续记录被跳过；
> * 页面级停止条件：**“整页全部是旧数据且没有需要处理的 ID”** 才停止。

#### 循环 1：Page 失败重试

1. 启动前，从 `load_state_from_db()` 得到 `pages_to_retry`。
2. 新增循环：

   ```python
   self.logger.info(f"开始 [循环1：Page失败重试]，共 {len(pages_to_retry)} 个页面...")

   for page_url in pages_to_retry:
       try:
           # 重新请求这个 page_url（POST 参数要与 get_liveroom_list 中保持一致）
           page_data = self.request_page_by_url(page_url)  # 可以是你封装的函数
           # 提取 item_list
           item_list = page_data["dataObj"]["list"]
           # 使用统一的页面处理逻辑（见下文 process_page_items）
           self.process_page_items(
               item_list=item_list,
               successful_ids=successful_ids,
               failed_ids=failed_ids,
               latest_success_time=latest_success_time,
               inc_data_for_this_run=inc_data_for_this_run,
               inc_ids_processed=inc_ids_processed
           )
           # 注意：在 `process_page_items` 内部，对每个 `live_info` 的 URL 字段进行标准化处理
       except Exception as e:
           # 本次运行仍然失败的页面，加入 newly_failed_pages
           newly_failed_pages.append(page_url)
   ```

   > 注意：这里的核心是**复用与循环 2 相同的页内处理逻辑**，保证行为一致。

#### 循环 2：增量爬取（带页面级停止）

1. 主循环示意（在 `parse_all_liveroomlist_data` 中）：

   ```python
   stop_pagination = False
   page = 1
   while not stop_pagination:
       page_url = 构造当前页的请求URL或标识     # 与 get_liveroom_list 参数对应

       try:
           page_data = self.get_liveroom_list(
               authorization_token=token,
               page=page,
               psize=page_size,
               ...
           )
           if not page_data or "dataObj" not in page_data:
               raise Exception("page_data 无效")
       except Exception as e:
           self.logger.error(f"获取分页URL (页码 {page}) 失败: {e}")
           newly_failed_pages.append(page_url)
           page += 1
           continue

       item_list = page_data["dataObj"].get("list", []) or []

       # 关键逻辑：页面级停止、页内不提前 break
       page_is_entirely_old = True
       items_to_crawl = []

       for item in item_list:
           item_id = str(item.get("id", "")).strip()
           item_starttime = str(item.get("starttime", "")).strip()   # 时间锚点字段统一用 starttime

           # 决策 A：跳过已知 ID（成功或失败都有记录）
           if item_id in successful_ids or item_id in failed_ids:
               continue

           # 决策 B：时间早于 latest_success_time 的旧数据
           if latest_success_time and item_starttime and item_starttime < latest_success_time:
               # 旧数据，可以跳过，但不能 break
               continue

           # 决策 C：需要处理的增量或失败补爬数据
           page_is_entirely_old = False
           items_to_crawl.append(item)

       # 实际发详情请求并写入 DB / 增量
       for item in items_to_crawl:
           status, live_info = self.crawl_single_item(item)
           # 标准化 URL 字段
           url_fields = ['video_url', 'cover_url', 'liveroom_url', 'original_playback_url', 'edited_playback_url', 'videosrc']
           for field in url_fields:
               if field in live_info and live_info[field]:
                   live_info[field] = self.normalize_url(live_info[field])
           # 写入 liversoms（使用 save_single_to_db，内部会处理除重）
           self.save_single_to_db(live_info)
           # 只对成功数据写入本轮 inc，并按 ID 去重
           if status == "success":
               item_id = str(live_info.get("id", "")).strip()
               if item_id and item_id not in inc_ids_processed:
                   inc_data_for_this_run.append(live_info)
                   inc_ids_processed.add(item_id)

       # 页面级停止判断：整页全是旧数据，且已经有 latest_success_time 时，停止翻页
       if page_is_entirely_old and latest_success_time:
           self.logger.info(f"第 {page} 页的所有数据均早于时间锚点，[循环2] 停止。")
           stop_pagination = True

       page += 1
   ```

2. 关键点总结：

   * **页内只用 `continue`，不准用 `break` 去提前终止整个页。**
   * `page_is_entirely_old` 只有在“本页所有 item 都已经在成功 / 失败集合中，或时间早于 `latest_success_time`”时才保持为 `True`，否则会被置为 `False`。
   * **页面级停止条件**：
     `if page_is_entirely_old and latest_success_time is not None:` 才停止分页。
   * 这样可以避免你之前提到的“第 3 条旧数据提前触发停止，导致第 4~10 条漏爬”的问题。

> 实际实现时，可以把上面的页内逻辑抽象成一个统一的辅助函数 `process_page_items(...)`，供循环 1 和循环 2 复用。
> 
> **重要：** 在 `process_page_items` 函数内部，对每个爬取到的 `live_info`，在保存到数据库之前必须对所有 URL 字段进行标准化处理（调用 `self.normalize_url()`）。

#### 循环 3：失败 ID 重试

1. 在循环 2 结束后，**先从数据库重新刷新 `failed_ids`**：

   ```python
   self.logger.info("刷新失败ID列表，为[循环3]做准备...")
   failed_ids = self.load_failed_ids_from_db()
   # load_failed_ids_from_db 内部执行：
   # SELECT id FROM liversoms WHERE video_url IS NULL OR video_url = '';
   ```

2. 然后对每一个失败 ID 进行重试：

   ```python
   self.logger.info(f"开始 [循环3：ID失败重试]，共 {len(failed_ids)} 个项目...")

   for item_id in failed_ids:
       # 如果本轮已经成功处理过（例如在循环1或循环2中成功了），则跳过
       if item_id in inc_ids_processed:
           continue

       status, live_info = self.crawl_single_item_by_id(item_id)
       # 标准化 URL 字段
       url_fields = ['video_url', 'cover_url', 'liveroom_url', 'original_playback_url', 'edited_playback_url', 'videosrc']
       for field in url_fields:
           if field in live_info and live_info[field]:
               live_info[field] = self.normalize_url(live_info[field])
       self.save_single_to_db(live_info)

       if status == "success":
           if item_id not in inc_ids_processed:
               inc_data_for_this_run.append(live_info)
               inc_ids_processed.add(item_id)
   ```

3. 这样可以保证：

   * 所有当前仍然 `video_url` 为空的 ID 都会在本轮被再次尝试；
   * 一旦成功，`save_single_to_db` 使用 `INSERT OR REPLACE` 配合唯一索引自动处理除重；
   * 同一个 ID 本轮只会写一次到 `inc` 文件（靠 `inc_ids_processed` 去重）。

   * "成功记录"判定条件：`video_url IS NOT NULL AND video_url != ''`；

3. **latest_success_time 一律基于 `starttime` 计算**，并且 `starttime` 存储格式要可排序（建议 `YYYY-MM-DD HH:MM:SS` 字符串）。
4. 页内循环只能用 `continue` 跳过，不得因时间条件提前 `break` 整个页。
5. 三重循环的顺序必须是：

   * 先 Page 失败重试 →
   * 再增量分页爬取（页面级停止） →
   * 最后 ID 失败重试。
6. **URL 标准化：**
   * 在保存到数据库之前，必须对所有 URL 字段进行标准化处理
   * 需要标准化的字段：`video_url`, `cover_url`, `liveroom_url`, `original_playback_url`, `edited_playback_url`, `videosrc`
   * 标准化应在 `save_single_to_db()` 调用之前完成，确保存入数据库的 URL 都是标准化后的格式
7. **除重机制：**
   * **数据库层面：** 通过唯一索引 `idx_unique_liveroom_video (zbId, id, video_url)` 确保数据唯一性
   * **应用层面：** `save_single_to_db()` 使用 `INSERT OR REPLACE`，配合唯一索引自动处理除重
   * **除重规则：** `zbId` (user_id) + `id` (liveroom_id) + `video_url` (标准化后) 的组合必须唯一
   * **工作原理：** 
     * 当尝试插入违反唯一索引的记录时，`INSERT OR REPLACE` 会自动删除旧记录并插入新记录
     * 无需手动查询，数据库会自动处理，性能更优
   * **这意味着：** 同一个用户的同一个直播间，如果 `video_url` 不同（比如不同时间的回放），可以存储多条记录

只要严格按照上面的“最终版爬取方案 V2”实现，你生成的新版本 `dynamicCrawler_vzan.py` 就能做到：

* 所有正确数据都被写入 SQLite；
* 所有失败数据都有记录并可重试；
* 增量文件 inc CSV 按 ID 去重；
* 充分利用时间顺序，只爬必要的增量数据；
* **不会出现“第 3 条记录旧 → 直接 break，导致第 4~10 条漏爬”的情况。**
