## 一、变更范围

- **目标**：在内容管理模块中支持**直播间（live_rooms）与分类（categories）的多对多**关系。
- **修改文档**：仅修改《直播核心功能设计文档_v6_内容管理模块设计文档-标签-分类-场次标签关联.md》；**不修改**《直播核心功能设计文档_v6_深度融合最终版.md》。
- **不涉及**：不增加分类的二级结构（不给 `categories` 增加 `parent_id`），保持当前一级科室（如肝胆科、骨科）设计。

## 二、与 v6 主文档的衔接（直播间侧命名与结构）

以下均引用自《直播核心功能设计文档_v6_深度融合最终版.md》：

- **表名**：直播间表为 `live_rooms`；主键为 `id` (UUID)。
- **房间路由**：`GET /api/v1/rooms`、`POST /api/v1/rooms`、`GET /api/v1/rooms/{room_id}`、`PATCH /api/v1/rooms/{room_id}`、`DELETE /api/v1/rooms/{room_id}` 等；路径参数为 `room_id`，对应 `live_rooms.id`。
- **房间模型**：创建请求使用 `RoomCreate`；房间详情响应为「Room + tabs」等，以 v6 主文档定义为准。

## 三、新增表：live_room_categories（直播间-分类关联表）

在主文档 **§2 数据库 DDL** 中新增 **2.4 live_room_categories**，表结构如下。风格与现有 `session_tags`、`categories` 及 v6 中 `live_rooms` 保持一致。

```sql
CREATE TABLE live_room_categories (
    room_id UUID NOT NULL,
    category_id UUID NOT NULL,
    is_primary BOOLEAN DEFAULT false,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (room_id, category_id),

    CONSTRAINT fk_live_room_categories_room_id
        FOREIGN KEY (room_id) REFERENCES live_rooms(id) ON DELETE CASCADE,
    CONSTRAINT fk_live_room_categories_category_id
        FOREIGN KEY (category_id) REFERENCES categories(id) ON DELETE CASCADE
);

CREATE UNIQUE INDEX idx_live_room_categories_room_primary
    ON live_room_categories (room_id)
    WHERE is_primary = true;

CREATE INDEX idx_live_room_categories_room_id ON live_room_categories(room_id);
CREATE INDEX idx_live_room_categories_category_id ON live_room_categories(category_id);

COMMENT ON TABLE live_room_categories IS '直播间与分类的多对多关联表';
COMMENT ON COLUMN live_room_categories.room_id IS '直播间ID，关联 live_rooms 表';
COMMENT ON COLUMN live_room_categories.category_id IS '分类ID，关联 categories 表';
COMMENT ON COLUMN live_room_categories.is_primary IS '是否为该直播间的主科室（可选，用于与 live_rooms.category_id 同步）';
```

- **唯一约束**：`(room_id, category_id)` 为 PRIMARY KEY。
- **级联**：与 `session_tags` 一致，关联表硬删除，房间或分类删除时 CASCADE。
- **is_primary**：可选；每个 `room_id` 至多一条 `is_primary = true`（由部分唯一索引保证）。**首版可仅实现多对多与三个 API，不实现 is_primary 与 live_rooms.category_id 的同步**，以降低实现复杂度。

## 四、新增 API 设计

| 能力 | 方法 | 路径 | 认证 | 说明 |
|------|------|------|------|------|
| 获取某直播间的分类列表 | GET | `/api/v1/rooms/{room_id}/categories` | 公开 | 返回该直播间关联的已启用分类列表 |
| 设置某直播间的分类列表 | POST | `/api/v1/admin/rooms/{room_id}/categories` | ADMIN/SUPERADMIN | 批量设置，支持 replace/append |
| 删除某直播间的单个分类关联 | DELETE | `/api/v1/admin/rooms/{room_id}/categories/{category_id}` | ADMIN/SUPERADMIN | 删除一条 live_room_categories 记录 |

### 4.1 GET /api/v1/rooms/{room_id}/categories

- 路径参数 `room_id` 对应 `live_rooms.id`。
- 联表查询 `live_room_categories` + `categories`，条件 `room_id = :room_id` 且 `categories.is_active = true`，按 `sort_order`、`name` 排序。
- 响应 `data` 复用 **CategoryItem**（或 CategoryBriefItem）。
- 若房间不存在返回 2001。

### 4.2 POST /api/v1/admin/rooms/{room_id}/categories

- 请求体：**LiveRoomCategoriesSetRequest** — `category_ids: List[UUID]`，`mode: Literal["replace","append"]`。
- **replace**：先删该 room 的 live_room_categories 再批量插入。
- **append**：仅插入，冲突忽略。
- 响应返回当前房间分类列表（如 **LiveRoomCategoriesSetResponse**：room_id、mode、categories）。

### 4.3 DELETE /api/v1/admin/rooms/{room_id}/categories/{category_id}

- 删除 `live_room_categories` 中对应行；不存在则 2001。

### 4.4 按分类筛选直播间

若需要「按分类筛房间」，建议在 v6 已有 **GET /api/v1/rooms** 上增加查询参数（如 `category_id`），语义为「至少属于该分类的直播间」。实现归属 v6 主文档或实现阶段约定；本模块仅提供 `live_room_categories` 数据支持。

## 五、新增 Pydantic Schema（建议）

在主文档 **§3** 中新增 **3.4 Live_Room_Categories Schemas**：

- **LiveRoomCategoriesSetRequest**：`category_ids: List[uuid.UUID]`（可做唯一性校验），`mode: Literal["replace", "append"]`。
- **LiveRoomCategoriesSetResponse**：`room_id: uuid.UUID`，`mode: str`，`categories: List[CategoryItem]`（或 CategoryBriefItem）。
- **LiveRoomCategoriesListResponse**：`data: List[CategoryItem]`。若仅需简要信息，可定义 **CategoryBriefItem**（id、name、slug），与 TagBriefItem 对应。

## 六、与 live_rooms.category_id 的关系

v6 中 `live_rooms` 已有 **category_id UUID NULL** 预留。

- **约定**：保留 `live_rooms.category_id` 作为可选「主科室」冗余，与 `live_room_categories` 并存。
- 若需要主科室：在 `live_room_categories` 中至多一条 `is_primary = true`，可将该 `category_id` 同步到 `live_rooms.category_id`。
- 若不需要：仅用 `live_room_categories`，不写 `live_rooms.category_id`。实现时二选一明确即可。
- **与房间创建/更新的衔接**：若 v6 的 `POST /api/v1/rooms` 或 `PATCH /api/v1/rooms/{room_id}` 当前或未来接受请求体中的 `category_id`，则应与上述主科室约定一致（例如仅作为主科室冗余，写入时同步插入或更新 `live_room_categories` 中该房间 `is_primary=true` 的一条）。
