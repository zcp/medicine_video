## 3.6. 跨层规范 (Cross-Cutting Concerns)

### 检测点 6.1 (安全规范)

**状态**: **[一致]**

**说明**: 
- Doc-API 中明确说明了权限要求：
  - 公开接口：`GET /tags`, `GET /categories`, `GET /sessions/{id}/tags`, `GET /sessions/search` 不需要认证
  - Admin接口：所有Admin接口需要强制认证，并检查管理员权限（`ADMIN` 或 `SUPERADMIN`）
  - 硬删除权限：只有 `SUPERADMIN` 可以执行硬删除操作
- Doc-API 中明确要求使用 `Depends(get_current_user)` 或 `Depends(get_current_user_optional)` 获取JWT Payload
- Service层接收 `user_id: UUID` 和 `user_role: LiveRoomMessageUserRole` 进行权限检查
- 与原始设计文档中的认证要求完全一致

### 检测点 6.2 (日志规范)

**状态**: **[一致]**

**说明**: 
- Doc-API 中详细定义了日志记录规范（Section 9.0）：
  - **INFO级别**: 记录正常业务操作（创建、更新、查询成功）
  - **WARNING级别**: 记录权限拒绝、业务异常（软删除、资源不存在）
  - **ERROR级别**: 记录系统异常、硬删除操作
- 日志内容要求：必须包含操作类型、资源ID、关键字段值、用户ID
- 禁止包含敏感信息（密码、Token、完整请求体）
- 位置：Service层记录业务日志，API层记录请求日志和异常日志
- 与原始设计文档中的日志记录要求一致

### 检测点 6.3 (隐式规范)

**状态**: **[一致]**

**说明**: 
- Doc-CRUD 和 Doc-API 严格遵守了学院派架构的隐式规范：
  - UUID在应用层生成（`uuid.uuid4()`），不依赖数据库默认值
  - 使用 `PATCH` 而非 `PUT` 进行部分更新
  - 分页查询通过两次查询实现（COUNT + 数据查询）
  - 使用 `selectinload` 或 `joinedload` 预加载关系，避免N+1查询
  - CRUD层不包含业务逻辑，Service层不处理事务
  - API层使用 `APIRouter(tags=["..."])` 不指定 `prefix`，`prefix` 在顶层统一指定
- 所有隐式规范都得到了严格遵守

## 3.9. 特殊业务逻辑检查

### 检测点 9.1 (软删除处理)

**状态**: **[一致]**

**说明**: 
- Doc-CRUD 和 Doc-API 中明确说明了软删除处理：
  - Tags和Categories使用软删除（`is_active=false`）
  - 查询时默认只返回 `is_active=true` 的记录
  - Admin接口可以通过 `include_inactive` 参数查看所有记录
- 与原始设计文档中的软删除策略一致

### 检测点 9.2 (批量操作模式)

**状态**: **[一致]**

**说明**: 
- Doc-API 中明确说明了批量设置标签的两种模式：
  - `replace` 模式：先删除现有标签，再添加新标签
  - `append` 模式：仅添加新标签，保留现有标签，过滤重复的 `tag_ids`
- Service层需要检查已存在的标签关联，过滤重复项
- 与原始设计文档中的批量操作要求一致

### 检测点 9.3 (标签搜索模式)

**状态**: **[一致]**

**说明**: 
- Doc-CRUD 和 Doc-API 中明确说明了标签搜索的两种模式：
  - `any` 模式：满足任一标签（OR逻辑），使用 `SessionTag.tag_id.in_(tag_ids)` 和 `DISTINCT` 去重
  - `all` 模式：满足所有标签（AND逻辑），使用子查询要求场次的关联标签数量等于 `len(tag_ids)`
- CRUD层提供 `get_sessions_by_tags` 函数支持两种模式
- Service层验证 `match_mode` 参数，抛出 `InvalidTagSearchModeException` 如果无效
- 与原始设计文档中的搜索模式要求一致

### 检测点 9.4 (引用关系检查)

**状态**: **[一致]**

**说明**:
