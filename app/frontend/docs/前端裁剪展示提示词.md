# 前端裁剪展示提示词（最终强化稿）

## 1. 角色与任务目标

你是一名资深前端工程师，负责在当前项目中补齐**头像裁剪、头像展示与上传闭环**。

本任务的目标不是把图片简单显示成圆形，而是建立一条清晰、稳定、可维护的头像链路：
- 从手机本地相册选择图片；
- 进入裁剪流程；
- 在固定裁剪框内拖动和缩放图片；
- 生成裁剪结果；
- 上传后回填正式 `avatar_url`；
- 头像在个人信息页稳定展示；
- 头像预览由独立预览组件承担，裁剪流程只负责裁剪与结果生成；
- 默认头像和失败兜底稳定可用。

本任务的核心原则：
- **优先补裁剪与上传闭环**；
- **预览由独立组件负责，裁剪流程不重复实现预览页面逻辑**；
- **裁剪结果与正式头像 URL 严格分层**；
- **不要新增重复的图片管理体系**。

## 2. 强约束与前置检查

### 2.1 默认前提
- 当前项目中已经存在个人信息页和编辑资料页；
- 当前前端项目位于 `D:\saas_app-main`，页面结构、路由组织和 API 风格已经固定；
- 头像能力是增量补充，不是重写个人资料系统；
- 头像预览建议抽成一个独立组件，供编辑页和个人信息页复用；
- 裁剪流程只负责生成结果，预览由独立组件负责；
- 预览只负责看图，不负责裁剪、上传和资料保存。

### 2.2 必须先阅读的文件
在开始写代码前，必须先阅读并理解：
- 当前个人信息页头像点击入口；
- 当前编辑资料页头像选择与上传实现；
- 当前头像展示样式与默认头像逻辑；
- 当前已有的图片预览方式或系统调用方式；
- 当前 `avatar_url` 的读取逻辑；
- 与头像相关的状态管理逻辑；
- 现有图片上传或请求封装方式。

### 2.3 头像数据源必须固定
在实现前必须明确：
- 裁剪前的原图只是本地临时状态；
- 裁剪结果只作为上传前中间态；
- 页面展示与预览主数据源是后端返回的正式 `avatar_url`；
- 临时路径不能写入长期资料状态；
- 如果支持本地即时预览，也只能作为当前会话内的短生命周期能力；
- 裁剪流程不应额外复制一套预览页面逻辑，预览统一复用组件。

### 2.4 禁止事项
- 禁止新建一套完全独立的个人资料系统；
- 禁止把裁剪逻辑散落到多个页面且彼此不一致；
- 禁止把头像展示、裁剪、预览、上传混成一个难以维护的大页面；
- 禁止把临时路径当成最终头像地址；
- 禁止把裁剪页写成复杂图片编辑器；
- 禁止为了头像功能大范围改动无关模块；
- 禁止在裁剪流程里重复实现预览页面。

### 2.5 文件修改边界
#### 允许修改
- 个人信息页；
- 编辑资料页；
- 新增头像裁剪页或裁剪组件；
- 头像预览组件；
- 头像展示相关样式；
- 少量与头像有关的状态管理逻辑；
- 少量与头像有关的类型定义。

#### 不允许随意修改
- 不允许重构整个请求框架；
- 不允许改动与头像无关的业务 API；
- 不允许改动登录、注册、验证码、密码重置等无关流程；
- 不允许新增一套平行的用户资料目录结构；
- 不允许把头像功能写成与账号管理耦合的复杂模块。

### 2.6 推荐执行顺序
1. 审查个人信息页与编辑资料页的头像入口；
2. 明确当前是否已有裁剪组件或裁剪页；
3. 明确头像预览是否可抽成独立组件；
4. 固定接口定义与状态字段；
5. 设计最小可用的裁剪与展示方案；
6. 只在必要位置补充裁剪、预览和上传逻辑；
7. 最后验证头像刷新、预览和兜底是否正常。

## 3. 页面职责与整体架构

### 3.1 职责分离
- **个人信息页**：展示当前头像，并提供预览入口；
- **编辑资料页**：负责选择图片、裁剪、上传；
- **头像裁剪页 / 裁剪组件**：负责本地图片裁剪；
- **头像预览组件**：负责大图查看；
- **资料更新接口**：只负责保存正式头像 URL；
- **裁剪流程内的结果确认**：只负责确认裁剪效果，不负责独立预览页跳转。

### 3.2 推荐结构
如果当前项目没有现成能力，建议新增：
- `src/pages/app/tabbar/my/edit-profile/avatar-crop.vue` 或同类裁剪页；
- `src/components/shared/AvatarPreview.vue` 或同类预览组件；
- 必要时增加一个轻量的裁剪辅助组件，例如 `AvatarCropper.vue`。

如果项目中已有可复用图片预览能力，优先在现有能力上增量接入，不要重复造轮子。

## 4. 任务一：补头像裁剪能力

### 4.1 任务目标
让用户选择本地图片后，先进入裁剪流程，再上传最终头像结果图。

### 4.2 数据流定义
推荐按以下方式处理：
1. 在编辑资料页点击“更换头像”；
2. 调用系统选图；
3. 进入裁剪页或弹出裁剪组件；
4. 对原图进行拖动、缩放和裁剪；
5. 生成裁剪结果图；
6. 在当前流程内调用预览组件查看裁剪结果（如需要）；
7. 调用上传接口；
8. 上传成功后回填正式 `avatar_url`；
9. 返回编辑资料页或个人信息页并刷新展示。

### 4.3 设计要求
裁剪交互应满足：
- 裁剪框固定不动；
- 图片可拖动、可缩放；
- 必须限制最小/最大缩放比例；
- 必须限制拖动边界，避免裁剪区域露白；
- 裁剪结果优先输出为正方形，便于后续圆形展示；
- 裁剪失败时要有可见提示与回退方案；
- 如果手势实现复杂，优先保证基础拖拽与缩放稳定；
- 若需要查看裁剪结果，应复用统一预览组件，而不是在裁剪页里再造一个独立预览页。

### 4.4 优先实现方式
- 优先在现有编辑资料页中增加裁剪入口；
- 如果裁剪逻辑较多，优先独立成裁剪页或裁剪组件；
- 预览能力必须复用统一组件，不要在裁剪流程里重复造轮子；
- 不建议在主编辑页里堆叠过多触摸计算逻辑。

### 4.5 完成标准
完成后应满足：
- 用户选图后能进入裁剪；
- 图片能正常拖动、缩放；
- 能生成稳定裁剪结果图；
- 裁剪结果可直接上传到后端；
- 裁剪流程不会破坏原有资料编辑能力。

## 5. 任务二：补头像展示能力

### 5.1 任务目标
让个人信息页中的头像展示稳定、统一，并与裁剪后的结果保持一致。

### 5.2 建议实现方向
建议优先补以下能力中的一项或多项：
- 头像统一圆形容器；
- 使用正式 `avatar_url` 展示头像；
- 头像加载失败时显示默认图；
- 页面刷新后仍显示后端返回的正式头像；
- 点击头像时交给统一预览组件查看大图。

### 5.3 设计要求
头像展示应满足：
- 圆形展示仅属于 UI 呈现，不要求图片文件本身必须是圆形；
- 头像加载失败必须有默认图；
- 本地临时路径只用于裁剪与即时预览，不用于最终持久化；
- `sourceImage` 只用于选图后的裁剪与即时预览；
- `croppedImage` 只用于上传前的中间态，不得写入最终资料；
- `avatar_url` 是唯一长期持久状态；
- 头像展示与资料页状态保持一致。

### 5.4 优先实现方式
- 优先复用现有 `displayAvatar` 或等价状态；
- 优先从后端返回的 `avatar_url` 读取头像；
- 如有本地临时头像，只用于裁剪中预览；
- 不建议把头像展示逻辑散落在多个页面里重复实现。

### 5.5 完成标准
完成后应满足：
- 个人信息页头像能稳定显示；
- 更新头像后页面能及时刷新；
- 默认头像与失败兜底正常；
- 圆形展示风格统一。

---

## 6. 任务三：统一头像预览能力

### 6.1 任务目标
让用户在编辑页或个人信息页点击头像时，可以查看矩形大图，而不是只看到圆形裁切后的局部效果。

### 6.2 推荐实现方式
头像预览建议抽为独立组件，供多个页面调用：
- `AvatarPreview.vue`
- 或同等职责的轻量预览组件

使用方式建议：
- 编辑页点击当前头像时打开预览组件；
- 个人信息页点击头像时打开预览组件；
- 如果需要更强控制，再考虑独立预览页作为补充；
- 默认不把预览做成复杂独立页面，除非项目已有页面化预览的统一规范。

### 6.3 设计要求
预览交互应满足：
- 预览时不要再使用圆形遮罩；
- 图片应以矩形大图或标准预览方式显示；
- 支持关闭、返回或遮罩点击关闭；
- 预览组件应轻量，不要负责上传或裁剪；
- 如果支持本地临时图预览，只允许在当前会话内使用；
- 预览组件必须能直接被编辑页和个人信息页复用。

### 6.4 预览组件边界
预览组件只处理以下事情：
- 接收图片 URL；
- 控制显示/隐藏；
- 展示大图；
- 提供关闭动作；
- 处理加载失败兜底。

预览组件不应处理：
- 图片裁剪；
- 图片上传；
- 资料保存；
- 复杂图片编辑；
- 与头像无关的业务状态。

### 6.5 完成标准
完成后应满足：
- 编辑页和个人信息页都能复用同一个预览能力；
- 点击头像能正常查看大图；
- 大图显示比例正常；
- 不影响头像圆形展示；
- 不影响裁剪和上传流程。

## 7. 与后端的配合要求

### 7.1 裁剪后再上传
前端应在裁剪完成后再调用上传接口，不要把原图直接作为最终头像。

### 7.2 上传成功后回填 URL
上传成功后必须使用后端返回的正式 `avatar_url` 更新用户资料状态。

### 7.3 资料页刷新
头像上传或资料更新后，必须重新渲染页面中的头像展示。

### 7.4 状态恢复流程
建议把头像上传和资料保存拆成可恢复流程：
1. 先保留本地裁剪结果；
2. 上传成功后再回填 `avatar_url`；
3. 若上传失败，保留裁剪结果与重试入口；
4. 若资料保存失败，不清空裁剪态和本地展示态；
5. 页面重新进入时，始终以后端正式 `avatar_url` 为准。

### 7.5 统一字段
前端必须继续使用现有 `avatar_url`，不要擅自新增重复字段。

## 8. 风险与隐患处理建议

### 8.1 裁剪交互实现复杂
AI 可能在拖拽、缩放、边界约束上写得不够稳。建议的规避方式是：
- 优先把功能拆成更具体的实现任务；
- 裁剪页/裁剪组件与预览组件分离；
- 如果仍使用一份总提示词，则必须明确“先实现裁剪，再接预览组件，再做展示”，避免一次性塞进一个大页面。

### 8.2 头像 URL 稳定性不足
建议使用稳定 URL，而不是临时路径。优先级建议：
1. 后端返回可长期访问的稳定地址；
2. 前端只保存 `avatar_url`；
3. 页面展示失败时回退默认头像；
4. 不在前端保存任何一次性临时文件地址；
5. 若需要会话内即时预览，本地路径仅限当前会话，不可进入长期状态。

### 8.3 手机端兼容性问题
建议：
- 裁剪页兼容触摸事件；
- 支持相册选择图片，必要时兼容相机；
- 控制图片缩放上下限；
- 裁剪框大小随屏幕自适应；
- 预览组件在窄屏下也要能正常展示与关闭。

### 8.4 上传失败后的状态恢复不完善
建议把头像上传和资料保存拆成可恢复流程：
1. 先保存裁剪结果到本地状态；
2. 上传成功后再回填 `avatar_url`；
3. 若上传失败，保留裁剪结果与重试入口；
4. 若资料保存失败，不清空裁剪态和本地展示态，允许用户继续重试。

## 9. 实现建议与代码修改边界

### 9.1 优先修改位置
优先修改：
- 个人信息页；
- 编辑资料页；
- 头像预览组件；
- 头像裁剪页或裁剪组件；
- 少量用户状态管理逻辑。

### 9.2 尽量不要做的事
- 不要把裁剪、上传、预览全部塞进一个函数；
- 不要把原图路径、裁剪结果、正式 URL 混成一个状态；
- 不要把临时路径写进最终用户资料；
- 不要重写整个个人资料页；
- 不要把预览组件写成二次图片编辑器；
- 不要在裁剪流程里重复实现预览页面。

### 9.3 可接受的小幅扩展
可接受的扩展包括：
- 新增裁剪页或裁剪组件；
- 新增预览组件；
- 新增上传状态；
- 新增默认头像与失败兜底逻辑；
- 新增图片拖拽和缩放交互状态。

## 10. 验收标准

若 AI 完成本任务，最终应满足以下要求：
- 用户从本地相册选择图片后能进入裁剪流程；
- 裁剪框固定，图片可拖动可缩放；
- 裁剪结果可成功生成；
- 头像在个人信息页中以圆形方式稳定展示；
- 编辑页或个人信息页点击头像时可调用统一预览组件查看矩形大图；
- 上传成功后头像状态能刷新；
- 默认头像与失败兜底正常；
- 不新增重复的图片管理体系。

---

## 11. 给 AI 的最终要求

可以直接向 AI 下达如下要求：
- 当前任务只做图片裁剪、头像展示与统一预览，不要扩展到无关模块；
- 必须先读现有前端编辑页、头像展示逻辑和 `avatar_url` 状态，再给实现方案；
- 头像预览必须**优先使用组件**，编辑页和个人信息页共享同一组件；
- 只有当组件无法满足某些端的交互约束时，才补独立预览页；
- 只允许在现有页面基础上增量补充裁剪、展示和预览能力；
- 禁止把临时路径当成最终头像地址；
- 本轮重点是：裁剪稳定、展示统一、预览轻量、返回清晰、组件优先。

---

## 12. 结论

本提示词服务于当前项目中头像裁剪与展示能力的补齐工作，目标是：
- 让图片裁剪稳定可用；
- 让头像展示统一可靠；
- 让点击预览轻量易复用；
- 让前端围绕现有 `avatar_url` 形成完整闭环；
- 在不破坏现有资料模块的前提下，完成最小而稳定的增量实现。
