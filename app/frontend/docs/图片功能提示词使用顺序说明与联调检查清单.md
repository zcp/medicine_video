# 图片功能提示词使用顺序说明与联调检查清单

## 一、使用顺序说明

当前这套图片功能提示词建议按以下顺序使用，不要跳步：

### 第 1 步：后端上传接口提示词
文件：`app修改记录/后端上传接口提示词.md`

#### 目的
先把图片上传接口、返回字段、存储方式、错误处理固定下来。

#### 你要让 AI 做的事
- 确认上传接口路径和方法；
- 固定请求字段 `file`；
- 固定响应字段 `avatar_url`；
- 完成图片落盘或对象存储；
- 支持 `PATCH /users/me` 写回头像 URL。

#### 为什么先做这一步
前端裁剪和预览最终都依赖后端返回的正式 `avatar_url`。如果接口不先固定，后面的前端实现很容易对不上。

---

### 第 2 步：前端裁剪展示提示词
文件：`app修改记录/前端裁剪展示提示词.md`

#### 目的
实现手机端选图、裁剪、拖动、缩放、生成结果图、上传前状态管理和头像圆形展示。

#### 你要让 AI 做的事
- 选择本地图片；
- 进入裁剪流程；
- 固定圆形裁剪框；
- 拖动/缩放图片；
- 生成裁剪结果；
- 上传成功后回填 `avatar_url`；
- 上传失败后保留裁剪状态，允许重试。

#### 为什么第二步做这一步
裁剪后的图片需要上传，而上传接口已经在第一步固定好了，所以这里可以直接按正式接口实现。

---

### 第 3 步：前端预览提示词
文件：`app修改记录/前端预览提示词.md`

#### 目的
实现点击头像后的矩形大图预览。

#### 你要让 AI 做的事
- 点击头像查看大图；
- 保持图片比例正常；
- 不再套圆形遮罩；
- 预览只负责展示，不负责裁剪、保存、上传；
- 使用正式 `avatar_url` 作为预览数据源。

#### 为什么第三步做这一步
预览是独立能力，建议在裁剪与上传闭环完成后再补，避免 AI 把多个职责混成一个页面。

---

## 二、整体推荐流程

建议的完整实施流程是：

1. 先生成后端上传接口；
2. 再生成前端裁剪展示；
3. 最后生成前端预览；
4. 再做一次联调检查；
5. 确认上传、展示、预览全部闭环。

---

## 三、联调检查清单

下面这份清单建议在前后端都生成代码之后逐项核对。

### A. 接口定义检查
- [ ] 上传接口路径已固定
- [ ] 上传方法已固定（通常为 `POST`）
- [ ] 上传字段名已固定为 `file`
- [ ] 上传返回字段已固定为 `avatar_url`
- [ ] 资料更新接口仍然复用 `PATCH /users/me`
- [ ] `GET /users/me` 能返回 `avatar_url`
- [ ] 前后端没有出现重复字段名，例如 `avatar`、`head_img`、`profile_pic`

### B. 后端上传检查
- [ ] 能接收单张图片上传
- [ ] 能校验文件类型
- [ ] 能校验文件大小
- [ ] 能拒绝非法文件
- [ ] 上传后返回的是稳定可访问的 URL
- [ ] 重启服务后头像地址仍然可用
- [ ] 后端响应里只保留一个权威头像字段 `avatar_url`

### C. 前端裁剪检查
- [ ] 从本地相册选择图片正常
- [ ] 进入裁剪页或裁剪组件正常
- [ ] 裁剪框固定不动
- [ ] 图片能拖动
- [ ] 图片能缩放
- [ ] 裁剪区域内不会明显露白
- [ ] 裁剪结果图能正常生成
- [ ] 裁剪结果不会直接写成最终持久头像地址

### D. 前端上传与状态恢复检查
- [ ] 裁剪完成后才上传
- [ ] 上传成功后回填正式 `avatar_url`
- [ ] 上传失败时保留当前裁剪结果
- [ ] 上传失败后允许重试
- [ ] 资料保存失败时不会清空本地裁剪态
- [ ] 页面重新进入后以后端正式 `avatar_url` 为准

### E. 前端头像展示检查
- [ ] 资料页头像圆形展示正常
- [ ] 默认头像兜底正常
- [ ] 头像加载失败时能回退默认图
- [ ] 刷新页面后仍显示正式头像
- [ ] 列表页、资料页展示风格一致

### F. 前端预览检查
- [ ] 点击头像能打开预览
- [ ] 预览显示为矩形大图
- [ ] 预览不再套圆形遮罩
- [ ] 图片比例正常
- [ ] 预览支持返回
- [ ] 预览不影响裁剪和上传流程

---

## 四、常见问题排查

### 1. 前后端字段对不上
优先检查：
- 上传接口字段是否仍然是 `file`
- 返回字段是否仍然是 `avatar_url`
- 前端是否把临时路径当成正式地址保存了

### 2. 裁剪后头像不显示
优先检查：
- 裁剪结果是否真正上传成功
- 上传后是否回填了正式 `avatar_url`
- 头像展示页是否读取了最新用户资料

### 3. 预览显示不正确
优先检查：
- 预览是否仍然使用了圆形头像容器
- 预览是否读取了临时路径而不是正式 URL
- 预览页是否被裁剪逻辑污染

### 4. 上传失败后状态丢失
优先检查：
- 是否保留了本地裁剪结果
- 是否把 `croppedImage` 过早清空了
- 是否在上传失败时错误地重置了头像状态

---

## 五、最终原则

这套图片功能的实现原则可以概括为三句话：

1. **后端先定接口，再让前端对接。**
2. **裁剪只生成结果，不直接成为最终持久状态。**
3. **预览只负责展示，不参与裁剪、上传和保存。**

只要按这个顺序和检查清单执行，整体实现会更稳，也更不容易出现前后端对不上的问题。
