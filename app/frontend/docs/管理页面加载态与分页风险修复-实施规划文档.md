## 一、背景与结论先行

管理端 5 个页面存在不同程度的加载态/分页风险：下拉加载后加载提示常驻、页面被全局遮罩挡住无法操作、刷新时空态白闪、内容不满一屏时连环自动加载、Tab/筛选切换后请求被吞导致数据错乱。

**两轮独立分析对比结论**：双方对 10 项具体问题全部达成共识（无实质冲突）；互为补充——A 轮补充了「`request.ts` 全局 showLoading 遮罩 + GET 重试链」与「admin 房间追加无去重」两个系统性根因；B 轮补充了「pages.json 页面级下拉刷新无收尾」「专家管理刷新空态白闪」「冷却吞补跑」三个更精确的症状定位。经源码逐行复核，合并后问题清单如下：

| # | 页面 | 问题 | 根因 | 严重度 |
|:-:|------|------|------|:---:|
| 1 | 全站房间 | 加载转圈常驻、页面被遮罩挡住无法操作 | 每页 40 个并发专家请求默认弹全局 `showLoading(mask)` 互相 show/hide | **P0** |
| 2 | 全站房间 | 下拉刷新指示器卡住 / 双重下拉冲突 | `refresher-triggered` 绑错变量 + pages.json 页面级下拉无收尾 | **P0** |
| 3 | 全站房间 | 列表重复行无限增长 / Tab·搜索期间刷新被吞 | 追加无去重 + `adminLoading` 直接 return 吞请求 | P1 |
| 4 | 专家管理 | 下拉/切 Tab 刷新时整页空态白闪 | 刷新清空列表但骨架条件只认 `isLoading`，刷新走 `isRefreshing` | **P0** |
| 5 | 专家管理 | 快速切 Tab 后列表停在旧 Tab 数据 | 800ms 冷却 + `pendingRefresh` 补跑互相打架 | P1 |
| 6 | 焦点图 | 内容不满一屏时连环自动加载 | 服务端 total 与客户端再过滤后展示数不一致，hasMore 不自校正 | **P1（高）** |
| 7 | 用户管理 | 失败后跳页 / 连环触底重复请求 | `page++` 先于请求 | P1 |
| 8 | 用户管理 | 切 Tab/筛选请求被静默丢弃 | `isLoading` 直接 return 吞请求 | P1 |
| 9 | 用户管理 | loadMore 后 2s 内下拉/切 Tab 无反应 | 2s 刷新黑名单误伤主动刷新 | P1 |
| 10 | 专家分类 | 与用户管理同套问题（size=200 降低暴露概率） | 同 7/8 | P2 |
| 11 | 专家管理 | 后端持续报错时触底即重发 3 次重试链 | loadMore 失败无冷却 | P2 |
| 12 | 专家分类 | 「待审核」Tab 恒传 `is_active:true`，非激活待审科室永不显示 | 参数口径 | P2 |

**实施总量估算**：约 3-4 人日（纯前端，无后端依赖；含 0.5d 前置核查 + 0.5d 验证/回归），分 7 个阶段（阶段 0 前置核查，之后每阶段有独立核查清单与退出条件）。

## 二、根因归类（跨页 6 类）

| 根因 | 影响 | 涉及页面 | 修复方向 |
|------|------|----------|----------|
| R1 加载态变量分裂：`isLoading`/`isLoadingMore`/`isRefreshing`/`adminLoading` 绑定错位 | 指示器卡住、空态误显 | 全站房间、专家管理 | 归位绑定 + 骨架条件扩展 |
| R2 hasMore 用服务端 total、展示用客户端过滤后列表 | 不满屏自激触底、连环加载 | 焦点图、用户管理(no-stream) | 按实际展示数自校正 total |
| R3 页码提前自增（`page++` 先于请求） | 失败后状态漂移、跳页、hasMore 失真 | 用户、分类、全站房间 | 成功后推进页码 |
| R4 并发用「直接 return」而非排队/序号 | Tab/筛选请求被吞、新旧数据集混搭 | 用户、分类、全站房间 | requestId 序号守卫 + pending 补跑 |
| R5 冷却/补跑机制互相打架 | 该补的请求被自己挡掉 | 专家管理 | 补跑跳过冷却 |
| R6 全局遮罩默认开启 + GET 重试链 | 页面被 mask 挡住、加载提示常驻最长 ~16-20s | 全部（全站房间最重） | 管理端/高频并发请求显式 `showLoading:false` |

## 五、实施目标与边界

### 5.1 实施目标

1. 消除四大症状：加载遮罩卡死 / 加载指示器永久挂起 / 刷新空态白闪 / 连环自动加载与重复错乱请求。
2. 根因修复而非打补丁：加载态变量归位、hasMore 口径一致、请求序号守卫、成功后推进页码、去重兜底。
3. 零行为回退：除 B2（下拉刷新入口统一）外，UI、文案、流程、分页参数、筛选逻辑全部保持不变。
4. 可分阶段独立提交：A→F 每阶段可独立编译验证、独立 commit，先止血（A/B）后加固（D/E/F）。

### 5.2 实施边界

**包含**：
- 上述 A-F 类实施项（5 个页面 + 6 个 API 模块 + `pages.json` 一项）
- API 模块仅做**向后兼容**的 options 参数扩展（默认行为不变）

**不包含**：
- `request.ts` 全局默认行为、auth store、后端契约与数据结构
- `src/pages/h5/` 下所有页面与调用点
- UI 样式、文案、分页 size、筛选规则、交互流程
- 需要后端配合的架构改动（批量接口等）

**例外项（须确认后实施）**：
- B2 `pages.json` 的 `enablePullDownRefresh` 改动影响"我的直播"模式下拉外观，属共享配置必要改动，实施前需需求方确认。

## 六、测试数据管理规范（横切项，全阶段生效，实施前必读）

> 原则：**最小化、可辨识、全登记、可清理、防误删**。本修复以防御性逻辑为主，预期多数阶段**无需创建测试数据**；仅在需要造数验证时走本规范。执行表见 `docs/管理页面加载态与分页风险修复-测试数据登记表.md`。

### 6.1 环境优先原则

1. 验证优先在联调环境（`.env.development` 指向的后端）进行。
2. 阶段 0 记录**数据基线**：5 个管理列表的当前总数与代表条目标题快照，作为实施结束后的核对基准（不删除、不修改任何基线内数据）。

### 6.2 可辨识命名

所有测试创建的数据（焦点图标题 / 用户昵称 / 房间标题 / 科室名 / 专家名等）**必须带统一前缀 `[TEST]`**（如 `[TEST]E1分页验证-0831`），便于列表检索与批量识别。禁止使用真实运营标题。

### 6.3 全量登记

每创建一个测试数据，立即在登记表追加一行（记录 ID / 数据 ID / 标题含前缀 / 关联资源 / 创建时间 / 用途关联实施项 / 清理状态）。

> 关联真实资源（room/专家/科室等）时**只引用其 UUID，不复制、不修改**该资源本身；禁止修改既有记录来"模拟"测试（如需改后还原，必须登记原值并验证还原）。

### 6.4 清理时机与方式

1. **每阶段退出条件**增加清理核查：本阶段登记表内 `[TEST]` 记录全部清理完毕，未清理不得进入下一阶段。
2. **全部实施结束**后统一终检：登记表无"待清理"项 + 各列表数量与阶段 0 基线一致。
3. 清理方式：管理端页面删除或对应 DELETE 接口；删除前执行 6.5 三查。

### 6.5 防误删核对（删除前三查）

1. **查 ID**：与登记表逐条比对，仅删除登记过的 ID；
2. **查标题**：删除前核对标题仍含 `[TEST]` 前缀；若前缀已被修改或无法辨认，**立即停止删除**，人工确认归属后再处理；
3. **查归属**：确认该记录不是既有运营数据（`created_at` 在实施窗口内、标题含前缀、与基线快照不重叠）。

### 6.6 风险声明

| 风险 | 概率 | 影响 | 缓解 |
|------|:---:|:---:|------|
| 测试数据残留（`[TEST]` 数据暴露在 C 端/管理端） | 中 | 中（数据污染） | 6.3 登记 + 6.4 阶段清理 + 终检基线比对 |
| 误删真实数据（删除接口不可恢复） | 低 | **高（不可恢复）** | 6.5 三查 + 登记表先行 + 前缀核对中断机制 |
| 误改真实记录（测试时改到既有数据） | 低 | 中 | 6.3 只新建不修改既有记录原则 |
