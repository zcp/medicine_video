> **文档版本**：v1.4
> **最后更新**：2026-07-23
> **涉及页面**：TabBar 中间按钮、首页 CategoryTabs ≡ 菜单、专家页筛选栏 ≡ 图标、我的页面（管理员视图）、今日场次管理页

## 1. 设计目标与原则

### 1.1 现有问题

当前管理员页面存在以下问题：

1. **导航层级过深**：管理员路径为 TabBar 齿轮 → 管理面板 → 点击功能 → 操作页，需要 3 次点击才能到达实际操作页面
2. **管理面板冗余**：管理面板作为独立页面，功能仅为「展示总量统计 + 功能入口」，而功能入口已在"我的"页面重复存在
3. **统计数据无效**：当前展示总量数据（共 X 个直播间、共 X 个专家），对管理员日常运营无行动驱动力
4. **用户功能干扰**：管理员"我的"页面的快捷操作行（收藏/关注/观看历史/订阅）对管理员几乎无用，挤占管理信息空间
5. **TabBar 角色分支**：中间按钮根据角色显示不同图标（普通用户= "+"、管理员=齿轮），增加了维护成本和用户认知负担

### 1.2 设计目标

- **路径最短**：管理员从首页到执行管理操作不超过 2 次点击
- **数据驱动**：统计数据从「静态总量」转向「动态待办」，推动管理员每日行动
- **角色统一**：TabBar 中间按钮不再根据角色做条件分支，全量用户统一行为
- **空间聚焦**：管理员"我的"页面移除用户向功能，全部空间服务于管理

### 1.3 设计原则

1. **面向行动**：每个数字都代表一个待办事项，点击即可处理
2. **今日优先**：区分「今日运营」和「全部管理」，引导管理员优先处理今日待办
3. **无重复入口**：每个功能只有唯一入口路径
4. **数据类型分离**：时间敏感型数据（今日直播/场次）每天归零；累积待办型数据（待审批/未归类）持续累积，处理后才减少。两类数据不混用标签
5. **关于"其他"分类**："其他"作为系统级熔断器（Circuit Breaker）存在，不是分类行为。当未知科室名出现时（如 CSV 导入），系统自动将科室挂载到"其他"分类下以避免 `category_id NOT NULL` 约束报错。"其他"中专家数量 = 词库覆盖率的反向指标，理想状态为接近 0
6. **运营指标合并**：直播间和场次是 1:N 关系，但管理员关注的运营指标是"今天有几场直播在跑"，不区分直播间数和场次数，统一使用「今日场次」
7. **渐进实施**：UI 层先行改造，数据层待后端具备后接入

### 2.2 数据类型说明（重要）

管理摘要中的数据分为两类，性质不同，展示方式也不同：

| 类型 | 特性 | 字段 | 展示方式 |
|------|------|------|---------|
| **时间敏感型** | 按天自然归零，第二天重新计算 | 今日直播数、今日场次数、正在直播数 | 前缀"今日"或"正在"，数字为当日/当前数据 |
| **累积待办型** | 持续累积，处理后才减少 | 待审批科室数、待审批专家数、未映射专家数 | 不加时间限定词，数字为"当前排队总量" |

**累积待办数据的滚动逻辑**：待审批科室/专家不因日期变更而消失。如果一个科室 7 月 20 日创建、22 日仍未审核，它在 20、21、22 日都显示为待审批。审核通过后计数才减少。这是与"今日直播"的本质区别。

**「未映射专家」不是分类，是工作队列**：未映射专家是指 `department_id = null` 的专家，他们没有关联任何分类。这是一个待办状态，不是分类归属。管理员需要在管理摘要中看到这个待办，去分配正确的分类。

**关于"其他"分类**："其他"是系统级熔断器（Circuit Breaker）。当 `_resolve_department_and_category` 无法匹配到现有分类时，`category_id NOT NULL` 约束要求有兜底值，否则整行创建会抛异常。"其他"中专家数量 = 词库覆盖率的反向指标，理想状态接近 0，但永远不该删除。

#### 3.2.2 新增管理摘要卡片

在个人信息卡片与直播管理之间，插入管理摘要区域（仅管理员可见）。布局采用 **2×2 网格**，第一行为运营状态（现在进行时），第二行为待办事项（需要处理）：

```
┌─────────────────────────┐ ┌─────────────────────────┐
│ 📺 今日场次              │ │ 🔴 正在直播              │  ← Row 1: 运营状态
│ 8 场今日场次             │ │ 2 场直播中               │
│ 查看详情 →              │ │ 进入直播间 →            │
└─────────────────────────┘ └─────────────────────────┘
┌─────────────────────────┐ ┌─────────────────────────┐
│ ⏳ 待审核                │ │ 🔗 未归类专家             │  ← Row 2: 待办事项
│ 科室 2 · 专家 1         │ │ 3 人未分配科室            │
│ 去审核 →                │ │ 去分配 →                 │
└─────────────────────────┘ └─────────────────────────┘
```

**设计考量**：

- **运营指标合并**：直播间（Room）和场次（Session）是 1:N 关系。一个 Room 可以有多场 Session（复用直播间配置）。但管理员关注的运营指标是"今天有几场直播在跑"，不区分直播间数和场次数，统一使用「今日场次」。因此 `today_live_rooms` 和 `today_sessions` 合并为一个卡片
- **「推送通知」不放在摘要卡片中**，因为它是一个纯导航入口，不展示数据。它的入口已存在于下方「管理功能」列表中，无需重复
- **「未映射专家」**取代了推送通知的卡片位，因为它是累积待办型数据且 `getUnmappedExperts()` API 当前可用
- **「待审批科室」和「待审批专家」**合并在同一张卡片中（"科室 2 · 专家 1"），节省卡片位给未映射专家

**卡片点击行为**：

| 卡片 | 数据类型 | 数据来源 | 点击跳转 | 目标页面状态 |
|------|---------|---------|---------|-------------|
| 📺 今日场次 | 时间敏感型 | `GET /admin/stats/daily → today_sessions` | `/pages/app/live-manage/list?filter=today` | 复用现有列表页，新增 filter 参数 |
| 🔴 正在直播 | 时间敏感型 | `GET /admin/stats/daily → live_now` | `/pages/app/live-manage/list?filter=live` | 复用列表页，筛选直播中 |
| ⏳ 待审核 | 累积待办型 | `getDepartments({is_verified:false}) + getAdminExperts({is_verified:false})` | 点击弹出 ActionSheet：「📁 科室审核」→ `/pages/app/admin/departments?tab=pending`，「👤 专家审核」→ `/pages/app/admin/expert-list?tab=pending` | 合并显示但入口分离，管理员选择处理哪种审核 |
| 🔗 未归类专家 | 累积待办型 | `getUnmappedExperts({page:1,size:1})` → `data.total`（✅ 已有 API） | `/pages/app/admin/expert-list?tab=unmapped` | 需新建专家列表页，预筛选未分配分类 |

**未映射专家的业务含义**：专家创建时 `department_id` 为空 → 该专家没有关联任何分类 → 前端分类浏览中不展示该专家 → 管理员需要在管理摘要中看到这个待办，去分配正确的分类。

**关于"其他"分类的定位**：

"其他"是一个**系统级熔断器**（Circuit Breaker），不是分类行为。在专家创建过程中，当 `_resolve_department_and_category` 无法匹配到现有分类时，`category_id` 的兜底值会设为"其他"分类的 ID。这是因为 `category_id` 是 `NOT NULL` 约束字段，没有这个兜底，整行创建会抛异常。

| 状态 | 含义 | 行动 |
|------|------|------|
| 零散专家在"其他" | 词库漏掉了某些科室 | 管理员添加新科室 → 映射走 |
| 大量专家在"其他" | 自适应匹配逻辑需要加强 | 检查匹配算法或补充同义词 |
| 长期接近 0 | 分类体系趋于成熟 | 保留兜底，不可去除 |

所以"未归类专家"卡片追踪的是 `department_id IS NULL` 的专家（完全没有分类），而落入"其他"分类的专家是有分类归属的但匹配不精确。两者是不同的状态，但管理员的行动目标一致——都把它们映射到正确的分类上。

```typescript
function handleMenuClick(): void {
  if (authStore.isAdmin) {
    // 管理员：弹出管理操作浮层
    uni.showActionSheet({
      itemList: ['📁 专家分类管理', '👤 专家审核'],
      success: (res) => {
        if (res.tapIndex === 0) uni.navigateTo({ url: '/pages/app/admin/departments/index' });
        if (res.tapIndex === 1) uni.navigateTo({ url: '/pages/app/admin/expert-list/index?tab=pending' });
      }
    });
    return;
  }
  // 普通用户：不变
  uni.navigateTo({ url: '/pages/app/categories/AllCategories' });
}
```

**设计考量**：
- 保留 Tab 栏对普通用户和管理的浏览功能都仍然有价值
- ≡ 按钮位置天然（最右侧、独立区域），适合做角色分支
- 不新增 UI 元素，不占用额外屏幕空间

## 4. 数据需求

### 4.1 管理摘要数据

**数据类型区分**：

| 卡片 | 数据类型 | 时间特性 | 数据字段 | 当前可用性 | 获取方式 |
|------|---------|---------|---------|-----------|---------|
| 📺 今日场次 | 时间敏感型 | 每天自然归零 | `today_sessions` | ❌ 后端缺 | `GET /admin/stats/daily` |
| 🔴 正在直播 | 时间敏感型 | 实时，无直播时为 0 | `live_now` | ❌ 后端缺 | `GET /admin/stats/daily` |
| ⏳ 待审核科室 | 累积待办型 | 持续累积，处理后才减少 | `pending_departments` | ✅ 当前可用 | `getDepartments({is_verified: false, page:1, size:1})` → `data.total`（已有参数） |
| 👤 待审批专家 | 累积待办型 | 持续累积，处理后才减少 | `pending_experts` | ⚠️ 需确认 | `getAdminExperts()` 需后端确认 `is_verified` 筛选支持 |
| 🔗 未归类专家 | 累积待办型 | 持续累积，分配后才减少 | `unmapped_experts` | ✅ **当前可用** | `getUnmappedExperts({page:1,size:1})` → `data.total`（已有 API） |

**累积待办数据的计数逻辑**（后端需保证）：
```
待审批科室数 = SELECT COUNT(*) FROM expert_departments 
               WHERE is_verified = false AND deleted_at IS NULL
               -- 不限制 created_at 范围，所有未审核的历史数据都算

未映射专家数 = SELECT COUNT(*) FROM experts
               WHERE department_id IS NULL AND deleted_at IS NULL
               -- department_id 为空即视为未映射，不限创建时间
```

### 4.2 所需后端端点

详见本文第 6 节「后端 API 需求」。

### 4.3 数据加载策略

```
onShow() → if (authStore.isAdmin) → 并行请求：
  1. GET /admin/stats/daily               → 运营概览 + 正在直播数
  2. getDepartments({is_verified: false, page:1, size:1}) → 待审批科室数 total
  3. getAdminExperts({is_verified: false, page:1, size:1}) → 待审批专家数 total（如后端支持）
  4. getUnmappedExperts({page:1, size:1})  → 未归类专家数 total（✅ 已有 API）
```

- **加载态**：卡片显示骨架屏或「--」
- **错误态**：静默降级，显示「--」
- **刷新策略**：每次页面 `onShow` 时刷新（管理员可能频繁切换页面后回来）
- **Phase 1 降级**：`GET /admin/stats/daily` 未上线时，今日场次和正在直播显示「--」或总量占位
- **边界情况**：一个专家可以同时满足 `is_verified=false` 和 `department_id=null`，前端不关心重叠（两个卡片显示不同维度的计数），后端 `GET /admin/stats/daily` 需保证 `pending_experts` 和 `unmapped_experts` 相互独立（见 6.1 节 SQL）

## 6. 后端 API 需求

### 6.1 统一运营统计接口（P0）

**请求**：
```
GET /api/v1/admin/stats/daily
Authorization: Bearer <token>
```

**响应**：
```json
{
  "code": 200,
  "message": "success",
  "data": {
    "today_sessions": 8,
    "live_now": 2,
    "pending_departments": 2,
    "pending_experts": 1,
    "unmapped_experts": 3
  }
}
```

**字段说明**（按数据类型分组）：

#### 时间敏感型（每天自然归零）

| 字段 | 类型 | 说明 | SQL 示意 |
|------|------|------|---------|
| `today_sessions` | int | 今日总场次数（合并了"今日直播"概念，直播间和场次是 1:N，管理员只关心场次数） | `SELECT COUNT(*) FROM live_sessions WHERE DATE(start_time) = CURRENT_DATE` |
| `live_now` | int | 当前正在直播的房间数 | `SELECT COUNT(*) FROM live_rooms WHERE live_status = 'live'` |
| `today_new_rooms` | int | 今日新创建的直播间数（可选，辅助指标） | `SELECT COUNT(*) FROM live_rooms WHERE DATE(created_at) = CURRENT_DATE` |

#### 累积待办型（持续累积，处理后才减少）

| 字段 | 类型 | 说明 | SQL 示意 |
|------|------|------|---------|
| `pending_departments` | int | 待审核分类数（累积值，不限创建日期） | `SELECT COUNT(*) FROM expert_departments WHERE is_verified = false AND deleted_at IS NULL` |
| `pending_experts` | int | 待审核专家数（累积值，不限创建日期） | `SELECT COUNT(*) FROM experts WHERE is_verified = false AND deleted_at IS NULL` |
| `unmapped_experts` | int | 未映射专家数（department_id 为空，不限创建日期） | `SELECT COUNT(*) FROM experts WHERE department_id IS NULL AND deleted_at IS NULL` |

**重要说明**：

- 待审核计数不限制 `created_at` 范围。如果一个科室 3 天前创建仍未审核，它在每一天的统计中都应该被计入 `pending_departments`。这与 `today_live_rooms` 每天自然归零的行为有本质区别。
- `unmapped_experts` 是独立的待办项，与 `pending_experts` 不重叠。一个专家可以同时是"已审核但未分配分类"（`is_verified=true` 但 `department_id=null`），这种情况会计入 `unmapped_experts` 但不计入 `pending_experts`。

**优先级**：P0 — Phase 2 的依赖，无此接口管理摘要只能展示总量

### 6.2 今日场次列表（P1）

**请求**：
```
GET /api/v1/admin/sessions/today?page=1&size=20
Authorization: Bearer <token>
```

**响应**：
```json
{
  "code": 200,
  "message": "success",
  "data": {
    "items": [
      {
        "id": "uuid",
        "room_id": "room-uuid",
        "title": "场次标题",
        "status": "live",
        "start_time": "2026-07-23T09:00:00Z",
        "room_title": "直播间标题",
        "cover_url": "/uploads/covers/xxx.jpg",
        "expert_name": "主讲专家"
      }
    ],
    "total": 8,
    "page": 1,
    "size": 20
  }
}
```

**筛选规则**：`WHERE DATE(start_time) = CURRENT_DATE`。

**说明**：合并了"今日直播间"概念。管理摘要点击「今日场次」卡片后进入此页面，展示今日所有场次。房间相关元数据（标题、封面、专家）通过 JOIN `live_rooms` 和场次关联获取。

**优先级**：P1 — 前端可先用 `GET /rooms` + 按 `created_at` 前端过滤做降级方案
