> **创建日期**: 2026-09-06

> **硬性边界**: **严禁在生产复刻《标签管理V2-dev词表清理与重建-SQL方案》的全量 DELETE**；生产标签可能关联真实运营词/用户 resolve 词/真实场次绑定，全量清理不可逆

## 二、冲突处理决策矩阵（导入前逐项定案）

| 冲突类型 | 判定 | 处置 |
|---|---|---|
| 同名且 is_active=true（source=admin） | 词已存在且启用 | 跳过导入；核对 content safety 语义一致后可保留，或停用后走治理 |
| 同名且 is_active=true（source=user） | 主播自建词已启用 | 二选一：① 保留 user 词（停用 admin 版不导入）；② 停用 user 词后导入 admin 词（resolve 命中 active 优先、软删词不复活，停用 user 词即可让位——停用词仍占名，需按下方"改名腾名"处理才能同名重建） |
| 同名且 is_active=false（软删占名） | 停用词占用唯一 name | **改名腾名**：PUT /api/v1/admin/tags/{id} 将软删词 name 改为 `<原名>_disabled_<yyyyMMdd>`（TagUpdate 支持改名，schemas/content_management.py:48/52），释放原名后再导入 admin 词；改名后软删词不再命中 resolve"软删同名 400"干扰（名字已变） |
| 语义近义（不同名） | 运营判断 | 保留或停用由运营决策，不做自动合并 |
| 无冲突 | 直接导入 | 走 §三 |

## 三、导入流程（与 dev Phase 3 同法）

1. **导入前 GET 去重**：`GET /api/v1/admin/tags` 分页拉全量（含软删），按 name 比对生成导入清单；
2. 以运营管理员登录态逐条 `POST /api/v1/admin/tags {name}`（落 source=admin + created_by）；
   - 重名会返回 **500/1002**（非 4001）→ 一律人工复核；
   - 本通道**无内容安全校验** → 合规依赖词表清单 §一 自检；
3. 导入完成后（可选，建议分批）以运营/测试账号 `POST /api/v1/content/tags/resolve {name}` 逐条回归：200/created=false 通过；422 = 用户侧绑不上，须换词（先在管理端删除/改名该 admin 词再重建，注意软删占名规则）；
4. 逐条勾选《正式医学标签词表建议清单》"自检/导入"列留档。

## 四、日常治理指引

- **主播 resolve 自建词（source=user）**：运营在管理端按热度与质量决定"转正"（语义=认可保留）或"停用"（软删）；
- **停用词占名与同名重建**：软删不释放唯一 name。同名重建前先 **改名腾名**（见 §二 第 3 行）；若无 API 物理删除能力，勿试图直接重建同名（将 500）；
- **新增词**：一律过《正式医学标签词表建议清单》§一 自检（禁含子串 + 全局唯一），再按 §三 导入；
- **词表增量**：以《正式医学标签词表建议清单》为"运营认可词库"基线，运营增删时更新该清单并标注版本/日期；
- **禁止操作**：禁止在生产运行 dev 清理 SQL；禁止 DROP/TRUNCATE 相关表；禁止按前缀模糊 DELETE tags。
