## ⚡ 最小落地方案（P0 只做这些）

> 现网：软删已是 `is_active=false`；C 端商品 ` _get_brand` **已拒绝未启用品牌**。P0 = **查漏补缺读过滤 + 确认不删成员**，不做批量改商品状态。

| P0 | 动作 |
|----|------|
| 1 | 审计 C 端：房间上的品牌列表、品牌 content、其它挂靠入口是否过滤 `is_active`；漏则补 |
| 2 | 回归：软删后 `brand_members` 行仍在；硬删有引用仍拒 |
| 3 | 文档/注释写清：不可售= C 端不可见；**现网无订单** |

| P0 不做 | 原因 |
|---------|------|
| 软删时批量 `OFF_SALE` | 读过滤已够；复开还要手动上架反而麻烦 |
| 新表 / 新 API | |
| 订单/退款 | 无交易 |

## 📌 核心定位说明

### 1. 本文档的定位

品牌软删后：挂靠与商品对 **C 端不透出**；成员行保留；停新卖（无订单）。

### 2. 核心特点

- ✅ 能读过滤就不写扩散（V1.1）  
- ✅ 与 R5、无订单边界一致  

### 3. 业务价值

下架品牌不在 C 端继续露脸/露货；误软删可复开并保留成员。

## 🎯 设计要点与约定

### 1.1 软删除策略

| 表 | 品牌软删时 | 说明 |
|----|------------|------|
| `brands` | `is_active=false` | 既有 |
| `brand_topics` / `brand_rooms` | **保留行** | C 端过滤 |
| `brand_members` | **保留行** | P42 |
| `brand_products` | **不改行（P0）**；靠品牌 `is_active` 读过滤 | P43 |

### 1.2 变更决策记录

#### 决策 1：商品停售如何实现（V1.1）

| 方案 | 结论 |
|------|------|
| A：C 端读路径过滤 `brand.is_active`（商品接口已有） | ✅ **P0 唯一必做：审计补漏** |
| B：软删批量 OFF_SALE | ❌ P0 不做（过重；复开体验差） |

**P0 拍板**: 只保证 C 端读不到未启用品牌及其商品/挂靠；Admin 仍可见挂靠便于恢复。

#### 决策 2：与《14》SOP

| 原 SOP | 本包 |
|--------|------|
| 封主播人工下架商品 | 仍有效 |
| 品牌软删 | **靠 is_active + 读过滤** 即对 C 不可售 |

#### 决策 3：已售订单

现网无订单；将来历史订单保留、只停新卖。

## 3. API 接口设计

### 3.1 【修改·行为】软删品牌（ADMIN）

**Endpoint**: `DELETE /api/v1/admin/brands/{brand_id}?hard_delete=false`（以现网为准）

**描述**: `is_active=false`。P0 **不**批量改商品 status。

**执行流程**:

1. Admin 权限  
2. 软删 `is_active=false`  
3. **不** DELETE members / rooms / topics  
4. **不** 批量 OFF_SALE（V1.1）  
5. 返回  

### 3.2 C 端商品列表

维持现网：`_get_brand` 未启用 → 2001。P0 回归即可。

### 3.3 房间/挂靠只读

审计过滤 `is_active`；Admin 可看未启用以便恢复。

### 3.4 硬删 / 复开

硬删规则不变。复开 `is_active=true` 后挂靠自然恢复；商品若仍 ON_SALE 且品牌已启用则 C 端可售（读过滤放行）——**这是最小方案的友好点**。

---

## 4. 执行流程详细说明

### 4.1 软删全链路

```
1. Admin 软删品牌
2. is_active=false
3. members/rooms/topics/products 行保留（不批量改商品）
4. C 端读路径过滤未启用品牌
5. 无订单需处理
```

### 4.2 与封主播 SOP

```
封主播 → 人工下架相关商品（14-V2）
品牌软删 → is_active + C 端过滤即可
```

## 6. 性能优化建议

### 6.1 数据库优化

- `brand_products(brand_id, status)` 索引若已有则复用；批量 UPDATE 按 brand_id  

### 6.2 缓存策略

- 品牌详情/商品列表缓存键含 `is_active` 或软删时主动失效  

### 6.3 应用层优化

- 房间多品牌展示：批量查品牌 id 后内存过滤 `is_active`，避免 N+1
