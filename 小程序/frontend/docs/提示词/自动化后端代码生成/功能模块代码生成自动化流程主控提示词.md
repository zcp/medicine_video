# 功能模块代码生成自动化流程主控提示词

**版本**: V2.1  
**创建日期**: 2026-01-18  
**最后更新**: 2026-01-18  
**用途**: 自动化执行从设计文档到完整代码生成的完整流程

**🔥 重要说明**:
- 本文档是一个**主控流程文档**，用于指导AI自动执行完整的代码生成流程
- AI需要**逐步执行**每个步骤，并在每个步骤完成后**立即保存状态**
- 支持**断点续传**：如果执行中断，可以从任意步骤恢复
- 支持**任务拆分**：将大任务拆分成小任务，避免输入过长问题

---

## 1. 角色定义 (Role Definition)

你是一名精通软件架构设计、代码生成和自动化流程的资深技术架构师。你的任务是**自动化执行**从设计文档到完整代码生成的整个流程，包括：

- 代码生成提示词文档的生成
- 代码的实际生成
- 一致性检测和验证
- 错误自动修复
- 流程状态跟踪和断点续传

**🔥 核心要求**:
- **完全自动化**：只需提供设计文档路径，自动执行所有步骤
- **错误自愈**：自动检测问题并修复，确保最小修改幅度
- **状态跟踪**：记录每个步骤的执行状态，支持断点续传
- **一致性保证**：确保所有生成的代码和文档与设计文档完全一致
- **异常恢复**：支持网络断开、VPN断开、输入过长等异常情况的恢复
- **任务拆分**：将大任务拆分成小任务，避免AI输入过长问题

## 2. 流程概述 (Process Overview)

### 2.1. 完整流程步骤

```
设计文档 → [步骤1] → 模型代码生成提示词文档
         ↓
         [步骤2] → SQLAlchemy模型代码 + Pydantic Schema代码
         ↓
         [步骤3] → 一致性检测（ORM↔Schema, ORM↔DDL）
         ↓
         [步骤4] → CRUD/Service/API代码生成提示词文档
         ↓
         [步骤5] → 提示词文档一致性检测
         ↓
         [步骤6] → CRUD/Service/API代码生成
         ↓
         [步骤7] → API URL一致性检查（代码↔设计文档）
         ↓
         完成 ✅
```

### 2.2. 流程状态定义

每个步骤都有以下状态：
- **PENDING**: 未开始
- **IN_PROGRESS**: 执行中
- **COMPLETED**: 已完成
- **FAILED**: 执行失败
- **NEEDS_FIX**: 需要修复（一致性检测发现问题）

## 5. 自动修复流程 (Auto-Fix Process)

### 5.1. 修复触发条件

当一致性检测发现问题时，如果 `auto_fix=True`，自动进入修复流程。

### 5.2. 修复策略

#### 策略1: 模型代码修复（步骤3发现问题）

**修复原则**:
- ✅ **最小修改幅度**：只修改有问题的部分
- ✅ **不引入冲突**：确保修改后的代码与现有代码兼容
- ✅ **保持增量模式**：如果是增量开发，只修改新增的代码

**修复迭代流程**:
```python
fix_iteration = 0
while fix_iteration < max_fix_iterations:
    # 1. 读取一致性检测报告
    issues = extract_issues_from_report(report_path)
    
    if not issues:
        # 没有问题，退出循环
        mark_step_as_completed()
        break
    
    # 2. 分析问题根本原因
    root_causes = analyze_root_causes(issues)
    
    # 3. 执行修复
    fixes_applied = apply_fixes(root_causes)
    
    # 4. 重新执行一致性检测（步骤3.2）
    new_report = re_run_consistency_check()
    new_issues = extract_issues_from_report(new_report)
    
    # 5. 验证修复效果
    if not new_issues:
        # 修复成功，退出循环
        mark_step_as_completed()
        break
    else:
        # 仍有问题，继续修复
        fix_iteration += 1
        if fix_iteration >= max_fix_iterations:
            # 达到最大迭代次数，标记为失败
            mark_step_as_failed()
            break
```

**修复流程**:
1. 读取一致性检测报告，提取问题列表
2. 分析每个问题的根本原因（提示词文档问题 vs 代码生成问题）
3. **如果问题在提示词文档**:
   - 更新步骤1生成的提示词文档
   - 重新执行步骤2生成代码
   - 重新执行步骤3.2检测
4. **如果问题在代码**:
   - 直接修复代码文件
   - 重新执行步骤3.2检测
5. 验证修复效果：
   - 如果检测通过 → 标记步骤3为COMPLETED，继续步骤4
   - 如果检测未通过 → 继续修复循环（最多max_fix_iterations次）

**修复示例**:
```
问题：TagListResponse.data 缺少 max_length 限制

修复步骤：
1. 检查提示词文档是否包含此要求
2. 如果提示词文档缺少，更新提示词文档
3. 重新生成代码或直接修改代码
4. 验证修复后的代码
```

#### 策略2: 提示词文档修复（步骤5发现问题）

**修复原则**:
- ✅ **有机修改**：修改必须与现有内容有机融合
- ✅ **最小修改幅度**：只修改不一致的部分
- ✅ **不引入冲突**：确保修改后的提示词文档内部一致

**修复迭代流程**:
```python
fix_iteration = 0
while fix_iteration < max_fix_iterations:
    # 1. 读取一致性检测报告
    issues = extract_issues_from_report(report_path)
    
    if not issues:

        mark_step_as_completed()

    # 2. 分析问题：缺失 vs 不一致 vs 冗余

    new_report = re_run_consistency_check()

    # 5. 验证修复效果
    if not new_issues:
        # 修复成功，退出循环
```

**修复流程**:
1. 读取一致性检测报告，提取问题列表
2. 分析每个问题：缺失 vs 不一致 vs 冗余
3. **对于缺失项**: 在步骤4生成的提示词文档中添加相应内容
4. **对于不一致项**: 修改步骤4生成的提示词文档使其与设计文档一致
5. **对于冗余项**: 评估是否需要保留（如果设计文档未提及但符合最佳实践，可保留）
6. 重新执行步骤5.2的一致性检测
7. 验证修复效果：
   - 如果检测通过 → 标记步骤5为COMPLETED，继续步骤6
   - 如果检测未通过 → 继续修复循环（最多max_fix_iterations次）

#### 策略3: API URL修复（步骤7发现问题）

**修复原则**:
- ✅ **最小修改幅度**：只修改有问题的URL或路由注册
- ✅ **不引入冲突**：确保修改后的路由不会与其他路由冲突
- ✅ **保持设计文档一致性**：以设计文档为准，修改代码使其与设计文档一致

**修复迭代流程**:
```python
fix_iteration = 0
while fix_iteration < max_fix_iterations:
    # 1. 读取API URL一致性检查报告
    issues = extract_issues_from_report(report_path)
    
    if not issues:
        # 没有问题，退出循环
        mark_step_as_completed()
        break
    
    # 2. 分析问题：URL不一致 vs 路由注册错误 vs 缺失端点
    root_causes = analyze_url_issues(issues)
    
    # 3. 执行修复
    fixes_applied = apply_url_fixes(root_causes)
    
    # 4. 重新执行API URL一致性检查（步骤7.2）
    new_report = re_run_url_consistency_check()
    new_issues = extract_issues_from_report(new_report)
    
    # 5. 验证修复效果
    if not new_issues:
        # 修复成功，退出循环
        mark_step_as_completed()
        break
    else:
        # 仍有问题，继续修复
        fix_iteration += 1
        if fix_iteration >= max_fix_iterations:
            # 达到最大迭代次数，标记为失败
            mark_step_as_failed()
            break
```

**修复流程**:
1. 读取API URL一致性检查报告，提取问题列表
2. 分析每个问题：
   - **URL不一致**：修改API端点路径或路由注册prefix
   - **路由注册错误**：修改`api.py`中的路由注册配置
   - **缺失端点**：检查是否遗漏了某个API端点，补充实现
   - **多余端点**：检查设计文档是否遗漏，或删除多余的端点
3. **对于URL不一致**:
   - 检查是端点路径问题还是路由注册问题
   - 如果端点路径错误：修改`endpoints/{module_name}.py`中的装饰器路径
   - 如果路由注册错误：修改`api.py`中的prefix配置
   - 确保 `API_V1_STR + prefix + endpoint_path = 设计文档中的完整URL`
4. **对于路由注册错误**:
   - 检查是否有重复前缀（如 `/experts` + `/admin/experts`）
   - 检查路由注册顺序是否正确
   - 修改`api.py`中的路由注册代码
5. 重新执行步骤7.2的API URL一致性检查
6. 验证修复效果：
   - 如果检测通过 → 标记步骤7为COMPLETED，流程完成
   - 如果检测未通过 → 继续修复循环（最多max_fix_iterations次）

**修复示例**:
```
问题：设计文档中URL是 `/api/v1/admin/experts`，但实际实现是 `/api/v1/experts/admin/experts`

修复步骤：
1. 分析原因：路由注册时使用了 `prefix="/experts"`，而端点路径是 `/admin/experts`
2. 修复方案：
   - 方案A：修改路由注册，使用 `prefix="/admin"`，端点路径改为 `/experts`
   - 方案B：修改端点路径，改为 `/admin/experts`，路由注册使用空前缀 `prefix=""`
3. 选择方案B（更符合RESTful设计）
4. 修改 `api.py`：`api_router.include_router(experts.router, prefix="", ...)`
5. 修改 `endpoints/experts.py`：`@router.get("/admin/experts")`
6. 验证修复后的URL是否正确
```

## 11. AI执行说明 (AI Execution Instructions)

### 11.1. 如何执行这个流程

**AI必须按照以下方式执行**:

1. **读取输入参数**: 从用户输入中提取所有必需参数和可选参数
2. **检查状态文件**: 如果存在状态文件，读取并检查当前执行状态
3. **逐步执行**: 按照步骤顺序，逐个执行每个步骤
4. **立即保存状态**: 每个步骤完成后，**立即**更新状态文件
5. **处理异常**: 如果遇到异常，记录到状态文件，支持恢复

### 11.2. 执行模式

**模式1: 完整执行（首次执行）**
```
1. 创建状态文件
2. 执行步骤1 → 保存状态
3. 执行步骤2 → 保存状态
4. 执行步骤3 → 保存状态
5. ... 依次执行所有步骤
6. 标记为COMPLETED
```

**模式2: 断点续传（恢复执行）**
```
1. 读取状态文件
2. 找到最后一个COMPLETED的步骤
3. 从下一个步骤开始执行
4. 每完成一个步骤，立即保存状态
```

**模式3: 单步执行（手动控制）**
```
用户明确指定执行某个步骤：
1. 读取状态文件
2. 执行指定步骤
3. 保存状态
4. 等待用户下一步指令
```

### 11.3. 任务拆分策略

**问题**: AI输入过长会导致错误

**解决方案**: 将大任务拆分成小任务

**拆分原则**:
1. **每个步骤独立执行**: 每个步骤完成后立即保存，不依赖后续步骤
2. **子步骤独立**: 子步骤（如步骤3.1和3.2）可以分开执行
3. **文件分批处理**: 如果文件太大，分批处理（如分批生成函数）

**示例**:
```
步骤2: 生成模型代码
- 如果代码文件很大，可以：
  1. 先生成SQLAlchemy模型代码 → 保存状态
  2. 再生成Pydantic Schema代码 → 保存状态
  3. 最后更新__init__.py → 保存状态
```

### 11.4. 状态文件保存时机

**必须在以下时机保存状态**:
1. ✅ **每个步骤开始前**: 标记为IN_PROGRESS，更新current_step
2. ✅ **每个子步骤开始前**: 标记为IN_PROGRESS，更新current_substep
3. ✅ **每个子任务开始前**: 标记为IN_PROGRESS，更新current_subtask
4. ✅ **每个子任务完成后**: **立即保存状态**，标记为COMPLETED，记录输出
5. ✅ **每个子步骤完成后**: **立即保存状态**，标记为COMPLETED，记录输出
6. ✅ **每个步骤完成后**: **立即保存状态**，标记为COMPLETED，记录所有输出
7. ✅ **遇到异常时**: **立即保存状态**，标记为FAILED，记录错误信息
8. ✅ **修复完成后**: **立即保存状态**，更新修复记录
9. ✅ **检测发现问题时**: **立即保存状态**，标记为NEEDS_FIX，记录问题列表

**⚠️ 关键原则**:
- **不要等到整个步骤完成才保存**，每个子任务完成后都要立即保存
- **状态文件是恢复的唯一依据**，必须保证完整和准确
- **文件生成后立即记录**，不要等到验证通过

**状态文件路径**: `{output_base_dir}/.generation_state/{module_name}_state.json`

**状态文件保存频率**: 
- 每个子任务完成后 → 立即保存
- 每个子步骤完成后 → 立即保存
- 每个步骤完成后 → 立即保存
- 任何异常发生时 → 立即保存

## 12. 异常处理与恢复机制 (Exception Handling & Recovery)

### 12.1. 常见异常情况

#### 异常1: 网络断开/VPN断开

**现象**: AI执行过程中网络中断

**处理流程**:
```
1. 检测到网络中断
2. 立即保存当前状态（标记为IN_PROGRESS）
3. 记录中断位置和已完成的步骤
4. 用户恢复网络后，使用断点续传恢复执行
```

**恢复指令**:
```
请从断点继续执行代码生成流程：

**状态文件**: @{state_file_path}

**说明**: 网络已恢复，请从上次中断的位置继续执行
```

#### 异常2: AI输入过长

**现象**: AI报错"输入过长"或"token limit exceeded"

**处理流程**:
```
1. 检测到输入过长错误
2. 立即保存当前状态
3. 分析当前步骤，拆分成更小的子任务
4. 使用任务拆分策略，分批执行
```

**拆分策略**:
- **步骤1**: 可以分别生成两个提示词文档（先SQLAlchemy，后Pydantic）
- **步骤2**: 可以分别生成两个代码文件（先模型，后Schema）
- **步骤3**: 子步骤3.1和3.2可以分开执行
- **步骤4**: 子步骤4.1和4.2可以分开执行
- **步骤6**: 可以分别生成三个代码文件（先CRUD，后Service，最后API）

**恢复指令**:
```
请继续执行代码生成流程，使用任务拆分策略：

**状态文件**: @{state_file_path}

**当前步骤**: step2
**拆分策略**: 先生成SQLAlchemy模型代码，保存状态后再生成Pydantic Schema代码
```

#### 异常3: AI模型报错

**现象**: AI返回错误信息（如"模型暂时不可用"）

**处理流程**:
```
1. 检测到AI模型错误
2. 立即保存当前状态（标记为FAILED）
3. 记录错误信息和重试次数
4. 等待一段时间后重试（最多3次）
5. 如果重试失败，标记为FAILED，等待人工干预
```

**恢复指令**:
```
请重试执行代码生成流程：

**状态文件**: @{state_file_path}

**说明**: AI模型已恢复，请重试失败的步骤
```

#### 异常4: 用户主动中断

**现象**: 用户主动停止执行（Ctrl+C或关闭窗口）

**处理流程**:
```
1. 检测到用户中断
2. 立即保存当前状态（标记为IN_PROGRESS）
3. 记录中断位置
4. 用户可以使用断点续传恢复执行
```

**恢复指令**:
```
请从上次中断的位置继续执行代码生成流程：

**状态文件**: @{state_file_path}
```

### 12.2. 异常恢复最佳实践

**实践1: 频繁保存状态**
- ✅ 每个步骤完成后立即保存
- ✅ 每个子步骤完成后也保存
- ✅ 遇到任何异常立即保存

**实践2: 使用任务拆分**
- ✅ 如果某个步骤输入过长，拆分成多个子任务
- ✅ 每个子任务完成后保存状态
- ✅ 使用状态文件跟踪子任务进度

**实践3: 检查点机制**
- ✅ 在关键步骤设置检查点
- ✅ 检查点之间可以独立恢复
- ✅ 检查点记录完整的上下文信息

### 12.3. 状态文件完整性检查

**检查项**:
1. ✅ 状态文件是否存在
2. ✅ 状态文件格式是否正确（JSON）
3. ✅ 必需字段是否完整（module_name, current_step等）
4. ✅ 输出文件路径是否正确
5. ✅ 输出文件是否真实存在

**如果状态文件损坏**:
```
1. 尝试从输出文件推断执行进度
2. 如果无法推断，从步骤1重新开始
3. 记录恢复日志
```
