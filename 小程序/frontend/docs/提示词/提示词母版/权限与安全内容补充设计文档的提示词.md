**当网络中断或模型响应慢时，按以下流程恢复**：

1. **读取执行状态文件**
   - 读取 `设计文档权限与安全内容补充-执行状态.json`
   - 确定当前处理的文档索引（`current_document_index`）
   - 确定当前执行的步骤（`current_step`）

2. **检查当前文档状态**
   - 如果状态为"✅ 已完成"，跳过该文档，处理下一个
   - 如果状态为"🔄 处理中"，从上次中断的步骤继续执行
   - 如果状态为"⚠️ 部分完成"，检查已完成步骤，从未完成的步骤继续

3. **继续执行**
   - 从 `current_step` 开始继续执行
   - 每完成一个步骤，更新状态文件
   - 完成所有步骤后，更新文档状态为"✅ 已完成"

4. **处理下一个文档**
   - 当前文档完成后，`current_document_index` + 1
   - 开始处理下一个文档

> **原则**：新增内容与现有“统一认证规范”“JWT说明”“日志脱敏简要”形成逻辑承接，不重复原文，不引入冲突。

### 4.1 权限设计内容补充（新增章节）
**建议插入位置**：在"文档规范说明"章节之后，或在"设计要点与约定"章节之后新增：

#### `X. 权限设计规范`（X为合适的章节编号）

**X.1 架构分层原则（架构红线）**
- API 层（Controller/Dependency）：只负责 Authentication（你是谁）
- Service 层（Domain Logic）：全权负责 Authorization（你能做什么）
- CRUD 层（Repository）：SQL 层面权限过滤（WHERE 条件实现）
- 关键约束：
  - API 层不做权限判断（不做授权拒绝）
  - Service 层通过权限守卫函数完成鉴权
  - CRUD 层禁止内存过滤，必须 SQL 过滤

**X.2 双轨鉴权模式**
- Strict Auth（强制鉴权）
  - 无 Token → 401
  - Token 无效/过期 → 401
  - 适用：所有写操作（POST/PATCH/DELETE）与敏感读
  - 依赖：`get_current_user`
- Optional Auth（可选鉴权）
  - 无 Token → 返回 None（匿名）
  - Token 无效/过期 → **401（严禁降级匿名）**
  - 适用：GET
  - 依赖：`get_current_user_optional`
- **关键提示**：Optional Auth 下 Token 无效必须 401，否则会导致“登录态用户过期后看不到私有资源”，引发前端状态错乱。

**X.3 Service 层权限守卫函数**

**类型 1：管理员权限检查**
```python
def _check_admin_permission(self, user_role: str) -> None:
    """检查管理员权限"""
    if user_role not in ['ADMIN', 'SUPERADMIN']:
        raise PermissionDeniedException("权限不足，需要管理员权限")
```

**类型 2：写权限检查（资源所有权）**
```python
def _check_write_permission(self, resource, user_id: UUID, user_role: str) -> None:
    """检查写操作权限（资源所有权）"""
    # Admin 上帝视角：通过
    if user_role in ['ADMIN', 'SUPERADMIN']:
        return
    # Owner 权限：通过
    if resource.user_id == user_id:
        return
    # 其他情况：拒绝
    raise PermissionDeniedException("权限不足，无权操作该资源")
```

**类型 3：资源可见性检查（404伪装）**
```python
def _check_resource_visibility(self, resource, user_id: Optional[UUID], user_role: Optional[str]) -> None:
    """检查资源可见性（404伪装）"""
    # 公开资源：所有人可访问
    if resource.is_private == False:  # 或 resource.is_active == True
        return
    # 未登录用户：返回 404（伪装）
    if not user_id:
        raise NotFoundException("资源不存在")
    # Admin 上帝视角：通过
    if user_role in ['ADMIN', 'SUPERADMIN']:
        return
    # Owner 权限：通过
    if resource.user_id == user_id:
        return
    # 其他情况：返回 404（伪装）
    raise NotFoundException("资源不存在")
```

**⚠️ 关键约束**：对无权访问的 Private 资源，必须返回 **404 Not Found**，严禁返回 403，以防止恶意用户通过枚举 ID 探测资源的存在性。

**X.4 CRUD 层权限过滤（SQL 强制）**

**核心原则**：
- **禁止内存过滤**：严禁在 Python 代码中先查询所有数据，再用 if 判断过滤
- **SQL 层面过滤**：必须在 WHERE 条件中应用权限过滤逻辑
- **业务与权限 AND 关系**：业务筛选条件与权限过滤条件必须用 AND 连接

**权限过滤逻辑**：
- **Admin 查询**（`role in ['ADMIN', 'SUPERADMIN']`）：无权限过滤，可查看所有资源
- **Regular User 查询**（`role == 'REGULAR'`）：`WHERE is_active=true` 或 `WHERE status='published'`
- **Anonymous 查询**（`role is None`）：`WHERE is_active=true` 或 `WHERE status='published'`

**方法签名规范**：
```python
async def get_tags_paginated(
    db: AsyncSession,
    page: int = 1,
    size: int = 20,
    search: Optional[str] = None,
    # ← 权限参数
    current_user_id: Optional[UUID] = None,
    role: Optional[str] = None
) -> Tuple[List[Tag], int]:
```

**实现示例**：
```python
# 1. 先应用业务筛选条件
business_filters = []
if search:
    business_filters.append(Tag.name.ilike(f'%{search}%'))

# 2. 再应用权限过滤条件（根据用户身份决定可见范围）
permission_filters = []
if role in ['ADMIN', 'SUPERADMIN']:
    # 管理员：无权限过滤
    pass
else:
    # Regular User / Anonymous：仅查看激活资源
    permission_filters.append(Tag.is_active == True)

# 3. 合并业务筛选条件和权限过滤条件（AND关系）
all_filters = business_filters + permission_filters
if all_filters:
    query = query.where(and_(*all_filters))
```

**X.5 用户身份提取规范**

**JWT Payload 结构**：

```json
{
  "user_id": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
  "role": "REGULAR",
  "type": "access",
  "exp": 1234567890
}
```

**代码提取方式**：
```python
# ✅ 正确做法（与v6主文档一致）
current_user: Dict = Depends(get_current_user)  # 或 get_current_user_optional
user_id = UUID(current_user["user_id"])  # 使用 user_id 而非 sub
user_role = current_user.get("role", "REGULAR").upper()

# ❌ 错误做法（不要使用JWT标准字段名）
# user_id = UUID(current_user["sub"])  # 系统中不存在此字段
```

**说明**：

- `user_id`：系统统一使用的用户唯一标识（public_id），**非 JWT 标准字段 `sub`**
    
- `role`：用户角色枚举值（如 `REGULAR`、`ADMIN`、`SUPERADMIN`）
    
- `type`：Token 类型（如 `access`）
    
- `exp`：Token 过期时间戳
    

**⚠️ 重要提示**：本系统统一使用 `user_id` 字段，而非 JWT 标准的 `sub` 字段。这是一个有意识的设计决策，已在所有文档中统一执行。

**Y.1 环境变量与配置管理规范（合并版）**

**环境变量文件结构**：
- 使用 `.env.example` 作为模板文件
- 所有敏感信息通过环境变量读取
- `.env` 文件必须添加到 `.gitignore`

**环境变量命名规范**：
- 使用大写字母和下划线：`POSTGRES_PASSWORD`
- 使用有意义的名称：`CORS_ORIGINS` 而非 `CORS`
- 分组前缀：`POSTGRES_*`, `JWT_*`, `CELERY_*`

**必需环境变量清单**：
- `POSTGRES_PASSWORD`：数据库密码（生产环境必须设置）
- `JWT_SECRET_KEY`：JWT密钥（生产环境必须设置，至少32字符）
- `CORS_ORIGINS`：CORS允许的域名（生产环境必须设置具体域名）

**配置验证要求**：
- 启动时验证必需的环境变量是否设置
- 验证敏感配置的安全性（如JWT密钥长度）
- 验证生产环境配置（如CORS不能为 `*`）

**配置验证实现示例**：
```python
def _validate_database_config(self):
    """验证数据库配置完整性"""
    if not self.POSTGRES_PASSWORD:
        raise ValueError(
            "POSTGRES_PASSWORD 环境变量未设置。"
            "生产环境必须设置此变量，不允许使用默认值。"
        )

def _validate_jwt_config(self):
    """验证JWT配置完整性"""
    if not self.JWT_SECRET_KEY:
        raise ValueError(
            "JWT_SECRET_KEY 环境变量未设置。"
            "生产环境必须设置此变量，且长度应至少32个字符。"
        )
    if len(self.JWT_SECRET_KEY) < 32:
        raise ValueError(
            "JWT_SECRET_KEY 长度不足32个字符，存在安全风险。"
        )
```

- 禁止：
  - 代码硬编码密码/密钥
  - 日志打印 Token/密码/连接串
  - 错误消息回传敏感内容
  - `.env` 入库

  - 统一通过环境变量/密钥服务读取
  - 提供 `.env.example`
  - 启动验证必需配置

**Y.3 日志脱敏规范（补全细则）**

**日志脱敏要求**：
- 记录日志时，不输出敏感信息（如：用户密码、Token、数据库连接URL等）
- 使用INFO级别记录正常业务操作
- 使用WARNING级别记录权限拒绝和业务异常
- 使用ERROR级别记录系统异常

**日志脱敏实现载体要求**：

为确保日志脱敏策略在系统中得到一致、可靠的执行，必须通过以下三类载体统一实现：

1. **日志脱敏工具函数**
   - 提供统一的脱敏工具函数（如 `sanitize_log(data)`），用于对日志内容中的敏感字段进行处理
   - 业务代码禁止自行实现零散的脱敏逻辑，必须复用统一工具函数

2. **敏感信息识别规则**
   - 基于字段名与内容模式进行识别，包括但不限于：
     - `password`、`secret`、`token`、`authorization`、`api_key`
   - 对匹配到的敏感信息进行掩码或移除处理，而非原样输出

3. **统一接入位置**
   - 日志脱敏逻辑应在日志格式化器（logging formatter）或中间件层统一接入
   - 禁止在各业务模块中分散处理，以避免遗漏和实现不一致

**日志脱敏实现示例**：
```python
# 安全日志：不打印完整连接URL（包含密码）
logger.info(
    f"尝试连接数据库: "
    f"server={settings.POSTGRES_SERVER}, "
    f"port={settings.POSTGRES_PORT}, "
    f"database={settings.POSTGRES_DB}, "
    f"user={settings.POSTGRES_USER}"
    # 不打印密码
)
```

**Y.4 错误消息脱敏规范**

**异常处理要求**：
- 在异常处理中，不要暴露敏感信息
- 不要打印完整的异常信息（可能包含连接字符串）
- 使用通用的错误消息

**错误消息脱敏示例**：
```python
# ✅ 正确做法
try:
    # 数据库操作
except Exception as e:
    logger.error(f"数据库操作失败: {type(e).__name__}")
    raise HTTPException(status_code=500, detail="内部服务器错误")

# ❌ 错误做法
try:
    # 数据库操作
except Exception as e:
    logger.error(f"数据库操作失败: {e}")  # 可能包含敏感信息
    raise HTTPException(status_code=500, detail=str(e))  # 暴露敏感信息
```

- 确保编号连续，不跳跃

### 10.2 现有内容识别

**不同文档的现有内容可能不同**：

- **专家模块**：已有"1.4 安全与配置规范"章节（第313-336行），需要扩展而非新增
- **品牌模块**：已有"1.4 安全与配置规范"章节（第257-278行），需要扩展而非新增
- **其他模块**：可能只有简要说明，需要新增完整章节

**处理原则**：
- 仔细阅读文档，识别现有安全相关内容
- 如果已有安全章节，则扩展该章节
- 如果只有简要说明，则新增完整章节
- 避免重复，保持逻辑连贯

### 10.3 模块特性适配

**不同模块可能有不同的权限需求**：

- **内容管理模块**：需要标签/分类的可见性检查（404伪装）
- **专家模块**：可能需要专家可见性检查
- **品牌模块**：品牌信息通常公开，可能不需要404伪装
- **用户偏好与通知模块**：用户只能访问自己的偏好和通知
- **用户行为模块**：用户只能访问自己的收藏、观看历史、订阅
- **首页与搜索模块**：主要是公开接口，权限需求较少

**处理原则**：
- 根据模块特性，选择适用的权限守卫函数
- 不是所有模块都需要404伪装（仅适用于有Private资源的模块）
- 不是所有模块都需要CRUD层权限过滤（仅适用于有权限过滤需求的模块）
- 保持通用性，但允许模块特定的适配

### 10.3.1 权限需求差异识别流程

**在执行步骤1的"权限需求差异分析"时，按以下流程进行**：

1. **识别模块权限特性**（必须执行）：
   - **是否有私有资源？**
     - 检查文档中是否有 `is_private`、`status`（非published状态）、`is_active`（False状态）等字段
     - 如果有 → 需要404伪装机制
     - 如果全部公开 → 不需要404伪装
   - **是否有系统级资源？**
     - 检查文档中是否有需要管理员权限的操作（如创建/删除系统配置）
     - 如果有 → 需要管理员权限检查函数
     - 如果没有 → 不需要管理员权限检查函数
   - **是否有用户专属资源？**
     - 检查文档中是否有 `user_id` 字段，且资源只能由创建者访问
     - 如果有 → 需要写权限检查函数
     - 如果没有 → 不需要写权限检查函数
   - **是否需要CRUD层权限过滤？**
     - 检查文档中是否有列表查询接口，且需要根据用户身份过滤结果
     - 如果有 → 需要CRUD层权限过滤
     - 如果全部公开 → 不需要CRUD层权限过滤

2. **对比标准模板**（必须执行）：
   - **标准模板要求的所有权限功能**：
     - 架构分层原则（API/Service/CRUD职责分工）
     - 双轨鉴权模式（Strict Auth / Optional Auth）
     - 3类权限守卫函数（管理员权限检查、写权限检查、资源可见性检查）
     - CRUD层权限过滤（SQL层面过滤）
     - 用户身份提取规范（`user_id` 而非 `sub`）
   - **对比目标文档的实际需求**：
     - 逐项检查每个功能是否适用于目标模块
     - 标记为：✅需要 / ❌不需要 / ⚠️部分需要
   - **记录差异**：
     - 在状态文件中记录差异分析结果
     - 格式：`{"permission_requirements_diff": {"架构分层原则": "需要", "404伪装": "不需要", ...}}`

3. **选择性应用策略**（在步骤3中执行）：
   - **对于不需要的功能**：
     - 在相应子章节中说明"本模块不适用"或"本模块为公开资源，无需404伪装"
     - 示例：品牌模块的权限设计规范中，资源可见性检查子章节可以说明"品牌信息通常公开，无需404伪装"
   - **对于部分需要的功能**：
     - 说明适用场景和限制条件
     - 示例：用户行为模块的CRUD层权限过滤可以说明"仅适用于用户专属资源的查询"
   - **对于完全需要的功能**：
     - 完整补充标准内容
     - 确保与标准模板保持一致
