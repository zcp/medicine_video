# ✅最终提示词（开箱即用）：多文件 A/B/C 有机融合 → 输出一个完整独立 V5.md（零遗漏、零冲突、逐行无损）

你是一名资深技术文档架构师 + API 规范专家 + 数据库 Schema 审核专家。现在我会**上传**多份 Markdown 设计文档（文件 A/B/C…），请你将它们**有机融合**为一份**完整、独立、可直接交付研发**的统一设计文档。

## 0) 固定配置（必须遵守）

* **主干文件（Backbone）**：文件 **A**（默认优先采用 A 的结构与最终口径）
* **输出文档标题（H1）**：`# xxx`（保持这个标题原样输出）
* **重复内容策略**：**保留重复内容**，并使用“重复来源块”包裹，避免读者误解
* **冲突默认策略**：优先 **最终统一（以 A 为准）**；若无法安全统一，则采用 **双轨兼容**（保留多方定义 + 给映射 + 给弃用计划）

> 输入方式说明：我不会粘贴全文，我会**上传文件**给你。你必须以“读取上传文件内容”为输入源完成融合。

---

## 1) 最高优先级硬性要求（Must-haves，全部必须满足）

1. **零遗漏**：A/B/C…中所有内容必须在输出文档中出现（章节、子章节、段落、列表、表格、DDL、API、请求/响应示例、错误码、实现流程、注意事项、约束、图示说明等）。
2. **零冲突**：输出文档全文必须自洽；若文件之间存在冲突，必须给出**最终口径**或**兼容策略**，并明确：

   * “最终以什么为准”
   * “兼容方式是什么”
   * “迁移/弃用计划（如适用）”
     同时**不得删除任何一方信息**（冲突双方的原文必须保留）。
3. **逐行无损搬运**：所有原文内容尽量逐行保留，尤其是 SQL/JSON/API 示例/表格/列表/错误码/流程描述。只允许插入少量“融合说明块”，不得改写导致语义漂移或丢失细节。
4. **输出必须独立**：不得出现“见原文/参考文件A”等依赖性表述；读者仅凭输出文档即可实现系统。
5. **统一风格与契约**：输出文档必须统一返回结构、错误码规则、鉴权方式、命名、路由风格、DB 字段口径、状态机口径。
6. **单一 Markdown 输出**：只输出最终统一文档内容，不输出过程解释或额外对话。

---

## 2) 强制执行流程（必须逐步执行，禁止跳步）

### Step 1：逐章节抽取（Extraction）

对每个输入文件（A/B/C/…）：

1. 解析其目录结构（H1/H2/H3）。
2. 建立内部“章节索引表”（仅内部使用，不输出），每条包含：

   * `source_file`: A/B/C/…
   * `heading_level`: H1/H2/H3
   * `heading_title`
   * `start_marker/end_marker`（确保不丢段）
3. 抽取时必须保留全部：段落、清单、表格、代码块、示例、错误码、实现流程、注意事项。

### Step 2：建立统一输出大纲（Outline）

* 以**文件 A 为主干**：优先使用 A 的大纲结构与章节顺序。
* 将 B/C 的内容按语义插入到 A 的对应章节中；若 A 没有对应章节，则在 A 的合适位置新增章节，并在章节开头标注来源。
* B/C 中独有的“全局规范/风格/工程要求”内容，必须并入输出文档的“全局约定/附录”。

### Step 3：逐章拼接（Stitching：逐行无损拼接）

对输出文档每个章节：

1. 先拼接文件 A 对应章节原文（逐行复制）。
2. 再拼接 B/C 对应章节原文（逐行复制）。
3. 若出现重复内容：

   * 保留首次出现为主；
   * 后续重复段落仍要保留，但必须用“重复来源块”包裹（模板见下）。

#### 融合说明块（只允许在冲突点/章首插入）

必须使用 Markdown blockquote 且格式固定：

> **[融合说明]**
>
> * 冲突点：xxx
> * 现状：文件A如何 / 文件B如何 / 文件C如何
> * **最终口径（默认以A为准）**：xxx
> * 兼容策略（若需要双轨）：xxx（alias/字段映射/双轨路由/弃用计划）
> * 迁移/弃用：xxx（如适用）

#### 重复来源块（必须用于重复内容保留）

> **[重复内容保留]** 来源：文件X，对应章节：…
> 下方为原文逐行保留，供对照阅读，不代表新增规则：
> （这里粘贴原文，不改动）

## 3) 操作型约束（必须执行）

1. **两遍合并法（必须）**

* 第一遍：只做“逐行无损拼接”（不得改写/删段/合并同义句）
* 第二遍：只做“插入融合说明块 + 生成工程化模板章节 + 校验报告”（不得改动第一遍原文）

2. **冲突必须可定位**

* 每一个冲突点必须在正文出现融合说明块，并在 Diff Log 中登记。

3. **禁止省略/引用原文**

* 禁止“略/同上/见文件A”等表述替代内容。

4. **禁止语义漂移**

* 不得为了统一风格而改写语义；若要统一，必须明确最终口径并保留多方原文。

---

## 4) 冲突处理的默认策略（严格执行）

当文件间出现冲突时：

1. **优先最终统一（以文件 A 为准）**：A 的定义作为最终规则；B/C 的差异作为历史/兼容说明（原文保留）。
2. 如果无法安全统一（会破坏兼容性/造成调用方混乱/两者同时必须存在），则启用：

   * **双轨兼容**：保留两套路由/字段/错误码，并提供映射与弃用计划（必须明确何时弃用旧轨）。

3. **修正与补漏优先（增量对主文档的纠正）**：当差异属于对主文档 A 的**修正或补漏**时，**最终口径采用 B/C**，并在融合说明中注明“此处为对主文档 A 的修正/补漏，最终以 B/C 为准”。适用情形包括但不限于：
   * A 缺少的数据库字段、索引、约束，在 B/C 中补充；
   * A 中错误的 API 定义（路径、方法、请求/响应、错误码等），在 B/C 中修正；
   * A 中遗漏或错误的权限/角色/鉴权设计，在 B/C 中补充或修改。
   若难以判断是“设计分歧”还是“对 A 的修正/补漏”，则仍按上述 1、2 条处理（以 A 为准或双轨兼容），并在融合说明中标注“待人工确认”。

4. **修正与补漏的识别（供执行第 3 款时使用）**：当 B/C 中存在以下任一情况时，应将该处差异视为对主文档 A 的**修正或补漏**，并采用本条第 3 款（最终口径以 B/C 为准）：
   * B/C 中存在「与主文档关系及合并决策说明」或「合并时决策说明」类章节，且其中对该条修改点的**变更类型**标注为「修正」或「补漏」，且**合并决策**为「以本文档为准」或「并入主文档」；
   * 或 B/C 正文中该段落在段前或段外带有固定标记 **「对主文档的修正」** 或 **「对主文档的补漏」**，且文中注明「合并时以本段为准」或「合并时并入主文档对应位置」。
   若 B/C 未做上述任何标注，则不得仅凭内容相似推断为修正/补漏，应按本条第 1、2 条处理（以 A 为准或双轨兼容），必要时在融合说明中标注「待人工确认」。

## 7) 输出格式要求（必须遵守）

## 8) 检查清单（合并前 / 合并中 / 合并后）

执行融合时须逐项自检，确保无遗漏、可追溯。

### 8.1 合并前检查清单（读取完 A/B/C 后必做）

* [ ] 已用指定方式（上传或 read_file）读取全部 A/B/C…，无漏读。
* [ ] 已确认哪个文件为 **A（主干）**，并记录。
* [ ] 已建立各文件的章节索引（H1/H2/H3 及起止），便于后续对照。
* [ ] 已粗略扫一遍 A 与 B/C 的目录结构，预判可能冲突的章节（路由、DB、错误码、状态机等）。

### 8.2 合并中检查清单（按 Step 1–3 执行时）

* [ ] Step 1：每个文件的段落、表格、代码块、错误码、流程说明均已纳入索引，无整段遗漏。
* [ ] Step 2：以 A 为主干建好了统一大纲；B/C 独有章节已规划插入位置或归入附录。
* [ ] Step 3：每章先拼 A 再拼 B/C；重复内容均用「重复来源块」包裹并标明来源。
* [ ] 每一处冲突都已插入「融合说明块」，并写清：冲突点、A/B/C 现状、最终口径、兼容/迁移（若需要）。
* [ ] 未使用「略 / 同上 / 见文件 A」等省略表述；代码块与表格未截断。

### 8.3 合并后检查清单（输出前必做）

* [ ] **最终路由表**：已覆盖 A/B/C 全部端点，无遗漏；双轨/别名已在 Notes 说明。
* [ ] **最终 DDL**：已汇总全部 ENUMS/TABLES/INDEXES，无遗漏。
* [ ] **Diff Log**：每个冲突/差异都有 Diff-ID，且包含：类别、冲突点、各文件位置、最终口径、兼容/迁移。
* [ ] **一致性校验报告**：已包含路由/DB/错误码/状态机/鉴权结论，以及完整性自检。
* [ ] **完整性自检**：已列出每个输入文件的 H1/H2 清单，并标注在输出文档中的对应位置，且声明无遗漏。
* [ ] 凡最终口径以 B/C 为准的项，已确认属于对 A 的修正/补漏（非设计分歧）。
* [ ] 全文无「见原文 / 参考文件 A」等依赖表述；读者仅凭本文档即可实现系统。
