# ✅ 代码生成提示词核心条目（完整版）

以下是代码生成提示词中**必须包含的内容**，用于确保代码风格统一、健壮性高、可维护性强，适用于 FastAPI 等异步 Web 框架下的高风险接口开发。

---

## 1. 核心编码原则 (Core Coding Principles)

### 🛡️ 安全异步异常处理 (Safe Async Exception Handling)

- **规则**：在任何 `try...except` 块中，如果需要使用来自数据库 ORM 对象（如 `current_user`）的属性（如 `current_user.id`）进行日志记录或错误处理，这些属性**必须在进入 `try` 块之前**被提取并存储到局部变量中。
- **指令**：**严禁**在捕获了数据库相关异常（如 `IntegrityError`）的 `except` 块中直接访问可能已与失效会话关联的 ORM 对象的属性。

---

## 2. 接口实现规范 (Endpoint Implementation)

### 🧱 主动变量提取 (Proactive Variable Extraction)

- **实现流程**：
  - 在进入 `try` 块之前，主动提取所有需要在异常处理中使用的变量（如：`user_id_for_logging = current_user.id`）。
  - 在 `except` 块中，**必须使用这些局部变量**进行日志记录或错误处理，避免访问失效对象。

### 🧪 异常处理 (Exception Handling)

- 将整个接口流程包裹在 `try...except` 块中。
- 若发生数据库查询等未知异常，应：
  - 记录错误日志；
  - 返回统一错误响应：
    ```python
    JSONResponse(
        status_code=500,
        content=error_response(code=1002, message='数据库查询错误')
    )
    ```

---

## 3. 响应处理规范 (Response Handling)

### ✅ 成功响应

- 所有成功返回**必须**调用 `success_response(data=...)` 函数构建响应内容。
- 示例：
  ```python
  return success_response(data=user_info)
  ```

### ❌ 错误响应

- 所有业务错误必须返回 `fastapi.responses.JSONResponse`，其 `content` 由 `error_response(...)` 构建。
- 示例：
  ```python
  return JSONResponse(
      status_code=400,
      content=error_response(code=1001, message='参数错误')
  )
  ```

> 假设 `success_response()` 和 `error_response()` 已定义在 `app/core/responses.py` 中。

---

## 4. 外部服务连接规范 (External Service Connections)

### 🔐 环境变量驱动配置

- 所有外部服务（如 Redis、数据库、第三方 API）的连接信息**必须**通过环境变量读取。
- 示例：
  ```python
  import os
  redis_host = os.getenv("REDIS_HOST", "localhost")
  redis_port = os.getenv("REDIS_PORT", "6379")
  ```
- 目的：确保代码在本地、Docker、测试、生产等不同环境下**无需修改即可运行**。

## 5. 接口设计规范 (API Design Principles)

### 🌐 RESTful 风格

- 所有接口必须遵循 RESTful 设计风格，包括但不限于：
  - 使用合适的 HTTP 方法（GET、POST、PUT、DELETE）；
  - URL 路径使用名词复数形式（如 `/users` 而非 `/user`）；
  - 使用嵌套路径表示资源关系（如 `/users/{user_id}/roles`）；
  - URL 中不包含动词，动作通过 HTTP 方法表达；
  - 返回统一结构的 JSON 响应（通过 `success_response` / `error_response`）。

## 【全项目通用安全与一致性规范（适用于所有 Model / Schema / API）】

在为本项目生成任何 Model、Schema、CRUD、Service、API 代码时，必须严格遵守以下全局约束。  
这些规则优先级 **高于** 具体模块的业务描述。

---

### 1. 内部 ID 不得对外暴露

1. 所有对外 API（包括 REST 接口、后台管理接口、开放平台接口）的 Response Schema 中：
   - **禁止** 直接暴露数据库内部主键字段，如：
     - `id`
     - `user_id`
     - 其他自增整型主键
   - 对外唯一标识统一使用：
     - `public_id`（推荐），或
     - 明确设计的业务编号字段（如 `order_no`, `transaction_id`）。

2. 如需在前端或第三方系统中引用某个资源，必须通过 `public_id` 或业务编号完成，不得依赖内部主键。

3. Service/CRUD 层可以自由使用内部 ID（`id`, `user_id` 等），但这些字段不得出现在：
   - API 输入模型
   - API 输出模型
   - 对外文档示例 JSON

---

### 2. 严格区分 API Schema 与 内部 CRUD Schema

本项目中的 Pydantic Schema 分为两大类，职责必须清晰分离：

#### 2.1 API 输入/输出 Schema（对外边界，安全优先）

- 示例：
  - `RegisterRequest`
  - `LoginRequest`
  - `UserProfileUpdate`
  - `PasswordChangeRequest`
  - `UserResponse`
  - 各模块的 `XXXRequest` / `XXXResponse`
- **安全强制规则：**
  - **不得包含任何内部控制字段或敏感字段**，包括但不限于：
    - 权限 / 角色类字段：`role`, `is_admin`, `is_superuser`, `is_active`, `status`（用于启停、审核等）
    - 安全/凭证类字段：`password_hash`, `salt`, `secret_key`, `access_key`, `internal_token`
    - 内部外键类字段：`user_id`, 其他内部 ID
  - 用户注册/登录类接口：
    - 只能接收明文 `password`（或类似字段），不允许接收 `password_hash`。
    - 用户无权自行指定自己的 `role` 或 `is_active`，这些字段只能由系统或管理员逻辑设置。

#### 2.2 内部 CRUD Schema（仅服务内部使用）

- 示例：
  - `UserCreateInternal`
  - `UserUpdateInternal`
  - `XXXCreateInternal`
  - `XXXUpdateInternal`
- 用途：
  - 封装 Service / CRUD 层写入数据库所需的 **完整字段集合**。
  - 可以包含：
    - `role`
    - `is_active`
    - `password_hash`
    - 内部使用的 `user_id`
    - 其他内部状态、控制字段
- 约束：
  - 这类 Schema **只能**在 Service/CRUD 层之间传递。
  - **禁止**在 API 路由函数中直接作为请求体模型暴露给外部调用方。
  - 如需实现管理员接口，必须定义单独的管理员专用 API Schema（如 `AdminCreateUserRequest`），由 Service 层将其转换为 `UserCreateInternal`。

### 3. Enum 字段声明规范（适用于所有 Model）

1. 所有使用 Python Enum 的字段，必须显式通过 `sqlalchemy.Enum` 声明参数，不允许裸用：
   - ❌ 禁止写法：
     ```python
     status = Column(Enum(StatusEnum))
     ```
2. 默认推荐写法（使用检查约束而非数据库原生 ENUM，便于迁移）：
   ```python
   from sqlalchemy import Enum as SQLEnum

   class StatusEnum(str, enum.Enum):
       PENDING = "PENDING"
       RUNNING = "RUNNING"
       DONE = "DONE"

   status = Column(
       SQLEnum(
           StatusEnum,
           native_enum=False,   # 必须显式指定
       ),
       nullable=False,
       server_default="PENDING",  # 如业务有默认值
   )
````

3. 如果某个模块确实需要绑定数据库原生 ENUM 类型：

   * 必须同时指定 `name` 和 `native_enum=True`，例如：

     ```python
     status = Column(
         SQLEnum(
             StatusEnum,
             name="task_status",    # 与 DDL 中 ENUM 类型名一致
             native_enum=True,
         ),
         nullable=False,
     )
     ```
   * 不允许省略 `name` 或默认为随机类型名。

4. 一致性检查要求：

   * 如果发现代码中存在 `Column(Enum(MyEnum))` 这种未显式指定 `native_enum`（或 `name`）的写法，视为“需要优化”的实现，应提示开发者补全参数。

### 4. 对外 ID 策略统一（适用于所有 Model / Schema）

1. 所有需要对外被引用的资源（用户、订单、任务、剪辑、文件、会话等），必须：
   * 在数据库中拥有 `public_id` 或业务编号字段。
   * 在对外 API 的 Response 中返回该字段。
2. 对外文档、前端交互、第三方集成都必须以 `public_id` 或业务编号作为主键，而非内部自增 ID。
3. 若存在需要通过 URL 访问资源的场景（如 `/api/v1/clips/{clip_id}`），`clip_id` 代表的必须是 `public_id` 或业务编号，而不是数据库内部的 `id`。

##### **测试数据隔离 (Test Data Isolation)**

* **指令**: 为了防止测试之间因违反数据库 `UNIQUE` 约束而产生冲突，所有唯一性字段（如 `username`, `email`, `product_code`, `transaction_id`）**必须**是随机生成的，以确保每次测试运行时的数据都是独一 un二的。
* **实现**:
    * 推荐安装并使用 `faker` 库 (`pip install Faker`)，因为它可以生成符合特定格式和长度要求的、更真实的数据。
    * 所有生成的随机数据**必须**严格遵守 `app/schemas/users.py` 中 Pydantic 模型的验证规则。
* **具体要求 (Requirements)**:
    * **`username`**:
        * **规则**: 必须符合 `schemas.UserBase` 中定义的 `min_length=1` 和 `max_length=50`。
        * **Faker 范例**: `fake.user_name()` 结合一个随机后缀，例如 `f"{fake.user_name()}_{uuid.uuid4().hex[:6]}"` 以确保唯一性。
    * **`email`**:
        * **规则**: 必须是一个有效的邮箱格式。
        * **Faker 范例**: `fake.email()`。
    * **`phone_number` (已补充)**:
        * **规则**: 长度不能超过20个字符。
        * **Faker 范例**: fake.phone_number() (可能需要根据具体格式进行调整)
    * **`product_code`**:
        * **规则**: 必须符合 `schemas.MembershipProductCreate` 中定义的 `min_length=1` 和 `max_length=50`。
        * **Faker 范例**: 使用大写字母和数字的组合，例如 `f"PROD_{''.join(random.choices(string.ascii_uppercase + string.digits, k=10))}"`。
    * **`transaction_id`**:
        * **规则**: 长度不能超过255个字符。
        * **Faker 范例**: `f"txn_{uuid.uuid4().hex}"`。
    * **禁止硬编码**: 在测试的“准备 (Arrange)”阶段，**严禁**使用硬编码的字符串（如 `'usera'`) 作为唯一性字段的值，除非测试目的就是为了验证重复性约束。
