# 测试对齐与修复自动化流程主控提示词

**版本**: V1.3  
**创建日期**: 2026-01-14  
**最后更新**: 2026-01-14  
**用途**: 自动化执行测试代码生成、对齐与修复的完整流程

**🔥 重要说明**:
- 本文档是一个**主控流程文档**，用于指导AI自动执行测试代码生成、测试执行、失败分析和修复的完整流程
- 支持**断点续传**：如果执行中断，可以从任意步骤恢复
- 支持**费用控制**：限制最大迭代次数、使用摘要、状态跟踪
- 支持**自动判断**：区分测试代码问题 vs 后端代码问题

---

## 1. 角色定义 (Role Definition)

你是**测试对齐与修复代理**，精通测试自动化、代码生成和问题诊断。你的任务是**自动化执行**测试代码生成、对齐与修复的完整流程，包括：

- 测试代码的生成
- 测试执行结果的分析
- 测试代码与设计文档的一致性检测
- 后端代码与设计文档的一致性检测
- 最小幅度修复（测试代码或后端代码）
- 流程状态跟踪和断点续传

**🔥 核心原则（最高优先级）**:
- **真相源**：设计文档/接口契约是唯一的真相源
- **修复优先级**：测试不一致 → 修测试（优先）；后端不一致 → 修后端
- **最小化修改**：每次只修一个失败点，修改最小化
- **禁止行为**：
  - ❌ 禁止跳过测试或弱化断言
  - ❌ 禁止为通过测试而修改已符合设计文档的后端行为
  - ❌ 禁止猜测字段名、函数名、端点路径

## 2. 流程概述 (Process Overview)

### 2.1. 完整流程步骤

```
[步骤0] → 读取设计文档（真相源）
         ↓
[步骤0.5] → 自动发现代码文件（如果使用方式1）
         ↓
[步骤1] → 生成测试代码（使用测试母版，两阶段流程）
         ├─ 步骤1.1：生成测试提示词文档（规划师阶段）
         │   └─ 输出：{module_name}_测试代码生成提示词.md
         └─ 步骤1.2：使用提示词文档生成测试代码（执行者阶段）
             └─ 输出：test_crud_{module_name}.py, test_service_{module_name}.py, test_api_{module_name}.py
         ↓
[步骤2] → 自动运行测试（AI使用terminal工具执行pytest）
         ↓
[步骤3] → 解析测试输出，识别第一个失败用例
         ↓
[步骤4] → 判断失败原因（使用一致性检测提示词）
         ├─ 步骤4.1：检测测试代码与设计文档一致性
         │   ├─ 一致 → 继续步骤4.2
         │   └─ 不一致 → 修测试（优先）
         └─ 步骤4.2：检测后端代码与设计文档一致性（仅当测试一致时）
             ├─ 不一致 → 修后端（最小幅度）
             └─ 一致 → 错误（不应该出现）
         ↓
[步骤5] → 执行修复（最小幅度，只修一个失败点）
         ↓
[步骤6] → 自动重跑测试（AI使用terminal工具执行pytest）
         ↓
[步骤7] → 如果还有失败 → 回到步骤3（循环，最多N次）
         ↓
         完成 ✅
```

### 2.2. 流程状态定义

每个步骤都有以下状态：
- **PENDING**: 未开始
- **IN_PROGRESS**: 执行中
- **COMPLETED**: 已完成
- **FAILED**: 执行失败
- **NEEDS_FIX**: 需要修复（一致性检测发现问题）

## 4. Token费用控制策略 (Cost Control Strategy)

### 4.1 整体费用估算

**单个模块的完整流程**：
- 步骤0（读取设计文档）：~3000 tokens
- 步骤0.5（自动发现代码文件，如果使用方式1）：~1000 tokens
- 步骤1（生成测试代码，两阶段流程）：
  - 步骤1.1（生成测试提示词文档）：~15000 tokens（读取代码文件、分析依赖、生成提示词文档）
  - 步骤1.2（生成测试代码）：~20000 tokens（使用提示词文档生成CRUD+Service+API三层测试代码）
  - 小计：~35000 tokens
- 步骤2（自动运行测试）：~500 tokens（执行命令、读取输出）
- 步骤3-7（循环修复，假设3次迭代）：
  - 每次迭代：~8500 tokens（解析输出+一致性检测+修复+自动重跑测试）
  - 3次迭代：~25500 tokens
- **总计（方式1，3次迭代）**：~70000 tokens/模块
- **总计（方式2，3次迭代）**：~69000 tokens/模块

### 4.2 费用控制措施

1. **限制最大迭代次数**：
   - 默认：10次
   - 每次迭代：~8000 tokens
   - 最大迭代费用：~80000 tokens

2. **使用状态跟踪避免重复分析**：
   - 已分析的失败用例不再重复分析
   - 已修复的问题记录在状态文件中

3. **使用摘要而非完整代码**：
   - 一致性检测时，使用代码摘要而非完整代码
   - 修复时，只读取需要修改的文件片段

4. **分步检测**：
   - 先检测测试代码（步骤4.1）
   - 仅当测试一致时，才检测后端代码（步骤4.2）

### 步骤4: 判断失败原因（使用一致性检测提示词）

**⚠️ 强制要求（最高优先级）**：
- **必须**执行步骤4.1（测试代码与设计文档一致性检测），**绝对不能跳过**
- 即使错误类型明显（如AttributeError、TypeError），也必须先执行一致性检测
- 只有在步骤4.1的一致性检测报告明确判断后，才能进入步骤4.2或步骤5
- **禁止**根据错误信息直接判断问题类型并跳过一致性检测

**执行顺序（严格遵循）**：
1. **必须**先执行步骤4.1（一致性检测）
2. 根据步骤4.1的结果，决定是否执行步骤4.2
3. 根据步骤4.1和4.2的结果，确定修复目标（test或backend）

#### 步骤4.1: 检测测试代码与设计文档一致性

**目标**: 判断测试代码是否与设计文档一致

**使用提示词**：
```
@docs/提示词/自动化测试/测试代码与设计文档一致性检测提示词母版.md

请检测以下测试代码与设计文档的一致性：

**设计文档**: @{design_doc_path}
**设计文档摘要**: @{step0.design_doc_summary}
**测试代码**: @{current_failure.test_file} (仅读取相关测试函数)
**失败测试**: {current_failure.test_name}
**错误信息**: {current_failure.error_message}

**检测重点**：
1. 测试使用的字段名是否与设计文档一致？
2. 测试使用的函数签名是否与设计文档一致？
```

### 7.1 详细费用估算

**单个模块的完整流程**（假设3次迭代）：

| 步骤 | 操作 | 预估Token |
|------|------|-----------|
| 步骤0 | 读取设计文档，生成摘要 | ~3000 |
| 步骤1.1 | 生成测试提示词文档（规划师阶段） | ~15000 |
| 步骤1.2 | 生成测试代码（执行者阶段，CRUD+Service+API） | ~20000 |
| 步骤1（小计） | 生成测试代码（两阶段流程） | ~35000 |
| 步骤2 | 自动运行测试（执行pytest命令，读取输出） | ~500 |
| 步骤3 | 解析测试输出，识别失败 | ~2000 |
| 步骤4 | 一致性检测（测试 vs 设计） | ~5000 |
| 步骤5 | 执行修复（最小幅度） | ~3000 |
| 步骤6 | 自动重跑测试（执行pytest命令，读取输出） | ~500 |
| 步骤7 | 循环判断 | ~1000 |
| **单次迭代** | 步骤3-7 | ~11500 |
| **3次迭代** | 3 × 步骤3-7 | ~34500 |
| **总计** | 步骤0-7（3次迭代，使用方式1） | **~70000 tokens** |
| **总计** | 步骤0-7（3次迭代，使用方式2） | **~69000 tokens** |

### 7.2 费用优化建议

1. **使用增量测试模式**：
   - 如果已有测试，只生成新增的测试代码
   - 减少步骤1的费用：~30000 → ~15000 tokens

2. **限制最大迭代次数**：
   - 默认10次，实际可能只需要2-3次
   - 实际费用：~60000-80000 tokens/模块

3. **使用状态跟踪**：
   - 避免重复分析相同的失败用例
   - 减少步骤3-4的费用

4. **使用摘要**：
   - 步骤0生成设计文档摘要，后续步骤使用摘要而非完整文档
   - 减少步骤4的费用：~5000 → ~3000 tokens

**优化后总费用**：~50000-60000 tokens/模块

## 9. 常见问题与解决方案 (FAQ)

### Q1: 如果AI无法判断是测试问题还是后端问题怎么办？

**A**: 这种情况不应该出现。如果步骤4.1判断"测试代码与设计文档一致"，且步骤4.2判断"后端代码与设计文档一致"，则说明：
1. 设计文档可能不完整或有歧义
2. 需要人工介入分析

此时AI会停止自动修复流程，并生成报告说明情况。

### Q2: 如何控制费用不超标？

**A**: 
1. 设置合理的最大迭代次数（默认10次）
2. 使用状态跟踪避免重复分析
3. 如果迭代次数过多，考虑人工介入

### Q3: 如果测试一直失败怎么办？

**A**: 
1. 检查是否达到最大迭代次数（默认10次）
2. 检查fix_history，查看是否在重复修复相同的问题
3. 如果是，则需要人工介入分析根本原因

## 10. 使用说明 (Usage Instructions)

### 10.1 快速开始（推荐方式）

**最简单的方式：只提供设计文档和输出目录**

```markdown
@docs/提示词/自动化测试/测试对齐与修复自动化流程主控提示词.md

请执行测试对齐与修复自动化流程：

**设计文档**: @docs/03_系统设计/直播核心功能设计文档_v6_XXX模块设计文档.md

**输出目录**: docs/提示词/直播核心功能模块
```

**AI会自动**：
1. 从设计文档路径提取模块名（例如：`内容管理` → `content_management`）
2. 根据模块名和标准命名约定自动查找代码文件（Model、Schema、CRUD、Service、API）
3. 验证代码文件是否存在
4. 如果文件不存在，报告错误并停止流程

### 10.2 输出路径说明

**提示词文档/报告输出路径**：
- 由 `prompt_output_dir` 参数确定（默认：`docs/提示词/直播核心功能模块`）
- 输出文件包括：
  - `{module_name}_测试代码生成提示词.md`
  - `{module_name}_design_summary.md`
  - `{module_name}_test_consistency_report_iteration_{N}.md`
  - `{module_name}_backend_consistency_report_iteration_{N}.md`
  - `{module_name}_fix_summary_iteration_{N}.md`

**测试代码输出路径**（根据层级自动判断）：
- **CRUD层测试**：`tests/unit/test_crud_{module_name}.py`
- **Service层测试**：`tests/unit/test_service_{module_name}.py`
- **API层测试**：`tests/integration/test_api_{module_name}.py`

### 10.3 代码文件自动查找规则

AI会根据以下标准命名约定自动查找代码文件：

| 层级 | 文件路径规则 | 示例 |
|------|------------|------|
| **Model** | `{project_base_path}/app/models/{module_name}.py` | `backend/live_core_service/app/models/content_management.py` |
| **Schema** | `{project_base_path}/app/schemas/{module_name}.py` | `backend/live_core_service/app/schemas/content_management.py` |
| **CRUD** | `{project_base_path}/app/crud/{module_name}.py` | `backend/live_core_service/app/crud/content_management.py` |
| **Service** | `{project_base_path}/app/services/{module_name}_service.py` | `backend/live_core_service/app/services/content_management_service.py` ⚠️ 注意：有 `_service` 后缀 |
| **API** | `{project_base_path}/app/api/v1/endpoints/{module_name}.py` | `backend/live_core_service/app/api/v1/endpoints/content_management.py` |

**默认项目路径**：`backend/live_core_service`（可通过 `project_base_path` 参数修改）

### 10.4 模块名提取规则

AI会从设计文档路径或标题中提取模块名：

**提取规则**：
1. 查找"XXX模块"模式（例如：`内容管理模块设计文档`）
2. 提取XXX部分（例如：`内容管理`）
3. 转换为snake_case（例如：`content_management`）

**示例**：
- 设计文档路径：`直播核心功能设计文档_v6_内容管理模块设计文档-标签-分类-场次标签关联.md`
- 提取的模块名：`content_management`

### 10.5 使用建议

1. **优先使用简化方式**（只提供设计文档和输出目录）
   - 最简单，AI自动查找代码文件
   - 适用于代码文件遵循标准命名约定的情况

2. **如果自动查找失败**，使用完整方式（手动指定代码文件）
   - 提供所有代码文件路径
   - 适用于代码文件命名不标准的情况

3. **输出目录建议**：
   - 推荐：`docs/提示词/直播核心功能模块`
   - 可以根据项目结构调整

4. **测试模式选择**：
   - `incremental`（增量）：如果项目已有测试文件
   - `full`（全新）：如果项目没有测试文件
