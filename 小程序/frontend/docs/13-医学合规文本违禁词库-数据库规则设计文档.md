## 📌 核心定位

### 1. 本文档做什么

在现有 `content_safety_rules` 表与规则引擎之上，定义：

- **表结构增量**：合规分类、法规溯源、强制级别
- **`rule_category` taxonomy**：14 大类运营违禁词 → **32 个**可落库的分类编码（含 framework 3 类）
- **完整违禁词 pattern**：comma 分隔词表 + 必要 regex，可直接写入 seed（政治类全量见 §1.4 API，seed 仅兜底）
- **seed 生成规则**：scene × field × category 矩阵与命名规范
- **法定 vs 平台**：哪些规则禁止运营关闭

### 2. 本文档不做什么

| 不在范围 | 原因 |
|---|---|
| 医疗机构资质、《医疗广告审查证明》 | 主体行为，非文本词库 |
| 执业范围 / 机构报备 / 离职身份 | 需专家档案交叉校验 |
| 医疗广告「仅限 8 项」白名单 | 结构化表单策略，非 keyword |
| 首诊 / 开方 / 直播诊疗 | 行为判定，非词库 |
| 血腥画面、头像图片 | 走 §1.4.6 图片审核 |

引擎调用方式、审计日志仍以《12》为准；**政治敏感文本**在《12》文本引擎之上 **叠加** §1.4 第三方 API（V1.0 占位）。

## 1. 数据库 Schema 增量

### 1.1 content_safety_rules 新增字段

在《12》§1.1 基础上 **ALTER** 三列（live_core / users 两库结构一致）：

```sql
-- ==========================================================
-- 增量：医学合规文本违禁词库分类字段
-- 执行时机：在 content_safety_rules 建表完成后
-- ==========================================================

ALTER TABLE content_safety_rules
    ADD COLUMN IF NOT EXISTS binding_level VARCHAR(20) NOT NULL DEFAULT 'platform',
    ADD COLUMN IF NOT EXISTS rule_category   VARCHAR(50) NOT NULL DEFAULT 'general',
    ADD COLUMN IF NOT EXISTS regulation_ref  VARCHAR(200);

ALTER TABLE content_safety_rules
    ADD CONSTRAINT chk_content_safety_rules_binding_level
        CHECK (binding_level IN ('statutory', 'platform'));

CREATE INDEX IF NOT EXISTS idx_content_safety_rules_category_enabled
    ON content_safety_rules (rule_category, enabled);

COMMENT ON COLUMN content_safety_rules.binding_level IS
    '强制级别：statutory=国家法定词库（禁止运营关闭）；platform=平台自主词库';
COMMENT ON COLUMN content_safety_rules.rule_category IS
    '违禁词分类编码，见本文档 §2';
COMMENT ON COLUMN content_safety_rules.regulation_ref IS
    '法规/规范溯源，如 广告法§16；多条用分号分隔';

-- 建议：seed 幂等依赖 rule_name 唯一
CREATE UNIQUE INDEX IF NOT EXISTS uq_content_safety_rules_rule_name
    ON content_safety_rules (rule_name);
```

> `rule_name` 在应用层已作为 seed 幂等键；生产库建议加 UNIQUE 索引，防止重复插入。

### 1.2 管理端约束（应用层）

| binding_level | `enabled=false` | `action` 允许值 | PATCH `pattern` | PATCH `binding_level` / `rule_category` |
|---|---|---|---|---|
| `statutory` | **禁止**（4001） | `block` / `warn`（**V1.1**：按分层策略矩阵；不再限制仅 block） | `political_sensitive` **禁止**；其余 statutory 允许（法务流程） | **禁止** |
| `platform` | 允许 | `block` / `warn` | 允许 | 允许（`rule_category` 建议创建后不变） |

> 各 scene 默认 action 见《12-13 分层策略 V1》§2.2；勿再假设「statutory ⇒ 一律 block」。

#### 1.2.1 管理端 Schema 增量（相对《12》§2.2）

`ContentSafetyRuleBase` / `ContentSafetyRuleItem` / `ContentSafetyRuleCreate` 增加：

```python
binding_level: Literal["statutory", "platform"] = "platform"
rule_category: str = Field(default="general", max_length=50)
regulation_ref: Optional[str] = Field(None, max_length=200)
```

`ContentSafetyRuleUpdate` **仅**允许更新：`pattern`、`action`、`severity`、`priority`、`enabled`、`remark`（**不可**改 `binding_level`、`rule_category`、`scene`、`target_field`、`match_type`）。

#### 1.2.2 管理端 PATCH 约束示例

**禁止关闭 statutory 规则** — `PATCH /api/v1/admin/content-safety/rules/{id}`，`{"enabled": false}`：

```json
{
  "code": 4001,
  "message": "statutory 规则禁止停用",
  "data": null,
  "timestamp": "2026-07-04T10:00:00Z"
}
```

**禁止修改 political_sensitive 词表** — `{"pattern": "新词1,新词2"}`：

```json
{
  "code": 4001,
  "message": "political_sensitive 本地兜底词表禁止通过管理端修改，请走第三方政治 API 厂商",
  "data": null,
  "timestamp": "2026-07-04T10:00:00Z"
}
```

**platform 规则允许 warn** — `{"action": "warn", "pattern": "测试warn"}` → `200 OK`（与《12》search warn 示例一致）。

### 1.3 pattern 存储约定

| 类型 | pattern 格式 | 示例 |
|---|---|---|
| `keyword` / `porn` / `gambling` / `fraud` | 英文逗号分隔，无空格 | `根治,治愈,100%有效` |
| `political`（本地兜底） | 英文逗号分隔，无空格 | 见 §3.4；**不含**领导人姓名；全量覆盖走 §1.4 第三方 API |
| `regex` | 单条正则 | `(治愈\|有效)率?\s*\d+[%％]` |
| `url` / `contact` | `builtin` | 沿用《12》 |

- 单条 `pattern` 建议 **≤ 8000 字符**；超长时拆为同 category 多条（后缀 `-2`、`-3`）
- 引擎 `normalize_text()` 去插符后匹配，词表 **不含** 刻意插符变体

### 1.4 政治敏感文本检测（第三方 API + 本地兜底）

**定位**：政治敏感全量检测 **不对接本地词库运维**；大顺采用 **第三方政治敏感词 API** 作为主路径，本地 `match_type=political` 规则仅保留可公开文档化的 **兜底 seed**（分裂、否定历史等），与 API 结果 **取并集**——任一命中即 `block`。

| 层级 | 职责 | V1.0 状态 |
|---|---|---|
| 第三方 API | 领导人姓名/外号、涉密军政、变体与组合等全量词库 | **占位，未接真实厂商** |
| 本地 `political_sensitive` | 公开可文档化兜底词表，写入 seed | 已定义，随 seed 落库 |
| 管理端追加 | **不用于** 政治类全量维护 | — |

**调用时机**：与《12》文本 `check_content_safety()` 同路径；每个文本字段在本地规则引擎评估后（或并行）调用 API。**不**将 API 词库同步写入 `content_safety_rules.pattern`。

**占位客户端（当前实现目标）**：

```python
# live_core_service/app/content_safety/political_text/client.py
# users/app/content_safety/political_text/client.py — V1.0 仅占位

from enum import Enum

class PoliticalTextProvider(str, Enum):
    PLACEHOLDER = "placeholder"  # 默认：开发联调，可配置 always_pass / stub_reject
    ALIYUN = "aliyun"            # 阿里云内容安全（文本）
    TENCENT = "tencent"          # 腾讯云文本内容安全
    NETEASE = "netease"          # 网易易盾（文本）


async def check_political_text(text: str, *, provider: PoliticalTextProvider) -> bool:
    """返回 True 表示命中政治敏感（应 block）。PLACEHOLDER 默认返回 False。"""
    ...
```

**生产配置**：`POLITICAL_TEXT_PROVIDER` 环境变量；`statutory` 类政治规则 **禁止** 运营关闭；API 开关与本地兜底 **同开同关**（无单独 bypass）。

**异常与决策**：API 调用超时/5xx/未配置密钥 → 与《12》文本引擎故障一致，**写入型接口**抛 `ContentSafetyServiceException`（HTTP 422，code=2004）；本地引擎与 API **并行**评估，任一命中即 `block`。

**审计**：API 命中时 `matched_rule_names` 记 `political-api`，`matched_rule_ids` 记 `null`（无本地 rule_id）；`reason_message` 记 `命中政治敏感（第三方 API）`。本地命中仍记 `{scene}-{field}-political_sensitive` 及对应 rule_id。

## 4. seed 生成规则

### 4.1 场景 × 字段矩阵

与《12》§1.4.3 一致：

| scene | target_field |
|---|---|
| `message` | `content` |
| `room_title` | `title` |
| `room_description` | `description` |
| `room_tab` | `tab_key`, `title`, `text_content` |
| `search_query` | `keyword` |
| `nickname`（users 库） | `nickname`, `bio` |

### 4.2 规则命名

```
{scene}-{target_field}-{rule_category}
```

示例：`message-content-absolute_superlative`

### 4.3 默认 action / severity

| binding_level | action | severity |
|---|---|---|
| `statutory` | 默认见《分层策略 V1》§2.2（可为 `block` 或 `warn`） | critical（warn 时可为 high） |
| `platform` | 默认见《分层策略 V1》§2.2 | high（`platform_circumvention` 可为 medium） |

> 【废弃】「statutory 一律 action=block」。按 scene 分档写入 seed。

### 4.4 规则数量估算

每个 **scene × target_field** 组合生成 **32 条**规则（`MEDICAL_LEXICON` 29 类 + `FRAMEWORK_RULES` 3 类，均在字段循环内写入，见 §4.5）。

| 库 | 字段数 | 计算 | 条数 |
|---|---|---|---|
| live_core | 7 | 7 × 32 | **224** |
| users | 2（nickname + bio） | 2 × 32 | **64** |

不含《12》search warn 示例条。framework 3 类（url/contact/fraud）**替代**原《12》四类独立命名中的 url/contact/fraud/keyword，医学 keyword 类按 §2 拆分为 29 个 `rule_category`。

### 4.5 seed.py 结构（伪代码）

```python
# live_core_service/app/content_safety/medical_lexicon_seed.py

MEDICAL_LEXICON: dict[str, dict] = {
    "absolute_superlative": {
        "pattern": "顶级,顶尖,...",  # 见 §3；禁止裸「最」「第一」「天花板」
        "match_type": "keyword",
        "binding_level": "statutory",
        "regulation_ref": "广告法§9;广告法§16",
        "priority": 11,
    },
    # ... 全文 pattern 以 §3 为准；action 按《分层策略 V1.1》§2.2 分档写入，勿写死 block
}

FRAMEWORK_RULES = [
    ("framework_url", "url", "builtin", 10, "platform", "url"),
    ("framework_contact", "contact", "builtin", 20, "platform", "contact"),
    ("framework_fraud", "fraud", FRAUD_PATTERN, 30, "platform", "fraud"),
]

TEXT_FIELD_MATRIX = { ... }  # 同 §4.1；users 库仅含 nickname 场景

def resolve_severity(cat: str, binding_level: str) -> str:
    if binding_level == "statutory":
        return "critical"
    if cat == "platform_circumvention":
        return "medium"
    return "high"

def build_medical_rules() -> list[dict]:
    rules = []
    for scene, fields in TEXT_FIELD_MATRIX.items():
        for field in fields:
            for cat, meta in MEDICAL_LEXICON.items():
                rules.append({
                    "rule_name": f"{scene}-{field}-{cat}",
                    "scene": scene,
                    "target_field": field,
                    "match_type": meta["match_type"],
                    "pattern": meta["pattern"],
                    "action": "<按分层策略档位：A/B 多为 warn，C/红线为 block>",
                    "severity": resolve_severity(cat, meta["binding_level"]),
                    "priority": meta["priority"],
                    "binding_level": meta["binding_level"],
                    "rule_category": cat,
                    "regulation_ref": meta.get("regulation_ref"),
                    "enabled": True,
                    "remark": f"分层策略V1.1 档位=…；词库 {cat}，见 add-docs/13 与 12-13 增量",
                })
            for fw_name, match_type, pattern, priority, binding_level, rule_category in FRAMEWORK_RULES:
                rules.append({ ... })  # rule_name = f"{scene}-{field}-{fw_name}"
    return rules
```

### 4.6 幂等与更新

- 以 `rule_name` 唯一判定  
- **分层策略 V1.1 词表升级**：已存在规则须 **UPDATE** `pattern` / `action` / `remark`（打破「仅跳过」）；推荐 migration 按 `rule_name` 同步 §3 与增量 §2.2  
- 日常运营：可通过管理端 PATCH `pattern`（statutory 受 §1.2 约束）；`political_sensitive` 除外  
- `binding_level=statutory` 的规则 PATCH 时 **禁止** `enabled=false`；**允许** `action` 在 block/warn 间调整

### 4.7 从《12》V2.2 默认 seed 迁移

上线医学词库时 **不**与旧规则长期并存，按库执行：

| 步骤 | live_core | users |
|---|---|---|
| 1 | 执行 §1.1 ALTER + UNIQUE 索引 | 同左 |
| 2 | 将旧规则批量 `enabled=false`：`rule_name` 匹配 `*-外链` / `*-联系方式` / `*-敏感词` / `*-广告引流` 及 `search_query-keyword-低风险提醒` | 停用 nickname 四类 + `avatar-avatar_url-*`（avatar 改走《12》§1.4.6，非 rules 表） |
| 3 | entrypoint 调用 `medical_lexicon_seed` 写入 224 条 | 写入 64 条 |
| 4 | `invalidate_all_rules_cache()` | 同左 |

> 旧规则保留行记录（`enabled=false`）便于审计对比；稳定运行 1 个版本后可物理清理（可选 P2）。
