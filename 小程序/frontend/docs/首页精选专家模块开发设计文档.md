# 首页精选专家模块开发设计文档

## 1. 背景与问题定义

专家页已经接入全量专家列表后，原先放在专家页里的“精选专家”内容不再适合继续占据专家页首屏，因为它与全量列表的定位重复，且会稀释专家页“检索与筛选”的核心任务。

首页是用户进入小程序后的第一内容层，适合承接“平台优先推荐”的内容入口。精选专家属于高频曝光、高点击、高关注转化的内容，因此应从专家页迁移到首页，并放在比直播间列表更靠前的位置，让用户在看直播前先看到值得关注的专家。

这次迁移不是简单挪位置，而是一次展示语义重构：

- 专家页继续承担“全量查找、筛选、排序、管理关注”的职责。
- 首页精选专家承担“平台推荐、快速识别、轻量关注”的职责。
- 首页展示方式必须和直播间列表区分开，不能再使用专家页那种纵向行列表。

## 2. 设计目标

### 2.1 功能目标

- 在首页 banner 下方增加一个独立的“精选专家”内容模块。
- 模块使用横向滑动列表，支持左右浏览更多专家。
- 每个专家以独立卡片展示，卡片内承载头像、姓名、职称、医院/机构信息。
- 卡片右上角显示星标，表示当前用户是否关注该专家。
- 支持点击卡片进入专家详情页。
- 支持在首页直接关注/取消关注，无需跳转到专家页。

### 2.2 视觉目标

- 首页保持“裸背景”感，不在专家模块外层再加大面积底色块。
- 模块使用轻边框、浅表面、低装饰度的卡片。
- 视觉重量要低于直播间卡片，避免首页过于拥挤。
- 星标要成为识别焦点，但不能喧宾夺主。

### 2.3 体验目标

- 用户第一眼能理解这是“平台精选”的专家推荐。
- 横向滑动的提示要明确，不能让用户误以为只展示一两个。
- 关注状态要即时反馈，避免“点了但没反应”的感觉。
- 在未登录状态下，点击关注要走统一登录引导。

## 3. 模块定位与页面结构

### 3.1 页面顺序

首页结构调整为：

1. 顶栏搜索区
2. 科室分类 Tabs
3. Banner 轮播
4. 精选专家模块
5. 直播状态筛选（预告 / 直播 / 回放）
6. 直播间列表
7. 快捷菜单

### 3.2 插入位置理由

精选专家放在 banner 之后、直播间筛选之前，原因有三点：

- banner 是首页第一视觉焦点，精选专家不应抢 banner 的首屏位置。
- 直播间筛选区之前留出一个“内容推荐缓冲层”，让首页节奏更完整。
- 精选专家与直播间列表是不同内容类型，插在它们之间更自然。

### 3.3 模块层级

精选专家模块本身由两层组成：

- 标题层：模块标题、说明文案。
- 内容层：横向滚动专家卡片列表。

模块外层不使用独立背景容器，只通过内部间距与卡片样式形成层次。

## 4. 数据来源与接口契约

### 4.1 精选专家列表

接口：`GET /api/v1/featured-experts`

用途：获取首页推荐展示的专家卡片列表。

建议参数：

- `limit`：前端按展示位数量控制，建议默认 `6`。

返回字段建议兼容以下内容：

- `id`
- `name`
- `avatar_url` / `avatarUrl` / `avatar`
- `title`
- `hospital`
- `department`

兼容原则：前端应尽量做字段归一化，避免后端字段命名轻微变化导致模块空白。

### 4.2 当前关注列表

接口：`GET /api/v1/users/me/followed-experts`

用途：判断当前用户是否已关注精选专家中的某一位，用于星标状态展示。

建议兼容字段：

- `expert_id`
- `id`

如果接口同时返回专家基础信息，也应继续以 `expert_id` 作为主键。

### 4.3 关注与取消关注

- 关注：`POST /api/v1/users/me/followed-experts`
- 取消关注：`DELETE /api/v1/users/me/followed-experts/{expert_id}`

前端行为要求：

- 关注成功后，立即把星标切换到已关注态。
- 取消关注成功后，立即切换回未关注态。
- 接口失败时不静默，至少要给出 toast 提示。

### 4.4 数据融合规则

首页精选专家的最终展示状态由两份数据合成：

1. 精选专家列表决定展示哪些卡片。
2. 已关注列表决定每张卡片右上角星标状态。

合成规则：

- 若 `featuredExperts` 中存在某专家但关注列表没有该 `id`，显示未关注。
- 若关注列表有某专家但不在精选列表，不在首页精选模块展示，但仍保留到用户关注体系里。

## 5. 页面布局与视觉规范

### 5.1 整体气质

模块风格要延续首页当前视觉体系，但要比直播间更轻。

- 不使用大面积阴影。
- 不使用重渐变背景。
- 不使用复杂装饰元素。
- 不使用密集边框与强烈分隔。

### 5.2 标题区

标题区建议包含两行：

- 主标题：精选专家
- 副标题：横向滑动查看更多

主标题用于建立语义，副标题用于提示交互方式。副标题必须足够轻，不与主标题抢权重。

### 5.3 卡片区

每张专家卡是首页模块中的核心视觉单元。

卡片需要同时承载四个层级信息：

1. 头像
2. 姓名
3. 职称
4. 医院/机构

星标位于卡片右上角，成为“状态识别点”。

卡片的排版顺序采用“上排紧凑识别、下排补充说明”的结构：

+- 第一行：头像与姓名同排，姓名独占文本宽度，不再和职称并排。
+- 第二行：职称独立成行，避免和姓名抢宽度。
- 第二行右侧可显示开播状态徽标，仅当专家当前直播时展示“直播中”。
+- 第三行：医院/机构信息。
+- 第四行：可选展示科室或补充说明。

这样可以明显压缩卡片纵向高度，避免专家卡看起来臃肿。

### 5.4 卡片风格要求

- 卡片边角圆润，但不需要过大圆角。
- 卡片边框要轻，不要视觉厚重。
- 背景尽量接近主题表面色，而不是纯白硬块。
- 点击反馈采用轻微缩放即可，不需要强动画。

### 5.5 头像规范

- 头像为圆形。
- 优先使用专家头像（经 `resolveMediaUrl` 归一化后的可访问地址）。
- **无头像 / 空字符串 / 空白 / 无法解析 / 加载失败**：必须使用项目统一兜底图 `DEFAULT_CONFIG.DEFAULT_AVATAR`（`/static/images/fallbacks/avatar-default.svg`），与关注专家列表、留言作者头像等保持一致；**不得**留下空白圆形，也**不要**另起一套 iconfont 占位替代该资源。
- 实现应对齐品牌卡模式：空值 → 缺省图；`@error` → 仍回落同一头像兜底图（头像资源仅有一套缺省图，无单独 error 图）。
- 头像与文字区之间要有明显留白，避免视觉拥挤。

### 5.6 文本规范

文本从上到下的重要性：

1. 姓名：最醒目，允许一行截断。
2. 职称：次级信息，展示专家身份。
3. 医院/机构：辅助信息，展示归属。

文本过长时必须截断，不允许把卡片撑高到破坏横向节奏。

### 5.7 星标规范

星标是状态按钮，不是纯装饰图标。

- 星标样式优先复用直播间收藏的同款 iconfont 图标语言，保持首页与直播间行为语义一致。
- 已关注：高亮色收藏实心态。
- 未关注：中性灰空心态。
- 星标需要固定在卡片右上角，位置独立，不和姓名区混排。
- 星标点击区域要足够大，避免小屏误触。

### 5.8 开播标志规范

若精选专家当前处于直播状态，职称同一行右侧需要展示一个轻量状态徽标，用于告诉用户“此人正在开播”。

- 状态为直播时显示“直播中”徽标。
- 状态不是直播时不显示徽标。
- 徽标要小，不得抢占姓名可读空间。
- 徽标颜色建议使用强调色系，但透明度要轻，避免压住整行文字。

## 6. 交互设计

### 6.1 卡片点击

点击卡片主体区域进入专家详情页。

要求：

- 点击卡片任意非星标区域都应跳转。
- 星标点击不触发卡片跳转。
- 跳转时使用专家 `id` 作为详情页参数。
- **浏览不鉴权**：未登录用户点击卡片进入专家详情属于公开浏览，不得拦截、不得 Toast「请先登录 / 未授权」、不得跳转登录页。
- 专家详情页加载时仅可请求公开接口（专家详情、专家场次等）；**禁止**在未登录态调用 `/users/me/*`（关注列表、收藏列表等），否则会误弹 401 错误。

### 6.2 关注切换

点击星标时，执行关注/取消关注。

交互要求：

- 未登录时，点击星标应跳转登录页。
- 已登录时立即发起接口请求。
- 请求中可临时阻止重复点击。
- 请求结束后同步更新本地状态。
- 登录引导仅适用于「关注 / 收藏」等用户行为，不得套用到「仅查看专家资料 / 直播列表」。

### 6.3 状态同步

关注状态需要同步两处：

- 首页星标状态。
- 用户关注列表数据源。

所以在关注成功或取消后，页面不应只改一个局部变量，而应该同时保证后续刷新能保持一致。

### 6.4 反馈文案

建议反馈：

- 关注成功：关注成功
- 取消关注成功：已取消关注
- 请求失败：操作失败
- 未登录：请先登录

文案必须短、明确、动作导向。

## 7. 状态设计

### 7.1 正常状态

模块正常显示，卡片可滑动，星标可点击。

### 7.2 空数据状态

当精选专家接口返回空数组时：

- 模块直接隐藏。
- 不展示空占位块。
- 不强行留空标题区。

这样可避免首页出现“空模块占位”破坏节奏。

### 7.3 加载状态

精选专家模块可以在首页首屏并行请求。

建议策略：

- 若数据未返回，模块先不占位或仅做轻量延迟渲染。
- 不强制展示骨架屏，以免干扰首页内容节奏。

如果后续需要骨架屏，也应保持轻量，而不是整块大灰块。

### 7.4 错误状态

精选专家接口失败时：

- 仅隐藏该模块，不阻断首页其他内容。
- 不影响 banner、直播间列表、分类等核心内容展示。
- 开发环境可打日志，线上尽量静默降级。

### 7.5 登录态状态

未登录用户：

- 可以看精选专家列表。
- 但点击星标时需要先登录。

已登录用户：

- 可直接关注/取消关注。
- 星标状态由关注列表同步得出。

## 8. 横向滚动规则

### 8.1 滚动方式

使用横向 `scroll-view` 承载卡片列表。

### 8.2 滚动提示

用户要能感知“这是一组可横滑内容”。

推荐手段：

- 卡片宽度不要铺满整屏。
- 右侧留出下一张卡片的视觉露出空间。
- 标题区副文案提示“横向滑动查看更多”。

### 8.3 卡片间距

卡片之间要有固定间距，避免密集堆叠。

### 8.4 首屏可见数量

建议首屏至少能完整看到 1 张卡片，并露出下一张卡片的一部分，帮助用户感知横向滚动行为。

## 9. 响应式与适配

### 9.1 手机端

移动端必须优先保证：

- 卡片宽度适合单手操作。
- 标题、头像、星标都能清晰识别。
- 不出现文字挤压或换行失控。

### 9.2 小屏适配

在较小屏幕上：

- 卡片宽度可以微调，但必须保证可点区域不变形。
- 医院名称过长时只展示一行。

### 9.3 横竖屏与平台兼容

当前小程序主场景是竖屏移动端，因此只需保证竖屏体验优先。若未来扩展到 H5 或平板，也应保持卡片可横滑且不破版。

## 10. 组件拆分方案

### 10.1 首页页面层职责

`src/pages/home/Home.vue` 负责：

- 请求精选专家数据。
- 请求当前关注列表。
- 调用关注/取消关注接口。
- 处理登录跳转。
- 处理详情页跳转。

### 10.2 组件层职责

`src/components/home/FeaturedExperts.vue` 负责：

- 展示精选专家横向列表。
- 渲染卡片结构。
- 接收关注状态映射。
- 把卡片点击和星标点击分别抛出事件。

### 10.3 职责边界原则

组件只负责展示和抛事件，不直接控制复杂业务流程；页面层负责业务决策、接口调用和状态落地。

这样做的原因是：

- 首页的登录态逻辑比较多。
- 关注状态要和全局行为统一。
- 组件如果承载过多业务，后续会影响复用与维护。

## 11. 数据归一化规范

由于当前项目不同接口的字段命名可能存在轻微不一致，首页精选专家模块必须做字段归一化。

### 11.1 专家列表字段兼容

允许兼容字段：

- `id` / `expert_id`
- `name` / `expert_name`
- `avatar_url` / `avatarUrl` / `avatar`
- `title` / `position` / `professional_title`
- `hospital` / `institution` / `organization`
- `department` / `dept_name`

### 11.2 归一化输出

最终用于页面渲染的数据对象应统一为：

- `id`
- `name`
- `avatarUrl`
- `title`
- `hospital`
- `department`

这样才能保证模板简单、显示稳定。

## 12. Mock 与本地联调要求

### 12.1 为什么要补 mock

如果没有 mock，本地开发时精选专家模块容易因为后端暂时未配齐而空白，影响验收。

### 12.2 mock 规则

本地 mock 至少应覆盖：

- 精选专家列表。
- 当前关注列表。
- 关注。
- 取消关注。

### 12.3 mock 数据要求

mock 数据应至少包含：

- 不少于 4 位专家。
- 至少 1 位默认已关注专家。
- 不同职称和医院字段，便于验证文本截断。
- 头像字段可统一使用同一默认头像资源，重点验证布局。

### 12.4 mock 的作用

mock 的目的不是模拟全部业务复杂度，而是保证：

- 模块能展示。
- 星标能切换。
- 首页结构能稳定验收。

## 13. 可维护性要求

### 13.1 代码分层

- 页面层处理业务。
- 组件层处理展示。
- mock 层只负责本地调试数据。

### 13.2 后续扩展点

后续如果要给精选专家加“推荐理由”“擅长领域”“直播中”标签，应优先扩展卡片内部信息层，而不是改变整体布局方向。

### 13.3 不建议的扩展方式

- 不要把精选专家做成大横幅。
- 不要把星标做成独立关注按钮块。
- 不要把模块背景做成大面积深色区块。

## 14. 风险与约束

### 14.1 数据风险

精选专家接口字段若与预期不完全一致，前端应通过归一化降低风险，但不能无限兼容到失控。

### 14.2 交互风险

星标和卡片点击容易互相干扰，因此必须严格区分点击区域。

### 14.3 视觉风险

如果卡片高度过高或信息太多，会破坏首页节奏，因此要控制卡片内容只保留最核心的三层文字。

### 14.4 登录态风险

未登录时的关注动作必须统一跳登录，否则会出现不同页面的体验不一致。

同时必须区分「浏览」与「用户行为」：

- 浏览专家详情是公开能力，未登录不应报错。
- 若详情页在未登录时顺带请求用户态接口（收藏/关注状态），会把 401 误展示成“点击专家就报错”，属于实现缺陷，必须避免。

## 15. 验收标准

模块通过验收需要同时满足以下条件：

1. 首页 banner 下方能看到“精选专家”。
2. 专家卡片是横向排列，而不是纵向列表。
3. 卡片中能看到头像、姓名、职称、医院信息；**无头像或头像加载失败时必须显示 `DEFAULT_AVATAR` 兜底图，不得空白圆。**
4. 右上角星标能准确显示关注状态。
5. 点击卡片可进入专家详情页。
6. 点击星标可直接关注/取消关注。
7. 未登录点击星标会进入登录流程。
8. **未登录点击卡片进入专家详情：可正常浏览，不弹登录/未授权错误。**
9. 空数据时模块自动隐藏。
10. 接口失败不影响首页其他内容。
11. 本地 mock 环境可以完整演示该模块。

## 16. 推荐实现顺序

如果后续继续迭代，推荐按以下顺序做：

1. 固定数据结构与接口字段归一化。
2. 完成横向卡片布局。
3. 接入关注状态和星标交互。
4. 补齐登录跳转与错误处理。
5. 再微调卡片视觉与间距。
