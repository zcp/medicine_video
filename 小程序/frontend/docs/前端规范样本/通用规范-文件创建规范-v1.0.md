## 一、说明

- 文件命名规则（避免传输/归档混淆）
- 文件存放路径（与模块结构一致）

- 本仓库下所有新增文件与新增目录

## 二、设计要点与约定

### 2.1 总体约定

- **可识别**：仅通过文件名与顶部元信息，即可判断“属于哪个项目/模块、用途是什么、版本是什么”。
- **可定位**：文件必须放在“唯一合理的位置”，避免重复目录、避免同类文件散落。
- **可追溯**：所有规范类/设计类文档必须有版本与更新日志。
- **可维护**：新增文件应尽量复用现有工具/封装（如 `src/utils/request.ts`），避免重复造轮子。

### 2.2 兼容性约定（Windows / Git）

- 禁止使用 Windows 不兼容字符：`< > : " / \\ | ? *`。
- 文件名避免尾部空格与尾部点号。
- 文档文件允许中文命名；代码与配置文件统一使用英文命名（便于跨平台与搜索）。

## 三、文件命名规范

### 3.1 命名的必备信息

- **必须包含项目名称**：用于文件在聊天/网盘/邮件中传输时不混淆。
- **必须包含版本号**：用于同一文档多版本并存/更新时不混淆。
- **建议体现类型**：规范/设计/指南/交付/问题清单/纪要 等。

### 3.2 文档文件命名（docs/）

#### 3.2.1 规范类（通用）

- 推荐：`通用规范-<主题>规范-v<版本>.md`
- 示例：`通用规范-文件创建规范-v1.0.md`

#### 3.2.2 设计类（项目/模块）

- 推荐：`<项目>-<主题>设计文档-v<版本>.md`
- 示例：`vzan_simul_frontend-登录与跨应用跳转设计文档-v1.0.md`

#### 3.2.3 开发指南类（模块落地）

- 推荐：`<模块>功能模块开发指南-v<版本>.md`
- 示例：`直播观看功能模块开发指南-v1.0.md`

#### 3.2.4 交付说明（HANDOFF）

- 推荐：`HANDOFF_<模块>_<范围>_交付说明-v<版本>.md`
- 示例：`HANDOFF_专家品牌直播间动态Tab_交付说明-v1.0.md`

#### 3.2.5 问题清单 / 对齐记录

- 推荐：`<主题>-问题清单-YYYY-MM-DD.md` 或 `<主题>-接口对齐问题总结-YYYY-MM-DD.md`

### 3.3 代码文件命名（src/）

#### 3.3.1 文件名大小写

- `.ts`：采用 `lowerCamelCase.ts`（与现有 `featuredContent.ts`、`notifications.ts` 风格一致）
- `.vue` 组件：采用 `PascalCase.vue`（组件）或 `index.vue`（页面入口）
- 目录名：采用 `kebab-case`（与 `subpackages/room-detail` 风格一致）

#### 3.3.2 禁止事项

- 禁止在代码文件名中夹带环境信息：`xxx-dev.ts`、`xxx-prod.ts`（环境差异应放在配置层）
- 禁止出现“临时/测试”但未声明用途的文件：`temp.ts`、`test2.vue`（若必须存在，需放入 `test/` 或 `mock/` 并说明）

## 四、目录与存放规范

### 4.1 顶层目录原则

- 禁止随意新增顶层目录；新增目录必须先判断是否可归入现有目录（`src/`、`docs/`、`scripts/`、`test/`、`src/mock/` 等）。

### 4.2 `docs/` 文档归档规则

- 业务设计/接口设计/模块指南：放在 `docs/` 根目录或对应子目录。
- “可复用的通用规范样本”：放在 `docs/前端规范样本/`。
- 文档若与某次交付强绑定：优先与同类 HANDOFF 文档放在一起，并在文档开头说明“适用版本/适用范围”。

### 4.3 `src/` 代码归档规则（常用）

- `src/pages/`：TabBar 主包页面
- `src/subpackages/`：分包页面（按业务模块建立 `kebab-case` 目录）
- `src/components/`：通用组件与业务组件
- `src/api/`：API 接口封装（一个业务域一个文件）
- `src/types/`：类型定义（一个业务域一个文件，与 `src/api/` 对齐）
- `src/utils/`：工具函数（通用且可复用；避免与业务强耦合）
- `src/store/`：Pinia 状态管理（若为空目录，保留 `.gitkeep` 并在 README/文档中说明启用策略）

## 五、不同文件类型的内容要求

> 说明：不同用途的文件必须具备不同的“最小可用内容（MVC: Minimum Viable Content）”。本章节定义各类文件的必填字段与推荐结构。

### 5.0 目录维度（所有文档类通用）

凡 `docs/` 下规范 / 设计 / 指南 / HANDOFF 等**文档类**新建或大改时，须带**可跳转目录**：

| 项 | 要求 |
|----|------|
| 位置 | 文首元信息（项目/版本/日期/状态等）之后、正文第一章之前 |
| 形态 | `## 📋 目录`（或 `## 📑 目录`）+ 有序列表；条目链到本文章节锚点 |
| 一致性 | 目录条目与一级（必要时二级）章节标题一一对应；增删章节时同步改目录 |
| 锚点 | Markdown 标题锚点或显式 `<a id="..."></a>` 均可；以预览可点击为准 |
| 短文豁免 | 正文一级标题 ≤3 个且全文很短时，可省略目录，但须在文首声明「本文过短，省略目录」 |

> 检查清单 §8.2「目录锚点可用」以此为准。代码文件（`src/**`）不适用本节。

### 5.1 规范类文档（如：通用规范）

**必填**：
- 项目、版本、创建日期、状态
- 说明（功能/适用范围/依据/声明）
- **目录**（见 §5.0）
- 设计要点与约定
- 检查清单
- 更新日志

**推荐补充**：
- 常见错误与反例
- 可复制模板

### 5.2 设计类文档（业务方案/技术方案）

**必填**：
- 项目、版本、创建日期、状态
- **目录**（见 §5.0）
- 背景与目标（说明“为什么做”）
- 范围定义（做什么/不做什么）
- 术语与关键概念
- 核心流程（可用文字 + 流程图/时序图，二选一即可）
- 数据结构/字段约定（与类型系统对齐）
- 权限与可见性（如涉及登录/角色/状态）
- 错误处理与兜底策略
- 测试要点（至少列出关键路径）
- 更新日志

#### 5.2.1 前端设计文档额外必填（体验层 + 落地层）

适用于 `Live-Saas-Wechat-*-前端设计文档-*.md` 及同类「前端设计」。真源说明见 [AI-工作约定 §5.1](../AI-工作约定.md)。

**管线**：后端/增量契约 → **一份**前端设计（体验写在契约前）→ 实现。禁止默认再开第三本「页面设计文档」。

**体验钉五问**（文首或范围/页面章须能直接答出）：

1. 给谁用？（普通用户 / 房主 / Admin；多面须分面）  
2. 做完哪一件事算成功？（闭环 + 完成定义）  
3. 首屏只能留什么？  
4. 空了、满了、没权限时怎么办？  
5. 本页明确不做什么？

**体验层推荐章节**（小增量可压缩为五问短表）：受众面、闭环与完成定义、非目标封印、入口与导航、信息架构/首屏、主路径、关键态、权限与人话、危险/可逆、对标边界。

**落地层推荐章节**：落点文件、API/字段摘录、类型映射、现码差集、分期与验收、命中的规范样本链接。

**裁剪**：小增量 = 五问 + 落地表；新管理列表/新 C 端主路径再补齐体验推荐章；跨多页编排才考虑另开「页面编排」类文档（勿与单功能前端设计重复开「页面设计」）。

### 5.3 开发指南（模块落地指导）

**必填**：
- 适用范围与入口（页面路由/菜单入口/触发条件）
- **目录**（见 §5.0）
- 依赖的 API 与类型文件（指向 `src/api/*` 与 `src/types/*`）
- 页面结构与组件复用策略
- 表单与校验（引用《编辑页面数据与校验规范》）
- 列表展示（引用《通用数据列表展示规范》）
- 返回与跳转（引用《页面返回机制设计文档》）
- 测试要点

### 5.4 交付说明（HANDOFF）

**必填**：
- **目录**（见 §5.0；短交付可豁免并声明）
- 交付范围（做了什么/没做什么）
- 文件清单（新增/修改的关键文件路径列表）
- 关键实现点（3-7 条即可）
- 风险与注意事项
- 待办（如果有）

### 5.5 API 文件（`src/api/*.ts`）

**必填**：
- 文件名与业务域一致（如 `expert.ts` 只放专家域接口）
- 所有接口使用统一请求封装（如 `src/utils/request.ts`）
- 入参/出参类型完整（来自 `src/types/*.ts`，禁止 `any` 泛滥）

**禁止**：
- 在 API 文件内硬编码 baseURL、Token、Secret 等（参考《前端配置安全性说明》与《前端安全编程规范》）

### 5.6 类型文件（`src/types/*.ts`）

**必填**：
- 与 API 业务域对齐
- 类型命名语义清晰：`Expert`、`ExpertDetail`、`ExpertListItem`、`CreateExpertPayload`、`UpdateExpertPayload` 等
- 对后端字段保持一致；如需前端映射，必须明确转换层位置（例如 `utils/mapper`）

### 5.7 页面文件（`src/pages/**/index.vue`、`src/subpackages/**/index.vue`）

**必填**：
- 路由参数解析（`onLoad`）与参数校验（非法时给出兜底提示/跳转）
- 接口调用与加载态/空态/错误态
- 返回策略（如需要返回按钮，遵循《页面返回机制设计文档》）

### 5.8 Mock/测试文件

- `test/`：放可运行的单元测试/组件测试，命名 `*.test.ts`
- `src/mock/` 或 `docs/`：放 Mock 规则/Mock 数据说明
- CSV/JSON 数据文件：必须说明来源、生成方式、脱敏策略（如包含用户信息）

## 七、创建与变更流程

### 7.1 新增文件（通用流程）

1. 确认文件类型（规范/设计/指南/代码/API/类型/测试等）
2. 选择唯一合理的存放路径（遵循第 4 章）
3. 按第 3 章规则命名文件
4. 按第 5 章填写“最小可用内容”（文档需元信息 + **§5.0 目录** + 更新日志）
5. 若新增页面/分包：同步更新 `pages.json` 与相关入口
6. 若新增 API/类型：保证与现有封装一致，并完成类型对齐
7. 自查：对照第 8 章检查清单

### 7.2 修改已有文件

- 修改规范/设计/指南类文档：必须更新“更新日志”。
- 修改 API/类型：必须同步影响面（调用方、页面、测试、Mock）。
