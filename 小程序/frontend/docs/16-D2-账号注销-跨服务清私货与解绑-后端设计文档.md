## 📌 核心定位说明

### 1. 本文档的定位

本文档专注于**账号注销成功之后**的 live_core **私货清理 + 身份解绑 + 已注销标记**：

**包含能力**:
- **专家认领解绑（P03）** / **品牌成员移除（P04，仅注销）**
- **个人关系清理（P05–P09）**：按上表软藏或物理删
- **已注销标记**：供 `16-D3` 留言展示，避免按页跨服务查 users
- **跨服务编排**：users → live_core Internal（best-effort）

**模块范围**:
- **0** 新业务表（P0 优先 Redis 标记；单表标记为备选）
- **1** 个 Internal 清理接口 + users 一处出站调用
- **明确不做**: 删房；删留言；封禁清私货；补偿表（P2）

### 2. 本文档的核心特点

- ✅ 私货对用户不可见 + 身份解绑
- ✅ **有 `is_active` 就软藏**，对用户行为模块更友好
- ✅ 封禁不触发（R2）
- ✅ 为 D3 提供本服务可读标记（最快闭环）

### 3. 业务价值说明

- 注销后「我的收藏/订阅/偏好」立刻空
- 专家位、品牌成员不残留死人号
- 留言占位不依赖每页调 users

| 表 | 日常用户操作 | **注销时（本包）** |

| `user_favorites` | `is_active=false` | **`is_active=false`（软藏）** |
| `user_subscriptions` | `is_active=false` | **`is_active=false`（软藏）** |

| `user_expert_subscriptions` | 取消关注硬删 | **物理 DELETE** |

### 1.2 变更决策记录

#### 决策 1：编排方式

| 方案 | 结论 |
|------|------|
| users commit 后 HTTP best-effort 调 live_core | ✅ **P0**（失败打日志，可手工重调同一 Internal） |
| MQ / 补偿表 | ❌ 非 P0 |

#### 决策 2：软藏 vs 一律物理删

| 方案 | 结论 |
|------|------|
| 有 `is_active` 软藏，其余物理删/解绑 | ✅ **V1.1 采用（更友好、更快）** |

#### 决策 3：封禁

| 方案 | 结论 |
|------|------|
| 仅注销触发 | ✅ |
| 封禁也清 | ❌ R2 |

#### 决策 4：已注销标记（供 D3）

| 方案 | 结论 |
|------|------|
| cleanup 开头 Redis `SADD deactivated_users` | ✅ **P0 优先（无 DDL）** |
| 单表 `deactivated_user_markers` | 备选 |
| 留言按页 batch 查 users.status | ❌ 不做（慢、违 V3） |

## 3. API 接口设计

### 3.1 【新增】注销清理（Internal）

**Endpoint**: `POST /api/v1/internal/users/{public_id}/deactivate-cleanup`

**描述**: 按用户物理清除私货并解绑认领/品牌成员。幂等：重复调用结果为 0 行删除仍返回 200。

**认证**: `X-Internal-Token`

**路径参数**:
- `public_id` (UUID, required): 用户 public_id

**请求体**:
```json
{
  "reason": "user_deactivate",
  "request_id": "optional-idempotency-key"
}
```

**成功响应** (`200 OK`):
```json
{
  "code": 200,
  "message": "success",
  "data": {
    "user_public_id": "uuid",
    "deleted_counts": {
      "user_favorites": 3,
      "user_subscriptions": 1,
      "watch_history": 10,
      "user_expert_subscriptions": 2,
      "user_preferences": 1,
      "notifications": 5,
      "user_search_history": 8
    },
    "unbound_experts": 1,
    "removed_brand_members": 1
  },
  "timestamp": "2026-07-22T10:00:00Z"
}
```

**失败响应** (`403`):
```json
{
  "code": 3002,
  "message": "内部服务鉴权失败",
  "data": null,
  "timestamp": "2026-07-22T10:00:00Z"
}
```

**执行流程**:

1. 校验 Internal Token（失败 → **403**）  
2. 解析 `public_id`  
3. **【最先】写入已注销标记**（Redis SADD 或 markers 表）——保证 D3 尽快生效  
4. 开事务  
5. `UPDATE experts SET user_id=NULL WHERE user_id=:uid`  
6. `DELETE brand_members WHERE user_id=:uid`  
7. `UPDATE user_favorites SET is_active=false WHERE user_id=:uid AND is_active=true`  
8. `UPDATE user_subscriptions SET is_active=false WHERE user_id=:uid AND is_active=true`  
9. `DELETE` watch_history / user_expert_subscriptions / user_preferences / notifications / user_search_history（按 user_id）  
10. commit；返回各表影响行数  
11. **禁止** 触碰 `live_rooms` / `live_room_messages`  

**HTTP状态码**: `200` / `403`（鉴权）/ `422` / `500`

---

### 3.2 【修改】注销账号出站（users）

**Endpoint**: `DELETE /api/v1/users/me`

**描述**: 在《10》流程 commit 成功后，增加 best-effort 调用本包 Internal 接口。

**执行流程（增量步骤）**:

1. …（验证码、会员闸门、软删、吊销，见《10》/`16-D0`）  
2. **users `commit` 成功**  
3. **【新增】** HTTP `POST {LIVE_CORE_URL}/api/v1/internal/users/{public_id}/deactivate-cleanup`  
   - Header: `X-Internal-Token`  
   - Timeout: 建议 3–5s  
4. 成功：打 info 日志（含 deleted_counts 摘要）  
5. 失败：**不**回滚注销；打 error；写入补偿（P1）或告警  
6. 向客户端返回注销成功（与清理成败解耦）

## 4. 执行流程详细说明

### 4.1 端到端

```
1. 用户注销
2. users 软删 + 吊销 + commit
3. users → live_core deactivate-cleanup
4. 解绑 experts / 删 brand_members
5. 物理清私货七类表
6. commit live_core
7. 返回注销成功给用户
8. [失败] 补偿重试（P1）
```

### 4.2 与封禁对比

```
封禁 → 仅吊销
     → 不调 deactivate-cleanup
     → brand_members / 私货保留
```

## 5. 错误处理与事务管理

### 5.1 错误处理策略

- Internal 鉴权失败 → 403，users 侧记失败  
- 部分 SQL 失败 → 整事务回滚，users 记失败并重试全量（接口幂等）  
- 禁止「清一半提交」  

### 5.2 事务管理规范

```python
async with db.begin():
    await unbind_experts(...)
    await delete_brand_members(...)
    await delete_favorites(...)
    # ... 其余表
# 成功一次性提交
```

**跨库**: users 已提交不可回滚；采用「注销成功 + 清理最终一致」。

## 6. 性能优化建议

### 6.1 数据库优化

- 各表已有 `user_id` 索引则直接 `DELETE WHERE user_id`  
- 若单用户通知量极大：可分批 `DELETE ... LIMIT` 循环（P1）

### 6.2 缓存策略

- 清理后如有「我的收藏」等缓存，按 `user_id` 失效  

### 6.3 应用层优化

- 单次 Internal 请求内顺序删除即可；勿对每张表单独 HTTP
