# 收藏功能：前端 Bug 修复记录

**问题**: 快速点击收藏导致并发请求（500/400 错误）+ `showLoading/hideLoading 必须配对使用` 警告  
**修复时间**: 2026-04-22  
**状态**: ✅ 已修复，需重新构建  
**涉及文件**: `src/utils/request.ts` · `src/store/userFavorites.ts` · `src/pages/live/LiveView.vue`

---

## 一、问题现象

微信开发者工具控制台：

```
POST /api/core/users/me/favorites  →  500 Internal Server Error
POST /api/core/users/me/favorites  →  400 Bad Request（已收藏）

vendor.js:5601  请注意 showLoading 与 hideLoading 必须配对使用
  hideLoading  @ request.js:146
  _callee$     @ request.js:227   ← finally 块
  addFavorite  @ favorites.js:5
  add          @ userFavorites.js:362
  handleFavorite @ LiveView.js:1559
```

同一次点击触发两条请求；第一条引发服务端并发写入冲突（500），第二条因已写入成功返回 400。

---

## 二、根本原因分析

### 根因 1 — `request.ts`：`handleError` 被调用两次

```typescript
// 问题代码
try {
  if (response.statusCode >= 400) {
    return this.handleError(...)   // ① handleError 抛出 Error
  }
} catch (error) {
  return this.handleError(error, finalConfig)  // ② catch 再次调用 → Toast/logger 触发两次
} finally {
  if (finalConfig.loading) this.hideLoading()
}
```

`handleError` 返回 `never`（始终 throw）。`try` 内调用后抛出的错误被 `catch` 再次捕获，导致错误 Toast 显示两次、loading 计数器被多减一次。

### 根因 2 — `request.ts`：`showToast` 隐式关闭 loading 对话框

WeChat 的 `uni.showToast` 和 `uni.showLoading` **共享同一个全局 overlay**。`handleError` 调用 `showToast` 时，WeChat 内部已隐式关闭了 loading 对话框。之后 `finally` 块仍调 `uni.hideLoading()`，WeChat 找不到激活的 loading → **触发警告**。

```
showLoading()                  ← count=1, WeChat 打开 loading
  请求返回 5xx/4xx
  handleError() 内:
    uni.showToast()            ← WeChat 关闭 loading（隐式，两者共享 overlay）
    throw
finally:
  hideLoading()                ← count: 1→0, 调 uni.hideLoading()
                                  WeChat: "无激活 loading" → ⚠️ 警告
```

> ⚠️ **常见误解**：下载 handler 直接调用 `uni.showLoading`（绕过计数器）属于另一个相关但独立的问题——当下载与收藏并发时会导致计数器串扰，但不是触发此条警告的根因。

### 根因 3 — `userFavorites.ts`：Store 层无每房间并发保护

`add()`/`remove()` 无幂等保护。页面层的 `favoriteBusy` 仅保护单个页面实例；微信小程序的 `setTimeout` 排队导致两次回调在同一 tick 均读到 `favoriteBusy = false` 并进入。

## 三、修复内容

### Fix 1 — `request.ts`：`__handled` 标记防止 `handleError` 二次调用

```typescript
// handleError 中
const err = new Error(message)
;(err as any).__handled = true   // ← 新增

// request() 的 catch 块
} catch (error: any) {
  if (error?.__handled) throw error   // ← 跳过已处理的错误
  return this.handleError(error, finalConfig)
}
```

同样修复了 `upload()` 方法的对应 `catch` 块。

### Fix 2 — `request.ts`：先 `hideLoading` 再 `showToast`，并加 count 守卫

```typescript
// handleError 中：调整执行顺序
if (config.loading) {
  this.hideLoading()             // ① 先关 loading（count 归零，uni.hideLoading() 正常调用）
}
if (config.showError !== false) {
  uni.showToast(...)             // ② 再弹 toast（overlay 已空，无冲突）
}

// hideLoading 加 count 守卫，防止 finally 二次调用
private hideLoading() {
  if (this.loadingCount <= 0) return   // ← 守卫：count=0 时提前退出
  this.loadingCount--
  if (this.loadingCount === 0) {
    uni.hideLoading()
  }
}
```

此后 `finally` 的 `hideLoading()` 因 count 已为 0 提前 return，不再调 `uni.hideLoading()`，警告消除。

### Fix 3 — `userFavorites.ts`：Store 层每房间并发保护

```typescript
// state
pendingRoomIds: new Set<string>()

// add / remove 统一三段式保护
async add(roomId: string) {
  const rid = String(roomId || '').trim()
  if (!rid) return
  if (this.pendingRoomIds.has(rid)) return   // ← 幂等：已在进行中则跳过
  this.pendingRoomIds.add(rid)
  try {
    // ... API 调用
  } finally {
    this.pendingRoomIds.delete(rid)           // ← 无论成败都释放
  }
}
```

### Fix 4 — `LiveView.vue`：下载 handler 改用统一计数器

```typescript
// 修复前
uni.showLoading({ title: '下载中...' })
uni.hideLoading()

// 修复后
import { showGlobalLoading, hideGlobalLoading } from '@/utils/request'
showGlobalLoading('下载中...')
hideGlobalLoading()
```

防止下载与收藏并发时 loading 计数器被直接绕过导致串扰。

## 四、三层防御体系

| 层级 | 位置 | 保护范围 | 机制 |
|------|------|---------|------|
| 页面层 | `LiveView.vue : favoriteBusy` | 同一页面实例的快速连击 | boolean 锁 |
| Store 层 | `userFavorites.ts : pendingRoomIds` | 跨组件并发触发同一房间 | Set 幂等 |
| 请求层 | `request.ts : __handled` | 单次请求内错误处理重复执行 | 已处理标记 |
| Loading 层 | `showGlobalLoading / hideGlobalLoading` | loading 计数器不被绕过 | 统一计数 |

> ❗ `__handled` 保护的是**单次请求内错误处理不重复**，不能防止并发多请求，两者职责不同。

## 五、已知的接口约定偏差（另文记录）

1. **HTTP 400 处理（前端适配正确，无需修改）**：后端返回 HTTP 400 表示"已收藏"，是符合 REST 规范的行为（比设计文档定义的 HTTP 200 + 业务码 2002 更标准）。Store 中对 400 的处理是合理的适配，不是临时补丁。
   → 详见 [`../api-contract/前后端接口偏差_2026-04-22.md` — 偏差一](../api-contract/前后端接口偏差_2026-04-22.md)

2. **收藏列表缺少 `room_title` / `room_cover_url`（后端 Bug，已有降级方案）**：后端未 JOIN `live_rooms` 表，前端已通过 `hydrateMissingRoomInfo()` 自动降级补全，收藏页不会永久为空，但每次刷新产生 N 条额外请求。
   → 后端修复见 [`../api-contract/后端修复-收藏列表字段缺失.md`](../api-contract/后端修复-收藏列表字段缺失.md)

## 六、验证方法

1. 快速连续点击收藏按钮 → 网络面板只出现 **1 条** `POST /users/me/favorites`
