## 偏差一：`POST /users/me/favorites` — 设计文档规范争议

### 现象

后端实际返回 HTTP 400（已收藏时），设计文档（V2.0 Section 4.8.1）定义为 HTTP 200 + 业务码 2002。

### 分析：后端的 HTTP 400 并非错误

| 方案 | REST 语义 | 行业惯例 |
|------|---------|---------|
| 设计文档：HTTP 200 + code 2002 | ❌ 状态码撒谎（200但业务失败） | 部分国内老系统风格 |
| 实际后端：HTTP 400 Bad Request | ✅ 请求本身有问题（重复收藏） | 符合 REST 规范 |
| 更优选择：HTTP 409 Conflict | ✅✅ 最精确（资源冲突） | 最标准写法 |

后端返回 HTTP 400 是更符合 REST 规范的行为，**不应要求后端改回 HTTP 200 + 业务码**。

### 前端适配现状（正确）

```typescript
// userFavorites.ts — 对 HTTP 400 的适配是合理的
if (statusCode === 400 && /已收藏|资源已存在|already/i.test(msg)) {
  this.favoriteStatus[rid] = true
  return
}
```

### 行动项

**设计团队**：评估是否将设计文档的 HTTP 200 + 2002 规范修订为 HTTP 400 或 HTTP 409，统一后续新接口的错误码约定。  
**前端**：当前适配无需改动，若后端将来改为 409，同步修改条件判断。

## 偏差二：`GET /users/me/favorites` — 响应字段缺失（后端 Bug）

### 文档定义（V2.0 Section 4.8.2）

```json
{
  "id": "...",
  "room_id": "...",
  "room_title": "肝胆外科微创手术研讨",
  "cover_url": "https://...",
  "created_at": "..."
}
```

### 实际行为（日志）

```
sample raw item keys: ["id", "room_id", "is_active", "created_at"]
```

实际响应中 `room_title`、`cover_url` 字段完全缺失，后端仅返回 `user_favorites` 表本身的字段，未 JOIN `live_rooms` 表。

### 前端降级方案（已存在）

`userFavorites.ts` 的 `fetch()` 完成后会自动触发 `hydrateMissingRoomInfo()`，通过逐条调用 `GET /rooms/{room_id}` 补全缺失的标题和封面。这个降级机制**已经实现并运行**，收藏页标题不会永久为空。

代价：每次刷新收藏列表后额外产生 N 条 `GET /rooms/{id}` 请求，N = 缺少标题的条数。

### 修复方向

**后端**（根本修复）：收藏列表 query 补充 JOIN `live_rooms` 表，返回 `room_title`、`cover_url`。后端修复后前端的 `hydrateMissingRoomInfo` 将自动跳过（因为字段已存在），无需改动前端代码。

## 偏差三：`POST /sessions/{id}/watch` — **前端 Bug**（两处）— ✅ 已修复（2026-04-23）

### Bug A：`progress` 字段单位错误（严重）

后端文档（V2.0 Section 4.9.1）定义 `progress` 为**秒数**：
```json
{ "progress": 360 }   // 360 秒 = 6 分钟
```

主路径 `recordWatchSession` 实际传入：
```typescript
// LiveView.vue L1272–1279
await recordWatchSession(sessionId.value, {
  progress: progressPercent,   // ← progressPercent 是 0~100 的百分比！
  lastPosition: lastPos        // lastPos 才是秒数
})
```

降级路径 `recordWatch` 传入：
```typescript
// LiveView.vue L1284
await recordWatch(sessionId.value, lastPos, { ... })   // ← lastPos 秒数，正确
```

| 路径 | `progress` 值 | 单位 | 是否符合文档 |
|------|------------|------|---------|
| 主路径 `recordWatchSession` | `progressPercent` | 百分比 0~100 | ❌ 错误 |
| 降级路径 `recordWatch` | `lastPos` | 秒 | ✅ 正确 |

**后端接口上线后，主路径会写入错误的进度数据**（用户看了 360 秒，后端收到 `progress: 2`）。

**修复**（前端）：
```typescript
// 修复前
progress: progressPercent,

// 修复后
progress: lastPos,    // 秒数，与后端文档一致
```

### Bug B：扩展字段平铺（次要）

文档要求扩展字段放入 `extra` 嵌套对象，前端将其平铺在根层：

```typescript
// 当前（平铺）
{ progress: lastPos, reason: 'pause', startTime: ..., duration: ... }

// 应改为
{ progress: lastPos, extra: { reason: 'pause', startTime: ..., duration: ... } }
```

后端若宽松处理平铺字段，不影响 `progress` 写入；若严格校验，会报 422。建议前端先修复 Bug A，再同步调整结构。

→ 详见 [`../watch-history/前端设计缺陷_2026-04-22.md`](../watch-history/前端设计缺陷_2026-04-22.md)

## 偏差四：`GET /me/preferences` — **前端路由配置错误** — ✅ 已修复（2026-04-23）

### 问题分析

`user_preferences` 存储科室星标、视图模式等行为偏好数据，与 `favorites`/`watch-history` 同属用户行为层，应由 Core Service 处理。原路径 `/me/preferences` 被 `shouldUseUsersGateway` 判定为 Users Service，路由错误。

| 接口 | 数据性质 | 修复前路径 | 修复后路径 |
|------|---------|-----------|-----------|
| `GET /me/preferences` | 行为偏好 | `/me/preferences` → Users Service ❌ | `/users/me/preferences` → Core Service ✓ |

### 已修复实现

`src/store/preferences.ts` 两处路径已更正为 `/users/me/preferences`：

```typescript
// 当前正确实现
async apiGetUserPreferences() {
  return request({ url: '/users/me/preferences', method: 'GET' })
},
async apiUpdateUserPreferences(patch) {
  return request({ url: '/users/me/preferences', method: 'PATCH', data: patch })
},
```

后端接口上线后以此路径验证（与后端设计文档 V2.1 Section 4.15 一致）。
