# 我的直播在清缓存后丢失（首页仍可见）根本闭环报告

缺陷ID: FE-BE-MYLIVE-20260506-01  
发现时间: 2026-05-06  
当前状态: 已定位链路，待补齐实证后关闭  
优先级: P1  
责任域: FE + BE + QA + 产品

## 1. 问题现象

同一管理员账号创建直播后：

1. 在我的直播页面可看到并管理该直播间。
2. 清除缓存后再次进入：
   - 首页仍能看到该直播间卡片。
   - 我的直播列表为空，找不到自己创建的直播间。

说明直播间实体仍存在，但我的直播链路在清缓存后不可恢复。

---

## 2. 关键结论

首页与我的直播是两条不同数据链路：

1. 首页走公开列表接口，不依赖本地 my_live_cache。
2. 我的直播依赖用户归属接口；接口失败时才回退本地 my_live_cache。
3. 清缓存会删除 my_live_cache，因此暴露用户归属接口不可用或规则不一致问题。
4. 现有设计文档对“我的直播间 / 按当前登录用户过滤”未形成统一契约；`GET /api/v1/rooms` 仅明确了通用列表语义与通用筛选，是否存在专用“我的房间”接口或 owner-only 过滤，仍需后端源码或联调继续核验。

---

## 3. 功能链路（代码锚点）

### 3.1 创建直播会写入本地缓存

1. 入口: src/pages/live/CreateLive.vue
2. 方法: persistMyLiveRoom(...)
3. 行为: 调用 upsertMyLiveCache(userId, roomData)

### 3.2 我的直播优先远端，失败才本地回退

1. 入口: src/pages/my-live/MyLive.vue
2. 行为:
   - 先调用 getMyRooms(undefined, 1, 20)
   - 成功时 mergeMyLiveCache(用户ID, 远端items)
   - 404 时 applyLocalFallback() 读取 readMyLiveCache(用户ID)
3. 路径来源: src/api/room.ts + src/config/api.ts 中 USER_BEHAVIOR.MY_ROOMS
4. 说明: 当前仅能确认前端存在该调用链路；后端是否对该路径提供正式支持，以及是否应改为专用“我的房间”接口，尚未得到源码级证实。

### 3.3 首页独立公开链路

1. 入口: src/pages/home/Home.vue
2. 行为: getHomepageRooms -> GET /homepage/rooms
3. 特征: 与 my_live_cache 无耦合

### 3.4 清缓存触发点

1. my_live_cache 键前缀: src/common/constants.ts 中 MY_LIVE_CACHE
2. 缓存读写: src/utils/myLiveCache.ts
3. 一旦清空缓存且远端接口不可用，页面将空列表。

## 4. 根本定义（先定规则再定责）

本问题是否为缺陷，取决于产品规则定义。必须先固化以下唯一口径：

1. 我的直播展示口径 A: 仅本人创建。
2. 我的直播展示口径 B: 本人创建 + 被授权管理。
3. 我的直播展示口径 C: 管理员可见全量。

当前建议默认口径为 B（兼顾归属性与运营授权），并在 PRD/API 契约中写死。未定口径前，禁止以主观预期判定后端或前端责任。

## 5. 登录态反证（必须具备）

为排除清缓存后未登录造成的假阳性，必须提供以下反证，未满足则不得关闭问题：

1. 清缓存后重新登录成功。
2. 登录后可调用至少一个鉴权接口成功（例如 /users/me 返回 200）。
3. 同一会话下，首页可见目标房间，同时我的直播为空或异常。
4. 记录请求头中 Authorization 已携带且非空。

结论规则：若以上 1 至 4 均成立，仍复现我的直播丢失，才能判定为登录态已排除。

## 7. 根因分层（在证据成立后使用）

### 7.1 主根因（当前证据下）

用户归属链路存在不可用或契约未明确的问题：运行时日志已显示 `/api/users/me` 与 `/api/core/users/me/rooms` 均返回 404，但在当前 workspace 内无法核对后端源码，因此无法进一步确认是路由缺失、实现缺失还是网关/权限配置问题。

### 7.2 放大因子

前端本机缓存降级不可跨设备且不可抗清缓存，掩盖了主链路缺陷并在清缓存后集中暴露。

### 7.3 非根因

首页正常仅说明公开可见性链路正常，不代表用户归属链路正常。

### 7.4 文档结论

现有设计文档已明确通用房间列表接口 `GET /api/v1/rooms`，但没有把“我的直播间 / owner-only”作为正式契约写清楚；因此“文档遗漏”成立，但“后端已支持 owner_only/user_id 过滤”目前不能视为已证实事实。

---

## 8. 修复方案（执行顺序）

### 第一步: 后端修正主链路

1. 明确唯一契约：是提供稳定的 GET /api/v1/users/me/rooms，还是在 GET /api/v1/rooms 上补充 owner-only 过滤语义。
2. 若采用“我的房间”专用接口，需要明确返回口径对齐第 4 章定义，并保证分页字段完整: items、total、page、size。
3. 若采用通用列表扩展方案，需要在文档中写死 owner_only / user_id / q 的组合语义与鉴权要求。

### 第二步: 前端降级策略收敛

1. 接口成功时以远端为准再 merge 本地缓存。
2. 接口失败且有缓存: 显示降级提示并埋点。
3. 接口失败且无缓存: 显示接口不可用提示，禁止误导文案为暂无创建。

### 第三步: 产品和文档固化

1. 在 PRD 与 API 文档写死我的直播归属定义。
2. QA 用例按定义拆分为创建者、授权管理者、管理员三组。
