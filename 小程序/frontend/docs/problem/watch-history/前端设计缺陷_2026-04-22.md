## 问题一：`flushWatchRecord` 虚假降级 — 两个函数调用同一路径

**状态**: ✅ 已修复（2026-04-23）— 移除虚假降级，改为单次 `recordWatchSession` 调用；请求体扩展字段统一包裹进 `extra`；删除 `history.ts` 中的 `recordWatch` 兼容函数

### 现象

每次视频暂停（pause 事件），控制台产生两条相同请求：

```
POST http://localhost:8080/api/core/sessions/{id}/watch  →  404
POST http://localhost:8080/api/core/sessions/{id}/watch  →  404
```

两条请求来自同一逻辑，`flushWatchRecord` 先调主路径，失败后"降级"到备用路径。

### 根因

`LiveView.vue` 的 `flushWatchRecord`（L1272–1296）设计了一个降级逻辑：

```
recordWatchSession（主路径）
    ↓ 失败
recordWatch（降级路径）
```

但 `src/api/session.ts` 中的 `recordWatchSession` 和 `src/api/history.ts` 中的 `recordWatch` 内部**均调用同一个路径**：`API_PATHS.HISTORY.RECORD_WATCH(sessionId)`。

实际效果：

```
第一次调用 → POST /sessions/{id}/watch → 404
  ↓ catch
第二次调用 → POST /sessions/{id}/watch → 404（完全相同的路径和参数）
```

降级没有切换到不同的备用端点，等于无意义地重复发了同一条请求，产生双倍 404 日志噪音，也意味着降级永远不能成功。

### 影响

- **功能**：观看记录目前完全无法写入（后端接口尚未上线），两次调用均失败，影响一致。
- **日志**：每次 pause 产生 2 条 404，实际应只有 1 条，干扰问题排查。
- **性能**：无谓消耗 1 次网络请求（后端接口上线后会产生两次真实请求，浪费服务器资源）。

### 已修复实现

`LiveView.vue` 中 `flushWatchRecord` 当前为单次调用，使用 `extra` 嵌套结构，无二次降级：

```typescript
await recordWatchSession(sessionId.value, {
  progress: lastPos,
  extra: { reason, startTime, endTime, duration: durationSec,
           lastPosition: lastPos, mediaDuration: mediaDur }
})
```

`src/api/history.ts` 中的 `recordWatch` 兼容函数已不再被 `flushWatchRecord` 调用。

接口请求体格式偏差详见：[`../api-contract/前后端接口偏差_2026-04-22.md` — 偏差三](../api-contract/前后端接口偏差_2026-04-22.md)

## 问题二：`recordWatchSession` 传入 `progress` 单位错误

**状态**: ✅ 已修复（2026-04-23）— `progress` 由 `progressPercent`（百分比）改为 `lastPos`（秒）  
**涉及文件**: `src/pages/live/LiveView.vue`

### 现象

后端文档（V2.0 Section 4.9.1）定义 `progress` 字段为**秒数**（整数，表示观看进度秒数）。

```json
{ "progress": 360 }   // 360 秒 = 6 分钟
```

### 根因（已修复）

修复前，主路径错误传入 `progressPercent`（0–100 百分比）而非 `lastPos`（秒）；同时存在虚假降级，降级路径恰好传入了正确单位，掩盖了主路径的问题。

### 已修复实现

当前 `flushWatchRecord` 中 `progress` 统一使用 `lastPos`（秒），与后端文档一致：

```typescript
// LiveView.vue — 当前正确实现
await recordWatchSession(sessionId.value, {
  progress: lastPos,           // ← 秒数，正确
  extra: { reason, startTime, endTime, duration: durationSec,
           lastPosition: lastPos, mediaDuration: mediaDur }
})
```

## 问题三：观看历史页缺少“预告”筛选项，且预告直播间开播后没有卡片提示

**状态**: 🟡 待修复
**涉及文件**: `src/pages/profile/ViewHistory.vue` · `src/store/watchHistory.ts` · `src/types/history.ts`

### 现象

当前观看历史页的筛选维度只有“直播/回放”，用户无法直接切换查看“预告”场次；当某个预告场次后续真正开播时，历史列表里的对应卡片也没有任何状态提示，容易让用户误以为列表没有更新。

### 期望设计

1. 观看历史页的筛选项应包含“预告”。
2. 预告场次在历史列表中应有独立状态展示，避免与直播/回放混淆。
3. 如果某个预告场次已经开始直播，原来的预告卡片上应出现明确提示，例如“已开播”“直播中”或同等语义的状态标识。
4. 如有进入直播间动作，卡片提示应优先指向“当前已开播”，避免用户继续按预告理解该场次。

### 影响

- **功能**：用户无法从观看历史中完整区分预告、直播、回放三种状态。
- **体验**：预告转直播后缺少显式提示，卡片状态不自解释。
- **一致性**：与首页“预告 / 直播 / 回放”的状态体系不一致。

### 建议实现方向

1. 在 `ViewHistory.vue` 的筛选器中补充“预告”标签。
2. 在 `watchHistory` 的 session 类型归类里保留 `scheduled` 状态，避免被合并成直播或回放。
3. 列表卡片增加状态徽标或提示条，用于表达“预告已开播”的状态变更。
4. 若后端能提供实时状态，卡片应在刷新后自动反映最新 `live_status`。

观看历史当前的数据归类与封面链路详见：[`../problem/README.md`](../problem/README.md)
