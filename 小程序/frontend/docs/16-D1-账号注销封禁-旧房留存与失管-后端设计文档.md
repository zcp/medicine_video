## 📌 核心定位说明

### 1. 本文档的定位

本文档专注于**账号注销 / 封禁 / 撤开播权**触发后，**自有直播间（旧房）**的策略约束与验收：

**包含能力（P0）**:
- **注销留房（Retention）**: 账号软删后 `live_rooms` 实体保留，不调用删房级联
- **原主失管（Owner Loss）**: 靠既有「禁登 + 会话吊销」达成；Admin 仍可管孤儿房
- **封禁/撤权不删房（Ban Isolation）**: 与《14-V2》C4/G2 对齐

**模块范围**:
- **0** 张新表、**0** 新接口（P0）
- 回归测试 + CR 约束为主
- **明确不做**: 清私货（→`16-D2`）；留言占位（→`16-D3`）；删房补订阅（→`16-D4`）；品牌（→`16-D5`）；会员挡注销（→`16-D0`）

### 2. 本文档的核心特点

- ✅ 与《16》R2/R3 同向
- ✅ 与《14-V2》B5 不打架：B5 仅 `NORMAL`；`DELETED`/`BANNED` 靠鉴权失管
- ✅ **最快可合**：几乎无功能代码

### 3. 业务价值说明

- 防止后续有人「顺手」在注销里调删房
- 用测试锁住《14-V2》「封禁 ≠ 砍流删房」

- **管理员权限（ADMIN/SUPERADMIN）**: 可管理任意房间（含原主已注销的孤儿房）

### JWT Token格式说明

```json
{
  "user_id": "uuid-string",
  "username": "demo",
  "role": "REGULAR",
  "can_stream": true,
  "exp": 1717756800
}
```

> Payload 用户标识为 `user_id`（= `public_id`）。`status=DELETED` 用户不应再拿到有效 Token（登录/刷新拒绝 + 吊销）。

## 🎯 设计要点与约定（P0）

### 1.1 数据库设计规范

1. **本包无新表、无新列（P0）**
2. 房间主键 / `user_id` 保持 UUID；注销后 `user_id` **仍保留原值**
3. 硬删房间仍走既有 `delete_room` → `delete_room_related`（**仅显式删房**；级联订阅见 `16-D4`）
4. `parent_room_id ON DELETE SET NULL` 不在本包变更

### 1.2 API 设计规范（P0）

1. **无新路径、无响应增量字段**
2. 失管 = 既有登录/刷新拒绝 + 会话吊销 → 写接口自然 401（`3001`）
3. 注销成功路径 **禁止** 调 live_core 删房

### 1.3 软删除策略

| 实体 | 策略 | 说明 |
|------|------|------|
| `users` | `status=DELETED` | 注销软删（既有） |
| `live_rooms` | **注销时不删** | 本包核心；硬删仅显式删房 |
| 封禁 `BANNED` | 不删房 | 对齐 R2 /《14-V2》 |

### 1.4 与《14-V2》B5 的边界（必读）

| 账号状态 | `can_stream` | 旧房写操作（改标题/结束/封面/删房） |
|----------|--------------|--------------------------------------|
| `NORMAL` | `false` | ✅ 仍可（B5） |
| `NORMAL` | `true` | ✅ 可 |
| `BANNED` | * | ❌ 无有效会话（401）；不自动删房 |
| `DELETED` | * | ❌ 原主不可登录；旧 Token 因吊销 401；Admin 仍可管 |

## 3. API 接口设计（P0）

### 3.1 【约束】注销账号 — 禁止删房（JWT）

**Endpoint**: `DELETE /api/v1/users/me`（网关路径以现网为准）

**描述**: 账号软删。本包 **不新增** 请求/响应字段；**增加实现约束与验收**：成功路径不得调用 live_core 删房 API / 内部删房。

**认证**: JWT

**成功响应**: 维持《10》（`200`，message=账号已注销）

**执行流程（本包关注点加粗）**:

1. 接收请求：校验 Body 验证码字段  
2. JWT 验证：`get_current_user`  
3. 验证码校验：失败 → 4003  
4. 会员闸门：活跃会员挡注销（若尚未落地，见 `16-D0`/《10》；本包不重复实现）  
5. 软删除：`users.status=DELETED`  
6. 吊销会话：refresh 黑名单 + `user_sessions_revoked`  
7. 提交 users 事务  
8. **禁止步骤**：不得 HTTP 调用 live_core `DELETE /rooms/{id}` 或批量删房  
9. 出站通知（**非本包必做，属 `16-D2`**）：commit 后 best-effort 清私货；**消费方仍禁止删房**  
10. 返回注销成功  

**HTTP状态码**: 维持《10》；本包不新增。

### 3.2 【明确维持】封禁 / 撤开播权（Admin）

**Endpoint**: `PATCH /api/v1/admin/users/{uuid}`（users）

## 4. 执行流程详细说明（P0）

### 4.1 注销 → 旧房（链 A 本包段）

```
1. 用户 DELETE /users/me
2. users 软删 + 吊销
3. [禁止] 调用删房
4. live_rooms 行仍在，user_id 仍指向原 public_id
5. 原主无法登录 / 旧 Token 吊销 → 无法写房（失管）
6. C 端 GET 房间：照常返回房间实体（P0 无 owner 展示字段）
7. Admin 仍可 PATCH/DELETE 该房
8. 冷却后运营显式删房 → 走既有级联（订阅补洞见 16-D4）
```

> 留言作者展示「账号已注销」→ **`16-D3`**，不是本包房间详情字段。

### 4.2 封禁 → 旧房

```
1. Admin PATCH status=BANNED
2. 吊销会话
3. 不删房、不关播（运营 SOP 另册）
4. 房间实体与级联关系不变
```

### 4.3 撤开播权 → 旧房（对照 B5）

```
1. Admin PATCH can_stream=false + 吊销
2. 不可新建房
3. status 仍为 NORMAL → 仍可管理旧房（B5，本包不改）
```

## 5. 错误处理与事务管理（P0）

### 5.1 错误处理策略

- 房间不存在 → 2001 / 404  
- 非 owner 非 Admin → 3002 / 403  
- 已注销/封禁原主持旧 Token 写房 → **3001 / 401（吊销）**  
- 注销事务失败 → 维持《10》既有码  

### 5.2 事务管理规范

- 注销事务 **仅** 在 users 库；**禁止** 分布式同事务删房  
- 房间写操作单库事务，维持现网

## 附录 B · P2 可选：写路径防御性 DELETED 门禁（非当前排期）

> **警告**：P0 失管主路径是 **401（吊销）**。以下 2004 为双保险，有事故再加。

### B.1 行为

在既有 owner/Admin 校验之后：非 Admin 且原主 `status=DELETED` → **403 + code=2004**。

```json
{
  "code": 2004,
  "message": "原主账号已注销，无法以所有者身份操作该房间",
  "data": {
    "room_id": "room-uuid",
    "reason": "owner_account_deleted"
  }
}
```

### B.2 Schema 草案

```python
class OwnerDeactivatedErrorData(BaseModel):
    room_id: UUID
    reason: str = "owner_account_deleted"
```

### B.3 实现建议

优先保证 users 对 DELETED 永不发有效 Token，使本门禁为防御性；避免每次写路径远程查 status。
