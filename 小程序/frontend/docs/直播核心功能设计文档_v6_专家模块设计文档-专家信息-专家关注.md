```json
{
  "code": 200,
  "message": "success",
  "data": { ... } | null,
  "timestamp": "2025-10-23T10:00:00Z"
}
```

### 分页响应格式

```json
{
  "total": 100,
  "page": 1,
  "size": 10,
  "items": [ ... ]
}
```

### 认证规范

- **公开接口**: 无需JWT Token
- **用户接口**: 需要JWT Token（`Authorization: Bearer <token>`）
- **Admin接口**: 需要JWT Token + `ADMIN` 或 `SUPERADMIN` 角色

### JWT Token格式说明

**Access Token Payload**:
```json
{
  "user_id": "user_uuid",        // 用户公开ID (users.public_id)
  "role": "ADMIN",               // 用户角色（REGULAR/MODERATOR/ADMIN/SUPERADMIN）
  "type": "access",              // Token类型
  "exp": 1757364000,             // 过期时间
  "iat": 1757363100,             // 签发时间
  "jti": "token_unique_id"       // Token唯一ID
}
```

**⚠️ 重要说明**：
- 本系统使用`user_id`字段（而非JWT RFC 7519标准的`sub`字段）
- 这是2025-12-19权限设计定稿时的有意识决策，为保持代码语义清晰
- 所有Service层方法、CRUD层方法、日志记录等都使用`user_id`命名

**详见**: 
- 《用户模块设计文档authing版+权限设计版.md》Section 7.1.3
- 《直播核心功能设计文档_v6_增加权限设计版.md》Section 0

### 业务状态码体系

| 业务状态码  | 含义 | 使用场景 |
|:-------|:-----|:---------|
| `200`  | 成功 | 操作成功完成 |
| `2001` | 资源不存在 | 查询的资源不存在 |
| `2002` | 资源已存在 | 创建时名称/唯一键冲突 |
| `2003` | 操作被禁止 | 删除被引用的资源等 |
| `2004` | 业务逻辑错误 | user_id已绑定等业务规则违反 |
| `3001` | 未认证 | Token缺失或无效 |
| `3003` | 权限不足 | 用户角色权限不足 |
| `4001` | 参数校验失败 | 请求参数格式/类型错误 |
| `1002` | 数据库错误 | 系统级数据库异常 |

### 权限设计规范

专家模块的权限设计遵循《直播核心功能设计文档_v6_增加权限设计版(非独立版).md》中的统一权限架构。

#### 架构分层原则

权限管理的职责分层如下：

- **API 层 (Controller/Dependency)**：仅负责 **Authentication (认证)** —— 解析"你是谁"（User 还是 Anonymous）。
  - 使用 `Depends(get_current_user)` 进行严格认证（写操作、用户专属操作）
  - 使用 `Depends(get_current_user_optional)` 进行可选认证（读操作）
  - 从JWT Token中提取 `user_id` 和 `role` 字段，传递给Service层

- **Service 层 (Domain Logic)**：全权负责 **Authorization (鉴权)** —— 判定"你能看吗/你能改吗"。
  - 实现权限守卫函数（`_check_admin_permission`、`_check_write_permission`、`_check_expert_visibility`等）
  - 根据用户角色和资源状态进行权限判断
  - 抛出相应的异常（`PermissionDeniedException`、`NotFoundException`等）

- **CRUD 层 (Repository/Data Access)**：负责在 **SQL 层面应用权限过滤逻辑**。
  - 根据用户身份在SQL查询中添加权限过滤条件
  - 禁止内存过滤，业务筛选条件与权限过滤条件使用 AND 关系组合
  - 对于用户关注列表，必须根据 `user_id` 进行过滤

#### 双轨鉴权模式

专家模块采用双轨鉴权模式，支持匿名访问和已登录用户访问：

- **Strict Auth (强制鉴权)**：
  - 适用场景：所有写操作（创建、更新、删除专家信息）、用户专属操作（关注/取消关注专家、获取关注列表）
  - 行为：无Token或Token无效时返回 `401 Unauthorized`
  - 对应依赖：`Depends(get_current_user)`

- **Optional Auth (可选鉴权)**：
  - 适用场景：公开资源的读操作（获取推荐专家列表、获取专家详情）
  - 行为：无Token时视为匿名用户，Token无效时返回 `401 Unauthorized`
  - 对应依赖：`Depends(get_current_user_optional)`
  - 注意：专家信息是公开资源，匿名用户和已登录用户都可以访问

**前端实现约束（与本鉴权模型对齐）**：

- 匿名用户打开专家详情属于公开浏览，前端不得因未登录而 Toast / 跳转登录。
- 详情页加载阶段仅允许调用公开读接口；未登录时禁止请求 `/users/me/*`（关注列表、收藏列表等），避免把用户态 401 误展示为“点专家就报错”。
- 关注、收藏等写操作再按 Strict Auth 引导登录。

#### 权限守卫函数

Service层应实现以下权限守卫函数：

##### 管理员权限检查

```python
def _check_admin_permission(
    self,
    user_role: Optional[str]
) -> None:
    """
    管理员权限检查（用于系统级资源管理）
    
    Args:
        user_role: 当前用户的角色（从JWT Token提取）
        
    Raises:
        PermissionDeniedException: 非管理员用户（403）
    """
    if user_role not in ['ADMIN', 'SUPERADMIN']:
        raise PermissionDeniedException("权限不足，需要管理员权限")
```

**适用场景**：
- 创建/更新/删除专家信息（系统级资源）
- 获取专家列表（Admin分页接口）

##### 写权限检查

```python
def _check_write_permission(
    self,
    resource_owner_id: UUID,
    current_user_id: UUID,
    user_role: str
) -> None:
    """
    写操作权限检查（用于用户专属资源操作）
    
    Args:
        resource_owner_id: 资源所有者的ID
        current_user_id: 当前用户的ID
        user_role: 当前用户的角色
        
    Raises:
        PermissionDeniedException: 无权操作（403）
    """
    # 管理员：可以操作所有资源
    if user_role in ['ADMIN', 'SUPERADMIN']:
        return
    
    # 资源所有者：可以操作自己的资源
    if resource_owner_id == current_user_id:
        return
    
    # 其他用户：拒绝
    raise PermissionDeniedException("权限不足，无权操作该资源")
```

**适用场景**：
- 用户关注/取消关注专家（用户只能操作自己的关注关系）
- 获取用户关注列表（用户只能查看自己的关注列表）

**注意**：专家模块的用户关注功能是用户专属资源，用户只能操作自己的关注关系。管理员可以查看所有用户的关注关系，但普通用户只能查看自己的。

##### 专家可见性检查

```python

    # 本模块中，专家信息完全公开，无需404伪装
```

**适用场景**：

#### CRUD层权限过滤

CRUD层应在SQL查询中应用权限过滤逻辑，避免内存过滤：

##### 用户关注列表查询权限过滤

```python
async def get_user_followed_experts(
    db: AsyncSession,
    user_id: UUID,
    page: int = 1,
    size: int = 10,
    current_user_id: Optional[UUID] = None,
    role: Optional[str] = None
) -> Tuple[List[Expert], int]:
    """
    获取用户关注的专家列表（带权限过滤）
    
    Args:
        db: 数据库会话
        user_id: 要查询的用户ID
        page: 页码
        size: 每页大小
        current_user_id: 当前用户的ID（可选）
        role: 当前用户的角色（可选）
        
    Returns:
        (专家列表, 总数)
    """
    # 权限过滤：普通用户只能查看自己的关注列表
    if role not in ['ADMIN', 'SUPERADMIN']:
        if current_user_id != user_id:
            raise PermissionDeniedException("权限不足，只能查看自己的关注列表")
    
    # 构建查询
    query = select(Expert).join(
        UserExpertSubscription,
        Expert.id == UserExpertSubscription.expert_id
    ).where(
        UserExpertSubscription.user_id == user_id
    )
    
    # 分页
    total = await db.scalar(select(func.count()).select_from(query.subquery()))
    query = query.offset((page - 1) * size).limit(size)
    
    result = await db.execute(query)
    return list(result.scalars().all()), total
```

**关键原则**：
- 普通用户只能查看自己的关注列表
- 管理员可以查看所有用户的关注列表
- 所有过滤条件在SQL层面完成，不使用内存过滤

#### 用户身份提取规范

**重要：统一使用 `user_id` 字段**

在所有API实现中，必须从JWT Token的 `user_id` 字段提取用户身份，而非JWT标准的 `sub` 字段：

```python
# API层：提取用户身份
current_user: Dict = Depends(get_current_user)
user_id = UUID(current_user.get("user_id") or current_user.get("sub"))
user_role = current_user.get("role", "REGULAR").upper()

# 传递给Service层
result = await service.follow_expert(expert_id, user_id, user_role)
```

**JWT Token格式**：
```json

  "role": "REGULAR",
  "email": "user@example.com",
  "exp": 1698765432
}
```

**注意**：
- 如果JWT Token中没有 `user_id` 字段，可以回退到 `sub` 字段（兼容性处理）
- 角色字段统一使用大写（`REGULAR`、`ADMIN`、`SUPERADMIN`）
- 匿名用户时，`user_id` 和 `role` 均为 `None`

## 1. 设计要点与约定

### 1.1 数据库设计规范

**遵循《直播核心功能设计文档_v6_深度融合最终版.md》Section 7.1规范**：

1. **UUID主键生成**：
   - ✅ 所有表的主键UUID**必须在应用层生成**（`uuid.uuid4()`）
   - ❌ 禁止使用数据库默认值 `DEFAULT gen_random_uuid()`
   - 原因：便于日志记录、批量插入优化、避免数据库特定依赖

2. **时间戳字段**：
   - 使用 `TIMESTAMPTZ` 类型，以UTC存储
   - `created_at`: `DEFAULT CURRENT_TIMESTAMP`
   - `updated_at`: `DEFAULT CURRENT_TIMESTAMP` + 触发器自动更新

3. **外键约束**：
   - 必须命名外键约束（`CONSTRAINT fk_<table>_<column>`）
   - 微服务架构下，跨服务引用（如user_id）在应用层验证，不添加数据库外键

4. **用户ID引用规范（重要！）**：

   **⚠️ 特别说明：本系统用户表采用双ID设计**
   
   根据《用户模块设计文档authing版+权限设计版.md》Section 3.1和《用户模块---配置与安全优化-实施指南.md》，用户表（users）采用**双ID架构**：
   
   | 字段名 | 类型 | 用途 | 暴露范围 |
   |--------|------|------|----------|
   | `user_id` | BIGINT | 数据库内部主键，自增 | ❌ 不对外暴露 |
   | `public_id` | UUID | 对外公开标识符 | ✅ 对外暴露（API、JWT） |
   
   **📌 本文档的命名约定**：
   - **本文档中所有表的 `user_id` 字段，实际上引用的是 `users.public_id`（UUID类型）**
   - 字段命名为 `user_id` 而非 `public_id` 是为了保持代码可读性（更符合直觉）
   - 但本质上存储和引用的是用户的公开UUID，不是内部自增ID
   
   **设计原因**：
   - **微服务架构隔离**：LiveCore Service 不直接访问 User Service 的数据库，仅通过 public_id 引用用户
   - **安全性**：避免暴露内部自增ID，防止用户信息遍历攻击
   - **JWT集成**：JWT Token的 `user_id` 字段存储的是 `public_id`，LiveCore Service 通过Token验证用户身份
   
   **实现要点**：
   - 数据库定义：`user_id UUID NOT NULL`（注意是UUID类型，不是BIGINT）
   - 外键处理：由于跨服务，不添加数据库外键约束，在应用层验证
   - JWT验证：`Depends(get_current_user)` 会从JWT Token的 `user_id` 字段提取 `public_id`，赋值给 `user_id` 变量
   - 数据库注释：`COMMENT ON COLUMN xxx.user_id IS '用户公开ID（users.public_id），应用层验证，JWT Token的user_id字段值'`
   
   **涉及的表**：
   - `experts.user_id` → `users.public_id`（可选，外部专家可为NULL）
   - `user_expert_subscriptions.user_id` → `users.public_id`

5. **字段注释**：
   - 所有表必须有 `COMMENT ON TABLE`
   - 关键字段必须有 `COMMENT ON COLUMN`

6. **索引策略**：
   - 外键字段必须添加索引
   - 常用查询条件添加复合索引
   - 唯一约束自动创建唯一索引

### 1.2 API设计规范

**遵循《直播核心功能设计文档_v6_深度融合最终版.md》Section 4规范**：

1. **HTTP方法**：
   - `GET`: 查询（幂等）
   - `POST`: 创建
   - `PATCH`: 部分更新（推荐）
   - `DELETE`: 删除

2. **路径设计**：
   - 公开接口: `/api/v1/<resource>`
   - 用户接口: `/api/v1/users/me/<resource>`
   - Admin接口: `/api/v1/admin/<resource>`

3. **认证要求**：
   - 使用 `Depends(get_current_user)` 或 `Depends(get_current_user_optional)` 提取JWT Token
   - 从Token的 `user_id` 字段提取用户公开ID（users.public_id）
   - 从Token的 `role` 字段验证权限（REGULAR/MODERATOR/ADMIN/SUPERADMIN）
   
   **代码提取示例**：
   ```python
   # ✅ 正确做法（与v6主文档一致）

   role = current_user.get("role")          # 提取用户角色
   ```

4. **鉴权策略**：
   根据《直播核心功能设计文档_v6_增加权限设计版(非独立版).md》的权限设计，本系统采用双轨鉴权模式：
   
   - **Strict Auth（强制鉴权）**：用于所有CUD操作和敏感信息读取
     - 实现方式：`current_user: Dict = Depends(get_current_user)`
     - 无Token或Token无效：返回401 Unauthorized
     - 适用接口：POST、PATCH、DELETE、Admin接口
   
   - **Optional Auth（可选鉴权）**：用于公开资源的读取操作（本模块未使用）
     - 实现方式：`current_user: Optional[Dict] = Depends(get_current_user_optional)`
     - 无Token：返回None，视为匿名用户
     - Token无效：返回401 Unauthorized（严禁降级为匿名）

5. **执行流程规范**：
   - 必须包含8-10步详细说明
   - 包含权限验证、参数校验、业务逻辑、异常处理、日志记录

### 1.3 软删除策略

**统一策略**：

#### 1.4.3 日志脱敏规范

##### 日志脱敏实现载体要求

所有日志输出必须经过脱敏处理，禁止直接输出敏感信息：

**需要脱敏的信息**：
- 数据库连接URL（包含密码）
- JWT Token完整内容
- 用户密码（即使已加密）
- API密钥
- 专家联系方式（contact_info字段）
- 其他敏感配置信息

**日志脱敏工具函数**：

```python
# app/core/logging_utils.py
import re
import logging

def sanitize_log_message(message: str) -> str:
    """对日志消息进行脱敏处理"""
    # 移除数据库连接URL中的密码
    message = re.sub(
        r'postgresql[+a-z]*://[^:]+:([^@]+)@',
        r'postgresql://***:***@',
        message,
        flags=re.IGNORECASE
    )
    
    # 移除JWT密钥（如果意外出现在日志中）
    message = re.sub(
        r'JWT_SECRET_KEY["\']?\s*[:=]\s*["\']?([^"\'\s]+)',
        r'JWT_SECRET_KEY="***"',
        message,
        flags=re.IGNORECASE
    )
    
    # 移除JWT Token完整字符串（仅保留前8个字符）
    message = re.sub(
        r'Bearer\s+([A-Za-z0-9_-]{8})([A-Za-z0-9_-]+)',
        r'Bearer \1...',
        message
    )
    
    return message

class SanitizedFormatter(logging.Formatter):
    """脱敏日志格式化器"""
    def format(self, record):
        record.msg = sanitize_log_message(str(record.msg))
        return super().format(record)
```

##### 日志级别使用规范

- **INFO级别**：记录正常业务操作（不包含敏感信息）
- **WARNING级别**：记录权限拒绝和业务异常（不包含敏感信息）
- **ERROR级别**：记录系统异常（不包含敏感信息，仅记录错误类型和位置）

**示例**：
```python
# ✅ 正确：不包含敏感信息
logger.info(f"用户 {user_id} 关注了专家 {expert_id}")
logger.warning(f"用户 {user_id} 尝试访问无权限的资源 {resource_id}")
logger.error(f"数据库操作失败: {type(e).__name__}")

# ❌ 错误：包含敏感信息
logger.info(f"数据库连接: {DATABASE_URL}")  # 包含密码
logger.error(f"异常详情: {str(e)}")  # 可能包含敏感信息
```

**专家联系方式脱敏**：
- contact_info字段仅记录字段存在性，不记录具体内容
- 示例：`logger.info(f"专家 {expert_id} 有联系方式: {bool(expert.contact_info)}")`

#### 1.4.4 错误消息脱敏

##### 异常处理中的脱敏

在异常处理中，不要向用户暴露敏感信息：

```python
# ✅ 正确：不暴露敏感信息
try:
    # 数据库操作
    result = await db.execute(query)
except Exception as e:
    logger.error(f"数据库操作失败: {type(e).__name__}")
    # 不打印完整的异常信息（可能包含连接字符串）
    raise HTTPException(
        status_code=500,
        detail="内部服务器错误"
    )

# ❌ 错误：暴露敏感信息
try:
    result = await db.execute(query)
except Exception as e:
    logger.error(f"数据库操作失败: {str(e)}")  # 可能包含连接字符串
    raise HTTPException(status_code=500, detail=str(e))  # 暴露给用户
```

##### 错误消息规范

- **用户可见错误**：仅返回通用的错误消息，不暴露系统内部细节
- **日志记录**：在日志中记录详细的错误信息（已脱敏），用于调试
- **错误码使用**：使用统一的错误码（如 `3003` 权限不足），而非详细的错误描述

### 1.5 专家模块特殊设计说明

#### 1.5.1 专家与用户的关联关系

**设计场景**：
1. **外部专家**：未注册平台账号的专家，仅有档案信息
   - `experts.user_id` 为 `NULL`
   - 由Admin手动创建专家档案，填写姓名、职称、医院等信息
   
2. **内部专家**：已注册平台账号的专家，可绑定用户
   - `experts.user_id` 关联 `users.public_id`
   - 专家可登录平台，查看和管理自己的直播场次
   - 一个用户只能绑定一个专家档案（`user_id` 字段有UNIQUE约束）

**业务规则**：
- Admin创建专家时，`user_id` 可选
- 若提供`user_id`，必须验证：
  1. 用户存在于users表
  2. 该user_id未被其他专家绑定
- 更新专家时，可以绑定或解绑`user_id`

#### 1.5.2 专家关注功能设计说明

**设计目标**：
- 用户可关注感兴趣的专家
- 专家开播时，向关注用户发送通知（与通知模块集成）
- "我的关注"页面实时显示关注专家的直播状态

**实现要点**：
- `user_expert_subscriptions` 表记录关注关系
- 关注时创建记录，取消关注时硬删除记录（不需要软删除）
- 获取关注列表时，联查 `live_sessions` 表获取专家的当前直播状态

```sql
CREATE TABLE live_session_experts (

    -- 外键字段
    session_id UUID NOT NULL REFERENCES live_sessions(id) ON DELETE CASCADE,
    expert_id UUID NOT NULL REFERENCES experts(id) ON DELETE CASCADE,

    -- 业务字段
    role VARCHAR(50) NOT NULL DEFAULT '主讲',  -- 专家角色：主讲、主持、嘉宾
    sort_order INT DEFAULT 0,  -- 显示顺序

    -- 时间戳
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    -- 唯一约束：同一场次同一专家只能有一个角色（主讲/主持/嘉宾）
    UNIQUE(session_id, expert_id, role)
);

-- 索引
CREATE INDEX idx_live_session_experts_session ON live_session_experts(session_id);
CREATE INDEX idx_live_session_experts_expert ON live_session_experts(expert_id);
CREATE INDEX idx_live_session_experts_role ON live_session_experts(session_id, role);

-- 注释
COMMENT ON TABLE live_session_experts IS '直播场次专家关联表（多对多关系），支持一个场次有多个专家（主讲、主持、嘉宾）';
COMMENT ON COLUMN live_session_experts.id IS '主键UUID，在应用层通过uuid.uuid4()生成';
COMMENT ON COLUMN live_session_experts.session_id IS '直播场次ID，关联live_sessions表';
COMMENT ON COLUMN live_session_experts.expert_id IS '专家ID，关联experts表';
COMMENT ON COLUMN live_session_experts.role IS '专家角色：主讲、主持、嘉宾';
COMMENT ON COLUMN live_session_experts.sort_order IS '显示顺序（数值越大越靠前）';
COMMENT ON COLUMN live_session_experts.created_at IS '关联创建时间';
```

**字段说明**：
- `session_id`: 直播场次ID，外键关联 `live_sessions.id`
- `expert_id`: 专家ID，外键关联 `experts.id`
- `role`: 专家角色枚举（`主讲`、`主持`、`嘉宾`）
- `sort_order`: 显示顺序（数值越大越靠前）
- `UNIQUE(session_id, expert_id, role)`: 同一场次同一专家只能有一个角色

**与专家关注功能的关系**：
- 本表（`live_session_experts`）：**场次层面的专家关联**（主讲、主持、嘉宾）
- 关注表（`user_expert_subscriptions`）：**用户层面的专家关注**（用户关注的专家列表）
- **两者独立**：一个是专家参与了哪些场次，一个是用户关注了哪些专家

**与 v6 主文档的关系**：
- 本表是**完全新增**的中间表
- **不修改** `live_sessions` 表的任何字段
- **不修改** `experts` 表的任何字段
- 所有外键约束在中间表定义，确保引用完整性

## 6. 错误处理与事务管理

### 6.1 错误处理策略

#### 业务错误

| 错误码  | 场景 | 处理方式 |
|------|------|---------|
| 2001 | 专家不存在 | 返回详细错误信息 |
| 2002 | 重复关注、重复绑定user_id | 返回已存在提示 |
| 2004 | user_id已绑定其他专家 | 返回业务逻辑错误 |
| 3001 | 未认证 | 提示重新登录 |
| 3003 | 权限不足（非Admin） | 返回权限不足 |
| 4001 | 参数校验失败 | 返回Pydantic验证错误 |

#### 系统错误

- **数据库连接失败**：返回1002，记录ERROR日志
- **唯一约束违反**：捕获IntegrityError，转换为业务错误
- **外键约束违反**：返回4001参数校验失败

### 6.2 事务管理规范

#### 单表操作

```python
# 示例：关注专家
try:
    subscription = UserExpertSubscription(
        id=uuid.uuid4(),
        user_id=user_id,
        expert_id=expert_id
    )
    db.add(subscription)
    db.commit()
    db.refresh(subscription)
    logger.info(f"User {user_id} followed expert {expert_id}")
    return subscription
except IntegrityError as e:
    db.rollback()
    if "uq_user_expert_subscriptions" in str(e):
        raise BusinessException(code=2002, message="您已关注该专家")
    raise
except Exception as e:
    db.rollback()
    logger.error(f"Failed to follow expert: {e}")
    raise
```

## 10. 专家与场次多对多关系实现方案

### 10.1 核心设计说明

本模块通过中间表 `live_session_experts` 实现 `live_sessions` 和 `experts` 的多对多关系：

- **设计方式**：使用独立的中间表（`live_session_experts`）
- **关系定义**：一个场次可以有多个专家（主讲、主持、嘉宾），一个专家可以参与多个场次
- **外键约束**：
  - `session_id` → `live_sessions.id`（`ON DELETE CASCADE`）
  - `expert_id` → `experts.id`（`ON DELETE CASCADE`）
- **业务字段**：
  - `role`：专家角色（`主讲`、`主持`、`嘉宾`）
  - `sort_order`：显示顺序（数值越大越靠前）
- **唯一约束**：`UNIQUE(session_id, expert_id, role)` - 同一场次同一专家只能有一个角色

### 10.2 与 v6 主文档的兼容性

**完全兼容，不修改现有表**：
- ✅ **完全不修改** `live_sessions` 表的任何字段
- ✅ **完全不修改** `experts` 表的任何字段
- ✅ 所有外键约束在中间表定义，确保引用完整性
- ✅ 级联删除保证数据一致性

**数据迁移影响**：
- ✅ 只需新增中间表 `live_session_experts`
- ✅ 无需修改现有表结构
- ✅ 无需数据迁移（新功能，不影响现有数据）

### 10.3 三种专家场景的独立性

#### 场景1：特色专家（首页推荐）
- **设计方式**：`experts.is_featured = true`
- **展示位置**：首页专家推荐列表
- **业务逻辑**：专家设置为"特色"时，自动在首页推荐位展示

#### 场景2：场次专家（主讲/主持/嘉宾）
- **设计方式**：`live_session_experts` 中间表
- **展示位置**：直播间详情页、场次信息展示
- **业务逻辑**：一个场次可以有多个专家（主讲1个+主持N个+嘉宾N个）
- **排序控制**：通过 `sort_order` 字段控制专家显示顺序

#### 场景3：用户关注专家
- **设计方式**：`user_expert_subscriptions` 表
- **展示位置**："我的关注"页面
- **业务逻辑**：用户关注感兴趣的专家，接收开播通知

**三个场景的独立性**：
- ✅ **完全解耦**：三个场景使用不同的表和关联方式
- ✅ **互不干扰**：修改"场次专家"不影响"特色专家"或"用户关注"
- ✅ **灵活组合**：可以同时支持所有三种场景

**LiveSessionExpert 模型**（新增）：

```python
from sqlalchemy import Column, String, Integer, ForeignKey, UniqueConstraint, Index
from sqlalchemy.dialects.postgresql import UUID
from sqlalchemy.orm import relationship
from app.database import Base
import enum


class SessionExpertRole(str, enum.Enum):
    """专家角色枚举"""
    MAIN_SPEAKER = "主讲"      # 主讲
    HOST = "主持"           # 主持
    GUEST = "嘉宾"          # 嘉宾


class LiveSessionExpert(Base):
    """
    直播场次专家关联表（多对多关系）
    
    用于管理场次与专家的关联关系，支持一个场次有多个专家（主讲、主持、嘉宾）。
    """
    __tablename__ = "live_session_experts"
    
    # 核心标识 (在应用层通过 uuid.uuid4() 生成)
    id = Column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)
    
    # 外键字段
    session_id = Column(
        UUID(as_uuid=True),
        ForeignKey("live_sessions.id", ondelete="CASCADE"),
        nullable=False,
        comment='直播场次ID，关联live_sessions表'
    )
    expert_id = Column(
        UUID(as_uuid=True),
        ForeignKey("experts.id", ondelete="CASCADE"),
        nullable=False,
        comment='专家ID，关联experts表'
    )
    
    # 业务字段
    role = Column(
        String(50),
        nullable=False,
        default=SessionExpertRole.MAIN_SPEAKER,
        comment='专家角色：主讲、主持、嘉宾'
    )
    sort_order = Column(
        Integer,
        nullable=False,
        default=0,
        comment='显示顺序（数值越大越靠前）'
    )
    
    # 时间戳
    created_at = Column(
        TIMESTAMP(timezone=True),
        nullable=False,
        server_default=func.now(),
        comment='关联创建时间'
    )
    
    # 关系定义
    # 多对一关系：一个关联记录属于一个场次
    session = relationship("LiveSession", backref="session_experts")
    # 多对一关系：一个关联记录属于一个专家
    expert = relationship("Expert", backref="session_experts")
    
    # 唯一约束：同一场次同一专家只能有一个角色
    __table_args__ = (
        UniqueConstraint('session_id', 'expert_id', 'role', name='uq_live_session_experts_session_expert_role'),
        Index('idx_live_session_experts_session', 'session_id'),
        Index('idx_live_session_experts_expert', 'expert_id'),
        Index('idx_live_session_experts_role', 'session_id', 'role'),
    )
    
    def __repr__(self):
        return f"<LiveSessionExpert(id={self.id}, session_id={self.session_id}, expert_id={self.expert_id}, role={self.role})>"
```

```python
    skip: int = 0,
    limit: int = 10
) -> dict:

    }
```

```python
def add_experts_to_session(

        session_experts.append(session_expert)
```
