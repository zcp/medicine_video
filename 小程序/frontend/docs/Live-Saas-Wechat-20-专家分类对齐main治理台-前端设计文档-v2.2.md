## 一、背景与目标

### 1.1 问题

| 现状 | 后果 |
|------|------|
| V2.0 / V2.1 已定稿词表 + 根分类细能力，但**壳层仍偏瘦列表**（多 picker、无 Tab、无「治理」） | 与运营所见 main/截图不一致，培训与对照成本高 |
| V2.0 将分类 merge / migrate / 级联删**封印** | main 阶段 4+ 已上线三类治理；本仓缺入口与封装 |
| 路径体系与 main 平行（`ExpertDepartmentList` vs `pages/app/admin/departments`） | 不能整页替换；需增量移植行为 |

### 1.2 目标

1. **壳层对齐**：Tab「全部分类 / 待审核科室」、顶栏「选择 / ＋ 新增分类」、搜索一行、分组行「编辑分类 + 治理」、默认展开策略贴近 main。  
2. **解封根分类治理**（相对 V2.0/V2.1）：迁移引用、合并分类（含 dry_run 预览）、删除冲突 409 → 确认级联。  
3. **保留本仓优势**：科室词条**停用可恢复**；根分类 slug / 描述 / sort_order（V2.1）；子科室改分类；Merge 词条可搜目标。  
4. **工程约束不变**：不平行复制 `pages/app`；不搬 H5；不前端子孙展开。

### 1.3 业务价值

- 运营对照 main/培训材料即可上手本仓同页。  
- 分类级安顿（迁引用、合并、级联停用）有入口，减少手工改库。  
- 不牺牲本仓已落地的软删与细字段。

## 三、术语与关键概念

| 术语 | 含义 |
|------|------|
| 专家分类（页） | 本仓入口文案；导航标题可与截图一致为「专家分类管理」或保持「专家分类」（实施时与 Profile/`pages.json` 统一一处即可） |
| 治理 | 根分类级 ActionSheet：编辑 / 迁移引用 / 合并 / 删除（级联安顿） |
| 迁移引用 | 将源分类下专家/科室/房间关联迁到目标；源分类本身不因 migrate 删除 |
| 合并分类 | 源并入目标；支持 `dry_run` 预览；可选子分类提升为一级 |
| 级联安顿 | 删除分类遇引用 → 409 references → `force` + 可选 `target_category_id` |
| 词条合并 | 仍指 `expert-departments/merge`（科室级）；与「合并分类」不同层 |

## 五、核心流程

### 5.1 浏览与待审

```text
进入专家分类
  → Tab「全部分类」：树模式（无搜索）/ 平铺（有搜索）
  → Tab「待审核科室」：等价 is_verified=false 列表（可仍分组或平铺，与实现选最小改）
  →「选择」→ 底栏批量通过 → 离开选择模式
```

### 5.2 根分类编辑（保持 V2.1）

```text
「＋ 新增分类」或「编辑分类」/ 治理→编辑
  → CategoryFormDialog
  → createCategory / updateCategory
  → 刷新分组
```

### 5.3 迁移引用

```text
治理 → 迁移引用
  → 源只读；选目标；选 scope
  → POST .../categories/{id}/migrate
  → Toast 已迁移专家/科室/房间数 → 刷新
```

### 5.4 合并分类

```text
治理 → 合并分类
  → 选目标；可选「子分类提升为一级」
  →「预览统计」dry_run=true → 展示 counts
  →「确认合并」dry_run=false → 刷新（源分组消失）
```

### 5.5 删除 / 级联安顿

```text
治理 → 删除分类
  → DELETE 非 force
  → 若 409：展示 references；可选 target；确认 force
  → 成功 → 刷新
文案：对运营优先「停用 / 级联停用」；若后端实为级联软删，禁止写「不可恢复」
```

```text
│   · …                                       │
│   ── [＋ 新增科室] ──                       │
```


### 6.2 行为要点

1. 搜索防抖 300ms；空 → 树；非空 → 平铺。  
2. 默认展开：对齐 main（`expandState !== false` 即默认展开）；若性能有压力可仅默认展开首组，须在实现备注。  
3. 分组「编辑分类」与治理内「编辑」同一 Dialog。  
4. 词条子卡「删除」：**保持停用**语义（可恢复）；与根分类「删除分类」文案区分。  
5. 顶栏筛选：V2.1「含已停用分类」等可收进次级入口或「更多筛选」，避免与 Tab 抢第一视线；**不强制删除**该能力。  
6. 弱入口「未分配专家 →」可保留，不进入主闭环。

### 6.3 弹窗字段（对齐截图）

| 弹窗 | 字段 |
|------|------|
| 新增/编辑根分类 | 分类名称（标准名）、口语名（可选，见 §九）、启用（编辑态）；**同时保留** slug/描述/排序（V2.1，可折叠或同表展示，禁止删字段） |
| 迁移引用 | 源分类、迁移到、迁移范围 |
| 合并分类 | 源分类、合并到、子分类提升为一级、预览区、取消 / 预览统计 / 确认合并 |
| 删除冲突 | references 各项计数、可选迁移目标、确认级联 |

## 八、API 封装约定

在本仓 `src/api/categories.ts` **增量**（路径与 main 对齐；经本仓 `request`）：

| 方法 | 路径 | 要点 |
|------|------|------|
| `migrateCategoryReferences` | `POST /admin/categories/{id}/migrate` | body: `target_category_id`, `scope`: `all` \| `experts` \| `departments` \| `rooms` |
| `mergeCategories` | `POST /admin/categories/merge` | body: `source_id`, `target_id`, `attach_children?`, `dry_run?` |
| `deleteCategory` 扩展 | `DELETE /admin/categories/{id}?force=&target_category_id=` | 非 force 遇引用 → 409 + `references` |

类型建议：`CategoryReferences` / `CategoryMigrateStats` / `CategoryMergeResult`（字段名对齐 main 响应）。

**阻塞条件**：本仓后端若尚未提供上述端点 → P1 不接通按钮（可隐藏治理子项或 Toast「后端未开通」）；**禁止**假成功。

词条级 API 仍走 `expertDepartments.ts`（含 merge 科室），不变。

## 九、数据结构与字段约定

| 字段 | 约定 |
|------|------|
| 根分类 `name` / `slug` / `description` / `sort_order` / `is_active` | **保持** V2.1 |
| `display_name`（口语名） | 【可选】后端有则表单增量 + C 端展示优先；无则 UI 可暂不展示或只读占位，**不**写死假数据 |
| 词条 `is_verified` / `is_active` / 同义词 | 不变 |
| 禁止 | 用 main 的 `department.ts` 覆盖本仓医院科室类型 |

## 十、错误处理与兜底

| 场景 | 处理 |
|------|------|
| 409 + references | 打开级联确认弹窗，展示计数 |
| migrate/merge 校验失败（目标=源、目标在子树等） | Toast 后人话；不刷新假状态 |
| 3003 无权限 | 入口隐藏；直打 API 人话 |
| 后端未实现治理 | 隐藏对应菜单项或明确不可用；不报网络堆栈 |
