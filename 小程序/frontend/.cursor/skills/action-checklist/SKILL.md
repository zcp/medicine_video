# 行动清单 + 自测收尾

## 本 Skill 做什么

做**任何**非单句问答的任务时：先分流并读匹配 Agent → 选最小化最友好方案 → **把行动清单写进对用户可见的回复** → 按步执行 → 自测收尾。  
不替代 [live-saas-workflow](.cursor/skills/live-saas-workflow/SKILL.md) 的分流/规范；分流之后用本 Skill 管执行节奏。  
相关文档跳转写法见 [AI-工作约定 §8](docs/AI-工作约定.md)。

## 为何必须「写出来再做」（不是可选礼貌）

常见失败（禁止再犯）：

| 错误做法 | 为何不算执行本 Skill |
|----------|----------------------|
| 只 Read 了本文件，心里默念步骤就改代码 | 用户看不见清单，无法核对范围与完成定义 |
| 只建内部 Todo / 子 agent 私有步骤 | 对用户不可见 = 未列清单 |
| §3 写了 `frontend` 却不 Read [frontend Agent](.cursor/agents/frontend.md) | 只贴了角色名，未遵守 Agent「开始前/禁止」 |
| 报 bug / 多步排查按「单句问答」跳过清单 | 例外被滥用；排查必须有根因步骤与自测 |

**口令**：没写进回复的清单 = 没做；没 Read 的 Agent = 没分流到位。

## 何时启用

| 启用（必须清单） | 可不启用（唯一例外） |
|------------------|----------------------|
| 改代码、改文档、排查/修 bug、设计梳理、多步分析 | 纯单点事实问答，且一眼能答（如「函数在哪个文件」） |

用户说「按行动清单」「一步一步」「带自测」时必须启用。  
**默认从宽启用**：拿不准是否单句问答时，**启用**。

## 方案原则（每次行动必须）

**最小化、最友好修改方案** —— 动手前先按此选方案，再写进行动清单；禁止一上来大改。

| 原则 | 做法 |
|------|------|
| 最小化 | 只改达成请求所需的最少文件/行；能改样式不改结构，能补丁不重写，能藏入口不删整页 |
| 最友好 | 优先用户可感知、风险低、可回退的做法；复用已有组件/变量/口径；避免顺手重构与扩大范围 |
| 先选方案 | 有多条路时，在清单里写清「采用的最小友好方案」一句话；不默认选「最完整/最彻底」 |

自测须核对：本次改动是否仍符合「最小化、最友好」。

## 方案原则补充：防「永远填不完的洞」

做管理端 / 运营页 / 多步产品设计时，除「最小化、最友好」外须先钉：

| 项 | 要求 |
|----|------|
| 一句话定位 | 本页只服务一条闭环（例：找准 → 删掉 → 离开） |
| 完成定义 | 用户几步内能做完主任务，即算设计完成 |
| 非目标封印 | 明确「本页永不做」的能力；真有需求另开页，不往当前页堆 |
| 对标边界 | 可学大厂信息架构（先钉容器、浏览优先）；不把另一类产品表面的能力清单默认搬进当前页 |

禁止：把「以后可能要」写成当前页待办；用功能堆砌替代闭环。

## 方案原则补充：主体库类 Admin 列表

做或改**主体库瘦 CRUD**（建档 / 改资料 / 启停，非多维运营台）时，自测或动手前过一遍：

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 闭环 | 搜/筛 → 建/改 → 停用 → 可恢复 |
| 2 | 生命周期文案 | 与真实语义一致（可恢复就说停用，别写「不可恢复」） |
| 3 | 列表扫视 | 关键态用标签/降透，不只靠灰色小字 |
| 4 | 筛选 | 主关键词 + 至少一维运营维；多维 query 勿误做成 AND 死结 |
| 5 | 顶栏 | 搜索一行；查询/新建/状态筛/重置尽量同操作行 |
| 6 | 行密度 | 操作贴行侧；无必要底部分割操作条 |
| 7 | API | 只用契约已有 query；不发明字段 |
| 8 | 非目标 | 本页封印写进页头/清单，防止越改越胖 |

**「只改一件」输出顺序**：生命周期 → 列表贴实体 → 一维筛选 →（可选）密度。

**口令**：能改样式不改结构；能可逆不停毁；能标签不堆行；能同排不另开一行。

细则与评审两面见 Agent [frontend](.cursor/agents/frontend.md)「管理端表面」。

## 流程（必须按序；缺一步 = 未完成）

### 0. 分流 + 读 Agent（在写清单前）

1. 按 [AI-工作约定](docs/AI-工作约定.md) §3 / Skill [live-saas-workflow](.cursor/skills/live-saas-workflow/SKILL.md) 定角色：`explorer` | `frontend` | `docs`  
2. **Read** [`.cursor/agents/<角色>.md`](.cursor/agents/)（至少一份）；遵守其开始前检查  
3. 在清单或回复里点明本轮角色（例：本轮 `frontend`）

### 1. 写行动清单（先写进回复，再改仓库）

在**任何**写文件 / 大段实现之前，对用户可见地给出简短清单，格式固定：

```text
行动清单
- [ ] S1 …（目标一句话；含采用的最小友好方案）
- [ ] S2 …
- [ ] S3 …
- [ ] S4 自测收尾
```

要求：

- 步骤可执行、有序；一步一事  
- 含「完成定义」（怎样算做完）  
- 范围不超出用户本轮请求  
- 改 `src/**` 时：清单须含**文档依据**（可跳转链接 + 章节/Endpoint），并**摘录本次必要字段**；有缺失/行业常见缺口须写「缺口/建议」；见 [AI-工作约定 §4.1](docs/AI-工作约定.md)  
- 仅建议/只读时：步骤是「查/对照/结论」，不是偷偷改仓库  
- **方案须是最小化、最友好**；若只能做大改，须在清单中说明原因  
- 可用 Todo 工具，但 **Todo 不能代替**回复里的可见清单  

### 2. 按步执行

- 严格按 S1 → S2 → … 推进；完成一步再勾选/标明 ✅  
- 中途发现清单不对：先改清单（说明变更），再继续，不 silently 跑偏  
- 执行中若冒出「顺便重构/统一改一片」：**停住**，除非用户本轮点名  

### 3. 自测收尾（必须）

全部步骤做完后，输出**自测表**，再给最终结论。未自测不得宣称完成。

```text
自测
| # | 检查项 | 结果 | 说明 |
|---|--------|------|------|
| 1 | 是否覆盖用户请求 | ✅/❌ | … |
| 2 | 是否超出范围 | ✅/❌ | … |
| 3 | 是否最小化、最友好 | ✅/❌ | … |
| 4 | 是否 Read 了匹配 Agent | ✅/❌ | explorer/frontend/docs |
| 5 | 清单是否对用户可见且按步执行 | ✅/❌ | … |
| 6 | （任务相关检查） | ✅/❌ | … |
```

按任务类型至少包含：

| 类型 | 自测至少检查 |
|------|----------------|
| 改代码 | 改动点是否符合请求；是否最小友好；**文档依据已点名且必要字段已摘录**；字段/路径/必填/格式已对齐；**缺口/行业常见建议是否已告知且未擅自入库**（[§4.1](docs/AI-工作约定.md)）；规范样本；**可验收最小集**（下表）；主体库 Admin 列表则过专用表 |
| 改文档 / Skill / Rule / Agent | 真源是否先改（习惯变时）；分层/命名/模板；补丁或重写；修订历史；若为**前端设计文档**：体验钉五问是否已写（[§5.1](docs/AI-工作约定.md)），且未默认另开第三本页面设计 |
| 只读分析 | 结论是否有代码/文档证据；不确定处是否标明 |
| 排查 | 根因是否有证据；修复是否对应根因（若已修） |

### 可验收最小集（改功能行为时；真源 [§4.2](docs/AI-工作约定.md)）

自测表任务相关行须覆盖（不适用则注明 N/A）：

| # | 检查项 | 说明 |
|---|--------|------|
| A | 完成定义 / 主路径 | 用户能否按设计做完主任务（写成**看见什么**，不是接口 200） |
| B | 契约对齐 | 碰 API/`types` 时：路径与关键字段已摘录且一致 |
| C | 关键态 | 空/错/无权限（设计已写的）有着落 |
| D | 验证方式 | **须含 L2 手测步骤**（见下）；或（按需）自动化；**不要求**每次都有测试文件/正式报告 |

改功能行为时还须 **Read** Skill [acceptance-handtest](.cursor/skills/acceptance-handtest/SKILL.md)：L1/L2/L3、**L2 六句**、命中类型的加测；自测表写清手测要点。  
口令：**可验收 ≠ 必须有测试文件**；**AI 勾 L1 ≠ 人已验收**；易碎逻辑再补 L3。

有 ❌ 则先修再交付，或明确列为残留问题（须标出，不得装 ✅）。

## 与用户沟通

- 清单宜短（通常 3～7 步）；大任务先拆里程碑再分子清单  
- **首条落地回复就应出现清单**（可与极短结论同行）；禁止改完一大片才补清单  
- 最终回复：清单完成情况 + 自测表 + 结论（改了什么/建议是什么）  
- 用户只要建议：清单与自测仍要做，但步骤保持只读  

## 禁止

- 无**可见**清单直接大改  
- 默念清单 / 仅内部 Todo 当作已列清单  
- 定了角色却不 Read 对应 Agent 文件  
- 做完不自测就报「已完成」  
- 自测项与任务无关的凑数，或把未做项标成 ✅  
- 借清单扩大用户未点名的范围  
- 绕过「最小化、最友好」做过度设计或顺手重构  
- 点名相关文档却只写裸路径/文件名、无可跳转 Markdown 链接（相对仓库根）  
- 改代码无文档依据却发明字段或偏离契约形状（见 [AI-工作约定 §4.1](docs/AI-工作约定.md)）  
- 声称已查文档却不摘录必要字段，或把未确认的「行业常见建议」直接写进代码
