### 1.2 新建：公共密码工具模块

**文件：** `backend/users/app/core/password.py`（新建）

**导出三个函数：**

| 函数 | 签名 | 用途 |
|------|------|------|
| `hash_password` | `(password: str) -> str` | 使用 bcrypt 哈希密码，返回 `$2b$...` 格式字符串 |
| `verify_password` | `(password: str, password_hash: str) -> bool` | 验证密码；自动识别 bcrypt（`$2b$/ $2a$` 前缀）和旧版 SHA-256（64 位 hex），走对应校验逻辑 |
| `is_legacy_sha256_hash` | `(password_hash: str) -> bool` | 判断给定哈希是否为旧版 SHA-256，用于登录后滚动升级判断 |

**设计要点：**

- `verify_password` 同时兼容新旧两种哈希，保证老用户不改密码也能登录。
- `AuthService` 和 `UserService` 都通过此模块调用，杜绝"登录验证走 bcrypt、注册仍写 SHA-256"的不一致。

**代码（完整）：**

```python
"""
密码工具模块 —— 提供安全的密码哈希与验证能力

- 使用 bcrypt 作为默认哈希算法
- 向下兼容旧版 SHA-256 哈希，支持老用户平滑迁移
- AuthService 与 UserService 共用，确保一致性
"""
import hashlib

import bcrypt


def hash_password(password: str) -> str:
    """使用 bcrypt 哈希密码"""
    return bcrypt.hashpw(password.encode(), bcrypt.gensalt()).decode()


def verify_password(password: str, password_hash: str) -> bool:
    """验证密码，兼容旧 SHA-256 哈希与新版 bcrypt 哈希"""
    if password_hash.startswith("$2b$") or password_hash.startswith("$2a$"):
        return bcrypt.checkpw(password.encode(), password_hash.encode())

    if len(password_hash) == 64 and all(c in "0123456789abcdef" for c in password_hash.lower()):
        return hashlib.sha256(password.encode()).hexdigest() == password_hash

    return False


def is_legacy_sha256_hash(password_hash: str) -> bool:
    """判断是否为旧版 SHA-256 哈希"""
    return (
        len(password_hash) == 64
        and all(c in "0123456789abcdef" for c in password_hash.lower())
        and not password_hash.startswith("$2b$")
        and not password_hash.startswith("$2a$")
    )
```

### 1.8 新增：`auth_service.py` —— 重置后会话吊销

#### 1.8.1 新增方法：`_revoke_user_sessions()`（约第 870 行）

```python
    async def _revoke_user_sessions(self, user_public_id: str):
        """密码重置后吊销该用户所有现存 refresh token

        当前项目无双持久化的 refresh token 表，因此使用 Redis 时间戳截止线方案：
        - 记录吊销时间戳
        - refresh_token 接口在签发新 access token 前，对比 token iat 与吊销时间
        - iat 早于吊销时间的 token 一律拒绝
        """
        revocation_key = f"user_sessions_revoked:{user_public_id}"
        await self.redis_client.set(
            revocation_key,
            datetime.utcnow().isoformat(),
            ex=86400 * 7,  # 7 天过期（与 refresh token 有效期一致）
        )
        logger.info(f"已吊销用户所有会话: public_id={user_public_id}")
```

**Redis Key 格式：** `user_sessions_revoked:{user_public_id}`（user_public_id 即 JWT payload 中的 `user_id` 字段，为 UUID 字符串）

#### 1.8.2 新增方法：`_is_user_sessions_revoked()`

```python
    async def _is_user_sessions_revoked(self, user_public_id: str) -> bool:
        """检查用户会话是否已被吊销"""
        revocation_key = f"user_sessions_revoked:{user_public_id}"
        return await self.redis_client.exists(revocation_key) > 0
```

### 2.4 新增方法：`verify_otp_and_issue_ticket()`

**文件：** `backend/users/app/services/auth_service.py`（约第 878 行之后）

**完整逻辑：**

```
1. Redis GET otp:{scenario}:{recipient}
2. 不存在 → InvalidTokenException("验证码不存在或已过期")
3. 解析 JSON（兼容旧版纯字符串回退）
4. attempts >= max_attempts(5) → 删除 OTP → RateLimitException
5. code != 用户输入 → attempts += 1，保留 TTL → InvalidCredentialsException("还剩 N 次")
6. code == 用户输入 → 删除 OTP
7. RESET_PASSWORD 场景 → 查用户 by recipient → ticket 嵌入 user_id
8. 生成 ticket_id → Redis SET ticket:{scenario}:{ticket_id} (TTL 600s)
9. 返回 { ticket, expires_in }
```

**关键代码段：**

```python
# 比对验证码（错误时保留 TTL）
if otp_data["code"] != verify_request.code:
    otp_data["attempts"] = otp_data.get("attempts", 0) + 1
    ttl = await self.redis_client.ttl(otp_key)
    if ttl <= 0:
        await self.redis_client.delete(otp_key)
        raise InvalidTokenException("验证码不存在或已过期")
    await self.redis_client.set(otp_key, json.dumps(otp_data), ex=ttl)
    remaining = otp_data["max_attempts"] - otp_data["attempts"]
    raise InvalidCredentialsException(f"验证码错误，还剩 {remaining} 次机会")
```

**注意：** 使用 `redis.ttl() → redis.set(ex=ttl)` 而非 `keepttl` 参数，确保跨 Redis 客户端版本兼容。

```python
async def _consume_ticket(self, purpose: str, ticket_id: str) -> dict:
    """校验并消费 ticket（单次使用，读取后立即删除）"""
    ticket_key = f"ticket:{purpose}:{ticket_id}"
    ticket_data_str = await self.redis_client.get(ticket_key)

    if not ticket_data_str:
        raise InvalidTokenException("凭证无效或已过期")

    await self.redis_client.delete(ticket_key)  # 原子消费
    return json.loads(ticket_data_str)
```

### 2.6 改造 `perform_password_reset()` 支持双路径

**文件：** `backend/users/app/services/auth_service.py`

**变更前：** 仅支持 `reset_token` 路径。

**变更后：** 支持两条路径并行：

| 路径 | 凭据字段 | 获取 user_id 的方式 | 适用场景 |
|------|---------|-------------------|---------|
| 邮箱 token | `reset_token` | Redis `password_reset:{token}` → user.id | Web 端旧流程 |
| OTP ticket | `reset_ticket` | `_consume_ticket("RESET_PASSWORD", ticket)` → ticket_data["user_id"] | App 端短信 OTP 流程 |

**关键代码段：**

```python

    raise InvalidCredentialsException("缺少重置凭据")

# 0.1 先校验密码强度（两种路径共用，避免弱密码浪费凭据）

    raise WeakPasswordException("新密码不符合强度要求")

# ---- reset_ticket 路径 ----

    ticket_data = await self._consume_ticket(
        purpose="RESET_PASSWORD",
        ticket_id=confirm_request.reset_ticket,
    )
    user_id = int(ticket_data["user_id"])

# ---- reset_token 路径（保留兼容）----
elif confirm_request.reset_token:
    reset_key = f"password_reset:{confirm_request.reset_token}"
    # ... 原有逻辑 ...
```

**完整流程：**


### B. 逐个改动对应什么功能环节

#### 改动 ①：密码哈希 SHA-256 → bcrypt（Phase 1）

**对应环节：** 注册时写入密码、登录时验证密码、忘记密码后设置新密码、"已登录修改密码"

**改了什么：**
- 新建 `password.py`，统一提供 `hash_password()` / `verify_password()` / `is_legacy_sha256_hash()`。
- `AuthService` 和 `UserService` 都调用这个模块，不再各自写 `hashlib.sha256`。

**为什么这样改：**
```
SHA-256 是通用哈希算法，设计目标是"快"。
bcrypt 是密码专用哈希算法，设计目标是"慢"（故意消耗 CPU 时间）。

快 = 攻击者每秒可尝试数十亿次暴力破解
慢 = 攻击者每秒只能尝试几百次

所以密码必须用 bcrypt（或 argon2），不能用 SHA-256。
这是安全领域的铁律，不是可选的优化。
```

**为什么兼容旧 SHA-256：**
老用户已经在数据库里有 SHA-256 哈希值。如果直接只支持 bcrypt，老用户会全部登不上。`verify_password()` 看到 `$2b$` 开头走 bcrypt，看到 64 位 hex 字符串走 SHA-256——这样老用户不改密码也能登录。

**为什么做"滚动升级"：**
老用户登录成功后，用他刚输入的明文密码计算一份 bcrypt 哈希，覆盖旧值。这样用户下次登录就走 bcrypt 了。用户零感知，不需要通知"请重置密码"。

**判断：** ✅ 必要，不过度。这是安全底座，所有后续功能都依赖它。

---

#### 改动 ②：修复 reset token 消费时序（Phase 1）

**对应环节：** 忘记密码 → 点击邮箱链接 → 输入新密码

**改了什么：**
原来：`删除 Redis token → 校验密码强度 → 更新数据库`
现在：`校验密码强度 → 删除 Redis token → 更新数据库`

**为什么这样改：**
```
假设用户输入 "123" 作为新密码：

旧逻辑：
  Redis.DEL(reset_key)     ← token 已删除
  validate("123")          ← 密码太弱，拒绝
  return 错误              ← 用户回到页面，但 token 没了！
  
用户刷新页面或重新点链接 → "链接已过期" → 只能重新申请重置

新逻辑：
  validate("123")          ← 先检查密码
  return 错误              ← 还没删 token，token 还在
  Redis.DEL(reset_key)     ← 用户输入了强密码才删

用户重新输入一个强密码，token 还在，可以继续。
```

**判断：** ✅ 必要。这是一个 Bug 修复，不涉及任何新功能。

#### 改动 ③：日志脱敏（Phase 1）

**对应环节：** 发送验证码（注册/忘记密码的前置步骤）、发送密码重置邮件

**改了什么：**
- `logger.info(f"模拟发送验证码: code={otp_code}")` → 不再打 code
- `logger.info(f"模拟发送密码重置邮件: reset_token={reset_token}")` → 不再打 token

**为什么这样改：**
```
日志通常会：
  - 写入文件（可能被备份、被运维人员查看）
  - 发送到日志聚合系统（ELK / 阿里云 SLS）
  - 可能被错误地提交到 Git

如果日志里有"验证码 123456"，任何能看到日志的人
都可以用这个验证码去重置密码或注册假账号。

这不是理论风险——GitHub 上搜 "password" 能搜到大量
不小心提交的密码；验证码泄露同理。
```

**判断：** ✅ 必要。这是安全基线。

---

#### 改动 ④：重置后会话吊销（Phase 1）

**对应环节：** 忘记密码 → 重置成功

**改了什么：**
- 新增 `_revoke_user_sessions()`：密码重置后在 Redis 写一条 `user_sessions_revoked:{public_id}`。
- 新增 `_is_user_sessions_revoked()`：检查是否有吊销记录。
- `refresh_access_token()` 中增加吊销检查。

**为什么这样改：**
```
场景：用户手机丢了，用电脑重置密码。

旧逻辑：
  重置密码 → 新密码生效
  但手机上的 App 还在用旧的 refresh_token
  → 捡到手机的人可以无限刷新 access_token
  → 可以继续操作账号

新逻辑：
  重置密码 → Redis 写入吊销标记
  手机 App 下次刷新 token → 检测到吊销 → 拒绝
  → 强制重新登录 → 需要新密码 → 捡手机的人登不进去
```

**判断：** ✅ 必要。这是安全闭环的关键一步。

---

#### 改动 ⑤：账号状态检查（Phase 1）

**对应环节：** 忘记密码（所有路径）

**改了什么：**
- `request_password_reset()`：BANNED/DELETED 用户不生成 token（但返回统一成功，防枚举）。
- `perform_password_reset()`：BANNED/DELETED 用户直接拒绝。

**为什么这样改：**
被封禁用户不应该能通过"忘记密码"重置密码然后重新登录。
这会让封禁形同虚设。

**判断：** ✅ 必要。

---

#### 改动 ⑥：OTP 存储升级为 JSON（Phase 2）

**对应环节：** 发送验证码（注册/忘记密码的验证码发送步骤）

**改了什么：**
Redis 中从 `"123456"` 变为 `{"code":"123456","attempts":0,"max_attempts":5}`。

**为什么这样改：**
```
旧存储只有验证码本身，没有"这个验证码已经被试了几次"的信息。
这意味着攻击者可以无限次尝试 6 位数字验证码。

6 位数字 = 100 万种组合
如果每次尝试 100ms，全部试完约 28 小时
但如果只试 5 次，攻击者几乎不可能命中

所以要加 attempt 计数。5 次错误 → 锁定 → 必须重新获取。
```

**判断：** ✅ 必要。没有这个，暴力破解只是时间问题。

---

#### 改动 ⑦：新增 `verify_otp_and_issue_ticket()` + `_consume_ticket()`（Phase 2）

**对应环节：** 注册的验证码校验步骤、忘记密码的验证码校验步骤、未来绑定手机号的验证码校验步骤

**改了什么：**
- 新增校验方法：验证 OTP → 签发 ticket
- 新增消费方法：读取 ticket → 删除 ticket → 返回 payload

**为什么这样改（核心设计理念）：**

```
这是整个架构中最关键的抽象：把"证明你是谁"和"做什么事"分开。

❌ 旧模型（无 ticket）：
  前端 → POST /register {phone, otp_code, password}
  问题：注册接口直接拿到了 OTP，如果注册接口有 bug，OTP 就泄露了。
  而且忘记密码、绑定手机号都要各自校验 OTP，代码重复。

✅ 新模型（有 ticket）：
  前端 → POST /verification-codes {phone}        ← 发验证码
  前端 → POST /verification-codes/verify {code}  ← 验证码换 ticket
  前端 → POST /password-reset {ticket, password} ← 用 ticket 重置密码
         POST /register/phone {ticket, ...}      ← 用 ticket 注册（Phase 3）
         POST /me/phone {ticket}                 ← 用 ticket 绑定（未来）

  好处：
  1. 业务接口（注册/重置/绑定）永远不接触原始 OTP
  2. ticket 只能使用一次，即使泄露也很快过期
  3. 所有"验证身份"的逻辑集中在一个地方
```

**类比：**
```
你去银行取钱：

❌ 旧模型：你给柜员看你的脸，柜员说"哦是你"，给你钱。
   每个柜员都要会人脸识别。

✅ 新模型：你在门口刷身份证 → 拿到一张叫号小票 →
   把票给柜员 → 柜员只看票，不看脸。
   人脸识别只在门口那台机器上。
```

**判断：** ✅ 必要。ticket 模型不是"过度设计"，而是"必备的分层"。所有现代互联网公司（微信、支付宝、抖音）都这样设计。

---

#### 改动 ⑧：`perform_password_reset()` 支持双路径（Phase 2）

**对应环节：** 忘记密码 → 重置密码（最后一步）

**改了什么：**
原来只能通过 `reset_token`（邮箱链接）路径重置。
现在同时支持 `reset_token`（邮箱）和 `reset_ticket`（短信 OTP 验证后获取）。

**为什么这样改：**
```
当前用户都是邮箱注册的，邮箱重置必须保留。
但未来 App 用户更多，App 端用短信 OTP 重置更方便。

两条路径都走到同一个"更新密码"逻辑，不重复代码。
选哪条路由"凭据字段"决定：有 reset_token 走邮箱，有 reset_ticket 走 OTP。
```

**判断：** ✅ 必要。但不是"过度设计"——只多了一个 `if/elif` 分支，`reset_token` 老路径代码完全没动。

---

#### 改动 ⑨：新增 API 端点 `POST /auth/verification-codes/verify`（Phase 2）

**对应环节：** 所有需要验证码验证的流程的第二步

**改了什么：**
新增了一个 HTTP 端点，接收 `{channel, recipient, scenario, code}`，调用 `verify_otp_and_issue_ticket()`，返回 `{ticket, expires_in}`。

**为什么这样改：**
有发码接口就必须有验码接口，这是基本闭环。没有验码接口，发码接口是废的。

**判断：** ✅ 必要。

### C. 复杂度评估：有没有过度设计？

| 改动 | 代码量 | 是否过度 | 判断理由 |
|------|--------|---------|---------|
| bcrypt 替换 SHA-256 | ~40 行新文件 | ❌ 不 | 安全基线，SHA-256 不可接受 |
| 滚动升级 | ~8 行 | ❌ 不 | 没有这个，老用户登录后密码还是 SHA-256，等于白升级 |
| 日志脱敏 | ~4 行改 | ❌ 不 | 改两行 log 语句，几乎零成本 |
| 重置时序修复 | ~5 行挪 | ❌ 不 | Bug 修复，只是挪了顺序 |
| 会话吊销 | ~25 行 | ❌ 不 | 没有这个，重置密码不能真正踢掉旧设备 |
| 账号状态检查 | ~8 行 | ❌ 不 | 只是加了两个 if |
| OTP JSON 存储 | ~5 行改 | ❌ 不 | 只是把字符串变成 JSON |
| verify + ticket 方法 | ~70 行 | ❌ 不 | 这是核心逻辑，70 行很精简 |
| _consume_ticket | ~12 行 | ❌ 不 | 就是 Redis GET + DEL |
| 双路径密码重置 | ~15 行 | ❌ 不 | 一个 if/elif 分支，没有重复代码 |
| 新 API 端点 | ~48 行 | ❌ 不 | 大部分是错误处理和日志 |

**结论：所有改动都是"恰好够用"，没有过度设计。**

```
过度设计是什么样的？

❌ 过度设计示例：为 ticket 建一张数据库表，有 status/created_at/updated_at 等字段，
   有 Alembic 迁移脚本，有 management command 清理过期 ticket……
   而实际上 Redis + TTL 就够了。

✅ 当前实现：Redis SET + TTL 到期自动删除。没有额外表、没有迁移、没有清理脚本。

Phase 1+2 总共新增约 250 行代码（含注释和空行），改动 10 个文件。
这是典型的"少就是多"——用最少的代码解决最关键的问题。
```

### D. 为什么必须分 Phase 而不是一次做完？

```
Phase 1 先修底座：
  不改任何接口、不引入新概念、不改 Redis 数据结构。
  只把"已经在用的东西"修正确（bcrypt、时序、日志、会话）。

  → 可以立刻部署到生产环境，风险极低。

Phase 2 再加闭环：
  基于 Phase 1 修好的底座，引入 ticket 概念。
  不影响 Phase 1 已稳定的旧路径（reset_token 照样能走）。

  → 即使 Phase 2 有 bug，旧路径不受影响，可以安全回滚。

如果 Phase 1 和 Phase 2 混在一起做：
  - 一次改动太多，排查困难
  - ticket 出问题时，不确定是 ticket 逻辑错了还是密码哈希错了
  - 无法"先上线底座，再上线闭环"
```
