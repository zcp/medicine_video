# 后端上传接口提示词

## 1. 适用对象与任务目标

本提示词适用于当前项目中**用户头像图片上传接口**的后端实现。

本任务的目标不是单纯把图片存起来，而是补齐一条稳定、可复用、可展示的上传闭环：
- 接收前端上传的本地图片；
- 对图片类型、大小、来源做基础校验；
- 将图片保存到稳定存储；
- 返回可直接用于前端展示的稳定 `avatar_url`；
- 支持将头像 URL 持久化到用户资料中；
- 与现有用户资料读取与更新接口保持一致。

本任务的核心定位是：
- **优先补稳定上传链路**；
- **优先保证上传结果可长期访问**；
- **优先复用现有 `avatar_url` 字段**；
- **不新增重复的用户资料体系**。

---

## 2. 强约束与执行前提

### 2.1 当前任务的默认前提
- 当前项目中已经存在用户资料更新能力，且 `avatar_url` 字段已进入现有模型和前端类型定义；
- 当前前端项目使用 `src/api/auth.ts` + `authUrl(path)` + `post/get/patch` 的封装风格，后端接口设计应与这一现有调用习惯保持一致；
- 当前任务是对头像上传链路进行补充与稳定化，而不是重写整个用户系统；
- 当前任务优先服务“图片能够稳定上传和稳定显示”的目标，不扩展到复杂图片管理场景。

### 2.2 禁止重复造接口
- 禁止新建一套独立的用户资料体系；
- 禁止为了头像上传另起一套完全重复的个人资料接口；
- 禁止将 `avatar_url` 替换为新的重复字段，例如 `avatar`, `head_img`, `profile_pic` 等；
- 如需增加上传能力，优先围绕现有用户模块做增量补充；
- 接口路径、请求字段、响应结构必须前后一致，避免让前端额外做兼容分支。

### 2.3 必须先审查再修改
在生成任何代码前，必须先读取并理解：
- 后端用户资料相关 API 文件；
- 后端用户模型与 schema 中关于头像字段的定义；
- 前端 `D:\saas_app-main\src\api\auth.ts` 中的 `updateProfile()` 与 `authUrl()` 风格；
- 前端个人信息编辑页的当前实现；
- 当前是否已有头像上传接口或通用文件上传能力。

严禁在未审查上述内容前直接：
- 猜测接口路径；
- 猜测字段名；
- 重写已有资料更新逻辑；
- 新建一套与现有字段不一致的头像方案。

### 2.4 文件级别约束
为了避免范围过宽，生成代码时必须严格限制可修改文件范围。

#### 允许修改的文件范围
- 后端用户资料相关 API 文件；
- 后端用户服务层与数据访问层中与头像字段相关的最小必要部分；
- 后端必要的图片存储工具或配置文件；
- 少量与头像上传相关的 schema 或响应模型；
- 前端必要的 API 封装文件，仅用于对接上传接口。

#### 不允许随意修改的文件范围
- 不允许重构整个用户系统；
- 不允许大范围修改请求框架或认证机制；
- 不允许改动与头像无关的其它业务 API；
- 不允许改动登录、注册、验证码、密码重置等无关流程；
- 不允许新增一套平行的用户资料目录结构。

### 2.5 默认执行顺序
1. 审查当前后端用户资料接口与数据模型；
2. 明确头像上传是否已有专用接口；
3. 如无专用接口，补充最小可用上传链路；
4. **先固定接口定义，再写实现代码**；
5. 统一上传结果字段与用户资料字段；
6. 核查后端返回的头像 URL 是否稳定可访问；
7. 再确认前端是否可以直接复用该 URL 展示头像。

## 3. 当前任务边界

### 3.1 本任务必须实现的内容
- 图片文件上传；
- 图片类型与大小校验；
- 上传后返回可访问的图片 URL；
- 将返回的 `avatar_url` 持久化到用户资料；
- 读取用户资料时可继续返回头像 URL；
- 上传失败时可明确返回错误信息。

### 3.2 本任务不要扩展的内容
本任务**不要**优先扩展以下方向，除非上传闭环必须依赖它们：
- 头像裁剪交互；
- 图片压缩算法优化；
- 多图上传；
- 头像历史版本管理；
- 图片审核工作流；
- 用户封面图、背景图等其他图片类型。

## 4. 现有资源与可复用基础

当前项目中可复用资源包括：
- 后端用户资料更新接口；
- 后端用户信息返回接口；
- 后端用户 schema 中的 `avatar_url` 字段；
- 前端 `src/api/auth.ts` 中的 `authUrl()` 风格与 `updateProfile()`；
- 前端用户信息状态管理与头像展示逻辑。

本任务必须优先复用上述资源，严禁为了上传功能复制一套新的用户资料模块。

## 5. 任务一：补后端图片上传能力

### 5.1 任务目标
让后端能够稳定接收前端上传的本地图片，并返回一个可直接用于前端展示的 URL。

### 5.2 建议实现方向
建议优先补以下能力中的一项或多项：
- 新增或完善头像上传接口；
- 接收 `multipart/form-data` 文件；
- 对文件类型、文件大小、文件名进行校验；
- 将图片保存到稳定存储；
- 返回标准化的 `avatar_url`；
- 支持后续通过资料更新接口写回用户表。

### 5.3 设计要求
后端上传能力应满足：
- 接口命名清晰；
- 返回结构统一；
- 文件存储位置稳定；
- 图片 URL 可长期访问；
- 与现有资料更新接口字段一致；
- 不破坏当前登录与资料读取流程。

### 5.4 优先实现方式
- 优先在现有用户模块中补充头像上传接口；
- 优先复用已有用户资料更新逻辑；
- 优先复用现有返回结构与错误处理方式；
- 如有通用文件上传能力，可先复用，再补齐头像场景的差异化逻辑。

### 5.5 完成标准
完成后应满足：
- 前端上传图片后能拿到稳定 URL；
- URL 写回用户资料后可再次查询到；
- 服务重启后头像仍可访问；
- 文件类型或大小不合法时能够明确报错。

---

## 6. 接口与数据定义要求

### 6.1 头像上传接口
建议采用如下模式之一，并在全项目中统一：
- `POST /users/me/avatar`；
- 或与现有用户模块风格一致的等价路径。

请求建议：
- `multipart/form-data`；
- 文件字段统一命名为 `file`；
- 只允许上传单文件；
- 头像图片不在后端做裁剪，只做接收与落盘。

响应建议：
```json
{
  "code": 200,
  "message": "success",
  "data": {
    "avatar_url": "https://example.com/uploads/avatar/xxx.jpg"
  }
}
```

### 6.2 用户资料更新接口
继续复用现有 `PATCH /users/me`，建议支持：
```json
{
  "nickname": "新昵称",
  "bio": "个人简介",
  "avatar_url": "https://example.com/uploads/avatar/xxx.jpg"
}
```

### 6.3 用户信息读取接口
`GET /users/me` 应继续返回 `avatar_url`，供前端个人信息页直接渲染。

## 7. 风险与隐患处理建议

### 7.1 图片 URL 稳定性不足
建议统一使用稳定可访问地址，不要把临时文件地址作为最终头像 URL。优先级建议：
1. 对象存储稳定 URL；
2. 持久化静态目录 + Nginx 暴露；
3. 避免临时目录或进程内临时路径。

### 7.2 上传失败后的状态恢复不完善
建议接口层尽量返回清晰的错误信息，并支持前端做“可恢复流程”：
- 上传失败不影响用户已保存资料；
- 资料更新失败不影响本地已选图片状态；
- 前端可重新发起上传或重新保存。

### 7.3 手机端兼容性问题
建议后端只负责稳定接收与返回，不把裁剪、缩放等移动端交互复杂度放到后端；文件类型和大小限制要明确，避免移动端过大图片导致接口超时或失败。

### 7.4 字段不一致风险
建议后端在响应中只返回一个权威字段 `avatar_url`，不要同时返回多个近似字段，避免前端映射混乱。

## 8. 实现建议与代码修改边界

### 8.1 优先修改位置
优先修改：
- 后端用户资料相关 API 文件；
- 后端用户服务与数据访问层；
- 必要的图片存储工具或配置；
- 少量响应结构与 schema 定义。

### 8.2 尽量不要做的事
- 不要为了头像上传重构整个用户系统；
- 不要新建第二套用户资料接口；
- 不要把临时路径当成最终头像地址保存到数据库。

### 8.3 可接受的小幅扩展
可接受的扩展包括：
- 新增一个头像上传专用接口；
- 新增基础文件校验与错误提示；
- 新增稳定存储适配；
- 新增默认返回结构。

## 9. 验收标准

若 AI 完成本任务，最终应满足以下要求：
- 用户可以从本地相册选择图片并上传；
- 后端能够稳定返回可访问的 `avatar_url`；
- 用户资料接口可正确保存并返回头像 URL；
- 上传失败时能返回明确错误；
- 不新增重复的用户资料字段或重复模块。

---

可以直接向 AI 下达如下要求：
- 当前任务只做后端图片上传接口，不要扩展到裁剪页；
- 必须先读现有后端用户资料接口与 `avatar_url` 字段，再给实现方案；
- 只允许在现有模块基础上增量实现上传闭环；
- 禁止新建重复用户资料体系；
- 本轮重点是：稳定上传、稳定返回 URL、稳定持久化，不要额外扩展其他图片业务。

## 11. 结论

本提示词服务于当前项目中头像上传能力的补齐工作，目标是：
- 让图片可以稳定上传；
- 让头像 URL 可以稳定返回并持久化；
- 让前后端围绕现有 `avatar_url` 形成闭环；
- 在不破坏现有资料模块的前提下，完成最小而稳定的增量实现。
