### 2.1 测试对齐与修复自动化流程主控提示词

**文件路径**: `docs/提示词/自动化测试/测试对齐与修复自动化流程主控提示词.md`

**用途**: 主控流程文档，指导AI执行从测试代码生成到修复的完整自动化流程

**核心功能**:
1. ✅ 支持自动化测试代码生成（步骤1）
2. ✅ 支持测试执行结果分析（步骤2-3）
3. ✅ 支持测试代码与设计文档一致性检测（步骤4.1）
4. ✅ 支持后端代码与设计文档一致性检测（步骤4.2）
5. ✅ 支持最小幅度修复（步骤5）
6. ✅ 支持循环修复流程（步骤3-7）
7. ✅ 支持费用控制（限制最大迭代次数）
8. ✅ 支持状态跟踪与断点续传（第6节）

**流程步骤**:
```
步骤0: 读取设计文档（真相源）
步骤1: 生成测试代码（使用测试母版）
步骤2: 自动运行测试
步骤3: 解析测试输出，识别失败
步骤4: 判断失败原因（一致性检测）
  ├─ 4.1: 检测测试代码 vs 设计文档
  └─ 4.2: 检测后端代码 vs 设计文档
步骤5: 执行修复（最小幅度，只修一个失败点）
步骤6: 自动重跑测试
步骤7: 循环判断（是否继续）
```

**费用估算**:
- 单个模块完整流程（3次迭代）：~67500 tokens
- 最坏情况（10次迭代）：~148000 tokens

## 3. 快速开始指南

### 3.1 前置条件

1. **设计文档**: 确保有完整的设计文档（包含DDL、API定义、Schema定义）
2. **目标代码文件**: 确保目标代码文件已存在（Model、Schema、CRUD、Service、API）
3. **测试脚本**: 确保有可执行的测试脚本（如 `./scripts/test.sh`）

### 3.2 启动自动化流程

**步骤1: 准备输入参数**

```markdown
**设计文档**: @docs/03_系统设计/直播核心功能设计文档_v6_XXX模块设计文档.md

**目标代码文件**:
- @app/models/xxx.py
- @app/schemas/xxx.py
- @app/crud/xxx.py
- @app/services/xxx_service.py
- @app/api/v1/endpoints/xxx.py

**模块名**: xxx
**输出目录**: docs/提示词/测试
**测试模式**: incremental（增量）或 full（全新）
**最大迭代次数**: 10（默认）
```

**步骤2: 执行主控提示词**

```
@docs/提示词/自动化测试/测试对齐与修复自动化流程主控提示词.md

请执行测试对齐与修复自动化流程：

[粘贴步骤1的输入参数]
```

**步骤3: 配合AI执行流程**

- AI执行步骤0-1后，会要求用户执行测试脚本
- 用户执行 `./scripts/test.sh > test_output.txt 2>&1`
- 将测试输出文件提供给AI
- AI继续执行步骤3-5
- 如果需要修复，用户重新执行测试脚本（步骤6）
- 循环直到所有测试通过或达到最大迭代次数

### 3.3 断点续传

如果流程中断，可以从状态文件恢复：

```
@docs/提示词/自动化测试/测试对齐与修复自动化流程主控提示词.md

请继续执行测试对齐与修复自动化流程：

**状态文件**: .generation_state/test_alignment_{module_name}_state.json
**从步骤**: step5（执行修复）
**新测试输出**（如果有）: test_output_iteration_2.txt
```

## 4. 使用示例

### 4.1 完整示例：内容管理模块

**输入**:

```
@docs/提示词/自动化测试/测试对齐与修复自动化流程主控提示词.md

请执行测试对齐与修复自动化流程：

**设计文档**: @docs/03_系统设计/直播核心功能设计文档_v6_内容管理模块设计文档-标签-分类-场次标签关联.md

**目标代码文件**:
- @app/models/content_management.py
- @app/schemas/content_management.py
- @app/crud/content_management.py
- @app/services/content_management_service.py
- @app/api/v1/endpoints/content_management.py

**模块名**: content_management
**输出目录**: docs/提示词/测试
**测试模式**: incremental
**最大迭代次数**: 10
```

**执行流程**:

1. AI执行步骤0（读取设计文档）
2. AI执行步骤1（生成测试代码）
   - 生成 `tests/test_crud_content_management.py`
   - 生成 `tests/test_service_content_management.py`
   - 生成 `tests/test_api_content_management.py`
3. AI要求用户执行测试
4. 用户执行 `./scripts/test.sh > test_output.txt 2>&1`
5. 用户将 `test_output.txt` 提供给AI
6. AI执行步骤3（解析测试输出）
7. AI执行步骤4（一致性检测）
   - 检测到：测试使用了字段名 `title`，但设计文档定义为 `name`
   - 判断：测试代码不一致
8. AI执行步骤5（修复测试代码）
   - 修改 `tests/test_crud_content_management.py:45`
   - 将 `tag.title` 修改为 `tag.name`
9. AI要求用户重跑测试
10. 用户执行 `./scripts/test.sh > test_output_iteration_1.txt 2>&1`
11. 用户将 `test_output_iteration_1.txt` 提供给AI
12. AI执行步骤7（循环判断）
    - 如果还有失败，回到步骤3
    - 如果没有失败，流程完成 ✅

**输出**:

- 测试代码文件（3个）
- 测试提示词文档
- 一致性检测报告（每次迭代1个）
- 修复摘要（每次迭代1个）
- 状态文件（JSON格式）

## 5. 核心原则

### 5.1 真相源原则

**定义**: 设计文档/接口契约是唯一的真相源

**应用**:
- 所有一致性检测都以设计文档为准
- 如果测试代码与设计文档不一致，修改测试代码
- 如果后端代码与设计文档不一致，修改后端代码
- 如果测试和后端都与设计文档一致，但测试仍然失败，说明设计文档有问题，需要人工介入

### 5.2 修复优先级原则

**顺序**:
1. **第一优先级**: 测试代码是否与设计文档一致？
   - 如果不一致 → 修改测试代码（优先）
2. **第二优先级**: 后端代码是否与设计文档一致？
   - 如果不一致 → 修改后端代码（最小幅度）
3. **第三优先级**: 设计文档是否有问题？
   - 如果都一致但测试仍失败 → 需要人工介入

### 5.3 最小化修改原则

**规则**:
- 每次只修复一个失败点
- 只修改必要的内容，不过度修改
- 不修改与当前失败无关的代码
- 增量测试模式：严禁修改已存在的其他测试函数

### 5.4 禁止行为

**严格禁止**:
- ❌ 禁止跳过测试或弱化断言
- ❌ 禁止为通过测试而修改已符合设计文档的后端行为
- ❌ 禁止猜测字段名、函数名、端点路径

## 6. 费用控制

### 6.1 费用估算

| 场景 | Token费用 | 说明 |
|------|----------|------|
| **单个模块（3次迭代）** | ~67500 tokens | 大多数模块预计2-3次迭代即可通过 |
| **单个模块（最坏情况）** | ~148000 tokens | 达到最大迭代次数（10次） |
| **费用（按 $2/M tokens）** | $0.13 - $0.30 | 单个模块的费用范围 |

### 6.2 费用控制措施

1. **限制最大迭代次数**：默认10次
2. **使用状态跟踪**：避免重复分析
3. **使用摘要**：避免重复读取完整文档
4. **分步检测**：先检测测试，再检测后端（70%的情况只需要检测测试）

### 6.3 费用优化建议

1. **使用增量测试模式**：只生成新增的测试代码，减少步骤1的费用
2. **提前检查设计文档**：确保设计文档完整，避免后续步骤浪费Token
3. **记录常见问题**：建立常见猜测问题库，在生成测试代码时自动避免

## 7. 常见问题

### Q1: 如何判断是使用增量模式还是全新模式？

**A**: 
- 如果项目已存在 `tests/conftest.py` 或任何 `tests/test_*.py` 文件 → 使用增量模式
- 如果项目完全没有测试文件 → 使用全新模式
- 如果不确定，优先使用增量模式（更安全）

### Q2: 如果AI判断错误怎么办？

**A**: 
- 一致性检测报告会提供详细的证据（引用原文和行号）
- 用户可以人工审核一致性检测报告
- 如果AI判断错误，用户可以手动修复，然后继续流程

### Q3: 如果循环修复一直失败怎么办？

**A**: 
- 流程会自动停止（达到最大迭代次数）
- 检查 `fix_history`，查看是否在重复修复相同的问题
- 如果是，需要人工介入分析根本原因

### Q4: 如何减少费用？

**A**: 
1. 确保设计文档完整（避免后续步骤浪费Token）
2. 使用增量测试模式（只生成新增的测试代码）
3. 提前检查测试代码是否有明显的猜测问题
4. 降低最大迭代次数（如果预算有限）

### Q5: 如何验证文档的正确性？

**A**: 
- 查看 `docs/提示词/测试自动化文档自检报告.md`
