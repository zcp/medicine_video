### 3.2 状态表设计（crawl_import_status）

**表名**：`crawl_import_status`（PostgreSQL）

**字段与约束**：

```sql
CREATE TABLE crawl_import_status (
    user_id   UUID PRIMARY KEY,                    -- 用户ID（主键）
    status    VARCHAR(20) NOT NULL DEFAULT 'running',  -- 状态：running, completed, failed
    progress  JSONB,                               -- 进度信息（JSON格式）
    updated_at TIMESTAMP NOT NULL DEFAULT NOW()    -- 更新时间
);

-- 索引：用于查询和清理过期记录
CREATE INDEX idx_crawl_import_status_updated_at ON crawl_import_status(updated_at);
```

**状态语义**：

* `running`：任务执行中
* `completed`：任务已完成
* `failed`：任务失败

**`progress` 字段结构（JSONB）**：

```json
{
  "start_time": "2025-11-19T10:00:00Z",
  "end_time": "2025-11-19T12:30:00Z" | null,
  "current_page": 5,
  "total_pages": 100,
  "crawled_rows": 500,
  "imported_rows": 450,
  "result": { ... } | null,  // 完成时返回完整结果（crawl_status, import_result等）
  "error": "错误信息" | null
}
```

进度结构可以按需要扩展，但**字段命名需清晰、使用小写+下划线，保持 JSON 友好**。

要求使用现有模型的统一风格：

* 使用 `datetime.utcnow` 作为默认时间
* 字段使用中文注释

示例模型结构（由 AI 按此风格生成具体代码）：

```python
from datetime import datetime
from sqlalchemy import Column, String, DateTime, Index
from sqlalchemy.dialects.postgresql import UUID, JSONB
from app.database import Base


class CrawlImportStatus(Base):
    """爬取导入任务状态表"""
    __tablename__ = "crawl_import_status"

    user_id = Column(UUID(as_uuid=True), primary_key=True, comment="用户ID")
    status = Column(String(20), nullable=False, default="running", comment="状态：running, completed, failed")
    progress = Column(JSONB, nullable=True, comment="进度信息（JSON格式）")
    updated_at = Column(
        DateTime,
        nullable=False,
        default=datetime.utcnow,
        onupdate=datetime.utcnow,
        comment="更新时间",
    )

    __table_args__ = (
        Index("idx_crawl_import_status_updated_at", "updated_at"),
    )
```

### 4.2 状态管理工具：`app/core/crawl_import_status.py`

需要实现以下三个核心函数，使用 SQLAlchemy Session，遵循统一异常与日志规范：

#### 4.2.1 `save_crawl_import_status(db, user_id, status, progress) -> bool`

功能：**保存（插入或更新）某用户的任务状态**

约束：

* 使用 PostgreSQL `INSERT ... ON CONFLICT (user_id) DO UPDATE` 实现**一个用户一条记录**的自动覆盖
* `status` 值限定为 `'running' | 'completed' | 'failed'`
* `progress` 为 dict，将直接写入 JSONB
* 成功时 `db.commit()` 并返回 `True`
* 失败时 `db.rollback()`、记录 ERROR 日志（带 `exc_info=True`），但**返回 False，不抛异常**（不影响主流程）

日志风格：

* 成功：`logger.info(f"状态保存成功 - User: {user_id_for_logging}, Status: {status}")`
* 失败：`logger.error(..., exc_info=True)`

#### 4.2.2 `get_crawl_import_status(db, user_id) -> dict | None`

功能：**按 user_id 查询状态**

返回结构：

```python
{
    "status": "running" | "completed" | "failed",
    "progress": {...} | None,  # 由 JSONB 自动转换为 dict
    "updated_at": "2025-11-19T10:00:00Z" | None
}
```

异常处理：

* 查询出错时，记录 ERROR 日志（`exc_info=True`），返回 `None`，不抛异常

#### 4.2.3 `check_running_task(db, user_id, max_running_hours: int = 3) -> bool`

功能：**用于并发控制，判断当前用户是否有“仍然有效的 running 状态”**

逻辑：

1. 查询 `status == 'running'` 的记录
2. 若不存在：返回 `False`
3. 若存在：

   * 若 `updated_at` 超过 `max_running_hours`（默认 3 小时）之前，则视为**异常状态**，记录 WARNING 日志并返回 `False`（允许新任务）
   * 否则返回 `True`（有正在运行的任务）
4. 若查询过程中抛异常：记录 ERROR 日志，并返回 `True`（**安全起见，阻止新任务**）

### 5.2 修改 `POST /api/v1/download/tasks/crawl-and-import`

目标：在**保持原有同步执行逻辑完全不变**的前提下，增加：

1. **变量提取 & 安全日志变量**

   * 从 `current_user` 中提取 `user_id_for_logging = current_user["user_id"]`（str）
   * 使用 `UUID(user_id_for_logging)` 生成真正的 `user_id` 对象
   * 约束：**不在任何日志中记录 token / cookie 的真实值**

2. **并发控制：检查是否已有运行中的任务**

   * 调用 `check_running_task(db, user_id)`
   * 若返回 `True`：

     * 通过 `get_crawl_import_status(db, user_id)` 获取当前 running 状态，用于返回给前端
     * 记录 WARNING 日志：`logger.warning(f"并发控制 - User: {user_id_for_logging}, 有正在运行的任务")`
     * 返回统一错误响应（**HTTP 200，业务 code=409**）：

       ```python
       return create_error_response(
           message="您有一个爬取导入任务正在执行中，请等待任务完成后再试",
           code=409,
           data={
               "status": "running",
               "start_time": progress.get("start_time") if progress else None,
               "suggestion": "您可以通过 GET /api/v1/download/tasks/crawl-import-status 接口查询任务状态",
           },
       )
       ```

3. **无运行任务：写入 `running` 状态**

   * 构造 `progress_data = {"start_time": datetime.utcnow().isoformat()}`
   * 调用 `save_crawl_import_status(db, user_id, "running", progress_data)`
   * 成功与否均不影响主流程；失败时 `save_crawl_import_status` 内部记录 ERROR/返回 False，上层只需记录 WARNING（可选）。

4. **调用服务层执行原有同步任务**

   * 保持原有 `DownloadService.crawl_and_import_tasks(...)` 调用与参数不变（包括 token/cookie 等），状态管理仅包裹在外层。

5. **成功完成后：写入 `completed` 状态**

   * 构建 `progress`：

     * `start_time`：沿用之前写入的值（可从状态中读取，也可在内存中缓存）
     * `end_time`: `datetime.utcnow().isoformat()`
     * `result`: 保存服务层返回的完整结果（包括 crawl_status / 导入统计 等）
   * 调用 `save_crawl_import_status(db, user_id, "completed", progress)`
   * 记录 INFO 日志：`logger.info(f"Crawl and import completed - User: {user_id_for_logging}, ...")`（禁止记录 token/cookie 值）

6. **异常处理：写入 `failed` 状态并保持原有错误处理**

   * 在 `except Exception as e:` 中：

     * 构造 `progress`：

       * `end_time`：当前时间
       * `error`: `str(e)`（注意不要包含 token/cookie）
     * 调用 `save_crawl_import_status(db, user_id, "failed", progress)`
     * 记录错误日志：
       `logger.error(f"Crawl failed - User: {user_id_for_logging}, Error: {str(e)}", exc_info=True)`
     * **保持原有异常传播方式**：如果原来是抛出异常，让全局异常处理中间件转换为统一响应，则继续抛出；如果原来在此处构造 `create_error_response` 返回，则保持该逻辑。

> 重要约束：**状态更新失败不能影响爬虫/导入主流程**，只记录日志即可。

### 5.3 新增 `GET /api/v1/download/tasks/crawl-import-status`

在 `download.py` 中新增一个查询接口：

* **路径**：`GET /api/v1/download/tasks/crawl-import-status`
* **认证**：必须依赖 `get_current_user`（JWT Token）
* **功能**：返回当前用户的状态信息（若存在）

**⚠️ 关键约束：路由定义顺序**

**FastAPI 路由匹配顺序问题**：
* FastAPI 按照路由定义的**顺序**进行匹配，**固定路径必须放在参数路径之前**
* 如果 `/tasks/{task_id}` 定义在 `/tasks/crawl-import-status` 之前，会导致：
  * FastAPI 尝试将 `crawl-import-status` 解析为 `task_id` 参数（UUID类型）
  * 解析失败，返回 **422 Unprocessable Entity** 错误
  * 函数根本不会被执行（所有日志和 print 都不会输出）
* **解决方案**：将 `@router.get("/tasks/crawl-import-status")` 路由定义放在 `@router.get("/tasks/{task_id}")` **之前**
* **检查方法**：在文件中搜索 `@router.get("/tasks/{task_id}")`，确保新路由定义在其之前

实现要点：

1. 从 `current_user` 中提取 `user_id_for_logging`、生成 `user_id = UUID(user_id_for_logging)`
2. 记录请求开始日志（INFO）
3. 调用 `get_crawl_import_status(db, user_id)`

   * 若返回 `None`：

     * 记录 INFO 日志：状态不存在
     * 返回 `create_error_response(message="未找到爬取导入任务状态", code=404)`
   * 若存在：

     * 记录 INFO 日志：状态查询成功
     * 返回 `create_response(data=status, message="查询成功", code=200)`
4. 任何异常：

   * 记录 ERROR 日志（`exc_info=True`）
   * 返回 `create_error_response(message="查询状态时发生错误", code=500)`

## 六、统一响应格式与错误码规范

**统一使用系统已有的响应封装工具：**

* 成功：`create_response(data=..., message="...", code=<业务码>)`
* 失败：`create_error_response(message="...", code=<业务码>, data=...)`

约定：

* **HTTP 状态码永远使用 200**（除非特殊全局错误），业务错误通过 `code` 字段表达
* 推荐业务 code：

  * `200`：成功
  * `404`：状态不存在
  * `409`：并发冲突（已有 running 任务）
  * `500`：查询/内部错误（仅状态查询接口内部使用）

响应结构固定为：

```json
{
  "code": 200,
  "message": "查询成功",
  "data": { ... } | null,
  "timestamp": "2025-11-19T10:05:00Z"
}
```

## 七、异常处理与日志规范

### 7.1 异常处理

* 继续使用现有异常体系（如 `CrawlerError`, `CrawlerConfigError`, `DatabaseError` 等）作为主业务异常。
* 状态更新相关函数：

  * `save_crawl_import_status` / `get_crawl_import_status` / `check_running_task` **内部捕获异常**，记录日志并返回安全值（`False`、`None` 或 `True`）；
  * 不向上抛出异常，以免破坏原有爬虫/导入主流程。
* API 层：

  * 对于状态查询接口：异常时转换为 `create_error_response(..., code=500)`；
  * 对于爬虫导入接口：保持原有异常传播方式不变，仅在外层附加状态更新逻辑。

### 7.2 日志规范（安全 + 分级）

统一日志级别：

* `INFO`：

  * 状态写入/更新成功
  * 状态查询成功
  * 爬虫导入开始、结束（不记录敏感信息）
* `WARNING`：

  * 并发控制触发（有 running 任务）
  * 检测到运行时间异常（running 超过 3 小时）
  * 状态更新失败但不影响业务主流程
* `ERROR`：

  * 数据库操作失败（保存/查询状态异常）
  * API 中未捕获的异常（附带 `exc_info=True`）

**安全要求（非常重要）：**

* 所有日志中**禁止记录 token 和 cookie 的实际值**；
  只能记录：

  * 是否来自“前端传递”或“配置读取”
  * 当前用户 ID、任务状态等非敏感信息
* 错误日志中禁止把 token/cookie 字符串拼接进异常消息。

## 九、前端集成约束（概要）
