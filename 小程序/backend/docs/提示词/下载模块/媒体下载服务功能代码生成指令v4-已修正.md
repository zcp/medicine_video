## 二、实现规范

### 2.1. 服务层实现规范

#### 2.1.1. 数据操作规范
- 使用 `model_dump()` 获取数据
- 使用 `**` 解包操作符创建实例
- 使用 `db.add()` 添加实例
- 使用 `db.commit()` 提交事务
- 使用 `db.refresh()` 刷新实例

#### 2.1.2. 错误处理规范
- 处理 `IntegrityError`
- 处理 `OperationalError`
- 处理 `SQLAlchemyError`
- 记录错误日志
- **必须在所有数据库操作异常时执行`db.rollback()`**
- **对于commit操作，必须包裹在try-except块中**
- **异常处理的层次原则**：
  * 谁commit谁rollback - 在执行commit的函数中捕获异常并rollback
  * 调用链保护 - 外层函数需要有兜底的异常处理和rollback
  * 避免冗余rollback - rollback是幂等操作，多次调用是安全的
- **异常后的对象刷新**：rollback后如果需要继续使用ORM对象，必须执行`db.refresh(obj)`重新加载

#### 2.1.3. 日志记录规范
- 记录创建操作
- 记录更新操作
- 记录删除操作
- 记录错误信息
- 记录关键参数

#### 2.1.4. 安全异步异常处理规范（核心原则）
**🛡️ 在异常处理中访问ORM对象的安全规则**：

- **规则**：在任何 `try...except` 块中，如果需要在 `except` 块中使用来自数据库ORM对象（如 `current_user`、`task`）的属性进行日志记录或错误处理，这些属性**必须在进入 `try` 块之前**被提取并存储到局部变量中。

- **禁止**：严禁在捕获了数据库相关异常（如 `IntegrityError`、`SQLAlchemyError`）的 `except` 块中直接访问可能已与失效会话关联的ORM对象的属性。

- **实现流程**：
  ```python
  # ✅ 正确做法：在 try 块之前提取
  user_id_for_logging = current_user["user_id"]  # 从JWT提取
  task_id_for_logging = str(task_id)  # 从参数提取
  
  try:
      # 数据库操作
      task = self.db.query(DownloadTask).filter(...).first()
      # 进一步操作...
  except SQLAlchemyError as e:
      # ✅ 使用之前提取的局部变量
      logger.error(f"操作失败 - 用户ID: {user_id_for_logging}, 任务ID: {task_id_for_logging}, 错误: {str(e)}")
      self.db.rollback()
      # ❌ 不要在这里访问 task.id 或 current_user.id
  ```

- **适用场景**：
  * API端点函数中的异常处理
  * 服务层方法中涉及数据库操作的异常处理
  * 任何可能导致数据库会话失效的操作

#### 2.3.4. API端点异常处理规范
**🧱 主动变量提取 + 统一异常处理**：

```python
from fastapi import APIRouter, Depends
from fastapi.responses import JSONResponse
from app.core.response import create_response, create_error_response

@router.post("/tasks")
async def create_task(
    task_data: DownloadTaskCreate,
    current_user: dict = Depends(get_current_user),
    db: Session = Depends(get_db)
):
    # 1. 在 try 块之前提取所有需要的变量（用于异常处理）
    user_id_for_logging = current_user["user_id"]
    resource_url_for_logging = str(task_data.resource_url)
    
    try:
        # 2. 业务逻辑
        service = DownloadService(db)
        task = service.create_download_task(task_data, user_id_for_logging)
        
        # 3. 转换为字典（处理UUID和datetime序列化）
        task_dict = {
            "id": str(task.id),
            "user_id": str(task.user_id),
            # ... 其他字段
        }
        
        # 4. ✅ 成功响应
        return create_response(
            code=201,
            message="创建下载任务成功",
            data=task_dict
        )
        
    except ValueError as e:
        # 5. ❌ 业务逻辑错误（如参数验证失败）
        logger.warning(
            f"业务逻辑错误 - 用户ID: {user_id_for_logging}, "
            f"资源URL: {resource_url_for_logging}, 错误: {str(e)}"
        )
        return JSONResponse(
            status_code=400,
            content=create_error_response(code=1001, message=str(e))
        )
        
    except SQLAlchemyError as e:
        # 6. ❌ 数据库错误
        logger.error(
            f"数据库错误 - 用户ID: {user_id_for_logging}, "
            f"错误: {str(e)}",
            exc_info=True
        )
        db.rollback()
        return JSONResponse(
            status_code=500,
            content=create_error_response(code=1002, message="数据库操作失败")
        )
        
    except Exception as e:
        # 7. ❌ 未知错误
        logger.error(
            f"未知错误 - 用户ID: {user_id_for_logging}, "
            f"错误类型: {type(e).__name__}, 错误: {str(e)}",
            exc_info=True
        )
        return JSONResponse(
            status_code=500,
            content=create_error_response(code=1000, message="服务器内部错误")
        )
```

## 三、核心功能实现

### 3.1. 下载功能概述
- **HLS视频流下载**
- **MP4视频文件下载**
- **图片资源下载**
- **并发下载控制**
- **断点续传**
- **失败重试机制**

### 3.2. HLS视频文件下载功能需求

#### 3.2.1. 下载功能
- 支持下载m3u8索引文件
- 支持下载ts分片文件
- 支持下载失败重试(最多重试3次)
- 支持下载进度实时更新
- 支持并发下载控制(最大并发数20)
- 支持分片并发下载(可配置并发数)
- 支持HLS分片失败容忍度(30%)

#### 3.2.2. 存储路径与命名规范
- **基础路径**: `/media/video_{video_id}/`
- **HLS文件路径**: `/media/video_{video_id}/hls/`
- **文件命名格式**:
  - **m3u8文件**: `{原始文件名}` 或 `video_{video_id}_{operation_type}_{timestamp}.m3u8`
  - **ts目录**: 在HLS文件路径下新建 `ts/` 目录
  - **ts文件**: `segment_{index:06d}_{video_id}_{operation_type}_{timestamp}.ts`
- **时间戳格式**: `YYYYMMDDTHHMMSS`
- **操作类型**: `fetch`, `upload`, `transcode` 等

#### 3.2.3. 数据记录
1. **下载成功**:
   - 将视频信息写入 `downloaded_videos` 表
   - 状态设置为 `completed`
   - 记录存储路径、文件大小等信息
   
2. **部分成功**:
   - 将视频信息写入 `downloaded_videos` 表
   - 状态设置为 `partial_completed`
   - 将失败的ts分片记录到 `download_failures` 表

3. **下载失败**:
   - 将失败信息写入 `download_failures` 表
   - 记录失败的资源URL、错误类型、错误信息

### 3.3. MP4视频文件下载功能需求

#### 3.3.1. 下载功能
- 支持直接下载MP4文件
- 支持下载失败重试(最多重试3次)
- 支持下载进度实时更新
- 支持并发下载控制

#### 3.3.2. 存储路径与命名规范
- **基础路径**: `/media/video_{video_id}/`
- **MP4文件路径**: `/media/video_{video_id}/mp4/`
- **文件命名格式**: `video_{video_id}_{operation_type}_{timestamp}.mp4`

#### 3.3.3. 数据记录
- 下载成功: 写入 `downloaded_videos` 表,状态为 `completed`
- 下载失败: 写入 `download_failures` 表,记录错误信息

### 3.4. 图片资源下载功能需求
- **功能**: 支持下载封面图和其他图片资源,支持失败重试
- **存储目录**: `/media/video_{video_id}/image/`
- **命名格式**: `cover_{video_id}_{operation_type}_{timestamp}.{ext}`
- **数据记录**: 与MP4下载类似,成功写入 `downloaded_videos` 表,失败写入 `download_failures` 表

### 3.5. 统一存储目录结构规范
- **Video ID 命名规范**:
  - **格式**: UUID格式
  - **示例**: `8723901837-f22d-41d4-a716-446655440001`
- **目录结构示例**:
  ```bash
  /media/video_8723901837-f22d-41d4-a716-446655440001/

  ├── mp4/
  │   └── video_8723901837-f22d-41d4-a716-446655440001_fetch_20250614T153000.mp4
  ├── hls/
  │   ├── index.m3u8
  │   └── ts/
  │       ├── segment_000000_8723901837-f22d-41d4-a716-446655440001_fetch_20250614T154501.ts
  │       ├── segment_000001_8723901837-f22d-41d4-a716-446655440001_fetch_20250614T154502.ts

### 3.6. 任务与状态管理

#### 3.6.1. 任务管理
- 下载任务管理
- 资源存储管理
- 失败任务重试
- 下载状态检查
- 失败记录管理

#### 3.6.2. 状态管理(TaskStatus枚举)
- `pending`: 等待下载
- `processing`: 下载中
- `completed`: 完全成功
- `partial_completed`: 部分成功(HLS分片失败率≤30%)
- `failed`: 失败
- `cancelled`: 已取消

### 3.7. 失败处理与并发控制

#### 3.7.1. 失败类型(FailureType枚举)
- `network_error`: 网络错误
- `timeout`: 超时错误
- `invalid_content`: 内容无效
- `storage_error`: 存储错误
- `permission_error`: 权限错误

#### 3.7.2. 失败记录状态(FailureStatusEnum)
- `pending`: 等待重试
- `retrying`: 重试中
- `abandoned`: 已放弃(重试次数超限或手动放弃)

#### 3.7.3. 重试策略
- **最大重试次数**: 3次
- **HLS分片失败容忍度**: 30%
- **自动放弃**: `retry_count >= 3` 时,自动将 `status` 改为 `abandoned`

#### 3.7.4. 并发控制
- **全局限制**:
  - **最大并发下载任务**: 100
  - **任务队列容量**: 1000
- **单任务限制**:
  - **最大并发下载数**: 20(HLS分片)
- **超时设置**:
  - **单个请求超时**: 30秒

## 四、API端点实现规范

### 4.1. 通用要求

#### 4.1.1. 基础要求
- 必须正确调用 `app/services/download_service.py` 中的对应函数
- 需严格遵守 **二、实现规范** 中的所有规范（特别是 **2.1.4、2.3** 节）

- 在业务逻辑中使用 `current_user["user_id"]` 进行用户数据隔离

#### 4.1.2. RESTful 设计规范
**🌐 所有接口必须遵循 RESTful 设计风格**：

1. **HTTP 方法使用规范**：
   - `GET`：查询资源（列表、详情）
   - `POST`：创建资源
   - `PUT`：完整更新资源
   - `PATCH`：部分更新资源
   - `DELETE`：删除资源

2. **URL 路径规范**：
   - 使用名词复数形式：`/tasks` 而非 `/task`
   - 使用嵌套路径表示资源关系：`/tasks/{task_id}/failures`
   - URL 中不包含动词，动作通过 HTTP 方法表达
   - 使用连字符 `-` 而非下划线 `_`：`/download-tasks` 而非 `/download_tasks`（如适用）

3. **状态码使用规范**：
   - `200 OK`：成功查询
   - `201 Created`：成功创建资源
   - `204 No Content`：成功删除资源（无返回内容）
   - `400 Bad Request`：客户端请求错误（参数验证失败等）
   - `401 Unauthorized`：未认证
   - `403 Forbidden`：无权限
   - `404 Not Found`：资源不存在
   - `409 Conflict`：资源冲突
   - `413 Payload Too Large`：请求体过大
   - `500 Internal Server Error`：服务器内部错误

4. **统一响应结构**：
   - 通过 `create_response()` / `create_error_response()` 确保响应格式一致
   - 包含 `code`、`message`、`data`、`timestamp` 字段

5. **API版本管理**：
   - 所有接口路径包含版本号：`/api/v1/download/tasks`

        )
        
    except TaskNotFoundError as e:
        # 6. ❌ 【必须】使用 JSONResponse + create_error_response 返回错误
        logger.warning(
            f"资源不存在 - 用户ID: {user_id_for_logging}, "
            f"任务ID: {task_id_for_logging}"
        )
        return JSONResponse(
            status_code=404,
            content=create_error_response(code=404, message="任务不存在")
        )
        
    except ValueError as e:
        logger.warning(
            f"参数错误 - 用户ID: {user_id_for_logging}, 错误: {str(e)}"
        )
        return JSONResponse(
            status_code=400,
            content=create_error_response(code=1001, message=str(e))
        )
        
    except SQLAlchemyError as e:
        logger.error(
            f"数据库错误 - 用户ID: {user_id_for_logging}, "
            f"任务ID: {task_id_for_logging}, 错误: {str(e)}",
            exc_info=True
        )
        db.rollback()
        return JSONResponse(
            status_code=500,
            content=create_error_response(code=1002, message="数据库操作失败")
        )
        
    except Exception as e:
        logger.error(
            f"未知错误 - 用户ID: {user_id_for_logging}, "
            f"任务ID: {task_id_for_logging}, "
            f"错误类型: {type(e).__name__}, 错误: {str(e)}",
            exc_info=True
        )
        return JSONResponse(
            status_code=500,
            content=create_error_response(code=1000, message="服务器内部错误")
        )
```

#### 4.2.6 启动下载任务
- **接口**: `POST /api/v1/download/tasks/{task_id}/start`
- **认证**: 需要JWT Token
- **描述**: 明确地开始一个pending状态的任务,将其交给后台工作队列执行
- **业务逻辑**:
  - 验证任务是否属于当前用户
  - 检查任务状态必须是 `pending`, `failed`, 或 `partial_completed`
  - **【关键】更新任务状态为`processing`（必须包含异常保护）**:
    * 包裹在try-except块中
    * 设置`task.status = TaskStatus.PROCESSING`
    * 设置`task.updated_at = datetime.utcnow()`
    * 执行`db.commit()`
    * 执行`db.refresh(task)`
    * 如果捕获`SQLAlchemyError`：记录错误日志，执行`db.rollback()`，抛出`DatabaseError`
  - **【新增】视频去重检查**（包含完整异常处理）:
    * **try块**: 
      - 查询`downloaded_videos`表中是否存在`video_url == task.resource_url`且`status IN ('completed', 'partial_completed')`的记录
      - 如果找到已完成或部分完成的视频:
        * 记录去重命中日志（包含任务ID、resource_url、已存在视频ID、已存在视频状态等信息）
        * 根据已存在视频的状态设置任务状态:
          - existing_video.status='completed': 任务标记为`completed`（`progress=1.0`）
          - existing_video.status='partial_completed': 任务标记为`partial_completed`（progress保持原有值）
        * 设置`completed_at`为当前时间
        * 创建新的`downloaded_video`记录关联到当前任务（`task_id=task.id`），复用已存在视频的`storage_path`、`file_size`、`status`等字段
        * **字段处理注意**: `liveroom_title`需使用`str()`转换，`liveroom_url`使用`task.resource_url`，`status`使用`existing_video.status`
        * 提交事务并返回任务（跳过后续下载流程）
        * 记录完成日志（包含最终状态和视频状态）
    * **except SQLAlchemyError**: 捕获数据库异常，记录警告日志，执行rollback和refresh，继续正常下载流程
    * **except Exception**: 捕获其他异常，记录错误日志（含堆栈），执行rollback和refresh，继续正常下载流程
    * **关键**: 任何去重检查异常都不应中断下载流程，而应降级为正常下载
    * 如果未找到或找到的视频状态是`failed`，继续正常下载流程
  - **【关键】下载执行（必须包含异常保护）**:
    * 整个下载执行包裹在try-except-finally块中
    * 根据`resource_type`调用相应的下载方法:
      - `hls`: 调用`download_m3u8()`
      - `mp4`: 调用`download_mp4_image()`
      - `image`: 调用`download_mp4_image()`
    * 调用结果处理方法（必须有外层异常保护）:
      - `_process_download_m3u8_result()` - 需要有自己的try-except和rollback
      - `_process_download_mp4_result()` - 需要有自己的try-except和rollback
      - `_process_download_image_result()` - 需要有自己的try-except和rollback
    * **except块**（捕获所有下载和处理异常）:
      - 记录错误日志（包含完整堆栈）
      - 执行`db.rollback()`回滚可能的部分更改
      - 执行`db.refresh(task)`重新加载任务对象
      - 设置`task.status = TaskStatus.FAILED`
      - 设置`task.last_error = str(e)`
      - 设置`task.updated_at = datetime.utcnow()`
      - 尝试创建失败记录（嵌套try-except，避免失败记录创建失败导致整体失败）
    * **finally块**:
      - 无论成功或失败，执行`db.commit()`提交最终状态
      - 执行`db.refresh(task)`刷新任务对象
- **性能优化**: 建议为`downloaded_videos`表的`(video_url, status)`创建组合索引

#### 4.2.7 重试下载任务
- **接口**: `POST /api/v1/download/tasks/{task_id}/retry`
- **认证**: 需要JWT Token
- **描述**: 重试失败或部分完成的下载任务
- **业务逻辑**（整个函数必须包裹在try-except块中）:
  - **try块**:
    * 验证任务状态必须是 `failed` 或 `partial_completed`
    * 检查 `retry_count` 是否超过最大重试次数(3次)，超过抛出`ValueError`
    * 查询所有`status='pending'`的失败记录
    * **智能重试策略**:
      - 如果存在m3u8/mp4/image级别的失败: 清空失败记录（commit），调用`start_download_task()`全量重新下载
      - 如果仅存在ts分片级别的失败: 调用`_retry_only_failed_segments()`仅重试失败分片
    * 更新 `retry_count += 1`
    * 根据重试结果更新任务状态
    * 执行多个commit操作（每个都需要在安全的上下文中）
  - **except ValueError**（业务逻辑异常，如重试次数超限）:
    * 记录日志
    * 直接重新抛出（不需要rollback）
  - **except SQLAlchemyError**（数据库异常）:
    * 记录错误日志（包含任务ID、错误信息、完整堆栈）
    * 执行`db.rollback()`
    * 抛出`DatabaseError`
  - **except Exception**（其他未预期异常）:
    * 记录错误日志（包含任务ID、错误类型、错误信息、完整堆栈）
    * 执行`db.rollback()`
    * 重新抛出异常

#### 4.2.8 批量导入下载任务（CSV）

  * **逐行处理**（关键：单行错误不中断整体流程）:
    - 每行数据独立在try-except块中处理
    - 验证失败时记录错误信息并使用`continue`跳过该行
    - 如果`skip_duplicates=true`，检查是否存在相同的任务组合（resource_url + liveroom_id + liveroom_title），存在则跳过
    - 创建任务成功后，如果`auto_start=true`则自动启动任务
    - 每100行提交一次事务优化性能
  * 返回详细的导入结果：总数、成功数、失败数、跳过数、失败行详情
  * 根据结果返回不同状态码：
    - 全部成功: 201
    - 部分成功: 207 (Multi-Status)
    - 全部失败: 400

#### 6.2.6 结果处理方法异常处理要求
**所有`_process_download_*_result`方法必须遵循以下异常处理规范**:
- **外层try-except块**: 包裹整个方法的逻辑
- **try块**: 执行所有业务逻辑（包括已有的内部try-except块）
- **except SQLAlchemyError块**:
  * 记录错误日志: "处理{资源类型}下载结果时数据库错误 - 任务ID: {task.id}, 错误: {str(e)}"，包含完整堆栈
  * 执行`self.db.rollback()`
  * 设置`task.status = TaskStatus.FAILED`
  * 设置`task.last_error = f"处理下载结果失败: {str(e)}"`
  * 重新抛出异常（让调用者知道失败）
- **except Exception块**:
  * 记录错误日志: "处理{资源类型}下载结果时发生错误 - 任务ID: {task.id}, 错误类型: {type(e).__name__}, 错误: {str(e)}"，包含完整堆栈
  * 执行`self.db.rollback()`
  * 设置`task.status = TaskStatus.FAILED`
  * 设置`task.last_error = f"处理失败: {str(e)}"`
  * 重新抛出异常
- **重要说明**: 这些方法不执行commit，由调用者的finally块统一commit，但必须在异常时rollback确保session清洁

## 九、重要业务规则

### 9.1. 任务状态转换规则
1. **创建任务**: 状态初始化为 `pending`
2. **启动任务**: `pending` → `processing`
3. **下载完成**:
   - 全部成功: `processing` → `completed`
   - 少量失败(失败率≤30%): `processing` → `partial_completed`
   - 大量失败(失败率>30%): `processing` → `failed`
4. **重试任务**:
   - M3U8级别失败: 全量重新下载
   - TS级别失败: 仅重试失败分片
   - 重试成功: `failed/partial_completed` → `completed`
5. **删除任务**: 仅允许删除非 `completed` 状态的任务

### 9.2. 失败记录处理规则
1. **失败记录创建**: 下载失败时自动创建
2. **重试次数限制**: 最多重试3次
3. **自动放弃**: `retry_count >= 3` 时,自动将 `status` 改为 `abandoned`
4. **手动放弃**: 用户可主动放弃失败记录
5. **失败容忍度**: HLS下载中,ts分片失败率≤30%视为可接受

### 9.3. 并发控制规则
1. **全局并发限制**: 最大100个下载任务同时执行
2. **单任务并发**: 最大20个分片同时下载
3. **超时设置**: 单个请求超时30秒

### 9.4. 权限验证规则
1. **所有接口**: 需要用户认证
2. **任务操作**: 仅允许操作自己的任务
3. **失败记录操作**: 仅允许操作自己任务下的失败记录
4. **视频查询**: 仅允许查询自己下载的视频
