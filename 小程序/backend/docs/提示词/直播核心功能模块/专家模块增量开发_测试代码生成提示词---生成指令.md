## 一、目的

本元提示词用于**两阶段测试生成流程**的**第一阶段（规划师）**：

1. **本阶段目标**：根据增量设计文档、CRUD/Service/API 增量提示词，以及既有测试提示词参考，生成一份**模块特定的《专家模块增量开发_测试代码生成提示词.md》**。
2. **第二阶段目标**：使用生成的提示词文档，AI 作为「执行者」生成实际的 `.py` 测试代码。
3. **核心价值**：确保生成的测试提示词文档满足测试母版的所有测试哲学、测试策略、测试规范、测试流程和测试标准，且**不猜测任何字段/函数**，通过**动态读取**构建充足上下文。

## 五、测试规范与标准（必须继承到生成的文档中）

生成的《专家模块增量开发_测试代码生成提示词.md》**必须**明确要求执行者遵循以下规范，并在 Section 2-5 中完整继承测试母版内容：

### 5.1 增量测试模式

- **测试模式**：明确标注为**增量测试生成模式**
- **最小幅度修改**：
  - ✅ 只追加新测试函数，不修改、不删除、不重命名已存在的测试函数
  - ✅ 不修改已有测试文件中的任何已有内容
- **conftest.py 约束**：
  - **优先不修改**：尽量复用现有 Fixture，仅在确有需要且无冲突时新增
  - 若必须新增 Fixture：仅允许**添加**新 Fixture、函数、变量、导入
  - ❌ 严禁修改、删除、重命名已有 Fixture、函数、变量
  - ✅ 新增前必须做冲突检查（命名、功能重复）
  - 若存在命名冲突或功能重复：应在**测试文件内部**定义新 Fixture，**避免修改 conftest.py**

### 5.2 增量数据库验证

- **原则**：数据库可能已有数据，**必须**使用增量判断方式验证，不得基于「总数」断言
- **正确做法**：
  - 创建测试：记录测试前 count/ids 基线，执行操作后断言 count 增加 1 或新记录 ID 在结果中
  - 删除测试：记录测试前 count，执行后断言 count 减少 1
  - 列表查询：记录测试前 ID 集合，创建新数据后断言新 ID 出现在结果中

### 5.3 随机 ID 与唯一性

- **唯一字段**：`name`、`user_id`、`(user_id, expert_id)` 等唯一约束字段，**必须**使用 Faker 或 `uuid.uuid4().hex[:8]` 等生成唯一值
- **外键字段**：**禁止**使用 `uuid.uuid4()` 作为外键值，必须先创建父对象，再使用其 ID
- **JWT/认证**：`user_id` 必须从 Token 解析，不得用随机 UUID 替代（除非明确测试「用户隔离」）

### 5.4 事务与隔离

- **默认**：测试函数中**不要**调用 `await db.commit()`，依赖 `db_session` fixture 的自动 rollback
- **例外**：仅当测试唯一性约束冲突、级联删除/外键约束时，可调用 commit

### 5.5 其他强制规范

- **函数式测试**：禁止类式测试（`class TestXXX:`）
- **async for 解包**：`db_session`、`async_client` 等 async generator fixture 必须使用 `async for x in fixture:` 解包
- **Service 层 Mock**：`db` 必须使用 `AsyncMock()`，CRUD 使用 `new_callable=AsyncMock`
- **外键自检**：生成后须检查 Arrange 中是否为每个外键显式创建了父对象

### 5.5.1 Service 层方法签名与 Mock 完整性（必须写入生成的文档）

生成的《专家模块增量开发_测试代码生成提示词.md》**必须**要求执行者遵守以下约定，避免签名不一致、可见性字段错误、await Mock 等错误：

- **方法签名从源码读取**：生成 Service 层测试前，**必须**从 `app/services/expert_service.py` 读取被测方法的**完整签名**（如 `_check_user_resource_permission(self, resource_owner_id, current_user_id, role)` 为三参），**禁止**仅凭方法名或旧用例推断；测试调用须与源码一致（如三参须传 `user_id, user_id, role`）。
- **调用链上的 CRUD 均须 Mock**：`check_is_followed` 先调用 `get_expert` 再 `get_subscription`，**必须同时 mock** `get_expert` 与 `get_subscription`，避免真实 CRUD 对 Mock 的 `db` 执行 `await` 导致 TypeError。
- **软删除/可见性以设计为准**：专家模块软删除为 **is_active=False**，可见性判定用 is_active；构造「已下架」须用 `create_mock_expert(is_active=False)`，断言软删除后须断言 `db_expert.is_active is False`，**禁止**沿用 is_featured。
