2. **🚨 [最高优先级] 测试事务管理与数据隔离**：

**核心原则：依赖fixture的自动rollback，不要在测试函数中commit**

**⚠️ 关键规则**：测试函数本身**严禁调用 `await db.commit()`**（除非是测试commit行为本身，如唯一性约束测试）

**为什么不应该在测试中commit？**
1. `conftest.py` 中的 `db_session` fixture 设计为在测试结束时自动 `rollback()`
2. 如果测试中调用了 `commit()`，数据会被真正写入数据库
3. fixture的 `rollback()` 无法回滚已提交的数据
4. 这会导致测试数据残留，破坏测试隔离

**正确的模式：**

```python
# ✅ 正确：CRUD层测试 - 不需要commit
@pytest.mark.asyncio
async def test_create_favorite(db_session):
    async for db in db_session:
        # 创建数据
        favorite = await crud_user_behavior.create_favorite(db, user_id, room_id)
        
        # CRUD函数内部会调用flush()，足以让数据对当前会话可见
        # 不需要commit，也能验证数据
        assert favorite.id is not None
        
        # 验证数据库记录（flush后即可查询）
        result = await db.execute(select(UserFavorite).where(UserFavorite.id == favorite.id))
        db_favorite = result.scalar_one_or_none()
        assert db_favorite is not None
        
        break  # 退出循环，触发fixture的自动rollback，清理测试数据

# ❌ 错误：调用commit导致测试隔离失败
@pytest.mark.asyncio
async def test_create_favorite_wrong(db_session):
    async for db in db_session:
        favorite = await crud_user_behavior.create_favorite(db, user_id, room_id)
        await db.commit()  # ❌ 数据被真正提交，无法回滚！
        break
```

**唯一可以使用commit的场景：**

1. **测试唯一性约束冲突**：
```python
# ✅ 正确：测试唯一性约束需要commit第一条数据
async def test_create_favorite_duplicate(db_session):
    async for db in db_session:
        # 第一条数据：commit以触发约束
        favorite1 = await crud_user_behavior.create_favorite(db, user_id, room_id)
        await db.commit()  # ✅ 必须commit，否则唯一性约束不生效
        
        # 第二条数据：期望违反唯一性约束
        with pytest.raises(DatabaseIntegrityException):
            favorite2 = await crud_user_behavior.create_favorite(db, user_id, room_id)
            await db.flush()  # flush即可触发IntegrityError
        break
```

2. **测试级联删除或外键约束**：

# ✅ 正确：测试级联删除需要commit父记录

**辅助函数的特殊处理：**

辅助函数（如 `create_test_room`）如果被多个测试复用，**可以**在内部commit：

```python
# ✅ 辅助函数可以commit（但要谨慎使用）
async def create_test_room(db: AsyncSession, **kwargs) -> LiveRoom:
    """创建测试房间的辅助函数"""
    room = LiveRoom(
        id=uuid.uuid4(),
        user_id=kwargs.get("user_id", uuid.uuid4()),
        title=f"测试房间_{uuid.uuid4().hex[:8]}",
        stream_key=f"stream_{uuid.uuid4().hex[:12]}",
        **kwargs
    )
    db.add(room)
    await db.flush()
    await db.commit()  # ✅ 辅助函数可以commit
    await db.refresh(room)
    return room

# 测试函数使用辅助函数（但不再commit）
async def test_get_favorite(db_session):
    async for db in db_session:
        room = await create_test_room(db)  # 辅助函数已commit
        
        # 直接验证，不需要再commit
        favorite = await crud_user_behavior.create_favorite(db, user_id, room.id)
        assert favorite.room_id == room.id
        break  # fixture的rollback会清理辅助函数创建的数据
```

**简化版 commit() 使用规则（总结）：**
- **默认规则**：测试函数中**不要**调用 `await db.commit()`，依赖 `db_session` fixture 的自动 `rollback()` 做测试隔离。
- **仅允许的三种场景**：
  1. 测试唯一性约束：需要 `commit` 第一条记录才能触发数据库唯一约束。
  2. 测试级联删除 / 外键约束：需要将父/子记录真正持久化后再验证删除行为。
  3. API测试中创建父对象：为了确保API调用时数据可见，可以commit父对象（但子对象不需要commit）。
- **生成后自检建议**：
  - [ ] 每个 `commit()` 调用旁边都有注释说明属于哪一种场景。
  - [ ] 普通 CRUD 测试（增删改查）中不存在"无理由"的 `commit()` 调用。

3. **🚨 [关键] 数据唯一性约束规范（避免测试间冲突）**：

**问题场景**：
- 在增量测试模式下，`db_session` fixture 只执行 rollback，不会清空已插入的数据
- 多个测试使用相同的唯一字段值导致唯一约束冲突
- 错误信息：`IntegrityError: 重复键违反唯一约束"uq_user_favorites_user_room"` 或 `"uq_user_subscriptions_user_target"`

**禁止行为**：
- ❌ **严禁**使用硬编码的唯一字段值（如 `room_id=uuid.UUID("12345678-1234-1234-1234-123456789012")`）
- ❌ **严禁**在多个测试中重复使用相同的唯一字段值
- ❌ **严禁**假设唯一字段值在测试间不会冲突

**正确做法**：
```python
# ✅ 正确：使用动态生成的唯一值
import uuid
from faker import Faker

fake = Faker()

@pytest.mark.asyncio
async def test_create_favorite(db_session):
    async for db in db_session:
        user_id = uuid.uuid4()  # ✅ 每次测试都生成新的UUID
        room = LiveRoom(
            id=uuid.uuid4(),  # ✅ 每次测试都生成新的UUID
            user_id=user_id,
            title=f"测试房间_{uuid.uuid4().hex[:8]}",  # ✅ 使用UUID生成唯一标题
            stream_key=f"stream_{uuid.uuid4().hex[:12]}",  # ✅ 使用UUID生成唯一stream_key
        )
        db.add(room)
        await db.flush()
        
        favorite = await crud_user_behavior.create_favorite(db, user_id, room.id)
        assert favorite.id is not None
        break

# ✅ 正确：使用Faker生成唯一值（适用于字符串字段）
@pytest.mark.asyncio
async def test_create_subscription(db_session):
    async for db in db_session:
        user_id = uuid.uuid4()
        room = LiveRoom(
            id=uuid.uuid4(),
            user_id=user_id,
            title=fake.company(),  # ✅ 使用Faker生成唯一标题
            stream_key=f"stream_{uuid.uuid4().hex[:12]}",
        )
        db.add(room)
        await db.flush()
        
        sub = await crud_user_behavior.create_subscription(
            db,
            user_id=user_id,
            target_type=SubscriptionTargetType.ROOM,
            target_id=room.id,
        )
        assert sub.id is not None
        break
```

**通用原则**：
- **必须**识别所有 `unique=True` 的字段（通过读取Model定义）
  - `UserFavorite`: `(user_id, room_id)` 唯一约束
  - `UserSubscription`: `(user_id, target_id, target_type)` 唯一约束
- **必须**为唯一字段生成唯一值（推荐：UUID或Faker）
- **必须**在增量测试模式下特别关注唯一性（因为数据不会自动清空）
- **推荐**使用UUID后缀（`f"{base_name}_{uuid.uuid4().hex[:8]}"`）作为通用方案
- **必须**导入 `Faker` 和 `uuid`（如果使用）

**增量测试模式特殊说明**：
- 在增量测试模式下，`db_session` fixture 只执行 rollback，不会清空数据
- 这意味着前一个测试插入的数据可能仍然存在于数据库中
- **必须**为所有唯一字段生成唯一值，避免与已有数据冲突

**🚨 [关键] API 层测试的用户身份一致性规范**：
- **问题场景**：测试中创建数据时使用随机 UUID（如 `user_id_from_token = uuid.uuid4()`），但 API 请求时使用 JWT token 中的真实 user_id，导致两个 ID 不匹配，查询返回 0 条记录。
- **禁止行为**：
  - ❌ **严禁**在 API 层测试中使用 `user_id_from_token = uuid.uuid4()` 创建数据
  - ❌ **严禁**将 UUID 对象用作 JWT token
  - ❌ **严禁**使用不稳定的 JWT 解析方式
- **正确做法**：
  - ✅ **从 JWT token 解析真实 user_id**（用于创建数据）：
    ```python
    import jwt
    from app.core.config import settings
    
    # 从 JWT token 解析 user_id
    payload = jwt.decode(regular_user_token, settings.JWT_SECRET_KEY, algorithms=["HS256"])
    user_id_from_token = payload.get("user_id")
    user_id_from_token = uuid.UUID(user_id_from_token) if isinstance(user_id_from_token, str) else user_id_from_token
    ```
  - ✅ **在 headers 中使用原始 JWT token**（用于 API 请求）：
    ```python
    headers = {"Authorization": f"Bearer {regular_user_token}"}
    ```
  - ✅ **确保测试场景一致性**：创建数据时使用的 `user_id` 和请求数据时使用的 `user_id` 必须是同一个（都来自 JWT token）
- **关键原则**：
  - 创建数据：从 JWT token 解析真实 `user_id`
  - API 请求：使用原始 JWT token 字符串
  - 避免随机：不要使用 `uuid.uuid4()` 作为 `user_id`，除非测试明确需要验证用户隔离

**数据隔离与用户身份的一致性原则**：
- **场景区分**：数据库隔离规范和 API 层测试的用户身份一致性规范针对不同的使用场景
- **数据库隔离**：
  - **适用场景**：防止测试之间因违反数据库 `UNIQUE` 约束而产生冲突
  - **应用对象**：唯一性字段（如 `(user_id, room_id)` 组合、`(user_id, target_id, target_type)` 组合）
  - **随机生成**：**必须**使用 UUID 生成唯一值（如 `user_id = uuid.uuid4()`, `room_id = uuid.uuid4()`）
- **API 层测试的用户身份一致性**：
  - **适用场景**：API 层测试中，创建数据和请求数据必须使用同一个 `user_id`（都来自 JWT token）
  - **应用对象**：`user_id` 字段（用于创建测试数据）
  - **避免随机**：不要使用 `uuid.uuid4()` 作为 `user_id`，除非测试明确需要验证用户隔离
- **不冲突**：这两个规范**不冲突**，因为它们针对不同的字段和场景
  - 数据库隔离：唯一性字段组合**必须**随机生成（每次测试生成新的 `user_id` 和 `room_id`）
  - 用户身份一致性：`user_id` 字段**必须**从 JWT token 解析，不随机生成（但不同测试可以使用不同的 `regular_user_token`）

4. **外键与数据准备**：  
   - 创建 `user_favorites` 时，如需要依赖 `live_rooms`，必须先通过 Model 创建对应房间记录；  
   - 创建 `watch_history` 时，类似地先创建 `LiveSession`（及其依赖的 `LiveRoom`）；  
   - 创建 `user_subscriptions` 时，根据target_type创建对应的 `LiveRoom` 或 `LiveSession`；  
   - 不能直接使用不存在的 `uuid.uuid4()` 作为外键。
