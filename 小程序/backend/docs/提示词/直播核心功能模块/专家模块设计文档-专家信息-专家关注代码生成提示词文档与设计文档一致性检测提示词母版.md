## 3. 审计清单 (Audit Checklist) - (!!! 必须逐项检测 !!!)

### 3.1. 功能覆盖度 (Function Coverage)

* **检测点 1.1 (功能完整性)**：`Doc-Design` 中提及的所有功能点、API 接口、或业务逻辑（例如 `GET /api/v1/featured-experts`, `POST /api/v1/admin/experts`, `POST /api/v1/users/me/followed-experts`），是否都在 `Doc-CRUD` 或 `Doc-API` 中被**完整覆盖**？

* **检测点 1.2 (功能冗余)**：`Doc-CRUD` 或 `Doc-API` 中是否存在 `Doc-Design` **未提及**的"额外"功能或 API？

**专家模块特定检查项**：
- ✅ 专家信息管理功能（创建、更新、删除、获取详情、获取列表、获取推荐列表、设置推荐）
- ✅ 专家关注功能（关注、取消关注、获取关注列表、检查是否已关注）
- ✅ 场次专家关联功能（设置场次专家、获取场次专家列表）

---

### 3.2. 业务逻辑与执行流程 (Business Logic & Flow)

* **检测点 2.1 (步骤一致性)**：`Doc-API` 和 `Doc-CRUD` 中描述的函数执行流程（例如：1. 验证参数 -> 2. 调用 Service -> 3. Service 调用 CRUD -> 4. CRUD 操作数据库）是否与 `Doc-Design` 中描述的业务步骤**完全一致**？

* **检测点 2.2 (数据流转)**：`Doc-Design` 中描述的数据处理逻辑（例如："Service 层需要验证user_id是否已被绑定"，"CRUD 层负责软删除：设置is_featured=false"）是否在对应的文档中得到准确体现？

* **检测点 2.3 (事务边界)**：`Doc-Design` 中（明示或暗示）的事务处理范围（例如："创建专家和验证user_id必须是原子的"）是否在 `Doc-CRUD` 中被正确实现？

**专家模块特定检查项**：
- ✅ 创建专家流程：验证JWT Token -> 检查管理员权限 -> 验证user_id（如果提供）-> 检查user_id是否已被绑定 -> 创建专家记录
- ✅ 关注专家流程：验证JWT Token -> 检查专家是否存在 -> 检查是否已关注 -> 创建关注记录
- ✅ 获取关注列表流程：验证JWT Token -> 查询关注记录 -> 查询专家信息 -> 查询直播状态（如果include_live_status=true）
- ✅ 删除专家流程：软删除（设置is_featured=false）而非硬删除

---

### 3.3. 数据库规范 (Database Specifications)

* **检测点 3.1 (字段名称)**：`Doc-CRUD` 中提到的数据库 Model 字段名，是否与 `Doc-Design` 中的**字段名**（例如 `expert_id`, `user_id`, `is_featured`）完全一致？

* **检测点 3.2 (字段类型)**：`Doc-CRUD` 中提到的数据库 Model 字段类型（例如 `UUID`, `String(120)`, `Boolean`），是否与 `Doc-Design` 中的**类型定义**完全一致？

* **检测点 3.3 (字段约束)**：`Doc-CRUD` 中提到的约束（如 `nullable=False`, `unique=True`, `server_default`），是否与 `Doc-Design` 中的**约束要求**完全一致？

**专家模块特定检查项**：
- ✅ `experts` 表：`user_id` 具有 `UNIQUE` 约束
- ✅ `user_expert_subscriptions` 表：`UNIQUE(user_id, expert_id)` 约束
- ✅ `live_session_experts` 表：`UNIQUE(session_id, expert_id, role)` 约束
- ✅ 所有外键使用 `ON DELETE CASCADE`
- ✅ 时间戳字段使用 `TIMESTAMP(timezone=True)` 和 `server_default=func.now()`

### 3.4. API 结构规范 (API Structure)

* **检测点 4.1 (路由 URL)**：`Doc-API` 中的 API 路由（例如 `/api/v1/featured-experts`, `/api/v1/admin/experts`, `/api/v1/users/me/followed-experts`）是否与 `Doc-Design` **完全一致**？

* **检测点 4.2 (HTTP 方法)**：`Doc-API` 中的 HTTP 方法（`POST`, `GET`, `PATCH`, `DELETE`）是否与 `Doc-Design` **完全一致**？

* **检测点 4.3 (请求体 Schema)**：`Doc-API` 中的请求体（Request Body）结构、字段名、类型、是否必填，是否与 `Doc-Design` **完全一致**？

* **检测点 4.4 (查询参数)**：`Doc-API` 中的查询参数（Query Params）名称、类型、默认值，是否与 `Doc-Design` **完全一致**？

**专家模块特定检查项**：
- ✅ `GET /api/v1/featured-experts`：查询参数 `limit` (int, 可选, 默认10, 最大50)
- ✅ `GET /api/v1/experts/{expert_id}/sessions`：查询参数 `page`, `size`, `role`
- ✅ `POST /api/v1/admin/experts`：请求体使用 `ExpertCreate` Schema
- ✅ `PATCH /api/v1/admin/experts/{expert_id}`：请求体使用 `ExpertUpdate` Schema（部分更新）
- ✅ `POST /api/v1/users/me/followed-experts`：请求体包含 `expert_id`
- ✅ `GET /api/v1/users/me/followed-experts`：查询参数 `include_live_status` (bool, 可选, 默认true)

### 3.5. 响应与异常处理 (Response & Exception Handling)

* **检测点 5.1 (成功响应)**：`Doc-API` 中定义的**成功响应**结构、字段名、和 `success_response` 规范，是否与 `Doc-Design` **完全一致**？

* **检测点 5.2 (业务异常)**：`Doc-Design` 中提及的业务异常情况（例如"专家不存在"、"该用户已绑定到其他专家档案"、"您已关注该专家"），是否在 `Doc-API` 或 `Doc-Service` 中有**对应的异常抛出**（例如 `NotFoundException`, `InvalidParameterException`）？

* **检测点 5.3 (错误码 Code)**：`Doc-API` 中返回的错误码（Message Code，例如 `2001`, `2002`, `2004`, `4001`），是否与 `Doc-Design` 中定义的**消息码规范**完全一致？

* **检测点 5.4 (HTTP 状态码)**：`Doc-API` 中返回的 HTTP 状态码（`400`, `404`, `409`, `500`）是否与 `Doc-Design` 中定义的**完全一致**？

**专家模块特定检查项**：
- ✅ 成功响应：`{"code": 200, "message": "success", "data": {...}, "timestamp": "..."}`
- ✅ 错误响应：`{"code": 2001, "message": "资源不存在", "data": {...}, "timestamp": "..."}`
- ✅ 业务异常：`user_id已绑定` → `InvalidParameterException` (code=2004)
- ✅ 业务异常：`已关注该专家` → `InvalidParameterException` (code=2002)
- ✅ 业务异常：`专家不存在` → `NotFoundException` (code=2001)

### 3.6. 跨层规范 (Cross-Cutting Concerns)

* **检测点 6.1 (安全规范)**：`Doc-Design` 中提及的安全要求（例如："此接口需要管理员权限"、"需要登录"、"公开访问"）是否在 `Doc-API` 中得到体现（例如 `Depends(get_current_user)`, `Depends(get_current_user_optional)`）？

* **检测点 6.2 (日志规范)**：`Doc-Design` 中提及的日志记录点（例如："记录INFO日志：专家创建操作"）是否在对应的文档（`Doc-API` 或 `Doc-CRUD`）中有明确的日志记录指令？

* **检测点 6.3 (隐式规范)**：`Doc-Design` 中所有**隐式**的规范（例如，设计文档通篇使用 `expert_id` 而非 `id`，使用 `user_id` 而非 `user_public_id`），是否在 `Doc-CRUD` 和 `Doc-API` 中得到了**严格遵守**？

**专家模块特定检查项**：
- ✅ 管理员接口：`POST /api/v1/admin/experts`, `GET /api/v1/admin/experts`, `PATCH /api/v1/admin/experts/{expert_id}`, `DELETE /api/v1/admin/experts/{expert_id}` 需要 `ADMIN` 或 `SUPERADMIN` 权限
- ✅ 登录用户接口：`POST /api/v1/users/me/followed-experts`, `DELETE /api/v1/users/me/followed-experts/{expert_id}`, `GET /api/v1/users/me/followed-experts` 需要登录（Strict Auth）
- ✅ 公开接口：`GET /api/v1/featured-experts`, `GET /api/v1/experts/{expert_id}`, `GET /api/v1/experts/{expert_id}/sessions` 公开访问（Optional Auth）
- ✅ 日志记录：创建、更新、删除操作记录INFO日志，UUID脱敏（只记录前8位）
- ✅ 敏感字段：`contact_info` 不在公开API响应中暴露

### 3.7. API-Service对应关系检测 (API-Service Mapping Verification)

* **检测点 7.1 (API端点 → Service方法)**：`Doc-API` 中列出的所有API端点，是否都有对应的Service方法（在第5节"Service层代码生成"中）？**严重程度：严重**（如果API端点缺少对应的Service方法，会导致代码生成时违反架构要求，API层直接调用CRUD层）

* **检测点 7.2 (Service方法 → API端点)**：`Doc-API` 中列出的所有Service方法（排除权限守卫函数如`_check_*`和纯业务辅助方法），是否都有对应的API端点（在第6节"API层代码生成"中）？**严重程度：中等**（如果Service方法缺少对应的API端点，可能是多余代码或遗漏的API端点）

**对应关系规则**（用于判断是否对应）：
- `GET /api/v1/featured-experts` → `get_featured_experts(...) -> List[FeaturedExpertItem]`
- `GET /api/v1/experts/{expert_id}` → `get_expert_detail(...) -> ExpertItem`
- `GET /api/v1/experts/{expert_id}/sessions` → `get_expert_sessions(...) -> Dict[str, Any]`
- `POST /api/v1/admin/experts` → `create_expert(...) -> ExpertItem`
- `GET /api/v1/admin/experts` → `get_experts_list(...) -> Dict[str, Any]`
- `PATCH /api/v1/admin/experts/{expert_id}` → `update_expert(...) -> ExpertItem`
- `DELETE /api/v1/admin/experts/{expert_id}` → `delete_expert(...) -> Dict[str, Any]`
- `POST /api/v1/users/me/followed-experts` → `follow_expert(...) -> Dict[str, Any]`
- `DELETE /api/v1/users/me/followed-experts/{expert_id}` → `unfollow_expert(...) -> Dict[str, Any]`
- `GET /api/v1/users/me/followed-experts` → `get_followed_experts(...) -> List[FollowedExpertItem]`
- `GET /api/v1/experts/{expert_id}/is-followed` → `check_is_followed(...) -> Dict[str, bool]`
- `POST /api/v1/sessions/{session_id}/experts` → `set_session_experts(...) -> Dict[str, Any]`
- `GET /api/v1/sessions/{session_id}/experts` → `get_session_experts(...) -> List[SessionExpertItem]`

**专家模块特定检查项**：
- ✅ 所有13个API端点都必须有对应的Service方法
- ✅ 权限守卫函数（`_check_admin_permission`, `_check_write_permission`, `_check_expert_visibility`）不需要对应的API端点
- ✅ Service方法必须与API端点的业务逻辑完全对应
