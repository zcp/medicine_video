## 3. 核心改造原则（⚠️ 必须严格遵守）

### 3.1. 最小幅度修改原则

```
✅ 只增加：
  - 权限相关的依赖注入（get_current_user、get_current_user_optional）
  - 权限相关的参数（user_id、user_role、current_user_id、role）
  - 权限守卫函数调用
  - 权限异常捕获

✅ 只修改：
  - 方法签名（增加权限参数）
  - 方法调用（增加权限参数传递）

❌ 禁止：
  - 修改任何业务逻辑执行流程
  - 删除或重命名任何现有方法
  - 改变任何方法的返回值结构（除非提示词明确要求）
  - 重写任何已有业务逻辑代码
```

### 3.2. 职责分层原则

```
API 层 (Controller/Dependency)：
  - 仅负责 Authentication (认证) —— 解析"你是谁"（User 还是 Anonymous）
  - 不做任何权限判断
  - 提取 user_id 和 role，传递给 Service 层

Service 层 (Domain Logic)：
  - 全权负责 Authorization (鉴权) —— 判定"你能看吗/你能改吗"
  - 调用权限守卫函数
  - 决定是否允许访问
  - 传递权限参数给 CRUD 层

CRUD 层 (Repository)：
  - 负责 SQL 层面的权限过滤
  - 在 WHERE 条件中应用权限过滤
  - 禁止内存过滤（性能陷阱）
```

### 3.3. 向后兼容原则

```
- 所有权限相关的改动必须对现有调用方透明
- 新增的权限参数必须使用 Optional 类型或合适的默认值
- 响应结构保持不变（除非提示词明确要求新增字段）
```

def _check_expert_visibility(self, expert: Expert, user_id: Optional[UUID], user_role: Optional[str]) -> None:
    """检查专家可见性（404 伪装机制）"""
    from app.exceptions import PermissionDeniedException, NotFoundException
    
    if expert.is_active:
        # 公开专家，所有用户可见
        return
    
    # 私有专家，检查权限
    if user_id is None:
        # 匿名用户无权访问私有专家
        raise NotFoundException("Expert not found")
    
    if user_role in ["ADMIN", "SUPERADMIN"]:
        # 管理员可查看所有专家
        return

    if expert.created_by == user_id:
        return
    
    # 其他用户无权访问私有专家

def _check_write_permission(self, resource, user_id: UUID, user_role: str) -> None:

        return

    if hasattr(resource, "created_by") and resource.created_by == user_id:

## 6. 错误处理与回滚机制

### 6.1. 错误类型

**类型 1：更新前检查失败**
- 症状：代码文件不存在、接口/方法不完整、权限策略不明确
- 处理：停止执行，报告问题，等待用户确认

**类型 2：代码更新失败**
- 症状：无法找到正确的代码位置、无法正确更新代码
- 处理：停止执行，报告问题，等待用户确认

**类型 3：更新后检查失败**
- 症状：更新后检查清单中任何一个检查项未通过
- 处理：回滚当前层级/模块的更新，报告问题，等待用户确认

**类型 4：最终检查失败**
- 症状：最终检查清单中任何一个检查项未通过
- 处理：报告所有失败的检查项，提供详细的失败原因，等待用户确认

### 6.2. 回滚机制

**自动回滚**：
- 如果更新后检查失败，AI 自动回滚当前层级/模块的更新
- 回滚后，恢复到更新前的状态

**手动回滚**（可选）：
- 用户可以要求 AI 回滚任何已更新的模块
- AI 提供回滚命令和步骤
