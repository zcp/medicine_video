**🔴 JWT字段使用规范（重要说明）**：

本系统JWT Token的Payload结构：
```json
{
  "user_id": "UUID字符串",  // 用户的public_id（非JWT标准字段）
  "role": "REGULAR",         // 用户角色枚举值
  "type": "access",          // Token类型
  "exp": 1234567890,         // 过期时间
  "iat": 1234567890,         // 签发时间
  "jti": "UUID字符串"        // Token唯一ID
}
```

**与《用户模块设计文档》的映射关系**：

⚠️ **关键差异**：《用户模块设计文档》中的JSON示例使用了JWT标准字段`sub`，但本系统实际实现**统一使用`user_id`**。

| 概念 | JWT标准 | 用户模块文档示例 | 本系统实际使用 | 说明 |
|------|---------|----------------|--------------|------|
| 用户标识 | `sub` | `sub` | **`user_id`** | 存储users.public_id（UUID） |
| 用户角色 | 自定义 | `role` | **`role`** | 枚举值：REGULAR/MODERATOR/ADMIN/SUPERADMIN |

**设计决策说明**：
- 虽然JWT RFC 7519标准推荐使用`sub`字段存储用户标识，但本系统为保持代码**语义清晰**，统一使用`user_id`字段。
- 这是一个**有意识的设计决策**，已在《v6主文档》和本文档中统一执行。
- 已生成的所有代码都基于`user_id`字段实现，前后端均使用此约定。

**代码提取方式**：
```python
# ✅ 正确做法（与v6主文档一致）
user_id = UUID(current_user["user_id"])
role = current_user.get("role")

# ❌ 错误做法（不要使用JWT标准字段名）
# user_id = UUID(current_user["sub"])  # 系统中不存在此字段
```

## 1. 核心设计原则 (Core Principles)

本设计严格遵循以下五条原则，任何代码实现均不得违背：

1.  **Public 开放原则**：标记为公开（`is_private=false`）的资源，必须允许**匿名用户**访问，以支持 SEO、分享和传播。
2.  **Private 隐私原则**：标记为私有（`is_private=true`）的资源，仅 **创建者（user_id）** 和 **Admin** 可见。
      * *关键约束*：对于无权访问的 Private 资源，必须返回 **404 Not Found**，严禁返回 403，以防止恶意用户通过枚举 ID 探测资源的存在性。
      * *字段说明*：`user_id` 字段存储的是用户的 `public_id`（从JWT的`user_id`字段提取），创建者即为资源的Owner。
3.  **写操作严控原则**：所有 CUD（创建、修改、删除）及敏感信息读取（如推流码），必须**强制登录**（Strict Auth）。
4.  **管理员上帝视角**：Admin/SuperAdmin 角色拥有全系统的读写权限，不受资源 `is_private` 属性的限制。
5.  **职责分层原则（架构红线）**：
      * **API 层 (Controller/Dependency)**：仅负责 **Authentication (认证)** —— 解析"你是谁"（User 还是 Anonymous）。
      * **Service 层 (Domain Logic)**：全权负责 **Authorization (鉴权)** —— 判定"你能看吗/你能改吗"。
      * **CRUD 层 (Repository/Data Access)**：负责在 **SQL 层面应用权限过滤逻辑** —— 禁止内存过滤，业务筛选条件与权限过滤条件使用 AND 关系组合。

## 2. 身份模型与鉴权策略 (Identity & Strategy)

### 2.1 用户状态模型

系统基于《用户模块》的 JWT 体系，将请求上下文分为三类状态：

| 状态 | 判定条件 (API 层行为) | 权限基线 |
| :--- | :--- | :--- |
| **Anonymous (匿名)** | 请求头 **无 Token** 或 Token 为空 | 仅可读 `is_private=false` 的资源 |
| **Regular (普通用户)** | 携带有效 Token，Role=`REGULAR` | 可读 Public + 读写 Own 资源 |
| **Admin (管理员)** | 携带有效 Token，Role=`ADMIN/SUPERADMIN` | 全局读写，无视 Private 限制 |

### 2.2 双轨鉴权模式 (Dual Auth Patterns)

为了在不拆分接口的前提下支持匿名访问，API 层引入两种依赖注入模式：

#### 模式 A：Strict Auth (强制鉴权)

  * **行为**：
      * 无 Token → **401 Unauthorized**
      * Token 无效 → **401 Unauthorized**
  * **适用场景**：所有写操作、敏感读操作（推流码）。
  * **对应依赖**：`get_current_user` (v6 原有逻辑)。

#### 模式 B：Optional Auth (可选鉴权)

  * **行为**：
      * 无 Token → 返回 `None` (视为匿名用户)。
      * **Token 无效/过期** → **401 Unauthorized**。
      * *注意*：这里必须报错，**严禁**降级为匿名用户。否则已登录用户在 Token 过期时会莫名其妙看不到自己的私有房间，导致前端状态错乱。
  * **适用场景**：资源详情、列表查询、播放地址。
  * **对应依赖**：`get_current_user_optional` (新增逻辑)。

### 3.1 直播间模块 (Room Domain)

该模块负责处理直播间的元数据。核心字段为 `is_private` (BOOLEAN) 和 `user_id`（存储创建者的public_id）。

#### 接口 1: 创建直播间

  * **Path**: `POST /api/v1/rooms`
  * **Auth 策略**: **Strict** (强制登录)
  * **API 层依赖**: `current_user: Dict = Depends(get_current_user)`
  * **Service 方法签名**:
    ```python
    async def create_room(
        self,
        data: RoomCreate,
        user_id: UUID,
        role: str
    ) -> Room:
        """
        创建直播间
        
        Args:
            data: 创建直播间的数据
            user_id: 当前用户的public_id（从JWT的user_id字段提取）
            role: 当前用户的角色
            
        Returns:
            创建的直播间对象
        """
    ```
  * **权限逻辑**: 所有登录用户均可创建直播间，`room.user_id` 自动设置为 `user_id`（创建者即owner）
  * **实现要点**:
    1. 生成唯一的 `stream_key`
    2. 设置 `room.user_id = user_id`（创建者即owner）
    3. 设置 `is_private` 默认值（根据请求体或默认为false）
    4. 调用 CRUD 层创建记录

#### 接口 2: 获取直播间列表 (核心修改)

  * **Path**: `GET /api/v1/rooms`
  * **Auth 策略**: **Optional** (可选鉴权)
  * **API 层依赖**: `current_user: Optional[Dict] = Depends(get_current_user_optional)`
  * **Service 方法签名**:
    ```python
    async def list_rooms(
        self,
        pagination: PageParams,
        user_id: Optional[UUID] = None,
        role: Optional[str] = None
    ) -> Tuple[List[Room], int]:
        """
        获取直播间列表（支持匿名访问）
        
        Args:
            pagination: 分页参数
            user_id: 当前用户的public_id（匿名时为None）
            role: 当前用户的角色（匿名时为None）
            
        Returns:
            (直播间列表, 总数)
        """
    ```
  * **权限逻辑与 SQL 策略**:
      * **Admin**: `SELECT * FROM live_rooms ...` (无过滤)
      * **Regular User**: `SELECT * FROM live_rooms WHERE is_private=false OR user_id={user_id}`
      * **Anonymous**: `SELECT * FROM live_rooms WHERE is_private=false`
      * *注意*：必须在 Repository 层通过 SQL 过滤，禁止查出所有数据在内存过滤（性能陷阱）。
  * **实现要点**:
    1. API层提取：`user_id = UUID(current_user.get("user_id")) if current_user else None`
    2. API层提取：`role = current_user.get("role") if current_user else None`
    3. 调用Service层并传递这两个参数
    4. CRUD层根据role和user_id构建不同的WHERE条件
    5. （增量说明）对于管理后台的 `RoomList` 视图，前端可通过额外的 Query 参数（例如 `owner_only=true`）或等价约定，指示 Service 层仅返回当前登录用户创建的房间；在该模式下 Regular 用户只看到 Own 资源，而 Admin/SUPERADMIN 仍返回全部房间列表用于平台级运营。

#### 接口 3: 获取直播间详情 (核心修改)

  * **Path**: `GET /api/v1/rooms/{room_id}`
  * **Auth 策略**: **Optional** (可选鉴权)
  * **API 层依赖**: `current_user: Optional[Dict] = Depends(get_current_user_optional)`
  * **Service 方法签名**:
    ```python
    async def get_room_detail(
        self,
        room_id: UUID,
        user_id: Optional[UUID] = None,
        role: Optional[str] = None
    ) -> Room:
        """
        获取直播间详情（支持匿名访问）
        
        Args:
            room_id: 直播间ID
            user_id: 当前用户的public_id（匿名时为None）
            role: 当前用户的角色（匿名时为None）
            
        Returns:
            直播间对象（包含tabs字段）
            
        Raises:
            RoomNotFoundException: 房间不存在或无权访问（404）
        """
    ```
  * **权限逻辑流程**:
    1.  `room = await self.crud.get(room_id)`，若不存在抛 `RoomNotFoundException`
    2.  调用 `self._check_room_visibility(room, user_id, role)`
    3.  若检查不通过，**抛出 RoomNotFoundException (404)**（隐藏私有资源的存在性）
    4.  查询并附加 tabs 字段（关联查询 `live_room_tabs` 表）
    5.  返回数据（包含tabs字段）
  * **实现要点**: 见 4.2 节的 `_check_room_visibility` 守卫函数

#### 接口 4: 修改/更新直播间

  * **Path**: `PATCH /api/v1/rooms/{room_id}`
  * **Auth 策略**: **Strict** (强制登录)
  * **API 层依赖**: `current_user: Dict = Depends(get_current_user)`
  * **Service 方法签名**:
    ```python
    async def update_room(
        self,
        room_id: UUID,
        data: RoomUpdate,
        user_id: UUID,
        role: str
    ) -> Room:
        """
        更新直播间信息
        
        Args:
            room_id: 直播间ID
            data: 更新数据
            user_id: 当前用户的public_id（从JWT的user_id字段提取）
            role: 当前用户的角色

            更新后的直播间对象
    ```

    4. 如果正在直播，抛出 `ActionForbiddenException`
    5. 执行更新
  * **实现要点**: 见 4.2 节的 `_check_write_permission` 守卫函数

    ```python
    async def get_stream_key(
    ```

### 4.1 依赖注入实现 (app/api/deps.py)

```python
from fastapi import Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer
from typing import Optional, Dict
from uuid import UUID

# 配置 OAuth2PasswordBearer，auto_error=False 用于 Optional Auth
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token", auto_error=False)

# 1. 强制鉴权 (Strict) - 用于写操作
async def get_current_user(token: str = Depends(oauth2_scheme)) -> Dict:
    """
    强制鉴权依赖注入
    
    Returns:
        用户信息字典 {"user_id": str(UUID), "role": str, "username": str}
        
    Raises:
        HTTPException(401): Token缺失或无效
    """
    if not token:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Missing authentication credentials",
            headers={"WWW-Authenticate": "Bearer"},
        )
    
    user = verify_token_service(token)
    if not user:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Could not validate credentials",
            headers={"WWW-Authenticate": "Bearer"},
        )
    return user

# 2. 可选鉴权 (Optional) - 用于读操作
async def get_current_user_optional(
    token: Optional[str] = Depends(oauth2_scheme)
) -> Optional[Dict]:
    """
    可选鉴权依赖注入
    
    Returns:
        - None: 匿名用户（无Token）
        - Dict: 用户信息字典（有有效Token）
        
    Raises:
        HTTPException(401): Token无效或过期（但不能降级为匿名）
    """
    # 场景 A: 无 Token → 返回 None，视为匿名用户
    if not token:
        return None
    
    # 场景 B: 有 Token → 必须验证
    user = verify_token_service(token)
    if not user:
        # 场景 C: Token 过期/伪造 → 必须报错！
        # 严禁降级为匿名，否则已登录用户看不到自己的私有资源
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Invalid or expired token",
            headers={"WWW-Authenticate": "Bearer"},
        )
    return user

def verify_token_service(token: str) -> Optional[Dict]:
    """
    验证JWT Token并返回用户信息
    
    Returns:
        用户信息字典或None
        字典结构: {"user_id": str(UUID), "role": str, "username": str}
    
    Note:
        ✅ 与v6主文档保持一致，使用`user_id`字段存储用户的public_id
    """
    try:
        import jwt
        from app.core.config import settings
        
        payload = jwt.decode(
            token,
            settings.JWT_SECRET_KEY,
            algorithms=["HS256"]
        )
        
        # 检查Token类型
        if payload.get("type") != "access":
            return None
        
        # ✅ 提取用户信息（与v6主文档一致）
        user_info = {
            "user_id": payload.get("user_id"),  # 与v6主文档一致
            "role": payload.get("role", "REGULAR"),  # 默认为REGULAR
            "username": payload.get("username"),
        }
        
        # 验证必要字段
        if not user_info["user_id"]:
            return None
        
        return user_info
    except jwt.ExpiredSignatureError:
        return None
    except jwt.InvalidTokenError:
        return None
    except Exception:
        return None
```

### 4.3 Repository 层查询优化

**原则**：尽可能下推过滤逻辑到数据库，避免内存过滤。

```python
# app/repositories/room_repository.py
from typing import Optional, List, Tuple
from uuid import UUID
from sqlalchemy import select, or_, and_, func
from sqlalchemy.ext.asyncio import AsyncSession
from app.models.room import LiveRoom

class RoomRepository:
    """直播间数据访问层"""
    
    async def find_visible_rooms(
        self,
        session: AsyncSession,
        user_id: Optional[UUID],
        role: Optional[str],
        page: int,
        size: int
    ) -> Tuple[List[LiveRoom], int]:
        """
        查询可见的直播间列表（带权限过滤）
        
        Args:
            session: 数据库会话
            user_id: 当前用户的public_id（匿名时为None）
            role: 当前用户的角色（匿名时为None）
            page: 页码（从1开始）
            size: 每页大小
            
        Returns:
            (直播间列表, 总数)
        """
        # 构建基础查询
        stmt = select(LiveRoom)
        
        # 根据用户身份应用不同的WHERE条件
        if role in ['ADMIN', 'SUPERADMIN']:
            # 管理员：无过滤，看所有
            pass
        elif user_id:
            # 普通用户：Public OR Own
            stmt = stmt.where(
                or_(
                    LiveRoom.is_private == False,
                    LiveRoom.user_id == user_id
                )
            )
        else:
            # 匿名用户：Only Public
            stmt = stmt.where(LiveRoom.is_private == False)
        
        # 计算总数
        count_stmt = select(func.count()).select_from(stmt.subquery())
        total_result = await session.execute(count_stmt)
        total = total_result.scalar_one()
        
        # 应用分页和排序
        stmt = stmt.order_by(LiveRoom.created_at.desc())
        stmt = stmt.offset((page - 1) * size).limit(size)
        
        # 执行查询
        result = await session.execute(stmt)
        rooms = result.scalars().all()
        
        return list(rooms), total
```

## 5. 审计与安全补充 (Security & Audit)

### 5.1 安全机制

1.  **404 伪装机制**：
      * 在 Service 层，对于 `_check_room_visibility` 失败的情况，必须抛出 `NotFoundException`。
      * 原因：如果返回 403，攻击者可以通过遍历 ID，根据返回码（404 vs 403）判断哪些 ID 是真实存在的私密房间。

2.  **敏感操作审计**：
      * 以下操作建议记录审计日志（Audit Log）：
          * 管理员修改/删除非自己的房间
          * 管理员查看 Private 房间的详情
          * 任何用户请求获取 Stream Key
          * Admin 创建/修改/删除 Tab（跨房间操作）
          * 房间创建者管理自己房间的Tab（可选记录，用于内容管理审计）
          * 批量导入操作
          * Admin 查看任意用户的 Private 留言

3.  **缓存策略影响**：
      * Public 接口（匿名访问）非常适合 CDN 缓存或服务端缓存
      * Private 接口（带 Token）**严禁**被公共 CDN 缓存
      * 在实现 `GET /rooms/{id}` 时，需注意 `Vary: Authorization` 头的使用，或者在应用层区分缓存 Key

### 5.2 幂等性保证

根据文档 v6 的设计，批量导入和 Import Session 接口支持幂等性：

1. **Room 维度去重**（通过 `external_room_id`）：
   - 同一 `user_id` 下，相同 `external_room_id` 只创建一次
   - 唯一索引：`CREATE UNIQUE INDEX idx_rooms_user_external ON live_rooms(user_id, external_room_id) WHERE external_room_id IS NOT NULL`

2. **Session 维度去重**（通过 `playback_url_hash`）：
   - 同一 `room_id` 下，相同 `playback_url` 只创建一次
   - 规范化 URL：`strip()` 去除首尾空格
   - 计算哈希：`playback_url_hash = hashlib.sha256(normalized_url.encode('utf-8')).hexdigest()`
   - 唯一索引：`CREATE UNIQUE INDEX idx_sessions_room_url_hash ON live_sessions(room_id, playback_url_hash) WHERE playback_url_hash IS NOT NULL`

## 6. 完整接口权限矩阵（快速参考）

### 6.1 角色说明与MODERATOR处理策略

本系统定义四种用户角色（详见《用户模块设计文档》§4.2）：

| 角色 | 枚举值 | MVP阶段权限 | 第二阶段规划 |
|------|-------|-----------|------------|
| 普通用户 | `REGULAR` | ✅ 基础权限 | 不变 |
| 房管 | `MODERATOR` | ⚠️ **等同于REGULAR** | 特定房间管理权限（删除留言、禁言用户） |
| 管理员 | `ADMIN` | ✅ 平台管理权限 | 不变 |
| 超级管理员 | `SUPERADMIN` | ✅ 最高权限 | 不变 |

**MVP阶段MODERATOR处理原则**:

1. **代码实现策略**：使用"白名单管理员"模式
   ```python
   # ✅ 正确写法（MVP阶段）
   if role in ['ADMIN', 'SUPERADMIN']:
       # 管理员特权
   else:
       # 普通用户（自动包含REGULAR和MODERATOR）
   
   # ✅ 或使用排除法
   if role not in ['ADMIN', 'SUPERADMIN']:
       # 对非管理员的限制（自动包含REGULAR和MODERATOR）
   ```

2. **权限矩阵列说明**：
   - **匿名 (Anonymous)**: 未携带JWT Token的请求
   - **Regular**: 包括`REGULAR`和`MODERATOR`角色（MVP阶段等价）
   - **Admin**: 包括`ADMIN`和`SUPERADMIN`角色

3. **设计理念**：
   - **MVP阶段**：MODERATOR角色被保留但**暂不启用特殊权限**，其权限完全等同于REGULAR普通用户
   - **未来扩展**：第二阶段将启用MODERATOR的**房间级别**管理权限（如删除留言、禁言用户）
   - **Tab管理权限**：在MVP阶段，MODERATOR等同于REGULAR，可以管理自己创建的房间的Tab；但MODERATOR不应具备全局Tab管理权限（如管理所有房间的Tab）

4. **未来扩展路径示例**：
   ```python
   # 第二阶段：启用MODERATOR的留言管理权限
   if role in ['ADMIN', 'SUPERADMIN']:
       # 全局管理权限
   elif role == 'MODERATOR':
       # 检查是否是该房间的房管
       if await self._is_room_moderator(user_id, room_id):
           # 该房间的管理权限
   
   # Tab管理权限：创建者或Admin（v6.1.1更新）
   # 注意：MODERATOR在MVP阶段等同于REGULAR，可以管理自己创建的房间的Tab
   if role not in ['ADMIN', 'SUPERADMIN'] and room.user_id != user_id:
       raise PermissionDeniedException("您只能管理自己创建的房间的Tab配置")
   ```

## 7. 开发自检清单 (Development Checklist)

开发人员在实现每个接口时，请对照以下清单：

- [ ] **1. 确定Auth模式**: 该接口是Strict还是Optional？
- [ ] **2. API层依赖注入**: 使用`get_current_user`还是`get_current_user_optional`？
- [ ] **3. Service方法签名**: `user_id`和`role`参数类型是否正确（UUID/Optional[UUID]和str/Optional[str]）？
- [ ] **4. 权限守卫调用**: 是否调用了`_check_room_visibility`或`_check_write_permission`？
- [ ] **5. Admin特权处理**: Admin角色是否正确绕过了is_private限制？
- [ ] **6. 字段一致性**: 
  - [ ] 使用 `is_private` 布尔字段（而非 visibility 枚举）
  - [ ] 使用 `user_id` 存储 public_id（而非 owner_public_id）
  - [ ] JWT中使用 `user_id` 字段提取 public_id
- [ ] **7. 错误码正确性**: 
  - [ ] 无Token且需要Strict Auth → 401
  - [ ] Token无效 → 401
  - [ ] 权限不足（已登录但非Owner/Admin）→ 403
  - [ ] Private资源但无权访问 → 404（而非403）
- [ ] **8. 日志审计**: 敏感操作（如Admin查看Private资源）是否记录审计日志？
- [ ] **9. 单元测试**: 是否覆盖了以下场景？
  - [ ] 匿名访问Public资源 → 成功
  - [ ] 匿名访问Private资源 → 404
  - [ ] Owner访问自己的Private资源 → 成功

  - [ ] Admin访问任意Private资源 → 成功
  - [ ] Token过期访问 → 401
  - [ ] 写操作无Token → 401
  - [ ] 写操作非Owner/Admin → 403
