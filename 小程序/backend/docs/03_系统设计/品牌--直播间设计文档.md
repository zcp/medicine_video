# 1. 设计要点与约定

## 1.1 直播间—品牌（Brand_Rooms）增量目标

### 1.1.1 新增业务场景

新增“直播间—品牌”能力，用于在**直播间页（Room Page）**展示绑定品牌。

### 1.1.2 展示承载位置：直播间品牌 Tab ✅（明确写入）

**品牌将在直播间页的「品牌 Tab」中展示。**

* 直播间页面具备 Tab 结构（由 `live_room_tabs` 表配置）
* “品牌 Tab”是 Tab 的一种业务承载类型（UI表现为一个 Tab 标签：品牌）
* “品牌 Tab”展示内容来源为 `brand_rooms` 关联的 room 品牌列表

> 说明：直播间 Tab 配置能力由主文档定义（`live_room_tabs` 表），因此本增量只负责“品牌内容”与“绑定关系”，不修改 Tab 系统本身。

### 1.1.3 采用方案 A（推荐默认）：互不覆盖，分场景展示 ✅

**展示规则（强约束）：**

* **直播间页（room page）**：只展示 **room 品牌**（品牌 Tab）
* **专题页（topic page）**：只展示 **topic 品牌**（专题赞助/合作品牌区）
* **专题进入房间**：房间页仍展示 room 品牌，不随入口变化

**优点**：

* 最清晰、最少歧义
* 不会出现“同一直播间在不同专题入口品牌不一样”的混乱

**缺点（运营诉求）**：

* 运营有时希望“专题赞助品牌”在房间里也露出

---

## 1.2 不冲突原则（核心）

为了避免专题品牌覆盖房间品牌，本增量严格使用：

* **数据隔离**：Topic品牌与Room品牌使用不同关联表

  * topic：`brand_topics`
  * room：`brand_rooms`
* **展示隔离**：不同页面展示不同来源

  * room page → `brand_rooms`
  * topic page → `brand_topics`

---

## 1.3 软删除策略（对齐原文档）

* `brands`：软删除（is_active=false）
* `brand_topics`：硬删除关联记录
* `brand_rooms`：硬删除关联记录（新增表保持一致）

## 2.3 brand_rooms（品牌-直播间关联表）✅ 新增

**设计说明**：

* 直播间主表为 `live_rooms`（见 v6 主文档）
* 本表仅做多对多关联，不修改 `live_rooms` 结构
* 与 `brand_topics` 写法一致（复合主键 + 外键 + 索引 + created_at）

```sql
CREATE TABLE brand_rooms (
    brand_id UUID NOT NULL,
    room_id UUID NOT NULL,

    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (brand_id, room_id),

    CONSTRAINT fk_brand_rooms_brand_id
        FOREIGN KEY (brand_id) REFERENCES brands(id) ON DELETE CASCADE,

    CONSTRAINT fk_brand_rooms_room_id
        FOREIGN KEY (room_id) REFERENCES live_rooms(id) ON DELETE CASCADE
);

-- 索引
CREATE INDEX idx_brand_rooms_brand_id ON brand_rooms(brand_id);
CREATE INDEX idx_brand_rooms_room_id ON brand_rooms(room_id);

-- 注释
COMMENT ON TABLE brand_rooms IS '品牌与直播间的多对多关联表，用于直播间页品牌Tab展示 room 绑定品牌';
COMMENT ON COLUMN brand_rooms.brand_id IS '品牌ID，关联brands表';
COMMENT ON COLUMN brand_rooms.room_id IS '直播间ID，关联live_rooms表';
```

```python
from pydantic import BaseModel, Field, ConfigDict
import uuid

from typing import List, Optional

class BrandRoomBindIn(BaseModel):
```

## 5.3 运营诉求兼容（可选增强，不破坏方案 A）

> 目标：运营希望“专题赞助品牌”也在房间内露出
> 原则：不覆盖 room 品牌，只做“附加展示”，且默认关闭。

### 5.3.1 查询参数：include_topic_brands（默认 false）

**接口**：`GET /api/v1/rooms/{room_id}/brands`

新增 Query：

| 参数名                  | 类型   | 默认值   | 说明                                       |
| -------------------- | ---- | ----- | ---------------------------------------- |
| include_topic_brands | bool | false | 是否附加返回专题赞助品牌（不覆盖room品牌）                  |
| topic_id             | uuid | null  | 当 include_topic_brands=true 时必填，用于明确入口专题 |

当 `include_topic_brands=true`，返回结构为（推荐结构化分组）：

```json

  "code": 200,
  "message": "success",
```

**强约束**：

* room_brands 永远来自 brand_rooms
* topic_brands 永远来自 brand_topics（由 topic_id 指定）
* 前端需明确标识 “专题赞助”，避免认知为房间品牌变化

# 6. 执行流程详细说明（以绑定直播间品牌为例）

以 `POST /api/v1/admin/rooms/{room_id}/brands` 为例：

1. API层 Strict Auth 校验 JWT，提取 `user_id` 和 `role`
2. Service层执行 `_check_admin_permission(role)`，非管理员返回 `3002`
3. 校验 room_id 存在性，不存在返回 `2001`
4. 校验请求体 brand_ids：UUID格式合法、去重
5. 查询 brands：确认全部存在且 is_active=true，否则返回 `2001`
6. 开启事务：删除 room_id 下旧关联（硬删除）
7. 批量插入 brand_rooms(brand_id, room_id)
8. 提交事务，记录INFO日志（脱敏）
9. 返回统一响应结构（code/message/data/timestamp）

---

# 7. 错误处理与事务管理

* 校验失败：返回 `4001`
* room/brand 不存在：返回 `2001`
* 权限不足：返回 `3002`
* 数据库异常：捕获后记录 ERROR 日志，返回 `1002`
* 绑定操作必须事务保证一致性（删除旧关系 + 写新关系）

# 8. 性能优化建议

* `brand_rooms.room_id` / `brand_rooms.brand_id` 已加索引

* 可在服务层做 30s~60s 的轻缓存（可选），避免高频刷新
