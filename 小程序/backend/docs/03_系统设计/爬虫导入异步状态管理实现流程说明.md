## 一、方案概述

### 1.1 核心思路

- **后端**：保持同步执行不变，只在执行前后记录任务状态到数据库
- **前端**：设置请求超时（30秒），超时后通过轮询状态查询接口获取任务进度
- **状态存储**：使用数据库表存储任务状态（方案3：最小化表设计，一个用户一条记录）

### 1.2 执行流程

```
前端请求（30秒超时）
    ↓
后端API：记录状态 "running"
    ↓
后端执行爬虫（同步，可能需要数小时）
    ↓
后端执行导入（同步）
    ↓
后端API：记录状态 "completed" 或 "failed"
    ↓
返回结果（如果前端还在等待）

【前端超时后】
    ↓
前端开始轮询状态查询接口（每10秒）
    ↓
查询状态：running → 继续轮询
    ↓
查询状态：completed → 显示结果，停止轮询
    ↓
查询状态：failed → 显示错误，停止轮询
```

## 二、后端实现流程

### 2.1 状态存储设计

#### 2.1.1 数据库表设计（方案3：最小化表设计）

**表名**：`crawl_import_status`

**设计原则**：
- 一个用户同时只能有一个爬取导入任务
- 新任务开始时自动覆盖旧的状态记录
- 使用 `user_id` 作为主键，简化查询逻辑

**表结构**：
```sql
CREATE TABLE crawl_import_status (
    user_id UUID PRIMARY KEY,                    -- 用户ID（主键）
    status VARCHAR(20) NOT NULL DEFAULT 'running',  -- 状态：running, completed, failed
    progress JSONB,                             -- 进度信息（JSON格式）
    updated_at TIMESTAMP NOT NULL DEFAULT NOW()  -- 更新时间
);

-- 索引：用于查询和清理过期记录
CREATE INDEX idx_crawl_import_status_updated_at ON crawl_import_status(updated_at);
```

**字段说明**：
- `user_id`：用户ID，主键，确保每个用户只有一条记录
- `status`：任务状态
  - `running`：执行中
  - `completed`：已完成
  - `failed`：失败
- `progress`：JSONB 字段，存储所有进度和结果信息
  ```json
  {
    "start_time": "2025-11-19T10:00:00Z",
    "end_time": "2025-11-19T12:30:00Z" | null,
    "current_page": 5,
    "total_pages": 100,
    "crawled_rows": 500,
    "imported_rows": 450,
    "result": { ... } | null,  // 完成时返回完整结果
    "error": "错误信息" | null
  }
  ```
- `updated_at`：最后更新时间，用于清理过期记录

#### 2.1.2 存储方案优势

**选择数据库方案的原因**：
1. **无需额外依赖**：系统已有 PostgreSQL 数据库，无需引入 Redis
2. **持久化可靠**：数据持久化存储，服务器重启不丢失
3. **查询方便**：使用 SQL 查询，支持复杂查询和统计
4. **实现简单**：表结构简单（4个字段），一个用户一条记录
5. **自动覆盖**：使用 `user_id` 作为主键，新任务自动覆盖旧记录
6. **与现有架构一致**：复用现有的数据库连接和 ORM 模式

#### 2.2.1 修改 `/tasks/crawl-and-import` 接口

**修改步骤**：

1. **在方法开始处**（获取 user_id 后）：
   - **变量提取（安全异步异常处理）**：
     - 提取 `user_id_for_logging = str(user_id)`
     - **注意**：不提取 token 和 cookie 到日志变量（安全要求）
   - **记录开始日志**：

   - **如果没有正在运行的任务**：
     - 创建状态记录，设置 `status="running"`，`progress` 中包含 `start_time=当前时间（datetime.utcnow().isoformat()）`
     - 调用状态存储函数保存状态（使用 `INSERT ... ON CONFLICT (user_id) DO UPDATE`）
     - 确保状态更新操作快速完成（非阻塞）
     - 状态更新失败不应该影响主流程（可以记录警告日志）

2. **在 try 块中**（执行爬取和导入前）：
   - 保持原有逻辑不变（同步执行）

3. **在成功返回前**（在 `crawl_and_import_tasks` 方法返回结果之前）：
   - 更新状态为 `status="completed"`
   - 设置 `end_time=当前时间（datetime.utcnow().isoformat()）`
   - 设置 `result=完整结果数据`（包含 crawl_status, crawl_rows, import_result 等）
   - 更新状态存储（状态更新失败不应该影响主流程）
   - 记录成功日志：`logger.info(f"Crawl and import completed - User: {user_id_for_logging}, ...")`（注意：不记录token/cookie）

4. **在 except 块中**（异常处理）：
   - 更新状态为 `status="failed"`
   - 设置 `end_time=当前时间（datetime.utcnow().isoformat()）`
   - 设置 `error=错误信息`（注意：不包含token/cookie）
   - 更新状态存储（状态更新失败不应该影响主流程）
   - 记录错误日志：`logger.error(f"Crawl failed - User: {user_id_for_logging}, Error: {str(e)}", exc_info=True)`
   - **注意**：错误日志中不记录 token 和 cookie 的值
   - 重新抛出异常（保持原有错误处理逻辑）

**关键点**：
- **并发控制**：在设置状态为 `running` 之前，先检查是否有正在运行的任务，防止用户频繁发起请求
- **异常状态处理**：如果 `updated_at` 超过 3 小时且状态仍为 `running`，视为异常状态，允许新任务（可选：更新旧状态为 `failed`）
- 所有状态更新操作应该是**非阻塞**的（快速完成）
- 状态更新失败不应该影响主流程（可以记录警告日志）
- 保持原有的同步执行逻辑完全不变

#### 2.2.2 新增 `/tasks/crawl-import-status` 接口

**新增位置**：`app/api/v1/endpoints/download.py`

**⚠️ 重要：路由顺序约束**

**FastAPI 路由匹配顺序问题**：
- FastAPI 按照路由定义的**顺序**进行匹配
- **固定路径必须放在参数路径之前**，否则会导致路由匹配错误
- 如果 `/tasks/{task_id}` 定义在 `/tasks/crawl-import-status` 之前，FastAPI 会尝试将 `crawl-import-status` 解析为 `task_id` 参数（UUID类型），导致 422 Unprocessable Entity 错误
- **解决方案**：将 `@router.get("/tasks/crawl-import-status")` 路由定义放在 `@router.get("/tasks/{task_id}")` **之前**

**接口设计**：
- **路径**：`GET /api/v1/download/tasks/crawl-import-status`
- **认证**：需要 JWT Token
- **功能**：查询当前用户最近一次爬取导入任务的状态

**实现步骤**：

1. **获取当前用户ID**（从 JWT Token）：
   - 使用 `get_current_user` 依赖注入获取用户信息
   - 从 `current_user` 字典中提取 `user_id`
   - 提取 `user_id_for_logging = str(user_id)`（用于日志记录）

2. **从状态存储中读取状态**：
   - 查询 `crawl_import_status` 表，使用 `user_id` 作为主键直接查询
   - SQL：`SELECT * FROM crawl_import_status WHERE user_id = ?`

3. **处理状态不存在的情况**：
   - 使用 `create_error_response(message="未找到爬取导入任务状态", code=404)` 返回
   - 记录日志：`logger.info(f"状态查询 - User: {user_id_for_logging}, Status: not_found")`

4. **返回状态数据**：
   - 如果状态是 `running`，返回当前进度信息
   - 如果状态是 `completed`，返回完整结果
   - 如果状态是 `failed`，返回错误信息

**响应格式**：
- **HTTP状态码**：200（遵循系统统一规范）
- **业务错误码**：200（成功）或 404（状态不存在）

**成功响应**（状态存在）：
```json
{
  "code": 200,
  "message": "查询成功",
  "data": {
    "status": "running" | "completed" | "failed",
    "updated_at": "2025-11-19T10:00:00Z",
    "progress": {
      "start_time": "2025-11-19T10:00:00Z",
      "end_time": "2025-11-19T12:30:00Z" | null,
      "current_page": 5,
      "total_pages": 100,
      "crawled_rows": 500,
      "imported_rows": 450,
      "result": { ... } | null,  // 完成时返回完整结果
      "error": "错误信息" | null
    } | null
  },
  "timestamp": "2025-11-19T10:05:00Z"
}
```

**状态不存在响应**：
```json
{
  "code": 404,
  "message": "未找到爬取导入任务状态",
  "data": null,
  "timestamp": "2025-11-19T10:05:00Z"
}
```

**实现方式**（遵循现有代码风格）：
```python
# 在 app/api/v1/endpoints/download.py 中
# ⚠️ 重要：此路由必须定义在 @router.get("/tasks/{task_id}") 之前，避免路由匹配冲突
from fastapi import Depends
from sqlalchemy.orm import Session
from uuid import UUID
from app.core.deps import get_current_user, get_db
from app.core.response import create_response, create_error_response
from app.core.crawl_import_status import get_crawl_import_status
import logging

logger = logging.getLogger(__name__)

@router.get("/tasks/crawl-import-status")
def get_crawl_import_status_endpoint(
    current_user: dict = Depends(get_current_user),
    db: Session = Depends(get_db)
):
    """
    查询爬取导入任务状态
    
    **认证**: 需要JWT Token
    """
    # ==================== 【核心规范0.1】变量提取（安全异步异常处理） ====================
    user_id_for_logging = current_user["user_id"]
    user_id = UUID(user_id_for_logging)
    
    logger.info(f"API /tasks/crawl-import-status: 请求开始 - 用户ID={user_id_for_logging}")
    
    try:
        # ==================== 业务处理 ====================
        status = get_crawl_import_status(db, user_id)
        
        if not status:
            logger.info(f"状态查询 - User: {user_id_for_logging}, Status: not_found")
            return create_error_response(
                message="未找到爬取导入任务状态",
                code=404
            )
        
        logger.info(f"状态查询成功 - User: {user_id_for_logging}, Status: {status.get('status')}")
        
        # ==================== 【核心规范0.2】统一响应处理 ====================
        return create_response(
            data=status,
            message="查询成功",
            code=200
        )
    except Exception as e:
        logger.error(f"状态查询失败 - User: {user_id_for_logging}, Error: {str(e)}", exc_info=True)
        return create_error_response(
            message="查询状态时发生错误",
            code=500
        )
```

- 如果状态不存在，返回 `code=404`，`data=null`

- `start_time`、`end_time`、`result`、`error` 等都存储在 `progress` 字段中

### 2.3 状态存储函数实现

#### 2.3.1 函数设计

**函数1：保存状态**
```python
from datetime import datetime
from uuid import UUID
from sqlalchemy.orm import Session
from sqlalchemy.dialects.postgresql import insert
from app.models.crawl_import_status import CrawlImportStatus
import logging

logger = logging.getLogger(__name__)

def save_crawl_import_status(db: Session, user_id: UUID, status: str, progress: dict) -> bool:
    """
    保存爬取导入任务状态
    
    Args:
        db: 数据库会话
        user_id: 用户ID
        status: 状态字符串（'running', 'completed', 'failed'）
        progress: 进度字典（包含 start_time, end_time, result, error 等）
    
    Returns:
        bool: 是否保存成功
    """
    try:
        # 使用 INSERT ... ON CONFLICT DO UPDATE 实现自动覆盖
        # 如果记录不存在则插入，存在则更新
        stmt = insert(CrawlImportStatus).values(
            user_id=user_id,
            status=status,
            progress=progress,
            updated_at=datetime.utcnow()
        )
        stmt = stmt.on_conflict_do_update(
            index_elements=['user_id'],
            set_={
                'status': stmt.excluded.status,
                'progress': stmt.excluded.progress,
                'updated_at': stmt.excluded.updated_at
            }
        )
        db.execute(stmt)
        db.commit()
        logger.info(f"状态保存成功 - User: {user_id}, Status: {status}")
        return True
    except Exception as e:
        db.rollback()
        logger.error(f"状态保存失败 - User: {user_id}, Error: {str(e)}", exc_info=True)
        # 状态更新失败不应该影响主流程（记录警告日志）
        return False
```

**函数2：读取状态**
```python
from uuid import UUID
from sqlalchemy.orm import Session
from app.models.crawl_import_status import CrawlImportStatus
import logging

logger = logging.getLogger(__name__)

def get_crawl_import_status(db: Session, user_id: UUID) -> dict | None:
    """
    获取爬取导入任务状态
    
    Args:
        db: 数据库会话
        user_id: 用户ID
    
    Returns:
        dict | None: 状态字典，如果不存在返回 None
        {
            "status": "running" | "completed" | "failed",
            "progress": { ... },
            "updated_at": "2025-11-19T10:00:00Z"
        }
    """
    try:
        record = db.query(CrawlImportStatus).filter(
            CrawlImportStatus.user_id == user_id
        ).first()
        
        if not record:
            return None
        
        return {
            "status": record.status,
            "progress": record.progress,  # JSONB 自动转换为 dict
            "updated_at": record.updated_at.isoformat() if record.updated_at else None
        }
    except Exception as e:
        logger.error(f"状态查询失败 - User: {user_id}, Error: {str(e)}", exc_info=True)
        return None
```

**函数3：检查是否有正在运行的任务**
```python
from uuid import UUID
from sqlalchemy.orm import Session
from datetime import datetime, timedelta
from app.models.crawl_import_status import CrawlImportStatus
import logging

logger = logging.getLogger(__name__)

def check_running_task(db: Session, user_id: UUID, max_running_hours: int = 3) -> bool:
    """
    检查用户是否有正在运行的爬取导入任务
    
    Args:
        db: 数据库会话
        user_id: 用户ID
        max_running_hours: 最大运行时间（小时），超过此时间且状态仍为running，视为异常状态，允许新任务
    
    Returns:
        bool: True 表示有正在运行的任务，False 表示没有
    """
    try:
        record = db.query(CrawlImportStatus).filter(
            CrawlImportStatus.user_id == user_id,
            CrawlImportStatus.status == 'running'
        ).first()
        
        if not record:
            return False
        
        # 检查是否超过最大运行时间（异常状态处理）
        if record.updated_at:
            max_time = datetime.utcnow() - timedelta(hours=max_running_hours)
            if record.updated_at < max_time:
                # 超过最大运行时间，视为异常状态，允许新任务
                # 可选：更新状态为 failed，记录异常信息
                logger.warning(
                    f"用户 {user_id} 的任务状态异常："
                    f"状态为 running 但已超过 {max_running_hours} 小时，"
                    f"最后更新时间为 {record.updated_at}"
                )
                return False
        
        return True
    except Exception as e:
        logger.error(f"检查运行任务失败 - User: {user_id}, Error: {str(e)}", exc_info=True)
        # 异常情况下，为了安全，返回 True（阻止新任务）
        return True
```

### 3.2 状态轮询实现

#### 3.2.1 新增状态轮询方法

**方法名**：`startStatusPolling(userId)`

**实现步骤**：

1. **创建轮询定时器**：
   - 使用 `setInterval`，每 10 秒查询一次
   - 保存定时器 ID 到组件状态（`pollingTimer`）

2. **查询状态接口**：
   - 调用 `downloadAPI.getCrawlImportStatus()`
   - 处理响应数据

3. **状态处理逻辑**：
   - **status === "running"**：
     - 显示进度信息（如果有）
     - 继续轮询
   - **status === "completed"**：
     - 显示成功消息
     - 停止轮询
     - 恢复按钮状态（`crawlImporting.value = false`）
     - 刷新任务列表
   - **status === "failed"**：
     - 显示错误消息
     - 停止轮询
     - 恢复按钮状态
   - **status === "not_found"**：
     - 可能是状态已过期或任务不存在
     - 停止轮询
     - 恢复按钮状态
     - 提示用户手动刷新

4. **轮询停止条件**：
   - 状态变为 `completed` 或 `failed`
   - 状态变为 `not_found`
   - 达到最大轮询时间（如 3 小时）
   - 组件卸载（`onUnmounted` 中清理）

5. **错误处理**：
   - 网络错误：记录日志，继续轮询
   - 认证错误：停止轮询，提示重新登录
   - 其他错误：记录日志，继续轮询（最多重试 3 次）

#### 3.2.2 进度显示

**显示位置**：可以在按钮旁边显示进度提示，或使用全局消息提示

**显示内容**：
- 如果 `progress` 存在且包含进度信息：
  - "正在爬取第 X/Y 页..."（从 `progress.current_page` 和 `progress.total_pages` 获取）
  - "已爬取 X 条数据，已导入 Y 条..."（从 `progress.crawled_rows` 和 `progress.imported_rows` 获取）
  - "任务开始时间：YYYY-MM-DD HH:mm:ss"（从 `progress.start_time` 获取）
- 如果 `progress` 不存在或为空：
  - "任务执行中，请稍候..."

## 五、关键实现要点

### 5.1 后端要点

1. **状态更新必须快速**：
   - 状态更新操作应该是非阻塞的
   - 状态更新失败不应该影响主流程

2. **状态过期和清理**：
   - 数据库记录不会自动过期，需要定期清理
   - 建议：创建定时任务，清理 `updated_at` 超过 7 天的记录
   - 清理 SQL：`DELETE FROM crawl_import_status WHERE updated_at < NOW() - INTERVAL '7 days'`
   - 或者：在查询时检查 `updated_at`，如果超过 3 小时且状态为 `running`，视为异常状态

3. **状态唯一性和并发控制**：
   - 每个用户同时只能有一个爬取导入任务
   - **在API层检查**：在设置状态为 `running` 之前，先调用 `check_running_task()` 检查是否有正在运行的任务
   - 如果有正在运行的任务，返回 HTTP 409 Conflict 错误，阻止新任务启动
   - 如果没有正在运行的任务，新任务开始时自动覆盖旧的状态记录
   - **异常状态处理**：如果 `updated_at` 超过 3 小时且状态仍为 `running`，视为异常状态，允许新任务（可选：更新旧状态为 `failed`）

4. **进度信息更新**（可选增强）：
   - 如果需要在执行过程中更新进度，可以在爬虫执行的关键点更新状态
   - 例如：每爬取一页后更新 `progress.current_page`

### 5.2 前端要点

1. **超时时间设置**：
   - 建议 30 秒（足够后端记录状态，不会让用户等待太久）
   - 可以根据实际情况调整

2. **轮询间隔**：
   - 建议 10 秒（平衡实时性和服务器压力）
   - 可以根据实际情况调整

3. **最大轮询时间**：
   - 建议 3 小时（足够覆盖最长任务时间）
   - 超过最大时间后停止轮询，提示用户手动刷新
   - 可以在查询时检查 `updated_at`，如果超过 3 小时且状态仍为 `running`，视为异常状态

4. **用户体验优化**：
   - 显示进度提示（如果有）
   - 提供"取消任务"功能（可选，需要后端支持）
   - 页面刷新后能恢复轮询状态

5. **错误处理**：
   - 网络错误：继续轮询（最多重试）
   - 认证错误：停止轮询，提示重新登录
   - 状态不存在：停止轮询，提示手动刷新

   - **在 `crawl_and_import_tasks` 方法成功返回前**：
     - 更新 `status="completed"` 并保存完整结果（包含 crawl_status, crawl_rows, import_result 等）
     - 调用 `save_crawl_import_status` 更新状态
   - **在异常处理中**：
     - 更新 `status="failed"` 并保存错误信息（注意：不包含token/cookie）
     - 调用 `save_crawl_import_status` 更新状态
     - 状态更新失败不应该影响主流程（记录警告日志）

2. **并发控制实现细节**：
   - 使用数据库查询来检查，确保原子性
   - 检查逻辑应该在设置状态为 `running` 之前执行
   - 考虑异常状态：如果 `updated_at` 超过 3 小时且状态仍为 `running`，视为异常状态，允许新任务

3. **状态更新频率**：
   - 初始状态：任务开始时更新一次（status="running"）
   - 完成状态：任务完成时更新一次（status="completed" 或 "failed"）
   - （可选）进度更新：如果需要在执行过程中更新进度，可以在关键点更新 `progress` 字段

4. **状态查询接口**：
   - 路径：`GET /api/v1/download/tasks/crawl-import-status`
   - 认证：需要 JWT Token（使用 `get_current_user` 依赖注入）
   - 返回：当前用户的状态信息（遵循系统统一响应格式）

5. **与现有系统的集成**：
   - 状态更新操作应该快速完成（非阻塞），不影响主流程
   - 状态更新失败不应该影响 `crawl_and_import_tasks` 的正常执行
   - 保持现有的异常处理逻辑不变（状态更新失败只记录警告日志）
   - 保持现有的日志记录逻辑不变（确保不记录token/cookie）
