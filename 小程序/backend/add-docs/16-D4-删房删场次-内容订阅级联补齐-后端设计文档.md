## 📌 核心定位说明

### 1. 本文档的定位

显式删房/删场次时补齐 `user_subscriptions` 级联，消除孤儿订阅。并入既有 `delete_room_related`，不另开总设计。

**明确不做**: 文件 GC；注销按 user 清（D2）。

### 2. 核心特点

- ✅ 与现网删收藏同风格（目标没了 → 关系物理删）
- ✅ 与 D2 入口不同：本包按 **target**，D2 按 **user**

### 3. 业务价值

「我的订阅」不再指向已删房/场次。

## 🎯 设计要点与约定

### 1.1 软删除策略

| 操作 | `user_subscriptions` |
|------|----------------------|
| 用户取消订阅 | `is_active=false`（既有） |
| 删房 / 删场次 | **物理 DELETE**（本包） |
| 账号注销 | 物理 DELETE by user（`16-D2`，不在此实现） |

### 1.2 变更决策记录

#### 决策 1：物理删 vs 软删孤儿

| 方案 | 结论 |
|------|------|
| 目标删除后只把订阅 `is_active=false` | ❌ 仍占唯一约束/残留分析噪音 |
| 物理删除目标下全部订阅行（含已软删行） | ✅ 采用 |

#### 决策 2：是否新建独立「级联服务」

| 方案 | 结论 |
|------|------|
| 新开总设计重写房下万物 | ❌ 《16》明确禁止 |
| 仅增补 `delete_room_related` + 删场次路径 | ✅ 采用 |

## 3. API 接口设计

### 3.1 【修改·行为】删除直播间（JWT）

**Endpoint**: `DELETE /api/v1/rooms/{room_id}`

**描述**: 权限通过后，`delete_room_related` 增加内容订阅清理，再 `remove(room)`。

**认证**: JWT（owner / Admin）

**请求体**: 无（维持现网）

**成功响应**: 维持现网

**执行流程**:

1. **接收请求**: `room_id`  
2. **JWT 验证**  
3. **权限检查**: owner 或 Admin（含 `16-D1` 失管规则若已合入）  
4. **存在性检查**: 房间不存在 → 2001  
5. **调用** `delete_room_related(db, room_id)`（见 §4.1 更新后顺序）  
6. **remove(room)** 并 commit（或按现网事务边界）  
7. **返回成功**  
8. **不** 删除对象存储封面/视频文件（P22/P32 另案）  
9. **捕获** IntegrityError → 409/2005（现网）  
10. **日志**: 记录订阅删除行数（info）

---

### 3.2 【修改·行为】删除场次（JWT）

**Endpoint**: 以现网为准（如 `DELETE /api/v1/sessions/{session_id}` 或挂在 rooms 下）

**描述**: 删除场次行之前/同一事务内，物理删除 `user_subscriptions` 中 `target_type=session AND target_id=session_id`。

**执行流程**:

1. 接收 `session_id`  
2. JWT + 权限（场次所属房 owner / Admin）  
3. 确认场次存在  
4. **【新增】** `DELETE FROM user_subscriptions WHERE target_type='session' AND target_id=:session_id`  
5. 按现网删除场次关联（标签/专家挂靠等 CASCADE 或应用层）  
6. 删除场次行  
7. commit  
8. 返回  
9. 日志 rowcount  
10. 不删对象存储文件

## 4. 执行流程详细说明

### 4.1 【修改】`delete_room_related` 推荐顺序

在《删除直播间-应用层级联删除-实现说明》基础上 **插入订阅清理**：

```
1. 查出该房 session_ids
2. 若有 session_ids:
   - live_session_experts
   - session_statistics
   - session_tags
   - live_room_messages (by session_id)
   - watch_history
   - 【新增】user_subscriptions WHERE target_type='session' AND target_id IN (session_ids)
3. 房间级:
   - brand_rooms
   - topic_category_rooms
   - live_room_categories
   - live_room_official_accounts
   - live_room_messages (by room_id)
   - live_room_tabs
   - user_favorites
   - 【新增】user_subscriptions WHERE target_type='room' AND target_id=:room_id
4. live_sessions (by room_id)
5. 外层 remove(room)
```

### 4.2 与 D2 入口对比

```
D2: DELETE ... WHERE user_id = :uid
D4: DELETE ... WHERE target_type/target_id = :room_or_session
```

## 5. 错误处理与事务管理

### 5.1 错误处理策略

- 订阅删除失败 → 与 `delete_room_related` 同样 rollback + `DatabaseOperationException`  
- 不出现「房已删但订阅残留」的部分成功（同事务）

### 5.2 事务管理规范

- 订阅删除与既有关联删除在同一 AsyncSession 事务  
- 提交点维持现网 `remove`/`delete_room` 约定  

---

## 6. 性能优化建议

### 6.1 数据库优化

- 确保 `(target_type, target_id)` 索引  
- `IN (session_ids)` 时 session 量大可分批（一般直播间场次有限）

### 6.2 缓存策略

- 若有「我的订阅」缓存，按被删 target 或依赖用户下次读取失效即可（P1）

### 6.3 应用层优化

- 一次 `DELETE ... IN (...)`，避免逐 session 循环 HTTP
