# 个人直播间列表 API 需求分析与验收标准（最新定稿）

## 1. 背景与问题

当前项目中直播间能力已具备，但前端"我的直播"页面在普通用户场景下缺少专用的个人直播间查询接口，无法高效支持不同账号查看自己创建的直播间。

- 后端现有 `GET /api/v1/rooms` 管理员接口可返回全部直播间，但权限设计未细化为"个人"筛选。
- 前端需要在"我的直播"页面展示当前登录用户创建的所有直播间。
- 业务目标是提供专用接口支持个人直播间的分页、搜索、排序、过滤。
- 管理后台管理员查看接口必须继续保持，不可替代。

本次需求核心是新增并落地"用户个人直播间列表API"，同时精化权限模型与查询策略。

当前实现状态说明：

- `GET /api/v1/users/me/rooms` 尚未在后端实现。
- 本文档用于定义该接口的目标契约、实施范围与验收标准，作为研发与联调基线。

## 2. 现状梳理

### 2.1 已有相关接口

- `GET /api/v1/rooms`：直播间列表（管理员/普通用户混用，权限不清晰）
- `POST /api/v1/rooms`：创建直播间
- `GET /api/v1/rooms/{id}`：直播间详情
- `PATCH /api/v1/rooms/{id}`：修改直播间（仅所有者/管理员）
- `DELETE /api/v1/rooms/{id}`：删除直播间（仅所有者/管理员）
- `GET /api/v1/rooms/{id}/sessions`：直播场次列表
- `POST /api/v1/rooms/{id}/sessions`：创建直播场次
- `GET /api/v1/sessions/{id}`：直播场次详情（含统计）
- `PATCH /api/v1/sessions/{id}`：修改直播场次
- `DELETE /api/v1/sessions/{id}`：删除直播场次
- `GET /api/v1/rooms/{id}/sub-venues`：分会场列表

### 2.2 前端调用现状

- 管理员直播管理页：走 `GET /api/v1/rooms`，需要查询所有。
- 用户"我的直播"页：**缺失专用接口**，目前无法高效过滤。

### 2.3 数据层可用字段

模型字段可支撑个人直播间列表查询与展示：

- `id`（UUID）
- `user_id`（所有者）
- `title`（直播间名称）
- `description`（描述）
- `cover_url`（封面）
- `stream_key`（推流密钥，仅所有者可见）
- `is_private`（是否私密）
- `record_by_default`（是否默认录制）
- `category_id`（分类）
- `is_active`（是否启用，V6 新增）
- `created_at`
- `updated_at`

## 3. 目标与范围

### 3.1 目标

1. 新增面向普通用户的个人直播间列表API。
2. 支持分页、搜索、排序、过滤（状态、分类等）。
3. 返回个人专属数据（含推流密钥、统计概览）。
4. 不影响管理员接口与详情接口行为。
5. 返回统一响应结构与错误码风格。
6. 为后续"直播统计大盘"、"直播分析"等功能提供稳定基础。

### 3.2 非目标

- 不替代管理员全量直播间查询接口。
- 不改变直播间权限模型整体架构。
- 不在本次需求中引入新的直播间创建工作流。

## 4. API 契约（对外）

### 4.1 路由与方法

- `GET /api/v1/users/me/rooms`

说明：使用 `/users/me/` 前缀表示"当前登录用户的个人资源"，与项目已有的稳定分流规则保持一致。

### 4.2 请求头

- `Accept: application/json`
- `Authorization: Bearer <token>`（**必需**，仅登录用户可访问）
- `X-Request-Id: <uuid>`（可选，便于链路追踪）

### 4.3 查询参数

- `page`：页码，`default=1`，`min=1`
- `size`：每页大小，`default=20`，`min=1`，`max=100`
- `keyword`：关键词，匹配直播间名称/描述
- `category_id`：分类筛选
- `is_private`：是否私密，可选 `true/false`
- `status`：直播间状态，可选值 `active/inactive`（基于 `is_active` 字段）
- `sort`：排序表达式，默认 `created_at:desc,id:asc`
- `cursor`：游标（可选，见第 7 节，推荐中长期启用）

## 7. 分页与排序策略（稳健性要求）

### 7.1 分页模式

- 短期兼容：支持 `page/size`（offset-based）。
- 中长期推荐：支持 `cursor` 分页（基于排序键游标）。

### 7.2 稳定排序

默认排序固定为：

- `created_at desc`（最新的直播间在前）
- `id asc`（强制最终稳定键）

支持的排序字段：

- `created_at`
- `updated_at`
- `session_count`（场次数量）
- `total_viewers`（总观看人数）

### 7.3 一致性声明

- offset 在并发写入下可能出现"重复/漏项"。
- 强一致翻页场景优先使用 cursor。
- 若请求携带 `cursor`，服务端应忽略 `page` 并返回 `next_cursor`。

## 9. 安全、权限与速率限制

### 9.1 访问策略

- **必需登录**：`GET /api/v1/users/me/rooms` 仅登录用户可访问。
- **所有权验证**：返回的直播间必须属于当前登录用户，不允许跨用户查询。
- **数据隔离**：确保不同用户之间数据完全隔离。

### 9.2 速率限制

- 登录用户：`300 req/min/user`。
- 超限返回 429，附带 `Retry-After` 头。

### 9.3 推流密钥约束（与当前实现一致）

- `stream_key` 仅用于直播推流鉴权，属于敏感字段。
- 当前接口仅允许返回当前登录用户自己的直播间，因此不会暴露他人密钥。
- 本文档聚焦“个人直播间列表查询”能力，不在本次需求中新增密钥轮换、多密钥、应急响应等扩展机制。
- 如后续有独立安全改造需求，应单列《推流密钥安全改造》专题文档与迭代计划。

### 9.4 防刷措施

- 连续深翻页 + 高频请求触发风控。
- 可配置验证码或临时封禁策略。
- 密钥查询频率限制：10次/分钟/用户（超过3次时记录可疑日志）

## 10. 字段隐私与暴露控制

### 10.1 返回给所有者的字段

- `id`
- `user_id`
- `title`
- `description`
- `cover_url`
- `stream_key`（**仅所有者可见**）
- `is_private`
- `record_by_default`
- `category_id`
- `is_active`
- `created_at`
- `updated_at`
- `session_count`
- `last_session_at`
- `total_viewers`

### 10.2 禁止暴露字段

- 内部审核记录、待审核状态。
- 风控标签、违规标记。
- 推送配置、通知状态等运营内部字段。
- 其他用户的个人直播间（即使是管理员，也应通过不同接口查询）。

## 11. 性能、索引与容量建议

### 11.1 索引建议（关系型数据库）

- 用户隔离索引：`(user_id, is_active, created_at, id)`。
- 状态筛选索引：`(user_id, is_active, created_at)`。
- 分类筛选索引：`(user_id, category_id, created_at)`。
- 关键词检索：全文索引（如 PostgreSQL GIN + tsvector，或 MySQL FULLTEXT）。

### 11.2 查询优化

- 列表接口仅查必要字段，避免 `SELECT *`。
- 使用 JOIN 或子查询高效获取 `session_count`、`last_session_at`、`total_viewers`。
- 对 `keyword` 长度与频率做限制（建议最大 100 字符）。
- 用户直播间列表通常不超过 100-1000 间，性能压力较小。

### 11.3 缓存建议

- 热点参数（如用户首页直播间列表）可做短缓存（30-60s）。
- 使用 Redis 缓存 `session_count`、`total_viewers` 等聚合值，异步更新。
- 缓存 Key 示例：`user:{user_id}:rooms:stats`。

### 11.4 成本估算建议

- 单个用户通常拥有 5-100 间直播间，查询性能无压力。
- 即使百万用户体量，单用户查询仍为小数据集，索引效率高。

## 12. 测试用例与验收脚本

### 12.1 单元测试（Service/CRUD）

- 参数边界：`page<1`、`size=0`、`size>100`。
- 排序解析：非法 sort 值回退默认排序。
- 过滤组合：`keyword + is_private + category_id + status`。
- 用户隔离：确保查询仅返回当前用户的直播间。

### 12.2 接口测试（API）

- 未登录请求返回 `401`。
- 登录请求返回正常数据。
- 跨用户查询被拒绝（若有此入口）。
- `GET /api/v1/users/me/rooms?page=1&size=20` 返回结构稳定。
- 空结果返回 `items=[]`、`total=0`、`has_more=false`。
- 参数越界返回 `4001`。
- DB 异常返回 `1002/5001` 且具备 `request_id`。
- 超限请求返回 `4291`。

### 12.3 集成与回归测试

- 创建直播间后，列表接口可立即查询到。
- 修改直播间后，列表数据同步更新。
- 删除直播间后，列表中移除该项。
- 管理员接口 `GET /api/v1/rooms` 不受影响。
- 详情接口 `GET /api/v1/rooms/{id}` 不受影响。

## 13. 兼容性、迁移与回滚方案

### 13.1 前端切换策略

1. 新接口上线并保持默认可用。
2. 前端"我的直播"页面切换到 `GET /api/v1/users/me/rooms`。
3. 前端列表页展示逻辑更新：只显示当前用户创建的直播间。

### 13.2 后端兼容性

- 保留旧 `GET /api/v1/rooms` 接口供管理员使用。
- 旧接口仍返回全量直播间（权限不变）。
- 新接口 `/users/me/rooms` 不与旧接口冲突。

### 13.3 回滚策略

- 通过特性开关立即关闭新接口（返回 404 或维护模式）。
- 前端需备好回退方案（如降级调用旧接口）。
- 后端保留兼容，不删除既有接口。

### 13.4 版本策略

## 15. 前端典型场景（UX 对齐）

### 15.3 推流配置场景

### 15.4 直播统计场景

- 列表页展示 `session_count`（累计直播场次）、`total_viewers`（总观看人数）。

## 18. 与专家接口的对标

| 维度 | 专家全量列表API | 个人直播间API | 说明 |

## 19. 结论

本次需求的落地点是新增并标准化 `GET /api/v1/users/me/rooms` 个人直播间列表接口，同时保证与现有管理员接口并行稳定。上线后实现明确分工：

- 管理后台：`GET /api/v1/rooms`（全量，管理员专用）
- 用户"我的直播"：`GET /api/v1/users/me/rooms`（个人，登录用户专用）
- 直播间详情：`GET /api/v1/rooms/{id}`（保持不变）

此接口为后续"直播统计大盘"、"智能推荐"等高阶功能奠定基础，同时提升用户个人直播管理的交互体验。
