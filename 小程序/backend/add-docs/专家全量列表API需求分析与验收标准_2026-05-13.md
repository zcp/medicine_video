# 专家全量列表 API 需求分析与验收标准（最新定稿）

## 1. 背景与问题

当前项目中专家能力已具备，但前端专家列表页在普通用户场景下实际使用的是精选专家接口，导致页面展示集合并非完整专家库。

- 数据库已有 400+ 专家。
- 前端列表页当前仅展示精选集合。
- 业务目标是专家列表页可分页访问全量可展示专家。
- 首页推荐位必须继续使用精选专家接口，不可替代。

本次需求核心是新增并落地“专家列表页专用的全量查询接口”，而非重做专家体系。

## 2. 现状梳理

### 2.1 已有相关接口

- `GET /api/v1/featured-experts`：首页精选专家
- `GET /api/v1/experts/{expert_id}`：专家详情
- `GET /api/v1/experts/{expert_id}/sessions`：专家参与场次
- `POST /api/v1/sessions/{session_id}/experts`：配置场次专家
- `GET /api/v1/sessions/{session_id}/experts`：获取场次专家
- `GET /api/v1/experts/{expert_id}/is-followed`：关注状态检查
- `POST /api/v1/users/me/followed-experts`：关注专家
- `DELETE /api/v1/users/me/followed-experts/{expert_id}`：取消关注专家
- `GET /api/v1/users/me/followed-experts`：已关注专家列表
- `GET /api/v1/admin/experts`：管理员专家分页列表
- `POST /api/v1/admin/experts`：创建专家
- `PATCH /api/v1/admin/experts/{expert_id}`：更新专家
- `DELETE /api/v1/admin/experts/{expert_id}`：删除专家
- `POST /api/v1/admin/experts/{expert_id}/avatar`：上传头像
- `POST /api/v1/admin/experts/batch-import`：批量导入

### 2.2 前端调用现状

- 普通用户专家页：走精选专家接口。
- 管理员专家页：走管理员分页接口。

### 2.3 数据层可用字段

模型字段可支撑全量列表查询与展示：

- `id`
- `name`
- `title`
- `hospital`
- `department`
- `expertise_areas`
- `bio`
- `avatar_url`
- `is_featured`
- `is_active`
- `sort_order`
- `created_at`
- `updated_at`

## 3. 目标与范围

### 3.1 目标

1. 新增面向专家列表页的全量查询接口。
2. 支持分页、筛选、排序、关键词检索。
3. 不影响精选接口与管理员接口行为。
4. 返回统一响应结构与错误码风格。
5. 为后续高级搜索/筛选提供稳定基础。

### 3.2 非目标

- 不替代首页精选接口。
- 不改变管理员接口权限语义。
- 不在本次需求中引入全新 API 前缀体系。

## 4. API 契约（对外）

### 4.1 路由与方法

- `GET /api/v1/experts`

### 4.2 请求头

- `Accept: application/json`
- `Authorization: Bearer <token>`（可选，登录时携带；匿名访问策略见第 9 节）
- `X-Request-Id: <uuid>`（可选，便于链路追踪）

### 4.3 查询参数

- `page`：页码，`default=1`，`min=1`
- `size`：每页大小，`default=50`，`min=1`，`max=100`
- `keyword`：关键词，匹配姓名/医院/科室/简介
- `department`：科室筛选
- `hospital`：医院筛选
- `is_active`：是否启用，默认 `true`
- `sort`：排序表达式，默认 `sort_order:asc,created_at:desc,id:asc`
- `cursor`：游标（可选，见第 7 节，推荐中长期启用）

```yaml

        - name: page

            type: integer
            minimum: 1
            default: 1
        - name: size
          in: query
          schema:
            type: integer
            minimum: 1
            maximum: 100
            default: 50
        - name: keyword
          in: query
          schema:
            type: string
        - name: department
          in: query
          schema:
            type: string
        - name: hospital

            type: string
        - name: is_active
          in: query
          schema:
            type: boolean
            default: true
        - name: sort
          in: query
```

## 7. 分页与排序策略（稳健性要求）

### 7.1 分页模式

- 短期兼容：支持 `page/size`（offset-based）。
- 中长期推荐：支持 `cursor` 分页（基于排序键游标）。

### 7.2 稳定排序

默认排序固定为：

- `sort_order asc`
- `created_at desc`
- `id asc`（强制最终稳定键）

### 7.3 一致性声明

- offset 在并发写入下可能出现“重复/漏项”。
- 强一致翻页场景优先使用 cursor。
- 若请求携带 `cursor`，服务端应忽略 `page` 并返回 `next_cursor`。

## 8. 错误码与 HTTP 状态映射

| 业务 code | HTTP 状态码 | 典型场景 | 示例响应 |
|---:|---:|---|---|
| 200 | 200 | 查询成功 | `{"code":200,"message":"success"}` |
| 4001 | 400 | 参数校验失败（如 `size>100`） | `{"code":4001,"message":"size 超过最大值 100"}` |
| 1002 | 500 | 数据库查询异常 | `{"code":1002,"message":"数据库错误"}` |
| 4011 | 401 | 需要登录但未登录 | `{"code":4011,"message":"未授权访问"}` |
| 4291 | 429 | 请求频率超限 | `{"code":4291,"message":"请求过于频繁"}` |
| 5001 | 500 | 通用服务器错误 | `{"code":5001,"message":"服务器内部错误"}` |

统一错误体：

```json
{
  "code": 4001,
  "message": "size 超过最大值 100",
  "timestamp": "2026-05-13T00:00:00Z",
  "request_id": "2be2f6d7-4f0d-4fce-8f88-63bb78807e20"
}
```

## 9. 安全、权限与速率限制

### 9.1 访问策略

- 默认允许匿名读（专家公开页场景）。
- 登录态可获得个性化扩展字段（如关注状态）。
- 如后续合规要求变化，可切换为“登录后可访问”。

### 9.2 速率限制

- 匿名：`60 req/min/IP`。
- 登录：`300 req/min/user`。
- 超限返回 429，附带 `Retry-After`。

### 9.3 防刷措施

- 连续深翻页 + 高频请求触发风控。
- 可配置验证码或临时封禁策略。

## 10. 字段隐私与暴露控制

### 10.1 对外公开字段

- `id`
- `name`
- `title`
- `hospital`
- `department`
- `expertise_areas`
- `bio`（可长度截断）
- `avatar_url`
- `is_featured`
- `is_active`
- `sort_order`
- `created_at`
- `updated_at`

### 10.2 禁止暴露字段

- 审核轨迹、内部备注、操作审计人。
- 内部统计与风控标签。
- 个人敏感联系方式（手机号/邮箱/住址）。

## 11. 性能、索引与容量建议

### 11.1 索引建议（关系型数据库）

- 过滤索引：`(is_active)`。
- 组合筛选索引：`(is_active, department)`、`(is_active, hospital)`。
- 排序分页索引：`(is_active, sort_order, created_at, id)`。
- 关键词检索：全文索引（如 PostgreSQL GIN + tsvector，或 MySQL FULLTEXT）。

### 11.2 查询优化

- 列表接口仅查必要字段，避免 `SELECT *`。
- 对 `keyword` 长度与频率做限制。
- 首屏热点参数可做短缓存（30-60s）。

### 11.3 成本估算建议

- 无索引模糊查询在万级以上会明显升高延迟。
- 百万级数据必须依赖全文索引或搜索服务，避免全表扫描。

## 12. 测试用例与验收脚本

### 12.1 单元测试（Service/CRUD）

- 参数边界：`page<1`、`size=0`、`size>100`。
- 排序解析：非法 sort 值回退默认排序。
- 过滤组合：`keyword + department + hospital`。

### 12.2 接口测试（API）

- `GET /api/v1/experts?page=1&size=50` 返回结构稳定。
- 空结果返回 `items=[]`、`total=0`、`has_more=false`。
- DB 异常返回 `1002/5001` 且具备 `request_id`。
- 超限请求返回 `4291`。

### 12.3 集成与回归测试

- 首页 `featured-experts` 不受影响。
- 专家详情接口不受影响。
- 管理员专家接口不受影响。

### 12.4 验收脚本建议

- 使用 `pytest + requests` 或 Postman/Newman 建立契约测试。
- CI 在后端合并请求时自动执行。

## 13. 兼容性、迁移与回滚方案

### 13.1 前端切换策略

1. 新接口上线并保持默认可用。
2. 前端通过 feature flag 按比例切流（10% -> 50% -> 100%）。
3. 首页继续调用 `featured-experts`，专家页切到 `experts`。

### 13.2 回滚策略

- 通过开关立即回退到旧调用链路。
- 后端保留兼容，不删除既有接口。

### 13.3 版本策略

- 本次为 `v1` 增量能力。
- 若出现不兼容变更，新增 `v2`，不直接破坏 `v1`。

## 15. 前端典型场景（UX 对齐）

### 15.1 首屏场景

- 请求：`page=1&size=50`。
- 展示：按默认稳定排序渲染。
- 继续加载：增量请求下一页或使用 `next_cursor`。

### 15.2 搜索与筛选场景

- 关键词输入优先走服务端检索。
- 科室/医院筛选与关键词可组合。

### 15.3 关注状态展示场景

- 登录用户可返回 `is_followed`（扩展字段）或批量查询关注态。
- 不推荐逐条 N+1 调用。

## 16. 最终验收标准

### 16.1 功能验收

- 数据库存在 400+ 专家时，列表页可分页完整访问全部可用专家。
- 首页精选位行为保持不变。
- 管理员列表行为保持不变。

### 16.2 接口验收

- `GET /api/v1/experts` 返回 200 且结构稳定。
- 参数越界返回 4001，不可突破上限。
- `keyword`、`department`、`hospital` 过滤有效。

### 16.3 工程质量验收

- Schema、CRUD、Service、Endpoint 职责清晰。
- 单元、接口、集成测试齐备并进入 CI。
- 监控、日志、限流配置上线前完成。

## 18. 结论

本次需求的落地点是新增并标准化 `GET /api/v1/experts` 全量专家接口，同时保证与精选接口、管理员接口并行稳定。上线后实现明确分工：

- 首页：`featured-experts`（精选）
- 专家页：`experts`（全量分页）
