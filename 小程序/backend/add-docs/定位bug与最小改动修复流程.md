# 定位 bug 与最小改动修复流程（建议照着做）

目标：在不“大改架构”的前提下，把 bug 修到可验证、可合并。

## 0. 开工前准备（一次性）

- 只改你负责的 service：先确认 bug 属于 `live_core_service` / `media_download_service` / `users` 哪一个。
- 能用现有模式就别引入新模式：先找仓库里有没有类似实现（grep/全局搜索）。
- 环境尽量复现同事的方式：优先用 `start-dev.bat` + compose（减少“我本地能跑你那不行”）。

## 2. “最小改动”的常用技巧

- 优先修边界条件（None/空字符串/空列表/0/时区/编码/文件路径）。
- 优先补小测试覆盖 bug（如果该 service 已经有 tests 目录）。
- 避免改函数签名/公共返回结构；如果必须改，先找现有响应封装/格式。
- 避免跨服务改动；确实跨服务时，把改动拆成 2 个小 PR（各自可回滚）。
