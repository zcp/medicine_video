### 2.1 仓库现状与启动路径梳理（只读）

- 阅读 Windows 启动脚本，确认本地启动入口：`start-dev.bat` 会执行 `docker-compose -f compose-app.windows.yml up -d` 并打印常用访问地址。
- 阅读 compose 配置，确认服务与端口：
  - live_core_service: 8000
  - media_download_service: 8001
  - user_service: 8002
  - nginx: 8080/8443
  - postgres: 5433（容器内 5432）
  - redis: 6380（容器内 6379）
  - srs: 1935/8080
- 确认后端容器依赖的 env 文件存在：`.env.docker`。
- 阅读 nginx 代理规则，确认关键路由：
  - `/api/core/` 代理到 core_api（live_core_service）的 `/api/v1/`
  - `/api/users/` 代理到 user_service 的 `/api/v1/`
  - `/api/v1/` 代理到 dl_api（media_download_service）的 `/api/v1/`

### 2.2 前端启动方式梳理（只读）

- 确认前端是 Vite 工程：`frontend/package.json` 提供 `npm run dev`。
- 注意到前端 `.env` 当前写的是：`VITE_API_BASE_URL=http://localhost:8083/api/v1`（端口 8083 在 Windows compose 默认端口中不存在）。

## 3. 发现与结论（为什么现在会出问题）

- 后端统一入口（本地）应优先使用：
  - 直接打服务：`http://localhost:8000` / `8001` / `8002`
  - 或走 nginx：`http://localhost:8080/api/core/...`
- 前端 `.env` 使用了 `8083`，这极可能导致前端请求打错地址，从而出现 404/跨域/连接失败等症状。
- 若要对齐生产路径（`/api/core/...`），本地应通过 nginx 的 `8080` 访问；若直接打 live_core_service，则应使用其真实路由前缀（通常是 `/api/v1/...`）。
