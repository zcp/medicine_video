## 📌 核心定位说明

### 1. 本文档的定位

本文档是 `标签管理` 模块的**增量设计**，在 V1「Admin 管词表 + 场次多对多绑定」基础上扩展开播侧能力：

**本次变更类型**:
- 【修改】绑/删场次标签权限：房主（开播者）或 Admin（阶段 1）
- 【修改】`SessionTagsSetRequest.tag_ids`：`0～5`；`replace` 空列表可清空（阶段 1）
- 【新增】`POST /api/v1/content/tags/resolve`：按名解析或创建标签（阶段 2）
- 【新增】`tags` 表溯源字段 `created_by`、`source`（阶段 2）
- 【废弃】无（不废弃任何 V1 路由）

**变更范围**:
- 1 张数据表变更（`tags` 新增 2 字段 + 2 索引；仅阶段 2）
- 3 个 API 接口变更（修改设标签 / 删关联；新增 resolve）
- 1 个 Schema 修改（`SessionTagsSetRequest`；阶段 1 已落地）
- 0 项种子数据修正；1 项迁移脚本（阶段 2）

**分阶段落地**:

| 阶段 | 内容 | 后端状态 |
|------|------|----------|
| 阶段 1 | 房主绑已有标签；`tag_ids` 0～5；`GET /tags?q=` 照旧 | ✅ 已落地 |
| 阶段 2 | `resolve` 自建 + `created_by`/`source` | ✅ 已落地 |

### 2. 本文档的核心原则

- ✅ **增量为主，不替代原有设计**: V1 中所有表、Admin CRUD、公开列表、搜场次保持不变
- ✅ **向后兼容**: 公开读路径与 Admin 写词表不受破坏；权限收窄属缺陷修复
- ✅ **风格一致**: 遵循 V1 命名、响应信封、错误码约定
- ✅ **可独立开发**: 阶段 1 / 阶段 2 可分期交付；阶段 2 不破坏阶段 1 契约
- ✅ **自建与 Admin CRUD 分离**: 用户走 resolve；运营仍走 `/admin/tags`

### 3. 业务价值说明

- **开播自助打标**: 房主可在创建/编辑场次时绑定内容标签，提升发现与筛选质量
- **词库可补全**: 未命中词库时可自建并立刻使用，避免「只能选已有」卡死创作
- **可控治理**: 保留全局 `name` 唯一与 Admin 停用入口，控制词表膨胀与合规风险

## 🔍 变更驱动力与问题分析

### 1. 变更背景

> 说明为什么需要这次变更，是什么触发了这次设计迭代。

| 时间 | 事件 | 影响 |
|------|------|------|
| 2026-06-07 | 《02》V1 设计完成 | Admin 管标签；文档写绑标签需 Admin |
| 2026-06 | 实现与前端 CreateLive 曾接绑标签 | 代码曾放过宽为「任意登录」；与产品预期不一致 |
| 2026-09-01 | 阶段 1 需求落地 | 开播者可绑已有标签，上限 5 |
| 2026-09-01 | 阶段 2 设计定稿 | 匹配不到词库时允许用户自建 |

### 2. 现有问题分析

#### 问题 1：绑标签权限与产品不符（严重程度：P0）— 阶段 1

**现象**:
- V1 文档约定绑标签需 Admin
- 实现曾仅校验「已登录」，任意 `REGULAR` 可改他人场次标签

**影响**:
- **业务影响**: 非房主可篡改他人场次标签
- **技术影响**: 与房间/场次写权限模型不一致
- **用户体验**: 开播者无法合法自助打标（若按文档仅 Admin）

**修改目标**:
- ✅ 写权限 = 场次所属房间 `user_id`（房主/开播者）或 `ADMIN` / `SUPERADMIN`
- ✅ 读列表 / `q` 联想保持公开

#### 问题 2：单场标签数量无产品上限（严重程度：P1）— 阶段 1

**现象**:
- Schema 曾为 `tag_ids` `min_length=1`、`max_length=50`
- 无法清空；数量过大易造成发现噪音

**影响**:
- **业务影响**: 标签过滥降低筛选质量
- **技术影响**: 空列表 `IN ()` 风险需一并规避
- **用户体验**: 无法「全部去掉标签」

**修改目标**:
- ✅ `tag_ids` **0～5**；`replace` + `[]` 清空
- ✅ `append` 后最终关联数 ≤ 5

#### 问题 3：闭集词库无法覆盖主播用语（严重程度：P1）— 阶段 2

**现象**:
- 阶段 1 仅能选已有标签
- 词库未覆盖时前端只能提示「请选已有」

**影响**:
- **业务影响**: 创作被词库卡住
- **技术影响**: 若直接开放 `/admin/tags` 则权限面过大
- **用户体验**: 无法补词

**修改目标**:
- ✅ 提供 resolve/ensure：命中复用，未命中创建
- ✅ 不开放用户调用 `/admin/tags`
- ✅ 可溯源、可 Admin 停用

### 3. 变更决策记录

> 记录本次变更中的关键设计决策，便于后续追溯。

#### 决策 1：文档形态 = 《02》V2 增量

**背景**: 需同时收录阶段 1 已落口径与阶段 2 自建设计。

**方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 新开 21-xxx 独立模块文 | 文件独立 | 表与路由仍属标签模块，编号割裂 | ❌ |
| 重写《02》全文 | 一处看完 | 破坏 V1 基线可追溯性 | ❌ |
| 《02》V2 增量 | 与《01-V2》惯例一致 | 需分阶段标注状态 | ✅ 采用 |

**最终决策**: 增量；文件名 `02-标签管理-V2-增量设计文档.md`。

**影响范围**: 仅文档组织；不新增业务域。

#### 决策 2：阶段 1 权限模型

**背景**: 纠正过宽「任意登录可写」。

**方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A：任意登录可写 | 实现简单 | 可篡改他人场次 | ❌ |
| B：仅 Admin | 与旧文档字面一致 | 开播者无法自助 | ❌ |
| C：房主或 Admin | 与房间/场次写权限一致 | 需查 session→room | ✅ 采用 |

**最终决策**: 方案 C。`owner` 定义为 `LiveRoom.user_id == current_user_id`。

**影响范围**: `POST/DELETE …/sessions/{id}/tags…`

#### 决策 3：阶段 2 自建入口形态

**背景**: 用户需要创建标签但不走 Admin CRUD。

**方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A：`POST /content/tags/resolve` | 职责清晰；绑标签契约不变 | 多一次往返 | ✅ 采用 |
| B：`set_session_tags` 接收 `tag_names` | 前端一次提交 | 接口变胖；难单独安全校验 | ❌ MVP 不做 |
| C：用户直调 `/admin/tags` | 零新接口 | 权限面过大；与运营 CRUD 混用 | ❌ 禁止 |

**最终决策**: 方案 A。

**影响范围**: 新增 resolve；设标签接口仍只收 UUID。

#### 决策 4：未审核标签是否进公开联想

**背景**: 自建后是否立刻可被 `q` 命中。

**最终决策**: MVP 下用户新建后 **`is_active=true` 且立即进入公开 `q` 联想**。`is_verified` 列为可选后期扩展，**不强制首期 DDL**。

**影响范围**: 阶段 2 创建默认值；公开 `GET /tags` 过滤语义不变。

#### 决策 5：重名策略

**背景**: `tags.name` 全局唯一。

**最终决策**: resolve 时 `strip` 后精确匹配；命中返回已有 id（`created=false`）；**不做模糊合并**。软删同名不自动复活。

**影响范围**: `ensure_tag` 实现。

### 1.2 【新增字段】`tags` 表新增 `created_by`、`source`（阶段 2）

**变更原因**: 区分运营词与用户自建，便于治理与审计。

```sql
-- ==========================================================
-- 变更：tags 新增 created_by / source
-- 文件建议：migrations/20260901_tags_user_create_attribution.sql
-- 说明：用户自建标签溯源；不改 name 唯一约束；不 DROP
-- ==========================================================

ALTER TABLE tags
    ADD COLUMN IF NOT EXISTS created_by UUID NULL,
    ADD COLUMN IF NOT EXISTS source VARCHAR(16) NOT NULL DEFAULT 'admin';

COMMENT ON COLUMN tags.created_by IS '创建者 public_id；Admin 手工创建可为 NULL';
COMMENT ON COLUMN tags.source IS '来源：admin=运营创建；user=用户 resolve 创建';

-- 历史数据：视为运营词表
UPDATE tags SET source = 'admin' WHERE source IS NULL OR source = '';

CREATE INDEX IF NOT EXISTS idx_tags_source ON tags(source);
CREATE INDEX IF NOT EXISTS idx_tags_created_by ON tags(created_by);
```

**向后兼容说明**:
- 现有数据: `source='admin'`，`created_by=NULL`
- 现有查询: 不强制过滤 `source`，公开列表行为不变
- 现有 API: `TagItem` 可增加可选字段；旧客户端忽略未知字段

**可选后期（本文不强制）**:

```sql

### 2.2 【新增】`TagResolveRequest` / `TagResolveResponse`（阶段 2）

class TagResolveRequest(BaseModel):
    """解析或创建标签（用户侧）"""
    name: str = Field(..., min_length=1, max_length=80, description="标签名（将 strip）")

    @field_validator("name")
    @classmethod
    def validate_name(cls, v: str) -> str:
        v = v.strip()
        if not v:
            raise ValueError("标签名称不能为空")
        if re.search(r'[<>\'";]', v):
            raise ValueError("标签名称不能包含特殊字符")
        return v


class TagResolveData(BaseModel):
    id: UUID
    name: str
    created: bool = Field(..., description="true=本次新建；false=命中已有")
    source: Optional[str] = None  # admin | user


class TagResolveResponse(BaseModel):
    code: int = 200
    message: str = "success"
    data: TagResolveData
    timestamp: datetime
```

## 3. API 接口变更设计

### 3.1 【修改】设置场次标签关联（阶段 1，已落地）

**Endpoint**: `POST /api/v1/content/sessions/{session_id}/tags`

**描述**: 为指定场次设置标签（replace / append）

**认证**: JWT

**变更说明**:
- **变更前**: 写权限口径过宽（曾等价于「已登录即可」）或文档写仅 Admin
- **变更后**: 场次→房间，**房主或 Admin**；`tag_ids` 长度 **0～5**

**权限**:
1. 查 `live_sessions`；不存在 → 404（2001）
2. 查所属 `live_rooms`；不存在 → 404
3. `role in {ADMIN, SUPERADMIN}` **或** `room.user_id == current_user_id`；否则 403（3003）

**请求体**:
```json
{
  "tag_ids": ["uuid-1", "uuid-2"],
  "mode": "replace"
}
```

- `tag_ids` 允许 `[]`（`replace` = 清空）
- `append` 时与已有去重后总数不得超过 5，否则 400（4001）

**向后兼容**:
- Admin 调用：兼容
- 非房主 REGULAR 写他人场次：**不兼容**（缺陷修复）
- 一次传 >5 个 id：422

### 3.2 【修改】删除场次标签关联（阶段 1，已落地）

**Endpoint**: `DELETE /api/v1/content/sessions/{session_id}/tags/{tag_id}`

**变更说明**: 权限与 3.1 对齐（房主或 Admin）。

### 3.3 【保持】公开标签列表 / 联想

**Endpoint**: `GET /api/v1/content/tags?q=&search_type=`

**说明**: 过滤语义不变（非 Admin 仅 `is_active=true`）。阶段 2 用户新建默认 active，可被联想命中。

### 3.4 【新增】解析或创建标签（阶段 2）

**Endpoint**: `POST /api/v1/content/tags/resolve`

**描述**: 按名称确保标签存在：命中返回已有；未命中则创建（`source=user`）

**认证**: JWT

**权限（MVP）**:
- `ADMIN` / `SUPERADMIN`：允许
- `REGULAR`：允许（与开播自建一致）；**不**要求携带 `session_id`
- 后期可选收紧（`can_stream` / 某房 owner）——首期不做

**请求参数**（Body）:
- `name` (string, required): 标签名，1～80，strip 后非空

**成功响应** (`200 OK`):
```json
{
  "code": 200,
  "message": "success",
  "data": {
    "id": "uuid",
    "name": "腹腔镜肝切除",
    "created": true,
    "source": "user"
  },
  "timestamp": "2026-09-01T13:00:00Z"
}
```

**执行流程**:

1. **接收请求**: API 接收 POST，解析 Body  
2. **JWT验证**: `Depends(get_current_user)`  
3. **权限检查**: 已登录（MVP）  
4. **Pydantic校验**: `TagResolveRequest`  
5. **内容安全**: `check_scene_fields(scene=tag_name, field=name)`；block → **422 / 2005**（`ContentSafetyBlockedException`）；服务异常 → **422 / 2004**  
   - **范围**: 仅本 Endpoint（用户 resolve / 自建）。`POST /admin/tags` 运营手工创建本期**不强制**同一校验（词表与运营可控）；若需对齐可另开任务  
   - **策略档位**: 见《[12-13](./12-13-内容安全分层策略-V1-增量设计文档.md)》——`tag_name` 归 **A 档**（展示型 UGC，同 `room_title`）  
   - **引擎登记**: 见《[12](./12-全局内容安全与审核-后端设计文档.md)》§1.4.3 / §4.2.6  
6. **业务逻辑** `ensure_tag`:  
   - 精确查 `name`  
   - 命中且 `is_active=true` → `created=false`  
   - 命中且 `is_active=false` → 400「标签不可用」（不自动复活）  
   - 未命中 → INSERT（`source=user`, `created_by=user_id`, `is_active=true`）→ `created=true`  
   - 并发唯一冲突 → 再查返回已有（幂等）  
7. **提交事务**: `await db.commit()`  
8. **返回响应**: `TagResolveResponse`

**HTTP状态码**:
- `200 OK`: 成功（含复用）
- `401 Unauthorized`: JWT 无效（3001）
- `400 Bad Request`: 参数错误 / 软删占用名（4001）
- `422 Unprocessable Entity`: 内容安全拦截（2005）或内容安全服务异常（2004）
- `403 Forbidden`: 权限不足（若后期收紧，3003）
- `500 Internal Server Error`: 内部错误（1002）

**与绑标签配合**:
```
resolve(name) → id → 本地 chip（≤5）→ POST …/sessions/{id}/tags { tag_ids, mode: replace }
```

### 3.5 【保持】Admin 标签 CRUD

路径与权限不变。阶段 2 Admin 创建应写 `source='admin'`，`created_by` 可记当前 Admin 或 NULL。

### 3.6 前端对接契约（非本仓实现）

| 能力 | 约定 |
|------|------|
| 阶段 1 | CreateLive 展示标签；`#`/空格 → chip；只提交已有 UUID；最多 5 |
| 阶段 1 | 匹配不到：提示选已有（阶段 2 上线前） |
| 阶段 2 | 未匹配 →「创建并使用」→ `POST /content/tags/resolve` → chip 用返回 id |
| 禁止 | 本地伪造 UUID；普通用户调 `/admin/tags` |

## 4. 执行流程变更说明

### 4.1 设置场次标签（阶段 1 后）

```
1. API 路由接收 POST
   → 2. JWT 验证
   → 3. 【修改】session → room → 房主或 Admin
   → 4. Pydantic（tag_ids 0～5）
   → 5. 标签存在性校验（空列表跳过）
   → 6. 【修改】append 时校验最终数量 ≤ 5
   → 7. CRUD set_session_tags（replace 空列表 = 清空）
   → 8. 提交事务
   → 9. 返回 JSON
```

### 4.2 开播侧打标签 + 自建（阶段 1+2 串联）

```
1. GET /content/tags?q= 联想
   → 2. 确认新词 → POST /content/tags/resolve
   → 3. chip 收集 UUID（≤5）
   → 4. POST …/sessions/{id}/tags  mode=replace
```
