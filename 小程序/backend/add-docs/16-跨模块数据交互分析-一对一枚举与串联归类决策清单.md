## 0. 主流视频平台对齐方针（拍板总口径）

> **前提**：总设计文案可与现网代码不一致，但敲定了总体方针——我们是医学直播软件，同时**希望数据处理方案致敬抖音、哔哩哔哩等大型视频平台**。本节先定「跟谁学什么」；细节按串在 §2.6 逐条给行动清单。

### 0.1 学什么 / 不学什么

| 维度 | 抖音 / B站类主流做法（抽象） | 我们对齐结论 | 医学场景可加严处 |
|------|------------------------------|--------------|------------------|
| 账号注销 | 软删账号；**有活跃付费会员则挡注销**；清「个人私货」；公开互动文案匿名化 | **对齐** | 医疗内容可要求更长冷却 / 运营复核后再硬处置房间 |
| 封禁 / 撤权 | **即时吊销会话**；**不自动删内容、不自动关房断流**（运营另处置） | **对齐**（《14-V2》已定 P12 不做） | 合规下架走运营 SOP，不绑在用户管理接口 |
| 创作者内容（房/视频） | 删内容 = **关系行级联清**；媒资文件多为 **异步 GC / 生命周期**，不与库行同步硬删 | **对齐** | 回放含敏感医学信息时可走「先不可见再 GC」 |
| 个人行为数据 | 注销时 **物理清或不可恢复隐藏**（收藏/历史/关注/订阅/偏好） | **对齐** | — |
| 公开 UGC（留言等） | 活跃账号评论展示**当前**昵称/头像；注销后正文保留、作者「账号已注销」占位 | **对齐**（活跃读当前见 07-V4；注销占位见 16-D3） | — |
| 商家 / 品牌下架 | **软下架**：C 端不显、不可售；关系行可留 | **对齐** | 药品/器械货架须随品牌不可售 |
| 分类 / UP 主下架 | 发现侧过滤；历史挂靠可残但列表不推 | **对齐（可能要做档）** | — |
| 两类「订阅」 | 付费会员 ≠ 内容追更订阅，**不做数据联动** | **对齐**（P49 不做） | — |

### 0.2 五条硬规则（写进后续包设计时不得反向）

| # | 硬规则 | 对应主流直觉 |
|---|--------|--------------|
| R1 | **有活跃会员 → 禁止注销**（先解约/到期再注销） | B站大会员 / 抖音付费会员挡注销 |
| R2 | **封禁/撤开播权 → 只吊销会话 + 能力开关；不自动删房/关房/断流** | 平台封号 ≠ 一键清空作品库 |
| R3 | **注销 → 清个人私货；公开留言匿名化；旧房默认「留实体、失管理权」+ 冷却后再运营处置（不与注销同事务硬删万物）** | 私货清、作品可冷处理 |
| R4 | **删房/删场次 → 关系级联必闭合（含内容订阅）；对象存储文件走异步回收，不阻塞删库** | 删稿清关系；CDN/对象存储后置 GC |
| R5 | **品牌软删 → C 端挂靠/商品一律不可见不可售；成员关系可留库** | 商家下架语义 |

## 方法（先别跳到大链）

1. **先一对一**：只看「A 变了，B 要不要定规矩」  
2. **再串联**：多个一对一若共用同一个中间点（如都挂在「旧房」上），才串成一条链  
3. **最后归类**：

| 分类 | 含义 |
|------|------|
| **要做** | 现在就要想清楚 / 排进近期 |
| **将要做** | 产品已定要做，但**不是现在**；现网可暂无，需另开设计时再动 |
| **可能要做** | 有风险或体验问题，看痛点再决定做不做 |
| **不做** | 明确不做，或只是易混/弱绑定 |

## 2. 串联：哪些一对一能串起来？

**串联规则（表用）**：一对一 X 的 **B** = 下一对 Y 的 **A**（或共用同一实体），则 X→Y 可串。

| **A** | 账号注销/封禁/撤开播权 | ①P01 **挡注销** → ②P02 **留房失管**（封禁不删房）→ ③仅显式删房才走房下孩子（引用链 C） | P01, P02, P20–P23, P25, P26a–c, P27, P28, P33；经 P23 再接 P24, P29–P32 | ③与链 C 共用房/场次孩子；主流对照见 §2.6.1 | **要做**（包1） |
