# 代码风格速记（尽量“像原作者写的”）

> 下面是从现有代码抽出来的习惯用法，修 bug 时尽量贴近。

## 1. FastAPI 组织方式

- `app/main.py` 负责：创建 `FastAPI()`、配置 CORS、中间件、`include_router(api_router, prefix=settings.API_V1_STR)`。
- 路由聚合通常在 `app/api/v1/api.py` 里做 `include_router(..., prefix=..., tags=[...])`。
- live_core_service 在 `FastAPI(..., redirect_slashes=False)` 上做了明确设置（避免 307）。新增路由时尽量不要引入“依赖 slash 重定向”的路径。

## 2. 配置读取

- 有的服务用 `Settings()` 实例（live_core_service），有的用 `settings` 单例（media_download_service/users）。
- 修 bug 时不要把“配置模式”统一化重构；只在当前 service 内保持一致。

## 3. 数据库与依赖注入

- 通常有 `app/database.py` 定义 `engine`、`SessionLocal`、`get_db()`。
- endpoints/service 层函数多用 `db: Session = Depends(get_db)` 或从 deps 引入。

## 4. 响应与异常

- 先找当前 service 是否有统一响应封装（例如 `app/core/response.py`）或统一的 JSONResponse 用法。
- 修 bug 时：优先复用已有的 `HTTPException` / `JSONResponse` 格式；不要自创新的响应结构。

## 5. 日志

- users 服务有日志脱敏：`setup_sanitized_logging()`。
- 需要加日志时：优先使用现有 logging 工具或模块内 logger；不要随手 print（除非仓库已普遍这样做且只是临时诊断）。

## 6. 最小改动偏好

- 不改 public API 结构、不改数据库 schema（除非 bug 明确指向 schema）。
- 能补测试就补同目录风格的测试：看 `tests/conftest.py` 和现有用例写法。
