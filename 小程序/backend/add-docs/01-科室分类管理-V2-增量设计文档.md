## 🔍 变更驱动力与问题分析

### 1. 变更背景

| 时间 | 事件 | 影响 |
|------|------|------|
| 2026-06-07 | V1 设计文档完成 | 15 个扁平分类，无层级 |
| 2026-06-09 | 分析 CSV 专家数据 | 发现 V1 种子分类仅覆盖 30.7% 的专家科室 |
| 2026-06-09 | 本次变更 | 引入层级分类，重建种子数据 |

### 2. 现有问题分析

#### 问题 1：种子分类覆盖率严重不足（严重程度：P0）

**现象**:
- V1 预置 15 个种子分类（普通外科、神经外科、心内科 等）
- CSV 中 387 名专家分布在 42 种不同科室
- V1 分类仅能覆盖 119/387 = **30.7%** 的专家

**影响**:
- **业务影响**: 大量专家无法按科室归类，用户按科室筛选时找不到对应专家
- **数据脱节**: CSV 中"妇科"（26人）、"器官移植科"（19人）、"生殖医学中心"（16人）等高频科室完全缺失
- **粒度不匹配**: CSV 科室是医院实际挂牌名（"胆胰外科"、"肝外科"），V1 分类是笼统学科名（"普通外科"）

**修改目标**:
- ✅ 从 CSV 提取真实科室，建立 100% 覆盖的分类体系
- ✅ 通过层级分类解决"粒度不匹配"问题（大科 → 小科）

#### 问题 2：扁平分类无法表达科室层级关系（严重程度：P1）

**现象**:
- V1 的 `categories` 表没有 `parent_id` 字段，所有分类平级
- 真实医院科室有天然层级：普通外科 → {胆胰外科, 肝外科, 胃肠外科, 乳腺外科, 甲状腺外科}
- 直播间关联"普通外科"时，无法自动包含其下子科室的内容

**影响**:
- **筛选粒度二选一**: 要么太粗（"普通外科"包含太多不相关内容），要么太细（用户需要逐个选择子科室）
- **用户体验差**: 首页分类 Tab 无法展示层级导航

**修改目标**:
- ✅ `categories` 表支持 `parent_id` 自引用，实现两级分类
- ✅ 直播间关联大类时，查询自动包含子类内容

### 3. 变更决策记录

#### 决策 1：分类层级深度

**背景**: 医院科室理论上可以无限细分（外科 → 普通外科 → 胃肠外科 → 胃肠外科一科），需要确定层级深度。

**方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 一级（扁平，V1 现状） | 简单 | 覆盖率低，粒度不匹配 | ❌ 放弃 |
| 两级（大科 → 小科） | 平衡简洁与精确 | 部分科室归属有争议 | ✅ 采用 |
| 三级及以上 | 最精确 | 过度复杂，前端展示困难 | ❌ 放弃 |

**最终决策**: 采用**两级分类**。第一级为"大科"（如普通外科、骨科），第二级为"小科"（如胆胰外科、脊柱外科）。直播间关联到第一级，专家关联到第二级。

**影响范围**: `categories` 表新增 `parent_id` 字段，前端分类 Tab 需支持层级展示。

#### 决策 2：种子数据来源

**背景**: V1 的 15 个种子分类是手动编写的，与 CSV 真实数据脱节。

**方案对比**:

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 保持 V1 手动编写 | 简单 | 覆盖率仅 30.7% | ❌ 放弃 |
| 直接用 CSV 原始值 | 100% 覆盖 | 太细碎（"胃肠外科一/二/三科"） | ❌ 放弃 |
| CSV 归类 + 合并 | 真实且不细碎 | 需要人工归类映射 | ✅ 采用 |

**最终决策**: 从 CSV 提取 42 个原始科室名，归类合并为两级分类体系。第一级约 15-20 个大科，第二级约 40-50 个小科。

**影响范围**: `seed.py` 中 `CATEGORIES_DATA` 需要完全重写。

## 1. 数据库变更设计（DDL）

### 1.1 【新增字段】`categories` 表新增 `parent_id`

**变更原因**: 支持两级分类层级，`parent_id` 指向父分类，`NULL` 表示一级分类。

```sql
-- ==========================================================
-- 变更：categories 新增 parent_id 字段
-- 说明：支持两级分类层级，parent_id=NULL 表示一级分类
-- ==========================================================

-- 新增字段（nullable，现有记录默认 NULL = 一级分类）
ALTER TABLE categories
    ADD COLUMN parent_id UUID NULL;

-- 外键约束（自引用，SET NULL 保护：删除父分类时子分类变为一级分类）
ALTER TABLE categories
    ADD CONSTRAINT fk_categories_parent
    FOREIGN KEY (parent_id) REFERENCES categories(id) ON DELETE SET NULL;

-- 索引：按 parent_id 查询子分类
CREATE INDEX idx_categories_parent_id ON categories(parent_id);

-- 复合索引：按 parent_id + sort_order 排序查询
CREATE INDEX idx_categories_parent_sort ON categories(parent_id, sort_order);

-- 字段注释
COMMENT ON COLUMN categories.parent_id IS '父分类ID（NULL=一级分类，非NULL=二级分类指向其父级）';
```

**向后兼容说明**:
- 现有数据: `parent_id` 默认 `NULL`，所有现有记录自动成为"一级分类"，行为不变
- 现有查询: 现有查询不涉及 `parent_id`，不受影响
- 现有 API: 现有 API 响应新增 `parent_id` 字段（值为 `NULL`），对调用方透明

### 1.2 约束说明

- **不加 CHECK 约束限制层级深度**: 应用层控制只允许两级（创建时校验 `parent_id` 指向的记录本身 `parent_id IS NULL`）
- **ON DELETE SET NULL**: 删除父分类时，子分类自动变为一级分类（而非级联删除），保护数据安全
- **name UNIQUE 约束不变**: 分类名称仍然全局唯一（跨层级），避免歧义

### 3.2 【新增】获取子分类列表

**Endpoint**: `GET /api/v1/content/categories/{category_id}/children`

**描述**: 获取指定一级分类下的所有子分类

**认证**: 公开访问（Public）

**路径参数**:
- `category_id` (UUID, required): 父分类ID

**成功响应** (`200 OK`):
```json
{
  "code": 200,
  "message": "success",
  "data": {
    "items": [
      {
        "id": "uuid-2",
        "name": "胆胰外科",
        "slug": "hepatobiliary-pancreatic",
        "parent_id": "uuid-1",
        "sort_order": 1,
        "is_active": true,
        "created_at": "2026-01-01T00:00:00Z",
        "updated_at": "2026-01-01T00:00:00Z"
      }
    ]
  },
  "timestamp": "2026-06-09T10:00:00Z"
}
```

**失败响应** (`404 Not Found`):
```json
{
  "code": 2001,
  "message": "父分类不存在",
  "data": null,
  "timestamp": "2026-06-09T10:00:00Z"
}
```

**执行流程**:

1. **接收请求**: API路由接收GET请求，解析路径参数 `category_id`
2. **参数校验**: 校验 `category_id` 是否为有效UUID
3. **父分类存在性检查**: 查询父分类是否存在，若不存在抛出 404
4. **构建查询**: `SELECT * FROM categories WHERE parent_id = :category_id AND is_active = true ORDER BY sort_order ASC`
5. **执行查询**: 异步执行数据库查询
6. **序列化响应**: 使用 `CategoryItem` Schema序列化
7. **返回响应**: 返回统一格式JSON

**HTTP状态码**:
- `200 OK`: 查询成功
- `404 Not Found`: 父分类不存在（code=2001）

### 3.3 【修改】创建分类 — 请求体增加 parent_id

**Endpoint**: `POST /api/v1/admin/categories`

**变更说明**: 请求体新增可选字段 `parent_id`

**新增校验逻辑**（Service 层）:
1. `parent_id` 不能指向自身
2. `parent_id` 指向的父分类必须存在
3. 父分类的 `parent_id` 必须为 `NULL`（只允许两级，不能创建三级分类）
4. 同一父分类下的子分类 `name` 不能重复

**Endpoint**: `GET /api/v1/admin/categories`

**变更说明**: 新增查询参数 `parent_id`，支持按父分类过滤子分类列表。

**新增请求参数**:

## 8. 迁移脚本

```sql
-- ==========================================================
-- 迁移脚本：categories 表新增 parent_id 层级字段
-- 文件：live_core_service/migrations/20260609_add_parent_id_to_categories.sql
-- 执行方式：
--   docker exec live-streaming-saas-v2-main-live_core_service-1 \
--     psql -U postgres -d live_core \
--     -f /app/migrations/20260609_add_parent_id_to_categories.sql
-- ==========================================================

-- 步骤1：新增 parent_id 字段（nullable，现有记录默认 NULL）
ALTER TABLE categories
    ADD COLUMN IF NOT EXISTS parent_id UUID NULL;

-- 步骤2：新增外键约束（自引用，SET NULL 保护）
DO $$
BEGIN
    IF NOT EXISTS (
        SELECT 1 FROM pg_constraint WHERE conname = 'fk_categories_parent'
    ) THEN
        ALTER TABLE categories
            ADD CONSTRAINT fk_categories_parent
            FOREIGN KEY (parent_id) REFERENCES categories(id) ON DELETE SET NULL;
    END IF;
END $$;

-- 步骤3：新增索引
CREATE INDEX IF NOT EXISTS idx_categories_parent_id
    ON categories(parent_id);

CREATE INDEX IF NOT EXISTS idx_categories_parent_sort
    ON categories(parent_id, sort_order);

-- 步骤4：字段注释
COMMENT ON COLUMN categories.parent_id
    IS '父分类ID（NULL=一级分类，非NULL=二级分类指向其父级）';

-- 验证
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_name = 'categories' AND column_name = 'parent_id';
```
