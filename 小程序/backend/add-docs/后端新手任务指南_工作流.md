# 后端新手任务指南（工作流｜从 0 到能修一个 bug）

适用场景：你第一次做后端；目标是在**不大改代码**的前提下，能把一个 bug 从“复现→定位→最小修复→验证→合并”完整闭环。

> 本仓库后端是多服务 FastAPI + Docker Compose：
> - live_core_service（8000）
> - media_download_service（8001）
> - user_service（8002）
> - nginx 代理（8080/8443）+ postgres（5433）+ redis（6380）+ srs（1935/8080）

## 0. 你需要准备什么（先不要改代码）

### 必装

- Docker Desktop（Windows，建议启用 WSL2 后端）
- Git
- VS Code（你现在已经有）

### 推荐（但不是必须）

- 一个可用的终端（PowerShell 即可）
- Python 本地环境（可选；这个仓库优先走 Docker，不强制你本机装依赖）

---

## 1. 第一次把环境跑起来（从这里开始）

### 1.1 阅读并按仓库约定启动

- 开发环境说明：见根目录的 [`README-Windows开发环境.md`](../README-Windows开发环境.md)
- Windows 一键启动（推荐）：
  - 启动：[`start-dev.bat`](../start-dev.bat)
  - 停止：[`stop-dev.bat`](../stop-dev.bat)
  - 仅重建代码（保留 DB）：[`rebuild.bat`](../rebuild.bat) `-c`
  - 完整重建（会更慢）：[`rebuild.bat`](../rebuild.bat) `-f`

> 你现在不需要理解脚本里每一行，只要能把服务拉起来。

### 1.2 验证服务是否启动成功

在浏览器打开（或用 curl）：

- `http://localhost:8000/`（live_core_service 根路径）
- `http://localhost:8001/`（media_download_service 根路径）
- `http://localhost:8002/`（user_service 根路径）

如果你想通过 nginx 走统一入口：

- `http://localhost:8080/`（nginx）

> 注意：生产域名上通常是 `https://.../api/core/...` 走 nginx 转发。

### 1.3 看日志（遇到启动失败时的第一动作）

- 全部服务日志：
  - `docker-compose -f compose-app.windows.yml logs -f`（文件：[`compose-app.windows.yml`](../compose-app.windows.yml)）
- 单个服务日志：
  - `docker-compose -f compose-app.windows.yml logs -f live_core_service`
  - `docker-compose -f compose-app.windows.yml logs -f user_service`

## 2. 搞清楚“请求会进哪个后端服务”（非常关键）

这个项目是**nginx 统一代理**，不同前缀会转给不同服务。

你只需要记住这两个最常用的：

- `/api/core/` → live_core_service（最终转到 `/api/v1/`）
- `/api/users/` → user_service（最终转到 `/api/v1/`）

nginx 规则在：[`nginx/nginx.conf`](../nginx/nginx.conf)

举例：

- 生产请求：`/api/core/users/me/favorites`
- 实际到 core 服务：`/api/v1/users/me/favorites`

> 所以你在后端代码里搜路由时，要搜 `/api/v1/...` 形式。

## 3. 你接到一个 bug 后，按这个顺序做（最小改动）

### 3.1 复现（必须能稳定复现）

- 记录：
  - 请求 URL
  - 方法（GET/POST/DELETE…）
  - 入参（query/body）
  - 期望结果 vs 实际结果
  - 返回状态码（404/500/422…）

建议把每个 bug 记录到：[`add-docs/定位bug与最小改动修复流程.md`](定位bug与最小改动修复流程.md)

### 3.2 定位到具体服务与路由文件

- 如果是 `/api/core/...`：先去 [`backend/live_core_service/app/api/v1/api.py`](../backend/live_core_service/app/api/v1/api.py) 看路由聚合，再去 [`backend/live_core_service/app/api/v1/endpoints/`](../backend/live_core_service/app/api/v1/endpoints/) 找具体函数
- 如果是 `/api/users/...`：去 [`backend/users/app/api/v1/api.py`](../backend/users/app/api/v1/api.py) 和 [`backend/users/app/api/v1/endpoints/`](../backend/users/app/api/v1/endpoints/) 找具体函数

定位技巧（VS Code 全局搜索）：

- 直接搜路径片段：例如搜 `"/users/me/favorites"`
- 直接搜 router 装饰器：例如 `@router.get("/users/me/favorites")`

### 3.3 看清楚是哪一层报错（Endpoint / Service / CRUD / DB）

常见结构：

- endpoints：参数解析、Depends、返回格式
- services：业务逻辑编排
- crud：数据库读写
- models：表结构

你只要顺着调用链找到**第一处抛异常的地方**。

### 3.4 定一个“最小修复策略”（不要顺手重构）

优先级建议：

1) 修边界条件（None/空列表/不存在记录/权限不足）
2) 修错误的查询条件/过滤
3) 修错误的异常捕获（把本该 404/403 的错变成 500）

避免：

- 改公共响应结构
- 改一堆文件还说不清为什么
- 全局格式化/重命名

### 3.5 加一个最小验证（优先用已有 tests）

仓库里很多服务自带 `tests/`。

- 如果有相近测试：照着写一个“复现 bug 的用例”，然后修到它通过
- 如果暂时没有测试：至少写清楚你怎么手工验证（curl/Swagger）

## 4. 两人分工协作与合并（避免冲突）

建议你们按“服务/模块”拆：

- 一个人负责：user_behavior（收藏/观看历史/订阅）
- 另一个人负责：rooms（列表/删除）+ tabs（公开可见方案）

分支命名建议：

- `bugfix/live-core-favorites-500`
- `bugfix/live-core-delete-room-500`

合并前 checklist：

- 能复现 → 能修复 → 能验证（至少一条明确验证路径）
- 只改必要行，没有“顺手重构”
- 跑过相关服务的启动，至少不报 import error

---

## 5. 你下一步该做什么（最短路径）

1) 安装并启动 Docker Desktop
2) 在仓库根目录运行 [`start-dev.bat`](../start-dev.bat)
3) 打开 `http://localhost:8000/docs`（或根路径）确认 core 服务活着
4) 从你们问题清单里挑一个“可直接定位路由”的（例如 `GET /users/me/favorites`）
5) 按第 3 节流程做：复现→定位→最小修复→验证

---

## 6. 常见卡点（新手友好）

- **404**：优先检查 nginx 代理前缀是否正确（`/api/core/` vs `/api/users/`），以及后端是否确实有对应路由
- **500**：99% 是后端抛了未处理异常；去对应服务日志找 traceback（比前端“内部服务器错误”有用）
- **启动慢/端口占用**：Windows 本机常见，按 [`README-Windows开发环境.md`](../README-Windows开发环境.md) 的建议排查
