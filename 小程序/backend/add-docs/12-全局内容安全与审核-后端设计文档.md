## 📌 核心定位说明

### 1. 本文档的定位

本文档专注于**全局内容安全与审核（Content Safety）**的完整后端实现设计，包括：

**包含模块**:
- **Content_Safety_Rules（内容安全规则）**: 按场景/字段/匹配类型维护拦截规则，供规则引擎加载
- **Content_Safety_Logs（内容安全审计日志）**: 记录每次校验的决策、命中规则与输入摘要
- **Content_Safety_Service（统一校验服务）**: 供各业务 Service 在写库前调用，不对外暴露独立写入主路径

**模块范围**:
- 2张数据表（`content_safety_rules`、`content_safety_logs`）
- 4个管理端 API 接口（规则列表/创建/更新/启停、审计日志列表；**无 DELETE**，停用走 `enabled=false`）
- 7 个**文本**写入场景接入规则引擎（nickname / message / room_title / room_description / room_tab / search_query / **tag_name**）
- **图片内容审核**（头像等）：上传时调用第三方 API，与文本规则引擎分离（§1.4.6，**当前仅占位**）
- 完整的 Pydantic Schemas 定义
- 完整的数据库 DDL 及索引设计
- 详细的执行流程说明（8-10 步）

### 2. 本文档的核心特点

- ✅ **内容完整性**: 包含内容安全模块全部后端设计，以及各业务场景的接入约定
- ✅ **独立可开发**: 规则引擎、审计、管理端可独立开发；业务接入按增量文档执行
- ✅ **与 v6 主文档保持一致**: 遵循统一响应、JWT、分层架构规范
- ✅ **上游依据**: 所有内容安全增量文档（06/07/10/搜索等）以本文档为唯一规则口径

### 3. 业务价值说明

**Content_Safety_Rules（内容安全规则）**:
- 对所有高风险文本输入统一规则口径，避免各业务模块重复实现过滤逻辑
- live_core 场景（留言/房间/搜索等）支持运营通过 **live_core 管理端 API** 维护敏感词、广告词
- nickname 文本规则在 **users 库**独立维护（seed 初始化，见 §1.6）；**头像图片违规**走 §1.4.6 上传审核，不走 `image_meta` / URL 白名单

**Content_Safety_Logs（内容安全审计日志）**:
- 记录 **warn / block** 决策及命中规则；纯 allow（未命中任何规则）**不写日志**

**Content_Safety_Service（统一校验服务）**:
- 业务 API 写库前统一校验；命中 block 拒绝写入；warn 允许写入并记日志
- 不新增「先调安全 API、再调业务 API」的两段式主流程

## 📖 文档规范说明

### 统一响应结构

所有 API 接口遵循统一的 JSON 响应格式：

```json
{
  "code": 200,
  "message": "success",
  "data": { ... },
  "timestamp": "2026-07-03T10:00:00Z"
}
```

### 统一分页格式

分页接口使用统一的分页响应结构：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "total": 100,
    "page": 1,
    "page_size": 20,
    "items": [ ... ]
  },
  "timestamp": "2026-07-03T10:00:00Z"
}
```

### 统一认证规范

本模块 API 接口使用以下认证级别：

- **业务写入校验（Internal）**: 不对外暴露独立 HTTP 入口，由各业务 Service 内部调用 `check_content_safety()`
- **管理员权限（ADMIN）**: 规则维护（GET/POST/PATCH，停用 `enabled=false`）、审计日志查询，需要 JWT 且角色为 ADMIN / SUPERADMIN

### JWT Token 格式说明

```json
{
  "user_id": "uuid-string",
  "username": "admin",
  "role": "ADMIN",
  "exp": 1717756800
}
```

> **重要说明**: JWT Payload 中用户标识字段为 `user_id`（非 `sub`），所有需要获取当前用户的接口均通过 `user_id` 字段提取用户身份。

### 业务状态码

| 状态码 | 说明 | 使用场景 |
|--------|------|----------|
| `200` | 成功 | 所有成功响应 |
| `1002` | 数据库错误 | 数据库操作异常 |
| `2001` | 资源不存在 | 规则 ID 不存在 |
| `2004` | 内容安全服务异常 | 规则加载/引擎故障，**写入型接口**默认拒绝（全项目其他模块的通用 2004 语义不变，内容安全场景专指此项） |
| `2005` | 内容违规 | 命中 block 规则 |
| `2006` | 内容低风险提醒 | 命中 warn 规则（写入审计日志 `reason_code`，HTTP 仍返回 200） |
| `3001` | 未授权 | JWT Token 缺失或无效 |
| `3002` | 权限不足 | 非管理员访问管理端接口 |
| `4001` | 参数校验失败 | 请求参数不符合 Schema 规范 |

## 🎯 设计要点与约定

### 1.1 数据库设计规范

1. **UUID 主键**: 所有表使用 `UUID` 类型作为主键
2. **时间戳**: 所有时间字段使用 `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP`
3. **外键约束**: users 库中 `created_by` 使用 `CONSTRAINT fk_content_safety_rules_created_by`
4. **软删除**: 规则表使用 `enabled` 字段启停，不做物理软删除；日志表仅追加写入
5. **索引策略**: `(scene, enabled, priority)` 加速规则加载；日志按 scene/user/resource 建索引
6. **字段注释**: 所有表和关键字段使用 `COMMENT ON` 添加中文注释

### 1.2 API 设计规范

1. **HTTP 方法**: GET（查询）、POST（创建）、PATCH（更新）
2. **URL 路径**: 管理端使用 `/api/v1/admin/content-safety/{resource}` 格式
3. **认证策略**: 管理端全部需要 ADMIN 权限；业务校验仅在 Service 层内部调用
4. **执行流程**: 每个管理端 API 包含 8-10 步详细执行流程说明（见 §3）

### 1.3 软删除策略

| 表名 | 策略 | 说明 |
|------|------|------|
| `content_safety_rules` | `enabled` 字段 | 停用规则不参与匹配，不物理删除 |
| `content_safety_logs` | 仅追加 | 审计日志不可修改、不可删除 |

### 1.4 内容安全校验规范

#### 1.4.1 接入原则

- 现有业务 API 保持职责不变，在 **Service 层写库前** 调用统一校验
- 不新增独立安全业务 API 作为前端写入主路径
- 同一请求涉及多个文本 scene 时（如 room_tab 多字段），**分 scene 或分字段**分别调用
- **头像图片**不在 `check_content_safety()` 文本规则中校验，见 §1.4.6
- 发布型写入在安全服务异常时 **默认拒绝**（422 + code=2004）

#### 1.4.2 全场景统一检测口径

**每个文本字段**写库前均须配置并执行以下四类检测：

| 检测类型 | `match_type` | 说明 | 默认 action |
|---|---|---|---|
| 外链 | `url` | http、www、短链、跳转域 | block |
| 联系方式 | `contact` | 手机号、QQ、微信号等 | block |
| 广告引流 | `fraud` | 加V、私聊、返利、兼职、刷单等 | block |
| 敏感词 | `keyword` | 运营维护词表 | block |

> **已废弃（V2.2 起不再使用）**：`avatar` 场景的 `image_meta` / URL 前缀白名单——无法识别图片内容本身，已从设计移除。

**图片类 UGC（头像等）**须在上传落盘前调用 **§1.4.6 图片内容审核 API**（微信/云厂商，当前占位）。

扩展类型（按需由运营添加）：`regex`、`html`、`political`、`porn`、`gambling`。

#### 1.4.4 默认规则生成策略

> **V2.2 基线 seed**（当前代码）：见下表 29 / 4 条。**医学合规词库上线后**由《13》替换为 224 + 64 条，priority 以《13》§2 为准；迁移步骤见《13》§4.7。

规则按 **场景 × 字段 × 检测类型** 矩阵自动生成，命名规范 `{scene}-{target_field}-{检测类型标签}`：

```
priority 10 → url
priority 12 → keyword（敏感词）
priority 20 → contact
priority 30 → fraud
```

**分库 seed 范围（V2.2 基线，已被《13》取代）**：

| 库 / 服务 | seed 场景 | 默认规则数 | 维护方式 |
|---|---|---:|---|
| live_core_test | message / room_title / room_description / room_tab / search_query / **tag_name** | **29**（基线）+ `tag_name` 随矩阵/医学 seed 扩展 | 管理端 API（§3） |
| users_service_test | nickname（nickname + bio 文本，V2.3 设计；V2.2 代码仅 nickname 4 条） | **4**（基线） / **64**（《13》） | seed 初始化 + 后续 P1 扩展 |

live_core 29 条 = 7 个文本字段 × 4 类 block 规则（28）+ 1 条 search warn 示例。users V2.2 基线 4 条 = nickname 四类 block；**《13》** 为 nickname + bio 各 32 类 = 64 条。**不含** avatar / `image_meta` 规则。

敏感词初始 pattern 为开发示例词；**live_core 场景**生产词表由运营通过管理端维护；**nickname** 词表暂由 users 库 seed/常量维护（见 §1.6）。

#### 1.4.5 决策与优先级

| 决策 | 行为 | HTTP | code |
|---|---|---|---|
| `block` | 拒绝写入 | 422 | 2005 |
| `warn` | 允许写入，写审计日志（reason_code=2006） | 200 | 200 |
| `allow` | 正常写入，**不写审计日志** | 200 | 200 |

同一字段命中多条规则：取 **priority 数值最小** 的规则集，再取 **action 最严重、severity 最高** 的决策。

#### 1.4.6 图片内容审核（与文本规则引擎分离）

**定位**：识别**图片内容**是否违规（色情、暴恐、政治敏感等）。在**文件落盘前**调用第三方 API；**不**通过 URL 字符串或 `image_meta` 白名单替代。

**适用资源（V2.2）**：

| 资源 | 接入点 | 说明 |
|---|---|---|
| 用户头像 | `POST /api/v1/users/me/avatar` | 微信小程序 `wx.uploadFile` → 本接口 |

| 通过 | 允许落盘，返回 `avatar_url` | 200 | 200 |
| 违规 | 拒绝保存文件，不写库 | 422 | 2005 |
| 审核服务不可用 | 默认拒绝（与文本安全一致） | 422 | 2004 |

**实现状态**：接口与 Client **仅占位**，`IMAGE_MODERATION_PROVIDER=placeholder` 时不调用微信/云厂商；对接真实 API 为 P0 后续项（见 §10.1）。

### 1.6 双库分治与规则维护边界

本模块在 **两个独立 PostgreSQL 库** 各部署一套 `content_safety_rules` / `content_safety_logs` 表与规则引擎代码副本：

| 维度 | live_core_service | user_service |
|---|---|---|
| 数据库 | `live_core_test` | `users_service_test` |
| 校验场景 | message / room_* / search_query | nickname / bio（文本规则，scene 均为 `nickname`） |
| 图片审核 | — | 头像 `POST /me/avatar` → §1.4.6（占位） |
| 管理端 HTTP API | ✅ 挂载 `/api/v1/admin/content-safety/*` | ❌ V2.2 未挂载 |
| 规则维护 | 管理端 GET/POST/PATCH | seed 初始化（nickname 4 条）；改词需改 seed 或 P1 同步方案 |
| 审计日志查询 | 管理端 logs API（仅本库） | 本库 logs，无对外 API |

**运维要点**：
- 在 live_core 管理端修改规则 **只影响 live_core 库**，不会同步到 users 库 nickname 规则
- users 库 nickname 敏感词变更：V2.2 通过更新 `users/app/content_safety/seed.py` 后重建/迁移；P1 可考虑 users 侧管理端或配置中心同步
- **头像图片审核**配置（`IMAGE_MODERATION_*`）在 users 服务环境变量维护，与 content_safety_rules 无关
- 两库 DDL 结构一致；users 库额外增加外键（§1.3）

文档中 **Endpoint** 默认为微服务 **内部路径**（FastAPI 注册路径）。经 nginx 对外暴露时需加网关前缀：

## 4. 执行流程详细说明

### 4.1 统一校验服务完整流程

```
1. 业务 Service 组装 ContentSafetyItem 列表
   → 2. 调用 check_content_safety(scene, items, resource_type, ...)
   → 3. 按 scene 从缓存/DB 加载 enabled 规则
   → 4. 逐字段执行规则引擎匹配（normalize → match → 决策）
   → 4b. 《13》§1.4：并行调用政治敏感文本 API（与本地引擎取并集；API 故障 → 2004）
   → 5. 仅 warn / block 时写入 content_safety_logs（纯 allow 不写日志）
   → 6. 若 overall_decision = block：抛出 ContentSafetyBlockedException(code=2005)
   → 7. 若规则加载/政治 API 异常：抛出 ContentSafetyServiceException(code=2004)
   → 8. allow/warn：返回 ContentSafetyCheckResult，业务继续写库
```

### 4.2 各业务场景接入流程

#### 4.2.1 用户昵称与头像（user_service）

**昵称（文本规则引擎）** — `PATCH /api/v1/users/me`：

```
PATCH /api/v1/users/me
  Body: { "nickname"?: "...", "bio"?: "..." }   ※ 不含 avatar_url
  → JWT 鉴权
  → 若 Body 含 avatar_url → 400/4001（请使用 POST /me/avatar）
  → nickname 有变更：check_content_safety(scene="nickname", field="nickname")
  → bio 有变更：check_content_safety(scene="nickname", field="bio")
  → block → 422/2005；文本安全异常 → 422/2004
  → allow/warn：更新 users 表（nickname / bio 等可写字段）
```

**头像（图片内容审核，§1.4.6）** — `POST /api/v1/users/me/avatar`：

```
POST /api/v1/users/me/avatar
  multipart 字段 file（JPG/PNG/WEBP）
  → JWT 鉴权
  → 读取文件字节
  → ImageModerationClient.moderate(scene="avatar")   ※ V2.2 占位，未接微信/云厂商
  → 违规 → 422/2005，不落盘
  → 审核不可用 → 422/2004
  → 通过 → 保存 uploads/avatars/{user_id}_{uuid}.{ext}
  → 更新 users.avatar_url，返回 { "avatar_url": "/uploads/avatars/xxx.jpg" }
```

- 客户端（微信小程序）须 `wx.uploadFile` 走 `POST /me/avatar`；**禁止**通过 PATCH 写入头像
- **`PATCH /me` 请求体不得包含 `avatar_url`**（`UserUpdateSelf` 无此字段）；若客户端传入 → `400/4001`，提示使用 `POST /me/avatar`
- `GET /me` 响应仍返回 `avatar_url`（只读展示）；DB 字段保留，**仅**由 `POST /me/avatar` 更新

## 5. 错误处理与事务管理

### 5.1 错误处理策略

**内容安全业务异常**:
- 命中 block（code=2005）→ HTTP 422
- 安全服务异常（code=2004）→ HTTP 422，写入型默认拒绝

**管理端业务异常**:
- 规则不存在（code=2001）→ HTTP 404
- 权限不足（code=3002）→ HTTP 403

**系统异常**:
- 数据库连接失败 → HTTP 500（code=1002）

**参数校验异常**:
- Pydantic 校验失败 → HTTP 422（code=4001）

### 5.2 事务管理规范

**业务写入场景**:
- 审计日志 flush 与业务写库在同一事务边界或同一编排单元内完成
- 写入成功但无对应审计日志，视为不完整实现

**规则变更**:
- 规则 UPDATE / INSERT 后立即 `invalidate_all_rules_cache()`
- 多实例部署：短 TTL（60s）+ 写时 invalidate

## 6. 性能优化建议

### 6.1 数据库优化

- **索引优化**: `(scene, enabled, priority)` 覆盖规则加载主路径
- **查询优化**: 日志分页按 `(scene, created_at DESC)` 索引
- **连接池**: 使用 SQLAlchemy `async_session` 连接池

### 6.2 缓存策略

- **规则缓存**: 按 scene 缓存启用规则，TTL 60 秒
- **缓存键**: `rules:{scene}`
- **缓存失效**: 管理端改规则后立即 invalidate；多实例依赖 TTL 兜底

### 6.3 应用层优化

- **批量字段校验**: 同 scene 多字段使用 `check_scene_fields()` 一次调用
- **异步处理**: 所有数据库操作使用 `async/await`

## 8. 错误码对照表

| 错误码 | 说明 | 使用场景 |
|--------|------|----------|
| `200` | 成功 | 所有成功响应 |
| `1002` | 数据库错误 | 数据库操作异常 |
| `2001` | 资源不存在 | 规则 ID 不存在 |
| `2004` | 内容安全服务异常 | 规则加载/引擎故障，**写入型接口**默认拒绝（全项目其他模块的通用 2004 语义不变，内容安全场景专指此项） |
| `2005` | 内容违规 | 命中 block 规则 |
| `2006` | 内容低风险提醒 | 命中 warn 规则（写入审计日志 `reason_code`，HTTP 仍返回 200） |
| `3001` | 未授权 | JWT Token 缺失或无效 |
| `3002` | 权限不足 | 非管理员访问管理端接口 |
| `4001` | 参数校验失败 | 请求参数不符合 Schema 规范 |
